Amazon Kinesis: Introdução Teórica & Deep Dive

Motor de streaming de dados em tempo real altamente escalável, baseado em Shards e controle de concorrência

O Amazon Kinesis Data Streams é um serviço de streaming de dados totalmente gerenciado e altamente durável, projetado para capturar continuamente gigabytes de dados por segundo de centenas de milhares de fontes (logs de servidores, transações financeiras, cliques em sites, telemetria de IoT). Ele permite que você construa aplicações de processamento de streaming em tempo real (Spark Streaming, Flink ou Lambda) para obter insights imediatos.

Escalabilidade
Particionamento por Shards
A unidade base de escala do Kinesis. Cada Shard fornece uma capacidade física fixa de escrita (1 MB/s ou 1.000 records/s) e leitura (2 MB/s). O throughput total do stream cresce de forma linear conforme novos shards são adicionados (rescaling via Split/Merge).
Roteamento
Partition Keys
Chave definida pelo produtor para rotear mensagens. O Kinesis aplica um hash MD5 sobre a Partition Key para mapear qual Shard receberá o registro. Chaves de alta cardinalidade garantem a distribuição homogênea dos dados entre os shards.
Durabilidade
Retenção de Mensagens
Ao contrário de filas clássicas (que apagam mensagens lidas), o Kinesis armazena dados em logs ordenados cronologicamente, retendo mensagens por padrão por 24 horas (configurável até 365 dias), permitindo múltiplos consumidores lerem simultaneamente.

Limites de Throughput e Consumo

Cada Shard provê capacidades estritas de trânsito físico que definem os limites de engenharia da sua aplicação:

  • Escrita (Ingress): Até 1 MB/s de taxa de transferência ou 1.000 registros de gravação por segundo.
  • Leitura (Egress): Até 2 MB/s por padrão (compartilhado entre todos os consumidores daquele shard). Esse limite pode ser contornado usando Enhanced Fan-Out (EFO), que aloca conexões HTTP/2 dedicadas de 2 MB/s por consumidor, reduzindo a latência de entrega para menos de 70 milissegundos.
⚠️ Ameaça de Throttling (ProvisionedThroughputExceededException): Se a sua aplicação produtora enviar registros que hash para o mesmo Shard ultrapassando o limite físico, o Kinesis rejeita os dados. É obrigatório que o produtor controle a volumetria e aplique tratamento de erro por meio de Exponential Backoff com Jitter.

Implementação de Produtor Python Resiliente com Boto3

O script a seguir implementa envio em lote com o método put_records e gerencia erros parciais nas mensagens enviadas (onde algumas foram aceitas e outras sofreram throttling):

import boto3
import time
import random
import json
from botocore.exceptions import ClientError

class ResilientKinesisProducer:
    def __init__(self, stream_name, region_name="us-east-1"):
        self.client = boto3.client('kinesis', region_name=region_name)
        self.stream_name = stream_name

    def send_batch_with_retry(self, records, max_retries=5):
        """Envia registros usando put_records com tratamento detalhado de falhas parciais."""
        formatted_records = [
            {
                'Data': json.dumps(r['data']).encode('utf-8'),
                'PartitionKey': r['partition_key']
            } for r in records
        ]
        
        attempt = 0
        base_delay = 0.1
        records_to_send = formatted_records
        
        while records_to_send and attempt < max_retries:
            try:
                response = self.client.put_records(
                    Records=records_to_send,
                    StreamName=self.stream_name
                )
                
                failed_count = response.get('FailedRecordCount', 0)
                if failed_count == 0:
                    return True
                
                # Filtra apenas os registros que falharam por throttling para reenvio
                failed_indices = []
                for i, res_rec in enumerate(response['Records']):
                    if 'ErrorCode' in res_rec:
                        failed_indices.append(i)
                
                records_to_send = [records_to_send[idx] for idx in failed_indices]
                
                # Jittered Exponential Backoff
                delay = (base_delay * (2 ** attempt)) + random.uniform(0, 0.1)
                time.sleep(delay)
                attempt += 1
                
            except ClientError as e:
                if e.response['Error']['Code'] == 'ProvisionedThroughputExceededException':
                    time.sleep(base_delay * (2 ** attempt) + random.uniform(0, 0.05))
                    attempt += 1
                else:
                    raise e
                    
        if records_to_send:
            raise RuntimeError(f"Falha ao processar {len(records_to_send)} registros após {max_retries} tentativas.")

Kinesis Data Firehose Dynamic Partitioning

Persistência otimizada no S3 sem UDFs de transformação

O Kinesis Data Firehose é um serviço de entrega *near-real-time* que agrupa dados por tempo (buffer) ou volume e os salva no S3. O maior problema histórico do Firehose era gravar arquivos com o prefixo fixo `YYYY/MM/DD/HH`. Atualmente, com a funcionalidade de Dynamic Partitioning, ele pode inspecionar o JSON da mensagem usando expressões JQ e criar subdiretórios baseando-se em colunas dinâmicas em runtime.

Exemplo de Configuração de Dynamic Partitioning

Imagine que as mensagens contenham os campos {"org_id": "empresa_a", "event_type": "click"}. Configuramos o prefixo de destino no S3 da seguinte forma:

# Expressão de extração JQ (Metadata Extraction)
org = .org_id
tipo = .event_type

# Template do prefixo S3 no Firehose
s3-bucket/trusted/org=!{partitionKeyFromQuery:org}/tipo=!{partitionKeyFromQuery:tipo}/ano=!{timestamp:yyyy}/mes=!{timestamp:MM}/
✓ Redução de Custos com Athena: O particionamento dinâmico baseado em colunas do negócio (como ID da empresa/cliente) no Firehose evita que consultas no Athena analisem dados de outras entidades, reduzindo em até 95% os bytes escaneados no S3.

Amazon MSK: Introdução Teórica & Sizing de Broker

Clusters Apache Kafka gerenciados e diretrizes de dimensionamento de hardware e partições

O Amazon MSK (Managed Streaming for Apache Kafka) é um serviço totalmente gerenciado que facilita a criação e execução de aplicações baseadas no Apache Kafka. O Kafka é um log de commit distribuído que organiza streams de eventos em Tópicos. O MSK elimina a sobrecarga operacional de gerenciar a infraestrutura do Kafka (como provisionamento de instâncias, patches do SO, resiliência de brokers e coordenação via Apache ZooKeeper/KRaft).

Topologia
Brokers & Replicação
Os nós de execução do Kafka. Cada partição de um tópico é replicada entre múltiplos brokers (geralmente Replication Factor = 3). Um broker é eleito como Leader para aquela partição, recebendo escritas/leituras, enquanto os outros agem como seguidores (In-Sync Replicas - ISR).
Concorrência
Partições & Consumidores
A unidade básica de paralelismo no Kafka. Tópicos são subdivididos em partições. Dentro de uma partição, as mensagens são estritamente ordenadas por offset. O paralelismo de leitura é limitado pelo número de partições (ex: 20 partições permitem no máximo 20 consumers simultâneos em um Consumer Group).
Armazenamento
Log Segments & Retention
Diferente de sistemas que dependem exclusivamente de RAM, o Kafka grava eventos em arquivos de log em disco de forma sequencial (altamente performático). A retenção é definida por tempo ou tamanho, limpando segmentos fechados antigos de forma assíncrona.

Diretrizes de Dimensionamento (MSK Broker Sizing Guidelines)

Dimensionar um cluster Kafka no MSK requer equilibrar volume de ingestão, taxa de replicação, retenção de dados no disco e a capacidade de cache em memória da JVM e do SO:

Fórmula e Regras Práticas para Sizing de Cluster
  • Armazenamento em Disco: Calcule o storage total necessário usando a fórmula:
    Storage Total (GB) = [Taxa de Ingestão (MB/s) * 3600s * 24h * Dias de Retenção * Fator de Replicação] * 1.15 (folga de index/compactação)
    Exemplo: Ingestão de 10 MB/s, retenção de 7 dias e replicação de 3:
    [10 MB/s * 86400s * 7 dias * 3] * 1.15 = [18.144.000 MB] * 1.15 ≈ 18,14 TB * 1.15 ≈ 20,86 TB de armazenamento total distribuído entre os brokers.
  • Capacidade de Memória (Page Cache): O Apache Kafka atinge performance extrema de leitura lendo direto do **Page Cache do Sistema Operacional** (evitando I/O de disco). Por padrão, a JVM do Kafka no MSK consome metade da RAM da instância (Heap). A outra metade deve ser suficiente para manter os logs de tópicos quentes ativos em cache.
    Regra prática: Mantenha em memória o equivalente a pelo menos as últimas 2 a 4 horas de tráfego de dados ativos de todo o cluster.
  • Cálculo do Número de Brokers: O mínimo recomendado em produção é **3 Brokers** (distribuídos em 3 Zonas de Disponibilidade distintas) para suportar falhas sem degradação do cluster. Se o armazenamento ou throughput por broker ultrapassar o limite da instância escolhida (ex: kafka.m5.large suporta até 10 TB de storage EBS e 100 MB/s de rede total), aumente a quantidade de brokers ou mude o tipo de instância.

Amazon ECS Fargate: Ingestão Computacional Escalável

Orquestração de contêineres Serverless para ingestão pesada de APIs e Webhooks de alto tráfego

Como Funciona

O Amazon ECS (Elastic Container Service) com o tipo de lançamento AWS Fargate é uma engine de computação serverless para contêineres. Diferente do AWS Lambda que possui limites rígidos de tempo (15 minutos) e memória efêmera, o ECS Fargate permite que aplicativos em Python, Go ou Node.js (empacotados via Docker) executem continuamente como serviços 24/7 sem a necessidade de provisionar instâncias EC2.

Em Engenharia de Dados, o ECS Fargate é a principal escolha para construir APIs de Ingestão de Borda (Edge APIs). Ele recebe o tráfego da internet (Webhooks, apps de celular) balanceado pelo ALB (Application Load Balancer), executa lógicas de validação sintática complexas (com bibliotecas pesadas incompatíveis com Lambda) e despeja as mensagens em buffers como o Amazon MSK ou Kinesis.

Vantagens e FinOps

  • Sem Timeouts: Executa o download, extração e parseamento de arquivos ZIP/CSV pesados (ex: > 5 GB) recebidos de SFTP ou APIs externas sem sofrer com o timeout de 15 minutos do Lambda.
  • Isolamento Multi-AZ: Provisiona tarefas de forma redundante e resiliente contra quedas de Availability Zones sem que você gerencie o Control Plane do Kubernetes.
  • FinOps (Spot Fargate): O ECS suporta o Fargate Spot Provider, utilizando capacidade ociosa de computação na nuvem da AWS, oferecendo descontos de até 70% sobre tarefas On-Demand normais (ideal para pipelines de conversão assíncrona não emergenciais).
💡 Desacoplamento Arquitetural: Nunca permita que as tarefas do ECS Fargate escrevam diretamente no Redshift ou em bancos relacionais durante a ingestão. Use o Fargate para capturar, validar o payload no Glue Schema Registry e escrever em buffers altamente escaláveis (Kinesis/MSK). Delegue o roteamento downstream para outros processos.

AWS DMS: Introdução Teórica & CDC Flow

Mecanismos de replicação lógica, captura contínua de alterações (CDC) e mapeamento físico de schemas

O AWS Database Migration Service (DMS) é um serviço gerenciado que permite migrar e replicar dados de bancos de dados relacionais, NoSQL e data warehouses para a nuvem AWS de forma segura. A funcionalidade mais crítica do DMS para Engenharia de Dados é o **CDC (Change Data Capture)**, que lê continuamente os arquivos de log de transação nativos do banco de origem (como o WAL no PostgreSQL ou Binlog no MySQL) e propaga essas alterações em tempo real para alvos como o Amazon S3, MSK ou Redshift.

Arquitetura
Replication Instance
O servidor EC2 gerenciado temporário ou permanente que executa as tarefas do DMS. Ele faz o trabalho pesado de ler os dados de origem, mantê-los em buffers de memória, converter formatos e gravá-los no destino final.
Conectividade
Source & Target Endpoints
Configurações de conexão que definem as fontes de dados e destinos. Endpoints de origem exigem parâmetros específicos no banco de dados para habilitar replicação lógica (ex: rds.logical_replication=1 no Aurora).
Processo
Full Load + CDC
O DMS inicia opcionalmente com o **Full Load** (cópia inicial em batch de todas as tabelas selecionadas) e automaticamente transiciona para o **CDC** (captura contínua e incremental) a partir do offset/LSN salvo.

Tradeoffs de Performance: Modos de Manuseio de LOB (Large Objects)

Um dos maiores gargalos em migrações via DMS é o manuseio de colunas que contêm tipos de dados grandes (como BLOB, CLOB, JSON, TEXT). O DMS possui três estratégias de replicação de LOBs:

  • 1. Full LOB Mode: O DMS migra todos os dados de LOB independentemente do tamanho.
    Como funciona: O DMS lê os dados da tabela em lotes, mas exclui as colunas LOB do lote inicial. Em seguida, para cada linha no lote, ele executa uma consulta individual (GET) na tabela de origem para buscar os dados do LOB.
    Impacto: A performance despenca de forma drástica devido ao excesso de viagens de rede (network round-trips) e queries unitárias na origem.
  • 2. Limited LOB Mode: O engenheiro de dados especifica um tamanho máximo em KB (ex: 32 KB) para o processamento de LOBs.
    Como funciona: O DMS lê as colunas LOB inline diretamente no lote inicial junto com os outros dados normais.
    Impacto: Velocidade extremamente alta. Porém, se um registro contiver um dado LOB maior que o tamanho definido, o DMS **truncará** o dado silenciosamente, gerando perda ou corrupção de dados.
  • 3. Inline LOB Mode: Uma abordagem híbrida que combina o melhor dos dois mundos.
    Como funciona: O engenheiro define um limite pequeno (ex: 8 KB) para LOBs inline. O DMS busca LOBs menores que esse limite na primeira query em lote. Se o LOB for maior, o DMS executa o fluxo do Full LOB apenas para esses registros específicos excedentes.
    Recomendação: É a melhor prática de design para manter alta vazão sem risco de truncamento de dados.

Configuração JSON de LOB no Task Settings

Abaixo está o bloco de configuração JSON das **Task Settings** do DMS configurado para rodar com o modo **Inline LOB** (recomendado):

// Trecho de Task Settings JSON
{
  "TargetMetadata": {
    "SupportLobs": true,
    "FullLobMode": false,
    "LimitedSizeLobMode": false,
    "InlineLobMaxSize": 8, // LOBs até 8KB são carregados inline
    "LoadMaxFileSize": 0,
    "ParallelLoadThreads": 8
  }
}

Tuning Fino das Configurações de Tarefa (Task Settings)

Para otimizar o throughput do DMS CDC e Full Load, os seguintes parâmetros JSON devem ser ajustados no arquivo de configurações da Task:

  • CommitRate: Controla o número máximo de registros que podem ser aplicados em uma única transação no target. O valor padrão é 10000. Para targets analíticos (como S3 Parquet ou Aurora PostgreSQL), aumentar o CommitRate otimiza a gravação física ao criar arquivos/lotes de commits maiores.
  • MaxFullLoadSubTasks: Define o número máximo de tabelas carregadas simultaneamente durante a fase de Full Load. O valor padrão é 8. Em instâncias de replicação grandes (ex: c5.2xlarge ou maior), aumentar para 15 a 20 reduz significativamente o tempo de carga histórica inicial.
  • ParallelLoadThreads: Permite paralelizar a carga de tabelas gigantescas de forma segmentada, dividindo-as por chaves numéricas primárias ou índices. Isso evita que uma única tabela monopolize uma única thread.
  • StreamBufferSettings: Configura o tamanho da memória alocada na instância de replicação para armazenar alterações do CDC em buffer antes de enviá-las ao destino. Evita lag de replicação quando a vazão da origem é muito rápida e o destino está lento.

Tratamento de Schema Evolution (DDL Drift)

Modificações de tabelas na origem (como comandos ALTER TABLE ADD COLUMN ou DROP COLUMN) podem causar a falha catastrófica da tarefa do DMS se não configuradas corretamente:

  • No arquivo JSON de Task Settings, configure o parâmetro TargetTablePrepMode e o objeto SchemaBehavior.
  • A melhor prática para manter a estabilidade do pipeline downstream (como no S3 Data Lake) é configurar o comportamento de DDL para **Ignorar (Do Nothing)** ou **Propagar (Cascade)** no target, garantindo que o Glue Data Catalog consiga mapear as novas colunas sem parar a tarefa.

DynamoDB Ingestion

Exportações consistentes PITR e streams em tempo real

A ingestão do DynamoDB para o Data Lake S3 deve ser separada entre histórico frio e incremental quente:

  • PITR Export to S3 (Histórico): Exporta dados em formato AWS Ion ou JSON nativo. Não consome recursos de computação ou RCU operacionais da tabela, eliminando o risco de queda do sistema de produção.
  • DynamoDB Streams (Real-Time): Dispara eventos contínuos a cada modificação na tabela, que podem ser capturados por funções AWS Lambda e persistidos de forma consolidada no S3.

Arquitetura de Leitura e Escrita

O DynamoDB oferece duas modalidades principais para gerenciamento de capacidade:

  • Provisioned (Provisionado): Requer que o engenheiro especifique o número de unidades de capacidade de leitura (RCU) e escrita (WCU). Ideal para tráfego previsível, podendo ser acoplado com Auto Scaling. Se a aplicação ultrapassar a capacidade provisionada num determinado segundo, a AWS recusa a requisição (Throttling).
  • On-Demand (Sob Demanda): Cobra pelo volume exato de requisições processadas. Escala instantaneamente e automaticamente até o limite da conta para lidar com picos massivos de tráfego, sem necessidade de configurar WCU/RCU, o que é ideal para e-commerce em períodos promocionais ou picos de carga inesperados, prevenindo quedas abruptas de serviço por Throttling de Escrita.

Estratégias de Chaves e Índices (Boas Práticas)

Diferente de bancos SQL que permitem buscas eficientes por qualquer coluna, no DynamoDB a performance é estritamente vinculada ao design das chaves de acesso:

  • Partition Key (PK): Determina o nó físico (hash) onde o dado será armazenado. A boa prática é usar IDs de alta cardinalidade (como `user_id`, `session_id` ou UUIDs) para evitar Hot Partitions, garantindo balanceamento de I/O por todo o cluster.
  • Sort Key (SK) - Opcional: Define a ordenação lógica dos itens de mesma PK. Ideal para queries de séries temporais ou relacionamentos hierárquicos, onde se busca o dado mais recente usando a PK combinada à busca com `BETWEEN`, `BEGINS_WITH` ou `>=` na SK (ex: `status_timestamp`).
  • Global Secondary Index (GSI): Cria uma projeção paralela assíncrona da tabela com chaves de partição e classificação diferentes. Permite realizar consultas alternativas de leitura (ex: buscar um usuário pelo email quando a PK principal da tabela base for seu `id_numerico`), mas há um custo de escrita adicional à medida que as atualizações são propagadas em background da tabela principal.
  • Local Secondary Index (LSI): Compartilha a mesma PK que a tabela principal, mas possui SK diferente. LSI tem a restrição de que precisa ser definido no momento da criação da tabela e as coleções de itens da PK têm limite de 10 GB. Preferir GSI sobre LSI nas arquiteturas modernas.
Infraestrutura como Código (Terraform) - DynamoDB Table

Exemplo de criação de uma tabela DynamoDB em Terraform. Boas práticas aplicadas em IaC: modo PAY_PER_REQUEST para flexibilidade na escrita/leitura sem se preocupar com gargalos imediatos (Throttling), proteção contra deleção acidental, encriptação no lado do servidor (SSE) usando KMS Customer Managed Keys para segurança adicional, e PITR habilitado para recuperação de backup contínuo.

  hash_key     = "user_id"
  range_key    = "session_timestamp"

  # Habilitando Deleção de Proteção para Tabelas Produtivas
  deletion_protection_enabled = true

  attribute {
    name = "user_id"
    type = "S"
  }

  attribute {
    name = "session_timestamp"
    type = "N"
  }

  attribute {
    name = "dispositivo"
    type = "S"
  }

  # Boas Práticas: Recuperação de Desastres Contínua
  point_in_time_recovery {
    enabled = true
  }

  # Global Secondary Index para buscas alternativas
  global_secondary_index {
    name               = "gsi_dispositivo_idx"

    range_key          = "session_timestamp"
    projection_type    = "INCLUDE"
    non_key_attributes = ["user_id"] # Projeta apenas colunas essenciais
  }

  # Boas Práticas: Segurança e Criptografia At-Rest
  server_side_encryption {
    enabled     = true
    kms_key_arn = aws_kms_key.dynamo_cmk.arn
  }

  tags = {
    Environment = "production"
    Team        = "data-engineering"
  }
}

Arquitetura de Leitura e Escrita Otimizada

A ingestão a partir de bancos relacionais para o Data Lake requer cuidado absoluto para não impactar o tráfego operacional da aplicação (OLTP):

  • Arquitetura de Leitura (Offloading): Consultas pesadas de ingestão em batch (via Spark/JDBC) nunca devem apontar para a instância primária (Writer). Em vez disso, provisione Read Replicas exclusivas para o processo analítico. Com o Amazon Aurora Serverless v2, a instância de réplica pode escalar recursos de CPU/RAM (ACUs) em segundos antes de a tarefa do Glue iniciar e contrair a zero (ou ao mínimo) ao terminar.
  • Arquitetura de Escrita: O Amazon Aurora possui uma arquitetura com storage desacoplado, replicado em 6 nós em 3 Zonas de Disponibilidade (Multi-AZ). A ingestão lógica que altera tabelas (inserts/updates) grava logs nativos diretamente na camada de armazenamento otimizada da AWS, reduzindo I/O na máquina de computação e aumentando a performance.

Estratégias de Índices e Chaves de Otimização

O desempenho da transferência relacional de dados sofre impactos profundos da modelagem do banco de dados na AWS:

  • Chaves Primárias Sequenciais: Chaves usando UUIDs distribuídos aleatoriamente espalham páginas (pages) B-Tree pelo disco, gerando alto índice de fragmentação. Prefira IDs autoincrementais padrão (BIGINT) ou padrões temporais para inserções otimizadas (append-only) que gravam no fim das páginas.
  • Índices B-Tree para Ingestões Incrementais: Pipelines de ingestão modernos (Incrementais) muitas vezes buscam dados novos usando um campo updated_at (ex: WHERE updated_at > ultima_extracao). Crie um índice específico nesta coluna. Caso não exista um índice suportando a coluna do filtro, o motor fará um Full Table Scan na réplica do RDS e derrubará a performance analítica.

Batch vs Streaming vs Lambda vs Kappa

Comparativo aprofundado dos padrões de design e latência

Padrão Latência Típica Complexidade e Custos Prós e Contras
Batch (Lotes) D+1 / Diário Baixa. Custos computacionais previsíveis. Prós: Fácil de testar, sem estado ativo. Contras: Latência alta de negócio.
Micro-batch 10s – 5min Média. Custos contínuos. Prós: Bom tradeoff latência vs custo S3. Contras: Risco de "small files problem".
Real-Time Streaming < 1s Alta. Custos permanentes e monitoramento complexo. Prós: Latência próxima de zero. Contras: Exige tratamento complexo de janelas de tempo.
Lambda Architecture Híbrida Muito Alta. Mantém código duplicado. Prós: Dados rápidos instantâneos e consistência batch. Contras: Difícil manutenção do código.
Kappa Architecture Variável Média-Alta. Depende do histórico no log. Prós: Um único pipeline para manter. Contras: Exige retenção longa nos tópicos Kafka/MSK.

Erros Comuns de Ingestão & Troubleshooting

Gargalos produtivos em operações de streaming e replicação

Kinesis · Throttling
ProvisionedThroughputExceededException
Causa: Chave de partição estática (ex: string vazia ou constante) concentrando dados no mesmo shard.

Fix: Adicione hashes aleatórios (salts) ou UUIDs nas chaves de partição para distribuir uniformemente o tráfego nos shards.
DMS · CDC
Replication Task em estado FAILED no restart
Causa: Log de transação (WAL/Binlog) foi rotacionado e deletado na origem antes do DMS realizar a leitura.

Fix: Aumente o tempo de retenção física de logs na origem (ex: 24 horas no RDS Postgres) para evitar perda de tracking do DMS.
Firehose · S3
Throttling de escrita de arquivos pequenos no S3
Causa: Configuração de buffer do Firehose muito curta (ex: 60s) forçando uploads contínuos que esgotam o limite de requests PUT no bucket.

Fix: Eleve o buffer do Firehose para 15 minutos (900s) ou 128 MB de volume mínimo de arquivo.
