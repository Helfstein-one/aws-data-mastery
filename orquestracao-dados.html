Orquestração de Pipelines de Dados

Orquestração Avançada: MWAA, Step Functions & Glue Workflows

Design de pipelines de dados resilientes, DAGs complexas, máquinas de estado serverless e tratamento corporativo de falhas em lote.

01

Os Três Pilares de Orquestração da AWS

Diferenças arquiteturais entre MWAA (Airflow), Step Functions e Glue Workflows

A orquestração de dados garante a execução lógica, ordenada e segura de tarefas de engenharia de dados (extração, carga, validação de qualidade e transformação). A tabela abaixo fornece o comparativo de tradeoffs essenciais para escolha de arquitetura:

Critério Amazon MWAA (Airflow) AWS Step Functions AWS Glue Workflows
Modelo Mental Baseado em tempo/agendamento (Time-driven) e DAGs complexas. Baseado em eventos (Event-driven) e transições de Estado. Orquestrador nativo e simples para recursos Glue.
Custo base Fixo por ambiente ativo (~$350/mês mínimo para MWAA). Por transição de estado (Serverless total - $0 se ocioso). Gratuito (cobra apenas o consumo das DPUs do Glue rodando).
Escalabilidade Escala horizontal de workers Fargate (demora minutos). Escala instantaneamente até milhares de execuções concorrentes. Limitada ao escopo do Glue Catalog e recursos nativos.
Limitações Overhead operacional de pacotes Python e latência de scheduler. Payload máximo de entrada/saída limitado a 256 KB. Incapaz de orquestrar recursos de fora do ecossistema Glue/S3.
Pontos de Atenção (Gotchas de Custo Silencioso):
• MWAA NAT Gateway Costs: O MWAA exige subredes privadas com NAT Gateway para baixar pacotes do PyPI e comunicar com o control plane da AWS. Se a sua DAG exporta gigabytes de dados pela internet pública através de conexões não otimizadas, a taxa de tráfego de dados do NAT Gateway pode superar o custo de processamento do Airflow. Habilite obrigatoriamente **VPC Endpoints** (S3, Glue, Athena, KMS) na VPC do MWAA.
• State Machine Loop Limits: Rodar loops infinitos ou processamento de milhares de itens um a um no Step Functions Standard pode inflar drasticamente o custo por transição de estado. Use o modo **Express State Machines** para fluxos rápidos orientados a eventos, e o modo **Standard** exclusivamente para fluxos de longa duração com dependência de aprovações humanas.
02

AWS Step Functions: State Machines para Pipelines

ASL (Amazon States Language), tratamento de erro ativo com Retry/Catch e IaC Terraform

O AWS Step Functions orquestra workflows serverless distribuídos. Sua grande vantagem reside no suporte nativo ao padrão **SDK Integration**, permitindo chamar serviços (como Glue, ECS, Athena) de forma direta e assíncrona usando o sufixo .sync, fazendo a State Machine aguardar a conclusão do Job de forma transparente e resiliente.

Código JSON ASL (Amazon States Language)

Definição declarativa da State Machine com tratamento de erros integrado. Ela tenta reexecutar o Glue Job até 3 vezes caso ocorra falha de rede antes de enviar a execução para o estado de erro:

  "States": {

Amazon MWAA: Apache Airflow em Escala Corporativa

Design de arquitetura distribuída, gerenciamento de estado das tarefas e orquestração de DAGs complexas

O Amazon MWAA (Managed Workflows for Apache Airflow) elimina a dor de cabeça de configurar clusters do Kubernetes, bancos Postgres externos (Metastore) e servidores web para rodar o Airflow. A AWS gerencia o autoscaling horizontal dos workers baseando-se no número de tarefas na fila (usando Celery Executor e Fargate Tasks).

Código Prático: DAG Python para Ingestão e Processamento (Athena & Glue)

O script abaixo demonstra uma DAG Airflow completa utilizando operadores modernos que disparam tarefas e aguardam ativamente sua conclusão, incluindo regras de ramificação e callbacks de falha:

from datetime import datetime, timedelta
from airflow import DAG
from airflow.providers.amazon.aws.operators.glue import GlueJobOperator
from airflow.providers.amazon.aws.operators.athena import AthenaOperator
from airflow.operators.empty import EmptyOperator

default_args = {
    'owner': 'data-platform-team',
    'depends_on_past': False,
    'start_date': datetime(2026, 1, 1),
    'retries': 2,
    'retry_delay': timedelta(minutes=5),
}

# Definição do escopo da DAG
with DAG(
    dag_id='mwaa_etl_orchestration_flow',
    default_args=default_args,
    description='DAG corporativa para rodar carga Glue e atualizacao Athena',
    schedule_interval='0 6 * * *', # Todos os dias às 6h da manhã
    catchup=False,
    max_active_runs=1, # Evita concorrência e race condition em escritas S3
) as dag:

    start = EmptyOperator(task_id='start_pipeline')

    # Task 1: Dispara o Job PySpark no AWS Glue e aguarda (wait_for_completion=True)
    run_glue_pyspark = GlueJobOperator(
        task_id='run_glue_pyspark_job',
        job_name='prod-processamento-vendas-job',
        script_args={
            '--env': 'production',
            '--exec_date': '{{ ds }}'
        },
        aws_conn_id='aws_default',
        wait_for_completion=True,
    )

    # Task 2: Executa query de otimização analítica no Athena (Compaction/Vacuum)
    run_athena_optimize = AthenaOperator(
        task_id='optimize_iceberg_table',
        query="OPTIMIZE iceberg_db.tb_vendas REWRITE DATA ('bin-pack')",
        database='iceberg_db',
        output_location='s3://prod-athena-query-results-bucket-xyz/output/',
        aws_conn_id='aws_default',
    )

    end = EmptyOperator(task_id='end_pipeline')

    # Cadeia de dependências lógicas
    start >> run_glue_pyspark >> run_athena_optimize >> end

Cases Reais, Diagnósticos & Perguntas de Entrevista

Resolução de problemas de concorrência, recuperação de falhas em lote e simulação avançada de entrevistas

Case 1 · Integração Cross-Account
Disparos de Pipelines Baseados em Eventos Multi-Conta
Desafio: O time de ingestão na Conta A carrega arquivos no S3. O pipeline de transformação reside na Conta B (Step Functions + EMR). Como iniciar o processamento na Conta B instantaneamente após a gravação na Conta A sem polling constante?
Solução: Configuração de uma regra de **Amazon EventBridge** na Conta A que intercepta eventos do S3 (via CloudTrail/S3 Event Notifications) e despacha o JSON do evento diretamente para um Barramento de Eventos (Event Bus) customizado na Conta B. Na Conta B, uma regra do EventBridge escuta o barramento e dispara o Step Functions com o payload do arquivo recebido, garantindo orquestração 100% orientada a eventos em milissegundos de latência.
Case 2 · Reprocessamento em Massa
Recuperação de Falhas de Partição em Lote (Backfill)
Desafio: Uma regra incorreta corrompeu as partições analíticas da camada Silver dos últimos 30 dias. O reprocessamento sequencial manual demoraria 24 horas e correria risco de race conditions (múltiplas execuções gravando ao mesmo tempo no mesmo diretório S3).
Solução: Utilização da Step Functions configurando o estado **Map State em modo Distribuído (Distributed Map)**. A State Machine lê a lista dos 30 diretórios corrompidos a partir de um JSON no S3 e lança sub-execuções paralelas isoladas com limite de concorrência fixado em 5 runs simultâneos (para não estourar o limite de CPU do cluster EMR). O backfill é executado de forma segura e paralela, reduzindo o tempo de recuperação de 24 horas para 1.5 horas.

Perguntas de Entrevista Técnica Avançadas

Pergunta 1: Como mitigar gargalos de latência de agendamento (Scheduling Overhead) ao rodar milhares de micro-tarefas rápidas no Airflow?

Resposta Esperada: O Apache Airflow não foi projetado para tarefas com latência de milissegundos devido à frequência de varredura do Scheduler (loop de parse das DAGs). Rodar milhares de micro-tarefas rápidas satura a CPU do banco de dados metastore e gera latência acumulada insustentável. A melhor prática de design é delegar as micro-tarefas rápidas e sequenciais para uma **State Machine no AWS Step Functions (Express Mode)** e usar o Airflow apenas para disparar e monitorar a State Machine como um único bloco lógico. Isso reduz a carga no scheduler do Airflow e diminui os custos de infraestrutura.

Pergunta 2: O que acontece com a execução de uma State Machine do Step Functions se o payload de dados lidos exceder o limite físico de 256 KB?

Resposta Esperada: A execução falhará imediatamente com um erro do tipo States.DataLimitExceeded. Para contornar essa limitação física de payload em pipelines que processam grandes listas de dados, a arquitetura deve utilizar o padrão **Claim Check**: a tarefa grava o payload volumoso temporariamente em um arquivo JSON no Amazon S3 e passa apenas a URI do S3 (o ponteiro) como string no payload da State Machine. As tarefas downstream leem a URI, buscam o arquivo do S3, realizam o processamento e salvam as saídas atualizadas no S3, preservando a State Machine limpa e abaixo do limite de 256KB.

Guia CLI: Diagnóstico e Operação via Linha de Comando

aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:pipeline-data-orchestrator \
  --input '{"execution_date": "2026-06-07"}'

# 2. Descrever o status de uma execução específica do Step Functions
aws stepfunctions describe-execution \
  --execution-arn arn:aws:states:us-east-1:123456789012:execution:pipeline-data-orchestrator:99b66a-12a

# 3. Listar execuções falhas de um workflow para diagnóstico
aws stepfunctions list-executions \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:pipeline-data-orchestrator \
  --status-filter FAILED

# 4. Trigger manual de uma DAG no Airflow (MWAA) via CLI do AWS SSM (Executar comando no container do Airflow)
aws mwaa create-cli-token --name prod-airflow-environment \
  | jq -r .CliToken \
  | xargs -I {} curl -s -X POST https://prod-airflow-env.c2.us-east-1.amazonaws.com/aws.local/action \
      -H "Authorization: Bearer {}" \
      -d '{"action": "dags trigger mwaa_etl_orchestration_flow"}'
