Modelagem de Dados

Por que Single-Table Design?

Single-table design em DynamoDB permite escalabilidade, baixa latência e custos reduzidos. Uma única tabela (CreditContractStateStore) armazena contratos, eventos, provisões e auditoria, acessada via PK, SK e GSI para diferentes padrões de query.

Benefício

✅ Performance

Latência < 10ms em queries via PK/SK. Sem joins entre tabelas.

Benefício

✅ Escalabilidade

Cresce para bilhões de items. Sem limite prático.

Benefício

✅ Custo

Pay-per-request. Sem desperdício com tabelas subutilizadas.

Benefício

✅ Auditoria

Event sourcing integrado. Histórico completo imutável.

Esquema Principal

CreditContractStateStore - Estrutura de Items

Cada item representa uma entidade diferente usando o padrão PK/SK hierárquico. Exemplos: contrato, evento, provisão, auditoria. Todos em uma única tabela.

PK (Partition Key) SK (Sort Key) Tipo Descrição
CONTRACT#12345 METADATA#0 Contrato Dados principais do contrato (cliente, limite, taxa)
CONTRACT#12345 STATE#2026-08-16 Estado Estado atual do contrato em data específica
CONTRACT#12345 EVENT#2026-08-15T10:30:00Z Evento Pagamento, atraso, transição de estado (event sourcing)
CONTRACT#12345 PROVISION#2026-08 Provisão Provisão ECL calculada para mês específico
CONTRACT#12345 AUDIT#2026-08-16T14:00:00Z Auditoria Log imutável de todas as mudanças

Access Patterns

Padrões de Query Otimizados

DynamoDB requires upfront planning of access patterns. Single-table design suporta múltiplos padrões via PK/SK primária e GSIs (Global Secondary Indexes).

Padrão Query Índice Latência
Buscar Contrato PK=CONTRACT#123, SK=METADATA#0 Primary <5ms
Histórico de Eventos PK=CONTRACT#123, SK begins_with EVENT# Primary <10ms
Contratos por Cliente GSI1: PK=CUSTOMER#789, SK begins_with CONTRACT# GSI1 <15ms
Contratos por Estado GSI2: PK=STATE#ATIVO, SK between dates GSI2 <20ms
Listar Atrasados GSI2: PK=STATE#ATRASADO, SK oldest first GSI2 <20ms

Arquitetura de Eventos

Event Sourcing integrado ao DynamoDB

Cada mudança em um contrato é registrada como um evento imutável no DynamoDB. O estado atual é sempre derivado da sequência de eventos (event sourcing).

💡 Sequência de Eventos - Jornada Completa
// Item 1: CONTRACT#123 + EVENT#2026-08-16T10:00:00Z { "eventType": "ContractCreated", "data": {"customerId": "c789", "limit": 10000}, "timestamp": "2026-08-16T10:00:00Z" } // Item 2: CONTRACT#123 + EVENT#2026-08-16T10:30:00Z { "eventType": "ContractApproved", "decision": "APPROVED", "timestamp": "2026-08-16T10:30:00Z" } // Item 3: CONTRACT#123 + EVENT#2026-09-05T14:20:00Z { "eventType": "PaymentReceived", "amount": 500, "timestamp": "2026-09-05T14:20:00Z" } // Item 4: CONTRACT#123 + EVENT#2026-10-05T00:00:00Z { "eventType": "PaymentMissed", "daysLate": 1, "timestamp": "2026-10-05T00:00:00Z" } // Estado Atual Derivado: // Todos os eventos acumulados = Estado = { // "state": "ATRASADO", // "daysLate": 1, // "totalPaid": 500, // "balance": 9500, // ... // }
🎯 Benefícios do Event Sourcing:

Auditoria completa (imutável), replay de eventos para debugging, derivar múltiplas projeções (COSIF, provisão, relatórios), conformidade com regulações (BACEN exige rastreabilidade).

🎯 Takeaways Principais

  • Uma Tabela: CreditContractStateStore com 5 tipos de items
  • PK/SK Hierárquicos: Modelo relacional em NoSQL
  • GSIs: Suportam queries por cliente, estado, data
  • Event Sourcing: Cada mudança é um evento imutável
  • Performance: < 5-20ms para todas as queries
  • Auditoria: Histórico completo para conformidade BACEN
