Padrões de Mensageria e Event-Driven (SQS & SNS)

Comunicação assíncrona desacoplada, tratamento de falhas, padrões avançados e infraestrutura como código (Terraform)

A mensageria assíncrona é a espinha dorsal de sistemas distribuídos modernos. Ela substitui chamadas diretas síncronas HTTP (que causam acoplamento forte e falhas em cascata) por filas e tópicos intermediários. Na AWS, os serviços nativos fundamentais para essa arquitetura são o Amazon SQS e o Amazon SNS.

Publish-Subscribe (Pub-Sub) - Amazon SNS

Distribuição 1-para-N (Broadcast)

O produtor publica a mensagem em um Tópico SNS. Múltiplos consumidores (filas SQS, Lambdas, Webhooks, endpoints HTTPS) assinam esse tópico e recebem uma cópia independente de cada mensagem. Ideal para espalhar eventos de negócios comuns (ex: "venda_concluida") para múltiplos domínios analíticos independentes.

Point-to-Point (Queue) - Amazon SQS

Processamento 1-para-1 (Buffer & Escalabilidade)

O produtor envia a mensagem para uma Fila SQS. Apenas um único consumidor processa cada mensagem por vez. Quando o processamento termina com sucesso, o consumidor exclui a mensagem da fila. Se o consumidor falhar, a mensagem retorna à fila após o período de visibilidade. Ideal para amortecer picos de carga (Throttling) e desacoplar escrita em bancos relacionais.

PADRÕES DE MENSAGERIA E EVENT-DRIVEN (FAN-OUT)

Internals e Dimensionamento Crítico do Amazon SQS

  • Standard vs FIFO Queues:
    • Standard: Taxa de transferência virtualmente ilimitada. Oferece entrega *at-least-once* (pelo menos uma vez, podendo haver duplicidade) e ordenação por *best-effort* (sem garantia estrita).
    • FIFO (First-In-First-Out): Limite de até 3.000 mensagens/segundo com batching (ou mais usando high throughput mode). Garante entrega *exactly-once* (exatamente uma vez no nível da fila) e ordenação estrita. Exige a definição de MessageGroupId (para ordenar grupos de mensagens) e MessageDeduplicationId (ou deduplicação baseada em hash do conteúdo).
  • Visibility Timeout (Tempo de Visibilidade): Quando um consumidor lê uma mensagem da fila, ela permanece fisicamente na fila mas fica "invisível" para outros consumidores por este intervalo de tempo.
    Regra de Sizing Fundamental: O Visibility Timeout deve ser configurado para no mínimo 6 vezes o tempo de execução máximo esperado do seu consumidor (ex: se o Lambda demora até 10 segundos para processar um lote, o Visibility Timeout deve ser de pelo menos 60 segundos). Caso contrário, a mensagem voltará a ficar visível antes de o processamento acabar, gerando duplicidade extrema e concorrência na gravação dos mesmos dados.
  • Short Polling vs Long Polling:
    • Short Polling: O SQS consulta apenas um subconjunto de seus servidores físicos de fila e retorna imediatamente, mesmo vazia. Aumenta drasticamente o número de requests cobrados.
    • Long Polling (Padrão Recomendado): O SQS espera até que uma mensagem chegue ou o timeout expire (máximo de 20 segundos) antes de responder. Reduz custos operacionais e requisições vazias a zero.

O Padrão Claim Check (Contornando o Limite de 256 KB)

O limite físico máximo de payload para mensagens do SQS e do SNS é de 256 KB. Quando pipelines de dados precisam trafegar registros volumosos (ex: grandes objetos JSON ou metadados de arquivos analíticos), aplicamos o Claim Check Pattern:

Passo Entidade Produtora Transporte (SQS) Entidade Consumidora
Ação Grava o payload bruto pesado no bucket S3 (camada temporária ou raw). Envia uma mensagem curta para o SQS contendo o Bucket Name e o Object Key (URI). Lê a mensagem curta da fila, usa as coordenadas para baixar o payload direto do S3 e executa o processamento.
Implementação PySpark/Python: Consumidor Claim Check

Abaixo está o script executado em uma task do ECS Fargate ou no Spark para resolver o payload utilizando Claim Check:

import json
import boto3

s3_client = boto3.client('s3')

def process_sqs_message_claim_check(sqs_record):
    # 1. Parse da mensagem curta da fila SQS
    message_body = json.loads(sqs_record['body'])
    
    # 2. Verifica se a mensagem contém as referências do S3 (Claim Check)
    if 's3_bucket' in message_body and 's3_key' in message_body:
        bucket = message_body['s3_bucket']
        key = message_body['s3_key']
        
        # 3. Baixa o payload pesado diretamente do S3
        print(f"Baixando payload pesado de s3://{bucket}/{key}")
        s3_object = s3_client.get_object(Bucket=bucket, Key=key)
        payload_data = json.loads(s3_object['Body'].read().decode('utf-8'))
        
        # 4. Processa os dados pesados
        execute_data_processing(payload_data)
        
        # Opcional: deletar o arquivo temporário do S3 após processamento bem-sucedido
        # s3_client.delete_object(Bucket=bucket, Key=key)
    else:
        # Processamento comum para payloads menores de 256 KB
        execute_data_processing(message_body)

def execute_data_processing(data):
    print(f"Processando registros: {len(data)}")

Filtragem de Mensagens no SNS (Message Filtering)

Em vez de entregar todas as mensagens de um tópico para todas as filas assinantes (o que geraria processamento desnecessário, concorrência e custos com Lambdas ignorando mensagens), configuramos Subscription Filter Policies no SNS:

Atributos da Mensagem Regra de Filtro da Fila A Regra de Filtro da Fila B
{ "domain": "financas", "region": "us-east-1" } Assinatura SQS Filtra por: { "domain": ["financas"] } ➔ Recebe Assinatura SQS Filtra por: { "region": ["us-west-2"] } ➔ Ignorado

Infraestrutura como Código (Terraform)

Abaixo está a implementação IaC completa de um padrão Fan-out resiliente contendo um Tópico SNS associado a uma fila SQS FIFO com Dead Letter Queue (DLQ), encriptação via chaves KMS e política de filtragem de atributos.

# 1. Chave KMS para Encriptação de Mensagens (Repouso)
resource "aws_kms_key" "sns_sqs_key" {
  description             = "Chave KMS para encriptar topicos e filas de dados"
  deletion_window_in_days = 7
  enable_key_rotation     = true
}

# 2. Topico SNS FIFO de Origem
resource "aws_sns_topic" "data_events_topic" {
  name                        = "vendas-events.fifo"
  fifo_topic                  = true
  content_based_deduplication = true
  kms_master_key_id           = aws_kms_key.sns_sqs_key.arn
}

# 3. Fila SQS FIFO Secundária (Dead Letter Queue)
resource "aws_sqs_queue" "analytics_dlq" {
  name                        = "analytics-processing-dlq.fifo"
  fifo_queue                  = true
  kms_master_key_id           = aws_kms_key.sns_sqs_key.arn
  message_retention_seconds   = 1209600 # Retém por 14 dias para auditoria
}

# 4. Fila SQS FIFO Principal (Consumer de Ingestão)
resource "aws_sqs_queue" "analytics_queue" {
  name                        = "analytics-processing-queue.fifo"
  fifo_queue                  = true
  kms_master_key_id           = aws_kms_key.sns_sqs_key.arn
  visibility_timeout_seconds  = 180 # 3 minutos (compatível com Lambda/Glue rápidos)
  message_retention_seconds   = 345600 # 4 dias

  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.analytics_dlq.arn
    maxReceiveCount     = 3 # Move para DLQ após 3 falhas de processamento
  })
}

# 5. Permissão para o SNS Enviar Mensagens para o SQS
resource "aws_sqs_queue_policy" "analytics_queue_policy" {
  queue_url = aws_sqs_queue.analytics_queue.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid       = "AllowSNSSend"
        Effect    = "Allow"
        Principal = "*"
        Action    = "sqs:SendMessage"
        Resource  = aws_sqs_queue.analytics_queue.arn
        Condition = {
          ArnEquals = {
            "aws:SourceArn" = aws_sns_topic.data_events_topic.arn
          }
        }
      }
    ]
  })
}

# 6. Assinatura do Tópico SNS direcionando para a Fila SQS com Message Filtering
resource "aws_sns_topic_subscription" "sns_to_sqs_subscription" {
  topic_arn = aws_sns_topic.data_events_topic.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.analytics_queue.arn

  # Apenas envia para esta fila se o evento for do domínio 'faturamento' ou 'vendas_online'
  filter_policy = jsonencode({
    domain = ["faturamento", "vendas_online"]
    source = [{"anything-but" : "legacy_system"}]
  })
}
Resiliência de Batching em Consumidores Lambda / ECS:
Para evitar reprocessar todas as mensagens corretas de um lote (batch) quando apenas uma mensagem falha, ative a opção ReportBatchItemFailures no gatilho do SQS. No retorno da sua função, envie um JSON contendo o array batchItemFailures com os IDs das mensagens específicas que deram erro. O SQS as manterá na fila principal para nova tentativa e removerá as mensagens bem-sucedidas imediatamente.

Amazon EventBridge e Arquiteturas Event-Driven

Disparos automatizados baseados em eventos lógicos, roteamento cross-account e agendamentos serverless globais

Pipelines analíticos eficientes não rodam em agendamentos fixos (cron jobs) se os dados originais chegam de forma contínua ou flutuante. A arquitetura Event-Driven (orientada a eventos) responde instantaneamente a mudanças físicas de infraestrutura ou de negócios usando o Amazon EventBridge.

Conceitos Chave do Amazon EventBridge

  • Barramentos de Eventos (Event Buses):
    • Default Event Bus: Recebe automaticamente todos os eventos gerados pelos próprios serviços da AWS (ex: modificações no S3, alteração de estados do EC2/ECS/Glue).
    • Custom Event Buses: Criados para receber eventos das suas próprias aplicações customizadas (ex: microsserviço no ECS publica "event_type": "pedido_pago"). Suporta barramentos centralizados e compartilhamento cross-account para centralizar auditoria de dados.
  • Regras de Roteamento (Rules) e Filtros de Padrão (Event Patterns): As regras aplicam padrões de correspondência (JSON matching) para interceptar apenas eventos específicos antes de enviá-los para um ou mais alvos (targets). 
    // Exemplo de Event Pattern para interceptar apenas arquivos Parquet criados na camada Raw do S3
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": {
      "name": ["empresa-data-lake-raw"]
    },
    "object": {
      "key": [{ "suffix": ".parquet" }]
    }
  }
}
  • EventBridge Scheduler vs EventBridge Rules (Cron):
    • Rules (Cron clássica): Baseada no barramento de eventos padrão, ideal para tarefas clássicas de infraestrutura em intervalos curtos.
    • Scheduler: Um serviço altamente otimizado para agendamentos individuais de alta densidade (milhões de schedules independentes). Suporta janelas flexíveis de execução, fuso horário nativo (Timezone), controle de retentativas automáticas com Dead Letter Queue (DLQ) associada ao target, e entrega do tipo *at-least-once*.

Input Transformers: Higienização de Payloads

Muitas vezes, o evento gerado pela AWS é gigante e contém dezenas de propriedades de metadados inúteis. Usando o Input Transformer, você filtra e mapeia apenas as chaves necessárias antes de disparar o Target final (evitando que o Glue ou ECS gaste CPU decodificando metadados redundantes da AWS):

// 1. Input Paths Map (extrai propriedades do evento S3)
{
  "s3_bucket": "$.detail.bucket.name",
  "s3_file_key": "$.detail.object.key"
}

// 2. Input Template (formato limpo entregue ao Target, ex: Glue Job)
{
  "raw_bucket_path": "s3:///",
  "ingested_at": ""
}

    input_paths = {
      bucket_name = "$.detail.bucket.name"
      file_key    = "$.detail.object.key"

    input_template = </"
}
EOF
  }

Orquestração e Workflows de Dados (Step Functions)

Orquestração serverless, DAGs programáticas, tratamento de erros, Map States e integrações Glue/EMR/ECS

Um pipeline complexo possui dependências rígidas: a camada Silver só pode rodar se a Bronze finalizar com sucesso, e a Gold depende de múltiplas tabelas da Silver. Para isso, usamos orquestradores de fluxo (Workflows). O AWS Step Functions destaca-se como o orquestrador serverless nativo por excelência na nuvem.

AWS Step Functions

Serverless State Machine

Melhor opção para fluxos integrando serviços AWS (Lambda, Glue, ECS, EMR, Athena, SQS, SNS). Cobra por transição de estado. Latência extremamente baixa, suporte visual completo e zero servidores para gerenciar.

AWS Glue Workflows

Orquestrador Interno Simplificado

Indicado apenas quando o ecossistema é 100% baseado em Crawlers e Glue Jobs. Muito limitado em termos de controle de fluxo lógico complexo, ifs/choices e integrações com computação customizada externa.

Amazon MWAA (Managed Airflow)

Programmatic Python DAGs

O padrão ouro do mercado para pipelines complexos e heterogêneos. Ideal para times de engenharia que preferem escrever dependências como código Python e integrar com bancos on-premises.

Step Functions: Standard vs Express Workflows

Característica Standard Workflows Express Workflows
Tempo de Execução Máximo Até 1 ano. Até 5 minutos.
Preço Cobrado por transição de estados (passos). Cobrado por volume de requisições e duração da computação (GB-segundo).
Taxa de Invocação Até 2.000 execuções por segundo. Mais de 100.000 execuções por segundo.
Garantia de Execução Exactly-Once. Histórico detalhado de passos no console visual para debugging. At-Least-Once. Logs enviados apenas para o CloudWatch. Sem console de visualização histórica passo a passo.
Ideal para... Orquestração de pipelines de dados batch de longa duração (ex: rodar EMR/Glue). Ingestão serverless de alta frequência, transformações de mensagens rápidas IoT, APIs REST.

Integração e Orquestração do Ecossistema de Dados

O Step Functions atua como maestro dos serviços computacionais de dados na AWS, usando Service Integrations (pontos `.sync`):

  • AWS Glue integration: Dispara o Glue Job e suspende o fluxo (arn:aws:states:::glue:startJobRun.sync) até que o Job termine, retornando o status final (SUCCEEDED/FAILED) para a máquina de estados tomar a decisão.
  • Amazon EMR (Ephemeral Clusters): Step Functions consegue instanciar um cluster EMR sob demanda (passo CreateCluster), enviar passos do Spark (passo AddJobFlowSteps), aguardar a conclusão (.sync), e terminar as instâncias de forma limpa (passo TerminateJobFlow), garantindo FinOps absoluto.
  • Amazon ECS Fargate Tasks: Dispara uma tarefa de contêiner customizada no Fargate (ex: scraping complexo ou inferência de IA) passando variáveis de ambiente dinâmicas capturadas de eventos anteriores.

Código ASL (Amazon States Language)

Abaixo está o código ASL JSON que define uma máquina de estados robusta. Ela roda um Glue Job, possui política de Retry com Backoff Exponencial para contornar limites de DPUs ocupadas, faz o Catch (Captura) de falhas e publica um alerta formatado em um tópico do Amazon SNS em caso de erro definitivo:

{
  "Comment": "Pipeline orquestrador de ETL com Retry e Notificacao de Erro",
  "StartAt": "ExecutaGlueETL",
  "States": {
    "ExecutaGlueETL": {
      "Type": "Task",
      "Resource": "arn:aws:states:::glue:startJobRun.sync",
      "Parameters": {
        "JobName": "spark-silver-processing-job",
        "Arguments": {
          "--camada": "silver",
          "--data_execucao.$": "$.input_s3_uri"
        }
      },
