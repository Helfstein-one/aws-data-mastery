Os 7 Pilares de uma Arquitetura de Dados Moderna

Diretrizes fundamentais para estruturação de projetos analíticos robustos e resilientes

Pilar 1

Decoupled Storage & Compute

Separação física completa entre a computação (EMR, Athena, Glue) e o armazenamento (Amazon S3). Permite desligar ou escalar máquinas de processamento sem riscos aos dados persistidos.

Pilar 2

Idempotência & Replayability

Todos os jobs devem ser projetados para rodar múltiplas vezes para o mesmo período sem gerar dados duplicados. O reprocessamento deve ser uma operação nativa e segura.

Pilar 3

Governança Fina (Least Privilege)

Acesso lógico centralizado por schemas, tabelas, colunas e linhas (AWS Lake Formation) ao invés de políticas brutas e desorganizadas em buckets S3.

Pilar 4

Observabilidade Ativa

Coleta em tempo real de throughput, latências, taxas de erro e consumo de hardware (YARN/JVM). Alertas automatizados antes que falhas impactem os consumidores.

Pilar 5

Custo-eficiência Nativo

Combinação estratégica de instâncias EC2 Spot transientes para processamento secundário, compressões Parquet ZSTD e S3 Intelligent-Tiering.

Pilar 6

Qualidade Declarativa

Garantia de integridade do dado na transição entre camadas Bronze, Silver e Gold por meio de ferramentas automáticas de validação de schemas (Glue Data Quality, Great Expectations).

Pilar 7

Infraestrutura como Código (IaC)

Toda a infraestrutura, permissões IAM, bancos e tabelas externas catalogadas criadas via scripts declarativos (Terraform/CDK), eliminando intervenções manuais.

09

Modern Data Lakehouse (S3 + Apache Iceberg)

Fusão da flexibilidade do Data Lake com as transações robustas do Data Warehouse

O layout Modern Data Lakehouse centraliza todo o storage no Amazon S3 em formatos colunares transacionais (Apache Iceberg) gerenciados pelo AWS Glue Data Catalog. Motores de processamento (EMR, Glue) e queries analíticas (Athena, Redshift Spectrum) operam diretamente sobre o mesmo dado, eliminando o overhead de movimentar dados fisicamente para silos proprietários.

  • Contexto: A arquitetura Modern Data Lakehouse na AWS representa o padrão estado da arte, eliminando silos e desacoplando Storage de Compute através do Apache Iceberg.

Vantagens do Apache Iceberg

  • Transações ACID completas: Garante escritas limpas simultâneas (leitores nunca leem dados parciais ou inconsistentes).
  • Schema Evolution seguro: Permite renomear, mover ou adicionar colunas sem corromper partições históricas.
  • Hidden Partitioning: O Iceberg assume a responsabilidade de extrair datas ou campos das partições na escrita e leitura física, eliminando a necessidade de passar caminhos explícitos de partição no SQL.
Infraestrutura como Código (Terraform) para criar o Lakehouse e Glue Data Catalog

Abaixo está a definição declarativa Terraform para criar o bucket S3 e registrar a tabela Apache Iceberg no AWS Glue Catalog.

# 1. Configurar o bucket S3 para armazenamento do Data Lakehouse
resource "aws_s3_bucket" "lakehouse_warehouse" {
  bucket = "company-datalake-iceberg-warehouse"
}

resource "aws_s3_bucket_server_side_encryption_configuration" "s3_encryption" {
  bucket = aws_s3_bucket.lakehouse_warehouse.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

# 2. Criar Database no Glue Data Catalog
resource "aws_glue_catalog_database" "analytics_db" {
  name = "analytics_db"
}

# 3. Registrar a Tabela no Glue Catalog como tipo Iceberg
resource "aws_glue_catalog_table" "iceberg_table" {
  name          = "historical_sales"
  database_name = aws_glue_catalog_database.analytics_db.name
  table_type    = "EXTERNAL_TABLE"
  
  parameters = {
    "table_type"      = "ICEBERG"
    "metadata_location" = "s3://${aws_s3_bucket.lakehouse_warehouse.bucket}/historical_sales/metadata/v1.metadata.json"
  }

  storage_descriptor {
    location      = "s3://${aws_s3_bucket.lakehouse_warehouse.bucket}/historical_sales/"
    input_format  = "org.apache.iceberg.mr.hive.HiveIcebergInputFormat"
    output_format = "org.apache.iceberg.mr.hive.HiveIcebergOutputFormat"

    ser_de_info {
      serialization_library = "org.apache.iceberg.mr.hive.HiveIcebergSerDe"
    }
  }
}

Arquitetura Lambda

Combinação balanceada de processamento Batch e Speed Layers para consistência e baixa latência

A Arquitetura Lambda resolve o tradeoff entre velocidade e consistência dividindo os dados recebidos em dois caminhos paralelos:

  • Batch Layer (Lote - Fria): Salva o dado bruto imutável (camada Bronze do S3) e executa transformações complexas de alta exatidão em períodos programados (ex: a cada hora ou dia) usando AWS Glue ou EMR.
  • Speed Layer (Tempo Real - Quente): Processa os eventos instantaneamente com latência de milissegundos usando AWS Kinesis ou Flink para gerar métricas rápidas (ex: contadores dos últimos 5 minutos).
  • Serving Layer (Consumo): Combina as queries das duas camadas (histórico consolidado + dados rápidos recentes) para entregar o resultado unificado para dashboards ou APIs.

Arquitetura Kappa

Pipeline único baseado puramente em streaming e logs imutáveis de eventos

A Arquitetura Kappa remove a complexidade de manter duas bases de código separadas (Batch e Speed). Ela assume que tudo é um fluxo contínuo de dados (streaming):

  • Os dados de entrada são armazenados em um log imutável ordenado por tempo (ex: tópicos com retenção longa no Amazon MSK / Apache Kafka).
  • Há um único motor de processamento (ex: Spark Structured Streaming ou Flink) lendo as mensagens e gravando na Serving Layer.
  • Reprocessamento histórico: Se uma regra de negócio mudar ou um bug for detectado, reinicia-se o ponteiro (offset) do consumidor Kafka para a posição zero (início dos tempos) e processa-se novamente as mensagens históricas pelo mesmo pipeline único.

Código PySpark Structured Streaming (Padrão Kappa) escrevendo em Iceberg

Abaixo está um script em PySpark Structured Streaming. Ele consome dados em tempo real do Amazon MSK (Kafka), decodifica o payload JSON, aplica uma janela de agregação de 5 minutos com tolerância de atraso (Watermark) de 10 minutos e escreve em uma tabela Apache Iceberg no S3.

from pyspark.sql import SparkSession
from pyspark.sql.functions import col, from_json, expr, window
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Inicializa sessão do Spark configurada para o Apache Iceberg
spark = SparkSession.builder \
    .appName("KappaKafkaToIceberg") \
    .config("spark.sql.extensions", "org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions") \
    .config("spark.sql.catalog.glue", "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.glue.catalog-impl", "org.apache.iceberg.spark.SparkGlueCatalog") \
    .config("spark.sql.catalog.glue.warehouse", "s3://my-datalake-warehouse-bucket/metadata/") \
    .getOrCreate()

schema = StructType([
    StructField("transaction_id", StringType(), True),
    StructField("user_id", StringType(), True),
    StructField("amount", DoubleType(), True),
    StructField("timestamp", TimestampType(), True)
])

# Consumindo do Amazon MSK (Kafka)
df_kafka = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092") \
    .option("subscribe", "transactions-topic") \
    .option("startingOffsets", "latest") \
    .load()

# Decodificando dados
df_decoded = df_kafka.selectExpr("CAST(value AS STRING)") \
    .select(from_json(col("value"), schema).alias("data")) \
    .select("data.*")

# Agregação por Janela Temporal (Event-time) de 5 minutos com Watermarking
df_aggregated = df_decoded \
    .withWatermark("timestamp", "10 minutes") \
    .groupBy(
        window(col("timestamp"), "5 minutes"),
        col("user_id")
    ) \
    .agg(expr("sum(amount) as total_gasto")) \
    .select(
        col("window.start").alias("janela_inicio"),
        col("window.end").alias("janela_fim"),
        col("user_id"),
        col("total_gasto")
    )

# Gravando na tabela de Serving (Apache Iceberg) de forma contínua
query = df_aggregated.writeStream \
    .format("iceberg") \
    .outputMode("append") \
    .option("path", "glue.db.aggregated_transactions") \
    .option("checkpointLocation", "s3://my-datalake-warehouse-bucket/checkpoints/agg_transactions/") \
    .start()

query.awaitTermination()

Data Mesh: Governança Descentralizada

Organização socio-técnica baseada em domínios de negócio e dados como produto compartilhados de forma distribuída

Diferente de arquiteturas monolíticas centrais, o Data Mesh descentraliza a custódia das informações baseando-se em quatro pilares fundamentais:

  1. Domain-Oriented Ownership: A responsabilidade de ingerir e limpar o dado é da equipe do domínio gerador (ex: o time de Vendas gerencia o pipeline de vendas; o time de Logística cuida de entregas).
  2. Data as a Product: Os dados limpos de cada domínio são expostos como produtos documentados e acessíveis a outros domínios de negócio.
  3. Self-Serve Data Platform: Uma plataforma única central gerenciada (infra/governança/S3) que provê ferramentas automatizadas para que as equipes criem seus pipelines sem precisar acionar um time central de TI.
  4. Federated Computational Governance: Definição de padrões de conformidade globais (ex: criptografia obrigatória KMS, tags padrão) auditados de forma automatizada por APIs.

Mecânica de Compartilhamento Cross-Account na AWS

Em topologias corporativas reais de Data Mesh, cada domínio reside em uma conta AWS distinta, enquanto uma conta de governança central gerencia as permissões globais usando o AWS Lake Formation e o AWS RAM:

AWS Lake Formation — Controle de Acesso Fine-Grained

  • Compartilhamento Federado por Metastore: O proprietário dos dados (Produtor) concede permissão ao catálogo de metadados para a conta central de Governança. A central gerencia quem pode visualizar ou acessar essas tabelas usando políticas corporativas globais.

O Athena aponta para esse Resource Link, que redireciona de forma invisível e transparente a consulta ao catálogo produtor original.
  • Bucket Policies Cruzadas: A conta consumidora precisa de permissão de leitura física no S3. O produtor deve configurar uma Bucket Policy que permita a ação s3:GetObject e s3:ListBucket para a Role/IAM do executor na conta de destino, validada pelo Lake Formation.
Manual Prático do Especialista em Dados - Recursos Cloud de Arquitetura & Sharing:

1. AWS Lake Formation (Cross-Account Granting)
• Como funciona na prática: O Lake Formation atua como um wrapper de segurança sobre o Glue Catalog e o S3. Em vez de gerenciar permissões no S3 e no Glue separa-mente, você concede privilégios SQL (SELECT, DESCRIBE) a contas externas ou usuários locais diretamente no console ou via API.
• Gargalos Físicos e Redirecionamento de Credenciais (Vending System): O principal gargalo do Lake Formation é o limite de requisições à API do STS (Security Token Service), responsável por gerar credenciais temporárias para o Athena ler dados no S3. Em queries de altíssima concorrência executadas por dezenas de usuários em lote, o Athena pode apresentar throttling de STS.
• Como evitar falhas: Faça o registro do bucket S3 no Lake Formation no modo Hybrid Access Mode ou habilite o cache de credenciais do Athena para reduzir chamadas ao STS.

2. AWS RAM (Resource Access Manager)
• Como funciona na prática: RAM permite compartilhar recursos de infraestrutura da AWS (como subnets VPC, tabelas Glue e licenças de software) entre contas da mesma AWS Organization sem precisar de replicação física de recursos.
• Gargalo e Comportamento: O RAM em si não possui gargalo de taxa de dados de tráfego, pois atua puramente no plano de controle de metadados. Apenas gerencia o handshake de convite/aceitação entre contas. As cotas principais são de limites de recursos compartilhados por conta (padrão 5.000 recursos por região).
