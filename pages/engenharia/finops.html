Boas Práticas de Engenharia de Custos

Otimização granular dos principais componentes do pipeline analítico AWS

Amazon S3 Lifecycle
Ciclo de vida inteligente
Transicione dados da camada Bronze (raw) para Glacier Flexible Archive após 60 ou 90 dias. Mantenha apenas o necessário para reprocessamento imediato em Standard Tier para mitigar custos de armazenamento fixo.
AWS Glue Tuning
DPU Optimization & Auto Scaling
Nunca utilize mais DPUs do que a sua volumetria exige. Ative o Auto Scaling no Glue (Spark) para ajustar a quantidade de executores dinamicamente e evitar desperdício de cobranças em períodos de ociosidade.
Amazon EMR Compute
Spot Instances & Graviton
Use instâncias Graviton (m6g, r6g) que entregam até 40% melhor performance por dólar gasto. Aloque nós do tipo Core em instâncias On-Demand para resiliência e nós Task em instâncias Spot com até 70% de desconto.
Athena Optimization
Partitioning & Parquet Conversion
O Athena cobra $5 por TB escaneado. Converta seus dados estruturados para Parquet (colunar compactado) e filtre queries usando partições explicitamente. Isso reduz o custo de scan em até 90%.

Monitoramento e Trade-offs com AWS Cost Explorer

Visibilidade de faturamento, alarmes financeiros e compilado de decisões arquiteturais na AWS.

Compilado de Trade-offs: Preços e Componentes

Decisões de engenharia devem equilibrar performance e custo. Abaixo, um resumo comparativo de componentes críticos de um pipeline de dados.

Componente Modelo de Precificação Trade-off Principal (Quando Usar) Risco FinOps
S3 vs DynamoDB S3: $0.023/GB + Puts/Gets
Dynamo: WCU/RCU ou On-Demand		 S3 para armazenamento de grandes volumes (Data Lake). DynamoDB para acesso transacional rápido. Custo de RCU/WCU escalando infinitamente sem limites.
EMR vs Glue EMR: Instância EC2/hr + EMR Fee
Glue: $0.44 por DPU/Hora		 EMR (Spot) para processamento contínuo. Glue para pipelines Serverless esporádicos. Glue rodando jobs lentos consome DPUs rapidamente ($$).
Athena vs Redshift Athena: $5 por TB escaneado
Redshift: RA3 Nodes ($/hr) + Storage		 Athena para queries ad-hoc. Redshift para Data Warehouse contínuo e Dashboards BI. Athena sem PARTITION faz Full Scan custoso.
Lambda vs ECS/Fargate Lambda: GB-segundo + Requests
ECS: vCPU/hr e GB/hr		 Lambda para orquestração leve. ECS para APIs robustas e containers pesados. Lambda com timeout alto em tarefas IO-bound.

AWS Cost Explorer

O Cost Explorer permite visualizar tendências históricas e projetar custos futuros. Na Engenharia de Dados, deve-se habilitar Cost Allocation Tags (Ex: Project: DataLake) para separar custos por centro de custo (Storage, Compute, Analytics).

AWS Budgets & Alarmes

Para evitar faturas astronômicas, utilize AWS Budgets para criar limites de gastos e configurar alertas via SNS/E-mail quando a previsão exceder 80% do orçamento mensal. Ações automáticas podem ser ligadas ao AWS Chatbot.

Dica de Arquitetura: Ao desenhar pipelines, sempre apresente justificativas financeiras. "Eu escolheria Glue pelo tempo rápido de deployment, mas se a volumetria passar de 5 Terabytes diários, faria sentido migrar para EMR com Instâncias Spot para economizar 70%." Isso demonstra forte maturidade em FinOps.

Como Analisar Custos Analíticos na AWS

Repositório de queries SQL no Athena (CUR) para auditoria financeira detalhada

Para rastrear de onde vem cada centavo gasto, a AWS oferece ferramentas específicas de monitoramento financeiro. A principal fonte de verdade absoluta para auditoria granular é o AWS Cost and Usage Report (CUR), que exporta logs detalhados de faturamento diretamente para um bucket S3 para análise no Athena:

Repositório de Queries de Auditoria FinOps (Athena SQL)

1. Auditoria de Custos de Processamento de Dados no NAT Gateway
Identifique quais NAT Gateways estão gerando taxas de transferência excessivas de dados para fora da VPC privada (geralmente por falta de VPC Endpoints):

SELECT 
    line_item_usage_account_id AS conta_aws,
    line_item_resource_id AS nat_gateway_id,
    -- Converte bytes em Gigabytes processados
    SUM(line_item_usage_amount) AS gb_processados,
    SUM(line_item_unblended_cost) AS custo_total_dolar
FROM 
    billing_cur_database.cur_table
WHERE 
    line_item_product_code = 'AmazonEC2'
    AND line_item_usage_type LIKE '%NatGateway-Bytes%'
    AND usage_start_date >= current_date - interval '30' day
GROUP BY 
    1, 2
ORDER BY 
    custo_total_dolar DESC;

2. Auditoria de Transações das APIs do AWS KMS
Descubra se jobs Spark ou queries Athena estão gerando centenas de milhares de requisições de descriptografia, estourando custos do KMS:

SELECT 
    line_item_usage_account_id AS conta_aws,
    line_item_operation AS operacao_kms, -- ex: Decrypt, GenerateDataKey
    SUM(line_item_usage_amount) AS total_chamadas_api,
    SUM(line_item_unblended_cost) AS custo_total_dolar
FROM 
    billing_cur_database.cur_table
WHERE 
    line_item_product_code = 'awskms'
    AND usage_start_date >= current_date - interval '30' day
GROUP BY 
    1, 2
ORDER BY 
    custo_total_dolar DESC;

3. Auditoria de Queries do Athena (Identificação de Lerdeza e Volume de Scan)
Encontre as queries SQL do Athena mais caras dos últimos 30 dias com base no volume físico de dados escaneados:

SELECT 
    line_item_usage_account_id AS conta_aws,
    line_item_resource_id AS query_execution_id,
    -- Converte bytes escaneados em Gigabytes
    (SUM(line_item_usage_amount) / 1024 / 1024 / 1024) AS gb_escaneados,
    SUM(line_item_unblended_cost) AS custo_query_dolar
FROM 
    billing_cur_database.cur_table
WHERE 
    line_item_product_code = 'AmazonAthena'
    AND line_item_usage_type LIKE '%QueryBytes%'
    AND usage_start_date >= current_date - interval '30' day
GROUP BY 
    1, 2
ORDER BY 
    custo_query_dolar DESC
LIMIT 15;
Manual Prático do Especialista em Dados - Recursos Cloud de FinOps:

1. Amazon Athena (Serverless Query Engine)
• Como funciona na prática: O Athena utiliza um pool compartilhado de workers baseados em Presto. Ele não cobra por CPU ou memória, mas exclusivamente por volume de dados lidos do S3 (US$ 5,00 por Terabyte escaneado, com um mínimo de 10 MB por query).
• Gargalos Financeiros: Se você rodar SELECT * FROM tabela WHERE data = '2026-06-05' em uma tabela não particionada, o Athena fará um scan completo no S3, gerando lentidão física e custos exorbitantes. Mantenha os dados em Parquet colunar e particione por datas de forma consistente para escanear apenas a partição necessária.

2. AWS Cost and Usage Report (CUR)
• Como funciona na prática: É o log definitivo de faturamento bruto da AWS. Ele detalha chaves de recursos exatas em formato tabular.
• Comportamento Físico: O CUR é gerado de forma assíncrona pela AWS várias vezes ao dia e gravado em um bucket S3 de sua propriedade. Para consultá-lo de forma performática, configure o CUR para ser exportado em formato Parquet particionado no S3 e use o Athena.

3. VPC Endpoints (Gateway vs Interface Endpoints)
• Como funciona na prática: Permitem que os recursos na sub-rede privada VPC (como os workers do AWS Glue ou do EMR) acessem serviços da AWS (S3, KMS, Secrets Manager) usando a rede interna da AWS, sem sair para a internet pública.
• Gargalo Financeiro Crítico (NAT Gateway): Sem um Gateway Endpoint do S3 configurado nas rotas da VPC privada, cada Gigabyte de dados lido ou gravado pelo Spark no S3 passará obrigatoriamente pelo NAT Gateway. O NAT Gateway cobra uma taxa de processamento de dados de aproximadamente US$ 0,045 por GB. Em pipelines de big data de escala de terabytes, isso pode gerar faturamentos de milhares de dólares em NAT Gateway sem necessidade.
• Resolução: Implante o Gateway Endpoint do S3. É um recurso 100% gratuito que cria um atalho direto na tabela de rotas da subrede, zerando a taxa de processamento de tráfego de dados para o S3. Para o KMS e Secrets Manager, use os Interface Endpoints (PrivateLink), que cobram uma pequena taxa fixa por hora, mas evitam taxas de transferência do NAT Gateway em alta volumetria.
AWS Budgets e Anomalias de Custo: Configure o AWS Cost Anomaly Detection utilizando Machine Learning nativo para identificar picos de consumo atípicos (ex: um loop infinito no Spark gerando 100 novas instâncias EC2) e notificar imediatamente o time via Slack ou e-mail.

Alocação de Custos FinOps Dinâmica: Rateio de Workgroups

Em lagos de dados compartilhados corporativos (Multi-Tenant Data Lakes), múltiplos times e centros de custo executam queries analíticas concorrentes. A melhor prática para ratear custos de forma dinâmica e justa baseia-se no uso de Amazon Athena Workgroups:

  • Isolamento Lógico: Crie um Workgroup para cada Centro de Custo/Squad (ex: wg-marketing, wg-financeiro).
  • Limites Rígidos de Escaneamento: Defina limites de dados escaneados por query (ex: limite de 10 GB por consulta no Marketing) e limites cumulativos diários/mensais para evitar queries cartesianas acidentais que impactem o orçamento geral.
  • Metodologia de Rateio Financeiro: As tags IaC associadas a cada Workgroup se propagam para o AWS CUR (Cost and Usage Report). Isso viabiliza o cálculo do custo exato por departamento a partir da extração do volume de dados processados por grupo de trabalho.
Query SQL: Rateio de Custos Athena por Workgroup

Para extrair o rateio de custos de faturamento agrupados por Workgroup no faturamento mensal do CUR:

SELECT 
    line_item_usage_account_id AS conta_aws,
    -- Identifica o Workgroup do Athena nas propriedades do recurso
    split_part(line_item_resource_id, '/', 2) AS workgroup_name,
    SUM(line_item_usage_amount) AS gb_escaneados,
    SUM(line_item_unblended_cost) AS custo_total_dolar
FROM 
    billing_cur_database.cur_table
WHERE 
    line_item_product_code = 'AmazonAthena'
    AND line_item_usage_type LIKE '%QueryBytes%'
    AND usage_start_date >= current_date - interval '30' day
GROUP BY 
    1, 2
ORDER BY 
    custo_total_dolar DESC;

Terraform: AWS Budgets & Alarmes Automatizados

A configuração abaixo ilustra como provisionar um orçamento da AWS via Terraform, disparando alertas via SNS quando o custo projetado ultrapassar o limite pré-definido:

# Topico SNS para alertas financeiros
resource "aws_sns_topic" "finops_alerts" {
  name = "finops-budget-alerts"
}

# Orcamento AWS focado no Lakehouse Analytics
resource "aws_budgets_budget" "lakehouse_budget" {
  name              = "monthly-lakehouse-budget"
  budget_type       = "COST"
  limit_amount      = "5000.0"
  limit_unit        = "USD"
  time_unit         = "MONTHLY"

  # Filtra especificamente as tags de ambiente e projeto
  cost_filter {
    name = "TagKeyValue"
    values = [
      "user:Project$Lakehouse",
      "user:Environment$Production"
    ]
  }

  # Alerta quando o custo projetado excede 90%
  notification {
    comparison_operator        = "GREATER_THAN"
    threshold                  = 90
    threshold_type             = "PERCENTAGE"
    notification_type          = "FORECASTED"
    subscriber_sns_topic_arns  = [aws_sns_topic.finops_alerts.arn]
  }

  # Alerta quando o custo real excede 100%
  notification {
    comparison_operator        = "GREATER_THAN"
    threshold                  = 100
    threshold_type             = "PERCENTAGE"
    notification_type          = "ACTUAL"
    subscriber_sns_topic_arns  = [aws_sns_topic.finops_alerts.arn]
  }
}

Estratégia de Tagging com Terraform IaC

Taggeamento consistente de recursos de dados para exploração no Cost Explorer

As tags de alocação de custos (Cost Allocation Tags) devem ser ativadas no painel da AWS Billing Console após o deploy. Sem elas, o AWS Cost Explorer exibirá apenas custos globais, impossibilitando identificar qual squad, projeto ou ambiente gastou mais.

Abaixo, apresentamos o código declarativo Terraform IaC que define tags obrigatórias padrão em todos os recursos do pipeline usando default_tags no provider da AWS:

# 1. Configuração do Provider com tags padrão
provider "aws" {
  region = "us-east-1"

  default_tags {
    tags = {
      Environment = "production"
      CostCenter  = "102040-data-analytics"
      Owner       = "data-engineering-team"
      Project     = "customer-churn-analysis"
      ManagedBy   = "terraform"
    }
  }
}

# 2. Exemplo de recurso: Bucket S3 com tags específicas herdando as tags globais
resource "aws_s3_bucket" "silver_lakehouse" {
  bucket = "company-datalake-silver-production"

  tags = {
    DataClassification = "confidential-pii"
    StorageType        = "lakehouse-iceberg"
  }
}

# 3. Exemplo de EMR Serverless Application com tags herdadas e locais
resource "aws_emrserverless_application" "spark_app" {
  name          = "spark-churn-analytics"
  release_label = "emr-6.10.0"
  type          = "spark"

  initial_capacity {
    initial_capacity_type = "Driver"
    initial_capacity_config {
      worker_count = 1
      worker_configuration {
        cpu    = "4 vCPU"
        memory = "16 GB"
      }
    }
  }

  tags = {
    ExecutionSchedule = "daily-04am"
  }
}
Explorando no Cost Explorer: Após aplicar o código Terraform acima, acesse o AWS Billing → Cost Allocation Tags e selecione as chaves CostCenter, Environment e Project como ativas. Em 24 horas, você poderá filtrar e agrupar gráficos de custos no Cost Explorer por esses valores lógicos.
