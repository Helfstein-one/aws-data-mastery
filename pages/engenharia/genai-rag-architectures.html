01

A Necessidade do RAG (Retrieval-Augmented Generation)

Como transformar um modelo probabilístico em um consultor corporativo confiável.

Um LLM cru é como um acadêmico brilhante trancado em uma sala sem internet: ele sabe tudo até a data do seu último treinamento, mas não sabe nada sobre os dados privados da sua empresa (suas apólices de seguro, as notas de versão do seu software, os registros de chamadas dos seus clientes).

Para resolver isso sem precisar re-treinar o modelo (o que seria caríssimo e lento), utilizamos o RAG. Em vez de perguntar diretamente ao LLM e torcer para ele não alucinar, nós dividimos o processo em três etapas:

  1. Retrieval (Recuperação): O usuário faz uma pergunta. Antes de ir para o LLM, transformamos a pergunta em vetor e buscamos no nosso Data Lake ou Vector DB os parágrafos exatos que respondem à pergunta.
  2. Augmentation (Expansão): Injetamos esses parágrafos dentro do prompt do usuário como "Contexto Adicional".
  3. Generation (Geração): O LLM recebe a pergunta + o contexto real da empresa e é instruído: "Responda a pergunta baseando-se estritamente no contexto abaixo."

02

Pipeline de Ingestão RAG — Chunking, Embedding e Upsert

O código completo de indexação: do documento S3 bruto até o vetor no OpenSearch Serverless.

A qualidade do RAG depende 80% da qualidade da ingestão. Um chunk mal feito garante recuperação irrelevante, mesmo com o melhor modelo. O pipeline abaixo usa chunking semântico (por frases/parágrafos, não por tamanho fixo), embeddings do Amazon Titan e upsert idempotente no OpenSearch Serverless (AOSS).

Chunking
Estratégia Semântica
Divida por parágrafos ou seções lógicas (H2/H3 em docs). Evite corte no meio de frase. Adicione overlap de 10-15% do chunk anterior para manter contexto nas bordas. Tamanho ideal: 300-500 tokens.
Embedding
Amazon Titan Text v2
amazon.titan-embed-text-v2:0 — 1024 dimensões, suporta até 8192 tokens por chunk. Para documentos multilíngues (PT/EN), Titan v2 performa melhor que modelos Open Source equivalentes.
Vector Store
OpenSearch Serverless
AOSS com índice k-NN (HNSW, cosine similarity). Sem gestão de cluster. Escala automático. Suporta campos de metadados filtráveis (source, dept, date) para filtros pré-retrieval.
import boto3, json, hashlib, re
from opensearchpy import OpenSearch, RequestsHttpConnection
from requests_aws4auth import AWS4Auth

s3      = boto3.client('s3')
bedrock = boto3.client('bedrock-runtime', region_name='us-east-1')

# Autenticação AOSS
credentials = boto3.Session().get_credentials()
awsauth = AWS4Auth(credentials.access_key, credentials.secret_key,
                   'us-east-1', 'aoss', session_token=credentials.token)
aoss = OpenSearch(
    hosts=[{'host': 'https://xxxx.us-east-1.aoss.amazonaws.com', 'port': 443}],
    http_auth=awsauth, use_ssl=True, verify_certs=True,
    connection_class=RequestsHttpConnection
)

def chunk_text(text: str, max_tokens: int = 450, overlap_ratio: float = 0.12) -> list[dict]:
    """Chunking semântico por parágrafo com overlap."""
    paragraphs = [p.strip() for p in re.split(r'\n{2,}', text) if p.strip()]
    chunks, current, current_tokens = [], [], 0
    overlap_buffer = []

    for para in paragraphs:
        tokens = len(para.split())
        if current_tokens + tokens > max_tokens and current:
            chunks.append({"text": " ".join(current), "tokens": current_tokens})
            # Mantém overlap: últimos 12% como contexto do próximo chunk
            overlap_size = max(1, int(len(current) * overlap_ratio))
            current = current[-overlap_size:] + [para]
            current_tokens = sum(len(p.split()) for p in current)
        else:
            current.append(para)
            current_tokens += tokens

    if current:
        chunks.append({"text": " ".join(current), "tokens": current_tokens})
    return chunks

def embed_text(text: str) -> list[float]:
    """Gera embedding com Amazon Titan Text Embeddings v2."""
    resp = bedrock.invoke_model(
        modelId='amazon.titan-embed-text-v2:0',
        body=json.dumps({"inputText": text, "dimensions": 1024, "normalize": True}),
        contentType='application/json'
    )
    return json.loads(resp['body'].read())['embedding']

def ingest_document(bucket: str, key: str, metadata: dict = None):
    """Pipeline completo: S3 → chunk → embed → upsert no AOSS."""
    content = s3.get_object(Bucket=bucket, Key=key)['Body'].read().decode('utf-8')
    chunks = chunk_text(content)

    for i, chunk in enumerate(chunks):
        doc_id = hashlib.sha256(f"{key}_{i}".encode()).hexdigest()[:16]
        embedding = embed_text(chunk["text"])

        aoss.index(index='knowledge-base', id=doc_id, body={
            "text":      chunk["text"],
            "embedding": embedding,
            "source":    f"s3://{bucket}/{key}",
            "chunk_idx": i,
            "tokens":    chunk["tokens"],
            **(metadata or {})
        })
    print(f"✅ {len(chunks)} chunks indexados de s3://{bucket}/{key}")

# Uso
ingest_document("my-docs-bucket", "policies/rh-2024.pdf.txt",
                metadata={"dept": "rh", "doc_type": "policy", "year": 2024})

03

Padrões Avançados de Busca (Vector Stores)

Chunking, pgvector, Busca Híbrida e Re-ranking.

Em sistemas produtivos sob alta escala de dados e variação linguística, o RAG simples ("ingestão crua → busca direta") costuma falhar por entregar informações desconexas. Adotamos estratégias avançadas para garantir máxima assertividade:

Padrão 1 · Fragmentação Inteligente

Hierarchical & Semantic Chunking

Hierarchical Chunking: Separa o documento em chunks pais (grandes resumos, ex: 2048 tokens) e chunks filhos (detalhes específicos, ex: 512 tokens). O banco faz a busca nos filhos, mas injeta o contexto dos pais no LLM, fornecendo profundidade estrutural.
Semantic Chunking: Em vez de quebrar textos por contagem de caracteres, analisa a variação semântica entre sentenças e divide o arquivo apenas quando há mudança evidente de tema, preservando o fluxo lógico de raciocínio.

Padrão 2 · Mecanismos de Busca

Busca Híbrida (Dense + Sparse Search)

Combina a força da busca vetorial semântica (Dense Retrieval via OpenSearch k-NN / pgvector, capturando intenções) com a busca léxica tradicional baseada em palavras-chave (Sparse Retrieval via BM25, capturando termos exatos, números de notas fiscais, IDs ou termos específicos da indústria). As duas pontuações são unificadas usando Reciprocal Rank Fusion (RRF) para gerar um ranking unificado.

Padrão 3 · Refinamento de Contexto

Re-ranking Semântico (Cohere Rerank)

A busca inicial no banco vetorial extrai uma ampla janela de documentos candidatos (ex: Top 25). Um modelo menor e ultra-rápido de cross-encoder (como Cohere Rerank) re-avalia e re-ordena as passagens contra a pergunta exata do usuário, reduzindo para o Top 3 final altamente relevante. Isso minimiza tokens inúteis injetados no prompt do LLM e reduz custos.

Padrão 4 · Otimização Financeira

Caching Semântico

Armazena em cache (DynamoDB/ElastiCache) a resposta gerada para perguntas semanticamente idênticas. Antes de disparar a busca vetorial, calcula o embedding da nova query e busca a similaridade de cosseno com o histórico. Se a similaridade for superior a 96%, serve a resposta imediatamente, reduzindo a latência para menos de 50ms.

Implementando Busca Semântica em SQL com pgvector

Você não precisa sempre provisionar um Cluster OpenSearch caro. O pgvector permite armazenar embeddings vetoriais (com 1536 dimensões, como do modelo Titan) diretamente no PostgreSQL (Amazon RDS/Aurora). Consultas usam o índice HNSW (Hierarchical Navigable Small World) para aproximar a busca de vizinhos mais próximos (ANN):

-- 1. Habilitar a extensão no banco RDS
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Criar a tabela com campo de embedding de 1536 dimensões
CREATE TABLE documentos_data_lake (
    id BIGSERIAL PRIMARY KEY,
    caminho_s3 VARCHAR(255) NOT NULL,
    conteudo_chunk TEXT,
    embedding_vetor vector(1536)
);

-- 3. Criar índice HNSW utilizando a distância de Cosseno (Cosine Distance)
CREATE INDEX idx_documents_hnsw_cosine 
ON documentos_data_lake 
USING hnsw (embedding_vetor vector_cosine_ops) 
WITH (m = 16, ef_construction = 64);

-- 4. Query semântica para buscar os 5 trechos mais similares ao vetor de busca do usuário
SELECT caminho_s3, conteudo_chunk, 1 - (embedding_vetor <=> '[0.015, -0.024, ..., 0.098]') AS similaridade
FROM documentos_data_lake
ORDER BY embedding_vetor <=> '[0.015, -0.024, ..., 0.098]'
LIMIT 5;
04

Busca Híbrida, Re-Ranking e Comparativo de Vector Stores

Como combinar busca semântica (vetorial) com busca por palavra-chave (BM25) para máxima precisão na recuperação.

A busca puramente vetorial é ótima para sinônimos e conceitos, mas péssima para nomes próprios, SKUs, siglas e termos exatos. A busca BM25 (TF-IDF moderno) é precisa para termos exatos mas ignora semântica. A Busca Híbrida com RRF (Reciprocal Rank Fusion) combina os dois rankings e supera ambos isoladamente em ~15-25% nos benchmarks MTEB.

def hybrid_search(query: str, index: str = 'knowledge-base',
                  k: int = 8, alpha: float = 0.6) -> list[dict]:
    """
    Busca híbrida: alpha=0.6 pesa 60% semântico + 40% BM25.
    RRF garante que resultados em ambos os rankings sejam favorecidos.
    """
    query_embedding = embed_text(query)

    # Query híbrida do OpenSearch (combina knn + match em uma única requisição)
    body = {
        "size": k,
        "query": {
            "hybrid": {
                "queries": [
                    {"knn": {"embedding": {"vector": query_embedding, "k": k}}},
                    {"match": {"text": {"query": query, "boost": 1 - alpha}}}
                ]
            }
        },
        "search_pipeline": {
            "phase_results_processors": [{
                "normalization-processor": {
                    "normalization": {"technique": "min_max"},
                    "combination": {"technique": "arithmetic_mean",
                                      "parameters": {"weights": [alpha, 1 - alpha]}}
                }
            }]
        }
    }
    hits = aoss.search(index=index, body=body)['hits']['hits']
    return [{"text": h['_source']['text'], "score": h['_score'],
              "source": h['_source']['source']} for h in hits]

def rag_answer(question: str) -> str:
    """Pipeline RAG completo: busca híbrida → LLM gera resposta fundamentada."""
    chunks = hybrid_search(question, k=6)
    context = "\n\n---\n\n".join([f"[Fonte: {c['source']}]\n{c['text']}" for c in chunks])

    prompt = f"""Responda à pergunta usando APENAS as informações dos documentos fornecidos.
Se a informação não estiver nos documentos, responda "Não encontrei nos documentos disponíveis."
Cite a fonte entre colchetes no final de cada afirmação.

<documentos>
{context}
</documentos>

<pergunta>{question}</pergunta>"""

    resp = bedrock.converse(
        modelId='anthropic.claude-3-5-sonnet-20241022-v2:0',
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 1000, "temperature": 0.1}
    )
    return resp['output']['message']['content'][0]['text']
