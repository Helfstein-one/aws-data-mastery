01

A Necessidade do RAG (Retrieval-Augmented Generation)

Como transformar um modelo probabilístico em um consultor corporativo confiável.

Um LLM cru é como um acadêmico brilhante trancado em uma sala sem internet: ele sabe tudo até a data do seu último treinamento, mas não sabe nada sobre os dados privados da sua empresa (suas apólices de seguro, as notas de versão do seu software, os registros de chamadas dos seus clientes).

Para resolver isso sem precisar re-treinar o modelo (o que seria caríssimo e lento), utilizamos o RAG. Em vez de perguntar diretamente ao LLM e torcer para ele não alucinar, nós dividimos o processo em três etapas:

  1. Retrieval (Recuperação): O usuário faz uma pergunta. Antes de ir para o LLM, transformamos a pergunta em vetor e buscamos no nosso Data Lake ou Vector DB os parágrafos exatos que respondem à pergunta.
  2. Augmentation (Expansão): Injetamos esses parágrafos dentro do prompt do usuário como "Contexto Adicional".
  3. Generation (Geração): O LLM recebe a pergunta + o contexto real da empresa e é instruído: "Responda a pergunta baseando-se estritamente no contexto abaixo."

02

Padrões Avançados de Busca (Vector Stores)

Chunking, pgvector, Busca Híbrida e Re-ranking.

Em sistemas produtivos sob alta escala de dados e variação linguística, o RAG simples ("ingestão crua → busca direta") costuma falhar por entregar informações desconexas. Adotamos estratégias avançadas para garantir máxima assertividade:

Padrão 1 · Fragmentação Inteligente

Hierarchical & Semantic Chunking

Hierarchical Chunking: Separa o documento em chunks pais (grandes resumos, ex: 2048 tokens) e chunks filhos (detalhes específicos, ex: 512 tokens). O banco faz a busca nos filhos, mas injeta o contexto dos pais no LLM, fornecendo profundidade estrutural.
Semantic Chunking: Em vez de quebrar textos por contagem de caracteres, analisa a variação semântica entre sentenças e divide o arquivo apenas quando há mudança evidente de tema, preservando o fluxo lógico de raciocínio.

Padrão 2 · Mecanismos de Busca

Busca Híbrida (Dense + Sparse Search)

Combina a força da busca vetorial semântica (Dense Retrieval via OpenSearch k-NN / pgvector, capturando intenções) com a busca léxica tradicional baseada em palavras-chave (Sparse Retrieval via BM25, capturando termos exatos, números de notas fiscais, IDs ou termos específicos da indústria). As duas pontuações são unificadas usando Reciprocal Rank Fusion (RRF) para gerar um ranking unificado.

Padrão 3 · Refinamento de Contexto

Re-ranking Semântico (Cohere Rerank)

A busca inicial no banco vetorial extrai uma ampla janela de documentos candidatos (ex: Top 25). Um modelo menor e ultra-rápido de cross-encoder (como Cohere Rerank) re-avalia e re-ordena as passagens contra a pergunta exata do usuário, reduzindo para o Top 3 final altamente relevante. Isso minimiza tokens inúteis injetados no prompt do LLM e reduz custos.

Padrão 4 · Otimização Financeira

Caching Semântico

Armazena em cache (DynamoDB/ElastiCache) a resposta gerada para perguntas semanticamente idênticas. Antes de disparar a busca vetorial, calcula o embedding da nova query e busca a similaridade de cosseno com o histórico. Se a similaridade for superior a 96%, serve a resposta imediatamente, reduzindo a latência para menos de 50ms.

Implementando Busca Semântica em SQL com pgvector

Você não precisa sempre provisionar um Cluster OpenSearch caro. O pgvector permite armazenar embeddings vetoriais (com 1536 dimensões, como do modelo Titan) diretamente no PostgreSQL (Amazon RDS/Aurora). Consultas usam o índice HNSW (Hierarchical Navigable Small World) para aproximar a busca de vizinhos mais próximos (ANN):

-- 1. Habilitar a extensão no banco RDS
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Criar a tabela com campo de embedding de 1536 dimensões
CREATE TABLE documentos_data_lake (
    id BIGSERIAL PRIMARY KEY,
    caminho_s3 VARCHAR(255) NOT NULL,
    conteudo_chunk TEXT,
    embedding_vetor vector(1536)
);

-- 3. Criar índice HNSW utilizando a distância de Cosseno (Cosine Distance)
CREATE INDEX idx_documents_hnsw_cosine 
ON documentos_data_lake 
USING hnsw (embedding_vetor vector_cosine_ops) 
WITH (m = 16, ef_construction = 64);

-- 4. Query semântica para buscar os 5 trechos mais similares ao vetor de busca do usuário
SELECT caminho_s3, conteudo_chunk, 1 - (embedding_vetor <=> '[0.015, -0.024, ..., 0.098]') AS similaridade
FROM documentos_data_lake
ORDER BY embedding_vetor <=> '[0.015, -0.024, ..., 0.098]'
LIMIT 5;
