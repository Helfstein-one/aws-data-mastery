AWS Lambda: Computação Sob Demanda

Modelos de invocação, MicroVMs (Firecracker) e estratégias para Data Engineering

O AWS Lambda é um serviço de computação Serverless que permite executar código sem provisionar ou gerenciar servidores. Por baixo dos panos, quando uma função Lambda é invocada, a AWS utiliza a tecnologia Firecracker (MicroVMs) para provisionar ambientes de execução isolados em frações de segundo, garantindo segurança multitenant e isolamento de recursos rígido.

Embora amplamente conhecido por arquiteturas web (ex: API Gateway + Lambda), no universo da Engenharia de Dados, o Lambda brilha na orquestração de eventos, ingestão em tempo real e transformações leves de micro-batching.

Modelos de Invocação (Invocation Types)

Request/Response
Síncrona (Sync)
O chamador (ex: API Gateway) aguarda ativamente a resposta. Se houver falha (timeout, erro 500), é responsabilidade do chamador realizar os retries (Backoff Exponencial).
Fire and Forget
Assíncrona (Async)
Usado com S3 (S3 Events) ou SNS. A AWS enfileira o evento internamente. Se a função falhar, o Lambda tenta o retry automaticamente por até 2 vezes.
Polling Fleet
Event Source Mapping
Exclusivo para Streams/Queues (Kafka, Kinesis, SQS, DynamoDB Streams). O serviço do Lambda possui pollers ocultos que leem os registros e invocam a função com lotes.

Padrões de Integração Serverless

API Gateway + Lambda + DynamoDB (Transacional Síncrono)

Este é o padrão ouro para construir microsserviços. O API Gateway atua como um escudo, gerenciando Throttling, Rate Limiting e Autenticação (Cognito), enquanto o Lambda executa a lógica de negócio e se conecta perfeitamente ao DynamoDB sem sofrer de esgotamento de conexões (já que a API do DynamoDB é puramente HTTP/HTTPS e serverless).

Conexão Privada VPC (Hyperplane ENI) para Data Lakes

No passado, conectar um Lambda a recursos privados (como um cluster Redshift ou RDS em uma sub-rede privada) resultava em Cold Starts mortais de mais de 10 segundos, porque a AWS criava uma Interface de Rede elástica (ENI) dedicada para cada microVM em tempo real. Hoje, o Lambda utiliza a arquitetura Hyperplane, que cria ENIs de longa duração e realiza um NAT escalável por trás dos panos, reduzindo o penalty de rede em sub-redes privadas para meros milissegundos.

Event Source Mapping (Kinesis to Lambda) — Fluxo de Ingestão e Retries

Tratamento de Erros em Event Source Mapping

Quando consumindo de filas (SQS) ou fluxos contínuos (Kinesis), as falhas não afetam apenas um evento isolado, mas sim um Batch inteiro. Se o seu Lambda pegar 100 registros do Kinesis e o 50º der erro, o comportamento padrão do Lambda é bloquear o Shard, fazendo retry infinitamente naquele batch inteiro até os registros expirarem (Retention Period).

Para evitar esse "Poison Pill", engenheiros usam o BisectBatchOnFunctionError: ao falhar, o Lambda divide o batch pela metade e tenta processá-los separadamente até isolar o registro com erro e enviá-lo para um destino de falha (SQS DLQ ou S3 Destination), liberando o shard instantaneamente.

Lambda Destinations vs DLQs

Historicamente, usava-se apenas as DLQs (Dead Letter Queues) vinculadas à própria função para capturar invocações falhas. Porém, a prática moderna adota Lambda Destinations.

  • As DLQs capturam apenas o payload original. Não há visibilidade sobre a Stack Trace do erro.
  • Os Destinations (OnSuccess, OnFailure) permitem rotear o resultado para SQS, SNS, EventBridge ou outra Lambda, incluindo no envelope JSON todo o Request Payload, o Response Context e a Exception detalhada, facilitando a observabilidade.

Tuning Avançado & Melhores Práticas

Performance em Serverless é diretamente proporcional aos custos. Entender como a AWS aloca recursos por debaixo dos panos é vital para FinOps e eficiência.

Conceito / Configuração Impacto Arquitetural Prática Recomendada
Lambda Layers & Zip Sizes O tamanho máximo de um pacote Lambda é 50MB (zip) e 250MB (descompactado). O tempo de descompactação afeta drasticamente o Cold Start. Mova pacotes pesados (pandas, scipy, drivers jdbc) para Lambda Layers. A camada é montada no `/opt` da VM de forma eficiente, permitindo deploys muito mais rápidos do código de negócio.
Custom Runtimes & Rust/Go Linguagens dinâmicas (Python/Node) exigem subida de interpretador. Java tem a JVM. Tudo impacta FinOps em bilhões de execuções. Para extrema performance, reescreva lógicas críticas em Rust ou Go, e use a imagem provided.al2023 (Amazon Linux 2023). O Cold Start cai para menos de 30ms, reduzindo absurdamente a conta final.
Alocação de Memória vs CPU A CPU do Lambda não é configurável isoladamente. Ela escala de forma estritamente proporcional à memória alocada (1 vCPU íntegra é atingida com ~1.7GB de RAM). Use ferramentas open-source como AWS Lambda Power Tuning (Step Functions) para achar o balanço matemático ótimo entre velocidade e custo para workloads pesados em dados (pandas/numpy).
Conexões com Bancos Relacionais Milhares de concorrências (funções instanciadas rapidamente) esgotam os pools de conexão tradicionais (PostgreSQL/MySQL), causando Connection Timeouts e derrubando o banco. Inicie as conexões de banco de dados fora do escopo do handler para aproveitar o reuso em instâncias quentes (Warm Starts) e adote o Amazon RDS Proxy.
Provisioned Concurrency Mantém instâncias prontas e "quentes" o tempo todo, pagando-se um valor fixo por hora. O Init Phase (bota, carrega bibliotecas) nunca acontece no caminho crítico da requisição. Ideal para APIs sensíveis a latência consumidas por UIs. Para ETL em batch/background ou processamento em fila, o Cold Start normal de alguns segundos é perfeitamente tolerável, economizando verba.
Graviton2 (ARM64) Altera a arquitetura do processador da MicroVM subjacente de x86 para processadores AWS Graviton baseados em ARM. Sempre ligue por padrão em Lambdas Python, Node e Java modernos. Oferece até 34% de melhora em custo-performance (mais rápido e preço por ms menor). Verifique dependências C++ ou binários pré-compilados.
/tmp Space Storage (Efêmero) Oferece de 512MB até 10GB de armazenamento local no disco da VM. Perfeito para baixar e manipular arquivos temporários antes de enviar ao S3 ou EFS acoplado, mas atenção: o estado sobrevive a Warm Starts, então limpe o `/tmp` no final da função se manipular dados sensíveis!
