AWS Lambda: Computação Sob Demanda

Modelos de invocação, MicroVMs (Firecracker) e estratégias para Data Engineering

O AWS Lambda é um serviço de computação Serverless que permite executar código sem provisionar ou gerenciar servidores. Por baixo dos panos, quando uma função Lambda é invocada, a AWS utiliza a tecnologia Firecracker (MicroVMs) para provisionar ambientes de execução isolados em frações de segundo, garantindo segurança multitenant e isolamento de recursos rígido.

Embora amplamente conhecido por arquiteturas web (ex: API Gateway + Lambda), no universo da Engenharia de Dados, o Lambda brilha na orquestração de eventos, ingestão em tempo real e transformações leves de micro-batching.

Modelos de Invocação (Invocation Types)

Request/Response
Síncrona (Sync)
O chamador (ex: API Gateway) aguarda ativamente a resposta. Se houver falha (timeout, erro 500), é responsabilidade do chamador realizar os retries (Backoff Exponencial).
Fire and Forget
Assíncrona (Async)
Usado com S3 (S3 Events) ou SNS. A AWS enfileira o evento internamente. Se a função falhar, o Lambda tenta o retry automaticamente por até 2 vezes.
Polling Fleet
Event Source Mapping
Exclusivo para Streams/Queues (Kafka, Kinesis, SQS, DynamoDB Streams). O serviço do Lambda possui pollers ocultos que leem os registros e invocam a função com lotes.

Padrões de Integração Serverless

API Gateway + Lambda + DynamoDB (Transacional Síncrono)

Este é o padrão ouro para construir microsserviços. O API Gateway atua como um escudo, gerenciando Throttling, Rate Limiting e Autenticação (Cognito), enquanto o Lambda executa a lógica de negócio e se conecta perfeitamente ao DynamoDB sem sofrer de esgotamento de conexões (já que a API do DynamoDB é puramente HTTP/HTTPS e serverless).

Conexão Privada VPC (Hyperplane ENI) para Data Lakes

No passado, conectar um Lambda a recursos privados (como um cluster Redshift ou RDS em uma sub-rede privada) resultava em Cold Starts mortais de mais de 10 segundos, porque a AWS criava uma Interface de Rede elástica (ENI) dedicada para cada microVM em tempo real. Hoje, o Lambda utiliza a arquitetura Hyperplane, que cria ENIs de longa duração e realiza um NAT escalável por trás dos panos, reduzindo o penalty de rede em sub-redes privadas para meros milissegundos.

S3 Event Notifications (Gatilho Assíncrono)

O padrão mais comum em Data Lakes: um arquivo aterriza no S3 (PutObject) e dispara a Lambda via notificação assíncrona. Como é um evento Async, se a Lambda falhar (ex: schema inválido), a própria infraestrutura da AWS enfileira e tenta reprocessar até 2 vezes (com backoff), antes de enviar para um Destination de falha, garantindo tolerância a falhas de rede de forma totalmente transparente.

Fanout Pattern (Microsserviços Desacoplados)

O padrão Fanout é o "Santo Graal" de arquiteturas reativas escaláveis. O Publisher (ex: sistema de vendas) posta no SNS uma única vez. O SNS espalha ("fans out") essa mensagem para múltiplas filas SQS (Billing, Inventory). Cada Lambda consome sua fila de forma autônoma (via ESM Polling). Se o time de Inventory introduzir um bug fatal na Lambda deles, a fila deles trava, mas o sistema de Billing continua intacto.

Orquestração Stateful (AWS Step Functions)

A Lambda é Stateless e tem duração máxima de 15 minutos. Quando você precisa orquestrar fluxos lógicos complexos (ex: pipeline ETL longo, aprovações manuais, rollbacks e retries agressivos), envolva suas Lambdas transacionais com o AWS Step Functions, que injeta o conceito de estado (State Machine) visualmente.

Event Source Mapping (Kinesis to Lambda) — Fluxo de Ingestão e Retries

Tratamento de Erros em Event Source Mapping

Quando consumindo de filas (SQS) ou fluxos contínuos (Kinesis), as falhas não afetam apenas um evento isolado, mas sim um Batch inteiro. Se o seu Lambda pegar 100 registros do Kinesis e o 50º der erro, o comportamento padrão do Lambda é bloquear o Shard, fazendo retry infinitamente naquele batch inteiro até os registros expirarem (Retention Period).

Para evitar esse "Poison Pill", engenheiros usam o BisectBatchOnFunctionError: ao falhar, o Lambda divide o batch pela metade e tenta processá-los separadamente até isolar o registro com erro e enviá-lo para um destino de falha (SQS DLQ ou S3 Destination), liberando o shard instantaneamente.

Lambda Destinations vs DLQs

Historicamente, usava-se apenas as DLQs (Dead Letter Queues) vinculadas à própria função para capturar invocações falhas. Porém, a prática moderna adota Lambda Destinations.

  • As DLQs capturam apenas o payload original. Não há visibilidade sobre a Stack Trace do erro.
  • Os Destinations (OnSuccess, OnFailure) permitem rotear o resultado para SQS, SNS, EventBridge ou outra Lambda, incluindo no envelope JSON todo o Request Payload, o Response Context e a Exception detalhada, facilitando a observabilidade.
Microservices Architecture (Serverless E-Commerce)

Esta é a arquitetura definitiva de Microsserviços 100% Serverless. O API Gateway expõe as rotas (/users, /orders) e faz o roteamento para Lambdas independentes (cada um sendo um microsserviço com seu próprio banco de dados isolado no DynamoDB). Para comunicação entre eles sem criar acoplamento síncrono rígido (Choreography), o serviço de Orders publica um evento no SNS ou EventBridge, e um serviço de Notificação independente consome esse evento assincronamente para enviar um e-mail de confirmação, garantindo resiliência extrema.

Ciclo de Vida da Execução (Execution Lifecycle)

Uma MicroVM no Lambda não surge magicamente rodando o seu código. O Cold Start é composto de 3 grandes sub-fases de inicialização (Init Phase):

1. Extension Init
Carregamento de Camadas
Se você usa Lambda Extensions (ex: Datadog agent, AppConfig) ou Layers grossas, o ambiente gasta tempo montando esses binários na pasta /opt da MicroVM antes de tudo.
2. Runtime Init
Boot do Interpretador
Subida da JVM (para Java), do Node v8 Engine, ou do interpretador CPython. É aqui que os Custom Runtimes (Rust/Go) brilham por não precisarem disso.
3. Function Init
Escopo Global (Seu Código)
Execução de todo o código que está FORA do seu handler (ex: import pandas, `boto3.client()`). É onde a conexão de banco de dados deve ficar para aproveitamento de Warm Starts.

Concurrency Limits & IAM Security

Estratégias de Concorrência

O limite padrão da AWS é de 1000 concorrências por região (Unreserved), o que significa que todas as suas Lambdas dividem essa cota. Se uma Lambda estourar e consumir tudo, as outras tomarão Throttling (Erro 429).

  • Reserved Concurrency: Dedica X conexões exclusivas para uma função. Se definido como 0, funciona como um *Kill Switch* emergencial para parar a função (útil contra DDoS).
  • Provisioned Concurrency: Paga-se por hora para manter X ambientes permanentemente "quentes", eliminando 100% o Init Phase e os Cold Starts em picos de acesso repentino.

Segurança IAM (O Dilema de quem acessa o quê)

Entender a diferença entre Roles e Policies é mandatório em provas de certificação e entrevistas AWS:

  • Execution Role (Resource: IAM Role): Define as permissões "de saída" da sua função. "A minha função Lambda TEM PERMISSÃO PARA escrever num DynamoDB?"
  • Resource-based Policy: Define as permissões "de entrada" na função. "Quem TEM PERMISSÃO PARA invocar essa Lambda?" (Ex: Permitir que o bucket S3 X tenha autorização de invocar sua função assíncrona).

Infraestrutura como Código (Terraform)

Provisionar Lambdas manualmente pelo Console da AWS é um anti-pattern em grandes empresas. Veja um exemplo prático de como declarar uma Lambda conectada a uma fila SQS usando Terraform (IaC):

resource "aws_iam_role" "lambda_exec_role" {
  name = "lambda_sqs_processor_role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action = "sts:AssumeRole"
      Effect = "Allow"
      Principal = { Service = "lambda.amazonaws.com" }
    }]
  })
}

# Anexa permissão para a Lambda ler a fila SQS (Execution Role)
resource "aws_iam_role_policy_attachment" "sqs_read" {
  role       = aws_iam_role.lambda_exec_role.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaSQSQueueExecutionRole"
}

# Declara a função Lambda
resource "aws_lambda_function" "processor" {
  function_name    = "order_processor"
  role             = aws_iam_role.lambda_exec_role.arn
  handler          = "app.lambda_handler"
  runtime          = "python3.11"
  filename         = "deployment_package.zip"
  
  memory_size      = 256
  timeout          = 30
  
  environment {
    variables = {
      STAGE = "production"
    }
  }
}

# Cria o Event Source Mapping (Gatilho da Fila SQS)
resource "aws_lambda_event_source_mapping" "sqs_trigger" {
  event_source_arn = aws_sqs_queue.my_queue.arn
  function_name    = aws_lambda_function.processor.arn
  batch_size       = 10 # Processa de 10 em 10 mensagens
}

Tuning Avançado & Melhores Práticas

Performance em Serverless é diretamente proporcional aos custos. Entender como a AWS aloca recursos por debaixo dos panos é vital para FinOps e eficiência.

Conceito / Configuração Impacto Arquitetural Prática Recomendada
Lambda Layers & Zip Sizes O tamanho máximo de um pacote Lambda é 50MB (zip) e 250MB (descompactado). O tempo de descompactação afeta drasticamente o Cold Start. Mova pacotes pesados (pandas, scipy, drivers jdbc) para Lambda Layers. A camada é montada no `/opt` da VM de forma eficiente, permitindo deploys muito mais rápidos do código de negócio.
Custom Runtimes & Rust/Go Linguagens dinâmicas (Python/Node) exigem subida de interpretador. Java tem a JVM. Tudo impacta FinOps em bilhões de execuções. Para extrema performance, reescreva lógicas críticas em Rust ou Go, e use a imagem provided.al2023 (Amazon Linux 2023). O Cold Start cai para menos de 30ms, reduzindo absurdamente a conta final.
Alocação de Memória vs CPU A CPU do Lambda não é configurável isoladamente. Ela escala de forma estritamente proporcional à memória alocada (1 vCPU íntegra é atingida com ~1.7GB de RAM). Use ferramentas open-source como AWS Lambda Power Tuning (Step Functions) para achar o balanço matemático ótimo entre velocidade e custo para workloads pesados em dados (pandas/numpy).
Conexões com Bancos Relacionais Milhares de concorrências (funções instanciadas rapidamente) esgotam os pools de conexão tradicionais (PostgreSQL/MySQL), causando Connection Timeouts e derrubando o banco. Inicie as conexões de banco de dados fora do escopo do handler para aproveitar o reuso em instâncias quentes (Warm Starts) e adote o Amazon RDS Proxy.
Provisioned Concurrency Mantém instâncias prontas e "quentes" o tempo todo, pagando-se um valor fixo por hora. O Init Phase (bota, carrega bibliotecas) nunca acontece no caminho crítico da requisição. Ideal para APIs sensíveis a latência consumidas por UIs. Para ETL em batch/background ou processamento em fila, o Cold Start normal de alguns segundos é perfeitamente tolerável, economizando verba.
Graviton2 (ARM64) Altera a arquitetura do processador da MicroVM subjacente de x86 para processadores AWS Graviton baseados em ARM. Sempre ligue por padrão em Lambdas Python, Node e Java modernos. Oferece até 34% de melhora em custo-performance (mais rápido e preço por ms menor). Verifique dependências C++ ou binários pré-compilados.
/tmp Space Storage (Efêmero) Oferece de 512MB até 10GB de armazenamento local no disco da VM. Perfeito para baixar e manipular arquivos temporários antes de enviar ao S3 ou EFS acoplado, mas atenção: o estado sobrevive a Warm Starts, então limpe o `/tmp` no final da função se manipular dados sensíveis!

Estrutura de Projeto (Clean Architecture)

O erro mais comum em Lambdas é o "Handler Gordo": colocar validação, regras de negócio e consultas SQL/Boto3 dentro da mesma função lambda_handler. Uma Lambda madura usa Arquitetura Hexagonal para separar responsabilidades. Veja o padrão ouro de diretório de projeto:

📦 order_processor/
 ┣ 📜 app.py                 # Lambda Handler (Porta de Entrada / Adaptador Web)
 ┣ 📜 requirements.txt       # Dependências externas (ex: boto3, pydantic)
 ┣ 📂 core/                  # Regras de Negócio Puras (Hexagonal Core)
 ┃ ┣ 📜 __init__.py
 ┃ ┗ 📜 order_service.py     # Lógica agnóstica de cloud (Pode rodar no Lambda ou on-prem)
 ┣ 📂 infra/                 # Adaptadores de Saída (Conexão com Mundo Externo)
 ┃ ┣ 📜 __init__.py
 ┃ ┗ 📜 dynamodb_repo.py     # Isolamento do Boto3 / Chamadas de rede
 ┗ 📂 tests/                 # Testes Unitários
   ┣ 📜 test_app.py
   ┗ 📜 test_order_service.py

Com a arquitetura dividida, o seu app.py se torna extremamente "magro" (Thin Handler). Ele apenas traduz a request HTTP/SQS para o seu Core. Além disso, as conexões de banco de dados ficam no escopo global para aproveitar os Warm Starts:

import json
import logging
from core.order_service import process_order
from infra.dynamodb_repo import DynamoOrderRepository

logger = logging.getLogger()
logger.setLevel(logging.INFO)

# ============================================================
# INIT PHASE (Executado UMA vez durante o Cold Start)
# Inicializa a conexão com o banco fora do handler!
# ============================================================
repo = DynamoOrderRepository(table_name="OrdersTable")

# ============================================================
# INVOKE PHASE (Executado a cada requisição / evento)
# ============================================================
def lambda_handler(event, context):
    """Handler magro: Apenas extrai o evento e delega para o domínio."""
    try:
        # 1. Extração (Adaptador de Entrada SQS)
        body = json.loads(event['Records'][0]['body'])
        order_id = body.get('order_id')
        
        # 2. Lógica de Negócio Pura (O Handler não sabe como funciona por baixo dos panos)
        result = process_order(order_id=order_id, repository=repo)
        
        # 3. Resposta de Sucesso
        return {
            "statusCode": 200,
            "body": json.dumps({"status": "SUCCESS", "data": result})
        }
        
    except Exception as e:
        logger.error(f"Erro ao processar pedido: {str(e)}")
