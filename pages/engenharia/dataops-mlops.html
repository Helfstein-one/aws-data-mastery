DataOps: Ciclos de Automação, Linhagem e Testabilidade

Garantindo resiliência, monitoramento de schemas e automação em pipelines de dados corporativos

DataOps é uma metodologia ágil voltada para o desenvolvimento e operacionalização de pipelines de dados. Na AWS, envolve a aplicação de práticas de engenharia de software (como CI/CD, testes unitários de dados e IaC) para mitigar quebras e garantir alta qualidade contínua.

Governança
Data Contracts (Contratos)
Definição formal e declarativa do schema e regras de negócios esperados na origem de dados analíticos. Impede que alterações não retrocompatíveis quebrem os pipelines analíticos a jusante (Schema Drift).
Qualidade
Testes Automatizados
Uso de bibliotecas de validação ativa (ex: Soda Core ou Great Expectations) rodando integradas a orquestradores para abortar execuções de dados inválidos antes que poluam a camada Silver/Gold.
Rastreabilidade
Data Lineage (Linhagem)
Mapeamento dinâmico do caminho percorrido pelos dados, do local de origem aos relatórios (ex: via padrões abertos como OpenLineage), simplificando a depuração e auditorias regulatórias.

Implementação de Data Contracts via JSON Schema em PySpark

Para garantir que o payload de entrada de uma fila (Kinesis/MSK) ou pasta S3 obedece estritamente ao contrato de dados acordado:

import jsonschema
from pyspark.sql.functions import udf
from pyspark.sql.types import BooleanType

# 1. Definição do Contrato de Dados Declarativo (Esquema e Regras)
DATA_CONTRACT = {
    "$schema": "http://json-schema.org/draft-07/schema#",
    "title": "ContratoClienteCadastrado",
    "type": "object",
    "properties": {
        "id_cliente": {"type": "integer"},
        "email": {"type": "string", "format": "email"},
        "idade": {"type": "integer", "minimum": 18},
        "data_cadastro": {"type": "string", "pattern": "^\\d{4}-\\d{2}-\\d{2}$"}
    },
    "required": ["id_cliente", "email", "idade"]
}

# 2. UDF Spark para validar cada linha contra o contrato
def validate_contract(row_json_str):
    try:
        data = json.loads(row_json_str)
        jsonschema.validate(instance=data, schema=DATA_CONTRACT)
        return True
    except Exception:
        return False

validate_contract_udf = udf(validate_contract, BooleanType())

# 3. Aplicação do contrato no DataFrame Spark e separação da Quarentena
df_raw = spark.read.text("s3://my-datalake/bronze/input/")
df_validated = df_raw.withColumn("valido", validate_contract_udf(df_raw["value"]))

df_clean = df_validated.filter(df_validated["valido"] == True)
df_quarantine = df_validated.filter(df_validated["valido"] == False)

# Salva registros saudáveis na Silver e envia rejeitados para correção
df_clean.write.format("iceberg").save("prod.silver.clientes")
df_quarantine.write.parquet("s3://my-datalake/quarantine/clientes/")

Data Quality Avançado & Observabilidade Estatística

Validação de dados em trânsito com AWS Glue Data Quality e Great Expectations

Data Quality não se resume a checar nulos. Em escala, envolve garantir que as distribuições estatísticas das partições não sofram desvios repentinos (Data Drift). A melhor prática é implementar o padrão de Circuit Breaker (Disjuntor): barrar o lote corrompido antes que ele chegue à camada Silver/Gold.

AWS Glue Data Quality (DQDL)

Motor serverless integrado ao Glue Data Catalog e Glue ETL. Usa a linguagem declarativa DQDL para avaliar regras em memória usando o poder distribuído do Spark (sem provisionar infraestrutura).

Great Expectations

Biblioteca open-source padrão de mercado. Permite compilar expectativas de dados em documentação legível e testá-las em PySpark, Pandas ou bancos via SQL (Athena/Redshift).

Implementação de Data Quality Circuit Breaker com AWS Glue

O código abaixo usa o EvaluateDataQuality do AWS Glue para validar um DataFrame. Se falhar, roteia o lote para um bucket de quarentena.

from awsglue.transforms import EvaluateDataQuality
from awsglue.context import GlueContext
from pyspark.context import SparkContext

sc = SparkContext()
glueContext = GlueContext(sc)

# Regras DQDL definidas como string (Geralmente carregadas do DynamoDB ou S3)
dq_rules = """
Rules = [
    IsComplete "id_cliente",
    IsUnique "email",
    ColumnValues "idade" >= 18,
    StandardDeviation "valor_compra" < 500
]
"""

# dynamic_frame_raw carregado da camada Bronze...

# Avalia Qualidade (O nó retorna 4 dataframes: sucesso, falha, resultados_das_regras e erros)
dq_results = EvaluateDataQuality.apply(
    frame=dynamic_frame_raw,
    ruleset=dq_rules,
    publishing_options={"dataQualityEvaluationContext": "AvaliacaoBronze", "enableDataQualityCloudWatchMetrics": True, "enableDataQualityResultsPublishing": True}
)

# Separa as linhas aprovadas das reprovadas
df_passed = dq_results["pass_data"]
df_failed = dq_results["fail_data"]

# Circuit Breaker: Verifica se o percentual de falha não excede o limite
total_count = dynamic_frame_raw.count()
failed_count = df_failed.count()

if failed_count > 0:
    # Roteia linhas sujas para quarentena no S3 para análise do Data Steward
    glueContext.write_dynamic_frame.from_options(
        frame=df_failed, connection_type="s3", connection_options={"path": "s3://datalake-quarantine/vendas/"}, format="parquet"
    )

if (failed_count / total_count) > 0.05: # Tolerância de 5%
    raise Exception(f"Falha de Qualidade: {failed_count} registros corrompidos excedem limite tolerado.")

# Prossegue gravação na camada Silver com linhas boas...

Contratos de Dados (Data Contracts)

Prevenção de schema drift usando JSON Schema e arquitetura orientada a domínio (Data Mesh)

Em ambientes descentralizados, as equipes de engenharia de software (produtores) frequentemente alteram esquemas de banco de dados (ex: renomear colunas) quebrando os pipelines do time de dados (consumidores) — problema conhecido como Schema Drift. O Contrato de Dados estabelece uma API formal entre produtor e consumidor.

A Regra de Ouro do Contrato: Um contrato de dados deve ser imposto no momento do CI/CD do produtor, e não apenas no pipeline do engenheiro de dados. Se o desenvolvedor tentar subir uma migração de banco que quebra o contrato analítico (removendo a coluna `cpf`), o GitHub Actions dele deve falhar o deploy.

Implementação com AWS EventBridge Schema Registry

Uma forma serverless de impor contratos é usando o EventBridge. Os eventos são enviados com um payload JSON estruturado e o Schema Registry valida automaticamente contra as tipagens cadastradas.

# Contrato JSON Schema (Armazenado no Git e sincronizado com EventBridge Registry)
{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "title": "UsuarioCriado_v2",
  "type": "object",
  "properties": {
    "user_id": { "type": "string" },
    "email": { "type": "string" },
    "plano_ativo": { "type": "boolean" }
  },
  "required": ["user_id", "plano_ativo"]
}

Data Lineage (Linhagem de Dados) & OpenLineage

Mapeamento grafológico de dependências ponta-a-ponta para auditoria LGPD e depuração

Linhagem de dados rastreia as origens, transformações e destinos finais de uma tabela ou coluna específica. É fundamental em auditorias de conformidade (LGPD/GDPR: "Mostre por onde esse CPF passou") e na análise de impacto ("Se eu alterar a tabela Vendas, quais dashboards do QuickSight vão quebrar?").

AWS Glue DataBrew / Macie

Mapeamento visual integrado na stack nativa da AWS. Excelente rastreamento dentro do ecossistema Glue.

OpenLineage (Padrão CNCF)

Padrão aberto multiplataforma. Jobs do Spark e tarefas do Airflow emitem eventos JSON genéricos que podem ser ingeridos por portais como Marquez ou DataHub.

Extraindo Linhagem de Jobs Spark (PySpark)

Configuração para forçar um job EMR a emitir eventos OpenLineage automaticamente em background toda vez que fizer um write() ou ler uma view SQL.

Plataforma de Testes & CI/CD Efêmero

Sandboxes no Amazon S3, dbt test e branches de dados para Pull Requests seguros

Em engenharia de software tradicional, compilar e testar uma aplicação web no PR é simples. Em engenharia de dados, compilar um modelo exige cruzar Terabytes de dados. Para testar queries com eficiência e baixo custo, utilizamos Sandboxing e WAP (Write-Audit-Publish).

Testes Unitários
PyTest + Local Spark
Usa mock data (dataframes criados em memória) para validar transformações lógicas (UDFs, groupBy, window functions) localmente na máquina ou no GitHub Actions.
dbt CI/CD
Schemas Efêmeros
Durante o PR, o dbt cria um schema temporário (dbt_pr_123) no Redshift/Athena. Roda os modelos de dados e os dbt tests (unique, not_null). Se falhar, bloqueia o PR. Se passar e o PR for aprovado, deleta o schema.

Padrão Write-Audit-Publish (WAP) com Apache Iceberg

O WAP evita que dados incompletos ou errados sejam vistos pelo painel de BI. Em vez de escrever e depois limpar em caso de erro, usamos a propriedade de isolamento transacional do formato Iceberg (Branching).

  1. Write (Escrever): O Job Spark cria uma ramificação (branch) escondida na tabela Iceberg (ex: branch_etl_2026) e escreve os dados novos lá. Usuários do Athena na main branch continuam vendo a tabela antiga.
  2. Audit (Auditar): Um job secundário roda regras Great Expectations apenas sobre a branch oculta.
  3. Publish (Publicar): Se todos os testes passarem, o Iceberg faz um merge/fast-forward da branch oculta para a `main` em milissegundos. Operação atômica.
# SQL no Spark para padrão WAP no Iceberg
# 1. Spark escreve na branch de auditoria específica daquela Run do Airflow
spark.conf.set("spark.wap.branch", "audit_run_948")
df_novo.write.format("iceberg").mode("append").save("prod.gold.faturamento")

# 2. Em outra etapa do orquestrador, audita a branch com Athena
# SELECT count(*) FROM prod.gold.faturamento FOR VERSION AS OF 'audit_run_948' WHERE valor IS NULL

# 3. Se aprovado, comita na main via procedure do Iceberg
spark.sql("CALL prod.system.fast_forward('prod.gold.faturamento', 'main', 'audit_run_948')")

MLOps: Ciclo de Vida do Modelo, Feature Store e Monitoramento

Orquestrando treinamento e monitoramento de modelos em produção sob a governança da AWS

MLOps estende as práticas de DevOps e DataOps para incorporar inteligência artificial e modelos preditivos em sistemas de produção de alta confiabilidade. Na AWS, o ecossistema centraliza-se em torno do Amazon SageMaker.

MLOps · Componente 1

SageMaker Feature Store

Repositório centralizado de variáveis analíticas. A Online Store (servida via DynamoDB de baixíssima latência) provê features em milissegundos para inferência em tempo real. A Offline Store (salva no S3 como Parquet/Iceberg) alimenta pipelines de treinamento em lote.

MLOps · Componente 2

SageMaker Model Registry

Cataloga e versiona modelos treinados. Permite gerenciar ciclos de aprovação manual ou automática baseados no cumprimento de limites de assertividade em ambientes de teste antes do deploy em produção.

MLOps · Componente 3

Model Monitor (Drift)

Varre continuamente as requisições que chegam ao Endpoint. Compara a distribuição física dos dados preditos (inferidos) contra a de treino, identificando desvios conceituais (Concept Drift) e populacionais (Data Drift) com alertas.

Implementação de SageMaker Pipelines com Python SDK

Código para definir de forma programática um pipeline de treinamento de modelos estruturado:

import sagemaker
from sagemaker.workflow.parameters import ParameterString
from sagemaker.workflow.steps import TrainingStep
from sagemaker.workflow.pipeline import Pipeline

session = sagemaker.Session()
role = sagemaker.get_execution_role()

# 1. Parâmetros de Entrada de Execução dinâmicos
input_data = ParameterString(
    name="InputDataUrl",
    default_value="s3://my-datalake/silver/features/dataset.parquet"
)

# 2. Definição do Estimador de Treinamento (XGBoost container)
image_uri = sagemaker.image_uris.retrieve("xgboost", session.boto_region_name, "1.5-1")
estimator = sagemaker.estimator.Estimator(
    image_uri=image_uri,
    role=role,
    instance_count=1,
    instance_type="ml.m5.xlarge",
    output_path="s3://my-datalake/models/artifacts/",
    sagemaker_session=session
)

# 3. Definição do Step de Treino
step_train = TrainingStep(
    name="TreinamentoXGBoost",
    estimator=estimator,
    inputs={
        "train": sagemaker.inputs.TrainingInput(
            s3_data=input_data,
            content_type="application/x-parquet"
        )
    }
)

# 4. Criação do Pipeline do SageMaker
pipeline = Pipeline(
    name="PipelineCreditoClientes",
    parameters=[input_data],
    steps=[step_train],
    sagemaker_session=session
)

# Grava e valida a estrutura lógica no SageMaker Hub
pipeline.upsert(role_arn=role)
# Executa o pipeline
execution = pipeline.start()

Feature Stores & Prevenção de Data Drift

Gestão centralizada de variáveis preditivas e alertas de degradação de modelos no Amazon SageMaker

O Amazon SageMaker Feature Store atua como o ponto de encontro entre o DataOps e o MLOps. Ele armazena as variáveis processadas (ex: media_compras_30dias) garantindo que os cientistas de dados não precisem reescrever as mesmas agregações lógicas (Feature Engineering) para cada novo modelo, e que o modelo inferido em tempo real utilize exatamente a mesma lógica de treinamento.

Prevenção de Training-Serving Skew: A discrepância entre os dados usados para treinar o modelo e os dados injetados na hora da predição é a principal causa de degradação da acurácia. O Feature Store resolve isso ao usar um backend unificado: grava no DynamoDB para predições online ultrarrápidas (<10ms) e espelha no S3 para os jobs de treinamento em lote.

Implementação de Alertas de Data Drift

Mesmo o melhor modelo degrada. Quando os hábitos de consumo mudam (ex: pandemia), as variáveis perdem poder preditivo (Concept Drift e Data Drift). O SageMaker Model Monitor analisa as requisições em tempo real comparando as distribuições estatísticas com os baselines do treinamento.

from sagemaker.model_monitor import DefaultModelMonitor
from sagemaker.model_monitor.dataset_format import DatasetFormat

# 1. Instancia o monitor de Drift de Dados do SageMaker
my_monitor = DefaultModelMonitor(
    role=role,
    instance_count=1,
    instance_type='ml.m5.xlarge',
    volume_size_in_gb=20,
    max_runtime_in_seconds=3600,
)

# 2. Configura a captura de dados no Endpoint de Produção
# Captura 100% dos payloads recebidos pelo modelo via API e joga no S3
my_monitor.suggest_baseline(
    baseline_dataset="s3://my-datalake/mlops/treino/baseline_data.csv",
    dataset_format=DatasetFormat.csv(header=True),
    output_s3_uri="s3://my-datalake/mlops/monitoring/baseline/",
    wait=True
)

# 3. Cria um Job agendado que compara captura vs baseline e alerta no CloudWatch se houver Drift de Kolmogorov-Smirnov
my_monitor.create_monitoring_schedule(
    monitor_schedule_name="DetecaoDriftDiaria",
    endpoint_input=predictor.endpoint_name,
    output_s3_uri="s3://my-datalake/mlops/monitoring/reports/",
    statistics=my_monitor.baseline_statistics(),
    constraints=my_monitor.suggested_constraints(),
    schedule_cron_expression="cron(0 0 * * ? *)",
    enable_cloudwatch_metrics=True
)

Git & CI/CD

Git Flow & Versionamento para Dados

Estratégias de versionamento, Git Actions, rollback e boas práticas aplicadas a pipelines de engenharia de dados (DataOps).

O que é o Git Flow em Dados?

No contexto de Engenharia de Dados, versionamento vai muito além do código-fonte (Python/Scala). Um Git Flow maduro envolve versionar infraestrutura (IaC), códigos de orquestração (Airflow), definições de schema e pipelines de transformação (dbt) de forma integrada e segura para não corromper o Data Lake.

Comandos Essenciais do Git
  • git init / clone: Inicializar ou baixar repositório.
  • git checkout -b <branch>: Criar e mudar para nova branch.
  • git add . / commit -m: Adicionar e persistir mudanças localmente.
  • git rebase origin/main: Atualizar sua branch com as últimas mudanças da main (evita merge commits sujos).
  • git push origin <branch>: Enviar código para o repositório remoto.
  • git stash: Salvar mudanças locais temporariamente sem commitar.
Estratégias de Rollback Seguras
  • git revert <commit_hash>: Recomendado. Cria um novo commit desfazendo as alterações do commit defeituoso. Mantém o histórico limpo e auditável.
  • git reset --hard <commit_hash>: Perigoso. Apaga o histórico local até o commit especificado. Nunca use na branch main de produção!
  • Rollback em Dados (Lógica + Estado): Reverter o código do Git é apenas 50%. Você também precisa reverter os dados afetados (Ex: usar Time Travel no Apache Iceberg: CALL system.rollback_to_timestamp(...)).

GitHub Actions (CI/CD) em DataOps

O CI/CD automatiza os testes e deploys para garantir que um PR ruim não quebre a produção.

.github/workflows/deploy_pipeline.yml
name: Data Pipeline CI/CD

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  test_and_lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.9'
      - name: Install dependencies
        run: pip install pytest flake8 black
      - name: Run Black & Flake8 (Linting)
        run: |
          black --check src/
          flake8 src/
      - name: Run Unit Tests (Pytest)
        run: pytest tests/

  deploy_to_aws:
    needs: test_and_lint
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          role-to-assume: arn:aws:iam::123456789012:role/DeployRole
          aws-region: us-east-1
      - name: Sync scripts to S3
        run: aws s3 sync src/ s3://meu-lake-artifacts/scripts/
Perguntas e Cases: Entrevistas sobre Git em Dados

P1: "Você mergeou um PR que quebrou a lógica de cálculo de receita no Spark em Produção. Como você atua?"
Resposta Esperada: "Primeiro, abro um PR com git revert do commit defeituoso para restaurar o código funcional o mais rápido possível e dou deploy. Depois, atuo no lado dos dados: utilizo os recursos de Time Travel do formato (Iceberg/Delta) para restaurar a tabela da camada Gold para o estado anterior à execução do job defeituoso. Em seguida, investigo a causa raiz localmente."

P2: "Por que não podemos versionar grandes arquivos .csv ou .parquet no Git?"
Resposta Esperada: "O Git foi feito para versionamento de arquivos de texto (código fonte), e rastrear diffs em binários pesados incha o repositório, deixando-o lento (Git Bloat). Para versionar dados (Machine Learning ou Data Lakes), devemos usar ferramentas específicas como DVC (Data Version Control) ou o versionamento em nível de formato de tabela (Apache Iceberg Snapshots)."
