AWS Glue: ETL Serverless e Dynamic Frames

Evolução de Schema com AWS Glue Schema Registry

Ao ingerir dados via Streaming (Kafka/Kinesis) para o Glue, o formato Avro/Protobuf é preferível ao JSON por possuir tipagem forte e binária. Mas o que acontece se o time de engenharia de software dropar uma coluna transacional vital? O AWS Glue Schema Registry entra como um validador de contrato.

Integrando as bibliotecas SerDe (Serializer/Deserializer) do Schema Registry nos Produtores (EC2/Lambdas) e Consumidores (Glue Jobs), garantimos Forward/Backward Compatibility. Se um payload ferir as regras (ex: apagar uma coluna que era required), a mensagem é bloqueada na origem antes mesmo de poluir o Tópico Kafka, evitando o "Data Poisoning" no Data Lake.

Como Funciona

O Glue utiliza um ambiente Spark totalmente gerenciado. Ele abstrai a gestão de clusters, permitindo focar no código Python/Scala. O Data Catalog atua como um Metastore centralizado para o Lakehouse.

  • Interactive Sessions: Permite desenvolvimento rápido via Jupyter Notebooks sem esperar minutos pelo provisionamento de clusters.
  • Glue Flex: Classe de execução de baixo custo (até 35% de economia) para jobs não críticos, utilizando capacidade excedente da AWS (similar ao Spot).

Performance & Configurações (Sizing de Workers e Executors)

Diferente do Spark tradicional onde você define spark.executor.instances, no AWS Glue você provisiona DPUs (Data Processing Units) e seleciona o Worker Type. O runtime do Glue configura a JVM automaticamente:

Worker Type DPUs vCPUs RAM Spark Executors por Worker Recursos por Executor Spark
G.1X 1 DPU 4 vCPUs 16 GB 1 Executor 4 vCPUs, 10 GB RAM (restante para OS/YARN)
G.2X 2 DPUs 8 vCPUs 32 GB 1 Executor 8 vCPUs, 24 GB RAM (ideal para grandes volumes de dados)
G.4X 4 DPUs 16 vCPUs 64 GB 1 Executor 16 vCPUs, 52 GB RAM (processamento massivo e ML local)
G.8X 8 DPUs 32 vCPUs 128 GB 1 Executor 32 vCPUs, 108 GB RAM (altamente intensivo em memória)
  • Worker Auto Scaling: Disponível no Glue 3.0+, escala dinamicamente o número de workers conforme a carga do job, reduzindo custos em shuffles ou processamentos variáveis.
  • Regra Prática de Tuning para OOM no Glue: Se o seu Job do Glue falhar por falta de memória física (OOM) no Worker, alterar de G.1X para G.2X dobra a memória disponível para o executor Spark (de 10GB para 24GB) mantendo o mesmo número de tarefas paralelas por nó, eliminando o estouro do contêiner JVM.

Aprofundamento Técnico: DynamicFrames e PySpark no Glue

O AWS Glue estende o Apache Spark através da API de DynamicFrames. Um DynamicFrame é semelhante a um DataFrame, mas projetado especificamente para lidar com dados que têm um schema inconsistente (comum em Data Lakes JSON/CSV). Ele infere o schema registro a registro, permitindo lidar com conflitos de tipos dinamicamente.

import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job

args = getResolvedOptions(sys.argv, ['JOB_NAME'])

# 1. Instância e Contextos: O GlueContext engloba o SparkContext padrão
sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.spark_session
job = Job(glueContext)
job.init(args['JOB_NAME'], args)

# 2. Leitura (Source): Criando um DynamicFrame a partir do Data Catalog
dyf = glueContext.create_dynamic_frame.from_catalog(
    database="lakehouse_raw",
    table_name="eventos_iot"
)

# 3. Tratamento de Conflito de Schema (ResolveChoice)
# Problema: Em alguns JSONs o campo 'id' veio como INT, em outros como STRING. 
# No Spark puro, isso causaria erro de casting. No Glue, o tipo inferido vira 'choice'.
# O ResolveChoice permite padronizar a coluna para um único tipo ou estruturar ambos.
resolved_dyf = dyf.resolveChoice(specs=[
    ("id", "cast:long"),           # Força tudo para long numérico
    ("timestamp", "cast:string")   # Força timestamps para string ISO8601
])

# 4. Transformações Avançadas (ApplyMapping)
# Remove colunas indesejadas, renomeia, e muda tipos ao mesmo tempo
mapped_dyf = ApplyMapping.apply(
    frame=resolved_dyf,
    mappings=[
        ("id", "long", "device_id", "long"),
        ("payload.temperature", "double", "temperatura", "double")
    ]
)

# Transição bidirecional entre Glue API e Spark puro para lógicas complexas
spark_df = mapped_dyf.toDF()
# ... transformações Spark SQL puras aqui ...
final_dyf = DynamicFrame.fromDF(spark_df, glueContext, "final_dyf")

# 5. Escrita (Sink): Gravando em S3 convertendo para Parquet (com Snappy)
glueContext.write_dynamic_frame.from_options(
    frame=final_dyf,
    connection_type="s3",
    connection_options={
        "path": "s3://meu-bucket/silver/eventos_iot/",
        "partitionKeys": ["ano", "mes", "dia"]
    },
    format="parquet"
)

job.commit()

Estratégias do ResolveChoice

Lidar com o tipo choice é essencial em ingestões JSON caóticas. O método aceita quatro operações principais:

  • cast:<type>: Força todos os valores conflitantes a tentarem conversão para o tipo especificado. Falhas viram null.
  • make_struct: Cria um objeto estruturado contendo ambos os tipos. Útil quando você não quer perder dados (ex: mantém a sub-coluna 'int' e a sub-coluna 'string').
  • project:<type>: Descarta os registros do tipo conflitante, retendo apenas o tipo especificado.
  • make_cols: Cria colunas separadas para cada tipo encontrado (ex: col_int e col_string).

Sink no Data Catalog e S3

O método write_dynamic_frame.from_options permite escrever diretamente no S3 definindo formatos (CSV, Parquet, ORC, Avro). Alternativamente, você pode usar write_dynamic_frame.from_catalog para atualizar partições no Metastore automaticamente ao escrever dados em tabelas já mapeadas, simplificando a pipeline downstream para o Athena sem precisar rodar um Crawler depois.

Transformações Nativas (DynamicFrame Methods)

Além do ResolveChoice e ApplyMapping, a API do Glue oferece métodos otimizados para pipelines severos:

  • Relationalize: O "Flatten" definitivo. Desmonta arrays e structs aninhados complexos (JSONs de dezenas de níveis) gerando múltiplas tabelas relacionais em memória interligadas por chaves de junção sintéticas geradas na hora. Ideal para preparar dados para Data Warehouses tradicionais.
  • Unbox: Se um sistema fonte mandou uma string JSON "encapsulada" dentro de um campo de texto puro, o Unbox tenta parsear a string e convertê-la estruturalmente em colunas reais.
  • Spigot: Uma válvula de amostragem no meio do DAG. Grava uma amostra dos registros processados num path S3 específico apenas para debug sem interromper o Job. Muito usado quando se quer investigar quebra de tipos.
  • DropFields / SelectFields: Operações clássicas de projeção empurradas (Pushdown) para acelerar processamento in-memory.
  • DetectPII / FindMatches: Funções avançadas com Machine Learning embarcado. O DetectPII escaneia o DynamicFrame e pode anonimizar, mascarar ou hashear dados sensíveis (CPFs, Cartões de Crédito) nativamente em trânsito antes de cair no S3. O FindMatches usa ML para deduplicar cadastros de clientes que não possuem chaves primárias exatas (ex: "Joao Silva" vs "J. Silva").

Integração Dinâmica com Data Catalog

No Spark tradicional, você gravaria o Parquet no S3 e depois rodaria um MSCK REPAIR TABLE ou usaria um Crawler para inferir as novas partições. No AWS Glue, você passa o parâmetro enableUpdateCatalog=True diretamente no sink:

sink = glueContext.getSink(
  connection_type="s3", path="s3://lake/gold",
  enableUpdateCatalog=True,
  updateBehavior="UPDATE_IN_DATABASE"
)
sink.setCatalogInfo(catalogDatabase="db", catalogTableName="tbl")
sink.writeFrame(dyf)

Isso atualiza schemas e registra novas partições transacionalmente assim que a escrita no S3 termina, deixando os dados instantaneamente visíveis no Amazon Athena.

Tuning Avançado via Job Parameters

A interface do AWS Glue esconde o ambiente YARN, mas você pode passar dezenas de parâmetros JVM e configurações Spark através dos Job Parameters (também acessíveis na UI aba "Job details"). Eis os mais críticos para engenharia avançada:

Parâmetro (Key) Impacto no Cluster Caso de Uso (Troubleshooting)
--conf spark.sql.shuffle.partitions Altera o número de partições de shuffle pós-join/groupby (Padrão: 200). Se você cruzar tabelas de 10TB no Glue G.2X e deixar 200, cada partição será de 50GB, estourando os workers. Aumente para 2000+.
--conf spark.yarn.executor.memoryOverhead Aumenta a margem de memória off-heap para YARN além dos 10% defaults. Quando o Glue Job falha silenciosamente por "Container killed by YARN for exceeding memory limits" em operações pesadas com Strings.
--enable-job-insights Ativa a UI de Observabilidade do Glue. Analisa data skewness (inclinação de dados) visualmente: mostra se um worker do Glue ficou processando 99% dos dados de uma chave "Nula".
--enable-continuous-cloudwatch-log Empurra logs do driver/executor quase em real-time para o CloudWatch. Indispensável para debugar Jobs que ficam travados ("hanging") por horas sem erro explícito por contenção de rede ou S3 throttling.
--datalake-formats Habilita bibliotecas otimizadas de ACID (Iceberg, Hudi, Delta). Se valor = iceberg, injeta os JARs necessários no classpath, permitindo MERGE INTO (UPSERTS) transacionais no S3.

Spark Structured Streaming & Stateful Processing

Pipelines de dados continuados exactly-once tolerantes a falhas

Diferente de sistemas puramente contínuos (como o Flink), o Spark Structured Streaming opera nativamente sob o modelo de Micro-Batching. A engine aguarda um intervalo de trigger configurável (ex: 10 segundos), coleta as mensagens que chegaram no Kafka/Kinesis nesse intervalo, e as processa usando o mesmo motor otimizado do Spark SQL (Catalyst/Tungsten) como se fossem um DataFrame estático convencional. Esse design unifica a API Batch e Streaming.

O Core da Semântica Temporal

⏱️ Event Time vs Processing Time

Em processamento de streaming, a confusão entre tempos gera corrupção analítica severa:

  • Event Time: O exato momento em que o evento ocorreu no mundo físico (ex: o usuário clicou no botão às 10:00). Embutido no payload (JSON). É a única métrica confiável para agregações de negócio.
  • Processing Time: O momento em que o nó do Spark recebeu e começou a processar o registro (ex: 10:15 devido a um atraso de rede). Se você agrupar por Processing Time, um pico de latência no Kafka agrupará cliques das 10:00 junto com os das 10:15, falsificando a curva de tráfego.

💧 Watermarking & "Late-arriving Data"

Em operações Stateful (agregações baseadas em janelas temporais baseadas no Event Time), o Spark precisa manter na RAM (State Store) o estado parcial das agregações. Se um celular ficar sem sinal, um evento de ontem pode chegar hoje (Late Data).

Para evitar que a memória do Spark estoure guardando todas as janelas do passado infinitamente (OOM), usamos o Watermark. Ele define o Allowed Lateness (Atraso Permitido).

Ex: .withWatermark("event_time", "10 minutes"). Se o evento mais recente processado tiver o Event Time 12:00, o Watermark avança para 11:50. Se um evento atrasado chegar com tempo 11:45, a janela correspondente já foi ejetada da RAM e finalizada para o sink; o evento atrasado é descartado silenciosamente para proteger o cluster.

Mecanismos Avançados de Streaming

🗂️ Windowing & Stateful Processing

Spark suporta três tipos de agrupamentos temporais para agregar o stream infinito de dados:

  • Tumbling Windows (Janelas Fixas): Não sobrepostas. Ex: Das 10:00 às 10:05, das 10:05 às 10:10. Cada evento pertence a uma única janela.
  • Sliding Windows (Janelas Deslizantes): Sobrepostas. Ex: Tamanho de 10 minutos, deslizando a cada 5 minutos. Um evento das 10:03 participará da janela [09:55-10:05] e [10:00-10:10].
  • Session Windows: Baseada na inatividade. Ex: Agrupa os cliques do usuário 123. Se ele ficar 30 minutos sem clicar, a janela fecha. Requer intenso uso do State Store.

🔄 Garantias de Entrega (Delivery Guarantees) & Checkpoints

Sistemas distribuídos falham. O Spark garante semântica Exactly-Once (fim a fim) combinando sinks idempotentes (como Delta Lake) com seu mecanismo rigoroso de Checkpoints & Write-Ahead Logs (WAL).

Antes de iniciar um micro-batch, o Spark escreve de forma síncrona no HDFS/S3 os exatos offsets do Kafka que vai ler. Se um nó Spot morrer durante o processamento, o Spark levanta a tarefa em outro nó, lê o WAL do S3, descobre exatamente em qual offset a falha ocorreu e reprocessa cirurgicamente sem perder ou duplicar dados.

⚠️ Backpressure & Throttling (Proteção de Carga)
Se o tráfego do Kafka explodir 100x na Black Friday, o Spark tentará puxar todos os milhões de registros para um único micro-batch, estourando a RAM (OOM) instantaneamente. Para gerenciar o Backpressure, o Spark não sinaliza ativamente ao Kafka para "parar", mas restringe o consumo na ponta do leitor via limites de trigger:
.option("maxOffsetsPerTrigger", "50000") - Força o Spark a ler, no máximo, 50 mil mensagens por micro-batch, limitando o throughput e mantendo o processamento estável mesmo sob pico severo.

Arquitetura End-to-End: Kafka para Delta Lake

Abaixo, um pipeline prático arquitetural que consome de um tópico de mensageria escalável e grava num formato Lakehouse garantindo atomicidade:

# 1. Leitura: Processamento incremental com backpressure controlado
df_stream = spark.readStream     .format("kafka")     .option("kafka.bootstrap.servers", "broker:9092")     .option("subscribe", "telemetria")     .option("startingOffsets", "earliest")     .option("maxOffsetsPerTrigger", "50000")     .load() # maxOffsetsPerTrigger controla o backpressure

# 2. Transformação, Windowing e Watermark
import pyspark.sql.functions as F
df_parsed = df_stream.selectExpr("CAST(value AS STRING) as json_data")     .withColumn("event_time", F.col("json_data.timestamp").cast("timestamp"))     .withWatermark("event_time", "10 minutes")     .groupBy(F.window("event_time", "5 minutes"), "json_data.sensor_id")     .agg(F.avg("json_data.temperatura").alias("media_temp"))

# 3. Escrita: Gravação Delta idempotente usando Triggers
# OutputModes: "append" (novos), "update" (alterados), "complete" (tabela inteira)
df_parsed.writeStream     .format("delta")     .outputMode("append")     .option("checkpointLocation", "s3://bucket/checkpoints/telemetria_agg/")     .trigger(processingTime="1 minute")     .start("s3://bucket/tabela_delta_agreggada/")
⚡ Modos de Trigger

A diretiva .trigger() determina quando o motor vai verificar por novos dados:

  • trigger(processingTime="10 seconds"): Executa micro-batches periodicamente a cada 10s. O mais usado.
  • trigger(availableNow=True): Modo Batch Híbrido. Consome todos os dados pendentes no Kafka de uma vez, mas quebrando em micro-batches em background para evitar OOM, e depois desliga o cluster. Ideal para orquestração noturna que precisa da resiliência dos checkpoints de streaming.
  • trigger(continuous="1 second"): Ignora o micro-batching. Cada tarefa puxa mensagens em polling contínuo da origem. Menor latência (~1ms), mas perde a capacidade de agregação stateful.

Apache Flink & Stateful Stream Processing

Tuning Avançado: RocksDB StateBackend & Unaligned Checkpoints

Em processamento Stateful de alto débito (bilhões de TPS), salvar o "Estado" de uma janela temporal na Heap do Java causa pausas infernais de Garbage Collection. O RocksDB StateBackend serializa o estado em disco local SSD (out-of-core), libertando a JVM e permitindo estados gigantescos.

Contudo, durante o Snapshot do Estado (Checkpointing para o S3 via protocolo Chandy-Lamport), o Flink pode gargalar se o throughput for muito alto (Backpressure). A ativação de Unaligned Checkpoints permite que os "Barriers" ultrapassem os buffers cheios, garantindo que o checkpoint termine rápido mesmo sob forte pressão de rede, à custa de armazenar os dados em trânsito no S3.

Processamento contínuo de eventos com baixa latência, tolerância a falhas e controle de estado

O Apache Flink é o principal motor para processamento contínuo de eventos (Streaming) de baixíssima latência (milissegundos) no mercado. Diferente do Spark Streaming (baseado em micro-batches), o Flink processa registro por registro (event-driven) e gerencia estados de memória complexos de forma nativa e tolerante a falhas.

Checkpoints vs Savepoints

Os mecanismos de persistência de estado do Flink servem a propósitos operacionais distintos:

  • Checkpoints (Automáticos): São disparados automaticamente pelo Flink para tolerância a falhas. Gravam snapshots assíncronos do estado distribuído no S3. Se um worker cair, o Flink lê o último checkpoint e retoma o processamento com garantia de exatamente-uma-vez (Exactly-Once).
  • Savepoints (Manuais/Administrativos): São snapshots disparados manualmente pelo administrador do sistema. Salva o estado completo da aplicação de forma portátil. É utilizado para atualizações de código do job, migrações de cluster ou redimensionamento de recursos.
RocksDB State Backend vs HashMap

O local onde o Flink armazena os estados das janelas e agregações temporárias em tempo de execução:

  • HashMap State Backend (Memória): Guarda todo o estado na heap da JVM do TaskManager. Latência de leitura/escrita extremamente baixa (nanossegundos), mas o tamanho do estado fica limitado à memória RAM disponível, podendo causar OutOfMemory (OOM).
  • RocksDB State Backend (Disco + Cache): Guarda o estado em um banco de dados embarcado fora do heap da JVM (Off-Heap) gravando em discos locais (NVMe/SSD). Permite armazenar terabytes de estado (maior que a RAM física). O Flink descarrega checkpoints assincronamente no S3.

Escrita de Query Analítica Real em Flink SQL

O Flink SQL permite descrever computações complexas de tempo real de forma declarativa. O exemplo abaixo implementa uma Janela Deslizante (Sliding Window) de 10 minutos que computa a soma de transações a cada 1 minuto a partir de dados brutos lidos do Amazon MSK (Kafka):

-- 1. Cria a Tabela de Origem mapeando o tópico do Amazon MSK (Kafka)
CREATE TABLE msk_transactions (
    transaction_id STRING,
    user_id STRING,
    amount DOUBLE,
    event_time TIMESTAMP(3),
    -- Declaração do Watermark: tolerância de atraso de dados de até 5 segundos
    WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
) WITH (
    'connector' = 'kafka',
    'topic' = 'production.transactions',
    'properties.bootstrap.servers' = 'broker1:9092,broker2:9092',
    'properties.group.id' = 'flink-sales-aggregation',
    'scan.startup.mode' = 'latest-offset',
    'format' = 'json'
);

-- 2. Executa a agregação contínua usando a Sliding Window (Hop Window)
SELECT 
    user_id,
    -- Início e Fim da Janela temporal
    window_start,
    window_end,
    COUNT(transaction_id) AS total_transactions,
    SUM(amount) AS total_amount
FROM TABLE(
    HOP(TABLE msk_transactions, DESCRIPTOR(event_time), INTERVAL '1' MINUTE, INTERVAL '10' MINUTE)
)
GROUP BY 
    user_id, window_start, window_end;
