System Design Document (SDD) para Projetos de IA

O ciclo de vida formal da engenharia de prompt para a produção em nuvem.

Em ambientes de Engenharia de Dados corporativos, a introdução de modelos de linguagem não deve ser feita de forma experimental. O desenvolvimento exige a elaboração de um System Design Document (SDD) formal. O SDD atua como o blueprint que traduz requisitos de negócio em especificações de arquitetura na nuvem.

Os 5 Pilares Fundamentais do SDD para GenAI:

  1. Fase 1: Escopo e Limites de Negócio (Requisitos):
    Definição explícita de SLAs de latência (ex: tempo máximo de inferência de 2.5s), orçamentos de custo de API (FinOps) e políticas de privacidade sob regulamentações (LGPD).
  2. Fase 2: Arquitetura Lógica e Fluxo (Data Flow):
    Especificação de como as queries fluirão. Define as regras de processamento (tamanho do chunking semantic, estratégia de busca híbrida k-NN + BM25 e Re-ranking).
  3. Fase 3: Arquitetura Física e Infra (AWS Stack):
    Mapeamento de recursos. Definição do uso de clusters OpenSearch, tabelas DynamoDB para cache semântico e execução de Lambdas. Estabelece a segurança estrita de privilégio mínimo via IAM e isolamento de rede através de VPC Endpoints.
  4. Fase 4: Avaliação Semântica (Evolutiva):
    Uso de frameworks de testes (como Ragas ou TruLens) para avaliar métricas como Faithfulness (se o LLM alucinou fora do RAG) e Answer Relevance antes de ir para produção.
  5. Fase 5: Observabilidade e Feedback Loop:
    Captura de tempos de inferência e custos via CloudWatch/Datadog para evitar estouros orçamentários.

Diagrama: Arquitetura Corporativa de Plataforma de IA Multi-Agentes com RAG

📌 Legenda Detalhada da Plataforma de IA Multi-Agentes:
  • [A] User App (API Gateway): Porta de entrada que autentica requisições e encaminha o evento para o grafo de agentes.
  • [B] Supervisor Agent (LangGraph Router): Agente roteador que analisa a intenção do usuário e delega sub-tarefas para agentes especializados.
  • [C] RAG Worker Agent: Agente responsável pela busca de contexto textual não-estruturado usando embeddings e vetorização.
  • [D] Data & SQL Agent: Agente especializado em traduzir perguntas em queries SQL seguras para execução em bancos analíticos.
  • [E] Aurora pgvector: Banco vetorial PostgreSQL gerenciado armazenando índices HNSW para busca semântica sub-milissegundo.
  • [F] Amazon Athena: Motor de consulta interativo Serverless que executa queries SQL sobre dados transacionais no formato Apache Iceberg.
  • [G] Amazon Bedrock Claude 3: Modelo sintetizador final que consolida os insights do RAG e das queries SQL em uma resposta coesa com autorreflexão.
Evolução da Arquitetura: A orquestração via AWS Lambda (Reasoning Loop) pode ser substituída integralmente pelo uso nativo do Amazon Bedrock Agents e Knowledge Bases, o que abstrai a manutenção do código de loop do ReAct.

Oportunidades e Trade-offs (Quando NÃO usar IA)

Um anti-padrão grave na engenharia de dados é o "LLM-washing" — tentar usar modelos gigantescos para resolver problemas triviais de programação.

  • Busca exata de fatos: Se o usuário quer saber o ID exato de um pedido, não use LLMs. Use uma busca de banco relacional indexada. LLMs são para análise qualitativa e busca semântica ("Encontre problemas comuns nos pedidos da região sul"), não quantitativa exata.
  • Filtros e Matemáticas Longas: LLMs são péssimos em realizar somas exatas sobre 10 mil linhas de um CSV (eles não "calculam", eles "preveem"). A abordagem correta é o LLM gerar um código SQL/Python que rode no Athena/Glue para fazer a agregação matemática determinística.
  • Custo de Operação: Processar 1 milhão de logs usando Claude 3.5 pode custar dezenas de dólares. Processar os mesmos logs extraindo Regex no Apache Spark custa centavos. A GenAI deve ser usada na camada de orquestração e raciocínio abstrato, não na camada de força-bruta computacional de dados estruturados.

Exemplo Prático: Orquestração Multi-Agente com LangGraph em Python

Abaixo apresenta-se um exemplo funcional de orquestrador Multi-Agentes utilizando LangGraph para delegar sub-tarefas entre um Agente RAG e um Agente SQL Data Engineer:

# Exemplo de Orquestração Multi-Agente com LangGraph
from typing import TypedDict, Annotated, Sequence
from langgraph.graph import StateGraph, END
from langchain_core.messages import BaseMessage, HumanMessage, AIMessage

# 1. Definir Estado do Grafo Multi-Agente
class AgentState(TypedDict):
    messages: Sequence[BaseMessage]
    next_step: str

# 2. Nó Roteador Supervisor (Decide qual agente especializado deve atuar)
def supervisor_node(state: AgentState):
    last_msg = state["messages"][-1].content
    if "relatório" in last_msg.lower() or "vendas" in last_msg.lower():
        return {"next_step": "sql_agent"}
    return {"next_step": "rag_agent"}

# 3. Nó Agente RAG (Busca semântica no banco vetorial)
def rag_agent_node(state: AgentState):
    resposta_rag = "Contexto recuperado via Aurora pgvector: Regulamento CMN 4.966 exige provisão esperada."
    return {"messages": state["messages"] + [AIMessage(content=resposta_rag)]}

# 4. Nó Agente SQL (Consulta estruturada no Amazon Athena)
def sql_agent_node(state: AgentState):
    resposta_sql = "Resultado SQL Athena: Total faturado no Q3 2026 foi R$ 14.2M."
    return {"messages": state["messages"] + [AIMessage(content=resposta_sql)]}

# 5. Construir o Grafo de Estados
workflow = StateGraph(AgentState)
workflow.add_node("supervisor", supervisor_node)
workflow.add_node("rag_agent", rag_agent_node)
workflow.add_node("sql_agent", sql_agent_node)

workflow.set_entry_point("supervisor")
workflow.add_conditional_edges(
    "supervisor",
    lambda x: x["next_step"],
    {"rag_agent": "rag_agent", "sql_agent": "sql_agent"}
)
workflow.add_edge("rag_agent", END)
workflow.add_edge("sql_agent", END)

app = workflow.compile()
print("Grafo Multi-Agente Compilado com Sucesso.")
