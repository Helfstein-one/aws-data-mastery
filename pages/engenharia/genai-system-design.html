01

Framework de Decisão: RAG vs Fine-Tuning vs Agents vs Prompt

O fluxograma definitivo para escolher a abordagem certa sem desperdiçar meses no padrão errado.

A escolha da abordagem define orçamento, complexidade e manutenção por anos. Use o framework abaixo como ponto de partida — cada pergunta elimina caminhos inadequados.

Critério Prompt Engineering RAG Bedrock Agents Fine-Tuning (LoRA)
Necessita de dados externos/recentes? ✗ Não ✓ Sim ✓ Sim (via tools) ✗ Não
Executa ações no mundo real? ✗ Não ✗ Não ✓ Sim ✗ Não
Output em formato muito específico / dialeto? ⚠️ Parcial ✗ Não ⚠️ Parcial ✓ Ideal
Dados mudam com frequência (<meses)? — ✓ Ideal ✓ Sim ✗ Caro re-treinar
Custo de implementação Horas Dias/semanas Semanas/meses Meses + dados
Custo de inferência/chamada $$ Baixo $$$ Médio $$$$ Alto $ Muito baixo
Latência típica < 2s 2-5s 5-30s < 1s
Caso de uso ideal Classificação, resumo, extração estruturada Q&A sobre documentos, chatbot corporativo Análise autônoma, workflows multi-step SQL-gen, tone-of-voice, domínio fechado
Regra de ouro:

Comece sempre pelo mais simples. Prompt Engineering resolve >40% dos casos de uso. Se não resolver, adicione RAG. Se precisar de ações externas, adicione Agents sobre o RAG. Fine-Tuning é o último recurso — use somente quando latência, custo de tokens ou qualidade de formato for o bottleneck insolúvel pelos outros padrões.

02

System Design Document (SDD) para Projetos de IA

O ciclo de vida formal da engenharia de prompt para a produção em nuvem.

Em ambientes de Engenharia de Dados corporativos, a introdução de modelos de linguagem não deve ser feita de forma experimental. O desenvolvimento exige a elaboração de um System Design Document (SDD) formal. O SDD atua como o blueprint que traduz requisitos de negócio em especificações de arquitetura na nuvem.

Os 5 Pilares Fundamentais do SDD para GenAI:

  1. Fase 1: Escopo e Limites de Negócio (Requisitos):
    Definição explícita de SLAs de latência (ex: tempo máximo de inferência de 2.5s), orçamentos de custo de API (FinOps) e políticas de privacidade sob regulamentações (LGPD).
  2. Fase 2: Arquitetura Lógica e Fluxo (Data Flow):
    Especificação de como as queries fluirão. Define as regras de processamento (tamanho do chunking semantic, estratégia de busca híbrida k-NN + BM25 e Re-ranking).
  3. Fase 3: Arquitetura Física e Infra (AWS Stack):
    Mapeamento de recursos. Definição do uso de clusters OpenSearch, tabelas DynamoDB para cache semântico e execução de Lambdas. Estabelece a segurança estrita de privilégio mínimo via IAM e isolamento de rede através de VPC Endpoints.
  4. Fase 4: Avaliação Semântica (Evolutiva):
    Uso de frameworks de testes (como Ragas ou TruLens) para avaliar métricas como Faithfulness (se o LLM alucinou fora do RAG) e Answer Relevance antes de ir para produção.
  5. Fase 5: Observabilidade e Feedback Loop:
    Captura de tempos de inferência e custos via CloudWatch/Datadog para evitar estouros orçamentários.

Diagrama: Arquitetura Corporativa de Agente Autônomo com RAG

RAG ARCHITECTURE — BEDROCK + PGVECTOR + KNOWLEDGE BASE
📌 Legenda & Arquitetura — System Design RAG Corporativo:
  • Componentes AWS / Módulos: Amazon API Gateway, AWS Lambda (Orquestrador), Amazon Bedrock Knowledge Bases (Titan Embeddings), Amazon Aurora (pgvector) / OpenSearch, Amazon Bedrock (Claude/Llama).
  • Integração: Requisição via API Gateway e Lambda para Amazon Bedrock Knowledge Base, que realiza a busca vetorial (kNN) no pgvector/OpenSearch e constrói o prompt enriquecido com chunks de contexto para o LLM.
  • Contexto: Desenho de solução de inteligência conversacional corporativa gerenciada com suporte a múltiplos motores de busca vetorial.
Evolução da Arquitetura: A orquestração via AWS Lambda (Reasoning Loop) pode ser substituída integralmente pelo uso nativo do Amazon Bedrock Agents e Knowledge Bases, o que abstrai a manutenção do código de loop do ReAct.
📌 Legenda & Arquitetura — Prompt Caching & Streaming:
  • Componentes AWS / Módulos: Client, ElastiCache Redis, Bedrock LLM, SSE Stream
  • Integração: Verificação de cache de prefixos de prompt e emissão contínua de tokens via Server-Sent Events.
  • Contexto: System design de alta performance.

Planilha técnica detalhada para orientar a escolha do modelo ideal com base no caso de uso, incluindo modelos abertos e proprietários.

Claude 3.5 Sonnet $3.00 Excelente (98%) Média (~1.8s) Desenvolvimento complexo, Text-to-SQL estruturado e agentes ReAct autônomos.

Oportunidades e Trade-offs (Quando NÃO usar IA)

Um anti-padrão grave na engenharia de dados é o "LLM-washing" — tentar usar modelos gigantescos para resolver problemas triviais de programação.

  • Busca exata de fatos: Se o usuário quer saber o ID exato de um pedido, não use LLMs. Use uma busca de banco relacional indexada. LLMs são para análise qualitativa e busca semântica ("Encontre problemas comuns nos pedidos da região sul"), não quantitativa exata.
  • Filtros e Matemáticas Longas: LLMs são péssimos em realizar somas exatas sobre 10 mil linhas de um CSV (eles não "calculam", eles "preveem"). A abordagem correta é o LLM gerar um código SQL/Python que rode no Athena/Glue para fazer a agregação matemática determinística.
  • Custo de Operação: Processar 1 milhão de logs usando Claude 3.5 pode custar dezenas de dólares. Processar os mesmos logs extraindo Regex no Apache Spark custa centavos. A GenAI deve ser usada na camada de orquestração e raciocínio abstrato, não na camada de força-bruta computacional de dados estruturados.

SDD Template — Documento de Decisão de Sistema (Preenchido)

Exemplo real de um SDD para um Agente Autônomo de Análise de Crédito com RAG + Bedrock Agents.

Um SDD (System Design Document) para projetos de IA deve responder: por que este padrão? (RAG, Agents, Fine-Tuning), quais os NFRs (latência, custo, disponibilidade) e quais os riscos mitigados. Abaixo um exemplo completo baseado em caso real de empresa financeira.

SDD — SISTEMA DE ANÁLISE DE CRÉDITO INTELIGENTE
Agente Autônomo: Análise e Aprovação de Crédito Pessoal
Versão 1.2 · Autor: Time de Dados · Status: Aprovado
Problema de Negócio
Analistas levam 45 min/processo de crédito manual. Meta: automatizar 70% dos casos de baixo risco em <60 segundos com aprovação >95% de acurácia vs. decisão humana.
Padrão Arquitetural Escolhido
Bedrock Agent + RAG + Guardrails — descartados: Fine-Tuning (dados mudam mensalmente), LLM puro (sem acesso a dados em tempo real).
NFRs (Non-Functional Requirements)
NFR Target Como Medido Mitigação se Falhar
Latência p95 < 8 segundos CloudWatch p95 por invoke_agent Ativar Prompt Caching, reduzir K do RAG de 8→4
Custo/Análise < R$ 0,15 Tokens × preço modelId (Haiku para SQL, Sonnet para decisão) Trocar decisão para Haiku 3.5 se custo exceder threshold
Disponibilidade 99.5% Alarme CloudWatch + fallback manual Cross-Region Inference Profile (us-east-1 → us-west-2)
Acurácia decisão > 95% vs. humano A/B test: 30% → humano, 70% → agente (shadow) Human-in-the-loop para casos limite (score 500-650)
Compliance BACEN 100% Audit trail completo em S3 (CloudTrail + Bedrock trace) Bloquear automação, escalar para comitê de risco
Stack de Componentes
ORQUESTRAÇÃO
Bedrock Agents (ReAct, Claude 3.5 Sonnet v2)
RAG / MEMÓRIA
Bedrock KB + OpenSearch Serverless
FERRAMENTAS
Lambda (Athena + Serasa API + Score Engine)
SEGURANÇA
Bedrock Guardrails (PII mask + topic deny)
OBSERVAB.
CloudWatch + Bedrock trace + RAGAS eval
CUSTO/MÊS
~$800 (10k análises/mês, Haiku+Sonnet mix)
Riscos e Mitigações
Risco: Alucinação em score de crédito → aprovação indevida
Mitigação: Guardrails grounding check + regra hard-coded: score < 300 sempre REPROVADO no código Lambda (não passa pelo LLM)
Risco: Latência > 8s em pico (Black Friday)
Mitigação: Prompt Caching para system prompt (~90% hit rate), Cross-Region Profile para desviar throttling
Risco: Custo explodindo com usuários abusando perguntas fora do escopo
Mitigação: Topic deny no Guardrail + rate limiting por userId na Lambda de entrada + CloudWatch alarm em $budget/dia
