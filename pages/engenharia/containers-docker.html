01

Fundamentos: Docker & Containers

Isolamento, Cgroups, Namespaces e o fim do "Na minha máquina funciona"

Um container é uma unidade de software empacotada com todas as suas dependências — código, runtime, bibliotecas do sistema e configurações — para que o aplicativo seja executado de forma rápida e confiável em qualquer ambiente. Diferente de máquinas virtuais (VMs) que emulam o hardware completo e possuem um SO próprio (Guest OS) pesado, os containers compartilham o kernel do sistema operacional host, sendo infinitamente mais leves e rápidos de inicializar.

Cgroups & Namespaces

O isolamento em containers Linux baseia-se em dois recursos principais do kernel: Namespaces isolam o que o processo consegue "ver" (IDs de processo, rede, pontos de montagem), enquanto Cgroups (Control Groups) limitam o que o processo consegue "usar" (CPU, Memória, I/O de disco). Se o processo tentar usar mais memória que o estipulado no cgroup, ocorrerá um OOMKilled (Out Of Memory).

Imagens vs Containers

Uma Imagem Docker é um template estático, construído em camadas read-only (Layered File System). Um Container é a instância em execução dessa imagem, possuindo uma camada adicional read-write temporária. O Dockerfile é a receita ("As Code") para criar essa imagem.

Boas Práticas de Dockerfile para Dados (Python)

Imagens analíticas costumam ser pesadas devido às bibliotecas (Pandas, Numpy, PyArrow). Use Multi-stage builds para não carregar compiladores (gcc) para a imagem de produção e aproveite o cache das camadas instalando dependências antes de copiar o código-fonte.

# Estágio 1: Builder
FROM python:3.9-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# Estágio 2: Produção (Runner)
FROM python:3.9-slim
WORKDIR /app
# Copia apenas as bibliotecas já compiladas
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "etl_pipeline.py"]

Ecossistema de Containers na AWS

Registry (ECR), Orquestração (ECS vs EKS) e Compute (EC2 vs Fargate)

Na AWS, a execução de containers se divide em três grandes frentes: Onde armazenar as imagens, quem vai orquestrar a frota de containers, e qual o hardware (compute) subjacente.

Registry
Amazon ECR
Elastic Container Registry: É o repositório privado da AWS onde suas imagens Docker ficam armazenadas. Suporta versionamento por tags, integração direta com IAM e varredura nativa (Scanning) para detectar vulnerabilidades CVE nas imagens antes do deploy.
Orquestração
Amazon ECS vs EKS
O ECS (Elastic Container Service) é o orquestrador nativo da AWS. É extremamente simples, integrado (CloudWatch, IAM, ALB) e tem baixa carga operacional. O EKS (Elastic Kubernetes Service) é o Kubernetes gerenciado; é agnóstico de nuvem, rico em features (Helm, Service Mesh), mas com uma curva de aprendizado e overhead de gestão maiores.
Compute
EC2 vs AWS Fargate
No modo EC2, você gerencia as máquinas virtuais (clusters) onde os containers rodam, otimizando custos com Spot Instances. O Fargate é o modelo Serverless de compute; a AWS provisiona o hardware dinamicamente por container. Você não gerencia servidores, focando 100% no desenvolvimento de tarefas (Tasks).

Containers na Engenharia de Dados & AI

Desacoplamento e reprodutibilidade com Glue, EMR, MWAA e SageMaker

A Engenharia de Dados moderna abandonou clusters estáticos instalados "na mão". A padronização via containers permite que equipes Data Ops entreguem produtos de dados com controle absoluto de versão.

  • AWS Glue Custom Visuals / Custom Images: O AWS Glue permite fornecer sua própria imagem Docker. Isso é essencial quando o seu job PySpark precisa de dependências pesadas de C++ (ex: bibliotecas geoespaciais avançadas, conectores proprietários C/C++ de mainframes) que não podem ser empacotadas via ZIP/Wheel tradicional devido ao limite de tamanho ou compilação local.
  • EMR on EKS (Spark no Kubernetes): Desacopla completamente a camada de armazenamento (S3) e de execução. Em vez de provisionar um cluster EMR longo e ocioso, jobs Spark são submetidos como Pods num cluster Kubernetes centralizado. Usa Pod Templates para garantir que o Driver rode em instâncias On-Demand (Garantia de Resiliência) e os milhares de Executors rodem em instâncias Spot (70% desconto).
  • Amazon MWAA (Managed Airflow) & ECS Operator: O Airflow não deve ser usado como motor de processamento pesado. O padrão de arquitetura correta é usar o ECSOperator. O Airflow envia o gatilho, e o processamento de Extração pesada (Crawlers customizados) roda de forma isolada em um container no ECS Fargate, não derrubando o scheduler do Airflow.
  • AWS Batch para Pipelines de Imagens/Genômica: Processamento assíncrono massivo otimizado para jobs não-Spark. Lê metadados de uma fila SQS e orquestra containers ECS/EKS transparentemente para processamento pesado em GPU.
  • AWS Lambda com Imagens de Container: O limite histórico do pacote ZIP do Lambda era de 250MB. Ao usar Imagens de Container armazenadas no ECR, o Lambda passa a suportar pacotes de até 10 GB! Padrão ouro para deploy de inferência de modelos Serverless que exigem as pesadíssimas bibliotecas TensorFlow ou PyTorch.
  • Amazon SageMaker Custom Containers: Para treinar modelos proprietários que não se encaixam nos frameworks built-in (SKLearn, XGBoost), cientistas de dados constroem uma imagem Docker customizada aderente ao contrato de APIs do SageMaker (escrevendo e lendo dos diretórios padronizados em /opt/ml/) e as publicam no ECR.

Workflow do Desenvolvedor: Compose & Makefile

Orquestrando localmente e automatizando builds

Em projetos reais de Engenharia de Dados, você raramente digita comandos docker run gigantescos no terminal. Utilizamos ferramentas auxiliares para documentar e orquestrar a execução local.

Docker Compose

O docker-compose.yml é usado para subir múltiplos containers que se comunicam. Exemplo: subir o Apache Airflow localmente ou um banco PostgreSQL junto com uma ferramenta de ingestão.

docker-compose.yml
version: '3.8'
services:
  postgres:
    image: postgres:14
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: datalake_meta
    ports:
      - "5432:5432"

  pyspark_env:
    build: .
    volumes:
      - ./scripts:/app/scripts
    depends_on:
      - postgres

Makefile para Dados

Engenheiros de software usam make para automatizar rotinas. Em dados, é extremamente útil para não ter que decorar as strings de conexão e os builds do Docker.

Makefile
IMAGE_NAME = my_data_pipeline:latest
AWS_ACCOUNT_ID = 123456789012
REGION = us-east-1

build:
	docker build -t $(IMAGE_NAME) .

run-local:
	docker run --env-file .env -v $(PWD)/data:/app/data $(IMAGE_NAME) python main.py

push-ecr: build
	aws ecr get-login-password --region $(REGION) | docker login --username AWS --password-stdin $(AWS_ACCOUNT_ID).dkr.ecr.$(REGION).amazonaws.com
	docker tag $(IMAGE_NAME) $(AWS_ACCOUNT_ID).dkr.ecr.$(REGION).amazonaws.com/$(IMAGE_NAME)
	docker push $(AWS_ACCOUNT_ID).dkr.ecr.$(REGION).amazonaws.com/$(IMAGE_NAME)

Templates AWS: EMR Serverless & Glue

Trazendo sua própria imagem (BYOC) para ambientes Serverless

Historicamente, gerenciar dependências no Glue e EMR (arquivos , bootstrap actions) era um pesadelo (causando conflitos de C++ e bibliotecas compiladas). A solução definitiva da AWS foi liberar o suporte a Custom Docker Images nestes motores.

Custom Image
AWS Glue BYOC
Você compila a imagem a partir da imagem base da AWS (amazon/aws-glue-libs:glue_3.0_ast_20220601) instalando suas bibliotecas Pandas/Numpy específicas via pip install ou conda, e envia pro ECR. O Job do Glue então aponta para essa imagem no momento do run.
Serverless Container
EMR Serverless Image
No EMR Serverless, você empacota seu código PySpark e todas as dependências nativas (como binários em C++) usando a imagem base do EMR. Isso garante tempos de spin-up muito menores comparados à instalação via shell script no startup.

Boas Práticas Extremos: Imagens Seguras e Leves

Multi-stage Builds e Cache de Camadas em Alta Performance

Escrever um Dockerfile que simplesmente funciona é fácil. Escrever um que seja rápido de fazer *Build*, leve para baixar e seguro contra ataques é a marca de um Especialista.

Layer Caching
Copiando Requisitos Primeiro
O Docker armazena cada linha do seu Dockerfile em uma camada. Se você copiar o código fonte antes do requirements.txt, qualquer mudança em um script forçará o recarregamento de todas as bibliotecas. Copie dependências primeiro!
Multi-Stage Build
Redução de Tamanho
Você compila bibliotecas em C (como Numpy ou Pandas) em um container "Builder" pesando 2GB e depois copia apenas os binários para a imagem final "Runner", que pesará 300MB.
Security
Usuário Non-Root
Nunca rode processos dentro do container como (UID 0). Crie um usuário dedicado (ex: ). Isso impede que invasões comprometam o Host Linux subjacente.
Dockerfile - Engenharia de Dados (Multi-stage)
# ESTÁGIO 1: Builder (Pesado, com compiladores C++)
FROM python:3.9-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN apt-get update && apt-get install -y gcc     && pip install --user -r requirements.txt

# ESTÁGIO 2: Runner (Leve, apenas para execução)
FROM python:3.9-slim
WORKDIR /app

# Criação do usuário Non-Root por segurança
RUN useradd -m appuser
USER appuser

# Copia apenas as bibliotecas já compiladas do estágio anterior
COPY --from=builder /root/.local /home/appuser/.local
ENV PATH="/home/appuser/.local/bin:$PATH"

COPY src/ .
CMD ["python", "main_pipeline.py"]

Cases Reais: Orquestração na AWS (ECS)

O Fim da Máquina Virtual "Zumbi"

ECS Fargate Architecture

Case 1: Migrando Cron Jobs para o ECS Fargate

Cenário: Um banco tinha uma máquina EC2 rodando 15 scripts de extração em Cron Tabs. Frequentemente os scripts conflitavam por falta de memória, a máquina travava de madrugada, e alguém tinha que acordar para reiniciá-la.

A Solução: A equipe transformou cada script em uma Imagem Docker isolada e os enviou para o Amazon ECR. Eles então utilizaram o AWS ECS Fargate (modo Serverless de Containers da AWS) com a configuração Scheduled Task (via Amazon EventBridge).

O Resultado: Agora, cada extração sobe seu próprio micro-computador independente apenas pela duração da execução (por exemplo, 5 minutos), desliga imediatamente após gravar no S3 e economiza custos de ociosidade, além de garantir isolamento de dependências.

VPC Endpoints (O Detalhe Oculto)

Na arquitetura do diagrama acima, observe que o Cluster Fargate reside em uma Private Subnet (sem acesso direto à internet para segurança bancária). Para conseguir fazer o docker pull do ECR de forma privada sem cruzar a internet, configura-se um VPC Endpoint ligando diretamente a rede interna da AWS aos serviços do ECR e S3.
