dbt no Lakehouse

Do caos das dezenas de scripts soltos para a verdadeira Engenharia de Software focada em Dados. Descubra como o dbt orquestra SQL escalável na AWS.

01
O Paradigma Moderno

A Ascensão do Analytics Engineer

Antigamente, as regras de negócios ficavam espalhadas em Views no banco, procedures pesadas ou em infinitos jobs do Spark (Python/Scala). Com a escalabilidade da nuvem (Data Warehouses e Lakehouses), processar SQL pesado deixou de ser o problema. O problema passou a ser: Como versionar, testar e orquestrar centenas de queries SQL com dependências complexas? O dbt preencheu essa lacuna.

Tudo é SQL

O dbt utiliza Jinja para injetar lógica dentro do SQL padrão. Se você sabe SQL e Jinja, você pode construir pipelines inteiros sem tocar em Python.

Linhagem Dinâmica

Ao usar a função {{ ref('modelo_base') }}, o dbt entende quem depende de quem. Ele compila um DAG automaticamente.

Testes e Docs

Defina testes no YAML (unique, not_null). O dbt gera documentação e roda testes de qualidade antes de inserir o dado.

02
Engrenagens

Modelagem e Materializações

Uma materialização define como a sua query será compilada e executada no banco alvo. No universo Iceberg + Athena, o dbt-athena (adaptador) traduz essas instruções.

View (Camada Bronze)

Cria apenas uma "lente" em cima dos dados crus. Não consome storage.

{{ config(materialized='view') }}

Table (Camada Silver)

Salva o resultado fisicamente (Drop/Create em todo refresh).

{{ config(materialized='table') }}

A Joia da Coroa: incremental

{{
  config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='transacao_id',
    table_type='iceberg'
  )
}}

WITH raw_data AS (
    SELECT id AS transacao_id, amount, created_at
    FROM {{ ref('raw_pagamentos') }}
)

SELECT * FROM raw_data
{% if is_incremental() %}
  WHERE created_at >= (SELECT MAX(created_at) FROM {{ this }})
{% endif %}
03
Beyond Modeling

Seeds & Snapshots (SCD2)

Além de processar SQL pesado, o dbt resolve dois problemas clássicos da engenharia de dados com comandos nativos impressionantes:

dbt seed (Tabelas Estáticas)

Esqueça a criação de scripts Python apenas para subir uma tabela "De/Para" (ex: mapeamento de CEPs, Feriados Nacionais). Você coloca um arquivo CSV na pasta data/ do seu projeto, roda dbt seed, e ele cria e popula a tabela no Data Warehouse automaticamente, permitindo usar {{ ref('feriados') }} em suas queries.

dbt snapshot (SCD Type 2)

Como você guarda o histórico de mudanças de uma tabela transacional (ex: um cliente mudou de plano Basic para Premium)? O dbt automatiza o Slowly Changing Dimension Type 2. Ele captura as mudanças e cria colunas dbt_valid_from e dbt_valid_to no banco alvo, apenas com um bloco de configuração Jinja!

04
Data Quality

Testes de Qualidade Nativos

O dbt inverte a lógica tradicional: você não testa os dados DEPOIS que eles quebram o dashboard. Você testa os dados DURANTE o pipeline, abortando a execução se algo estiver errado (Fail-Fast).

schema.yml (Testes Genéricos) YAML 
version: 2
models:
  - name: dim_clientes
    columns:
      - name: cpf
        tests:
          - unique
          - not_null
      - name: status_conta
        tests:
          - accepted_values:
              values: ['ativo', 'cancelado']
tests/assert_saldo_positivo.sql SQL (Teste Singular) 
-- Testes singulares em SQL devem retornar as linhas que FALHARAM.
-- Se a query retornar 0 linhas, o teste passou.

SELECT
    conta_id,
    saldo_atual
FROM {{ ref('fct_saldos') }}
WHERE saldo_atual < 0
05
DRY (Don't Repeat Yourself)

O Poder das Macros e Jinja

Um dos maiores problemas do SQL purista é a repetição de código. Se você precisa anonimizar PII (Personal Identifiable Information) como CPF em 50 tabelas, você repetiria a mesma regra 50 vezes. Com o dbt, você usa Macros (funções em Jinja) para encapsular regras de negócio complexas.

macros/mask_cpf.sql Jinja Macro 
{% macro mask_cpf(column_name) %}
    REGEXP_REPLACE({{ column_name }}, '^[0-9]{3}\.[0-9]{3}\.[0-9]{3}', '***.***.***')
{% endmacro %}
models/silver/stg_clientes.sql dbt SQL 
SELECT
    id_cliente,
    nome,
    {{ mask_cpf('documento_cpf') }} AS cpf_mascarado,
    data_cadastro
FROM {{ ref('raw_clientes') }}
06
Observabilidade

Linhagem de Dados (Lineage DAG)

Graças à função {{ ref('modelo') }}, o dbt entende exatamente quem depende de quem e constrói o DAG (Directed Acyclic Graph) automaticamente. Se a tabela Source quebrar ou atrasar, o dbt sabe e pode impedir que os Dashboards lá na ponta consumam dados inconsistentes.

07
System Design

Orquestrando dbt com Amazon Athena

O dbt não processa dados. Ele apenas compila o SQL e submete para um Compute Engine. Na AWS, o parceiro ideal para processamento serverless no S3 é o Amazon Athena integrado ao Apache Iceberg.

08
Estudo de Caso

Refatorando 3.000 linhas de Stored Procedures

O Problema: Uma grande Fintech processava o fechamento contábil rodando Stored Procedures massivas de 3.000 linhas no Redshift. Era impossível testar pedaços menores do código e, quando o pipeline falhava, levava horas de engenharia para debugar qual sub-select exato causou a falha.

Quebra em Modelos Menores

O monólito de 3.000 linhas foi quebrado em 15 arquivos dbt (modelos) muito menores. Cada pedaço se transformou em uma View intermediária na camada Silver. Agora, o código é testável, modularizado e versionado no Git como um software de verdade.

Testes Automáticos (Fail Fast)

Foi adicionado um teste customizado de sum(credito) = sum(debito) entre as camadas. Se o balanço não fechar perfeitamente no meio do pipeline, o dbt alerta e aborta a execução antes de popular a tabela final (Gold), salvando a contabilidade de emitir reports errados para auditorias.
