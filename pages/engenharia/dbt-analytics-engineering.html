dbt no Lakehouse

Do caos das dezenas de scripts soltos para a verdadeira Engenharia de Software focada em Dados. Descubra como o dbt orquestra SQL escalável na AWS.

01
O Paradigma Moderno

A Ascensão do Analytics Engineer

Antigamente, as regras de negócios ficavam espalhadas em Views no banco, procedures pesadas ou em infinitos jobs do Spark (Python/Scala). Com a escalabilidade da nuvem (Data Warehouses e Lakehouses), processar SQL pesado deixou de ser o problema. O problema passou a ser: Como versionar, testar e orquestrar centenas de queries SQL com dependências complexas? O dbt preencheu essa lacuna.

Tudo é SQL

O dbt utiliza Jinja para injetar lógica dentro do SQL padrão. Se você sabe SQL e Jinja, você pode construir pipelines inteiros sem tocar em Python.

Linhagem Dinâmica

Ao usar a função {{ ref('modelo_base') }}, o dbt entende quem depende de quem. Ele compila um DAG automaticamente.

Testes e Docs

Defina testes no YAML (unique, not_null). O dbt gera documentação e roda testes de qualidade antes de inserir o dado.

02
System Design

Orquestrando dbt com Amazon Athena

O dbt não processa dados. Ele apenas compila o SQL e submete para um Compute Engine. Na AWS, o parceiro ideal para processamento serverless no S3 é o Amazon Athena integrado ao Apache Iceberg.

Modelagem e Materializações

Uma materialização define como a sua query será compilada e executada no banco alvo. No universo Iceberg + Athena, o dbt-athena (adaptador) traduz essas instruções.

View (Camada Bronze)

Cria apenas uma "lente" em cima dos dados crus. Não consome storage.

{{ config(materialized='view') }}

Table (Camada Silver)

Salva o resultado fisicamente (Drop/Create em todo refresh).

{{ config(materialized='table') }}

05. DRY (Don't Repeat Yourself)

O Poder das Macros e Jinja

Um dos maiores problemas do SQL purista é a repetição de código. Se você precisa anonimizar PII (Personal Identifiable Information) como CPF em 50 tabelas, você repetiria a mesma regra 50 vezes. Com o dbt, você usa Macros (funções em Jinja).

macros/mask_cpf.sql Jinja Macro
{% macro mask_cpf(column_name) %} REGEXP_REPLACE({{ column_name }}, '^[0-9]{3}\.[0-9]{3}\.[0-9]{3}', '***.***.***') {% endmacro %}

E no seu modelo, você apenas chama a macro:

models/silver/stg_clientes.sql dbt SQL
SELECT id_cliente, nome, {{ mask_cpf('documento_cpf') }} AS cpf_mascarado, data_cadastro FROM {{ ref('raw_clientes') }}

07. Estudo de Caso

Case Real: Refatoração de 3.000 linhas de Stored Procedures

O Problema: Uma grande Fintech processava o fechamento contábil rodando Stored Procedures de 3.000 linhas no Redshift. Era impossível testar pedaços do código. Quando dava erro, levava horas para debugar qual sub-select falhou.

A Solução com dbt:

🔪 Quebra em CTEs Físicas

O monólito de 3.000 linhas foi quebrado em 15 arquivos menores (modelos). Cada pedaço se transformou em uma View intermediária na camada Silver, testável e auditável.

✅ Testes Automáticos

Foi adicionado um teste de sum(credito) = sum(debito) entre as camadas. O dbt alertava falhas antes mesmo de popular a tabela final (Gold), salvando a contabilidade de reportar erros.
