01

Engenharia de Prompting Avançada

Como garantir que o LLM responda exatamente no formato (JSON/XML) que o seu pipeline de dados precisa.

A Engenharia de Prompt não é sobre "saber falar com o robô de um jeito educado". Em pipelines corporativos automatizados, é sobre Design de Instrução Estruturada. Para obtermos respostas determinísticas, estruturadas e reproduzíveis, aplicamos as seguintes metodologias consolidadas:

Comportamento
Atribuição de Persona
Em vez de perguntar diretamente, defina o papel do LLM: "Você é um Engenheiro de Dados Sênior especialista em Apache Spark...". Isso ajusta os vetores probabilísticos do modelo para o jargão técnico, filtrando explicações leigas e garantindo que o código gerado utilize boas práticas do mercado.
Instrução
Few-Shot Prompting
Consiste em injetar 2 ou 3 exemplos explícitos de entrada vs saída diretamente no prompt (geralmente usando tags <exemplo>). Isso ensina o modelo a responder num formato exato (ex: um JSON com chaves específicas) sem a necessidade de re-treinamento (fine-tuning) na infraestrutura.
Raciocínio
Chain-of-Thought (CoT)
Ao forçar o modelo a "pensar em voz alta" antes de responder (usando a tag <thinking>), nós literalmente expandimos os cálculos probabilísticos dele. Isso melhora drasticamente a precisão matemática e lógica, pois ele estrutura o problema passo a passo antes de emitir a resposta definitiva.

O Padrão ReAct (Reason + Action)

LLMs tradicionais são passivos: recebem um texto e retornam um texto. Agentes Autônomos (como Amazon Bedrock Agents) são ativos. Eles utilizam o padrão ReAct para se transformarem em orquestradores capazes de realizar ações no mundo real.

O ciclo ReAct funciona através de um loop contínuo:

  1. Reason (Pensar): O modelo recebe o objetivo ("Quero saber se houve anomalia nas vendas de hoje"). Ele deduz: "Para saber as vendas de hoje, preciso acessar o banco de dados."
  2. Action (Agir): O modelo invoca uma ferramenta (Tool/Action Group) externa. Na AWS, isso geralmente é uma Função Lambda que o modelo dispara via API passando parâmetros (ex: query_sales(date='today')).
  3. Observation (Observar): A Lambda roda no Redshift/Athena e retorna o resultado para o modelo.
  4. Repetição: O modelo pensa sobre o resultado recebido. Se o resultado indicar uma anomalia, ele toma uma nova ação (ex: acionar a tool de envio de e-mail). Se terminou, ele formula a resposta final para o usuário.

Isso é o que permite criarmos "Data Analysts Virtuais" dentro do Slack da empresa, capazes de rodar queries no Data Lake, cruzar dados com planilhas de metas, e gerar gráficos em tempo real.

02

Bedrock Agents na Prática — Action Groups e boto3

Como criar, configurar e invocar um Agente autônomo na AWS com ferramentas reais (Lambda + OpenAPI).

Um Bedrock Agent é composto por três peças: o Foundation Model (cérebro), um ou mais Action Groups (conjunto de ferramentas definidas em OpenAPI) e, opcionalmente, uma Knowledge Base (memória semântica). O agente orquestra tudo autonomamente usando o loop ReAct.

Foundation Model
Raciocínio (ReAct)
Claude 3.5 Sonnet raciocina sobre o objetivo, decide qual ferramenta chamar e em qual ordem. Suporta multi-turn com histórico de conversação automático via sessionId.
Action Group
Ferramentas (OpenAPI)
Cada ferramenta é descrita por um schema OpenAPI 3.0 e executada por uma função Lambda. O agente lê o schema para saber quais parâmetros passar e o que esperar de retorno.
Knowledge Base
Memória Semântica (RAG)
O agente consulta automaticamente a KB antes de raciocinar. Nenhum código extra: basta associar a KB ao agente no console ou via boto3 knowledgeBases.
Session State
Memória de Sessão
O sessionState permite injetar variáveis de contexto (promptSessionAttributes) e arquivos de resultado (files) diretamente no raciocínio do agente sem re-treinar nada.

Criando um Agente com Action Group via boto3

O fluxo completo de criação tem 4 etapas: criar o agente, criar o action group com o schema OpenAPI, preparar (compilar) o agente e criar um alias para invocação. O schema OpenAPI vive em S3.

import boto3, json

bedrock_agent = boto3.client('bedrock-agent', region_name='us-east-1')

# 1. Criar o agente
agent = bedrock_agent.create_agent(
    agentName='data-analyst-agent',
    agentResourceRoleArn='arn:aws:iam::123456789012:role/BedrockAgentRole',
    foundationModel='anthropic.claude-3-5-sonnet-20241022-v2:0',
    instruction="""Você é um analista de dados sênior. Use as ferramentas disponíveis
    para responder perguntas sobre vendas, anomalias e métricas de negócio.
    Sempre execute queries antes de responder — nunca invente números.""",
    idleSessionTTLInSeconds=3600
)
agent_id = agent['agent']['agentId']

# 2. Associar Action Group com schema OpenAPI no S3
bedrock_agent.create_agent_action_group(
    agentId=agent_id,
    agentVersion='DRAFT',
    actionGroupName='DataQueryTools',
    actionGroupExecutor={
        'lambda': 'arn:aws:lambda:us-east-1:123456789012:function:DataAgentTools'
    },
    apiSchema={
        's3': {
            's3BucketName': 'my-agent-schemas',
            's3ObjectKey': 'data-agent-openapi.json'
        }
    },
    description='Ferramentas: query_athena, get_anomalies, list_tables'
)

# 3. Preparar (compilar) o agente
bedrock_agent.prepare_agent(agentId=agent_id)

# 4. Criar alias de produção
alias = bedrock_agent.create_agent_alias(
    agentId=agent_id,
    agentAliasName='prod-v1'
)
alias_id = alias['agentAlias']['agentAliasId']
print(f"Agent pronto: {agent_id} / Alias: {alias_id}")

Schema OpenAPI da Ferramenta (data-agent-openapi.json)

O schema define as ferramentas que o agente pode chamar. Cada operationId vira um botão que o LLM pode pressionar. A descrição é o que o modelo usa para decidir quando usar a ferramenta.

  "paths": {
    "/query_athena": {
      "post": {
        "operationId": "query_athena",
        "description": "Executa uma query SQL no Amazon Athena sobre o Data Lake. Use para responder perguntas numéricas sobre vendas, clientes e produtos.",
        "requestBody": {
          "content": {
            "application/json": {
              "schema": {
                "type": "object",
                "properties": {
                  "sql_query": { "type": "string", "description": "Query SQL válida no dialeto do Athena/Presto" },
                  "database": { "type": "string", "description": "Nome do database no Glue Catalog" }
                },
                "required": ["sql_query", "database"]
              }
            }
          }
        }
      }
    },
    "/get_anomalies": {
      "post": {
        "operationId": "get_anomalies",
        "description": "Detecta anomalias estatísticas em uma métrica para um período dado. Usa SageMaker RCF internamente.",
        "requestBody": {
          "content": { "application/json": { "schema": { "type": "object",
            "properties": {
              "metric_name": { "type": "string" },
              "start_date": { "type": "string", "description": "ISO 8601 date" },
              "end_date": { "type": "string" }

Invocando o Agente (invoke_agent)

bedrock_agent_runtime = boto3.client('bedrock-agent-runtime', region_name='us-east-1')

def invoke_data_agent(question: str, session_id: str) -> str:
    response = bedrock_agent_runtime.invoke_agent(
        agentId='ABCDEF1234',
        agentAliasId='TSTALIASID',
        sessionId=session_id,
        inputText=question,
        # Injeta variáveis de contexto sem mudar o prompt base
        sessionState={
            'promptSessionAttributes': {
                'user_role': 'data_analyst',
                'default_database': 'sales_gold'
            }
        },
        enableTrace=True  # Retorna trace do ReAct loop para debug
    )

    # A resposta é um EventStream (streaming)
    full_response = ""
    for event in response['completion']:
        if 'chunk' in event:
            full_response += event['chunk']['bytes'].decode()
        elif 'trace' in event:
            trace = event['trace']['trace']
            if 'orchestrationTrace' in trace:
                orch = trace['orchestrationTrace']
                if 'invocationInput' in orch:
                    print(f"🔧 Tool chamada: {orch['invocationInput']}")
    return full_response

# Uso
resposta = invoke_data_agent(
    question="Houve alguma anomalia nas vendas esta semana? Se sim, qual região foi impactada?",
    session_id="sessao-usuario-123"
)
print(resposta)

Multi-Agent: Padrão Supervisor + Subagentes

Como orquestrar múltiplos agentes especializados sob um agente supervisor — o padrão mais robusto para automação corporativa.

Um único agente com muitas ferramentas fica lento e comete mais erros — o modelo perde foco. O padrão Supervisor + Subagentes divide responsabilidades: um agente mestre recebe a tarefa de alto nível e delega para agentes especialistas (SQL Agent, Anomaly Agent, Report Agent). O Bedrock suporta isso nativamente com o tipo de Action Group AGENT_COLLABORATOR.

Supervisor
Orquestrador Mestre
Recebe o objetivo final do usuário, decompõe em subtarefas e delega para subagentes. Agrega os resultados e gera a resposta consolidada. Tem pouquíssimas ferramentas diretas.
Subagente SQL
Especialista em Dados
Tem acesso apenas às tools de query: query_athena, query_redshift, list_tables. Sem acesso a envio de e-mail ou criação de relatório — princípio do menor privilégio.
Subagente Report
Gerador de Artefatos
Recebe dados estruturados e tem tools de criação: generate_pdf, send_email_ses, upload_to_s3. Nunca acessa o banco de dados diretamente.
# Associar um subagente ao supervisor via AGENT_COLLABORATOR
bedrock_agent.create_agent_action_group(
    agentId=supervisor_agent_id,
    agentVersion='DRAFT',
    actionGroupName='SQLSpecialist',
    actionGroupExecutor={
        'customControl': 'RETURN_CONTROL'  # Supervisor decide quando delegar
    },
    agentCollaborator={                     # Tipo especial: outro agente
        'agentId': sql_subagent_id,
        'agentAliasId': sql_alias_id,
        'collaboratorName': 'SQLSpecialist',
        'collaborationInstruction': "Especialista em queries SQL. Chame-o quando precisar de dados quantitativos do Data Lake."
    }
)

# O supervisor agora pode "chamar" o SQL agent como se fosse uma tool
# O Bedrock gerencia o handoff e retorno de contexto automaticamente

## Exemplo de trace: Supervisor → SQL Agent → Athena → Volta ao Supervisor
## 1. User: "Qual o faturamento por região esta semana?"
## 2. Supervisor THOUGHT: "Preciso de dados → vou chamar SQLSpecialist"
## 3. SQLSpecialist ACTION: query_athena("SELECT region, SUM(revenue) ...")
## 4. SQLSpecialist OBSERVATION: {"SP": 1200000, "RJ": 800000, ...}
## 5. Supervisor ANSWER: "SP liderou com R$1.2M (60% do total)..."

Few-Shot Prompting com Exemplos Estruturados (Claude XML)

Para tarefas de geração de código ou SQL, few-shot prompting com exemplos explícitos em tags XML reduz drasticamente erros de formato:

def nl_to_sql(natural_language_query: str, schema_context: str) -> str:
    prompt = f"""Você é um especialista em SQL para Amazon Athena (Presto).
Converta a pergunta em linguagem natural para SQL válido.

<regras>
- Use apenas as tabelas e colunas listadas no schema
- Sempre inclua LIMIT 1000 em queries sem GROUP BY
- Datas no formato 'YYYY-MM-DD'
- Nunca use subconsultas quando JOIN resolve
</regras>

<schema>
{schema_context}
</schema>

<exemplo>
<pergunta>Qual o total de vendas por produto este mês?</pergunta>
<sql>
SELECT produto_id, produto_nome, SUM(valor_venda) AS total_vendas
FROM sales_gold.fato_vendas
WHERE DATE(dt_venda) BETWEEN DATE_TRUNC('month', CURRENT_DATE) AND CURRENT_DATE
GROUP BY 1, 2
ORDER BY total_vendas DESC
LIMIT 100
</sql>
</exemplo>

<pergunta>{natural_language_query}</pergunta>

Responda apenas com o bloco <sql>...</sql>."""

    bedrock = boto3.client('bedrock-runtime', region_name='us-east-1')
    resp = bedrock.converse(
        modelId='anthropic.claude-3-5-haiku-20241022-v1:0',  # Haiku: mais barato p/ SQL
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"temperature": 0.0, "maxTokens": 500}
    )
    raw = resp['output']['message']['content'][0]['text']
    # Extrai apenas o SQL da tag
    import re
    match = re.search(r'<sql>(.*?)</sql>', raw, re.DOTALL)
    return match.group(1).strip() if match else raw
