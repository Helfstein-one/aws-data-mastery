ELT, SaaS & AWS Zero-ETL

Por que processar dados em voo com clusters pesados se você pode carregar dados brutos nativamente e processar via SQL?

01
O Paradigma

ETL Clássico vs ELT Moderno

Com storage barato (S3) e compute escalável (Athena/Redshift), a transformação mudou para o final do pipeline.

O Passado (ETL)

  • Transformação Externa: Ocorria em memória (Spark/Glue) antes de salvar o dado.
  • Fragilidade: Se a regra de negócio mudasse, você perdia o dado original e precisava extrair da fonte de novo.
  • Código Complexo: Dependia fortemente de Scala/Python e dezenas de scripts.

O Moderno (ELT)

  • Transformação no Destino: Joga o dado cru no DW (Redshift/Snowflake) e transforma via SQL.
  • Resiliência: Se a regra de negócio mudar, basta rodar a query SQL de novo no dado cru que já está salvo.
  • Acessibilidade: Qualquer Analista que sabe SQL (dbt) pode criar pipelines de ponta a ponta.
02
SaaS Ingestion

Airbyte & Fivetran

Antes, para extrair dados do Salesforce ou do Zendesk, equipes inteiras mantinham scripts Python usando a biblioteca `requests`, lidando manualmente com paginação, backoff exponencial, tokens de autenticação expirados e limites de taxa (rate limiting).

Conectores Gerenciados

Ferramentas como Fivetran (pago) e Airbyte (open-source) trazem centenas de conectores nativos. Você insere suas credenciais de API, e eles assumem a responsabilidade de manter o dado sincronizado no seu Data Warehouse ou Lakehouse de forma incremental.

Normalização Automática

A maioria das APIs retorna JSONs profundamente aninhados. O Airbyte/Fivetran "achata" (unnest) esses JSONs automaticamente em tabelas relacionais ou colunares (Parquet) na camada Bronze/Raw, facilitando a vida do Engenheiro.

03
AWS Innovations

AWS Zero-ETL

O futuro dos dados transacionais não tem pipelines de extração.

Aurora to Redshift

O Aurora não replica o banco lendo os dados, ele replica no nível de blocos de armazenamento físico (storage volume) direto para o cluster Redshift em segundos. Zero impacto de performance no banco transacional e fim dos lambdas e Kinesis Streams intermediários.

DynamoDB to OpenSearch

Dados injetados no DynamoDB (NoSQL) são instantaneamente indexados num cluster Amazon OpenSearch para buscas complexas em Full-Text. Tudo isso como uma funcionalidade "Point-and-Click" da AWS, sem escrever uma única linha de código.

Insight Arquitetural: O AWS Zero-ETL mata a categoria de "Engenharia de Transporte de Dados". Ao invés de você perder noites escrevendo Lambdas para sincronizar bancos, a AWS faz a ponte física na camada de hardware do data center, para você focar 100% nas regras de negócio da sua empresa.
04
Under the Hood

Change Data Capture (CDC)

Tanto as ferramentas modernas de ELT (Airbyte) quanto o AWS Zero-ETL não ficam rodando "SELECT * FROM tabela" de hora em hora. Isso mataria o banco de produção. Eles utilizam CDC (Change Data Capture), lendo diretamente os arquivos físicos de log do banco de dados (WAL no PostgreSQL, Binlog no MySQL).

05
Prática Analítica

Consumindo Zero-ETL no Redshift

Na AWS, quando você cria uma integração Zero-ETL entre um cluster Aurora MySQL e o Redshift, você não escreve um pipeline. Você apenas aceita a integração e cria um banco de dados federado no Redshift.

Redshift Query Editor SQL 
-- 1. Cria o banco de dados no Redshift apontando para o identificador da integração Zero-ETL
CREATE DATABASE my_aurora_integration 
FROM INTEGRATION 'arn:aws:rds:us-east-1:123456789012:integration:11111-2222-3333-4444';

-- 2. Imediatamente (com segundos de delay), você pode consultar os dados do Aurora VIVOS!
SELECT 
    u.country,
    COUNT(o.order_id) AS total_orders,
    SUM(o.amount) AS total_revenue
FROM my_aurora_integration.sales_db.users u
JOIN my_aurora_integration.sales_db.orders o ON u.id = o.user_id
WHERE o.created_at > CURRENT_DATE - INTERVAL '7 days'
GROUP BY 1;
06
Estudo de Caso

Migração de APIs para Fivetran

O Problema: Uma startup de e-commerce mantinha 40 scripts em Lambda (Python) para baixar dados do Zendesk, Shopify, Facebook Ads e Google Analytics. Eles gastavam 60% do tempo dos engenheiros consertando os scripts porque as APIs de origem mudavam constantemente ou quebravam por Rate Limiting.

A Solução ELT:

Fim do Código Customizado

Todos os 40 scripts foram deletados. Eles configuraram conectores do Fivetran/Airbyte que nativamente lidam com paginação, backoff e rate limits das APIs. Os dados crus foram jogados diretamente no Snowflake/Redshift.

Transformação no DW

Os Engenheiros de Dados passaram a atuar como Analytics Engineers, usando o dbt (SQL) dentro do Redshift para tratar os JSONs sujos do Zendesk e juntar com os dados do Shopify, agregando valor imediato ao negócio.
