Garbage Collection & Heap Tuning

Otimização de pausas Stop-The-World e JVM Tuning avançado

Configurações para Garbage Collector G1

O G1GC divide a memória Heap da JVM em pequenas regiões e analisa qual região possui maior volume de dados inúteis para liberar primeiro, evitando a suspensão de threads executores.

spark.executor.extraJavaOptions =
  -XX:+UseG1GC
  -XX:InitiatingHeapOccupancyPercent=35
  -XX:G1HeapRegionSize=16m
  -verbose:gc -XX:+PrintGCDetails

Identificação de gargalos de GC no Spark UI

Analise a coluna GC Time no Executors Tab: Se o tempo de GC superar 10% do tempo de processamento total, você deve aumentar a memória dos executores ou reduzir o paralelismo local diminuindo cores.

Shuffle, Skew, Salting e Pandas UDFs

Resolução de gargalos causados por desbalanceamento em joins e otimização de UDFs com Apache Arrow

O Data Skew (desvio de dados) ocorre quando uma chave específica acumula mais de 80% do volume físico dos dados (ex: chaves nulas ou registros de auditoria padrão). O executor encarregado por processar essa chave demorará muito mais tempo que os demais, deixando os cores ociosos e estendendo a duração do estágio.

🔍 Como Diagnosticar Skew no Spark UI

Navegue até a aba Stages, selecione o estágio problemático lento e abra a seção Task Metrics (Stage Details):

  • Métrica Duration: Ordene as tarefas pela coluna Duration. Se o tempo da task no P95 / Max for superior a 5x a mediana, há indicativo claro de desvio (Skew).
  • Shuffle Read Size: Verifique a distribuição do tamanho de leitura de shuffle por task. Task com leitura muito maior que a média aponta skew na chave de junção.

⚙️ Otimização Automática: AQE (Spark 3.x+)

Configure os parâmetros abaixo no `spark-defaults` para permitir que o Catalyst divida dinamicamente partições assimétricas:

spark.sql.adaptive.enabled = true
spark.sql.adaptive.skewJoin.enabled = true
spark.sql.adaptive.coalescePartitions.enabled = true

1. Otimização via Salting (Distribuição de Chave no Join)

A técnica de Salting resolve o skew adicionando um sufixo numérico aleatório (o "sal") às chaves da tabela gigante e explodindo a tabela menor correspondente para conter todas as combinações desse sal, distribuindo os registros de forma uniforme pelos executores durante o shuffle:

import pyspark.sql.functions as F
n_salts = 50  # Fator de salting (número de partições paralelas para dividir o skew)

# Tabela principal com skew: adiciona salt aleatório (0 a n_salts-1)
df_large_salted = df_large.withColumn(
    "salt", (F.rand() * n_salts).cast("int")
).withColumn("salted_key", F.concat(F.col("key"), F.lit("_"), F.col("salt")))

# Tabela de lookup (pequena): explode gerando todas as chaves salgadas possíveis
df_small_exploded = df_small.withColumn(
    "salt", F.explode(F.array([F.lit(i) for i in range(n_salts)]))
).withColumn("salted_key", F.concat(F.col("key"), F.lit("_"), F.col("salt")))

# Executa o join distribuído sem sobrecarregar um único nó (No skew bottleneck)
df_joined = df_large_salted.join(df_small_exploded, "salted_key").drop("salt", "salted_key")

2. Otimização de UDFs com Pandas UDF (Vectorized Arrow)

As UDFs (User Defined Functions) comuns do PySpark forçam a JVM a serializar os dados linha a linha para enviá-los ao interpretador Python, gerando uma sobrecarga severa e possíveis OOMs na User Memory. As Pandas UDFs otimizam esse processo transferindo dados em blocos (batches) usando o Apache Arrow diretamente na memória:

import pandas as pd
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import DoubleType

# Ativa o Apache Arrow para otimização de conversão
# spark.conf.set("spark.sql.execution.arrow.pyspark.enabled", "true")

# Pandas UDF Vectorized usando type hints do Python
@pandas_udf(DoubleType())
def predict_discount_udf(price: pd.Series, rate: pd.Series) -> pd.Series:
    # Executa a operação vetorizada rápida usando Pandas/NumPy C-extension
    return price * (1.0 - rate)

# Uso da UDF vetorizada no DataFrame do Spark
df_processed = df_sales.withColumn(
    "final_price", 
    predict_discount_udf(F.col("base_price"), F.col("tax_rate"))
)
# Execução extremamente veloz e segura contra estouro de memória!
06.5

Funções Avançadas de API PySpark & Otimização

Higher-Order Functions (HOFs), Bloom Filters, Window Functions de alto desempenho e Exemplos de Código Baseados em Cores

As funções nativas do PySpark (disponíveis em pyspark.sql.functions) são implementadas em Scala/Java no backend e executadas diretamente no nível da JVM do Executor. Elas se beneficiam do Catalyst Optimizer (para colapsar expressões) e do Tungsten Engine (geração de código e alocação de memória direta). Isso significa que elas são drasticamente mais rápidas e eficientes em termos de memória do que as funções definidas pelo usuário (UDFs) em Python regular. Sempre dê preferência à API nativa do PySpark.

Higher-Order Functions (HOFs) em Arrays

Evite o uso de F.explode() seguido de F.groupBy(), pois isso duplica os dados em memória e gera shuffles desnecessários. Use HOFs para manipular arrays diretamente no executor:

# Filtrar elementos de um array sem explode
df.withColumn("active_users", F.expr("filter(users_array, x -> x.status == 'active')"))

# Transformar elementos do array em tempo real
df.withColumn("prices_with_tax", F.expr("transform(prices_array, p -> p * 1.10)"))

Bloom Filters para Otimização de Busca

Em vez de varrer petabytes de dados procurando uma chave específica, um Bloom Filter cria uma estrutura probabilística mínima na memória que testa a presença do dado (sem falsos negativos). Útil antes de joins pesados:

# Cria o Bloom filter da tabela de anomalias (muito pequena)
bf = df_anomalies.stat.bloomFilter("user_id", expectedNumItems=1000, fpp=0.01)

# Filtra a tabela massiva ANTES do join (Filter Pushdown aprimorado)
df_massive_filtered = df_massive.filter(F.col("user_id").might_contain(bf))

Otimização de Window Functions: rangeBetween vs rowsBetween

A especificação física do Frame da Window Function muda drasticamente o consumo computacional:

  • rangeBetween (Padrão): Agrupa dados baseando-se no valor da chave de ordenação. O Spark mantém na memória todos os registros atrelados àquele valor lógico, podendo causar picos de uso da Execution Memory se houverem milhares de registros com o mesmo valor (Data Skew na partição da window).
  • rowsBetween (Performance Otimizada): Usa a posição física da linha, independentemente do valor da chave. A alocação de memória do executor é perfeitamente previsível (ex: os últimos 10 registros lidos fisicamente). Use sempre que a regra de negócio permitir contagem posicional no lugar da contagem por valor.

Dica de Debugging e Testes com Exemplos Simples (Cores)

Para testar e depurar lógicas complexas sem depender de clusters caros, crie conjuntos de dados (DataFrames) mínimos na memória. A abordagem visual com "cores" facilita o rastreamento lógico do agrupamento e ordenação (Window Functions):

from pyspark.sql import SparkSession
from pyspark.sql.window import Window
import pyspark.sql.functions as F

spark = SparkSession.builder.appName("DebugLocal").getOrCreate()

# Criação de um DataFrame mínimo para depurar a lógica
data = [
    ("Vermelho", "Carro", 100),
    ("Vermelho", "Moto", 50),
    ("Azul", "Carro", 120),
    ("Azul", "Bicicleta", 30),
    ("Verde", "Caminhão", 500)
]
df_colors = spark.createDataFrame(data, ["Cor", "Veículo", "Preço"])

# 1. Definindo a Window particionada pela Cor
window_spec = Window.partitionBy("Cor").orderBy(F.desc("Preço"))

# 2. Aplicando funções avançadas usando a API PySpark nativa
# Função row_number() numera as linhas dentro de cada partição de cor
df_ranked = df_colors \
    .withColumn("Rank", F.row_number().over(window_spec)) \
    .withColumn("Preco_Maximo_Cor", F.max("Preço").over(window_spec.rangeBetween(Window.unboundedPreceding, Window.unboundedFollowing)))

df_ranked.show()
# Dica de Debugging: Use .explain(True) para ver o plano físico gerado
# df_ranked.explain(True) # Mostra o Sort, Window, e Projection no plano físico.

Tuning da API estruturada do PySpark: Práticas de Performance

Abaixo estão descritas as principais boas práticas e armadilhas ao utilizar as projeções e transformações do PySpark no dia a dia:

Operação / Abordagem Padrão Recomendado (Best Practice) Padrão Evitado (Anti-Pattern) Impacto Físico de Performance
Múltiplas Projeções df.select(F.col("a"), F.col("b") + 1, F.col("c") * 2) (Usa uma única etapa de projeção no Catalyst). Enfileirar sucessivos .withColumn("b", F.col("b") + 1).withColumn("c", F.col("c") * 2). StackOverflowException: Cada withColumn adiciona um nó projetivo recursivo no plano lógico do Spark. Se você encadear mais de 20-30 withColumn, a análise do Catalyst falha estourando a pilha de chamadas da JVM.
Namespaces e Duplicidades Fazer alias explícito dos DataFrames locais antes do Join: df_esq.alias("esq").join(df_dir.alias("dir"), "id"), referenciando depois como F.col("esq.valor"). Tentar resolver ambiguidades renomeando colunas duplicadas manualmente com listas posicionais pós-join. Ambiguous Column Exception: Referenciar F.col("id") após um join onde ambos os lados possuem uma coluna chamada "id" causa falha em runtime. O Spark perde a linhagem física do ponteiro da coluna se não houver alias explícito.
Unificação de DataFrames df_a.unionByName(df_b, allowMissingColumns=True) df_a.union(df_b) Corrupção Silenciosa de Dados: O union() padrão do Spark faz a união puramente posicional. Se o schema da tabela A for [nome, idade] e a tabela B for [idade, nome], o Spark mesclará as colunas invertidas sem emitir alertas. O unionByName valida e alinha as colunas pelos nomes lógicos.
Camadas de Abstração SQL Manipular o DataFrame de forma encadeada via API Funcional (DataFrame API). Abusar de createOrReplaceTempView("minha_view") e escrever blocos massivos de SQL em string dentro de spark.sql(). Perda de Rastreamento de Erros e Tipagem: Embora o Catalyst compile ambos para o mesmo plano físico final, strings SQL impedem IDEs de fazer linting estático de colunas e erros de sintaxe, além de mascarar a árvore de dependência de linhagem (lineage) no código.

Dicionário Avançado de Funções Nativas do PySpark (`pyspark.sql.functions`)

Todas as funções nativas abaixo rodam diretamente em código compilado na JVM do Spark, eliminando 100% da necessidade de UDFs Python tradicionais:

1. Funções Base, Seleção & Expressões
  • col(nome_coluna): Cria uma referência lógica para a coluna física de um DataFrame. Permite operações tipadas avançadas.
  • expr(expressao_sql): Faz o parse de um trecho de sintaxe SQL clássica e compila em uma coluna PySpark estruturada. Excelente para operações matemáticas rápidas.
  • array(*cols): Concatena múltiplos campos isolados de uma linha em uma estrutura de dados do tipo Array.
# Exemplo Prático de col(), expr() e array() em um único select()
df_final = df_colors.select(
    F.col("Cor"),
    F.expr("Preço * 1.10").alias("Preco_Com_Imposto"),
    F.array(F.col("Veículo"), F.col("Cor")).alias("Metadados_Veiculo")
)
2. Manipulação Avançada de Strings
  • concat(*cols): Concatena strings físicas de colunas sem delimitadores.
  • substring(col, start, len): Recorta uma string baseando-se em índices numéricos físicos (1-indexed).
  • regexp_replace(col, pattern, replacement): Utiliza expressões regulares (Regex) nativas em Java/JVM para limpar e substituir caracteres complexos.
  • lower() / upper() / trim(): Normalizações clássicas de espaçamento e caixa de caracteres.
# Exemplo Prático de limpeza de strings
df_limpo = df.select(
    F.concat(F.col("codigo_pais"), F.col("telefone")).alias("numero_completo"),
    F.substring(F.col("data_string"), 1, 4).alias("ano_extraido"),
    F.regexp_replace(F.col("texto"), r"[^a-zA-Z0-9 ]", "").alias("texto_alfanumerico"),
    F.lower(F.trim(F.col("nome_usuario"))).alias("username_normalizado")
)
3. Coleções Complexas (Arrays e Maps)
  • explode(col): Desmembra uma linha contendo um Array/Map em múltiplas linhas (uma linha por elemento). *Cuidado de Performance:* Gera duplicação de dados nas outras colunas e força re-particionamentos se mal posicionado.
  • array_contains(col, value): Retorna um boolean testando se o valor reside no array.
  • map_keys() / map_values(): Extraem chaves ou valores de estruturas chave-valor (Maps) em forma de array.
  • element_at(col, index): Obtém elemento em índice do array ou valor da chave do map de forma segura (retorna nulo se não existir, sem quebrar o job).
  • flatten(col): Transforma um array bidimensional (`Array[Array[T]]`) em um array plano unidimensional (`Array[T]`).
  • array_join(col, delimiter): Concatena todos os elementos do array em uma única string usando o delimitador.
# Exemplo Prático de manipulação de coleções complexas
df_colecoes = df.select(
    F.explode(F.col("itens_carrinho")).alias("item_carrinho"),
    F.array_contains(F.col("tags_tags"), "VIP").alias("is_vip"),
    F.element_at(F.col("mapa_propriedades"), "cor_favorita").alias("cor_usuario"),
    F.flatten(F.col("arrays_aninhados")).alias("array_plano"),
    F.array_join(F.col("historico_cidades"), " -> ").alias("linha_tempo_cidades")
)
4. Operações Temporais (Datas)
  • to_date(col, format): Converte uma string formatada em uma coluna de data real estruturada.
  • date_add(col, days): Adiciona dias corridos a uma data analítica.
  • datediff(end, start): Calcula a distância exata em dias entre duas colunas temporais.
  • months_between(end, start): Retorna a diferença fracionária de meses entre datas.
  • current_date(): Injeta a data corrente do sistema nos nós executores.
  • date_format(col, format): Converte uma data física em string seguindo padrão de renderização.
# Exemplo Prático de data
df_data = df.select(
    F.to_date(F.col("data_texto"), "yyyy-MM-dd").alias("data_efetiva"),
    F.date_add(F.col("data_venda"), 30).alias("vencimento_fatura"),
    F.datediff(F.current_date(), F.col("data_cadastro")).alias("dias_de_fidelidade"),
    F.date_format(F.col("data_entrega"), "EEEE, MMMM yyyy").alias("data_formatada_extensa")
)
5. Lógicas Condicionais e Segurança
  • when(condition, value) / otherwise(value): A estrutura condicional recomendada do Catalyst (Case/When).
  • coalesce(*cols): Retorna a primeira coluna que não possuir valor nulo dentro da lista informada. Muito mais rápido que condicionais when().otherwise() para tratamento de nulos.
  • hash(*cols): Gera um hash de 32 bits (MurmurHash3) sobre os valores passados. Excelente para criar chaves substitutas rápidas ou hashes de validação de qualidade sem custo de criptografia pesada (SHA-256).
# Exemplo Prático de condicionais e tratamento de nulos
df_seguro = df.select(
    F.when(F.col("score") > 700, "Aprovado")
     .when(F.col("score") >= 500, "Em Analise")
     .otherwise("Reprovado").alias("status_analise"),
    F.coalesce(F.col("telefone_celular"), F.col("telefone_residencial"), F.lit("Sem Contato")).alias("contato_principal"),
    F.hash(F.col("id_cliente"), F.col("data_nascimento")).alias("chave_surrogate_cliente")
)
6. Janelas (Window Functions) e Agregações
  • row_number(): Numeração sequencial contínua da linha dentro do frame da janela.
  • rank() / dense_rank(): Classificações ordenadas. O dense_rank não pula números sequenciais na classificação caso ocorram empates de valores.
  • lead(col, offset) / lag(col, offset): Acessam registros de linhas posteriores ou anteriores à linha física corrente dentro da janela, permitindo cálculos de deltas de tempo/valores sem fazer Joins caros.
  • countDistinct(*cols): Agregação agregadora de contagem de valores únicos de forma distribuída.
# Exemplo Prático de Window Functions e Agregações
from pyspark.sql.window import Window

window_cliente = Window.partitionBy("id_cliente").orderBy("data_transacao")

df_analitico = df.select(
    F.col("id_cliente"),
    F.col("valor_transacao"),
    F.row_number().over(window_cliente).alias("numero_transacao_cliente"),
    F.dense_rank().over(window_cliente).alias("rank_densificado"),
    (F.col("valor_transacao") - F.lag("valor_transacao", 1).over(window_cliente)).alias("dias_desde_ultima_transacao"),
    F.lead("valor_transacao", 1).over(window_cliente).alias("valor_proxima_transacao")
)

Debugging Avançado de Partições Físicas no PySpark

Em processamento analítico distribuído, ter partições com tamanhos assimétricos (Data Skew) faz com que um único executor Spark execute 90% do trabalho enquanto o restante fica ocioso. Para debugar de forma vasta o estado das partições de um DataFrame, utilize a inspeção de RDDs e metadados no Spark Submit:

Código de Diagnóstico de Particionamento (Physical Partition Inspection):
Cole o código abaixo no console ou registre no log de execução de homologação para diagnosticar o número e tamanho de cada partição do DataFrame na RAM: 
# 1. Obtém a quantidade física de partições alocadas no cluster
num_particoes = df.rdd.getNumPartitions()
print(f"Total de Particoes Fisicas: {num_particoes}")

# 2. Glom() agrupa os registros de cada partição em uma lista local
# Mapeia e coleta a quantidade de registros residentes em cada partição individual
distribuicao_particoes = df.rdd.glom().map(len).collect()

for part_idx, count in enumerate(distribuicao_particoes):
    print(f"Particao [{part_idx}]: {count} registros")

# 3. Calcula métricas de assimetria (Skewness)
max_count = max(distribuicao_particoes)
min_count = min(distribuicao_particoes)
avg_count = sum(distribuicao_particoes) / len(distribuicao_particoes)
print(f"Max: {max_count} | Min: {min_count} | Avg: {avg_count}")
print(f"Skew Ratio (Max / Avg): {max_count / avg_count:.2f}x (Valores > 1.5x indicam assimetria severa!)")

Dinâmica de Escrita: Cálculo de Partições e Sizing no S3

Estratégias matemáticas de particionamento (repartition vs coalesce) para combater o Small Files Problem no Data Lake

Escrever dados no S3 de forma ingênua (usando partições originadas de shuffles arbitrários) é a causa número um do Small Files Problem. Milhares de arquivos minúsculos (ex: 2KB) destroem a performance do S3 (estourando cotas de requisição de API GET/PUT) e arruínam a latência do Athena/Redshift, que precisam abrir e fechar conexões de metadados para cada arquivo. O tamanho ideal alvo por arquivo colunar (Parquet/Iceberg) no S3 deve ser entre 128 MB e 256 MB.

repartition(N)

Causa um Shuffle completo na rede (Caro). Ele espalha os dados perfeitamente de forma uniforme (Round-Robin) por todos os executores. Use sempre antes de gravações grandes no S3 para garantir que todas as partições de saída tenham exatamente o mesmo tamanho em Megabytes, prevenindo Skew Files.

coalesce(N)

Não causa Shuffle (Barato). Ele apenas "funde" partições locais na memória do nó executor. Perigo Fetal: Chamar coalesce(10) logo após um read() encolhe o paralelismo lógico do cluster para 10 slots de CPU instantaneamente, deixando centenas de cores ociosos durante o resto do processamento!

Implementação: Cálculo Dinâmico de Sizing para Escrita

Hardcodar partições (ex: df.repartition(200)) é um erro crasso. Se a volumetria de dados crescer no Natal, os arquivos gerados serão de 2GB (lentos de processar). Se a volumetria cair, gerarão 200 arquivos minúsculos. A solução é calcular a volumetria dinamicamente no final da DAG:

import pyspark.sql.functions as F
from pyspark.sql import DataFrame

def write_optimized_lake_table(df: DataFrame, s3_path: str, target_size_mb: int = 128):
    # 1. Obtém o número total de linhas do DataFrame final
    # Obs: Se já houver um count() prévio cacheado no job, use-o para evitar re-scan.
    total_rows = df.count()
    if total_rows == 0:
        return

    # 2. Estimativa heurística pesando o tamanho da linha serializada (ex: 200 bytes por linha)
    # Em produção, um sample de 1% do df pode determinar o tamanho médio dinâmico em Bytes.
    bytes_per_row = 150 
    
    # 3. Calcula o volume total estimado e determina o número de arquivos (partições) exatos
    total_size_mb = (total_rows * bytes_per_row) / (1024 * 1024)
    ideal_partitions = max(1, int(total_size_mb / target_size_mb))
    
    print(f"Escrevendo {total_size_mb:.2f} MB distribuídos em {ideal_partitions} arquivos parquet de ~{target_size_mb} MB")

    # 4. Redistribui uniformemente e grava no S3
    df.repartition(ideal_partitions) \
      .write \
      .mode("overwrite") \
      .format("parquet") \
      .save(s3_path)

# Chamada do pipeline final
write_optimized_lake_table(df_vendas_finais, "s3://meu-lake/silver/vendas/")
Alternativa do Motor do Spark (Auto Sizing): Em ambientes com EMR 6.x+ ou AWS Glue, você pode delegar o limite de registros do arquivo ao Catalyst definindo spark.sql.files.maxRecordsPerFile = 1000000 na configuração do cluster. Isso forçará o writer a "fechar" o arquivo parquet e abrir um novo assim que bater 1 milhão de linhas, independentemente das partições em RAM.

Estratégias Físicas de Join no Spark

Mapeamento profundo de cruzamentos analíticos em nível de rede, memória e disco

Diferente de bancos de dados relacionais em um único servidor, um Join Distribuído no Spark é a operação mais custosa que existe, pois exige que dados relacionados que estão espalhados em dezenas de servidores (Executors) trafeguem pela rede para a mesma máquina a fim de serem cruzados. O Catalyst Optimizer escolhe automaticamente entre três algoritmos físicos principais, baseando-se no tamanho (em bytes) estimado das tabelas.

Broadcast Hash Join (BHJ)
✓ Sem Shuffle de Rede Pesado
Copia a tabela inteira e envia para todos os executores na memória. Elimina totalmente o embaralhamento de chaves na rede. Padrão Ouro para Dimensões.
Sort-Merge Join (SMJ)
Forte Shuffle
Lê, faz o Hash, trafega pela rede, Ordena (Sort) no disco local e depois mescla os ponteiros iterativamente. Extremamente robusto para cruzamentos Massivos x Massivos.
Shuffle Hash Join (SHJ)
Shuffle & RAM Pesada
Distribui e mapeia os blocos via Rede e constrói HashMaps parciais na memória. Usado quando a tabela menor é maior que o broadcast, mas caberá num bucket hash isolado de um único executor.
DIAGRAMA 1: BROADCAST HASH JOIN (Ouro para Tabelas Menores)
Mecânica do Broadcast Hash Join: O Spark ignora o terrível particionamento de rede. O Driver pega a tabela menor (até 10MB default), monta um dicionário HashMap no Driver e envia uma cópia idêntica (Broadcast) para a RAM de cada um dos executores do cluster. Assim, a tabela Fato de Terabytes sofre join sem trafegar pela rede.
DIAGRAMA 2: SORT-MERGE JOIN (O Padrão para Tabelas Massivas)
Mecânica do Sort-Merge Join (SMJ): Esse é o rei do processamento Big Data de petabytes. Como as tabelas A e B não cabem em memória isolada, ambas sofrem Exchange/Shuffle pela rede para caírem no exato mesmo executor baseado no valor do hash da chave. Após a chegada de ambas as metades (Data Skew é crítico aqui!), se estourar a RAM, o Spark faz Spill para o disco EBS, ordena iterativamente (Sort) ambos os lados da chave e finalmente avança simultaneamente mesclando ponteiros lado-a-lado (Merge). Lento, mas resiliente a quebras de nó.
DIAGRAMA 3: SHUFFLE HASH JOIN (Intermediário em RAM)
Mecânica do Shuffle Hash Join (SHJ): Idêntico ao SMJ na brutalidade da fase de Shuffle (trafegando tudo). A diferença é que não perde I/O com a fase de *Sort*. O lado Menor da partição do Join constrói um Hash Map em memória na partição isolada do executor. Se houver desbalanço (Skew) ou o tamanho da tabela menor ultrapassar a RAM Task-local disponível, resultará fatalmente em `OutOfMemoryError (OOM)` travando seu pipeline. O Catalyst (no AQE) prevê isso e faz fallback para SMJ, por isso o SHJ costuma estar em desuso sem um override manual ou auto-tune severo.
Algoritmo de Join Mecânica de Funcionamento Interno Sensibilidade a Data Skew Quando Usar / Forçar no Código
Broadcast Hash Join (BHJ) O Driver puxa a tabela pequena (Dimensão), cria uma tabela Hash (Chave/Valor) na memória JVM e empurra via rede uma cópia exata para a RAM de cada executor que possui pedaços da tabela gigante. As tarefas vasculham a Hash localmente, sem embaralhar a tabela gigante pela rede. Baixa. Como o dado cruza localmente em memória, se uma chave pesada existir na tabela gigante, ela não vai travar um único executor aguardando transferências. Tabelas menores que 10MB (Default configurado via spark.sql.autoBroadcastJoinThreshold). Para forçar: df1.join(F.broadcast(df_small), "id"). Cuidado com OOM no Driver se a tabela crescer subitamente.
Sort-Merge Join (SMJ)
  1. Shuffle Phase: Avalia as chaves de ambas as tabelas gigantes. Usa partições Hash e move os registros pela rede para que chaves idênticas de ambas as tabelas caiam no exato mesmo nó.
  2. Sort Phase: Se a memória encher (inevitável em Petabytes), salva os dados temporários no disco local (Spill) e Ordena os registros em cada partição por chave.
  3. Merge Phase: Escaneia os dois conjuntos ordenados iterativamente lado a lado usando ponteiros combinando-os.
 Extrema. Se o cliente ID=99 for a "Amazon" e possuir 10 bilhões de registros de vendas, todos os 10 bilhões irão para a rede em direção ao mesmo executor singular. Esse executor fará "Spill to Disk" constante, travando por 10 horas enquanto os outros 199 executores terminam em 1 minuto. O SMJ é o rei indiscutível para cruzar Tabelas Fato x Fato (Massivo x Massivo). É ativado por padrão se o Spark deduzir que ambas são grandes. Exige alta capacidade de I/O em discos temporários EBS (gp3/NVMe) dos nós Worker.
Shuffle Hash Join (SHJ) Semelhante ao SMJ, faz o Shuffle de ambas as tabelas para mapeá-las fisicamente na rede por chave. Contudo, ele pula a etapa de Sort e simplesmente cria Tabelas Hash em memória na partição para a menor tabela. É OOM na certa se a tabela for muito maior que a RAM do executor alocado para aquela partição. Alta. Mesmos problemas do SMJ no shuffle, mas falhará abruptamente (OOM) em vez de gravar no disco lentamente (como faz o Sort-Merge) porque não faz Spill da árvore de chaves. Ideal quando a tabela é grande demais para caber inteira no Driver (abortando o Broadcast), mas depois de shufflada, as partições resultantes cabem tranquilamente na memória de um Executor sem dar Spill. O Catalyst do Spark 3 com AQE costuma migrar para SMJ automaticamente se pressentir falta de RAM.
⚠️ Warning Especialista: Cartesian / Cross Joins e a Explosão de RAM

Um join sem critério de filtro claro ou usando predicados não equitativos (ex: df1.join(df2, df1.data > df2.data)) não consegue aplicar os algoritmos baseados em Hash. O Spark degrada a performance para um Broadcast Nested Loop Join (BNLJ) ou, pior, lança uma exceção pedindo ao usuário que autorize o produto cartesiano spark.sql.crossJoin.enabled=true. Um Cross Join O(N*M) entre duas tabelas de 10 milhões de linhas tentará processar 100 Trilhões de combinações, aniquilando qualquer cluster Cloud instantaneamente.

Guia Definitivo: DataFrame API & Boas Práticas

Como escrever código PySpark sustentável, de alta performance e legível

A DataFrame API é a espinha dorsal do PySpark moderno. Diferente dos antigos RDDs, o DataFrame se beneficia do Catalyst Optimizer, construindo um plano lógico de execução que otimiza agregações e joins por baixo dos panos. Abaixo estão os padrões cruciais para engenharia de dados.

Evite Encadeamento Infinito (Chaining): Embora seja possível encadear 20 .withColumn(), isso estoura a pilha de recursão do Java e destrói o Lineage do Spark, gerando StackOverflowErrors no driver. Use a função .select() com expressões múltiplas sempre que possível.
python 
# ❌ Anti-Pattern: Chaining excessivo e recálculo
df_bad = df \
    .withColumn("ano", F.year("data_venda")) \
    .withColumn("mes", F.month("data_venda")) \
    .withColumn("dia", F.dayofmonth("data_venda")) \
    .withColumn("total_com_imposto", F.col("valor") * 1.15)

# ✅ Best Practice: Projeção única e limpa
df_good = df.select(
    "*",
    F.year("data_venda").alias("ano"),
    F.month("data_venda").alias("mes"),
    F.dayofmonth("data_venda").alias("dia"),
    (F.col("valor") * 1.15).alias("total_com_imposto")
)

Trade-offs: DataFrame API vs Spark SQL
  • Vantagem do DataFrame API: Verificação de sintaxe em tempo de compilação (IDE aponta o erro de digitação), facilidade de modularização, passagem de parâmetros dinâmicos de forma elegante sem concatenar strings propensas a SQL Injection.

  • Melhor Prática: Utilize DataFrame API para ingestão, leitura, partições dinâmicas e tipagem estrita de colunas. Utilize Spark SQL para agregações complexas de negócios que mudam frequentemente, encapsuladas em blocos configuráveis (ou dbt).

Níveis de Persistência de Dados (Cache & Persist)

Comparativo físico de cacheamento e níveis de persistência para reutilização de DataFrames

MEMORY_ONLY
Acesso veloz direto em RAM (deserializado).
Recalcula se faltar memória (alto risco de GC se o DF for gigante).
MEMORY_AND_DISK
Resiliente. Sem perda ou recálculo de dados.
Escrita lenta em disco quando os dados transbordam da RAM.
MEMORY_ONLY_SER
Extremamente compacto (salva como array de bytes na RAM).
Exige processamento de CPU extra para serializar/deserializar.
DISK_ONLY
Sem qualquer pressão sobre a RAM da Heap JVM.
Acesso muito lento devido ao I/O físico de leitura do disco.
MEMORY_AND_DISK_SER
Melhor balanço para produção de larga escala.
Custo médio de processamento de CPU para serializar.
OFF_HEAP
Bypass de GC. Gerenciado diretamente pelo Tungsten na RAM do S.O.
Requer habilitar spark.memory.offHeap.enabled = true e alocação prévia.
Tradeoff Avançado de Produção (Serialization & GC): O uso padrão do DataFrame API (df.cache()) mapeia para MEMORY_AND_DISK. Se o DataFrame tiver 50GB descompactados, ele inundará a Heap da JVM, acionando o Garbage Collector a todo instante (Stop-The-World), travando todos os cores. Em cenários Staff-Level, recomenda-se explicitamente o uso de df.persist(StorageLevel.MEMORY_AND_DISK_SER) acompanhado da configuração spark.serializer = org.apache.spark.serializer.KryoSerializer no cluster. Isso armazena os dados não como objetos Java dispersos, mas como um bloco binário massivo e coeso, reduzindo a pegada na RAM em até 80% e eliminando a pressão de limpeza do GC, trocando memória por um pequeno gasto de CPU (descompressão).

Tema 1 · Teoria: Window Functions & Sessionization

O Paradigma do Deslocamento Temporal e Construção de Sessões

A Física da Operação: Diferente de um GROUP BY tradicional que comprime (esmaga) milhões de registros em uma única linha (ex: somatório global), uma Window Function permite realizar operações de agregação (Soma, Média) ou navegação (Lag, Lead) mantendo a granularidade original das linhas. O Spark cria "janelas" lógicas deslizantes na memória para cada registro, olhando para trás e para frente num contexto delimitado por uma chave (PARTITION BY) e uma ordenação (ORDER BY). O maior perigo físico aqui é a exceção OutOfMemory (OOM) se uma única janela (ex: um usuário muito ativo) for maior que a RAM de um único executor.

O Problema Prático (Sessionization): Precisamos mapear as jornadas de usuários num site. Se o usuário ficou 30 minutos inativo, consideramos que a sessão antiga "fechou" e qualquer clique futuro abrirá uma "nova sessão". Isso é resolvido rastreando a distância temporal (Gap) entre um clique e o anterior.

Exemplo 1.1: Identificação de Gaps e Sessões (PySpark)
from pyspark.sql import functions as F
from pyspark.sql.window import Window

# 1. Definimos a Janela Particionada por Usuário e Ordenada pelo Tempo Cronológico
w_user_time = Window.partitionBy("user_id").orderBy("event_timestamp")

# 2. LAG: Busca o exato momento do clique anterior. Se for o primeiro clique, retorna NULL.
df_lag = df_events.withColumn("prev_timestamp", F.lag("event_timestamp").over(w_user_time))

# 3. Cálculo do GAP e Flag de Nova Sessão
# Lógica: Se o tempo atual menos o tempo anterior for maior que 1800 segundos (30 min), marcamos com '1' (início).
df_gap = df_lag.withColumn(
    "is_new_session",
    F.when(F.col("prev_timestamp").isNull(), 1)
     .when((F.col("event_timestamp").cast("long") - F.col("prev_timestamp").cast("long")) > 1800, 1)
     .otherwise(0)
)

# 4. Criação do ID único da sessão via SOMA CUMULATIVA
# A janela avança linha a linha desde o início (unboundedPreceding) até a linha atual (currentRow)
w_cumulative = Window.partitionBy("user_id").orderBy("event_timestamp")\
    .rowsBetween(Window.unboundedPreceding, Window.currentRow)

df_sessions = df_gap.withColumn("session_id", F.sum("is_new_session").over(w_cumulative))

# Para gerar um ID Global único, podemos concatenar o usuário com o número da sessão local
df_final = df_sessions.withColumn("global_session_id", F.concat_ws("_", F.col("user_id"), F.col("session_id")))
Exemplo 1.2: A Solução Elegante usando SQL (Trino/Athena/SparkSQL)
WITH lags AS (
  SELECT 
    user_id,
    event_timestamp,
    LAG(event_timestamp) OVER (PARTITION BY user_id ORDER BY event_timestamp) as prev_timestamp
  FROM raw_events
),
flags AS (
  SELECT 
    user_id,
    event_timestamp,
    -- Converte timestamp pra EPOCH (segundos) para achar a diferença de 30 min
    CASE 
      WHEN prev_timestamp IS NULL THEN 1
      WHEN UNIX_TIMESTAMP(event_timestamp) - UNIX_TIMESTAMP(prev_timestamp) > 1800 THEN 1
      ELSE 0
    END as is_new_session
  FROM lags
)
SELECT 
  user_id,
  event_timestamp,
  -- Soma cumulativa atuando como gerador sequencial de IDs de sessão
  SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_timestamp ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) as session_id
FROM flags;
Exemplo 1.3: Running Totals (Faturamento Acumulado) - PySpark

Outro uso comum de Window. Calcule a receita acumulada diária sem agrupar toda a tabela.

w_running = Window.partitionBy("ano_mes").orderBy("data_venda")\
    .rangeBetween(Window.unboundedPreceding, Window.currentRow)
    
df_running = df_faturamento.withColumn(
    "receita_acumulada_mes", 
    F.sum("valor_venda").over(w_running)
)
Tema 2 · Teoria: Parseamento de Estruturas Aninhadas (Complex Types)

Explode, Lateral Views e Navegação em Grafo de JSONs

A Mecânica Estrutural: Dados provenientes de bancos NoSQL (como MongoDB ou DynamoDB) e de APIs modernas não são tabulares (planos). Eles vêm no formato de árvores, com Tipos Complexos do Spark: ArrayType (Listas) e StructType (Objetos aninhados). O processamento analítico (como o envio para um Data Warehouse columnar) exige que essas árvores sejam transformadas em um modelo relacional (Flattening). A operação mais custosa dessa etapa é o explode(), pois ela atua como um multiplicador cartesiano restrito: se um usuário tiver 5 compras num Array, a linha do usuário é duplicada (achatada) em 5 linhas individuais herdando as características da raiz.

Diferença de Performance: O explode() puro ignora a linha raiz se o array estiver vazio ou nulo (Perda de dados). Em pipelines Enterprise, utilizamos estritamente o explode_outer() (ou LEFT JOIN LATERAL) para garantir que um usuário que fez um cadastro mas não comprou nada seja mantido na tabela (ficará com campos nulos nas colunas de compras).

Exemplo 2.1: Achatamento Massivo de Array de Structs (PySpark)
# Imagine o JSON: {"order_id": "123", "items": [{"id": 1, "price": 10}, {"id": 2, "price": 20}]}
# Schema: StructType(StructField("order_id", String), StructField("items", ArrayType(StructType(id, price))))

# Passo 1: Explodir o Array para gerar uma linha por Item, preservando orders sem items (explode_outer)
df_exploded = df_orders.withColumn("item_obj", F.explode_outer("items"))

# Passo 2: Navegar no Struct interno usando notação de ponto (Dot Notation)
df_flat = df_exploded.select(
    F.col("order_id"),
    F.col("item_obj.id").alias("product_id"),
    F.col("item_obj.price").alias("product_price")
)

# Passo 3: Drop do array original super pesado da memória
df_final = df_flat.drop("items", "item_obj")
Exemplo 2.2: O Motor SQL e as Views Laterais (LATERAL VIEW)

O SQL padrão antigo não sabe lidar com Arrays de tamanho variável por linha. O Hive introduziu e o Spark absorveu a sintaxe de exibição lateral, que atua como um cross join da linha com os itens do array da própria linha.

SELECT 
  o.order_id,
  item.id AS product_id,
  item.price AS product_price
FROM raw_orders o
-- EXPLODE_OUTER garante que pedimos LEFT OUTER JOIN, preservando ordens vazias
LATERAL VIEW OUTER explode(o.items) exploded_table AS item;

-- No PostgreSQL ou Athena mais modernos, a sintaxe de desdobramento (UNNEST) é comum:
SELECT 
  o.order_id,
  item.id AS product_id,
  item.price AS product_price
FROM raw_orders o
LEFT JOIN UNNEST(o.items) AS t(item);
Tema 3 · Teoria: Multi-Dimensional Aggregation (Cubes, Rollups, Pivots)

Engenharia de Cubos Analíticos no Motor de Dados

A Ciência da Agregação: Fazer milhares de Group Bys para alimentar um Dashboard gera custos enormes se cada consulta varrer a tabela fato crua. Técnicas avançadas calculam todas as combinações hierárquicas possíveis em uma única varredura dos dados usando os operadores ROLLUP, CUBE, e GROUPING SETS.

  • ROLLUP: Cria subtotais hierárquicos focados (Direcional). Ex: Se você rodar Rollup por (País, Estado, Cidade), ele criará agrupamentos para (País, Estado, Cidade), depois (País, Estado, NULL) que é o total do estado, depois (País, NULL, NULL) que é o total do País, e (NULL, NULL, NULL) que é o total global. Custo de computação linear `N+1`.
  • CUBE: Computa absolutamente todas as permutações cruzadas. Criará os totais do ROLLUP, mas também combinações isoladas como (NULL, Estado, NULL), quebrar por estado independente de país. Custo muito mais pesado `2^N`.
  • PIVOT: Transposição de valores literais de uma coluna-linha para virarem os nomes físicos das colunas. Essencial para transformar séries temporais (uma linha por mês) em colunas tabulares (Jan_Revenue, Feb_Revenue...).
Exemplo 3.1: Construindo Tabelas Dinâmicas Transpostas (PIVOT) em PySpark
# Cenário: Tabela com colunas [Loja, Mes, Faturamento]. Queremos [Loja, Fat_Jan, Fat_Fev, Fat_Mar]

df_pivot = df_vendas.groupBy("loja_id") \
    .pivot("mes", ["Janeiro", "Fevereiro", "Marco", "Abril"]) \
    .agg(
        F.sum("faturamento").alias("total"), 
        F.count("transacoes").alias("qnt_vendas")
    ) \
    .fillna(0) # Remove Nulos de meses que não tiveram venda

# Atenção (Otimização OOM): SEMPRE forneça a lista de valores literais no método pivot([...]). 
# Se você deixar vazio, o Spark fará um "Scan Distribuído Extra" na tabela inteira apenas 
# para descobrir os valores distintos antes de pivotar, dobrando o tempo de processamento.
Exemplo 3.2: O SQL Poderoso para Grouping Sets e Rollup

O SQL moderno permite flexibilidade insana no planejamento de totais parciais e cruzamentos, essencial para materialização rápida do Tableau/PowerBI.

-- Rollup: Hierarquia rígida (Ano -> Mes -> Dia)
SELECT 
  ano, 
  mes, 
  dia, 
  SUM(receita) as faturamento_total
FROM fato_vendas
GROUP BY ROLLUP (ano, mes, dia);

-- Grouping Sets: Total controle de quais "Group Bys" rodar de uma vez só no mesmo Dataset Resultante
SELECT 
  categoria,
  marca,
  regiao,
  SUM(vendas) as total
FROM produtos
GROUP BY GROUPING SETS (
  (categoria, marca),  -- Visão de concorrência por categoria
  (regiao),            -- Visão macro territorial isolada
  ()                   -- Total Global da Tabela
);
Tema 4 · Teoria: Deduplicação Resiliente e Histórico Dimensional (SCD Tipo 2)

Isolando a Verdade Num Mar de Eventos Duplicados

A Raiz do Problema: Sistemas de ingestão como Kafka/Kinesis garantem At-Least-Once Delivery. Portanto, a duplicação no Data Lake é certa. Além disso, quando o status de um pedido muda de "Aguardando" para "Pago" para "Enviado", cada mudança é um evento separado. Como saber a foto atual do pedido sem descartar a história de como ele chegou lá?

Abordamos de duas formas: (A) Deduplicação lógica de última foto mantendo só o mais recente. (B) Criação de uma Tabela Dimensional Slowly Changing Dimension Tipo 2 (SCD-2), que insere controle de vigência usando colunas temporais Data_Inicio_Validade e Data_Fim_Validade (sendo a linha ativa marcada com NULL ou data no infinito 9999-12-31).

Exemplo 4.1: Deduplicação Extremamente Otimizada de Última Foto (PySpark)
# O método .dropDuplicates(["user_id"]) é "Não determinístico" na nuvem (você não escolhe qual linha ele mantém).
# Para manter a linha mais recente com exatidão garantida, usamos row_number().

w_dedup = Window.partitionBy("user_id").orderBy(F.col("update_timestamp").desc())

# Pega o primeiro evento (mais recente) de cada usuário e joga fora o resto.
df_gold_latest = df_silver_events.withColumn("rank", F.row_number().over(w_dedup)) \
    .filter(F.col("rank") == 1) \
    .drop("rank")
Exemplo 4.2: Construção manual do Histórico SCD-2 (Tratando Eventos Históricos)

O lead() olha para o futuro na sua partição, roubando o timestamp do próximo evento para fechar a sua janela atual valid_to.

# Ordenamos os eventos do usuário do mais antigo pro mais novo.
w_hist = Window.partitionBy("pedido_id").orderBy("data_evento")

df_scd2 = df_status_pedidos.withColumn(
    "data_inicio_vigencia", F.col("data_evento")
).withColumn(
    "data_fim_vigencia", F.lead("data_evento", 1).over(w_hist)
).withColumn(
    "is_active", F.when(F.col("data_fim_vigencia").isNull(), True).otherwise(False)
)
Exemplo 4.3: O Motor MERGE (Upsert Lakehouse) em SQL Delta/Iceberg

O paradigma Lakehouse moderno realiza o SCD e o Upsert via ACID transactions em SQL, sem precisar reescrever a tabela inteira (Técnica do Merge on Read/Write).

-- Sincronizando tabela alvo com dados vindos de staging usando UPSERT (Update/Insert)
MERGE INTO gold_users AS target
USING staging_users_cdc AS source
ON target.user_id = source.user_id
WHEN MATCHED AND source.op = 'DELETE' THEN 
  DELETE -- Deleta se a origem informou remoção
WHEN MATCHED AND source.update_timestamp > target.update_timestamp THEN 
  UPDATE SET * -- Atualiza só se a origem for mais recente que o alvo
WHEN NOT MATCHED THEN 
  INSERT * -- Insere o cadastro inteiramente novo
Tema 5 · Teoria: Fuga das UDFs Padrões e Otimização Nativa

Evitando a Morte da Serialização na JVM: Apache Arrow e Expressões Nativas

O Pesadelo da UDF Python: Quando você escreve uma @udf em Python e aplica em um DataFrame, o Spark é obrigado a pausar o processamento ultra-otimizado (C++/Tungsten), serializar a linha via Socket (Pickle), enviar para um processo filho Python, aguardar o processamento monothread lento do Python e retornar. Isso é uma tragédia de performance. Regra #1 da arquitetura Spark: Evite UDFs como se fossem pragas. Use funções nativas. Se precisar interagir com Arrays internamente, use Higher-Order Functions (SQL native lambda functions). Se precisar MUITO de Python (ex: rodar um modelo Scikit-Learn ou cálculo matemático denso), use Pandas UDF que trabalha vetorialmente movendo blocos em memória via Apache Arrow sem serialização ineficiente.

Exemplo 5.1: Operações em Array SEM UDF usando Higher-Order Functions (Spark 2.4+)

Multiplicando todos os números de um array interno do DataFrame sem escrever Python customizado.

# Imagine um DataFrame com uma coluna array_col = [10, 20, 30]

# O método F.transform aplica uma função anônima lambda diretamente no código C++ da engine.
df_dobrado = df.withColumn(
    "array_multiplicado", 
    F.transform("array_col", lambda item: item * 2)
)

# O método F.filter limpa lixo de dentro de um array do DataFrame sem explodir ele.
df_filtrado = df_dobrado.withColumn(
    "array_somente_maior_25",
    F.filter("array_multiplicado", lambda item: item > 25)
)

SELECT 
  id,
  TRANSFORM(array_col, x -> x * 2) as array_multiplicado,
  FILTER(array_col, x -> x > 25) as array_somente_maior_25

Exemplo 5.2: O Refúgio Vetorizado (Pandas UDF Series)

Quando a transformação é impossível de fazer via Spark SQL puro (ex: aplicar modelo de IA nos dados, regex monstruosos, bibliotecas C), usamos o Pandas UDF do tipo SCALAR. O código recebe não uma linha, mas uma pd.Series (coluna do Pandas com 10.000 linhas) em memória Arrow (Zero-Copy) e retorna 10.000 linhas de uma vez.

import pandas as pd
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import StringType

# O decorador informa que a saída é String. 
# Tipagem forte com pandas Series (pd.Series)
@pandas_udf(StringType())
def mascara_cpf_vetorizada_udf(cpf_series: pd.Series) -> pd.Series:
    # A operação string do Pandas é vetorizada (roda compilada em C por baixo)
    # Extrema velocidade substituindo regex linha a linha por operação matricial.
    return cpf_series.str.replace(r'(\d{3})(\d{3})(\d{3})(\d{2})', r'***..-**', regex=True)

# Aplicação simples, como se fosse uma função padrão nativa
df_anonimizado = df_banco.withColumn("cpf_ofuscado", mascara_cpf_vetorizada_udf(F.col("cpf_cru")))
