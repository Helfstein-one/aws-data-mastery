Amazon EMR em Instâncias EC2 (Classic Cluster)

Arquitetura física, controle de custos com Spot/Fleets e gerenciamento de filas de execução YARN

O Amazon EMR (Elastic MapReduce) na versão EC2 é a implantação mais poderosa e flexível do ecossistema Hadoop. Aqui, o usuário possui controle total sobre a infraestrutura física (Sistema Operacional, rede, discos e instâncias AWS), assumindo também o custo operacional de gerenciamento.

5. O Pitch de Business Value (Proposta de Valor)

Utilizar o EMR em EC2 com a estratégia agressiva de "Task Nodes" em instâncias Spot e uso do "Managed Scaling" permite reduzir a conta de OPEX da nuvem em até 80% comparado a clusters Hadoop On-Premise ou clusters puramente On-Demand. Isso transforma custos fixos ociosos em despesas elásticas precisas e destrava o orçamento (FinOps) para inovar em novos produtos de dados.

Arquitetura do Cluster EMR & Guia de Instâncias Master/Core/Task

Topologia física do cluster e tradeoffs entre armazenamento HDFS local vs S3 (EMRFS)

AMAZON EMR — TOPOLOGIA MASTER / CORE / TASK NODES
Explicação:
  • Componentes: MASTER NODE (On-Demand, m5.xlarge), YARN ResourceManager, HDFS NameNode, CORE NODES (On-Demand r5d.2xlarge NVMe), Core 1 e Core 2, HDFS DataNode + YARN NodeManager + Spark Executors, TASK NODES (Spot c5.2xlarge), Task 1 e Task 2, Solo YARN NodeManager + Executors (sem HDFS — Spot safe), S3 / EMRFS, Glue Catalog
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas indicam a direcionalidade entre os elementos do diagrama.
  • Contexto: O diagrama mostra a topologia física do cluster EMR: Master coordena (RM + NameNode), Core Nodes guardam dados HDFS e executam jobs (nunca Spot), Task Nodes apenas processam (sem HDFS — podem ser 100% Spot para economia de até 80% no custo).

Como Funciona & Arquitetura (Guia de Instâncias Master/Core/Task)

O EMR on EC2 permite rodar o ecossistema Hadoop completo. A separação física dos nós permite otimização de custos e performance:

  • Master Node (Coordenação): Orquestra o cluster (HDFS NameNode e YARN ResourceManager). Não faz processamento pesado de dados. Famílias recomendadas: m5.xlarge / m5.2xlarge. Para produção crítica, use 3 Masters para alta disponibilidade (Active-Passive NameNodes).
  • Core Nodes (Dados + CPU): Executam os Daemons HDFS DataNode e executores Spark. Requerem alta performance de disco local e RAM. Famílias recomendadas: r5d.2xlarge / r6gd.2xlarge (o "d" indica NVMe SSD local, ideal para blocos HDFS e shuffle local rápido) ou instâncias i3en/i4g de armazenamento intenso. Nunca use Spot aqui em produção!
  • Task Nodes (Processamento Puro): Não guardam dados HDFS. Apenas rodam executores do YARN/Spark. Famílias recomendadas: c5.2xlarge / c6g.2xlarge (otimizadas para CPU) ou r5.2xlarge se o job exigir mais memória física. Use 100% Spot Instances nos Task Nodes para máxima otimização FinOps.
  • Managed Scaling: Redimensiona o cluster automaticamente em segundos com base em métricas do YARN, muito mais eficiente que o Auto Scaling tradicional do EC2.

Performance & Configurações

  • Instance Fleets: Permite misturar até 30 tipos de instâncias EC2, garantindo que o cluster suba mesmo com baixa disponibilidade de certos tipos de Spot.
  • EMR Runtime: Ativado por padrão nas versões 6.x+, traz otimizações de query e melhor integração com S3 (EMRFS).
  • Configuração via JSON: Permite tunar o `spark-defaults`, `yarn-site` e `capacity-scheduler` diretamente no provisionamento.
  • Graceful Decommissioning: Vital para clusters que utilizam Spot nos Task Nodes. O YARN gerencia o desligamento da instância transferindo dados locais de shuffle antes do nó ser removido, mitigando erros de FetchFailedException.
  • Ajuste de YARN Queues: Utilizando o CapacityScheduler, você pode criar filas lógicas que particionam os recursos do cluster EC2 entre múltiplos pipelines concorrentes.
Configuração de Filas Concorrentes (capacity-scheduler.xml)

Exemplo de tuning de fila YARN para dividir recursos do cluster: 60% para a fila producao e 40% para a fila analistas:

<configuration>
  <property>
    <name>yarn.scheduler.capacity.root.queues</name>
    <value>producao,analistas</value>
  </property>
  <property>
    <name>yarn.scheduler.capacity.root.producao.capacity</name>
    <value>60</value>
  </property>
  <property>
    <name>yarn.scheduler.capacity.root.analistas.capacity</name>
    <value>40</value>
  </property>
  <property>
    <name>yarn.scheduler.capacity.root.producao.maximum-capacity</name>
    <value>100</value>
  </property>
</configuration>

Amazon EMR Serverless: Agilidade e Escala

Dynamic Resource Allocation (DRA) & Decommissioning

O Dynamic Resource Allocation permite que o Spark Serverless encolha e expanda o cluster on-the-fly baseado no tamanho do backlog das partições agendadas no TaskScheduler. O trade-off crítico aqui é o Shuffle Data Loss. Se um executor processar dados de map-side shuffle e for devolvido para a nuvem (scale-in) antes do reduce-side, os dados são perdidos e a stage precisa ser recomputada.

A solução AWS é o Graceful Decommissioning acoplado com um serviço externo de Shuffle (External Shuffle Service), que faz o backup transparente dos dados de embaralhamento antes do desligamento do nó.

Operação sem gerenciamento de servidores com performance de EMR

Como Funciona

O EMR Serverless desacopla o gerenciamento de instâncias da execução do job. Você cria uma "Application" (Spark ou Hive) e submete "Job Runs". Não há S.O. para atualizar e nem instâncias para gerenciar.

  • Pre-initialized Capacity: Mantém um pool de workers "quentes" prontos para processar. Elimina o tempo de boot de 5-10 min do EC2, iniciando o processamento em segundos.
  • Isolamento: Cada Job Run roda em um ambiente isolado, evitando conflitos de bibliotecas ou competição de recursos entre diferentes pipelines.

Performance, Dimensionamento & FinOps (ACUs Sizing)

No EMR Serverless, os custos e recursos são dimensionados em ACUs (Application Capacity Units). Você define limites máximos e recursos por executor Spark:

  • Configuração de Workers: Diferente do Glue, você tem controle granular sobre os recursos de cada worker (ex: 2 vCPU e 16 GB RAM) até limites de 16 vCPU / 120 GB por worker.
  • Fórmula de Cobrança / Sizing:
    Custo = (vCPU_total * Tempo_sec * $/vCPU-hora) + (RAM_total_GB * Tempo_sec * $/GB-hora)
    Boas Práticas de Sizing: Para jobs I/O intensive ou de processamento de texto pesado (ex: parsing JSON complexo), utilize mais vCPU por worker (ex: 4 vCPU e 16 GB RAM). Para Joins e agregações analíticas pesadas (onde ocorre muito spill), utilize mais memória por worker (ex: 2 vCPU e 32 GB RAM).
  • Customização de Disco: É possível configurar o armazenamento efêmero por worker (de 20GB a 200GB), crucial para shuffles pesados.
  • Custom Docker Images: Você pode empacotar bibliotecas Python/C++ complexas no Amazon ECR em uma imagem base customizada, acelerando a inicialização e garantindo isolamento total (multi-tenant).
5. O Pitch de Business Value (Proposta de Valor)

O EMR Serverless remove inteiramente o atrito do "Capacity Planning" e do gerenciamento de patches do ciclo de vida da infraestrutura. A equipe técnica foca 100% no desenvolvimento de pipelines de dados (aumento da produtividade). Com a cobrança precisa por segundo de execução baseada na memória consumida e sem a necessidade de pagar por horas ociosas de clusters ligados 24x7, observamos redução de OPEX imediata para workloads de picos instáveis e sazonais.

Amazon EMR on EKS: Processamento Multi-Tenant

Orquestração de jobs Spark como contêineres nativos no Kubernetes com alta densidade

Como Funciona

O EMR on EKS permite executar aplicativos Apache Spark diretamente em clusters do Amazon Elastic Kubernetes Service (EKS). Diferente do YARN tradicional, o EKS agenda pods (Driver e Executors) no cluster K8s, permitindo rodar workloads analíticos ao lado de microsserviços.

  • Isolamento Multi-Tenant: Jobs de equipes diferentes rodam em namespaces separados.
  • IRSA (IAM Roles for Service Accounts): O EKS injeta permissões granulares via OIDC. Cada job assume uma Role IAM específica, garantindo que o Pod A só acesse o Bucket A, melhorando drasticamente a segurança em relação ao EMR EC2.

Performance & Configurações

  • Autoscaling com Karpenter: O Karpenter provisiona nós EC2 otimizados "just-in-time" para os pods pendentes do Spark, escalando massivamente em segundos e maximizando a taxa de acerto de Spot Instances.
  • Custom Docker Images: Empacote dependências complexas (ML, drivers nativos) em imagens Docker, acelerando os cold starts e garantindo constância no runtime.
  • Shuffle Tracking: No EKS, o Spark Shuffle Tracking evita a perda de dados cruciais quando pods em nós Spot são interrompidos pelo Auto Scaler.

Deep Dive de Orquestração: Karpenter e Interrupções Spot

A arquitetura recomendada para EMR on EKS envolve o uso massivo de instâncias AWS Spot para reduzir custos de processamento em até 80%. Para que isso funcione sem degradar severamente os SLAs, tecnologias específicas do Kubernetes são aplicadas:

Karpenter "Just-in-Time" Provisioning

Diferente do Cluster Autoscaler clássico que dependia de Auto Scaling Groups (ASG) engessados, o Karpenter fala diretamente com a API do EC2. Quando o Spark Driver pede 50 novos executors (pods), o Karpenter lê os requisitos de vCPU/RAM de cada pod pendente e liga nós EC2 no tamanho e família exata (ex: c6g.4xlarge Graviton) em menos de 1 minuto, desativando-os instantaneamente quando o job acaba (Scale to Zero).

Graceful Decommissioning & Shuffle Tracking

Quando a AWS reivindica uma instância Spot (aviso de 2 minutos), o Karpenter inicia o draining do Node. O Spark é notificado e entra em modo de Graceful Decommissioning. Ele para de agendar novas tasks para aquele executor específico e começa a migrar blocos de dados de *Shuffle* em memória para os outros pods sobreviventes, prevenindo a temida exceção de `FetchFailedException` que forçaria o recálculo de gigabytes de dados.

IRSA (IAM Roles for Service Accounts)

Em ambientes multi-tenant do Kubernetes, injetar chaves AWS estáticas é um erro crítico de segurança. O EKS utiliza OIDC (OpenID Connect) acoplado ao IAM. Cada Job Spark do EMR on EKS ganha sua própria ServiceAccount. Assim, o Job do time de Finanças ganha acesso temporário (via token JWT trocado por STS) ao bucket de Finanças, enquanto o Job de Marketing não enxerga nada fora de seu escopo, rodando no exato mesmo nó EC2 físico.

PodTemplate do Spark (Customização de Infraestrutura)

O EMR on EKS permite injetar Sidecars (ex: Datadog, Splunk), modificar afinidade (Taints/Tolerations) ou forçar armazenamento NVMe efêmero via PodTemplates declarativos:

# spark-executor-template.yaml
apiVersion: v1
kind: Pod
spec:
  # Atribui a permissão granular via IRSA ao executor
  serviceAccountName: "spark-finance-sa"
  nodeSelector:
    # Força o executor a rodar apensas em Spot Instances ARM (Graviton)
    karpenter.sh/capacity-type: spot
    kubernetes.io/arch: arm64
  containers:
  - name: spark-kubernetes-executor
    volumeMounts:
    - name: spark-local-dir-1
      mountPath: /tmp/spark-local-dir
  volumes:
  - name: spark-local-dir-1
    # Usa um volume NVMe efêmero acoplado para absorver Shuffles pesados
    hostPath:
      path: /mnt/d1
5. O Pitch de Business Value (Proposta de Valor)

A adoção de EMR on EKS capitaliza sobre a estratégia de Infraestrutura Convergente. Ao unificar equipes de DevOps, Engenharia de Software e Engenharia de Dados em um único orquestrador de contêineres (Kubernetes), reduzimos o Custo Total de Propriedade (TCO) ao compartilhar hardware de maneira extremamente densa (utilização de CPU L1/L2 na casa dos 85%+). A governança de segurança também é simplificada pelo IAM Role for Service Accounts, eliminando riscos de compliance e vazamento de dados corporativos.

Famílias de Instâncias EC2 e Dimensionamento de Hardware

Em ambientes EMR baseados em EC2 (ou EKS), a seleção da família de instâncias afeta drasticamente a performance física do Spark:

  • Memory-Optimized (Família R - ex: r5, r6g): Oferecem alta densidade de RAM por vCPU (8 GB de RAM por core). Padrão ouro para Spark, reduzindo o estouro de Heap JVM e minimizando a necessidade de Spill to Disk em joins Sort-Merge e operações de agregação pesadas.
  • Compute-Optimized (Família C - ex: c5, c6g): Fornecem processamento bruto (2 GB de RAM por core). Indicado apenas para jobs de modelagem leve ou transformações semânticas pesadas (ex: cálculo de embeddings, criptografia de campos, geoprocessamento complexo) onde a RAM não é o gargalo.
  • General Purpose (Família M - ex: m5, m6g): Proporção balanceada (4 GB de RAM por core). Boa opção para nós de Driver ou clusters pequenos de desenvolvimento compartilhado.
  • Storage-Optimized (Família I - ex: i3, i3en): Equipados com discos físicos NVMe locais de altíssimo throughput. Indispensável para jobs massivos que exigem gravações monstruosas de Shuffle, servindo como área temporária extremamente veloz em substituição ao EBS tradicional.

Causa: Script de bootstrap na inicialização do EC2 travou ou retornou código de erro diferente de zero.

Evolução Arquitetural: Enterprise Data Mesh na AWS

O nível mais alto de maturidade em plataformas de dados combina Streaming, Batch, Governança Fina, FinOps e Segurança de Redes.

Um engenheiro de dados sênior não escreve apenas scripts Spark. Ele projeta a plataforma que escala para milhares de analistas simultâneos, distribuídos globalmente e operando em domínios autônomos, tudo isso garantindo conformidade (LGPD/GDPR) e eficiência de custos através de FinOps.

Master Architecture: Enterprise Data Mesh
Explicação Arquitetural:
  • Componentes Chaves: VPC, VPC Endpoints, MSK, RDS, DMS, S3 Iceberg, EMR Serverless, AWS Lake Formation, IAM, KMS, Athena, Redshift, Cost Explorer
  • Contexto: Esta arquitetura representa o ápice corporativo. O ecossistema é encapsulado em uma VPC isolada. Os produtores de eventos em tempo real (MSK) e transacionais batch (RDS/DMS) operam de forma descentralizada. Os dados fluem para o armazenamento Iceberg central, que não é governado por senhas, mas pelo AWS Lake Formation (controle em nível de linha/coluna). Todo o gasto da plataforma é tagueado via Cost Explorer, garantindo a cobrança correta (chargeback) para cada domínio de negócio consumidor.

1. Isolamento Físico e Lógico (VPC & IAM)

Toda a infraestrutura roda dentro de uma VPC privada. Isso significa que serviços como o Amazon EMR e MSK não possuem IPs públicos expostos à internet. Para ler do S3, configuramos VPC Endpoints (Gateway/PrivateLink), forçando o tráfego a trafegar apenas via backbone físico da AWS, prevenindo exfiltração de dados por hackers externos.

2. Governança e Segurança Fina

Bancos tradicionais falham por dependerem de acessos IAM amplos ao S3. Na era do Data Mesh, usamos o AWS Lake Formation. Com ele, o domínio de Marketing pode acessar a tabela de Vendas via Athena, mas o Lake Formation ofusca dinamicamente a coluna de CPF e filtra linhas onde `regiao != Brasil`. Isso é implementado via Data Filters atrelados à Role do usuário logado.

3. FinOps & Chargeback

Com múltiplos domínios consumindo o cluster compartilhado (EMR Serverless e Redshift), o time de engenharia obriga que todos os jobs submetidos tenham Cost Allocation Tags explícitas (ex: `CostCenter: Marketing`, `Project: Recomendacao`). O AWS Cost Explorer lê essas tags e gera faturas separadas, punindo áreas que criam "queries pesadas" ineficientes no Athena.

Integrações End-to-End no Ecossistema AWS

Visão arquitetural conectando ingestão, processamento e serving no Data Lake AWS

Um pipeline de dados de ponta a ponta na AWS quase nunca existe isolado apenas com o Spark. Ele opera dentro de uma malha arquitetural composta por serviços complementares.

🔗 Ingestão > Spark > DW

Caminho Crítico: Kinesis Data Firehose entrega JSONs brutos no S3 (Bronze). Um job EMR Spark (Agendado via Airflow/MWAA) lê esses JSONs, faz a limpeza, aplica regras de negócio (Silver) e realiza as agregações OLAP salvando em formato Parquet/Iceberg (Gold). Finalmente, o Amazon Redshift Spectrum lê os dados Delta/Iceberg do S3 para disponibilização aos analistas de BI.

🛡️ Governança & Segurança E2E

Caminho Crítico: Ao rodar o EMR Serverless, os dados sensíveis no S3 estão criptografados via AWS KMS (SSE-KMS). O Spark no EMR utiliza o AWS Glue Data Catalog como Metastore central. As permissões de acesso em nível de coluna/linha (Fine-Grained Access Control) são aplicadas pelo AWS Lake Formation, garantindo que o Cientista de Dados usando o Athena só enxergue as colunas permitidas da tabela Iceberg.

5. O Pitch de Business Value (Proposta de Valor)

Adoção de uma arquitetura Data Lakehouse unificada (Kinesis + EMR + Iceberg + Athena) desagrega os custos de armazenamento e computação (Storage and Compute Decoupling). Isso resolve o problema clássico de Lock-in e altos custos fixos de licenciamento de Data Warehouses monolíticos. O valor para o negócio está em pagar apenas pelos bytes lidos via Athena (modelo Pay-per-Query) ou pela hora computacional exata do EMR, maximizando o EBITDA enquanto habilita uma plataforma flexível para múltiplos casos de uso (BI, Machine Learning e GenAI) em um único lago de dados seguro.
