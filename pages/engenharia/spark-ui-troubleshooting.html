Tuning do Spark — Guia Completo de Produção

Receitas de configurações de performance detalhadas e seguras para workloads analíticos corporativos

🔧 Receitas de Configurações Base de Alta Performance (spark-defaults.conf)

1. Otimização Adaptativa (Adaptive Query Execution - AQE)

⚙️
spark.sql.adaptive.enabled = true: Ativa o AQE, permitindo otimizações em tempo de execução.
spark.sql.adaptive.coalescePartitions.enabled = true: Junta partições pequenas pós-shuffle automaticamente para evitar overhead de agendamento de tasks minúsculas (small files na memória).
spark.sql.adaptive.advisoryPartitionSizeInBytes = 134217728: Define o tamanho ideal de partição lida pós-shuffle como 128 MB (ótimo para vazão de I/O).
spark.sql.adaptive.skewJoin.enabled = true: Detecta automaticamente desvios bruscos (skew) em chaves de join e divide partições gigantes em sub-tasks menores para processamento paralelo uniforme.

2. Tuning de Rede & Timeouts de Shuffle

🌐
spark.network.timeout = 800s: Limite máximo de tempo que o Spark espera por pacotes de rede entre nós (default 120s). Evita erros de executor perdido por oscilações na rede AWS ou pausas longas de GC.
spark.core.connection.ack.wait.timeout = 600s: Aumenta o tempo limite de aceno de conexões TCP físicas.
spark.shuffle.file.buffer = 1m: Buffer em RAM (default 32 KB) usado antes de escrever blocos de shuffle temporários no disco local, reduzindo a concorrência e o tempo de busca de cabeçote do EBS.
spark.reducer.maxSizeInFlight = 128m: Tamanho máximo de dados requisitados simultaneamente de outros executores de forma assíncrona, acelerando o throughput do shuffle read.

3. Gerenciamento de Memória & Project Tungsten

🧠
spark.memory.fraction = 0.8: Eleva o espaço do Spark Memory para 80% da Heap da JVM em instâncias r5 de grande porte, deixando menos área ociosa na User Memory para jobs puramente SQL/DataFrame.
spark.memory.storageFraction = 0.2: Limita a área imune de Storage a 20% do pool Spark. Excelente para ETLs que não usam cache/persistência de dados, liberando espaço máximo imune para a Execution Memory resolver Shuffles e Joins complexos.
spark.memory.offHeap.enabled = true: Ativa a alocação de dados Off-Heap.
spark.memory.offHeap.size = 4294967296: Reserva 4 GB de memória do sistema operacional (Off-Heap) por executor para o Project Tungsten ordenar dados em formato binário sem poluição de GC.

4. Serialização e Compressão

📦
spark.serializer = org.apache.spark.serializer.KryoSerializer: Substitui a serialização Java padrão pela Kryo, que é até 10x mais rápida e gera representações de objetos muito menores.
spark.kryoserializer.buffer.max = 1024m: Define o tamanho máximo de buffer do Kryo para lidar com registros extremamente grandes de forma segura.
spark.io.compression.codec = zstd: Utiliza compressão ZSTD para dados internos temporários de shuffle, reduzindo I/O e uso de rede no cluster com baixo consumo de CPU.

5. Escrita no Data Lake (Evitando Small Files)

💾
spark.sql.sources.commitProtocolClass = org.apache.spark.internal.io.cloud.PathOutputCommitProtocol: Utiliza protocolo otimizado de commmit para S3 que elimina operações de rename demoradas.
spark.sql.parquet.compression.codec = zstd: Força arquivos finais Parquet a serem compactados com ZSTD no S3.

Guia de Resolução de Erros & Troubleshooting

Receitas e diagnósticos para os 10 problemas e exceções clássicos da JVM e do Spark em produção

OOM / JVM
java.lang.OutOfMemoryError: Java heap space
Causa: Os executores ou o Driver esgotaram a memória Heap física devido a partições excessivamente grandes (Data Skew), processamento de registros gigantes de texto (JSON/XML) ou chamadas abusivas de .collect() de DataFrames volumosos para a memória do Driver.

Fix: Aumente a quantidade de partições lidas, ative o AQE (spark.sql.adaptive.skewJoin.enabled) ou reduza o número de cores por executor (liberando mais RAM por tarefa). Evite UDFs tradicionais que acumulam referências.
YARN / OS
Container killed by YARN for exceeding memory limits
Causa: A memória total do container (Heap + Off-Heap) excedeu o limite provisionado no ResourceManager. Ocorre frequentemente em jobs PySpark com uso pesado de Pandas/PyArrow (vetorização) ou bibliotecas C++ nativas.

Fix: Eleve a memória de overhead configurando spark.executor.memoryOverhead. Como regra prática, defina entre 15% a 20% do valor total de spark.executor.memory (mínimo de 384 MB).
PERFORMANCE
Straggler Tasks (Job travado em 99%)
Causa: Severo desbalanceamento de partições (Data Skew). Uma única partição contém a maior parte dos dados e é direcionada a um único executor, mantendo-o ocupado por horas enquanto os demais ficam ociosos.

Fix: Ative a partição automática de skew join do AQE ou aplique a técnica manual de Salting adicionando um prefixo aleatório às chaves de junção para distribuí-las horizontalmente pelo cluster.
PERFORMANCE
Too many small files (Overhead de metadados)
Causa: Milhares de pequenos arquivos gravados no S3/HDFS. Isso gera milhões de chamadas I/O HTTP `GET`/`LIST` para leitura no Driver do Spark, travando a compilação de metadados e o planejamento do job.

Fix: Utilize df.coalesce(N) antes da escrita final para arquivos em lote ou configure spark.sql.files.maxPartitionBytes (padrão 128 MB) para juntar arquivos menores durante a leitura.
SERIALIZAÇÃO
SparkException: Task not serializable
Causa: O Spark tenta serializar o código de uma transformação para despachar para os executores, mas encontra referências a objetos do Driver não serializáveis (ex: conexões de banco de dados HTTP, loggers, ou a própria SparkSession).

Fix: Instancie e feche conexões JDBC/HTTP dentro de um escopo local na task usando foreachPartition, evitando referenciar variáveis globais criadas fora do loop executor.
SHUFFLE / REDE
FetchFailedException - shuffle data lost
Causa: Um executor morreu no meio do pipeline (por OOM ou encerramento de nó Spot da AWS) e os arquivos intermediários de shuffle gerados por ele foram perdidos, fazendo com que as tarefas dependentes falhem.

Fix: Se estiver no EKS/Kubernetes, ative o Shuffle Tracking do Spark 3.x+; se estiver no YARN, habilite o External Shuffle Service (spark.shuffle.service.enabled = true) para desacoplar e salvar arquivos locais.
SCHEMA / COMPILAÇÃO
AnalysisException: cannot resolve column
Causa: Erro ortográfico ou conflito de namespace de colunas ao referenciar colunas em estruturas de junção de DataFrames de nomes idênticos sem apelidos (aliases) explícitos.

Fix: Utilize namespaces claros, renomeie colunas duplicadas usando withColumnRenamed antes da junção e execute diagnósticos prévios imprimindo o schema lógicos com df.printSchema().
STREAMING
StreamingQueryException: checkpoint incompatível
Causa: O schema dos dados de origem ou a estrutura lógica da query de streaming (ex: novos operadores de janela) foram alterados, tornando incompatíveis os estados e offsets persistidos no diretório de checkpoint.

Fix: Delete o diretório antigo de metadados de checkpoint do S3 ou crie e aponte para um novo diretório exclusivo de versionamento de checkpoint antes do deploy do novo código em produção.
GC / TIMEOUT
Executor heartbeat timed out
Causa: Pausa de Garbage Collection extremamente longa da JVM Heap (Stop-the-world). O executor congela todas as threads para liberar espaço e falha em responder as mensagens de heartbeat de saúde do Driver.

Fix: Altere o Garbage Collector padrão para o G1GC (-XX:+UseG1GC), configure tamanhos maiores de Heap ou aumente o timeout limite de rede configurando spark.network.timeout = 800s.
I/O / STORAGE
Full scan desnecessário em tabelas Parquet
Causa: Consultas lentas em tabelas Parquet/Delta devido à ausência de filtros baseados nas colunas físicas de partição estruturadas na gravação, forçando o Spark a ler e deserializar arquivos inteiros.

Fix: Certifique-se de salvar os arquivos usando .partitionBy("ano", "mes") nas colunas mais acessadas e verifique se as queries analíticas de leitura utilizam ativamente esses mesmos campos de partição nos filtros.

Estratégias de Diagnóstico Especialista

Mecanismos profundos de inspeção: Thread Dumps, Heap Dumps e Log de GC

🧵 Thread Dumps (Caça a Deadlocks)

Se o job estiver BLOCKED mas a CPU estiver em 0%, você tem um Deadlock ou contenção de recurso externo.

  • Como gerar: Use jstack <pid> no nó worker ou veja pela Spark UI (Executors -> Thread Dump).
  • O que buscar: Threads no estado WAITING (on object monitor) apontando para a mesma referência de memória.

🧠 Heap Dumps sob OOM

Para descobrir vazamentos de memória (Memory Leaks) em bibliotecas customizadas.

  • Configuração: Adicione -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/spark-heapdump.hprof nas extraJavaOptions.
  • Análise: Abra o arquivo .hprof no Eclipse Memory Analyzer (MAT) para ver quais objetos estão retendo a Heap.
Análise Proativa de Garbage Collection:
Habilite -XX:+PrintGCDetails -XX:+PrintGCTimeStamps. Se você observar "Full GC" frequentes seguidos de pouca liberação de memória, sua Old Generation está saturada. Aumentar a spark.memory.fraction pode piorar a situação; o fix real é aumentar a memória física do nó ou reduzir o paralelismo local.

Guia Prático da Interface Spark UI

Como ler métricas e depurar gargalos de memória e rede nas principais abas da interface

A Spark UI é a ferramenta de monitoramento em tempo real padrão do ecossistema. Engenheiros de dados seniores utilizam as abas lógicas abaixo para caçar gargalos de desempenho físico:

1. Jobs Tab

Fornece uma linha do tempo macro de todas as ações de dados executadas no código da aplicação. Cada Action de escrita, agrupamento ou contagem gera uma entrada de Job.

  • O que buscar: Padrões de execução em paralelo e o tempo total decorrido de processamento de ponta a ponta.
  • Alerta vermelho: Múltiplos jobs sequenciais pequenos executados um após o outro, indicando que o desenvolvedor inseriu ações desnecessárias como .count() ou .show() no meio do pipeline de produção, forçando a quebra de lazy evaluation.

2. Stages Tab

Detalhamento de cada estágio isolado separado por Shuffles físicos. Fornece uma tabela descritiva das Tasks executadas.

  • Métrica Chave - GC Time (Tempo de Coleta de Lixo): Indica quanto tempo os executores Java passaram congelados para limpar objetos obsoletos da Heap. Se o GC Time ultrapassar 10% do tempo do Stage, aumente a Heap ou ative o Garbage Collector G1.
  • Métrica Chave - Spill (Memory) / Spill (Disk): Ocorre quando os dados de uma partição não cabem na Execution Memory reservada. O Spark serializa os registros excedentes e grava no disco local. Isso degrada a performance em até 10x. Solução: aumente o paralelismo de partições ou mude para instâncias de maior RAM.
  • Métrica Chave - Shuffle Read Blocked Time: Tempo que uma Task passou esperando dados chegarem via rede de outros executores. Valores altos indicam congestionamento de rede ou saturação física dos nós do cluster.

3. Storage Tab

Exibe os DataFrames ou RDDs que foram explicitamente colocados na memória do cluster por meio de comandos de cache (.cache() ou .persist()).

  • O que analisar: A fração do conjunto de dados que de fato reside na RAM do cluster (Fraction Cached). Se estiver abaixo de 100%, significa que o cluster sofreu eviction e está recalculando partições direto da fonte S3 durante as ações, gerando lentidão severa.

4. Executors Tab

Visão física de hardware de cada executor em execução na JVM dos workers.

  • O que monitorar: O volume total de dados gravados fisicamente em disco por executor e a contagem de tarefas ativas por core. É a melhor aba para identificar desvios bruscos de desbalanceamento de processamento por nó.

5. SQL Tab (Execution Plan Visualization)

Desenha graficamente o plano físico compilado e otimizado pelo Catalyst Optimizer. É a aba mais importante para entender o comportamento computacional das queries.

  • Whole-Stage CodeGen Inspection: Elementos e operadores agrupados em caixas azul-escuras marcadas com um asterisco (ex: *(1) Sort ou *(2) HashAggregate) representam trechos de código que foram compilados em um único loop em Java físico nativo, otimizados para velocidade.
  • Join Selection Validation: Verifique se a query utilizou um BroadcastHashJoin ou se realizou um dispendioso SortMergeJoin com troca massiva de dados (Exchange). Isso valida se as regras de tamanho dinâmico do AQE funcionaram.

Troubleshooting Visual: Skew, Spill, OOM e GC

Exemplos reais de código e como os problemas se materializam na interface do Spark

1. O Código (Data Skew & Spill Intencional)

O Data Skew (Viés de Dados) ocorre quando uma chave de Join ou GroupBy concentra a esmagadora maioria dos registros (ex: ID de "Cliente Não Cadastrado" = -1). Isso joga quase todos os dados para um único Executor (Core), que invariavelmente sofre Spill (transbordo para o disco) e eventual OOM (Falta de Memória).

python 
# Criando Skew Intencional: 99% dos dados possuem customer_id = 999
spark.conf.set("spark.sql.shuffle.partitions", "200")
spark.conf.set("spark.executor.memory", "2g")

skewed_data = spark.range(0, 10000000) \
    .withColumn("customer_id", F.when(F.col("id") < 9900000, 999).otherwise(F.col("id")))

# O Shuffle joga todos os "999" para a mesma Partição!
result = skewed_data.groupBy("customer_id").count()
result.write.format("noop").mode("overwrite").save()

2. Como o Skew aparece na Spark UI (Aba Stages)

Na aba de Stages, o sintoma clássico de Skew é o Max Task Time ser absurdamente superior ao Median Task Time. Veja o simulador da UI abaixo:

Spark UI > Stages > Stage 12
Total Tasks: 200
Metric Min 25th percentile Median 75th percentile Max
Duration 0.8 s 1.1 s 1.2 s 1.5 s 14.5 min
GC Time 10 ms 15 ms 22 ms 35 ms 3.2 min
199/200 Tasks Succeeded
1/200 Tasks Active (Stuck)
O Veredito: 199 cores (Tasks) acabaram em 1 segundo. 1 único Core recebeu 99% dos dados e está "preso" calculando o agrupamento do cliente "999" por mais de 14 minutos. O GC Time (Garbage Collection) dessa Task está altíssimo (3.2 min), provando que o executor está lutando para não estourar a memória.

3. Como o Spill aparece na Spark UI (Aba Tasks)

Quando a memória alocada para execução (Execution Memory) enche, o Spark salva o excesso em disco (Spill). O Spill degrada a performance do nó violentamente devido ao I/O físico (Disco e Rede).

Tasks Details (Sorted by Duration)
Task ID Status Duration Shuffle Read Size Spill (Memory) Spill (Disk)
145 RUNNING 14.5 min 8.2 GB 24.5 GB 4.1 GB
146 SUCCESS 1.2 s 14.2 MB 0.0 B 0.0 B
A Matemática do Spill: Note que o Spill (Memory) é muito maior que o Spill (Disk). Isso ocorre porque o tamanho em memória considera objetos Java inflados (uncompressed deserialized), enquanto no disco os dados são gravados serializados e comprimidos. Qualquer valor > 0.0 B nessas colunas exige sua atenção!

4. O Destino Final: OOM (Out of Memory) na Aba Executors

Se o Spill não for suficiente e a sobrecarga do Garbage Collector for extrema (passando mais tempo reciclando do que calculando), a JVM do nó Worker irá travar e será morta pelo YARN/Kubernetes (Status: Dead).

Executors
Executor ID Status Cores Active Tasks Failed Tasks Task Time
driver Active 0 0 0 0 ms
1 Dead 4 0 1 15.1 min
2 Active 4 0 0 1.4 s
Reason for Death: Container killed by YARN for exceeding memory limits. 2.5G of 2G physical memory used. Consider boosting spark.executor.memoryOverhead.

Leitura Avançada: DAG, Environments & Desbalanceamento

Dominando as entranhas da Spark UI para orquestração de alta performance

1. A Aba "Environment" (O Checkup Inicial)

Muitos engenheiros ignoram a aba Environment, mas ela é o primeiro lugar que você deve olhar ao assumir o troubleshooting de um job legado. Ela lista todas as variáveis de ambiente, dependências (Jars) e as Spark Properties em vigor.

Propriedades Chave para Auditar:
  • spark.sql.shuffle.partitions: Se estiver no valor default (200) e você estiver processando Terabytes de dados, os executores vão colapsar (Spill). A regra prática é ter partições de 100MB a 200MB.
  • spark.memory.fraction: (Default 0.6). Define a divisão da memória Heap entre a Execution Memory (para joins e shuffles) e Storage Memory (para caches). Se o job tem muito cache, aumente. Se tem muitos Joins, reduza.
  • spark.executor.memoryOverhead: Memória extra alocada fora da Heap (Off-Heap). Vital se você estiver usando PySpark (Python Pandas UDFs executam na memória Overhead, não na Heap Java!).

2. Desbalanceamento Crítico: Lendo a Aba Tasks

Além do tempo (Duration), o maior delator de um Skew violento são as colunas de I/O. Veja este exemplo clássico onde a quantidade de registros destruiu um executor.

Tasks Details (Task Imbalance Detection)
Task ID Status Duration Shuffle Read Size / Records Shuffle Write Size / Records
34 RUNNING 22.5 min 12.4 GB / 45,000,000 ---
35 SUCCESS 0.8 s 4.2 MB / 1,500 2.1 MB / 800
A Solução (Salting Technique): Para resolver isso, adicionamos uma coluna "Salt" (um número aleatório de 1 a N) na chave problemática. Isso força o Hash Partitioner a quebrar esses 45 milhões de registros da chave "999" em N partições (distribuindo para diferentes tasks), realizando um Join em duas etapas (Partial Aggregation -> Global Aggregation).

3. Como Interpretar o DAG (Directed Acyclic Graph)

O DAG é a bússola do Engenheiro de Dados. Cada caixa representa uma transformação, e as linhas representam a movimentação dos dados. As barreiras entre Stages são invariavelmente criadas por operações que requerem a rede do cluster (Shuffles / Exchanges).

Stage 1
Scan parquet
S3://bucket/table_A
*(1) Project & Filter
WholeStageCodegen (JIT)

Exchange (Shuffle)
Stage 2
*(2) HashAggregate
WholeStageCodegen (JIT)
A Regra de Ouro do DAG:
1. Onde você vê *(1) ou *(2), o Spark pegou todas as transformações daquele bloco (ex: ler, filtrar, selecionar colunas) e compilou num único loop em linguagem de máquina nativa (Tungsten WholeStageCodegen). É ultra-rápido!
2. Onde você vê a palavra Exchange, o motor foi obrigado a pausar a execução, serializar todos os dados no disco local e traficá-los pela rede para que os executores consigam montar os agrupamentos ou joins globais. É aqui que os Jobs gargalam. Minimizar Exchanges é a essência do Tuning.

4. Padrões Mortais do DAG: SortMergeJoin vs BroadcastHashJoin

A melhor forma de testar sua habilidade em ler DAGs é analisando planos de Join. Quando você cruza duas tabelas, o comportamento do Spark muda radicalmente dependendo do tamanho das tabelas envolvidas.

Caso A: O DAG Pesado (SortMergeJoin)

Ocorre quando as duas tabelas são gigas ou terabytes (Default do Spark). As duas tabelas são lidas em paralelo, e ambas sofrem um Exchange (Shuffle) simultâneo para que as chaves idênticas sejam enviadas para o mesmo executor. A visualização se parece com um "Y" de ponta cabeça.

Stage 11 (Tabela Fato)
Scan parquet
Exchange
Stage 12 (Tabela Dim)
Scan parquet
Exchange
Stage 13 (Join & Sort)
*(3) SortMergeJoin
Inner Join
Perigo Iminente: A presença de dois Stages lado-a-lado engatilhando "Exchanges" significa que o cluster parou o processamento e está traficando Terabytes na rede. Se uma das chaves for mal distribuída, haverá Spill ou OOM (como vimos no tópico de Desbalanceamento).

Caso B: A Bala de Prata (BroadcastHashJoin)

Ocorre quando aplicamos o comando broadcast(df_pequeno) ou quando o Spark AQE detecta que uma das tabelas tem menos de 10MB. O Spark envia a tabela inteira para todos os executores usando BitTorrent (BroadcastExchange), aniquilando o Shuffle pesado da tabela Fato.

Stage 11 (Tabela Fato)
Scan parquet
*(1) Filter
Stage 12 (Tabela Dim Pequena)
Scan parquet
BroadcastExchange
Ainda no Stage 11!
*(1) BroadcastHashJoin
Inner Join
Vitória Arquitetural: A Tabela Fato inteira não teve um único bloco de Shuffle. O processamento ocorre localmente no mesmo Stage (Stage 11), consumindo o Broadcast. O tempo do seu job deve cair de horas para minutos. Esta é a assinatura visual perfeita de um Job ultra otimizado!

Performance Callout: Dicas de Tuning

Otimizações cruciais para grandes volumes de dados

📦 Small Files em Spark

Ter milhares de arquivos pequenos no S3 causa overhead massivo de metadados. Solução: Use df.repartition(n) ou df.coalesce(n) visando arquivos de ~128MB.

🚀 Speculative Execution

Evita que "stragglers" (tasks lentas) atrasem o job inteiro ao lançar cópias em outros nós. Configure spark.speculation=true.
