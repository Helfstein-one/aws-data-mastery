Analytics & Serving

Serving & Analytics de Dados

Arquiteturas analíticas de alto desempenho no S3 com Amazon Athena Serverless e Data Warehouses Massivamente Paralelos com Amazon Redshift.

01

Amazon Athena

Tuning Avançado: Athena Partition Projection

O comando MSCK REPAIR TABLE é o maior vilão da performance de Data Lakes em tabelas altamente particionadas. Ele precisa listar fisicamente todas as pastas do Amazon S3 (ListObjectsV2) para descobrir novas partições (como ano=2023/mes=10/dia=05). Em tabelas com milhares de partições, isso pode demorar de minutos a horas e custar centenas de dólares em requisições de API.

A solução corporativa é a Partition Projection. Em vez de ler o S3 ou o AWS Glue Data Catalog, você injeta lógica matemática na definição da tabela (DDL). Exemplo: "A partição de data varia de 2020-01-01 a NOW, injetada diariamente". O Athena calcula a existência da partição em memória sub-segundo, eliminando 100% das chamadas de ListObjects do S3 e pulando o Glue, acelerando o tempo de planejamento da query em até 100x.

Cost Optimization: Athena Result Caching & QuickSight SPICE

Um Dashboard no Amazon QuickSight com modo de consulta direta (Direct Query) contra o Amazon Athena vai cobrar por Terabytes lidos a cada vez que qualquer usuário mexer num filtro. Se o Dashboard tiver 10 painéis (10 queries), e 100 usuários abrirem ao mesmo tempo, a fatura explodirá.

As duas defesas arquiteturais contra "Bankrupcy by BI" são:

  • Athena Query Result Caching: Permite reaproveitar resultados exatos de queries executadas recentemente (ex: max_age = 60 minutos). Se a query for idêntica, o Athena não cobra 1 centavo pela varredura de dados e retorna em milissegundos o que já estava cacheado no S3.
  • QuickSight SPICE (Super-fast, Parallel, In-memory Calculation Engine): Ao invés de *Direct Query*, o dashboard ingere os dados do Athena uma única vez pela manhã (Schedule) para o SPICE (Memória RAM do QuickSight). Milhões de interações de usuários batem apenas no SPICE, com custo de processamento analítico no Athena exatamente ZERO no resto do dia.
: Introdução Teórica & Funcionamento

O motor serverless de consultas interativas sobre dados armazenados de forma distribuída no S3

O Amazon Athena é um serviço de consulta interativa serverless que permite analisar dados diretamente no Amazon S3 utilizando SQL padrão. O Athena é construído sobre o motor open-source Trino (antigo Presto), especializado em queries ad-hoc de baixa latência em escala petabyte. Por ser totalmente serverless, não há necessidade de provisionar ou gerenciar clusters (computação desacoplada de armazenamento), e você é cobrado estritamente pelo volume de dados escaneados por consulta.

Arquitetura
Computação Desacoplada
O Athena lê dados brutos do S3 em tempo de execução. O processamento SQL é distribuído dinamicamente entre workers gerenciados pela AWS, sem persistência local.
Integração
Glue Data Catalog
Funciona como o repositório central de metadados. O Glue armazena a estrutura de schemas, tabelas e caminhos S3 (serdes) que o Athena interpreta para rodar SQL.
Mapeamento
Partition Pruning
Em vez de ler o bucket inteiro, o Athena usa chaves de partição (pastas no S3) para ignorar arquivos irrelevantes, reduzindo o volume escaneado e o custo.

Correção, Balanceamento e Metadados de Partições

Gerenciar partições corretamente é fundamental para a performance do Amazon Athena e o controle de custos.

Estilo Hive vs Iceberg

Tradicionalmente (estilo Hive), o Athena exige que você adicione explicitamente novas partições (ex: novas pastas no S3) ao Glue Catalog. Para formatas modernos como Apache Iceberg, os metadados lidam com o particionamento de forma transparente via *manifests*, tornando comandos de reparação desnecessários e otimizando a leitura.

Correção Manual (Hive)

Quando novos arquivos chegam ao S3 fora do fluxo de um Crawler, o Athena não os enxerga automaticamente em tabelas Hive. Usa-se o comando para varrer o S3 e atualizar o Glue:

-- Escaneia o S3 e adiciona partições faltantes no Glue
MSCK REPAIR TABLE meu_db.minha_tabela;
⚠️ Atenção: Em tabelas massivas, `MSCK REPAIR` é extremamente lento e oneroso, e pode falhar.
Performance
Balanceamento e Problema dos Arquivos Pequenos (Small Files Problem)
O Athena funciona melhor lendo arquivos entre 128MB e 512MB. Particionamento excessivo (ex: por hora e minuto) ou fluxos de streaming constantes geram milhões de "arquivos pequenos" (KBs) no S3. O tempo gasto abrindo conexões de rede supera o tempo de leitura real.

Soluções para balanceamento:
  • Evite partições granulares demais. Em vez de ano/mes/dia/hora, consolide em ano/mes/dia dependendo do volume.
  • Agende rotinas periódicas (com AWS Glue Job ou comandos de Compaction no Iceberg) para ler arquivos pequenos e reescrevê-los em arquivos Parquet de 256MB.

Partition Projection Avançado

Otimização de tempo e I/O de consultas via computação de caminhos baseados em metadados:

Como Funciona

Tradicionalmente, o Athena consulta o AWS Glue Catalog para listar as partições físicas de uma tabela no S3. Em tabelas com milhões de partições, essa consulta de metadados torna-se o principal gargalo de performance analítica.

O Partition Projection inverte esse modelo: ao invés de ler metadados do catálogo, o Athena calcula os caminhos das partições no S3 em tempo de execução, baseando-se em regras configuradas no DDL. Isso elimina a latência de rede entre o motor de query e o repositório de metadados.

Performance & Vantagens

  • Latência Zero de Metadados: Redução drástica no tempo de planejamento da query (Planning Time) para datasets massivos.
  • Automatização: Elimina a necessidade de rodar MSCK REPAIR TABLE ou chamadas de API AlterTable para registrar novas partições.
  • Escalabilidade: Ideal para buckets com alta cardinalidade de partições (ex: por minuto, por IoT device ID).
💡 Insight Técnico: O Partition Projection é especialmente poderoso para dados de logs e telemetria onde o crescimento de partições é contínuo e previsível (baseado em tempo).

DDL Multi-Chave com Partition Projection (Ano, Mês, ID de Cliente)

Abaixo está o DDL para mapear partições que misturam data com IDs numéricos de clientes de forma dinâmica:

CREATE EXTERNAL TABLE clickstream_logs (
    event_id string,
    event_name string,
    user_id string
)
PARTITIONED BY (year string, month string, client_id string)
ROW FORMAT SERDE 'org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe'
LOCATION 's3://meu-datalake-gold/logs/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.year.type' = 'integer',
    'projection.year.range' = '2024,2030',
    'projection.month.type' = 'integer',
    'projection.month.range' = '1,12',
    'projection.month.digits' = '2',
    'projection.client_id.type' = 'integer',
    'projection.client_id.range' = '1,100',
    'storage.location.template' = 's3://meu-datalake-gold/logs/year=${year}/month=${month}/client=${client_id}/'
);

Melhores Práticas (Storage & API)

  • Formatos Colunares: Sempre armazene dados em Parquet ou ORC para permitir o Predicate Pushdown em nível de coluna.
  • Intervalos Reais: Configure o projection.COLUMN.range o mais próximo possível da realidade para evitar que o Athena tente calcular caminhos inexistentes.
  • Tipos de Dados: Use enum para listas fixas de valores e date para partições temporais complexas.

Integração via API & S3

O Partition Projection é configurado via TBLPROPERTIES na criação ou alteração da tabela. Ele altera o comportamento da API do Athena durante a execução, mas os dados no S3 devem seguir um padrão de nomenclatura consistente definido no storage.location.template.

✓ Pro Tip: Combine Partition Projection com S3 Inventory para auditar a consistência entre o template configurado e os arquivos físicos no bucket.

01.2

A Arquitetura Oculta: Motor Trino e AWS Glue APIs

Como o Athena compila SQL e orquestra workers efêmeros para escanear PBs no S3 em segundos.

Embora o Amazon Athena seja um produto Serverless empacotado pela AWS, o seu cérebro de processamento é um cluster Trino (antigo PrestoSQL) altamente customizado que roda em VPCs invisíveis gerenciadas pela Amazon. Para dominar a performance analítica, precisamos entender como o Coordinator do Trino interage com as APIs de metadados antes mesmo de ler o primeiro byte do S3.

AMAZON ATHENA SERVERLESS ARCHITECTURE
Explicação:
  • Componentes: AMAZON ATHENA SERVERLESS ARCHITECTURE, BI Client (JDBC/ODBC), Amazon Athena Serverless API, Managed Trino (PrestoSQL) Cluster, Trino Coordinator (Query Planning), Trino Worker 1, Trino Worker 2, AWS Glue Catalog, Amazon S3 (Data Lake)
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.
  • Contexto: O diagrama "AMAZON ATHENA SERVERLESS ARCHITECTURE" ilustra a arquitetura da solução para o tópico em questão.

A Fase de Planejamento (Planning Time)

Quando a requisição chega, o Trino Coordinator assume o controle. O primeiro gargalo que a maioria dos engenheiros desconhece é a dependência profunda das APIs do AWS Glue. Antes de rodar, o Coordinator dispara as chamadas glue:GetDatabase e glue:GetTable para descobrir a tipagem das colunas e os formatos de compressão (SerDe).

Se a tabela for particionada (estilo Hive), o Coordinator lança milhares de paginações da API glue:GetPartitions. Em tabelas com dezenas de milhares de partições, essa fase pode demorar minutos, fazendo a query "travar no Planejamento" antes mesmo da execução real começar. Solução: Utilizar Partition Projection ou formato Apache Iceberg.

A Fase de Execução (Execution Time) e os Trino Splits

Uma vez que o plano de execução físico foi compilado e todas as rotas de S3 mapeadas, o Coordinator distribui a tarefa em centenas de Trino Workers dividindo o trabalho em unidades lógicas chamadas Splits.

Um "Split" geralmente equivale a um bloco HDFS/S3 físico (ex: um chunk de 128MB de um arquivo Parquet). Se você tiver milhares de arquivos de 1KB (Small Files Problem), o Coordinator sofrerá Head-of-Line Blocking tentando enfileirar milhares de minúsculos Splits para os workers, matando a performance. Se tiver arquivos muito grandes (10GB) não-segmentáveis (como JSON comprimido em GZIP), 1 único worker ficará preso lendo todo o arquivo enquanto os demais ficam ociosos. Otimização Suprema: Arquivos Parquet/ORC de ~128MB a 512MB com compressão Snappy, permitindo que cada Split seja perfeitamente processado em paralelo por múltiplos workers.

Durante a leitura, os workers aplicam o Predicate Pushdown, ou seja, só baixam da rede os blocos do formato Parquet estritamente necessários para satisfazer o seu WHERE ou SELECT. Finalmente, os dados são processados e agregados na memória RAM dos workers, e o Coordinator devolve a resposta condensada ao Client.

: Federated Query & Workgroups

Consultas federadas nativas, gerenciamento de concorrência massiva e isolamento de carga de trabalho

Federated Query (Consultas Federadas)

O Athena Federated Query permite aos engenheiros consultarem dados diretamente em fontes externas (como Amazon RDS, DynamoDB, Redshift, Snowflake, etc.) fazendo JOINs em tempo real com o Data Lake no S3 sem precisar desenvolver complexos pipelines de ETL (CDC).

  • Arquitetura Serverless: Utiliza funções AWS Lambda com conectores pré-construídos que agem como interfaces de comunicação, convertendo respostas dos bancos operacionais para o formato colunar Apache Arrow.
  • Predicate Pushdown: O motor do Athena empurra inteligentemente os filtros (WHERE) para a fonte original através da Lambda, garantindo que o RDS ou DynamoDB trafegue pela rede apenas os dados estritamente necessários, minimizando latências e OOM.

Workgroups & Capacity Reservations (FinOps e Isolamento)

Para evitar que consultas analíticas pesadas (ETLs) impactem dashboards executivos de tempo real no QuickSight, o Athena provê mecanismos robustos de segregação:

  • Athena Workgroups: Permitem separar usuários, times ou aplicações. Cada Workgroup pode ter limites de bytes escaneados e métricas CloudWatch dedicadas, bloqueando automaticamente queries que estouram o orçamento configurado.
  • Provisioned Capacity: Para SLAs rígidos sem concorrência compartilhada, clientes alocam blocos de DPUs (Data Processing Units) dedicados. Isso blinda as queries críticas contra o enfileiramento padrão "noisy neighbor" nas regiões superlotadas da AWS.
  • Result Reuse: Para concorrência extrema (centenas de visualizações do mesmo dashboard na mesma hora), o recurso Result Reuse retorna o cache computado anteriormente da query do S3, reduzindo o tempo de resposta e zerando o custo repetido de scan analítico.

Deep Dive em Consultas, Metadados e Performance

Otimização de queries analíticas, manipulação de dados complexos e inspeção de infraestrutura via SQL.

Consultas Simples e Avançadas

O Athena processa JSONs aninhados e Arrays de forma nativa sem necessidade de pré-processamento. Utilize o UNNEST para explodir listas em linhas.

-- Consulta Avançada: Desaninhar array de objetos JSON e filtrar
SELECT
    u.id,
    u.nome,
    pedidos.valor
FROM usuarios u
CROSS JOIN UNNEST(u.historico_pedidos) AS t(pedidos)
WHERE pedidos.valor > 1000;

Leitura de Metadados de Arquivo

Muitas vezes é necessário saber exatamente de qual arquivo do S3 um registro veio ou qual a idade dele para debug e linhagem de dados.

-- Extraindo linhagem de arquivo e data de modificação física
SELECT
    u.id,
    u.nome,
    "$path" AS origem_s3,
    "$file_modified_time" AS modificacao_s3
FROM usuarios u
LIMIT 10;

Otimização de JOINs e Performance

  • Maior para a Esquerda: Coloque sempre a tabela com maior cardinalidade no lado esquerdo do JOIN (ou no FROM principal), e a menor à direita. O motor distribui as tabelas menores na memória dos workers.
  • Predicate Pushdown: Aplique filtros (WHERE) nas partições antes de fazer o JOIN, reduzindo o tráfego de rede no cluster.
  • Aproximações Rápida: Se não precisar de precisão absoluta, use approx_distinct() no lugar de COUNT(DISTINCT). Ele é ordens de grandeza mais rápido e consome menos memória.

Consultas ao Information Schema

Auditoria e governança baseada em SQL. O Athena expõe um catálogo em tempo real sob o schema information_schema.

-- Listar todas as views ativas no catálogo do Glue via Athena
SELECT table_schema, table_name, view_definition
FROM information_schema.views
WHERE table_schema = 'meu_datalake';

CTAS (Create Table As Select) vs INSERT INTO

Em pipelines construídos inteiramente em SQL dentro do Athena, a escolha da instrução afeta violentamente a infraestrutura física de armazenamento subjacente:

  • INSERT INTO: Adiciona dados a uma tabela existente. Se você rodar 100 INSERT INTO de pequenas quantidades, você criará 100 arquivos pequenos no S3, desencadeando o "Small Files Problem". Ideal apenas para appends de grandes lotes.
  • CTAS (Create Table As Select): Uma instrução monolítica que cria uma nova tabela e insere o resultado da query. O motor Trino otimiza a escrita no S3 paralelizando o job e gravando blocos maiores (chunks) nativamente em formato Parquet com compressão Snappy/ZSTD. Pro Tip: É a forma mais rápida de transformar 10.000 arquivos CSV brutos em alguns poucos arquivos Parquet otimizados.

Athena Engine Version 3 (Trino) e Iceberg

Com a migração do Athena para a Engine v3, ele tornou-se um motor DML (Data Manipulation Language) maduro para o formato Apache Iceberg, não servindo apenas para leituras, mas para pipelines de engenharia ativos.

  • Operações Nativas (ACID): Você pode usar UPDATE, DELETE FROM e MERGE INTO diretamente na console do Athena. Isso varre as tabelas Iceberg e cria automaticamente novos arquivos delta (Copy-On-Write ou Merge-On-Read).
  • Time Travel e Rollback: A Engine v3 lê nativamente metadados temporais. É possível recuperar o estado exato de uma tabela de ontem ou desfazer um DELETE acidental apenas com SQL:
    SELECT * FROM tb_vendas FOR TIMESTAMP AS OF (current_timestamp - interval '1' day)
5. O Pitch de Business Value (Proposta de Valor)

Adotar o Amazon Athena é um movimento estratégico focado diretamente em margem de lucro (EBITDA). Ao transferir o custo computacional analítico para um modelo 100% sob demanda e alocado por carga de trabalho, nós reduzimos drasticamente o OPEX (despesas operacionais) associado à manutenção de clusters ociosos ou licenciamentos caros.

Através de uma estratégia sólida de FinOps, garantimos que os custos fiquem dentro do orçamento, com bloqueios automatizados para consultas mal otimizadas. Isso nos proporciona um Time-to-Market imbatível: a equipe de dados entrega insights valiosos instantaneamente usando ferramentas já conhecidas pelo mercado, diminuindo drasticamente os riscos operacionais (Risk Mitigation) de manutenções prolongadas e empoderando as linhas de negócios a tomarem decisões baseadas em dados com flexibilidade total.

Manutenção de Tabelas Apache Iceberg no Lakehouse

Técnicas essenciais de Compaction (OPTIMIZE) e limpeza de versões antigas (VACUUM) via Athena/Spark

Em arquiteturas modernas de Lakehouse usando o formato Apache Iceberg, a escrita de múltiplos micro-batches ou pipelines de streaming gera o clássico Small Files Problem (milhares de arquivos pequenos que degradam a performance de leitura devido à latência de abertura de arquivos no S3). Além disso, atualizações frequentes geram arquivos de metadata antigos e arquivos órfãos. Para manter a performance ideal, realizamos manutenções contínuas:

1. Compaction (OPTIMIZE)

O processo de Compaction consolida arquivos pequenos em arquivos maiores otimizados para leitura (geralmente ~512MB ou 1GB). Ele lê múltiplos arquivos de dados e os reescreve de forma combinada e sequencial, gerando novos manifestos de metadados.

-- Comando SQL no Amazon Athena v3 para rodar Compaction
OPTIMIZE iceberg_db.tb_vendas REWRITE DATA (
    'bin-pack' -- Consolida arquivos sem reordenar
);

2. Remoção de Históricos (VACUUM)

O Iceberg provê suporte a Time Travel mantendo snapshots antigos. Sem manutenção, o storage do S3 cresce indefinidamente. O VACUUM (ou expiração de snapshots) apaga os snapshots obsoletos e deleta fisicamente os arquivos do S3.

-- Comando SQL no Amazon Athena para remover dados antigos
VACUUM iceberg_db.tb_vendas RETAIN 7 DAYS; -- Exclui snapshots com mais de 7 dias
✓ Pro Tip (Manutenção Automatizada via PySpark): Para datasets de grande escala, configure tarefas diárias ou semanais via AWS Glue ou EMR usando a API do Spark para gerenciar a expiração de metadados e otimização física: 
# Execução de Spark SQL para otimização de layout de dados
spark.sql("CALL glue_catalog.system.rewrite_data_files(table => 'iceberg_db.tb_vendas', options => map('max-file-size-bytes', '536870912'))")

# Expiração de Snapshots antigos para economizar custos de S3
spark.sql("CALL glue_catalog.system.expire_snapshots(table => 'iceberg_db.tb_vendas', older_than => TIMESTAMP '2026-06-01 00:00:00')")

Amazon Redshift: Introdução Teórica & Arquitetura MPP

O Data Warehouse corporativo escalável baseado em processamento massivamente paralelo

O Amazon Redshift é um serviço de Data Warehouse analítico rápido e totalmente gerenciado em escala petabyte. Ele é construído com base em uma arquitetura de Shared-Nothing e processamento MPP (Massively Parallel Processing). Ao contrário dos bancos transacionais tradicionais (OLTP), que armazenam registros em linhas para rápida inserção/atualização, o Redshift armazena dados em colunas (columnar storage). Isso reduz drasticamente a necessidade de I/O em queries analíticas, pois apenas as colunas envolvidas na query são lidas do disco.

Arquitetura
Leader Node
O nó de coordenação. Recebe a query SQL da aplicação, faz o parsing, gera o plano de execução otimizado, compila código C++ otimizado para o plano e distribui para os Compute Nodes.
Processamento
Compute Nodes & Slices
Os nós que realizam o processamento real. Cada Compute Node possui múltiplos Slices (unidades de processamento com disco e memória dedicados) que executam a query compilada em paralelo.
Armazenamento
RA3 & Managed Storage
Os nós modernos da série RA3 utilizam caches locais SSD de altíssima performance para dados quentes, enquanto o storage frio é arquivado de forma transparente e ilimitada no Amazon S3.

Otimizações de Modelagem Física: Chaves e Distribuição

A performance das consultas no Redshift depende de como os dados são organizados nos discos de cada nó (slices). Configuramos isso via Sort Keys e Distribution Styles (DISTSTYLE):

Conceito Estratégia Cenário Ideal
DISTSTYLE AUTO Padrão inicial Redshift escolhe e muda de ALL para KEY conforme o crescimento do dataset.
DISTSTYLE KEY Baseado em Coluna Colunas que participam frequentemente de JOINS em comum entre fatos e dimensões.
DISTSTYLE ALL Replicação Completa Tabelas de dimensões muito pequenas (< 2-3M registros) copiadas em todos os nós.
DISTSTYLE EVEN Distribuição Circular Tabelas grandes sem chaves claras de JOINS comuns. Balanceamento uniforme garantido.

Sort Keys: Compound vs Interleaved

  • Compound Sort Keys (Padrão): Melhores quando as queries filtram com base em colunas em uma ordem fixa (ex: data_venda e depois id_cliente). O Redshift ordena fisicamente os dados nesta ordem hierárquica.
  • Interleaved Sort Keys: Dá o mesmo peso para todas as colunas em filtros arbitrários (ex: filtro por id_cliente de forma isolada ou data_venda de forma isolada). Útil para tabelas analíticas ad-hoc dinâmicas. Requer manutenção constante de `VACUUM`.

DDL de Produção Otimizado (Redshift):

CREATE TABLE fct_vendas (
    id_venda INT ENCODE az64,
    id_cliente INT ENCODE az64,
    valor_total NUMERIC(12,2) ENCODE az64,
    data_venda TIMESTAMP ENCODE az64
)
DISTSTYLE KEY
DISTKEY(id_cliente)
COMPOUND SORTKEY(data_venda, id_cliente);
✓ Compressão AZ64: Sempre utilize a codificação colunar moderna az64 para tipos numéricos e temporais no Redshift. Ela fornece alta compressão física em disco com performance de descompressão até 70% superior a LZO/ZSTD.

Evolução Arquitetural: Nós RA3 e Managed Storage

Tradicionalmente (nós DS2 ou DC2), o Redshift possuía armazenamento e computação acoplados nativamente na mesma máquina física. Para escalar o disco, você era obrigado a adicionar mais instâncias, aumentando excessivamente os custos de CPU/RAM desnecessários.

Nós RA3 (Desacoplamento)

A família RA3 introduziu o Redshift Managed Storage (RMS). Os dados não ficam mais retidos obrigatoriamente no EBS local. O disco do Compute Node atua apenas como um cache SSD local de altíssima performance para "Dados Quentes" (Hot Data). Dados mais antigos ("Dados Frios") são movidos automaticamente para o S3 de forma transparente.

Isso permite escalar o armazenamento até Petabytes pagando apenas o preço do S3, enquanto a escalabilidade de CPU se mantém desacoplada focada apenas em performance de leitura.

Redshift Data Sharing

Graças ao armazenamento dissociado no RMS, o Redshift introduziu o Data Sharing. Diferente de pipelines ETL complexos de exportação de dados, o Data Sharing permite que o Cluster A (ex: Produtor de Vendas) compartilhe tabelas lógicas ao vivo com o Cluster B (Consumidor Analítico) ou até mesmo com Redshift Serverless.

  • Zero Cópia de Dados: O consumidor lê fisicamente o Managed Storage do produtor, sem replicação.
  • Isolamento Físico: A query de leitura executada pela equipe B consome estritamente a CPU/RAM do Cluster B, preservando a estabilidade e performance dos jobs do Cluster A.

Gerenciamento de Workloads (WLM) e Auto Scaling

Em ambientes com alta concorrência de usuários simultâneos, o banco tradicional bloqueia gerando enfileiramento (queueing). O Redshift lida com isso de duas maneiras estruturais:

Workload Management (AutoWLM e SQA)

O Automatic WLM aloca dinamicamente memória e slots de processamento para diferentes grupos de usuários. Para combater a frustração, o Redshift usa Machine Learning via SQA (Short Query Acceleration).

Se uma query simples ("qual o total de vendas hoje?") entrar atrás de um ETL de 3 horas na fila, o SQA identifica via heurística que a query é curta e cria uma faixa expressa prioritária em um pool oculto de recursos, respondendo-a imediatamente sem que o usuário tenha que esperar o ETL finalizar.

Concurrency Scaling e AQUA

Para picos de acessos extremos, o Concurrency Scaling levanta cópias efêmeras do cluster em milissegundos para absorver leituras. Mas para acelerar queries pesadas na própria base, o Redshift introduziu o AQUA (Advanced Query Accelerator). O AQUA é um cache distribuído construído em instâncias FPGA personalizadas da AWS que fica "abaixo" dos Compute Nodes, próximo ao S3. Ele intercepta as varreduras de dados e executa operações de filtragem (LIKE) e agregação a nível de hardware antes mesmo que os dados trafeguem pela rede até o Compute Node principal, acelerando as queries em até 10x sem custo adicional nos nós RA3.

Query Monitoring Rules (QMR)

Mesmo com WLM e SQA, uma única query mal otimizada com um Join Cartesiano gigante feita por um analista júnior pode derrubar a memória do cluster. As Query Monitoring Rules (QMR) permitem criar limites hard. Exemplo: Abortar query SE bytes_scanned > 500GB E tempo_execução > 300s. Isso garante SLAs estritos de sobrevivência da arquitetura contra o temido erro "Disk Full" no disco temporário do Compute Node.

Análise de Performance de Query via EXPLAIN

Como ler o plano de execução do Redshift e identificar gargalos de redistribuição de dados na rede

Para otimizar queries lentas, execute o comando EXPLAIN na frente do SELECT. O Redshift retorna a árvore de passos do otimizador. O foco principal deve ser a identificação de movimentação física na rede:

EXPLAIN SELECT * FROM fct_vendas v JOIN dim_cliente c ON v.id_cliente = c.id_cliente;
Identificando Gargalos de Distribuição no Plano
  • DS_BCAST_INNER (Broadcast): Muito custoso. O Redshift está copiando a tabela interna inteira na rede para todos os nós por falta de chave de distribuição comum.
    Fix: Mude a chave de distribuição das tabelas para `KEY` usando a chave comum de Join.
  • DS_DIST_BOTH (Re-distribuição): Ambas as tabelas estão sendo re-particionadas em memória via rede durante o Join.
    Fix: Configure chaves idênticas de distribuição KEY na coluna de junção de ambas as tabelas.
  • DS_DIST_NONE (Ideal): Sem tráfego de rede. Os dados a serem unidos já residem nas mesmas fatias de disco locais. Esse é o Join ideal de alta performance.

Exemplo Prático 1: Plano Não Otimizado (DS_BCAST_INNER)

Abaixo vemos o plano gerado quando a tabela menor dim_cliente não possui distribuição por chave compartilhada, exigindo broadcast físico de seus registros para todos os compute nodes:

# EXPLAIN OUTPUT (Tabelas com distribuição circular ou não correspondentes)
XN Hash Join DS_BCAST_INNER  (cost=100.25..54200.40 rows=2500000 width=128)
  Hash Cond: (v.id_cliente = c.id_cliente)
  ->  XN Seq Scan on fct_vendas v  (cost=0.00..25000.00 rows=2500000 width=84)
  ->  XN Hash  (cost=50.00..50.00 rows=50000 width=44)
        ->  XN Seq Scan on dim_cliente c  (cost=0.00..50.00 rows=50000 width=44)

Exemplo Prático 2: Plano Otimizado (DS_DIST_NONE)

Abaixo vemos o plano gerado quando ambas as tabelas são distribuídas pela chave correspondente (id_cliente). Os dados residem nos mesmos discos locais, anulando a necessidade de tráfego de rede:

# EXPLAIN OUTPUT (Ambas as tabelas otimizadas com DISTSTYLE KEY no id_cliente)
XN Hash Join DS_DIST_NONE  (cost=100.25..25150.00 rows=2500000 width=128)
  Hash Cond: (v.id_cliente = c.id_cliente)
  ->  XN Seq Scan on fct_vendas v  (cost=0.00..25000.00 rows=2500000 width=84)
  ->  XN Hash  (cost=50.00..50.00 rows=50000 width=44)
        ->  XN Seq Scan on dim_cliente c  (cost=0.00..50.00 rows=50000 width=44)

Erros Comuns no Consumo & Soluções

Troubleshooting de performance em queries analíticas e cargas de data warehouse

Redshift · COPY
Comando COPY extremamente lento ou travado
Causa: Ingestão baseada em arquivo único massivo CSV bruto no S3. O Redshift não consegue paralelizar e apenas uma slice processa o arquivo todo.

Fix: Salve os dados em múltiplos arquivos Parquet compactados (Snappy/ZSTD) no S3. Alinhe o número de arquivos com o número múltiplo de slices de disco do cluster Redshift.
Athena · Custo
Queries custando dezenas de dólares por execução
Causa: Query varrendo arquivos sem compressão ou sem particionamento, escaneando o bucket do datalake inteiro (Full Table Scan).

Fix: Sempre use formato Parquet, filtre usando colunas de partição ocultas do Iceberg, ou configure Partition Projection limitando o volume de bytes escaneados.
