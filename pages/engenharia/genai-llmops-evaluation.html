LLMOps & Model Evaluation

1. O Problema da Avaliação em GenAI

Diferente do Machine Learning tradicional (onde você avalia a acurácia, F1-Score ou RMSE de forma objetiva), avaliar as respostas de um LLM é muito mais subjetivo. Como saber matematicamente se a resposta de um RAG (Retrieval-Augmented Generation) foi "boa" ou "ruim"? É aqui que entram os frameworks de Evaluation e a disciplina de LLMOps.

🎯

Model Evaluation (Avaliação)

Medir sistematicamente a qualidade (Alucinação, Relevância, Fidelidade) das respostas geradas pelo seu LLM contra um Ground Truth ou dataset de ouro.

🕵️

Tracing & Observability

Monitorar o pipeline em produção. Capturar o Prompt, a latência do VectorDB, o consumo de tokens e a cadeia de pensamento (CoT) dos agentes.

⚙️

Prompt Tracking

Versionar prompts como código (Git) ou no MLflow. Evita o caos de não saber qual prompt gerou qual resposta em produção.

2. Avaliando RAG (Framework RAGAS)

O RAGAS (Retrieval Augmented Generation Assessment) é o padrão de mercado para avaliar sistemas RAG. Ele isola a avaliação em dois eixos: Retriever (A busca no VectorDB foi boa?) e Generator (O LLM gerou a resposta corretamente baseada no contexto?).

Métrica (RAGAS) Avalia o quê? Pergunta Chave Como resolver pontuação baixa?
Faithfulness Generation A resposta foi baseada APENAS no contexto recuperado? (Evita alucinação) Melhorar o Prompt (Ex: "Não use conhecimento prévio, responda apenas com base no texto.")
Answer Relevance Generation A resposta gerada realmente responde à pergunta inicial do usuário? Usar um LLM mais inteligente (Claude 3.5 Sonnet / LLaMA 3 70B).
Context Precision Retrieval Os chunks mais relevantes foram retornados no TOPO da busca (rank 1 e 2)? Adicionar um Re-ranker (ex: Cohere ReRank) após a busca semântica.
Context Recall Retrieval O contexto recuperado tem informações suficientes para responder a pergunta? Melhorar a estratégia de Chunking ou fazer Busca Híbrida.
💡 LLM-as-a-Judge: O RAGAS não usa humanos para dar a nota (0.0 a 1.0) para cada métrica. Ele usa um LLM forte (Geralmente Claude Opus ou GPT-4) atuando como "Juiz" para avaliar a saída do seu sistema RAG de produção.

3. Tracing & Observabilidade de Agentes

Quando você constrói Agentes ou fluxos orquestrados via LangChain/LlamaIndex, um simples prompt do usuário gera múltiplas chamadas à API, queries no banco e decisões lógicas ocultas. Sem Tracing, você fica cego.

Monitorando o Pipeline (LangSmith / MLflow) 
Trace ID: 9f8a-3c2b (Latência Total: 3.4s | Custo Total: $0.003)

└─ User Input: "Quantos clientes temos em atraso e quem é o devedor mestre?"
   ├─ Tool: Text-to-SQL (Latência: 1.2s | Tokens: 400)
   │  └─ Output: SELECT COUNT(*) FROM tb_clientes WHERE status = 'atraso'
   ├─ Tool: Vector Search (Latência: 0.5s | Documents: 3)
   │  └─ Output: [Doc1: "O devedor mestre é a Empresa X..."]
   └─ LLM Synthesize (Latência: 1.7s | Tokens: 850)
      └─ Output: "Temos 450 clientes em atraso. O devedor mestre é a Empresa X."

No ecossistema corporativo, isso é feito interceptando as chamadas via Callbacks. Na AWS, você pode enviar esses rastros de telemetria diretamente para o Amazon Bedrock (Model Invocation Logging) gravando no CloudWatch ou S3.
