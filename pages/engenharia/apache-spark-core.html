Apache Spark & Amazon EMR

Arquitetura profunda de processamento distribuído, otimização física de CPU/memória e guias práticos de tuning e troubleshooting.

01

Apache Spark: Introdução Teórica & Abstrações

Visão geral sobre o motor distribuído em memória e abstrações de dados fundamentais

O Apache Spark é um motor de computação distribuída projetado para processamento de big data de alta performance. Diferente do ecossistema Hadoop tradicional (que grava resultados intermediários de map-reduce no HDFS), o Spark opera prioritariamente em memória (in-memory processing), mantendo os dados cacheados na RAM dos executores e reduzindo o gargalo de I/O de disco físico. O ciclo de otimização do Spark baseia-se no Catalyst Optimizer, que compila expressões SQL lógicas em código Java otimizado em tempo de execução (JIT).

Abstração
RDD (Resilient Distributed Dataset)
Abstração de baixo nível do Spark. Garante tolerância a falhas armazenando a árvore de lineage necessária para recomputar partições perdidas do cluster em caso de falhas físicas.
Abstração
DataFrame & Dataset
Abstração de alto nível com schemas estruturados. Permite ao Catalyst Optimizer otimizar a query, colapsando projeções e empurrando predicados para leitura física de arquivos.
Execução
Lazy Evaluation & DAG
Operações no Spark apenas constroem um grafo acíclico direcionado (DAG) que é otimizado e compilado. A execução real só é acionada após a chamada de uma Action.
Compartilhamento
Shared Variables (Broadcast & Accumulators)
Broadcast: Variáveis read-only distribuídas uma vez por nó (não por task). Accumulators: Variáveis write-only para contadores agregados de forma associativa e comutativa no Driver.
Metadados
Spark Catalog & Hive Metastore
Interface de abstração para gerenciar metadados de tabelas, databases, funções e views. No EMR, geralmente integra-se ao AWS Glue Data Catalog para persistência global.
Performance
Protocolos de Serialização
O Spark usa Java Serialization por padrão, mas o Kryo Serialization é recomendado por ser 10x mais compacto e veloz, reduzindo o uso de rede durante Shuffles.
Recurso
Spill to Disk
Mecanismo de segurança onde dados transbordam da RAM para o disco local (EBS/Instance Store). Causa lentidão massiva (I/O Wait), mas evita o travamento total do cluster por OOM.

Gerenciamento de Memória Unificado (Unified Memory Management)

A partir do Spark 1.6, o Unified Memory Manager flexibilizou a barreira rígida entre Execution e Storage Memory. A fração conjunta (spark.memory.fraction, padrão 60% da Heap) é compartilhada dinamicamente:

  • Eviction Dinâmica: Se a Execution Memory precisar de mais espaço durante um Shuffle ou Join e houver memória ociosa no bloco de Storage, ela pode "despejar" (evict) blocos em cache (salvando em disco se configurado com MEMORY_AND_DISK) para evitar o erro de Out of Memory (OOM).
  • Imunidade da Execution Memory: O inverso não é verdadeiro. A Storage Memory não pode expulsar dados da Execution Memory, pois isso interromperia o processamento ativo da Task.
  • Unroll Memory: Antes de um bloco de dados ser efetivamente armazenado no cache (Storage), o Spark precisa "desenrolar" (unroll) os dados serializados iterando pelos registros. Esse processo consome memória temporária que é alocada e contabilizada como parte da Storage Memory. Caso não haja espaço suficiente para desenrolar o bloco, ele nem chega a ser armazenado.
  • Off-Heap Execution: Ativar o spark.memory.offHeap.enabled = true e configurar spark.memory.offHeap.size permite que o Project Tungsten aloque dados brutos diretamente na memória do sistema operacional usando a API Unsafe. Essa abordagem escapa completamente do ciclo de Garbage Collection do Java, resultando em pausas nulas e alta performance para operações intensivas em ponteiros.
02

Arquitetura e Ciclo de Execução Spark

Orquestração distribuída profunda: Driver, Cluster Manager e Workers/Executors

A execução física de uma aplicação Spark segue um modelo mestre-escravo coordenado de forma centralizada pelo Driver Node e escalado horizontalmente através de Workers (Executors) controlados por um Cluster Manager (como YARN, Kubernetes ou o mestre do EMR). Compreender os componentes lógicos abaixo é essencial:

  • Driver (Mestre): O processo que executa o main() do usuário, inicia o SparkSession, constrói a DAG (Directed Acyclic Graph), coordena o planejamento lógico e físico das consultas com o Catalyst Optimizer e agenda tarefas físicas através do Task Scheduler.
  • Cluster Manager: O enforcer externo (ex: ResourceManager do YARN ou K8s Control Plane) que aloca contêineres e recursos de máquina física sob demanda ao cluster.
  • Worker Node / Executor JVM: Processos isolados em execução nas máquinas do cluster que executam as tarefas individuais de dados (Tasks), armazenam dados em cache (Storage Memory) e gravam logs e dados intermediários de rede (Shuffle Files). Cada Executor possui vCPUs alocadas (cores) e memória RAM Heap/Off-Heap.

Ciclo de Execução: Do Código da Aplicação à Computação no Cluster

Quando uma ação (Action) é chamada na aplicação PySpark:

  1. Criação do Plano Lógico: O Spark compila o código em uma DAG de transformações lógicas lazy.
  2. Divisão em Jobs: Cada Action dispara exatamente um Job no Spark.
  3. Fatiamento em Stages: O DAG Scheduler analisa as dependências lógicas. Se houver dependência estreita (Narrow Dependency, ex: select, filter), as operações rodam juntas no mesmo estágio. Se houver dependência larga (Wide Dependency, ex: groupBy, join), o Spark quebra a execução em um novo Stage, pois exige troca de registros pela rede (Shuffle).
  4. Despacho de Tasks: Cada Stage é dividido em Tasks físicas (exatamente uma task para cada partição de dados do DataFrame). O Task Scheduler despacha as tasks para os executores com capacidade ociosa de cores.
02.5

Hadoop, YARN e a Pirâmide de Execução do Spark

A base física infraestrutural e a hierarquia lógica de comando

Para dominar o Spark no EMR, é preciso entender que ele não roda no vácuo. O Spark utiliza o Hadoop YARN (Yet Another Resource Negotiator) como seu Cluster Manager padrão. O YARN é o "sistema operacional" do cluster, responsável por fatiar o hardware físico (CPU/RAM) em unidades isoladas chamadas Containers.

Componentes do YARN

  • ResourceManager (RM): O mestre global (no Master Node). Ele decide quem ganha recursos no cluster.
  • NodeManager (NM): O agente local em cada Worker. Monitora o consumo de recursos do nó e reporta ao RM.
  • ApplicationMaster (AM): Um container especial (um por aplicação Spark) que negocia recursos com o RM e coordena os Executors. No Spark, o Driver pode atuar como AM ou lançar um AM separado (modo cluster).

A Pirâmide de Execução Spark

Existe uma hierarquia rigorosa de como o código se transforma em processamento:

  1. Application: O programa completo (ex: seu script PySpark).
  2. Job: Disparado por uma Action (ex: .save(), .collect()).
  3. Stage: Conjunto de tasks que podem rodar sem mover dados pela rede. Quebrado por Shuffles.
  4. Task: A menor unidade de trabalho. Processa uma única partição física de dados em um único core de CPU.

03

Cálculo de Alocação de Memória, Cores & Particionamento

Spark Executor Memory Allocation Formula
Fórmula Especialista: Se você tem uma máquina de 32GB e pede spark.executor.memory = 32g, seu job vai FALHAR com Container killed by YARN for exceeding memory limits. Por quê? Porque o YARN precisa alocar a Heap Memory + Memory Overhead + espaço do OS. A regra de ouro é pedir no máximo 85% da memória física como YARN Container, e desse container, reservar 10% para o memoryOverhead.

Fórmulas práticas de dimensionamento físico para instâncias EC2 e regras de ouro de paralelismo

Dimensionar incorretamente as configurações de submissão do Spark gera instabilidade ou desperdício severo de custos de infraestrutura analítica no EMR. Abaixo estão descritas as contas detalhadas para duas famílias de instâncias EC2 de hardware distintos, seguidas do passo a passo matemático prático para dimensionar qualquer cluster:

Fórmula de Dimensionamento Físico de Executores (Passo a Passo):
  1. Passo 1 (Recursos Disponíveis para o YARN): Deixe sempre 1 core físico e cerca de 4 GB a 8 GB de RAM por nó reservados estritamente para o funcionamento do sistema operacional e do Daemon do YARN NodeManager. O restante é o pool disponível de fato para o Spark.
  2. Passo 2 (Cores por Executor): Defina spark.executor.cores = 5 por padrão. Este é o número ideal testado na indústria: acima de 5 cores, o processamento sofre com contenção de escrita concorrente em disco de shuffle e gargalos na coleta de rede da JVM; abaixo de 5, perde-se a localidade local de leitura multithread.
  3. Passo 3 (Executores por Nó): Divida a quantidade de cores restantes no nó (Passo 1) por 5 (Passo 2). Exemplo: Se sobram 15 cores, teremos 15 / 5 = 3 executores por nó.
  4. Passo 4 (Memória por Executor & Overhead): Divida a RAM disponível por nó pelo número de executores calculados no Passo 3. Do resultado, deduza cerca de 10% a 15% para a memória de Overhead do Spark (spark.executor.memoryOverhead, com mínimo absoluto de 384 MB). O restante é a Heap do Executor.

Cenário 1: Instância Memory-Optimized (r5.4xlarge)

  • Hardware Físico: 16 vCPUs (cores) e 128 GB RAM.
  • Reserva do S.O. & YARN: 1 core e 4 GB RAM. Sobram 15 cores e 124 GB RAM.
  • Cores por Executor: Fixado em 5 cores.
  • Quantidade de Executores por nó: 15 / 5 = 3 executores por nó.
  • Memória total disponível por executor: 124 GB / 3 = 41.3 GB.
  • Ajuste do Overhead (10%):
    • spark.executor.memory = 37g
    • spark.executor.memoryOverhead = 4g (37g * 0.10 ≈ 3.7g -> arredondado para 4g).

Cenário 2: Instância Compute-Optimized (c5.9xlarge)

  • Hardware Físico: 36 vCPUs (cores) e 72 GB RAM.
  • Reserva do S.O. & YARN: 1 core e 4 GB RAM. Sobram 35 cores e 68 GB RAM.
  • Cores por Executor: Fixado em 5 cores.
  • Quantidade de Executores por nó: 35 / 5 = 7 executores por nó.
  • Memória total disponível por executor: 68 GB / 7 = 9.7 GB.
  • Ajuste do Overhead (10%):
    • spark.executor.memory = 8g
    • spark.executor.memoryOverhead = 1g (excedente necessário para operações de runtime).

Parâmetros de Recursos — Referência Rápida

Parâmetro do Spark Valor Recomendado O que Controla Físicamente
spark.executor.cores 4 ou 5 Número de threads paralelas rodando simultaneamente por executor.
spark.executor.memory 16g a 48g (depende da instância) Quantidade máxima de RAM alocada para a Heap da JVM por executor.

⚠️ Armadilha Frequente: Dynamic Allocation sem Limites Claros
Habilitar alocação dinâmica (spark.dynamicAllocation.enabled = true) sem definir tetos restritos pode esgotar toda a capacidade do seu cluster YARN e gerar concorrência excessiva de I/O em disco. Configure sempre com limites rígidos em produção: 
spark.dynamicAllocation.enabled = true
spark.dynamicAllocation.minExecutors = 1
spark.dynamicAllocation.maxExecutors = 100
spark.dynamicAllocation.initialExecutors = 5
spark.dynamicAllocation.executorIdleTimeout = 60s
spark.dynamicAllocation.schedulerBacklogTimeout = 1s
No EMR EC2, prefira o Managed Scaling no nível de infraestrutura do cluster em vez de configurações desreguladas de Dynamic Allocation puras de aplicação para melhor controle de FinOps.

Regras de Ouro de Particionamento & Paralelismo

📏 Tamanho Ideal de Partição

O tamanho ótimo de partição física na RAM e no disco deve residir entre 128 MB e 512 MB.

  • Partições Pequenas (<10 MB): Geram um overhead monstruoso de agendamento de tarefas na CPU (Task Scheduling Overhead) no Driver.
  • Partições Gigantes (>2 GB): Geram estouro de Heap na JVM do executor (Java Heap Space OOM) e forçam spillage ineficiente para o disco local.

🔄 shuffle.partitions vs default.parallelism

  • spark.sql.shuffle.partitions (Padrão: 200): Controla estritamente o número de partições criadas após operações físicas de Shuffle em APIs SQL e DataFrames (ex: Joins, GroupBy).
  • spark.default.parallelism: Controla o número padrão de partições geradas após transformações de RDDs de baixo nível se o usuário não especificar.
  • Ação do AQE: Se o Adaptive Query Execution (AQE) estiver ativado, o Spark junta partições pequenas pós-shuffle em runtime automaticamente, mitigando configurações estáticas incorretas.
04

Tungsten & JIT: Engine de Execução Física

Aceleração física em nível de hardware, alocação de memória direta e Whole-Stage CodeGen

O Project Tungsten e o compilador Just-In-Time (JIT) formam a base da performance moderna do Spark. A premissa central é que a barreira para o processamento distribuído mudou do I/O (Disco/Rede) para a CPU e memória. O Tungsten otimiza agressivamente o modo como as instruções são dadas aos registradores da CPU e como os bytes são alocados na memória, escapando das abstrações pesadas da Java Virtual Machine (JVM).

CATALYST OPTIMIZER → TUNGSTEN ENGINE → JIT CODEGEN
Explicação:

Physical Planner AQE (Broadcast Hash Join vs Sort-Merge Join), PROJECT TUNGSTEN, Whole-Stage CodeGen (Janino bytecode, *HashAggregate), Off-Heap Memory (Unsafe API, sem GC), JVM JIT Compiler (Native Machine Code, CPU Registers / L1)
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas indicam a direcionalidade entre os elementos do diagrama.
  • Contexto: O diagrama ilustra o pipeline de compilação do Spark: o Catalyst Optimizer transforma o código DataFrame em plano físico otimizado, o Tungsten gera bytecode e aloca memória off-heap sem GC, e o JIT da JVM compila para código nativo que roda diretamente nos registradores da CPU.

⚙️ Deep Dive: Whole-Stage CodeGen e Eliminação de Funções Virtuais

No processamento SQL tradicional (Modelo Vulcano), cada operador na query (ex: Filter -> Project -> Aggregate) chama um método .next() para buscar a próxima linha. Essas chamadas de funções virtuais têm alto custo na CPU, causando falhas nos preditores de branch de hardware e quebrando o pipeline da CPU.

A Solução: O Tungsten gera um código Java único que colapsa toda a árvore de operações em uma única função otimizada com um loop "for". O Janino compiler compila esse Java em tempo de execução para bytecode, e a JVM aplica o JIT (Just-In-Time) compilation para gerar as instruções de máquina da CPU host.

🔍 Prática: Encontrando o JIT na Spark UI

Como saber se o seu código foi acelerado? Abra a aba SQL/DataFrame na Spark UI. Operadores marcados com um asterisco (ex: *(1) Filter ou *(2) HashAggregate) significam que múltiplas etapas foram compiladas dinamicamente em uma única função nativa.

Você também pode usar df.explain(True) no console. O plano físico mostrará "WholeStageCodegen" envolvendo os operadores que foram fundidos para rodar na CPU como código nativo otimizado.

Catalyst Optimizer: O Coração Estruturado do Spark

O Catalyst Optimizer é um otimizador extensível baseado em regras escrito em Scala que gerencia todo o ciclo de compilação lógica de consultas DataFrame/SQL:

  1. Análise (Analysis): O Spark analisa a sintaxe da query e consulta o Catalog (ex: Glue Data Catalog) para resolver nomes de colunas, tabelas e tipos lógicos. Retorna um Analyzed Logical Plan.
  2. Otimização Lógica (Logical Optimization): Aplica regras de transformação clássicas como Constant Folding (calcula valores constantes estáticos em tempo de otimização) e Predicate Pushdown (empurra filtros para a leitura do arquivo no S3, evitando carregar dados indesejados).
  3. Planejamento Físico (Physical Planning): Gera múltiplos planos físicos reais baseado nas estatísticas da tabela (Custo Físico). O Spark calcula o custo computacional de cada plano (ex: escolher entre Sort-Merge Join ou Broadcast Hash Join) e seleciona o mais barato.
  4. Geração de Código (Code Generation): Compila o plano físico escolhido em bytecode Java (através do Janino compiler) rodando nativamente na JVM dos executores. O Whole-Stage CodeGen colapsa várias operações em um único loop em Java.
5. O Pitch de Business Value (Proposta de Valor)

Ao modernizar os pipelines para aproveitar plenamente a API de DataFrame em vez de RDDs ou UDFs complexos, habilitamos o Tungsten e o JIT para atingir Time-to-Market de dados em frações do tempo original. Do ponto de vista de EBITDA e FinOps, a geração dinâmica de código e alocação eficiente da CPU L1/L2 significa que os jobs executam até 10x mais rápido. Isso reduz diretamente as horas/máquina faturadas (OPEX) no cluster AWS, melhorando margens de lucro operacionais e destravando recursos para outras iniciativas de análise de dados sem aumento do TCO.
