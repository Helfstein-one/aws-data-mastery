Os Três Pilares de Orquestração da AWS

Diferenças arquiteturais entre MWAA (Airflow), Step Functions e Glue Workflows

AWS ORCHESTRATION LANDSCAPE
Explicação:
  • Time-Driven (MWAA): Orquestração baseada em rotinas agendadas (cron), construindo Grafos Direcionados Acíclicos (DAGs) complexos para processamento batch no EMR ou Glue.
  • Event-Driven (Step Functions): Orquestração reativa (desencadeada pelo EventBridge), construindo Máquinas de Estado Serverless com transições de sucesso/falha para acionar Lambdas e Glue Jobs.

A orquestração de dados garante a execução lógica, ordenada e segura de tarefas de engenharia de dados (extração, carga, validação de qualidade e transformação). A tabela abaixo fornece o comparativo de tradeoffs essenciais para escolha de arquitetura:

Critério Amazon MWAA (Airflow) AWS Step Functions AWS Glue Workflows
Modelo Mental Baseado em tempo/agendamento (Time-driven) e DAGs complexas. Baseado em eventos (Event-driven) e transições de Estado. Orquestrador nativo e simples para recursos Glue.
Custo base Fixo por ambiente ativo (~$350/mês mínimo para MWAA). Por transição de estado (Serverless total - $0 se ocioso). Gratuito (cobra apenas o consumo das DPUs do Glue rodando).
Escalabilidade Escala horizontal de workers Fargate (demora minutos). Escala instantaneamente até milhares de execuções concorrentes. Limitada ao escopo do Glue Catalog e recursos nativos.
Limitações Overhead operacional de pacotes Python e latência de scheduler. Payload máximo de entrada/saída limitado a 256 KB. Incapaz de orquestrar recursos de fora do ecossistema Glue/S3.
Pontos de Atenção (Gotchas de Custo Silencioso):
• MWAA NAT Gateway Costs: O MWAA exige subredes privadas com NAT Gateway para baixar pacotes do PyPI e comunicar com o control plane da AWS. Se a sua DAG exporta gigabytes de dados pela internet pública através de conexões não otimizadas, a taxa de tráfego de dados do NAT Gateway pode superar o custo de processamento do Airflow. Habilite obrigatoriamente VPC Endpoints (S3, Glue, Athena, KMS) na VPC do MWAA.
• State Machine Loop Limits: Rodar loops infinitos ou processamento de milhares de itens um a um no Step Functions Standard pode inflar drasticamente o custo por transição de estado. Use o modo Express State Machines para fluxos rápidos orientados a eventos, e o modo Standard exclusivamente para fluxos de longa duração com dependência de aprovações humanas.

AWS Step Functions: State Machines para Pipelines

ASL (Amazon States Language), tratamento de erro ativo com Retry/Catch e IaC Terraform

O AWS Step Functions orquestra workflows serverless distribuídos. Sua grande vantagem reside no suporte nativo ao padrão SDK Integration, permitindo chamar serviços (como Glue, ECS, Athena) de forma direta e assíncrona usando o sufixo .sync, fazendo a State Machine aguardar a conclusão do Job de forma transparente e resiliente.

Amazon MWAA: Apache Airflow em Escala Corporativa

Design de arquitetura distribuída, gerenciamento de estado das tarefas e orquestração de DAGs complexas

O Amazon MWAA (Managed Workflows for Apache Airflow) elimina a dor de cabeça de configurar clusters do Kubernetes, bancos Postgres externos (Metastore) e servidores web para rodar o Airflow. A AWS gerencia o autoscaling horizontal dos workers baseando-se no número de tarefas na fila (usando Celery Executor e Fargate Tasks).

Código Prático: DAG Python para Ingestão e Processamento (Athena & Glue)

O script abaixo demonstra uma DAG Airflow completa utilizando operadores modernos que disparam tarefas e aguardam ativamente sua conclusão, incluindo regras de ramificação e callbacks de falha:

from datetime import datetime, timedelta
from airflow import DAG
from airflow.providers.amazon.aws.operators.glue import GlueJobOperator
from airflow.providers.amazon.aws.operators.athena import AthenaOperator
from airflow.operators.empty import EmptyOperator

default_args = {
    'owner': 'data-platform-team',
    'depends_on_past': False,
    'start_date': datetime(2026, 1, 1),
    'retries': 2,
    'retry_delay': timedelta(minutes=5),
}

# Definição do escopo da DAG
with DAG(
    dag_id='mwaa_etl_orchestration_flow',
    default_args=default_args,
    description='DAG corporativa para rodar carga Glue e atualizacao Athena',
    schedule_interval='0 6 * * *', # Todos os dias às 6h da manhã
    catchup=False,
    max_active_runs=1, # Evita concorrência e race condition em escritas S3
) as dag:

    start = EmptyOperator(task_id='start_pipeline')

    # Task 1: Dispara o Job PySpark no AWS Glue e aguarda (wait_for_completion=True)
    run_glue_pyspark = GlueJobOperator(
        task_id='run_glue_pyspark_job',
        job_name='prod-processamento-vendas-job',
        script_args={
            '--env': 'production',
            '--exec_date': '{{ ds }}'
        },
        aws_conn_id='aws_default',
        wait_for_completion=True,
    )

    # Task 2: Executa query de otimização analítica no Athena (Compaction/Vacuum)
    run_athena_optimize = AthenaOperator(
        task_id='optimize_iceberg_table',
        query="OPTIMIZE iceberg_db.tb_vendas REWRITE DATA ('bin-pack')",
        database='iceberg_db',
        output_location='s3://prod-athena-query-results-bucket-xyz/output/',
        aws_conn_id='aws_default',
    )

    end = EmptyOperator(task_id='end_pipeline')

    # Cadeia de dependências lógicas
    start >> run_glue_pyspark >> run_athena_optimize >> end

2. O Princípio da Idempotência (Golden Rule)

Por que Idempotência separa Juniores de Seniores?

Em engenharia de dados, Idempotência significa que uma tarefa pode ser re-executada infinitas vezes e o estado final do banco de dados será sempre o mesmo, sem duplicar registros.

  • Abordagem Junior (Não Idempotente): Fazer INSERT INTO lake_table SELECT * FROM raw_layer. Se a DAG falhar no meio, um retry vai duplicar os dados amanhã.
  • Abordagem Sênior (Idempotente): Fazer `MERGE` (Upsert no Iceberg), ou deletar a partição D-1 `DELETE FROM table WHERE data='2024-01-01'` antes de rodar o `INSERT` do lote. Airflow depende da idempotência dos workers para garantir a sanidade dos dados em caso de falhas.
