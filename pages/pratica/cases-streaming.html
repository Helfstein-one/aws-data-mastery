Case 1: Plataforma de Eventos de Streaming E-commerce (High-Throughput)

Ingestão assíncrona em tempo real para prevenção de fraudes e persistência ACID em Lakehouse Iceberg

Este caso prático ilustra a infraestrutura de uma empresa de varejo global que precisa coletar cliques, visualizações, adições ao carrinho e compras em tempo real. O sistema deve atender a dois requisitos conflitantes: baixa latência para alimentar um motor de análise de fraudes em tempo real e estruturação barata no S3 (formato colunar indexado) para análises analíticas e machine learning.

Detalhamento do Fluxo Operacional Passo a Passo

  1. Ingestão Escalável com ECS Fargate & ALB: Os aplicativos de clientes e navegadores web disparam requisições POST para a rota de coleta. O Application Load Balancer (ALB) intercepta as chamadas e as balanceia de forma round-robin entre as tarefas do contêiner rodando no Amazon ECS Fargate. O uso de Fargate elimina a gerência de servidores de computação tradicionais. O contêiner de ingestão é ultra-leve (escrito em Python FastAPI ou Go) e sua única responsabilidade é validar sintaticamente a estrutura básica e escrever a mensagem assincronamente no Kinesis.
  2. Desacoplamento e Escala com Kinesis Data Streams: O Kinesis Data Streams age como buffer absorvendo picos violentos de tráfego. Ele está configurado em modo *Provisionado* ou *On-Demand* com partições (shards) que escalam conforme a volumetria de entrada. A chave de partição (Partition Key) é definida como o id_usuario para garantir que eventos de um mesmo usuário caiam no mesmo shard, mantendo a ordem sequencial das transações.
  3. Caminho Rápido (Speed Path) - Prevenção de Fraudes: Uma função AWS Lambda lê micro-lotes (batch window de 1 segundo) diretamente dos Shards do Kinesis com baixíssima latência. O Lambda executa regras de fraude rápidas baseadas em padrões (ex: compras sequenciais em menos de 2 segundos) e atualiza o estado operacional instantaneamente no Amazon DynamoDB (chave-valor de latência inferior a 10ms).
  4. Caminho Analítico (Storage/Batch Path) - Firehose e Compactação: Em paralelo, o Kinesis Data Firehose consome do stream. Ele realiza buffering (ex: aguarda encher 128MB ou completar 5 minutos) para evitar o problema de arquivos pequenos (*Small Files*). O Firehose lê o catálogo de metadados do AWS Glue e converte dinamicamente os payloads JSON para o formato binário colunar Apache Parquet antes de gravar os arquivos na camada Bronze do Amazon S3.
  5. Camada de Otimização e Qualidade (AWS Glue Spark Job): Um Job periódico do AWS Glue (PySpark) lê os arquivos Parquet da camada Bronze. Ele executa três etapas cruciais:
    • De-duplicação: Utiliza o DropDuplicates com base no ID único do evento, tratando duplicidades inevitáveis em sistemas distribuídos (at-least-once).
    • Mecanismo de Data Quality (DQDL): Executa testes declarativos de integridade. Se o lote tiver um índice de falhas intolerável, aciona o disjuntor enviando o lote corrompido para o bucket de Quarentena e disparando um alerta no Slack via Amazon EventBridge. Se passar, grava os dados na camada Silver em tabelas formatadas em Apache Iceberg.
    • Tuning do Iceberg: Executa o comando Spark SQL OPTIMIZE table REWRITE DATA para mesclar arquivos temporários em blocos maiores e remover metadados obsoletos.
  6. Consumo Analítico Federado: Cientistas de dados e analistas de BI utilizam o Amazon Athena para realizar consultas SQL analíticas complexas e rodar relatórios no QuickSight consumindo diretamente da camada Silver/Gold sem que o processamento interfira na latência transacional da aplicação.

Interações Principais e Fluxo de Dependências

  • ECS Fargate → Kinesis Data Streams: Os contêineres ECS mantêm instâncias persistentes do cliente Boto3 do Kinesis em memória global. Recriar o cliente HTTP/SDK a cada requisição adiciona um handshake SSL lento e desnecessário. A API publica no Kinesis usando PutRecords (em lote de até 500 registros por chamada) para otimizar throughput de rede.
  • Firehose → Glue Schema Catalog → S3 Bronze: O Kinesis Firehose consome continuamente os eventos. A cada intervalo de buffer, ele solicita o esquema de colunas ao Glue Catalog. Caso algum payload JSON possua campos corrompidos impossíveis de converter em Parquet, o Firehose desvia a mensagem para uma pasta específica processing_failed/ no bucket Bronze, permitindo que a ingestão não pare por causa de arquivos mal formatados.

Possibilidades de Desmembramento e Modularização

Para otimizar o ciclo de desenvolvimento, isolar falhas e garantir a governança por equipes autônomas, esta arquitetura pode ser desmembrada em três módulos independentes:

1. Microsserviço de Ingestão (API)

O ALB + ECS Fargate pode ser isolado como um microsserviço de borda com pipeline de CI/CD próprio. Ele expõe um endpoint REST estável e grava no Kinesis sem conhecer os processos analíticos downstream, permitindo deploys frequentes sem impactar o Data Lake.

2. Motor de Prevenção de Fraude

O fluxo de baixa latência (Kinesis Data Streams + Lambda + DynamoDB) pode rodar em uma conta AWS separada de Risco/Segurança. A leitura concorrente das partições do Kinesis garante que análises analíticas pesadas não gerem latência na prevenção de fraudes.

3. Pipeline de Analytics & Lakehouse

A ingestão assíncrona baseada em Kinesis Firehose + Glue Spark + S3 Silver pode ser mantida pela equipe de Engenharia de Dados Central. A transformação e compactação periódica das tabelas Apache Iceberg ocorrem em background, isoladas do tráfego web real-time.

Pontos de Atenção Críticos para Produção (Case 1)

Pontos de Atenção da Engenharia:
  • Throttling de Gravação no Kinesis: Cada Shard do Kinesis suporta no máximo 1 MB/s ou 1000 registros/s de escrita. Sob pico de 50x, se a quantidade de shards não escalar dinamicamente (Split Shards), o ECS receberá erros de ProvisionedThroughputExceededException. Os contêineres devem amortecer isso implementando buffers de memória locais e retentativas exponenciais com Jitter.
  • Buffer do Firehose e Small Files: Configurar o Firehose com buffers pequenos (ex: 5MB ou 60s) gera milhões de arquivos minúsculos no S3. O ideal para o pipeline analítico é fixar o buffer no limite máximo suportado pelo seu SLA (ex: 128MB ou 5 minutos) para que os arquivos cheguem na Bronze com tamanhos saudáveis para leitura.
  • DynamoDB WCU Exhaustion: O Lambda que avalia a fraude pode escalar horizontalmente em milissegundos. Se a tabela do DynamoDB estiver em modo Provisionado com WCUs baixos, o Lambda sofrerá throttling ao registrar transações. Ative o modo On-Demand (Pay-Per-Request) na tabela do DynamoDB para mitigar picos agressivos de transações do e-commerce.

A plataforma deve absorver esses fluxos com alta durabilidade, persistir em tabelas de séries temporais de baixa latência para monitoramento do operador em tempo real e estruturar um Datalake histórico para treinamento de modelos de IA de detecção de anomalias.

O IoT Core Rules Engine intercepta as mensagens publicadas no tópico e aplica filtros em SQL (ex: SELECT * FROM 'telemetry/#' WHERE temperatura > 80).

O AWS Glue Job subsequente compacta e de-duplica as mensagens gravando em tabelas formatadas em Apache Iceberg para fins de Datalake corporativo de longa retenção.
  4. Inteligência Preditiva com Amazon SageMaker: Cientistas de dados utilizam o Amazon SageMaker para ler os dados analíticos históricos da camada Iceberg, treinar modelos de previsão de séries temporais e detecção de anomalias (como floresta de isolamento ou XGBoost), exportando os pesos para inferência operacional de manutenção preventiva em máquinas físicas.

Interações Principais e Fluxo de Dependências

  • IoT Core Rules Engine → Timestream & Firehose: A regra age como um roteador declarativo (circuit splitter). O processador envia dados com formatos otimizados para séries temporais (medidas, dimensões) ao Timestream, e payload bruto estruturado ao Firehose sem requerer código intermediário computacional, economizando custos.

Possibilidades de Desmembramento e Modularização

Nas fábricas inteligentes, a separação entre operações de tempo real e modelagem preditiva estatística é fundamental. O desmembramento se dá em três frentes:

1. Gateway de Telemetria IoT

O AWS IoT Core funciona como um broker MQTT gerenciado ultra-disponível. Ele recebe as mensagens dos sensores industriais e usa regras nativas (IoT Rules) para rotear mensagens de forma isolada, impedindo que falhas em downstream afetem o fluxo de recebimento.

2. Monitoramento Operacional (Real-Time)

O processamento analítico de streaming com Kinesis Data Analytics (Flink) e gravação no Amazon Timestream roda de forma ininterrupta. Ele serve painéis operacionais e sistemas SCADA de alarmes rápidos, isolado de pipelines pesados.

3. Laboratório de IA e Analytics Histórico

O pipeline offline com AWS Glue + S3 Silver (Iceberg) + SageMaker treina modelos preditivos a partir dos dados consolidados no S3. O deploy do modelo em endpoints REST independentes serve inferências preditivas sem interferir nos alarmes de chão de fábrica.

Pontos de Atenção Críticos para Produção (Case 4)

Pontos de Atenção da Engenharia:
  • Timestream RAM Storage TTL Costs: O Timestream gerencia automaticamente dois níveis de armazenamento: memória (RAM) e magnético (Cold). Armazenamento em memória RAM é extremamente caro. Configurar um TTL em memória muito longo (ex: > 3 dias) gera faturas astronômicas. Configure o TTL da RAM para poucas horas (ex: 2h a 6h) e delegue análises históricas longas para o disco magnético ou para o S3.
  • Out-of-Order Data em Séries Temporais: Sensores industriais em áreas remotas perdem conexão de rede e enviam dados acumulados atrasados com timestamps retroativos. O Timestream rejeita inserções que ultrapassam o limite de janela configurado de registros passados. Ajuste a janela de inserção tardia (Magnetic store write property) para cobrir o SLA de desconexão das máquinas físicas.

Case 6: Feature Store Real-time & Motor de Recomendação

Processamento e serving de features de baixa latência usando SageMaker Feature Store, cacheamento em Redis e inferência de recomendação em ECS Fargate

Uma plataforma de streaming de mídia precisa sugerir vídeos de forma altamente personalizada. O motor de IA necessita de dados em tempo real (ex: últimas 5 categorias de vídeos assistidos nos últimos 10 minutos) e dados históricos (ex: preferência de gênero dos últimos 6 meses). A arquitetura implementa uma Feature Store dual (Online de baixíssima latência e Offline para histórico) para servir os modelos de Machine Learning.

Explicação:

  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.

Detalhamento do Fluxo Operacional Passo a Passo

  1. Ingestão em Stream de Alta Frequência: Eventos de cliques de navegação (clickstream) e visualizações de vídeos são empurrados para o Amazon Kinesis Data Streams.
  2. Agrupamento e Agregação via Spark Streaming (EMR): Um Job contínuo do Structured Spark Streaming rodando no EMR Serverless consome os eventos, executa agregações em janelas de tempo deslizantes (ex: soma de categorias assistidas nos últimos 10 minutos por ID do usuário) e escreve na Feature Store.
  3. Dupla Persistência na SageMaker Feature Store: A SageMaker Feature Store gerencia automaticamente a dupla gravação:
    • Online Store (Baixa Latência): Armazena apenas o estado mais recente de cada feature no DynamoDB (ou Redis corporativo) para serving rápido (<10ms).
    • Offline Store (Histórico): Agrupa modificações e as escreve periodicamente no Amazon S3 em formato Parquet para treinamento de novos modelos e retrocesso temporal (time-travel).
  4. Serving de Inferência com Latência de Milissegundos: A API de recomendação rodando em ECS Fargate recebe a requisição do usuário. Ela consulta a Online Feature Store para resgatar as features comportamentais recentes do ID do usuário, alimenta o modelo local de recomendação e retorna a lista ordenada de conteúdos sugeridos.

Possibilidades de Desmembramento e Modularização

Para garantir que recomendações em tempo real sejam fornecidas em menos de 10ms, separamos a atualização de variáveis do cálculo de inferência:

1. Streaming Feature Ingestion

Processadores Spark Streaming (rodando no EMR) consomem logs brutos de cliques do Kinesis e atualizam as variáveis de estado no cache de baixíssima latência (Online Feature Store no Redis ou DynamoDB) de forma assíncrona, desacoplada do cliente web.

2. Feature Store (Online & Offline)

O armazenamento é segmentado fisicamente. A Online Store (Redis/DynamoDB) serve a API de recomendação rápida, enquanto a Offline Store (S3 Iceberg) acumula registros históricos para retreinar modelos de machine learning periodicamente em batch.

3. Inference API & Model Serving

O contêiner do ECS Fargate hospeda a lógica de serving. Ele recebe o ID do usuário, faz um lookup rápido na Online Store para coletar as features calculadas e submete o vetor de features ao SageMaker Model Endpoint, retornando a recomendação ao app.

Pontos de Atenção Críticos para Produção (Case 6)

Pontos de Atenção da Engenharia:
  • Feature Drift e Consistência Online/Offline: O maior erro em plataformas de recomendação é a assincronia entre o cálculo da feature no treino (offline) e no serving (online). Se o script PySpark calcular a média de cliques de um jeito no batch, mas a API calcular de outro no streaming, o modelo gerará predições ruins. Utilize a SageMaker Feature Store como única fonte da verdade e execute testes de validação contínuos comparando os vetores online com os snapshots offline.
  • DynamoDB Provisioned Capacity para Online Store: Por padrão, a Online Feature Store utiliza DynamoDB sob o capô. Em plataformas com milhões de usuários ativos, o pico de requisições de leitura de features excederá a capacidade e causará erros de throttling na recomendação. Ative o Auto-scaling de Read Capacity Units (RCUs) ou configure o DynamoDB em modo On-Demand para evitar queda nas recomendações sob pico.

Case 11: API de Ingestão de Alta Volumetria com Amazon ECS Fargate

Construção de uma API HTTP Serverless resiliente e auto-escalável para ingestão de eventos mobile, protegida por ALB e bufferizada no Kinesis

Um aplicativo móvel de entregas com milhões de usuários precisa enviar coordenadas geográficas e status de corridas a cada 5 segundos para a nuvem. Ligar os dispositivos diretamente ao AWS API Gateway geraria custos inviáveis devido ao billing por requisição. A arquitetura propõe um Application Load Balancer (ALB) na frente de um cluster Amazon ECS Fargate rodando uma API leve e assíncrona que joga os dados diretamente em um Amazon Kinesis Data Stream.

Case 10.5 — API de Ingestão Fargate
Explicação:
  • Componentes: HIGH-THROUGHPUT INGESTION API, Mobile / Web Clients, Application Load Balancer, ECS Fargate (Ingestion API), Amazon MSK (Kafka Buffer)
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.
  • Contexto: O diagrama "Case 10.5 — API de Ingestão Fargate" ilustra a arquitetura da solução para o tópico em questão.

Detalhamento do Fluxo Operacional

  1. Ingress e Load Balancing: O tráfego entra através do ALB (Application Load Balancer), que assume o trabalho custoso da terminação TLS/SSL. O ALB enxerga as tarefas ativas do Fargate através do mecanismo de roteamento e balanceia as requisições HTTP REST mantendo conexões keep-alive (para não reabrir a porta TCP toda hora).
  2. API Asynchronous Processing no Fargate: Os contêineres rodam micro-frameworks assíncronos que possuem suporte a concorrência enorme em uma única vCPU (como Python AsyncIO ou Goroutines). O container recebe o JSON, valida os tipos de dados e faz um PutRecords batch para o Amazon Kinesis Data Streams usando o Boto3/AWS SDK, respondendo rapidamente ao cliente 202 Accepted para economizar bateria do celular e banda.
  3. Buffering e Tolerância a Picos: O container do Fargate não insere os dados diretamente num banco de dados, protegendo o Lakehouse. A carga recai toda sobre o Kinesis, que escala em Shards independentes da web.
  4. Target Tracking Auto Scaling Predictivo: Uma política de Target Tracking atrelada ao ECS Service monitora a métrica `ALBRequestCountPerTarget` (requisições por contêiner). Antes do contêiner ficar lento, o ECS provisiona automaticamente mais Tasks Fargate (Cold Start em ~40s) para manter a performance instântanea intacta.

Case 14: Analytics em Tempo Real com Athena Federated Query e Otimização de Custos

Orquestração de consultas cruzadas entre o Lakehouse S3 e bancos operacionais RDS/DynamoDB, controlando limites de concorrência e custos com Athena Workgroups e Result Caching

Uma plataforma global de e-commerce necessitava fornecer dashboards atualizados no QuickSight para gerentes de categoria e de vendas regionais. Os dados históricos de vendas profundos (Petabytes) estão totalmente persistidos no Amazon S3 estruturados no formato Apache Iceberg colunar para otimização de varredura. Todavia, os status precisos dos estoques fracionários e de entregas logísticas dos pedidos em andamento do dia se atualizam e vivem no Amazon Aurora PostgreSQL transacional e no Amazon DynamoDB. Rodar pesados ETLs assíncronos batch a cada hora gerava defasagem de SLA, mas ligar ferramentas de replicação contínua CDC puramente analítica por cima do banco de faturamento gerava riscos absurdos de concorrência.

Detalhamento do Fluxo e Arquitetura

  1. Athena Federated Query Mesh: O time eliminou o ETL tradicional ponta-a-ponta, optando pelo poder da federação sob demanda. Utilizou o Amazon Athena configurando nativamente Data Source Connectors implementados em AWS Lambda. O Athena agora enxerga tanto o Aurora PostgreSQL quanto o DynamoDB como catálogos virtuais do tipo tabela.
  2. Cross-Join Transparente de Arquitetura Limpa: Quando o gestor acessa o painel de "Vendas Históricas Cruzadas com Entregas de Hoje", o Athena recebe o SQL global e executa internamente o quebra-cabeça de dividir as queries e executar JOINs em memória paralela (Presto/Trino clusterizado). O motor do Athena aciona o conector Lambda e o força a enviar lógicas avançadas de filtros SQL limitadores diretamente para a execução do PostgreSQL, processo conhecido como Predicate Pushdown (ex: WHERE id_categoria = 'eletronicos' AND entrega = 'pendente'). O Aurora responde e a Lambda traduz eficientemente os blocos de dados transacionais vindos do banco via JDBC direto para arrays estruturados compactos em padrão de memória veloz Apache Arrow, injetando de volta na rede para o motor analítico mestre unificar com a leitura bruta que ocorre no S3.
  3. Blindagem do Banco de Faturamento (Isolation Layer): Para evitar que chamadas federadas ad-hoc sobrecarreguem e esgotem o limitador de conexões abertas do banco Aurora sob cargas desproporcionais ou subidas mal otimizadas do Lambda Connector, a chamada JDBC analítica bate de frente no Amazon RDS Proxy intermediário. Este retém o pooling constante multiplexado sob demanda e preserva a máquina do DB limpa de choques TCP de latência.
  4. Otimização Extrema de Custos FinOps:
    • Athena Result Reuse (Reuso de Resultados): Consultas executivas nos dashboards do QuickSight são frequentemente apertadas em F5 por gerentes repetidamente nas reuniões. Cada refresh enviaria os mesmos terabytes do S3 por hora a $5/TB. Para contornar, a flag global de Query Result Reuse foi ligada ao Workgroup Athena. Com uma carência (TTL) calibrada para 30 minutos, idênticas chamadas SQL encontram a resposta materializada anterior em cache (sem que os dados do Iceberg tenham sofrido writes no meio tempo), retornando resultados instântaneamente para o visor com preço real de zero dólares.
    • Athena Workgroups Limitadores com Capacity Reservations: Em workflows agressivos de encerramento mensal financeiro (book closings) nos relatórios que não suportam oscilações diárias da fila ruidosa da AWS por estar competindo com outras empresas locais por computação multilocatário do Serverless, as queries são engatadas à um Workgroup Athena VIP comutado sob a funcionalidade de Athena Provisioned Capacity. Esse mecanismo retém blocos exclusivos (DPUs) da infraestrutura da nuvem AWS para bater sempre as metas pesadas no SLA do cronograma fiscal.

Case 19: Plataforma de Análise de Risco Híbrida em Tempo Real (MLOps + DataOps)

Implementação integrada de MSK, Flink, SageMaker Feature Store e detecção contínua de Drift sob Contratos de Dados

Uma grande instituição financeira precisa avaliar o risco de crédito para transações de pagamentos instantâneos (PIX/TED). O sistema deve validar cada transação de entrada contra contratos de dados rígidos, calcular features agregadas em tempo real com estado (streaming), enriquecer o contexto de inferência buscando no SageMaker Feature Store Online e monitorar continuamente se as populações de dados inferidos sofreram variações estatísticas drásticas que invalidem o modelo preexistente.

Arquitetura da Solução Híbrida

  1. Validação Ativa de Contrato (DataOps): As requisições de pagamentos são ingeridas no Amazon MSK. O micro-serviço validador consome as transações de entrada e roda rotinas de checagem contra esquemas JSON de contratos de dados. Mensagens corrompidas são desviadas imediatamente para uma pasta de Quarentena no S3.
  2. Cálculo de Variáveis com Flink (Feature Ingestion): Registros aprovados entram no processador contínuo Apache Flink, que calcula agregações temporais de janelas deslizantes (ex: quantidade de tentativas nos últimos 15 min, volume médio por hora). O Flink atualiza estes dados a cada segundo diretamente no SageMaker Feature Store Online (DynamoDB).
  3. Inferência Segura e Grounding: O serviço de crédito (Lambda) recebe a transação ativamente. Ele consulta o SageMaker Feature Store Online obtendo as features em menos de 8ms, anexa no payload e executa a inferência contra o SageMaker Endpoint do modelo.
  4. Detecção de Drift e Retreinamento (MLOps): As requisições e respostas do endpoint do modelo são logadas em buckets S3. Diariamente, um Job do SageMaker Model Monitor analisa os logs contra a base de treinamento. Caso identifique um desvio estatístico de População (Data Drift) com Wasserstein distance superior a 0.1, dispara alertas e invoca a Step Functions orquestrando o SageMaker Pipelines para re-treinar o modelo com os dados mais recentes na Offline Store S3.
Resultado de Negócio:

A unificação dos ciclos de engenharia e modelagem (DataOps + MLOps) garantiu zero interrupções nos pipelines de crédito por Schema Drift. A taxa de falsos positivos em fraudes de risco contínuo caiu 40% graças à ingestão em tempo real de features no Feature Store Online, e o re-treinamento autônomo reduziu a dependência de intervenção humana.

Case 20: Ingress Analítico Multirregião de Altíssima Disponibilidade (Serverless)

Arquitetura global de recepção de eventos usando Route 53, CloudFront com WAF, API Gateway direto para SQS e barramento com VPC PrivateLink

Uma corporação global de streaming de vídeo coleta dados de telemetria de milhões de dispositivos (Smart TVs, Mobile) simultaneamente. O volume de entrada atinge picos de 300.000 requisições por segundo. O sistema de coleta não pode sofrer quedas sob hipótese alguma, precisa barrar robôs na borda, deve apresentar latências de ingestão inferiores a 50ms nas regiões locais e transferir os registros de forma 100% privada e isolada para processamento Spark em sua VPC.

Arquitetura da Solução Global

  1. DNS Inteligente (Route 53): O tráfego do usuário final é roteado usando a política de Roteamento por Latência do Route 53, que direciona as requisições de telemetria automaticamente para a região AWS operacional geograficamente mais próxima do dispositivo.
  2. Filtros e Caching de Borda (CloudFront + WAF): O CloudFront recebe as chamadas HTTPS. O AWS WAF atua inspecionando assinaturas de payloads na borda para bloquear bots e spam de dados. Arquivos estáticos de configuração de telemetria são cacheados localmente com TTL curto.
  3. Ingress Desacoplado Serverless (API Gateway + SQS): A API Gateway recebe as requisições POST validadas. Em vez de acionar Lambdas (que sofreriam com limites de concorrência), a API Gateway grava o payload bruto diretamente em uma fila Amazon SQS local utilizando a integração direta do serviço (`aws:sqs`). A resposta do POST é enviada de volta ao cliente em menos de 25ms.
  4. Isolamento de Rede via VPC PrivateLink: Os motores analíticos de processamento (AWS Glue Spark Jobs e clusters EMR) residem em uma VPC privada e isolada (sem Internet Gateway). O Glue lê as mensagens da fila SQS e se conecta às tabelas do Data Lakehouse e ao Glue Data Catalog trafegando dados exclusivamente por Interface VPC Endpoints (PrivateLink) e Gateway Endpoints internos, garantindo conformidade regulatória máxima e eliminando tarifas de tráfego de dados por NAT.
Resultado de Negócio:

A eliminação de Lambdas na etapa de ingress cortou custos operacionais em 65%. O uso de VPC Endpoints reduziu em 92% os custos de transferências de dados de rede da VPC analítica, e a arquitetura ativa-passiva gerenciada pelo Route 53 resultou em 99,999% de disponibilidade global medida.

Case 39: Operação de Câmbio & Compliance em Real-Time

Case 39 • Express Workflows

Cenário: Das +10.000 operações de câmbio por dia, ~4.000 (Invoices, Certificados de origem) são "desviadas" para uma API de análise por imagem durante a transação. O sistema central fica aguardando um JSON estruturado de retorno.

Desafio: SLA extremamente crítico. 10 minutos de SLA rígido para Invoices e Certificados que necessitam passar por "Compliance / Listas Restritivas", caso contrário a operação transacional do banco quebra ou sofre sanções internacionais.

Solução AWS: Como exige tempo real e baixa latência (menos de 10 min de execução), migramos para o Step Functions Express Workflows (que dura no máximo 5 minutos e cobra por GB-segundo, suportando alto throughput). A camada de consulta de compliance utiliza o DynamoDB DAX (cache em milissegundos) para verificar listas restritivas instantaneamente antes de disparar o Webhook de retorno.
