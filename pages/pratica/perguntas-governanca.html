Questão 5 · Segurança AWS

Como o AWS Lake Formation garante a segurança granular se o usuário final não tem acesso físico ao Bucket S3 no IAM?

Mecanismo de Credential Vending: Este é um conceito avançado de segurança. O usuário final (ou a role do Athena/EMR) tem permissões concedidas diretamente no Lake Formation (ex: acesso de leitura à coluna X da tabela Y). No entanto, a role do usuário não tem nenhuma permissão física de leitura (s3:GetObject) nas políticas do IAM associadas ao bucket S3 onde a tabela está salva.

Passo a Passo do Fluxo de Autenticação:
  1. O usuário executa a query SELECT coluna_permitida FROM tabela no Athena.
  2. O Athena envia a solicitação para o Lake Formation validando se o usuário possui essa permissão lógica.
  3. Se autorizado, o Lake Formation assume temporariamente uma Role de serviço interna que possui privilégios de leitura no bucket S3 físico.
  4. O Lake Formation gera credenciais temporárias de curto prazo (Credential Vending) e as entrega de volta ao motor do Athena.
  5. O Athena lê fisicamente os blocos de dados Parquet diretamente do S3 usando as credenciais temporárias concedidas, aplica os filtros de linha/coluna e retorna o resultado limpo para o usuário, bloqueando qualquer possibilidade de bypass.
Questão 8 · Segurança AWS

Por que utilizar a governança baseada em tags (LF-TBAC) no Lake Formation é superior a Named Resource Access em ambientes com milhares de tabelas?

Limitação de Named Resources (RBAC): Em ambientes corporativos gigantes, conceder acesso apontando explicitamente para o nome do banco e da tabela (ex: GRANT SELECT ON db.tabela1 TO role) gera uma explosão de políticas de acesso. É impossível manter, auditar e escala esse modelo para 10.000 tabelas.

Funcionamento da Governança baseada em Tags (TBAC):

O Administrador cria chaves de tags lógicas no Lake Formation (ex: tag Area=Financeiro, tag Sensibilidade=PII) e as vincula a bancos, tabelas ou colunas específicas. Em seguida, cria uma única regra lógica de acesso no Lake Formation: "A equipe de Contabilidade pode ler qualquer tabela que contenha a tag Area=Financeiro E Sensibilidade=Publico". Quando uma nova tabela do financeiro é criada pelo Glue Crawler, basta atribuir a tag para que as permissões de acesso sejam herdadas automaticamente, sem necessidade de atualizar nenhuma política do IAM ou concessões nominais.

Questão 11 · Migração de Dados (CDC)

O que provoca latência de replicação (Source/Target Latency) em tarefas CDC do AWS DMS e como otimizar o processamento de colunas LOB?

Funcionamento de LOBs (Large Objects): Colunas contendo grandes cadeias de texto ou dados binários (JSON, CLOB, BLOB) degradam a replicação contínua do DMS.

  • Full LOB Mode: O DMS replica o registro normal e, em seguida, executa uma consulta cara de retorno na origem para extrair os dados da coluna LOB. Isso gera uma latência absurda de rede e banco em tabelas com alta concorrência.
  • Limited LOB Mode: O DMS aloca um buffer fixo em memória (ex: 32 KB) para ler os LOBs na mesma requisição de varredura. Dados de LOB maiores que o buffer configurado são truncados. É a opção de alta performance recomendada para produção.

Tuning no Target para Alta Vazão (Batch Apply):

Por padrão, o DMS executa instruções SQL uma a uma no banco de destino. Mude o parâmetro de processamento da tarefa para o modo Batch Apply (configuração BatchApplyEnabled = true) para acumular alterações e aplicá-las em transações em lote agrupadas, reduzindo a latência do Target.

Questão 12 · Teorema PACELC

Qual o tradeoff de consistência e latência (Teorema PACELC) ao escolher entre Aurora Global Database e DynamoDB Global Tables?

Entendendo o Teorema PACELC: Uma extensão do teorema CAP. Ele dita: Se houver uma partição de rede (P), escolha entre Disponibilidade (A) ou Consistência (C). Caso contrário (E - Else), escolha entre Latência (L) ou Consistência (C).

Tradeoffs em Entrevista Técnica:
  • DynamoDB Global Tables (Modelo PA/EL): Sob partições de rede, mantém a disponibilidade local alta (PA). Em estado normal, prioriza latências de escrita extremamente baixas em milissegundos nas regiões locais enviando replicações de forma assíncrona (EL), garantindo eventual consistência entre regiões distantes.
  • Aurora Global Database (Modelo PC/EC): Sob partições, pode parar escritas na região secundária para garantir consistência física exata (PC). Em estado normal, o Aurora usa replicação física otimizada em nível de storage de baixa latência mas síncrona/consistente para evitar conflitos de dados históricos (EC).

Questão 17 · Contratos de Dados & Governança

Como implementar um contrato de dados (Data Contract) resiliente na AWS para garantir o alinhamento de esquema e evitar que mudanças não retrocompatíveis quebrem os pipelines analíticos downstream?

Conceito de Contrato de Dados: Um contrato de dados é um acordo formal entre os geradores de dados (sistemas produtores/microsserviços) e os consumidores de dados (times analíticos). O objetivo é bloquear alterações silenciosas de esquema (Schema Drift) diretamente na origem.

Arquitetura na AWS: Para viabilizar esta governança de maneira automatizada e assíncrona:

  • Mecanismo de Validação: O microsserviço produtor serializa as mensagens usando formatos binários autopredicativos (como Apache Avro ou Protocol Buffers) ou schemas JSON, registrando-os no AWS Glue Schema Registry. O produtor valida cada payload localmente antes do envio. Se a estrutura violar o contrato ativo, a publicação falha imediatamente.

Qualquer modificação no contrato passa por um pipeline de pull-request onde o GitHub Actions faz a validação de compatibilidade retroativa contra o Glue Schema Registry usando a AWS CLI (modo de validação BACKWARD, impedindo remoção de campos requeridos ou mudança de tipos).
  • Circuit Breaker Downstream: Caso um payload fora do formato passe por brechas (como migrações desordenadas), o Spark Streaming ou AWS Lambda de ingestão na camada Bronze utiliza o Schema Registry para decodificar a mensagem. Em caso de erro de deserialização, a mensagem corrompida é desviada para um bucket de quarentena no S3 para análise e alertas são enviados via Amazon SNS para o canal de engenharia.

Isso permite antecipar picos de tráfego escalando contêineres Fargate antes que a CPU atinja 100% de uso, o que causaria timeout nas conexões.
Questão 19 · Observabilidade & Datadog

Como configurar uma observabilidade avançada de pipelines de dados analíticos na AWS usando o Datadog para monitoramento de latência e qualidade?

Monitoramento além do CloudWatch: Embora as métricas padrão da AWS (como uso de CPU no EMR ou contagem de erros de Lambda) ajudem, elas não são suficientes para diagnosticar lentidões complexas em pipelines analíticos de múltiplos estágios (Ex: Spark -> S3 -> Redshift -> Athena). O Datadog unifica logs, traces distribuídos e métricas personalizadas em um único plano de visualização.

Padrão de Monitoramento de Engenharia no Datadog:
  • Distributed Tracing (APM) no Spark: Configure o Datadog Agent como um DaemonSet (no EMR em Kubernetes) ou ative a biblioteca Java Datadog APM no Spark Submit (-javaagent:/caminho/dd-java-agent.jar). Isso permite visualizar exatamente quanto tempo cada Task do Spark gasta lendo arquivos Parquet do S3 vs executando processamento em memória, identificando shuffles problemáticos de rede.
  • Envio de Métricas Customizadas com DogStatsD: Dentro do código de processamento (PySpark, Glue ou ECS), envie métricas específicas de qualidade e progresso usando o protocolo UDP (DogStatsD). Por ser UDP, o disparo não gera latência ou bloqueia o pipeline.
    Exemplo: statsd.gauge('data_pipeline.rows_processed', 150000, tags=['layer:silver', 'job:ingestion_v2']).
  • Alertas de Anomalia de Volume (Anomaly Detection): Configure alertas no Datadog que utilizam aprendizado de máquina para prever tendências históricas diárias ou semanais. O alerta dispara se o volume de dados cair abruptamente (ex: queda de 30% em relação ao comportamento típico de terças-feiras), indicando um problema silencioso de silenciamento de fontes upstream.
Questão 21 · Cases & Streaming / Ingestão (Case 1)

Questão 37 · AWS IAM Permission Boundaries vs SCPs

Qual a diferença prática de aplicação e avaliação lógica entre Permission Boundaries e Service Control Policies (SCPs) no AWS Organizations, e como essas estruturas impedem escalada de privilégios em times de engenharia?

Service Control Policies (SCPs): São políticas de governança centralizadas aplicadas em nível de conta, OU (Organizational Unit) ou organização no AWS Organizations. Elas definem o limite máximo de permissões para a conta inteira (incluindo o usuário Root). Uma SCP que bloqueia a exclusão do S3 Guard (ex: s3:DeleteBucket) impede qualquer Role da conta de fazê-lo, independente das políticas do IAM local.

Diferença de Escopo e Avaliação Lógica:
  • Permission Boundaries (Fronteiras de Permissão): São aplicadas a usuários ou Roles locais do IAM. Elas definem as permissões máximas efetivas que uma entidade do IAM pode ter. É usada principalmente para delegar a criação de papéis (roles locais de Glue, Lambda, EMR) a Engenheiros de Dados. Isso evita que o engenheiro crie uma Role com AdministratorAccess para uso próprio e escale seus privilégios (Privilege Escalation), já que as ações da nova role estarão sempre limitadas pela Permission Boundary.
  • Mecanismo de Avaliação Lógica (Intersecção de Permissões): Na AWS, as permissões efetivas finais de uma chamada de API são a interseção lógica de:
    Identity-Based Policy (IAM Policy) AND Permission Boundary AND SCP (Organizations) AND Resource-Based Policy (S3 Bucket/KMS Key).
    Se qualquer uma dessas camadas declarar um Deny explícito, a requisição é sumariamente negada.

  • EMR Serverless: Solução mais fácil (low-ops) com ótimo FinOps. Possui pre-initialized capacity que inicia jobs quase imediatamente. Resolve os problemas sem a complexidade de gerenciar um Control Plane de Kubernetes.
Questão 40 · EMR & Resiliência Spot

Como arquitetar resiliência no EMR on EC2 ou EMR on EKS para mitigar perdas catastróficas de dados via FetchFailedException quando instâncias Spot são desligadas pelo provedor AWS?

Problema Crítico de Shuffle e Instâncias Spot: O Spot AWS pode remover um nó com um aviso prévio curto (2 minutos). Se um Executor Spark operando no nó Spot estava retendo os blocos de dados intermediários de um pesado GROUP BY (dados de shuffle), o desligamento repentino apagará esses dados de disco local. As tarefas downstream (Reduce) falharão por FetchFailedException, forçando a DAG do Spark a retroceder os estágios (stages) e recalcular toda a base, podendo causar atrasos de horas.

Técnicas de Mitigação: Graceful Decommissioning & Shuffle Tracking:
  • No EMR on EC2: Projete o cluster utilizando Spot Instances estritamente para Task Nodes (puramente computacionais sem réplicas HDFS de storage). Ative a flag do YARN de Graceful Node Decommissioning. Quando a AWS envia o sinal de interrupção, o YARN marca o nó como "DECOMMISSIONING" e copia ativamente os dados locais cruciais do NodeManager para as máquinas Core (On-Demand) remanescentes nos 2 minutos disponíveis de tolerância, resguardando o progresso da query.
  • No EMR on EKS (Spark 3.2+): Habilite a propriedade spark.dynamicAllocation.shuffleTracking.enabled=true e ative o Executor Decommissioning nativo do K8s (spark.decommission.enabled=true e spark.storage.decommission.shuffleBlocks.enabled=true). Com isso configurado, ao receber o SIGTERM de finalização, o pod executor inicia uma migração paralela forçada transferindo (push-based) seus dados Shuffle e RDD/Cache via rede P2P para um pod sobrevivente.
Questão 42 · ECS Fargate vs Lambda

Comparativo Avançado: Como o ciclo de vida (Cold Start) impacta a escolha entre AWS Lambda e ECS Fargate na Ingestão de Telemetria IoT e quais estratégias de autoscaling o Fargate exige para não gerar perdas (Dropped Connections)?

Cenário de Entrevista: O cliente precisa ingerir sinais contínuos de sensores de frota 24/7. Ocasionalmente o tráfego dobra instantaneamente. Decida o compute.

Resposta Técnica:
  • O Problema do Cold Start em APIs: AWS Lambda sofre de Cold Starts quando a concorrência explode subitamente, pois a AWS aloca instâncias isoladas (microVMs Firecracker). Se a inicialização do ambiente de execução (especialmente Java/C# ou Python com muitas bibliotecas) demorar 5 segundos, as requisições HTTPS do cliente durante o pico sofrerão latência gigantesca e possíveis Timeouts pelo API Gateway.
  • A Vantagem do ECS Fargate "Always-On": O ECS opera com instâncias containerizadas persistentes. Tarefas já ativas suportam concorrência interna alta assíncrona (ex: um servidor FastAPI no Fargate processando 2000 req/s por contêiner simultaneamente através de async/await e connection pooling), não precisando invocar novas VMs linha a linha.
  • Auto-scaling Tuning no ECS: O ECS demora muito mais para subir uma nova tarefa Fargate (Task Provisioning Latency, ~30 a 60 segundos por pull de imagem Docker pesada) em comparação com milissegundos do Lambda. Portanto, no ECS, devemos escalar antes da crise: usar o Target Tracking Scaling Policy fixado em, digamos, 50% de uso de CPU (e não 90%), ou criar regras proativas preditivas baseadas no horário de pico, de forma que os novos contêineres estejam com status RUNNING antes que os servidores ativos enfileirem e percam as conexões (Dropped Connections).
Questão 43 · Armazenamento ECS Fargate

Como gerenciar gargalos de armazenamento efêmero ao baixar e processar blocos massivos de dados estruturados (>50GB) dentro do ECS Fargate, dada a limitação de disco containerizada?

Desafio Técnico em ETL Serverless: Tarefas tradicionais do Fargate sobem com um disco de armazenamento efêmero restrito (20GB).   • Expansão de Disco Efêmero (Ephemeral Storage): Ajustar a configuração da Task Definition no parâmetro ephemeralStorage para solicitar um montante até o limite máximo de 200GB (que acarretará em custos proporcionais atrelados ao tempo de vida da task).

O container monta o EFS via NFS no diretório de extração local, podendo manipular Terabytes de informações elásticas sob demanda persistente com concorrência para múltiplos containers paralelos lerem do mesmo storage se necessário.
Questão 44 · Data Quality & Custos FinOps

Como otimizar os custos computacionais proibitivos de execução de regras de Data Quality (DQDL ou Great Expectations) que analisam a unicidade ou a completude em tabelas gigantescas (Petabytes) do Data Lake?

Cenário de Entrevista: Executar IsUnique "id_cliente" em uma tabela de 5 Petabytes todos os dias leva horas e consome recursos massivos de Spark Shuffle para calcular o agrupamento completo.

Resposta Técnica (Técnicas de Escala):
  • Isolamento Incremental (Push-down): Nunca execute testes de Data Quality na tabela integral a cada execução de batch. Restrinja o DataFrame lido passando predicados de tempo no pushdown, avaliando apenas a partição ingerida no dia (ex: df.filter("data_ingestao = current_date")). Teste a integridade apenas sobre os incrementos da jornada (Delta).
  • Aproximação Probabilística: Se o teste de unicidade (IsUnique) e contagem exata não for estritamente financeiro e sim comportamental, troque contagens exatas onerosas (como COUNT(DISTINCT id)) por algoritmos probabilísticos leves embutidos na engine (como o HyperLogLog no Spark/Presto). O algoritmo fornece ~98% de precisão gastando uma fração minúscula de RAM e processamento.
  • DQ Integrado via Iceberg/Delta: Bancos e formatos modernos (Apache Iceberg) mantêm metadados com contagens de colunas, mínimos, máximos e nulos pré-computados (File-Level Stats) sem a necessidade de varrer os dados fisicamente. Queries otimizadas podem extrair métricas de completude lendo apenas as tabelas de manifesto de forma gratuita e imediata.
Questão 45 · FinOps & Segurança (KMS)

Como as chaves do AWS KMS podem inflar de forma silenciosa e catastrófica o faturamento de consultas no Athena/EMR em tabelas com criptografia SSE-KMS, e qual a estratégia para mitigar custos de chamadas de API KMS?

O Ralo de Dinheiro Oculto: Por padrão, a criptografia SSE-KMS no S3 exige que, para cada bloco ou arquivo lido/escrito no bucket, seja executada uma chamada de API `kms:Decrypt` ou `kms:GenerateDataKey`. Quando consultas analíticas no Athena ou EMR varrem dezenas de milhões de pequenos arquivos em buckets S3 protegidos, a conta AWS é tarifada em centavos por requisição KMS. Esse custo de chamadas de API KMS pode superar com folga o custo de armazenamento e computação combinados.

A Solução Otimizada: S3 Bucket Keys

Habilite a propriedade S3 Bucket Key nas configurações do bucket. Quando ativada, a AWS gera uma chave de bucket de curto prazo no nível do S3 e a utiliza para criptografar/descriptografar dados locais. Isso reduz o volume de chamadas de API do KMS para o S3 em até 99%, derrubando o custo operacional de segurança de forma imediata.

Questão 47 · FinOps & Networking

Como auditar custos ocultos de Data Transfer e NAT Gateway gerados por tarefas analíticas no EMR/Glue que processam dados do S3 em subredes privadas, e qual a solução arquitetural ideal de custo zero?

A Pegadinha das Redes na AWS: Quando executores do EMR ou Glue rodam em subredes privadas de uma VPC, por padrão, qualquer chamada à internet ou serviços AWS (incluindo o S3) é roteada através do NAT Gateway da subrede. A AWS cobra uma tarifa por gigabyte processado (Data Processing charge) no NAT Gateway. Varrer 10 TB de dados no S3 geraria cerca de $450 apenas em tarifas de transferência de rede no NAT Gateway.

A Solução Suprema: Gateway VPC Endpoint para S3

Crie um VPC Endpoint do tipo Gateway para o S3 na tabela de roteamento da sua VPC privada. Essa configuração cria uma rota interna privada direta e gratuita entre os recursos da subrede privada e o S3, desviando do NAT Gateway e reduzindo o custo de transferência de dados desse tráfego para zero.

Questão 48 · IA Generativa & Caching Semântico

Como projetar um mecanismo de Caching Semântico usando Redis em uma plataforma de dados com LLMs para evitar custos redundantes de tokens de inferência e reduzir a latência de buscas duplicadas?

Cenário de Desperdício: Em aplicações de RAG corporativo ou de buscas internas em linguagem natural, múltiplos usuários realizam perguntas semanticamente muito similares (ex: "Qual é o faturamento de vendas de maio de 2026?" vs "Quanto faturamos nas vendas em maio de 26?"). Processar cada uma enviando-a ao Bedrock Sonnet consome milhares de tokens e eleva a latência.

A Solução: Cache de Vetores com Distância de Cosseno no Redis

Ao receber uma pergunta, calcule seu embedding. Execute uma busca KNN baseada em distância de Cosseno contra uma base de perguntas e respostas já cacheadas no Amazon ElastiCache Redis (usando o tipo de dados nativo de busca vetorial). Se a similaridade semântica for acima de um limiar rígido (ex: > 95%), retorne a resposta salva no cache de forma instantânea (latência < 10ms) sem invocar o modelo de linguagem, gerando 100% de economia de custo em tokens para aquela requisição.

Questão 49 · RAG & Chunking de Arquivos

Quais são as diferenças práticas, vantagens e riscos entre as estratégias de Chunking Estático (Fixed-size) e Chunking Dinâmico (Semantic Chunking) para ingestão em bases vetoriais no S3?

Impacto no RAG: Se a estratégia de quebra do documento for ruim, informações importantes de um parágrafo serão cortadas pela metade entre dois chunks diferentes. Isso degrada o embedding do vetor (dilui o significado) e impede que o LLM responda com precisão.

Análise de Estratégias:
  • Chunking Estático (Character/Token Limit): Divide o texto em um número fixo de caracteres ou tokens (ex: 512 tokens) com uma zona de overlap (ex: 10%). É rápido e simples de rodar via Glue Spark, mas pode cortar frases no meio, destruindo o contexto.
  • Chunking Dinâmico (Semantic Chunking): Utiliza um modelo de embedding ou parser sintático para identificar transições reais de tópicos e quebras naturais de parágrafos/seções. Garante que uma unidade lógica de conteúdo (ex: um capítulo ou tabela inteira) permaneça íntegra no mesmo chunk, maximizando a relevância semântica recuperada pela query vetorial.
Questão 50 · RAG & Métricas de Avaliação (Ragas)

Como avaliar sistemática e quantitativamente a qualidade de um pipeline RAG em produção na AWS sem depender de avaliações manuais humanas?

O Problema da Caixa Preta: Pipelines RAG falham silenciosamente: o banco vetorial pode trazer contexto correto mas o LLM ignora (Falta de Fidelidade), ou o banco traz contexto errado e o LLM alucina. Avaliar manualmente é lento e inviável em larga escala.

A Solução: Framework Ragas (Retrieval Augmented Generation Assessment)

Implemente rotinas automatizadas no SageMaker rodando o framework Ragas que usa LLMs potentes (ex: Claude 3.5 Sonnet) como avaliadores imparciais. Avalie o pipeline sob três pilares numéricos chave de 0 a 1:

  • Faithfulness (Fidelidade): Mede se a resposta gerada é inteiramente derivada do contexto recuperado (evita alucinações de conhecimento prévio do modelo).
  • Answer Relevance (Relevância da Resposta): Mede se o texto gerado realmente responde à pergunta formulada pelo usuário (evita respostas genéricas ou evasivas).
  • Context Recall (Recuperação do Contexto): Mede se o banco vetorial conseguiu recuperar todas as informações necessárias na base de conhecimento para construir a resposta correta.
Questão 54 · MLOps & Feature Store

Como arquitetar uma ingestão em tempo real de variáveis analíticas (Feature Store) com baixíssima latência na AWS integrando MSK, Flink e SageMaker Feature Store?

Desafio de Latência: Para detecção de fraudes ou score de crédito em tempo real, modelos de ML precisam consultar features agregadas recentes (ex: "soma de transações do cliente nos últimos 5 minutos") em menos de 10 milissegundos. Processar isso em batch seria ineficaz.

Arquitetura para Ingestão e Baixa Latência:
  • Fluxo de Processamento (MSK + Flink): Os eventos de transações entram no Amazon MSK. O Managed Service for Apache Flink consome as mensagens em tempo real e calcula agregações deslizantes (sliding windows) em memória com estado.
  • Ingestão no Feature Store Online: O Flink envia o resultado agregado usando chamadas simultâneas `PutRecord` para o Amazon SageMaker Feature Store (Online Store). O Feature Store Online escreve estes valores em tabelas do DynamoDB gerenciadas internamente, garantindo latências de leitura inferiores a 10ms na inferência do modelo.
  • Persistência no Feature Store Offline: Automaticamente, o SageMaker sincroniza estes registros para a Offline Store (no S3 como Parquet) para que os cientistas de dados re-treinem os modelos em batch usando dados históricos consolidados.

Como projetar um validador de contratos de dados em tempo real acoplado à ingestão S3 para isolar registros corrompidos de forma serverless?

Risco de Quebra: Se a equipe de produto alterar o schema de origem (ex: remover coluna obrigatória ou mudar string para int), isso causará erros de conversão de tipos no Spark/Athena, derrubando painéis. Precisamos de uma barreira defensiva.

Solução de Validação Ativa (Credential Vending + Lambda):

Questão 56 · GenAI & OpenSearch Tuning

Como sintonizar o balanceamento de relevância semântica contra busca léxica em buscas híbridas (Dense + Sparse) usando Amazon OpenSearch Serverless?

Desafio de Precisão: Em buscas híbridas, a distância de cosseno dos embeddings lida mal com termos exatos (ex: códigos de produtos), enquanto a busca léxica clássica (BM25) não entende sinônimos. Como unificar as notas de forma balanceada?

Ajuste Operacional (RRF Tuning):

Utilize o algoritmo Reciprocal Rank Fusion (RRF) no OpenSearch. Configure o parâmetro de ponderação de relevância inicial (normalmente pesos como 0.7 para embeddings semânticos para cobrir intenções amplas, e 0.3 para palavras-chave para assegurar acertos técnicos de termos específicos). Questão 57 · VPC Endpoints & Custos NAT

Como a arquitetura de VPC Endpoints (Gateway vs Interface) reduz drasticamente as faturas de rede (NAT Gateway) em pipelines analíticos que leem petabytes do S3?

Gargalo de FinOps de Rede: Por padrão, containers rodando em subredes privadas (ECS/Glue/EMR) acessam endpoints públicos (como S3 e DynamoDB) roteando o tráfego via NAT Gateway. O NAT Gateway cobra uma taxa fixa por GB processado (~$0.045/GB). Sob picos de processamento de petabytes de dados brutos, o custo de rede pode superar o custo de computação dos clusters.

Ação Corretiva: Gateway Endpoints

Associe um Gateway Endpoint para S3 e DynamoDB diretamente à tabela de rotas das subredes privadas. O Gateway Endpoint roteia o tráfego de dados de forma transparente pela rede privada interna da AWS para os serviços sem sair para a internet pública e sem passar pelo NAT Gateway. O recurso é gratuito e elimina 100% da tarifa por GB do NAT para esses serviços.

Ressalva de Entrevista: Outros serviços (como Kinesis, Secrets Manager ou Glue Schema Registry) requerem Interface Endpoints (PrivateLink), que utilizam Elastic Network Interfaces (ENIs) locais e cobram uma taxa fixa horária mais taxa de dados menor, sendo ainda assim muito mais em conta que o NAT Gateway para grandes volumes.

Questão 58 · API Gateway Direct Ingestion

Qual o ganho arquitetural, de custo e latência de configurar a integração direta (Service Integration) do API Gateway com SQS/Kinesis em vez de usar uma Lambda intermédia de repasse?

Vantagens da Integração Direta:
  • Latência: O API Gateway escreve diretamente na fila/stream reduzindo a resposta do webhook para menos de 40ms.
  • Resiliência: Elimina o risco de atingir o limite de concorrência simultânea do AWS Lambda em picos extremos de tráfego.
  • Custo: Paga-se apenas pelo volume de chamadas à API Gateway e requisições do SQS, reduzindo a conta de computação analítica em até 70% na etapa de ingress.

Sobrecarga do Engine: Dashboards de BI atualizando a cada segundo podem gerar centenas de queries repetidas que analisam os mesmos dados históricos. No Athena, isso explode a fatura linearmente; no Redshift, consome filas de concorrência e causa travamentos.

Questão 61 · EMR Spot Instances & YARN Decommissioning

Como gerenciar de forma resiliente a interrupção física de instâncias Spot analíticas nos Task Nodes de um cluster EMR no EC2 para prevenir falhas de "FetchFailedException" nos jobs Spark?

Gargalo Operacional: A remoção abrupta de um nó Spot que estava hospedando resultados intermediários de map-reduce força o Spark a reprocessar estágios (stages) inteiros. Se os metadados forem perdidos de forma recorrente, o job falha por timeout ou contagem máxima de tentativas de stage excedida.

Configuração de Alta Resiliência:

Para contornar o problema, ative o Graceful Decommissioning no YARN e configure as diretivas do Spark:

  1. YARN Decommissioning Timeout: Defina yarn.resourcemanager.decommissioning.timeout (ex: 300 segundos). Isso dá tempo para que o nó em processo de terminação transfira seus dados de shuffle local para nós persistentes (Core Nodes) antes de cair.
  2. Spark Decommissioning: Ative spark.decommission.enabled = true e spark.storage.decommission.enabled = true. O Spark proativamente migrará blocos de RDD armazenados em cache e arquivos de shuffle persistidos no disco local do executor sendo finalizado para outros executores ativos no cluster.
Questão 65 · Broadcast Join Driver OOM

Por que forçar um Broadcast Join (BHJ) em um DataFrame que excede o limite configurado em autoBroadcastJoinThreshold pode estourar a memória (OOM) do Driver Node antes mesmo dos executores iniciarem o processamento?

Gargalo do Fluxo do Broadcast: Ao executar um Broadcast Join, o Driver Node do Spark precisa realizar um download físico completo (collect) de todos os dados do DataFrame broadcasted a partir dos nós do cluster para sua memória JVM local. Ele constrói a tabela hash em memória no Driver e a serializa para enviar a cópia para todos os executores.

Impacto e Mitigação:

Se a tabela de broadcast for muito volumosa (ex: 5 GB), o Driver tentará alocar esse volume massivo em sua memória Heap local. Se a JVM do Driver estiver configurada com 4 GB de RAM, o processo falhará imediatamente com java.lang.OutOfMemoryError: Java heap space. Para mitigar, nunca force broadcast via hint de tabelas cujo tamanho físico seja maior do que a memória disponível do Driver.

Questão 66 · Orientação a Objetos em Pipelines de Dados

Benefícios da Arquitetura OOP em Dados:
  • Reutilização e Manutenibilidade (Abstração & Herança): A lógica de conexão e persistência reside em classes base (ex: DataConnector). Mudar a origem de arquivos locais para o S3 exige apenas trocar a classe especializada (ex: instanciar S3Connector), sem tocar no código de transformação.

Questão 70 · AWS Direct Connect Failover & BGP Routing

Como projetar uma arquitetura de rede híbrida resiliente de alta disponibilidade para ingestão de dados on-premises para a AWS utilizando AWS Direct Connect (DX) com failover automático para VPN Site-to-Site, garantindo que o tráfego prefira o DX sob condições normais usando atributos de roteamento BGP?

Desafio de Roteamento Dinâmico: O tráfego híbrido de dados volumosos precisa trafegar de forma prioritária pelo link privado de fibra óptica (Direct Connect) devido à largura de banda e estabilidade. A VPN IPSec deve atuar puramente como canal de failover passivo.

  • Tráfego de Saída da AWS (Outbound): Configure o atributo BGP Local Preference no roteador virtual da AWS. Defina um valor de Local Preference maior para a sessão BGP do Direct Connect (ex: 200) e um valor menor para a conexão BGP da VPN (ex: 100).   • Tráfego de Entrada na AWS (Inbound): Para forçar a AWS a preferir o DX ao enviar dados para a origem, anuncie os prefixos on-premises com AS PATH Prepend na sessão BGP da VPN Site-to-Site (adicionando o seu ASN local repetidas vezes, ex: 3 a 5 vezes). A AWS preferirá o caminho do DX porque ele apresentará um AS PATH menor (caminho mais curto). Alternativamente, utilize comunidades BGP suportadas pela AWS (como 7224:7100 para baixa preferência na VPN).
Questão 73 · Integração EMR, NLB e PrivateLink

Como expor de forma segura endpoints internos de interfaces web de um cluster EMR privado (como o Spark History Server na porta 18080 ou JupyterHub) para outras VPCs ou redes parceiras de forma centralizada e sem utilizar Internet Gateways?

Desafio de Segurança Corporativa: Expor clusters de processamento analítico (EMR) diretamente na internet pública cria vetores de ataque catastróficos. Toda a comunicação deve ser puramente interna e encapsulada na rede da AWS.

  • Interface VPC Endpoint: Na VPC de consumo (onde estão os analistas ou parceiros), crie um Interface VPC Endpoint apontando para o Endpoint Service criado. A AWS provisionará placas de rede virtuais (ENIs) locais que resolvem o tráfego diretamente para o NLB privado e consequentemente para as portas internas do EMR de forma segura, com criptografia em trânsito e latência de sub-milissegundos.
Questão 74 · IAM Trust Policies Avançadas & Prevenção de Confused Deputy

Ao configurar uma Role para o AWS Glue ou EMR Serverless, como a Trust Policy (Política de Confiança) deve ser codificada para impedir o ataque de Confused Deputy (Deputado Confuso), e qual o papel das chaves de condição aws:SourceArn e aws:SourceAccount neste cenário?

Desafio de Segurança Multi-Tenant: Serviços analíticos compartilhados da AWS rodam em infraestruturas multi-tenant. Se você autorizar o serviço (ex: glue.amazonaws.com) a assumir sua Role globalmente sem restrições, uma conta externa AWS maliciosa poderia instruir o Glue a rodar um Job assumindo o ARN da sua Role, obtendo acesso de leitura/gravação ao seu datalake S3 privado.

Solução Arquitetural de Relação de Confiança:
  • Mecanismo de Defesa: A Trust Policy deve limitar de forma explícita o escopo de atuação do serviço. Anexamos chaves de condição na política que forçam o principal a bater com o ID da sua conta e com ARNs controlados.
  • Condições Recomendadas:
    • aws:SourceAccount: Garante que apenas recursos criados sob o seu ID de conta AWS (ex: 123456789012) consigam induzir o serviço a assumir a Role.
    • aws:SourceArn: Restringe a invocação a ARNs específicos (ex: apenas o Job do Glue de nome job-silver-vendas pode assumir a Role).
Questão 75 · Segurança Cross-Account em Data Lake: Bucket Policy + KMS Key Policy

Em um cenário Data Mesh, um job PySpark rodando na Conta Consumidora A precisa ler dados analíticos Parquet salvos no S3 na Conta Produtora B. Os dados estão encriptados via chave KMS CMK customizada na Conta B. Como devem interagir as políticas IAM da Role da Conta A, a Bucket Policy da Conta B e a Key Policy do KMS da Conta B para permitir o acesso de menor privilégio?

Desafio de Avaliação de Políticas Cross-Account: Em acessos na mesma conta, basta a Role ter permissão no IAM. Em acessos cross-account (contas diferentes), a AWS exige autorização explícita em ambos os lados: na política de identidade do chamador e nas políticas de recurso do proprietário do recurso (Bucket Policy e KMS Key Policy).

Arquitetura de Concessão Cross-Account:
  1. Permissões na Conta Consumidora A (Identity-Based): A Role de execução do Spark na Conta A deve receber permissões explícitas no IAM de leitura no S3 (s3:GetObject, s3:ListBucket) apontando para o ARN do bucket da Conta B, e descriptografia no KMS (kms:Decrypt) apontando para o ARN da chave KMS da Conta B.
  2. Bucket Policy na Conta Produtora B (Resource-Based): A Bucket Policy da Conta B deve autorizar explicitamente o ARN físico da Role da Conta A a listar e ler objetos: 
    {
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::ACCOUNT_A:role/data-processing-role" },
  "Action": ["s3:GetObject", "s3:ListBucket"],
  "Resource": ["arn:aws:s3:::bucket-conta-b", "arn:aws:s3:::bucket-conta-b/*"]
}
  3. KMS Key Policy na Conta Produtora B (Resource-Based): A política da chave KMS customizada na Conta B deve conter um statement autorizando o ARN da Role da Conta A a realizar a descriptografia (kms:Decrypt, kms:DescribeKey). Sem este passo, o Spark baixará os bytes do S3 mas falhará em decodificar o Parquet, gerando erro de I/O.
Questão 76 · Privilege Escalation e Permission Boundaries em Times de Dados

Para dar autonomia a engenheiros de dados em uma grande corporação, foi cedida a eles permissão de criar novas Roles de execução no IAM para Glue e Lambda. Como evitar que um engenheiro abuse dessa autonomia para criar uma Role com permissões administrativas completas (Administrador) e a assuma (Privilege Escalation)?

Risco de Quebra de Governança: Um usuário com permissão de criar Roles (iam:CreateRole) e anexar políticas (iam:AttachRolePolicy) pode anexar a política gerenciada AdministratorAccess a uma Role nova e depois usá-la em um Lambda para alterar a infraestrutura corporativa.

Solução IaC com Permission Boundary:
  • Fronteiras de Permissão do IAM: O administrador de segurança da AWS cria uma política limite chamada Permission Boundary (que descreve as ações máximas que qualquer recurso de dados pode rodar, ex: ler S3, gravar logs, ler Glue, sem acessos administrativos de rede ou billing).
  • Vinculação via Políticas IAM: Na política IAM dos engenheiros de dados, a permissão iam:CreateRole só é concedida sob a condição estrita de que a nova Role criada venha associada à Permission Boundary predefinida: 
    {
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:PutRolePermissionsBoundary"],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "iam:PermissionsBoundary": "arn:aws:iam::123456789012:policy/data-boundary"
    }
  }
}
  • Resultado Prático: Mesmo que o engenheiro crie uma Role e tente anexar AdministratorAccess a ela, o poder de execução efetivo daquela Role será restrito ao escopo declarado na Permission Boundary, mitigando a escalação de privilégios.
Questão 77 · Slowly Changing Dimensions (SCD) no Data Lake

Como gerenciar alterações cadastrais históricas em tabelas de dimensão (Slowly Changing Dimensions - SCD) utilizando ferramentas de processamento de dados na AWS, e quais os trade-offs entre Tipo 1, Tipo 2 e Tipo 4?

Conceito de SCD: Entidades descritivas (como dados cadastrais de clientes ou produtos) mudam de valor lentamente ao longo do tempo. Capturar e registrar essas mudanças de forma controlada é fundamental para manter a consistência e a rastreabilidade histórica em análises analíticas de faturamento e vendas.

Tipos de SCD e Implementação na AWS:
  • SCD Tipo 1 (Sobrescrita Direta): O novo valor cadastral substitui o antigo. Não há histórico.
    • Caso de Uso: Correção de erros ortográficos simples.
    • Implementação: No PySpark/Glue, execute uma query de UPDATE ou um merge direto de partição utilizando formatos transacionais (como Apache Iceberg/HUDI).
  • SCD Tipo 2 (Histórico por Versões com Linhas Adicionais): Uma nova linha é inserida para registrar a mudança, mantendo a linha antiga ativa sob indicadores temporais (colunas data_inicio, data_fim e flag registro_ativo).
    • Caso de Uso: Mudança de endereço de cliente para cálculo de tributação histórica de vendas.
    • Implementação: No Spark/Iceberg, utilize o comando MERGE INTO comparando a chave natural. Se houver diferença nos dados descritivos, expire o registro antigo setando registro_ativo = false, data_fim = timestamp_atual, e insira a nova linha ativa.
  • SCD Tipo 4 (Tabela de Histórico Separada / Outrigger): A dimensão principal mantém sempre apenas o valor atual ativo (estilo Tipo 1), mas cada modificação é gravada em uma tabela satélite separada de histórico (Log de Alterações).
    • Caso de Uso: Rastreabilidade de status de contratos muito dinâmicos sem inflar a tabela de dimensão principal.
    • Implementação: Insira o registro Tipo 1 na dimensão principal via Iceberg e, em paralelo, envie o evento de mudança bruto para um bucket S3 histórico usando Kinesis Data Firehose para compor a tabela histórica de auditoria de forma assíncrona.
Questão 79 · Chaves Substitutas (Surrogate Keys) vs. Chaves Naturais

O que são chaves substitutas (Surrogate Keys) e por que elas são fundamentais em modelagem dimensional de Data Warehouses em vez do uso direto de chaves naturais de negócio vindas dos bancos OLTP?

Conceito de Chave Substituta: Uma chave substituta (Surrogate Key) é um identificador numérico artificial e sequencial (ou um Hash MD5/SHA256 gerado deterministicamente) gerado no Data Warehouse para atuar como chave primária de uma tabela de dimensão. A chave natural é o identificador gerado pelo sistema transacional de origem (ex: id_usuario no banco OLTP ou CPF).

Vantagens Técnicas e Motivações:
  • Independência de Sistemas de Origem: Sistemas transacionais podem ser migrados, resetados ou substituídos. Se duas fontes diferentes usarem o mesmo ID de chave natural para entidades distintas, o Data Warehouse sofrerá colisão. A chave substituta isola o Data Warehouse e garante unicidade global.
  • Suporte a Histórico de Mudanças (SCD Tipo 2): Para registrar a alteração de endereço de um cliente mantendo o histórico, precisaremos de duas linhas na dimensão para a mesma chave natural (ex: duas linhas com CPF 123.456...). Como a chave primária da tabela de dimensão deve ser única, a chave natural não serve. A Surrogate Key diferencia as versões físicas do mesmo cliente (ex: SK `1004` e SK `2854` mapeando para o mesmo CPF).
  • Performance Física de Joins: Fazer joins entre chaves de texto longas (como chaves compostas de string ou UUIDs) é computacionalmente caro. Usar chaves substitutas inteiras (Integers ou BigInt) compactas acelera a comparação na memória do motor analítico (Redshift/Spark) e reduz o tamanho dos índices e das tabelas Fato.
Questão 81 · Contratos de Dados no CI/CD (DataOps)

Como você garantiria, de forma automatizada, que a equipe de engenharia de software (produtores de dados) não suba para produção uma alteração de banco de dados que quebre os pipelines analíticos?

Cenário de Quebra Silenciosa: O desenvolvedor backend renomeia a coluna `id_cliente` para `customer_id` no banco transacional. O pipeline do Glue ETL falha de madrugada pois esperava o nome antigo.

A Solução DataOps (Shift-Left):
  • JSON Schema via Git: A equipe de dados e engenharia de software criam um repositório central contendo um JSON Schema que define os dados exatos esperados no Datalake (tipos de dados, nomes de colunas obrigatórias). Isso atua como um Contrato Analítico.
  • Validação no GitHub Actions do Produtor: Quando o desenvolvedor abre um PR (Pull Request) com migrações de banco (ex: via Flyway ou Liquibase), o pipeline CI/CD invoca um linter ou script automatizado que compara a estrutura final da migração proposta com o Contrato Analítico (JSON Schema).
  • Bloqueio Automático: Se a mudança violar o contrato (ex: excluir uma coluna requerida), o pipeline falha automaticamente o teste unitário (Red Build), impedindo o merge do código na branch principal até que a equipe de dados seja consultada para adaptar o contrato e o pipeline simultaneamente.
Questão 83 · Linhagem Multi-Cluster com OpenLineage

Por que utilizar o padrão aberto OpenLineage acoplado a serviços de backend como Marquez, em vez de depender exclusivamente das ferramentas nativas de linhagem do AWS Glue, em um ecossistema complexo?

A Necessidade de Linhagem Holística: Ecossistemas de dados raramente utilizam apenas um mecanismo computacional. Você pode ter Spark rodando no EMR, consultas SQL no Snowflake, jobs nativos de Glue, orquestração via Apache Airflow e transformações no dbt.

A Vantagem do OpenLineage:
  • Padronização de Telemetria: O OpenLineage não é um software servidor, mas uma especificação JSON/API aberta. Ferramentas distintas (Airflow, Spark, dbt, Flink) instrumentadas com o client do OpenLineage emitem os eventos da mesma forma unificada.
  • Rastreamento Cross-Platform: As soluções nativas de linhagem de nuvens (como Glue DataBrew ou Macie) mapeiam perfeitamente transformações executadas internamente por elas, mas são "cegas" caso uma tabela externa gerenciada em outra conta ou engine (Databricks, Snowflake) afete a tabela do S3. O OpenLineage centraliza todos os sinais num único DataHub (como Datahub Project ou Amundsen), propiciando um grafo de dependência e auditoria de impacto cobrindo toda a corporação.
Questão 84 · MLOps e SageMaker Feature Store

O que é "Training-Serving Skew" em Machine Learning e como o SageMaker Feature Store atua mitigando esse problema em vez de simplesmente salvar as agregações diretamente no S3 e no DynamoDB separadamente?

Dissonância Cognitiva do Modelo: O Training-Serving Skew ocorre quando o código Python em batch usado para preparar as variáveis (features) no treinamento usa dados sutilmente diferentes, ou processados com regras matemáticas divergentes da API em tempo real (ex: média de vendas calculada em pandas no notebook vs calculada no backend em Go).

Solução via Repositório Unificado:
  • Singularidade de Engenharia: O engenheiro de ML cria uma feature (ex: `score_risco`) e envia para o SageMaker Feature Store. A ferramenta encarrega-se da distribuição automática com consistência.
  • Online vs Offline Store Integrados: O SageMaker bifurca de forma transparente a feature: armazena a versão mais recente em uma Store Online (backend DynamoDB ou ElastiCache gerenciado) para garantir leituras em menos de 10ms aos endpoints de ML ao vivo; e sincroniza periodicamente em tabelas Parquet/Iceberg em uma Store Offline no S3, guardando todo o histórico de dados (Time Travel) para permitir o treinamento retroativo exato e consistente em lote.
Questão 85 · Prevenção de Drift de Modelos em Produção

Como identificar e alertar degradação proativa de inferência (Model Decay) de Modelos ML via SageMaker Model Monitor sem depender da realimentação retroativa (ground truth) de vendas geradas pelo negócio?

A Degradação Pós-Deploy: Após implantar um modelo (ex: aprovação de crédito) na AWS via SageMaker Endpoint, o contexto socioeconômico de longo prazo muda (ex: alta de juros ou mudança nos salários médios). Esperar semanas para constatar que o crédito aprovado estava causando inadimplência pode ser catastrófico.

Data Drift Monitoring (Monitoramento Estatístico Passivo):
  • Geração do Baseline Estatístico: Durante a fase final do treinamento, o Data Scientist exporta um relatório (Baseline) contendo as distribuições, médias e desvios padrão exatos das colunas do dataset aprovado de treino.
  • Captura Contínua: O SageMaker Endpoint é configurado para amostrar 100% (ou frações) das requisições JSON que recebe da rua e espelhá-las em um bucket S3 de monitoria.
  • Comparação Kolgomorov-Smirnov Automatizada: O SageMaker Model Monitor varre as predições salvas via S3 de hora em hora. Utilizando distâncias estatísticas (como o teste de Kolmogorov-Smirnov), ele compara se a distribuição da variável que está chegando (ex: média salarial informada no payload json) sofreu Data Drift expressivo em relação à média treinada do Baseline. Se o desvio for violado, o CloudWatch emite um alerta para o acionamento via EventBridge do Pipeline de Retreinamento (Amazon SageMaker Pipelines).
Questão 91 · EMR on EKS, Instâncias Spot e Perda de Shuffle

Ao utilizar instâncias Spot via Karpenter para orquestrar centenas de pods de Executors Spark no EKS, como evitar que o cluster perca dias de reprocessamento quando a AWS revogar as máquinas Spot (aviso de 2 minutos)?

Cenário de Desastre: Um job de 8 horas está na 7ª hora realizando um Shuffle pesado (agrupamento). A AWS exige de volta 5 instâncias Spot onde rodavam 20 Executors. Ao matá-los abruptamente, blocos essenciais de shuffle são deletados do disco local daquelas EC2. O job lança um `FetchFailedException` e reinicia do zero.

Diagnóstico e Mitigação OBRIGATÓRIA:
  • Spot Interruption Notice: O Karpenter é configurado nativamente com o EventBridge para capturar o "AWS Spot Interruption Notice" 2 minutos antes do corte, marcando o nó Kubernetes como Cordoned/Draining.
  • Graceful Decommissioning & Shuffle Tracking: No EMR on EKS, ativa-se spark.decommission.enabled=true e spark.storage.decommission.shuffleBlocks.enabled=true. Ao receber o alerta do Karpenter, o Spark trava a alocação de novas tasks naqueles 20 executors condenados e, em vez de morrer, passa os 2 minutos inteiros transmitindo freneticamente seus blocos críticos de Shuffle na memória para os Executors sobreviventes nas instâncias On-Demand. O nó morre após 2 minutos, mas o trabalho dos blocos foi salvo, o job continua normalmente sem FetchFailedException!

Arquitetura IAM Hub & Spoke: Gerenciamento Multi-Account

A Pergunta: Em grandes corporações usando Data Mesh, os dados ficam em uma conta central, e os times (Analytics, ML, Eng) usam contas separadas. Como eles acessam os dados da conta central com segurança?

A Solução: IAM AssumeRole Cross-Account

O padrão adotado é o Hub and Spoke. A conta central (Hub) armazena os buckets S3 e políticas de permissão. As contas "Spoke" possuem IAM Roles. O Lake Formation / IAM da conta central permite explicitamente que as Roles das contas Spoke façam um sts:AssumeRole ou possuam Cross-Account Access. Assim, o faturamento da computação ocorre nas contas Spoke, mantendo a governança dos dados estrita no Hub.

Em uma topologia Data Mesh com 25 contas produtores distribuídas, qual a função do Amazon DataZone na abstração de infraestrutura e como ele simplifica os grants Cross-Account manuais do Lake Formation?

O Amazon DataZone resolve a "camada de abstração de negócios" do Data Mesh. Ele fornece um portal web onde as contas AWS viram "Domínios" e as tabelas viram "Data Assets".
