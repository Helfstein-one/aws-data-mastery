Originação, KYC e Modelagem de Risco

O início do relacionamento: como o Onboarding gera dados vitais para os modelos de Scoring e determinação da Probability of Default (PD).

Conceito de Negócio: KYC (Know Your Customer) e Onboarding

A primeira etapa de um relacionamento bancário é a captura de dados demográficos, biométricos e financeiros (renda presumida). O KYC é um imperativo regulatório estruturado sob as normativas de PLD/AML (Prevenção à Lavagem de Dinheiro / Anti-Money Laundering) do Banco Central. Além de validar a identidade e a origem dos recursos para evitar atividades ilícitas, a instituição precisa responder a uma pergunta de $1 milhão na perspectiva de crédito: "Qual a probabilidade deste cliente não me pagar?" Essa métrica é conhecida como PD (Probability of Default).

A Engenharia por trás do Risco de Crédito (Scoring)

O Credit Scoring é o coração da operação de crédito. Ele classifica o cliente em Ratings (ex: AA, A, B, C... H) que determinam o limite pré-aprovado, a taxa de juros e o nível de provisionamento exigido pelo regulador.

Consultas Regulatórias: SCR e Bureaus
No onboarding, o sistema consulta o SCR (Sistema de Informações de Crédito do Banco Central), uma base de dados mandatória que registra todas as operações de crédito (exposição total) e eventuais atrasos, além do Serasa/Boa Vista. A engenharia orquestra essas APIs (via Lambda/Step Functions) e cria um Cache Analítico (ex: TTL no DynamoDB/Redis) para evitar pagar múltiplas vezes pela mesma consulta.
Modelagem de Scoring e Open Finance
Para aprovar um empréstimo em milissegundos via MLOps, a Engenharia constrói uma Feature Store. Com o Open Finance, enriquece-se o modelo com o fluxo de dados interbancários:
  • Comportamento transacional e atrasos consistentes em outras instituições.
  • Renda real aferida via histórico bancário e fluxo de caixa (PIX).
  • Comprometimento de Renda consolidado (DTI ampliado).

Deep Dive Arquitetural: Event Sourcing & Padrão Outbox

Bancos escaláveis não operam apenas lendo o estado atual do banco de dados (CRUD tradicional). Eles utilizam Event Sourcing, onde toda mudança de estado é um evento imutável. Para garantir que um evento de negócio seja gravado no banco relacional (Aurora) e transmitido para o Data Lake (S3) com garantia transacional, utilizamos o Padrão Outbox.

-- Transação ACID no Banco Core (PostgreSQL)
BEGIN;
  -- 1. Insere o contrato na tabela de negócio
  INSERT INTO contratos (id, cliente, valor) 
  VALUES ('c-123', 'cpf-99', 5000);
  
  -- 2. Insere na tabela Outbox na mesma transação
  INSERT INTO outbox (id, aggregate_type, payload) 
  VALUES (gen_random_uuid(), 'CONTRATO_CRIADO', '{"id":"c-123"}');
COMMIT;
Debezium & Kafka (CDC)
O Debezium (conector Kafka Connect) lê o WAL (Write-Ahead Log) do banco de dados interceptando as linhas da tabela outbox em tempo real. Ele publica esse evento em um tópico do Amazon MSK (Kafka) com a garantia de At-Least-Once (Pelo menos uma vez). Isso isola o banco de produção da carga de leitura analítica.

Matemática do Contrato: Juros, IOF e Amortização

A física do dinheiro: como um contrato é capitalizado ao longo do tempo e os dois principais sistemas de pagamentos.

1. Juros Simples vs. Compostos

O mercado de crédito opera esmagadoramente com Juros Compostos (juros sobre juros). A fórmula clássica de capitalização é M = C * (1 + i)^t, onde C é o Capital, i a taxa de juros e t o tempo.

Imposto sobre Operações Financeiras (IOF)
No Brasil, toda operação de crédito sofre tributação de IOF. Ele é composto por duas partes:
  • IOF Fixo (Alíquota Adicional): Geralmente de 0,38% incidente sobre o valor total do crédito.
  • IOF Diário: Um percentual (ex: 0,0082% ao dia) cobrado pelo tempo que o dinheiro fica emprestado (limitado a 365 dias).
Na Engenharia, o IOF é calculado na emissão (D0) e financiado junto com o principal, formando o Custo Efetivo Total (CET).

2. Tabela Price vs. Tabela SAC

Característica Tabela Price (Sistema Francês) Tabela SAC (Amortização Constante)
Valor da Parcela Fixo do início ao fim do contrato. Decrescente. A primeira é mais cara, a última é a mais barata.
Amortização da Dívida Crescente. No início abate pouca dívida e paga muito juro. Fixa/Constante. O saldo devedor cai de forma igual todos os meses.
Juros Pagos Decrescentes. O total de juros no final é maior que na SAC. Decrescentes rápidos. O total de juros no final é menor que na Price.

Como calcular em PySpark: Recriando Curvas em Escala

Em um banco com milhões de contratos ativos, iterar linha por linha é insustentável. Engenheiros de Dados frequentemente recriam curvas de amortização de forma distribuída usando PySpark. Eles projetam os fluxos de caixa futuros (Cash Flow Forecasting) para provisionamento contábil e testes de estresse (ALM). Utilizando pandas_udf (UDFs vetorizadas do Apache Arrow), aplicamos a matemática financeira simultaneamente em centenas de partições, viabilizando o cálculo massivo.

# PySpark + Pandas UDF: Tabela SAC Massiva
import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf('array<struct<mes:int, parcela:double, saldo:double>>')
def vetorizar_sac(capital: pd.Series, taxa: pd.Series, meses: pd.Series) -> pd.Series:
    res = []
    for c, t, m in zip(capital, taxa, meses):
        amort = c / m
        saldo = c
        curva = []
        for mes_idx in range(1, int(m) + 1):
            juros = saldo * t
            parcela = amort + juros
            saldo -= amort
            curva.append({'mes': mes_idx, 'parcela': parcela, 'saldo': saldo})
        res.append(curva)
    return pd.Series(res)

df_contratos = df.withColumn("curva_projetada", vetorizar_sac("valor_financiado", "taxa_mensal", "prazo"))
# PySpark + Pandas UDF: Tabela Price Massiva
import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf('array<struct<mes:int, parcela:double, saldo:double>>')
def vetorizar_price(capital: pd.Series, taxa: pd.Series, meses: pd.Series) -> pd.Series:
    res = []
    for c, t, m in zip(capital, taxa, meses):
        parcela = c * (t * (1+t)**m) / ((1+t)**m - 1)
        saldo = c
        curva = []
        for mes_idx in range(1, int(m) + 1):
            juros = saldo * t
            amort = parcela - juros
            saldo -= amort
            curva.append({'mes': mes_idx, 'parcela': parcela, 'saldo': saldo})
        res.append(curva)
    return pd.Series(res)

df_contratos = df.withColumn("curva_projetada", vetorizar_price("valor_financiado", "taxa_mensal", "prazo"))

Transição de Fase: Do Modelo à Realidade

A matemática de contratação estabelece o plano ideal (Tabela Price/SAC). Porém, o mundo real introduz quebras de expectativa: antecipações, atrasos e falhas operacionais sistêmicas. É aqui que saímos do ambiente determinístico de cálculos e entramos no gerenciamento do caos operacional: a fase de Pós-Venda.

Pós-venda, Inadimplência e Reconciliação

A fase complexa do Billing: liquidações, cálculos de multas, estornos e motores de conciliação.

Liquidação Antecipada (VPL)
Por lei (Resolução CMN), o cliente tem o direito de antecipar parcelas ou quitar o contrato obtendo abatimento proporcional dos juros futuros. Para isso, aplicamos a fórmula do Valor Presente Líquido (VPL), descontando os fluxos de caixa futuros usando a taxa de Deságio (geralmente idêntica à taxa efetiva da contratação). Em arquiteturas orientadas a eventos, a Engenharia de Dados consome o tópico AntecipacaoEfetuada no Amazon MSK/Kafka. Esse evento engatilha jobs em Streaming (Flink) ou Batch (Spark) que reprocessam a Curva de Amortização do contrato, expurgando os juros futuros e recalculando métricas de risco essenciais, como a Duration e o saldo médio da carteira do banco.
Atraso: Multa + Juros de Mora
Quando a data de vencimento é rompida sem confirmação de pagamento, inicia-se o cálculo punitivo:
1. Multa Moratória: Valor fixo percentual (limitado a 2% pelo CDC) aplicado uma única vez sobre o principal em atraso.
2. Juros de Mora: Penalidade contínua (ex: 1% ao mês), capitalizada pro-rata die por cada dia de inadimplência.
A engenharia modela esses acréscimos como rubricas separadas na Tabela Fato para que a área contábil consiga isolar a Receita de Juros Originais da Receita de Penalidades e Recuperação.

O Desafio da Engenharia: Inconsistências de Dados e Conciliação

Em instituições financeiras, frequentemente existem vários sistemas lidando com o mesmo dinheiro: o Sistema de Faturamento (Billing), o Sistema Transacional (Core Banking), o Barramento de Pagamentos (SPB/PIX) e o Livro Razão (Ledger).

Case de Divergência: O "Falso Inadimplente" do Fim de Semana

Cenário: Sexta-feira às 23h, o cliente paga a fatura via boleto. O sistema de Billing do banco registra o pagamento imediatamente (status = PAGO). Porém, a Câmara de Compensação (CIP/SLC) agrupa os boletos processados fora do horário e só liquida financeiramente o lote na manhã de segunda-feira.

O Problema: Se a rotina analítica de crédito roda no sábado ou domingo (batch D-0), ela consulta o Ledger Financeiro — que ainda não recebeu a confirmação de liquidação da CIP. Resultado: o cliente aparece como "Overdue" (Inadimplente) e seu Rating no Bacen é rebaixado indevidamente, gerando reclamações e risco regulatório.

Solução de Engenharia: O Motor de Reconciliação deve cruzar a perna do Billing (status PAGO) com a perna do Ledger (confirmação CIP pendente) e marcar esses casos como "Pendente de Liquidação" ao invés de "Overdue".

A Complexidade do Motor de Reconciliação

Construir um Motor de Reconciliação maduro é um dos desafios de engenharia mais complexos no mundo financeiro. Não se trata de um simples JOIN entre tabelas. O Gateway de Pagamentos (SPB, PIX, Adquirentes) e o Core Ledger possuem latências diferentes, taxas de falha sistêmicas e chaves de idempotência (como o E2E ID do PIX) que frequentemente sofrem mutação ou truncamento em sistemas legados. A engenharia cria motores robustos (ex: Spark Structured Streaming, Flink) que implementam lógica Fuzzy Matching, janelas temporais de tolerância e filas de DQL (Dead Letter Queue) para exceções. Os três cenários analíticos fundamentais que o motor resolve são:

  • Full Match: 1-para-1 ou 1-para-N (um pagamento liquidando múltiplas parcelas). As chaves primárias e valores batem até a última casa decimal.
  • Quebra de Valor ou Tolerância (Mismatch): O cliente pagou R$ 999,99 ao invés de R$ 1000,00. Regras de negócio podem ditar write-offs automáticos (ajuste operacional de 1 centavo via API) para não travar a conciliação por micro-divergências.
  • Orphan Events (Falta de Perna): O extrato do Bacen acusa entrada de R$ 500 no PIX, mas não há UUID correspondente no Billing. Gera-se uma exceção para o backoffice financeiro ou dispara-se um webhook de alerta (Alarme P1), pois o dinheiro está "voando" sem rastreabilidade de negócio.

Deep Dive de Engenharia: Late Arriving Events & Retrospectiva Contábil

Em sistemas financeiros complexos, a realidade não acontece em ordem cronológica perfeita. O maior inimigo do engenheiro de dados é o Late Arriving Event (Evento que chega atrasado).

O Desafio dos Late Arriving Events e Watermarking

Em processamento temporal distribuído, o Tempo do Evento (quando a transação ocorreu) quase nunca é igual ao Tempo de Processamento (quando chegou no servidor). Imagine um motor de Apropriação ou Conciliação em Apache Flink (Stateful Streaming) computando o fluxo diário com uma Tumbling Window das 23h às 23h59. Um cliente realiza um PIX às 23h58, mas os nós de rede de uma adquirente parceira congestionam, e a mensagem só atinge seu cluster Kafka à 00:45 do dia seguinte. A janela de agregação do dia D já foi fechada, sumarizada e os saldos foram enviados ao Banco Central.

Solução de Engenharia: Frameworks modernos separam os tempos utilizando Watermarks, uma heurística de progresso do tempo baseada em eventos. Configuramos um Allowed Lateness (ex: tolerância máxima de 2 horas). Durante esse período, o estado da janela é mantido na memória (RocksDB). Mas se o evento chegar após a tolerância máxima, ele torna-se estritamente um Late Arriving Event. Em vez de ser descartado, o Flink o redireciona para um fluxo paralelo usando Side Outputs. A arquitetura de dados deve então orquestrar um pipeline de Correção Contábil Retroativa (Backposting), gerando eventos de ajuste no Ledger (Livro-Razão) referenciados à data original (D-1). Essa robustez garante que o balanço final nunca seja corrompido por instabilidades de rede.

Transição de Fase: Do Caos Transacional à Ordem Contábil

Enquanto a fase de Pós-Venda lida com movimentações físicas, perdas, recuperações e conciliações atrasadas, a Contabilidade tem a missão rigorosa de traduzir toda essa complexidade em um formato padronizado (Livro-Razão) que reflita o verdadeiro "Patrimônio" do banco perante o Banco Central e acionistas, independente das instabilidades operacionais.

Contabilidade Bancária & Engenharia Avançada

O coração financeiro: Stop Accrual, Write-off, Diferimentos e Razonetes baseados em Event Sourcing.

Saldo Contábil vs. Saldo Devedor Total

No banco transacional, um contrato de empréstimo de R$ 10.000 (principal) a 2% a.m. durante 12 meses gera um Saldo Devedor Total (principal + juros futuros) de ~R$ 12.682. Porém, o Saldo Contábil (o que consta no Balanço Patrimonial no ativo) é o valor presente da carteira: R$ 10.000 no dia da concessão. A diferença de ~R$ 2.682 são juros ainda não incorridos, que serão reconhecidos como receita gradualmente via Apropriação Diária (Accrual). Resumindo:

  • Saldo Contábil (Curva): Valor presente do contrato registrado no Ativo do banco. Cresce a cada dia conforme os juros são apropriados.
  • Saldo Devedor Total: Soma de todas as parcelas futuras (principal + juros). É o que o cliente deve ao banco no cenário de quitação antecipada sem desconto.

Apropriação Diária (Spot Accrual)

A engenharia de dados precisa construir uma máquina de apropriação. Todo fim de dia (D-0), um pipeline em Spark calcula a fração de juros que o banco "ganhou" naquele dia e atualiza o fato diário.

PIPELINE DE APROPRIAÇÃO CONTÁBIL (ACCRUAL)
Regulamentação e Provisões: IFRS 9 & Resolução CMN 4.966

A contabilidade de crédito evoluiu do modelo de perdas incorridas (esperar o calote acontecer) para o modelo de Expected Credit Loss (ECL - Perda Esperada), exigido pelo IFRS 9 e regulado no Brasil pela Resolução CMN 4.966. No momento da concessão (D-0), a engenharia de dados já apoia os cálculos de PD, LGD (Loss Given Default) e EAD (Exposure at Default) para provisionar o risco e classificar a operação em estágios (Estágios 1, 2 e 3). Essa Provisão para Perdas Esperadas impacta diretamente o resultado do banco antes mesmo de qualquer atraso.

Inadimplência Extrema: Stop Accrual & Write-off

Stop Accrual
Sob a ótica do CMN 4.966 (Estágio 3), quando o crédito sofre degradação severa ou atinge cerca de 90 dias de atraso, o banco para de apropriar juros como receita (Stop Accrual). A dívida continua subindo, mas o banco deixa de reconhecer receita de juros no resultado, migrando para reconhecimento no recebimento, refletindo a alta incerteza.
Write-off (Baixa a Prejuízo)
Geralmente, diante da irrecuperabilidade (ex: longo atraso > 360 dias), o contrato é baixado definitivamente do Ativo (Write-off). Na arquitetura de dados, injetamos um evento `is_written_off=TRUE`. A cobrança é terceirizada e, caso seja recuperada futuramente, o valor entra como Receita de Recuperação de Crédito.

Deep Dive Arquitetural: O Razonete Contábil no Data Mesh

As Partidas Dobradas exigem que todo evento financeiro gere, no mínimo, dois lançamentos simétricos: um Débito (D) e um Crédito (C). Em arquiteturas modernas (Data Mesh), não deixamos que o domínio de negócio (Ex: Cartão de Crédito, Financiamento) suje seu banco de dados com regras contábeis puras. Em vez disso, usamos um Microserviço Tradutor Contábil (Accounting Engine).

1. Evento de Negócio (Raw)
O domínio de Cartões emite um evento agnóstico: { "tipo": "PAGAMENTO_RECEBIDO", "valor": 150.00 } via Kafka. Ele não sabe o que é Ativo, Passivo ou DRE.
2. Accounting Engine (Tradutor)
Uma aplicação streaming consome esse evento, busca os identificadores das contas contábeis correspondentes (COA - Chart of Accounts) e gera os Eventos de Razonete duplos.
3. Ledger Analítico (Iceberg)
O Data Lake armazena a tabela unificada do Razonete usando Apache Iceberg. Tabelas particionadas por data_referencia e conta_contabil garantem queries de fechamento milionárias rodando em segundos no Athena.
ARQUITETURA DE RAZONETE DISTRIBUÍDO E PARTIDAS DOBRADAS (DATA MESH)
Garantia de Qualidade: Data Contracts & Idempotência

Ao desacoplar o sistema transacional do motor contábil, é imperativo usar Data Contracts (como Protobuf ou Confluent Schema Registry). Se o desenvolvedor backend mudar o payload de "PAGAMENTO_RECEBIDO" para "PAGAMENTO_CONCLUIDO" sem avisar, o pipeline de dados quebra silenciosamente, destruindo o balanço do banco.

Além disso, o motor de Accounting e o Iceberg precisam garantir a Idempotência (processar uma mensagem duas vezes não deve gerar dois débitos). A tabela Iceberg processa deduplicação analítica via chave de event_uuid cruzado com MERGE INTO.

Deep Dive em Riscos e Validação Regulatória

A física pesada por trás do provisionamento de capital, Basileia III e modelagem estocástica massiva com Big Data.

1. Risco de Crédito: A Era do IRB (Internal Ratings-Based)

O Risco de Crédito evoluiu de planilhas de Excel para modelos massivos de Machine Learning. Sob o Acordo de Basileia, os bancos podem utilizar a abordagem padrão do BACEN ou adotar o IRB (Internal Ratings-Based). No IRB, o banco desenvolve seus próprios modelos internos para calcular a Perda Esperada (ECL - Expected Credit Loss).

  • PD (Probability of Default): A probabilidade de um cliente entrar em calote (default) em 12 meses. O BACEN exige que esses modelos sejam rigorosamente validados, sem viés (bias) sociodemográfico (fairness).
  • LGD (Loss Given Default): Qual a recuperação financeira real em caso de calote (após leilões judiciais, venda de dívidas em FIDC).
  • EAD (Exposure at Default): O saldo devedor projetado para o momento da quebra. Para derivativos de balcão (OTC), o EAD é volátil e exige simulações sofisticadas (CVA - Credit Valuation Adjustment).
Data Lineage e Resolução CMN 4.557 / 4.966
Bancos sofrem auditorias rigorosas do Banco Central (BACEN). Quando o modelo nega crédito ou aumenta a provisão, o regulador exige a rastreabilidade completa (Data Lineage). Na AWS, isso é implementado forçando todas as queries passarem pelo AWS Lake Formation, mapeando qual versão do modelo no SageMaker consumiu qual snapshot do Iceberg no S3.

2. Risco de Mercado: Value at Risk (VaR) e Monte Carlo Estocástico

Enquanto o risco de crédito foca na falência do tomador, o Risco de Mercado mede o quanto o banco pode perder devido à volatilidade diária de preços, câmbio e taxas de juros. A métrica absoluta global é o VaR (Value at Risk) com 99% de confiança estatística.

Bancos Tier-1 abandonaram o VaR Histórico/Paramétrico em favor do VaR por Simulação de Monte Carlo. Isso exige projetar 10.000 caminhos aleatórios (Movimento Browniano Geométrico - GBM) para todas as curvas de juros e reprecificar milhões de derivativos da tesouraria para cada cenário.

Arquitetura do Motor de Stress Testing AWS

MONTE CARLO PIPELINE (VAR)

O Código: Engine de Simulação (Movimento Browniano Geométrico)

Na tesouraria moderna, o Quant modela as curvas e a Engenharia escala. Usamos Apache Spark (Amazon EMR). Através do pandas_udf, distribuímos o cálculo matricial (NumPy) para milhares de vCPUs rodando instâncias Spot no AWS. Cada nó calcula o "choque estocástico" em milissegundos.

# PySpark + NumPy: Simulação de Monte Carlo (Value at Risk)
import numpy as np
import pandas as pd
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import ArrayType, DoubleType

# Configuração Matemática (Movimento Browniano Geométrico)
# dS = S * (mu * dt + sigma * dW)
CENARIOS = 10000
HORIZONTE_DIAS = 10

@pandas_udf(ArrayType(DoubleType()))
def monte_carlo_var(preco_atual: pd.Series, volatilidade: pd.Series, drift: pd.Series) -> pd.Series:
    res = []
    # Vetorização por Ativo (Ex: PETR4, WINZ, DI1)
    for S0, sigma, mu in zip(preco_atual, volatilidade, drift):
        dt = 1 / 252.0  # Dias úteis no ano
        
        # Gera a matriz de choques aleatórios normais Z ~ N(0,1)
        # Shape: (Cenários, Dias) = (10.000, 10)
        Z = np.random.standard_normal((CENARIOS, HORIZONTE_DIAS))
        
        # Calcula a variação estocástica acumulada
        # Matriz de Retornos Diários
        retornos = (mu - 0.5 * sigma**2) * dt + sigma * np.sqrt(dt) * Z
        
        # Produto cumulativo para encontrar o preço final projetado
        preco_futuro = S0 * np.exp(np.sum(retornos, axis=1))
        
        # Encontra a perda (P&L) em cada cenário
        pnl = preco_futuro - S0
        
        # Calcula o VaR (Percentil 1% pior caso das 10.000 simulações)
        var_99 = np.percentile(pnl, 1)
        res.append([float(var_99), float(np.mean(pnl))])
        
    return pd.Series(res)

# Aplicação distribuída no Data Lake (Centenas de nós Spark)
df_risco = df_carteira.withColumn(
    "var_stats", 
    monte_carlo_var("mtm_usd", "volatilidade_implícita", "taxa_livre_risco")
)

Architecture Hardening & Resilience

1. Fault Tolerance on Amazon EMR (Spot Interruption Mitigation): Utilizing a heterogeneous cluster fleet with task nodes on Spot instances, we enforce YARN Node Decommissioning coupled with Amazon EC2 Spot Interruption Notices. Upon receiving the two-minute warning via EventBridge, EMR gracefully drains active containers, preventing localized data loss and re-scheduling Spark tasks to remaining nodes without job failure.

2. Security & Compliance (BACEN Guidelines): All market data payloads (yield curves, volatility surfaces) at rest in Amazon S3 are encrypted utilizing SSE-KMS with Customer Managed Keys (CMKs), ensuring granular key rotation and CloudTrail audit logging for `GenerateDataKey` operations. Access control is governed by AWS Lake Formation, enforcing cell-level filtering (row/column-level security) to restrict access to sensitive financial instruments based on the principal's IAM role.

3. Data Lineage & Audit Reproducibility: To ensure deterministic Monte Carlo re-runs for regulatory backtesting, input datasets are versioned. The exact S3 object version IDs (or Delta Lake/Iceberg snapshot IDs) of the yield curves and RNG seed states used during execution are persisted into an immutable Amazon DynamoDB audit ledger, enabling exact bit-for-bit replayability.

3. Risco de Liquidez (ALM): LCR e NSFR

Após cobrir crédito (calote) e mercado (preço), resta o Risco de Liquidez (Cash Flow). O banco não quebra pela perda em si, mas pela falta de dinheiro em caixa na compensação noturna (SPB). O setor de ALM (Asset Liability Management) gerencia esse "descasamento".

LCR (Liquidity Coverage Ratio)
Resiliência de Curto Prazo. O banco precisa provar ao BACEN, gerando relatórios D-0, que possui ativos superlíquidos (Títulos Públicos) suficientes para sobreviver a uma corrida bancária de 30 dias sob severo estresse.
NSFR (Net Stable Funding Ratio)
Métrica de Longo Prazo. Garante que se o banco conceder um financiamento imobiliário de 30 anos (Ativo Iliquido), ele está financiando isso com captações estáveis (LCI/Poupança), e não com CDI de curtíssimo prazo, evitando alavancagem suicida.

Deep Dive Regulatório e Data Mesh

O Peso da Regulação na Engenharia de Dados

A arquitetura de dados financeiros não é desenhada apenas para escalabilidade ou performance, mas fundamentalmente para o Compliance Regulatório. A evolução das normativas brasileiras e internacionais obriga a engenharia a adotar paradigmas avançados de isolamento e governança, sendo o Data Mesh o modelo arquitetural definitivo para suportar essa complexidade.

1. PLD/AML (Circular BACEN 3.978)

Prevenção à Lavagem de Dinheiro (PLD) e Financiamento ao Terrorismo (CFT)

A Circular 3.978 obriga as instituições a monitorarem continuamente as transações e o perfil de risco dos clientes, reportando operações suspeitas ao COAF. Atrasos ou falhas de detecção resultam em perda da licença bancária.

Tradução para Data Mesh: O domínio transacional emite eventos crus (ex: transferências PIX) via mensageria (Kafka/Kinesis). O domínio de Compliance consome esses eventos quase em tempo real (Spark Streaming/Flink) cruzando-os com listas restritivas (OFAC, PEPs). Para proteger dados PII, o AWS Lake Formation aplica Column-Level Security (anonimizando nomes) e Row-Level Security (filtrando apenas transações suspeitas), garantindo que nem mesmo os engenheiros do Data Lake tenham acesso indevido à privacidade dos clientes.

2. Basileia III e a Retenção Histórica (IRB)

Acordos de Basileia e Internal Ratings-Based Approach (IRB)

Para determinar o Capital Regulatório que o banco deve reter, o BACEN permite modelos internos de risco de crédito (IRB), desde que o banco consiga provar a robustez dos modelos com séries históricas extensas.

Tradução para Data Mesh: O domínio de Risco (Credit Scoring) atua como Produtor de Dados de Modelagem. Ele obriga o Data Lake a armazenar "Safras" (Vintages) de crédito por até 10 anos. Para viabilizar esse volume (Petabytes) sem explodir custos (FinOps), a engenharia aplica ciclos de vida rigorosos: os modelos processam no Amazon EMR sobre tabelas Iceberg e, mensalmente, os logs de inferência antigos são transicionados para Amazon S3 Glacier Deep Archive. Quando o BACEN exige auditoria (Backtesting retroativo), a arquitetura restaura o gelo sob demanda via Athena.

3. Dupla Contabilidade (Resolução CMN 4.966 / IFRS 9)

Expected Credit Loss (ECL) e o Desafio Multi-Ledger

As normas mudaram de "Perda Incorrida" (provisionar quando o cliente não paga) para "Perda Esperada" (provisionar no dia do empréstimo baseado no rating). Além disso, reportar BRGAAP (local) e IFRS 9 (matriz internacional) simultaneamente tornou-se o padrão.

Tradução para Data Mesh: Cria-se uma fronteira estrita. O domínio de Originação gera um evento agnóstico ("CONTRATO_ASSINADO"). Esse evento viaja pelo Data Contract até o domínio de Accounting, onde motores de tradução em Flink bifurcam a transação em dois Livros-Razão (Multi-Ledger) armazenados no Redshift ou Iceberg. Um pipeline calcula o Accrual e Stop Accrual na ótica IFRS, enquanto outro processa as diretrizes do COSIF (Plano de Contas do Bacen).

4. Reportes Massivos e CVM (Securitização)

DOC 3040/3044 (SCR)
Normativa: Obrigatoriedade do envio mensal de todos os saldos e garantias da carteira de crédito.
Engenharia: Tratado como um Consumer Data Product regulatório. Jobs noturnos no AWS Glue consolidam trilhões de linhas. O maior desafio é o Data Quality: garantir que a soma dos XMLs gerados para o BACEN (Data Mart regulatório) bata centavo por centavo com a tabela de saldos contábeis do Iceberg (Single Source of Truth).
CVM (FIDCs) e AWS RAM
Normativa: Securitização de recebíveis exige segregação total entre a Originadora e a Custodiante do Fundo.
Engenharia: É a aplicação máxima do Data Mesh. Criam-se Contas AWS separadas (Multi-Account). A Originadora não envia mais arquivos `.csv`; ela expõe tabelas do Iceberg ou Redshift via AWS Resource Access Manager (RAM) e Lake Formation (Cross-Account Sharing). A Custodiante consulta os dados na sua própria conta, garantindo independência jurídica e imutabilidade dos direitos creditórios auditados pela CVM.

Legenda do Mapa Arquitetural (Enterprise Data Platform)

Este diagrama consolida o fluxo de vida dos dados em 5 grandes fronteiras (Swimlanes):

  • 1. Source Systems: Origem dos dados financeiros (Bancos legados, APIs de cartão, Gateways). Representam os domínios transacionais.
  • 2. Ingestion & Orchestration: A malha conectiva. O DMS puxa as tabelas relacionais em CDC (Change Data Capture), o MSK (Kafka) ingere os eventos em tempo real, e o MWAA (Airflow) orquestra a batuta.
  • 3. Medallion Lakehouse: O coração analítico (S3 Bronze, Silver, Gold). O Spark no EMR faz o processamento pesado e reconciliação, enquanto o Iceberg garante a transacionalidade (ACID) na camada Silver.
  • 4. Serving & Analytics: A entrega do valor. Athena para consultas Ad-hoc, Redshift para Data Marts estruturados de finanças e SageMaker rodando inferência de ML para score de crédito.
  • 5. Governance & Security: A base que permeia toda a plataforma. O Lake Formation governa quem acessa qual coluna, e o KMS criptografa os dados financeiros PII (Personal Identifiable Information).

billing_df = spark.readStream.format("kafka") \
    .option("kafka.bootstrap.servers", "boot-x.msk.aws:9098") \

    .option("kafka.bootstrap.servers", "boot-x.msk.aws:9098") \
    .option("subscribe", "gateway-events") \

# 3. Stream-to-Stream Join com Watermark (Evita OOM - Out of Memory)
# Exige que o pagamento chegue no máximo 2 horas após a fatura
reconciled_df = billing_df.withWatermark("timestamp", "2 hours").alias("bill") \
    .join(
        gateway_df.withWatermark("timestamp", "2 hours").alias("pay"),
        expr("""
            bill.invoice_id = pay.invoice_id AND
            pay.timestamp >= bill.timestamp AND
            pay.timestamp <= bill.timestamp + interval 2 hours
        """)
    )

# 4. Grava no Data Lake (Apache Iceberg) para auditoria

    .format("iceberg") \
    .outputMode("append") \
    .option("checkpointLocation", "s3://finance-lake/checkpoints/reconciliation/") \

-- Athena SQL: Fechamento D-0 e Livro-Razão (Ledger)
-- Calcula o saldo diário de cada conta contábil baseado nos eventos do Iceberg

WITH daily_movements AS (
    SELECT 
        account_id,
        date_trunc('day', transaction_date) AS ledger_date,
        SUM(CASE WHEN transaction_type = 'CREDIT' THEN amount ELSE 0 END) AS total_credit,
        SUM(CASE WHEN transaction_type = 'DEBIT' THEN amount ELSE 0 END) AS total_debit
    FROM 
        aws_catalog.finance.reconciled_ledger
    WHERE 
        status = 'CLEARED'
    GROUP BY 
        1, 2
)
SELECT 
    account_id,
    ledger_date,
    total_credit,
    total_debit,
    (total_credit - total_debit) AS daily_net_balance,
    -- Window function para rodar o saldo acumulado (Running Total)
    SUM(total_credit - total_debit) OVER (
        PARTITION BY account_id 
        ORDER BY ledger_date 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_balance
FROM 
    daily_movements
ORDER BY 
    account_id, ledger_date DESC;
