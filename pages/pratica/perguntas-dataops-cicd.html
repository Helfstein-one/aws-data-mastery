Questão 7 · Apache Spark

Como a memória do executor JVM do Spark é subdividida internamente e como debugar erros de OOM no User Memory vs Execution Memory?

Física da Memória Spark: A memória total (Executor JVM Heap) é subdividida em três grandes blocos controlados pelas propriedades de configuração do Spark:

  • Spark Memory (60% por padrão, via spark.memory.fraction): Subdividido dinamicamente entre Execution Memory (usado para shuffles, joins e agregações) e Storage Memory (usado para caching/persistence e transmissão de variáveis de broadcast).
  • User Memory (40% restante): Reservado para estruturas de dados do próprio usuário em código PySpark (UDFs Python, metadados internos de partições do Spark).
  • Reserved Memory: 300 MB fixos do Spark para garantir a execução estável do motor interno.

Spark JVM Memory Model
Caso de Debug em Processo Seletivo:

Se você receber OOM no User Memory, a causa provável é o uso de Python UDFs pesados sem otimização ou tentativa de processar metadados gigantes no driver. Resolva migrando UDFs Python puras para funções nativas da API DataFrame do Spark (Spark SQL) que rodam nativamente na JVM (otimizadas pelo compilador Catalyst).

Questão 20 · Qualidade de Dados & Glue DQ

Como desenhar um mecanismo de "Circuit Breaker" de Qualidade de Dados na AWS usando o AWS Glue Data Quality e regras DQDL?

Data Quality como Proteção: Consumir dados errados ou corrompidos em relatórios e dashboards gera desconfiança nos negócios. A melhor estratégia é rodar regras de integridade diretamente nos estágios de ingestão e, caso as regras falhem, acionar um disjuntor (Circuit Breaker) que interrompe o fluxo de dados para as camadas finais e isola os dados ruins para investigação.

Uso do AWS Glue Data Quality (DQDL): A linguagem de definição de qualidade do Glue permite criar regras declarativas e de fácil leitura para avaliar seus Data Frames. Um exemplo de arquivo declarativo DQDL:

Rules = [
  RowCount between 1000 and 2000000,
  Completeness "user_id" = 1.0,
  Completeness "email" > 0.95,
  IsUnique "user_id",
  ColumnDataType "created_at" = "Timestamp",
  ColumnValues "status" in ["ATIVO", "INATIVO", "PENDENTE"]
]
Fluxo e Arquitetura do Circuit Breaker:
  1. O Job do AWS Glue ou PySpark lê os dados da camada Bronze e executa a verificação declarada na regra DQDL usando a biblioteca nativa do Glue.
  2. A avaliação retorna um score de sucesso (ex: 85% das regras passaram, mas a unicidade de user_id falhou).
  3. Se o score for menor que o limite aceitável do contrato de qualidade (ex: 100% para chaves primárias e completeness), o pipeline ativa o disjuntor:
    • Grava o lote corrompido em uma pasta isolada no S3 (s3://data-quarantine-bucket/bronze-failures/) para fins de depuração.
    • Gera uma falha explícita no Job do Glue (ou levanta uma exceção no código Python), impedindo que o pipeline envie os dados para a camada Silver.
    • Publica um evento no Amazon EventBridge, que engatilha uma notificação integrada para o time via Slack e ativa alertas no Datadog.
Questão 32 · dbt Core & dbt Cloud no AWS Glue

Como estruturar a integração do dbt com o AWS Glue (usando o dbt-glue adapter) para executar modelos analíticos sobre o motor PySpark, e quais as melhores práticas para gerenciar modelos incrementais em tabelas Apache Iceberg sem sofrer com OOM ou corrupção de snapshots?

Mecanismo dbt-glue: O dbt Core/Cloud utiliza o conector dbt-glue para compilar queries SQL escritas em Jinja e transformá-las em blocos de execução Spark SQL. O dbt se conecta ao AWS Glue através de Interactive Sessions (Sessões Interativas baseadas em Jupyter Notebook Kernel) ou submetendo tarefas transientes de Glue Jobs. O Glue interpreta as tabelas físicas mapeadas no AWS Glue Data Catalog.

Estratégias de Modelos Incrementais & Evolução de Schema no Iceberg:
  • Estratégias de Carga Incremental: Ao atualizar dados em tabelas Iceberg usando dbt incremental, utilize incremental_strategy='merge' em vez de append. A estratégia merge executa um UPSERT lógico no Iceberg baseado em chaves exclusivas. O Iceberg gerencia isso de forma nativa por meio de Merge-on-Read (MoR) (gravação rápida escrevendo arquivos de exclusão) ou Copy-on-Write (CoW) (reescrevendo os arquivos afetados no S3). Para tabelas de escrita massiva, prefira MoR para evitar lentidão no commit Spark.
  • Gestão de DDL Drift: Ative a propriedade do dbt on_schema_change='sync_all_columns'. Graças à flexibilidade de metadados do Apache Iceberg, adicionar ou remover colunas ocorre sem a necessidade de reescrever arquivos Parquet históricos no S3. O Iceberg apenas atualiza o esquema no JSON de metadados da tabela, sincronizando com o Glue Catalog de forma instantânea.
  • Prevenção de OOM no Driver: Evite carregar grandes volumes de dados de logs no driver dbt/Glue executando operações que envolvam collect (como dbt_utils.get_column_values). Limite as transações executando compactação de dados (OPTIMIZE) de forma desacoplada do fluxo de execução do dbt para evitar concorrência no metadados do Iceberg.
Questão 4 · Amazon Athena

Como resolver o erro "Metadata limit exceeded" ou queries Athena que falham por timeout antes de iniciar o scan dos dados?

Causa Física: Quando o Athena executa uma query em uma tabela particionada convencional (ex: particionada por ano/mes/dia/cliente), ele precisa fazer chamadas de API para o AWS Glue Data Catalog para listar os arquivos físicos correspondentes às partições solicitadas. Se a tabela tem milhões de partições, a fase de planejamento da query excede os limites de limite de API do Glue e gera timeout antes do processamento dos dados começar.

A Solução Suprema: Partition Projection

O Partition Projection armazena as regras de geração das partições diretamente como propriedades da tabela no Glue Catalog (ex: ano varia de 2020 a 2026). O Athena calcula em memória os caminhos físicos do S3 baseando-se nas datas passadas no filtro SQL, ignorando completamente as chamadas de API do catálogo e eliminando o timeout.

-- Exemplo de registro de tabela Athena com Partition Projection configurado
CREATE EXTERNAL TABLE sales_projected (
    id_venda string,
    valor double
) 
PARTITIONED BY (ano string, mes string)
LOCATION 's3://my-datalake/sales/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.ano.type' = 'integer',
    'projection.ano.range' = '2020,2026',
    'projection.mes.type' = 'integer',
    'projection.mes.digits' = '2',
    'projection.mes.range' = '1,12',
    'storage.location.template' = 's3://my-datalake/sales/ano=${ano}/mes=${mes}/'
);
Questão 30 · Amazon Redshift Serverless

Como funciona o mecanismo de auto-scaling de concorrência (Concurrency Scaling) do Amazon Redshift Serverless e como o uso inadequado do comando COPY a partir do S3 com arquivos mal-distribuídos pode anular o paralelismo dos slices de computação (Slices Skew)?

Concurrency Scaling no Redshift: O Redshift Serverless dimensiona dinamicamente a computação adicionando recursos adicionais de processamento (clusters transitórios) sob concorrência pesada de leitura. No entanto, na fase de gravação e ingestão via comando COPY, a concorrência e o paralelismo dependem estritamente da estrutura física dos arquivos a serem ingeridos do S3.

O gargalo de Slice Skew na ingestão COPY:
  • Ingestão Sem Divisão (Single File Gzip): Se dispararmos um COPY de um único arquivo compactado gigante de 100 GB em formato Gzip (dados_vendas.csv.gz), o Redshift será incapaz de dividir o arquivo e ler em paralelo. Apenas um único slice de computação no cluster trabalhará descompactando e gravando os registros, enquanto os demais slices ociosos aguardam, gerando lentidão extrema (slice skew).
  • Melhor Prática de Divisão (Split Files): Divida os arquivos de dados na origem no S3 em múltiplos fragmentos comprimidos de tamanhos uniformes e idênticos (ex: 20 arquivos de 5 GB em vez de 1 de 100 GB), com uma quantidade correspondente a um múltiplo do número de compute slices do seu cluster de destino. O comando COPY acionará todos os slices do cluster para carregar cada arquivo em paralelo de forma direta e instantânea.
Questão 63 · Amazon Aurora Replica Lag & Read Scaling

Como mitigar gargalos de performance e isolar o tráfego operacional (OLTP) de gravação durante extrações analíticas massivas no Amazon Aurora PostgreSQL?

Desafio de Concorrência: Consultas analíticas pesadas (Full Table Scans) concorrendo com gravações na instância primária (Writer) geram locks de páginas de banco de dados e saturação de I/O de disco.

Estratégia Arquitetural de Ingestão:
  • Leitura via Reader Endpoint com Autoscaling: Aponte o pipeline analítico (JDBC Spark) estritamente para o Reader Endpoint do Aurora. Configure o auto-scaling do cluster Aurora com base na utilização média de CPU dos nós leitores. À medida que o job analítico inicia, réplicas adicionais são ligadas dinamicamente e as conexões balanceadas em round-robin.
  • Minimização de Lag de Réplica: Devido à arquitetura de armazenamento compartilhado do Aurora (Aurora Storage Volume), as réplicas analíticas não processam gravações físicas de dados nos seus discos. No entanto, elas devem atualizar seus caches locais na memória RAM com os logs de transação da Writer. Monitore a métrica AuroraReplicaLag e garanta que queries pesadas não mantenham transações abertas por longos períodos, o que impediria a réplica de atualizar sua memória (gerando lag artificial).
Questão 67 · Apache Iceberg WAP (Write-Audit-Publish) Pattern

Como funciona o padrão arquitetural WAP (Write-Audit-Publish) no Apache Iceberg e como as branches lógicas da tabela previnem a ingestão de registros órfãos ou inválidos na camada final de Serving?

Gargalo Operacional: Em pipelines analíticos tradicionais (Hive/Parquet puro), se um erro de qualidade de dados ocorrer no final de uma transação batch de 10 milhões de registros, a tabela física já estará modificada, forçando reversões complexas (rollbacks em S3) ou poluindo relatórios ativos de BI.

Arquitetura e Fluxo do WAP:
  • Write (Escrever na Branch): O pipeline PySpark ou dbt grava as alterações apontando para uma branch lógica temporária da tabela Iceberg (ex: df.option("branch", "wap_temp").save(...)). Os dados físicos são salvos no S3, mas o snapshot principal (main branch) da tabela continua inalterado.
  • Audit (Auditar): Ferramentas de validação ativa ou queries SQL rodam contra a branch temporária buscando quebras de contratos de dados (valores negativos, nulos em PKs).
  • Publish (Publicar via Fast-Forward): Se os testes passarem, a engine executa uma chamada de sistema (ex: CALL system.cherry_pick_snapshot()) para avançar a referência da branch main para o snapshot validado. Caso contrário, a branch temporária é descartada, impedindo a exposição dos dados inválidos.
Questão 78 · Star Schema vs. Snowflake no Amazon Redshift

Ao projetar um Data Warehouse corporativo no Amazon Redshift, qual arquitetura de modelagem de dados é preferível entre Star Schema e Snowflake Schema, e qual o impacto dos Joins na execução distribuída do cluster?

Gargalo de Processamento Distribuído: O Amazon Redshift é um banco de dados Massivamente Paralelo (MPP). Em queries distribuídas, realizar joins exige que as fatias de dados de diferentes nós computacionais sejam redistribuídas pela rede (Data Shuffle) para que os registros correspondentes sejam pareados na memória física.

Estratégia Recomendada para o Redshift:
  • Preferência pelo Star Schema: O Star Schema é amplamente preferido em relação ao Snowflake no Redshift. Por possuir dimensões desnormalizadas e achatadas, as queries analíticas exigem apenas um nível de join (Fato ➔ Dimensão). Isso diminui drasticamente a necessidade de shuffles de rede complexos e agiliza a execução da query.
  • O Problema do Snowflake no Redshift: No Snowflake, a normalização fragmenta os dados em múltiplas tabelas (Fato ➔ Cliente ➔ Cidade ➔ Estado). Queries analíticas básicas exigem joins em cascata. O otimizador de plano do Redshift precisará mover dados de várias dimensões entre nós para resolver a query, gerando congestionamento na rede interna do cluster.
  • Otimização com Chaves de Distribuição: No Star Schema, configure a chave de distribuição (DISTKEY) da tabela Fato e da maior dimensão (ex: Cliente) com o mesmo campo ID. O Redshift executará o join localmente sem mover dados de nó em nó. Para as demais dimensões menores (como Tempo e Categoria), use DISTSTYLE ALL para clonar as tabelas em todos os nós, garantindo joins de latência zero.
Questão 82 · Padrão Write-Audit-Publish (WAP) com Apache Iceberg

Como o padrão Write-Audit-Publish, possibilitado por formatos de tabela como Apache Iceberg, evita que dados mal formatados poluam a camada Gold (apresentação) do Data Lake e interfiram nos dashboards?

O Problema da Gravação Suja: Historicamente, os jobs do Spark escrevem os dados diretamente na tabela final. Se o job falhar pela metade ou carregar dados nulos acidentalmente, os dashboards apontados para essa tabela apresentarão dados inconsistentes aos usuários de negócio antes que o time de dados perceba o problema.

O Pipeline Seguro (Branching Analítico):
  • Write (Escrever): O job de ETL do Spark não escreve diretamente na branch principal. Ele cria e escreve os dados em uma ramificação oculta de auditoria no Iceberg (ex: `branch_audit_etl`). Os dashboards do QuickSight ou Tableau conectados no Athena apontam para a branch `main` e continuam lendo os dados de ontem com performance normal.
  • Audit (Auditar): Um job secundário de Data Quality (ex: usando Great Expectations ou Glue Data Quality) é acionado para varrer apenas a `branch_audit_etl`, aplicando regras como limiares estatísticos (standard deviation) e limites nulos.
  • Publish (Publicar): Apenas se a auditoria passar com sucesso, uma operação (stored procedure) atômica do Iceberg `fast_forward` transfere e torna os dados dessa branch visíveis na branch `main`. Toda a transição leva milissegundos e elimina a janela de inconsistência de dados.
Questão 90 · Redshift Managed Storage (RA3) e Custos Operacionais

Qual o argumento financeiro e de governança para convencer um CTO a migrar Clusters Redshift on-premise style (DS2/DC2) para a família RA3 com Data Sharing, quando a empresa possui 5 squads diferentes consumindo e copiando dados uns dos outros?

Cenário: Equipes de Marketing, Risco, Finanças e Vendas rodam complexos pipelines (AWS Glue) toda madrugada apenas para copiar tabelas do "Cluster Core" para seus próprios "Clusters Departamentais", encarecendo a conta da AWS e gerando dessincronia (dados velhos).

A Solução (Storage Desacoplado):
  • Dissociação Paga Apenas o Necessário: Em DC2 (acoplado), escalar o disco para armazenar mais histórico obrigava a pagar por caríssimos chips de CPU adicionais ociosos. No RA3, os dados pesados moram fisicamente no S3 (preço ínfimo de centavos por GB), mantendo a CPU dimensionada apenas para a força da query.
  • Morte do ETL de Cópia via Data Sharing: Com o RA3, o Storage reside no S3. Isso permite habilitar o Data Sharing. O Cluster de Marketing pode ler a tabela de Vendas ao vivo, utilizando apenas o próprio poder computacional de Marketing, sem que o pipeline precise mover um único byte fisicamente, eliminando a fatura do AWS Glue e a obsolescência de dados.
Questão 96 · Redshift RA3, Data Sharing e Estrangulamento de Concorrência (Staff Level)

Sua empresa consolidou dezenas de Terabytes no Amazon Redshift (família RA3) adotando o "Managed Storage". Durante a madrugada, longos processos de ETL de Ingestão saturam os Compute Nodes. Ao mesmo tempo, o time de engenharia global e analistas tentam visualizar os dashboards no QuickSight. A infraestrutura inteira sofre lentidão severa. Como isolar perfeitamente a computação mantendo "Single Source of Truth"?

Cenário: Você deseja parar as filas de "Noisy Neighbors". A diretoria descarta mover os dados lidos para bancos relacionais e exige usar o Redshift DW.

Diagnóstico e Ação (Desacoplamento Arquitetural de CPU):
  • A Causa Física (Acoplamento de Concorrência Clássico): Embora o Redshift RA3 desacople o Storage (guardando dados frios no S3 RMS e caches no SSD local), as cargas de trabalho (ETLs e leituras Ad-Hoc) ainda competem violentamente pelo mesmo cluster Leader e pelos mesmos Slices do Compute Node. Mesmo com o AutoWLM ou Concurrency Scaling ativados, um volume massivo de Ingestões DML (INSERT/UPDATE/COPY) engasga o pipeline da fila, exigindo IOPS intensos no EBS local e travando a CPU que o QuickSight depende.
  • A Mitigação Estrutural (Redshift Data Sharing Producer/Consumer): A estratégia de Staff Engineer é criar um ambiente Multi-Cluster sem copiar os dados. Você mantém o cluster RA3 original dedicado puramente à gravação e transformações intensas (o Cluster "Produtor"). Você então provisiona um segundo cluster Redshift (ou até um Redshift Serverless Pay-Per-Query) atuando como "Consumidor", focado em Servir Dashboards. Questão 12 · Teorema PACELC

Qual o tradeoff de consistência e latência (Teorema PACELC) ao escolher entre Aurora Global Database e DynamoDB Global Tables?

Entendendo o Teorema PACELC: Uma extensão do teorema CAP. Ele dita: Se houver uma partição de rede (P), escolha entre Disponibilidade (A) ou Consistência (C). Caso contrário (E - Else), escolha entre Latência (L) ou Consistência (C).

Tradeoffs em Entrevista Técnica:
  • DynamoDB Global Tables (Modelo PA/EL): Sob partições de rede, mantém a disponibilidade local alta (PA). Em estado normal, prioriza latências de escrita extremamente baixas em milissegundos nas regiões locais enviando replicações de forma assíncrona (EL), garantindo eventual consistência entre regiões distantes.
  • Aurora Global Database (Modelo PC/EC): Sob partições, pode parar escritas na região secundária para garantir consistência física exata (PC). Em estado normal, o Aurora usa replicação física otimizada em nível de storage de baixa latência mas síncrona/consistente para evitar conflitos de dados históricos (EC).

Regras de Gestão de DDL no DMS:

Técnicas de Mitigação: Graceful Decommissioning & Shuffle Tracking:
  • No EMR on EC2: Projete o cluster utilizando Spot Instances estritamente para Task Nodes (puramente computacionais sem réplicas HDFS de storage).   • Usamos EMR (EC2 ou EKS) quando: O volume é brutal (PetaBytes), precisamos de latências mínimas (Streaming 24/7), ou necessitamos baixar drasticamente o custo usando EC2 Spot Instances e processadores Graviton (ARM). O EMR permite customizar completamente o ecossistema (Hive, Presto, Flink, Spark) e bibliotecas de baixo nível do SO. Contras: Alto overhead. O time precisa orquestrar steps, gerenciar Bootstrap actions e monitorar a saúde do cluster.
  • Meio termo (EMR Serverless): Para workloads do Spark/Hive que querem a velocidade de submissão do EMR com instâncias customizadas, mas sem gerenciar instâncias master/core/task.
Questão de Especialista 3 · EMR Setup

Como funciona a arquitetura de nós (Master, Core, Task) no Amazon EMR e como você configuraria um cluster altamente otimizado para custos usando Instance Fleets?

A Arquitetura Interna: Um cluster EMR tradicional no EC2 é composto por três tipos de nós:

  • Master Node: Roda o YARN ResourceManager e o HDFS NameNode. É o cérebro. Se ele cair, o cluster morre. Best Practice: Instância On-Demand com Multi-Master para HA (Alta Disponibilidade).
  • Core Nodes: Rodam o YARN NodeManager (para processar tasks do Spark) E armazenam os dados do HDFS DataNode. Best Practice: Instâncias On-Demand. Se um core spot for desligado, o HDFS perde blocos, causando lentidão para replicar o dado.
  • Task Nodes: Rodam APENAS o processamento (YARN NodeManager). Não armazenam HDFS. Best Practice: 100% Spot Instances. Se caírem, o YARN apenas refaz o processamento em outro nó sem perda de dados permanentes.
Configuração Avançada (Instance Fleets):

Para maximizar a economia no Task Node, usamos Instance Fleets em vez de Instance Groups. No Fleet, eu configuro 5 tipos diferentes de famílias de EC2 (ex: m5.2xlarge, m5a.2xlarge, r5.2xlarge) e peço "Capacidade Alvo". O EMR busca automaticamente no mercado de Spot da AWS qual dessas instâncias está mais barata e com menor risco de interrupção naquele exato segundo, criando um cluster de "frankenstein" ultra barato (até 80% de desconto) e altamente resiliente à perda de Spot em massa de uma única AZ ou família.

Questão de Especialista 5 · Tuning PySpark Avançado

Como você realiza o "Tunning" de uma pipeline de dados em Spark lidando com Skewness extremo (um cliente gigante causa gargalo em 1 partição) e uso de Joins?

A Sintomatologia do Skewness: O Job do Spark tem 200 partições. 199 terminam rapidamente e 1 partição fica travada calculando. Isso acontece porque a chave do Join/GroupBy não é uniformemente distribuída (ex: `id_empresa = Matriz_Gigante` gera 5 bilhões de registros, outras 10 mil empresas geram 100 registros cada).

A Estratégia de Guerra (Tuning Toolkit):
  • Ataque 1: Broadcast Hash Join. Se eu estiver cruzando essa tabela distorcida com uma tabela pequena de clientes, eu evito completamente o shuffle (onde o erro ocorre) envelopando a pequena no `broadcast(df)`. O Spark cria tabelas hash na memória de todos os nós.
  • Ataque 2: Salting (A cartada final). Se ambas as tabelas forem gigantes e o Broadcast for impossível (OOM), o shuffle (Sort-Merge) vai engasgar naquela chave monstruosa.

    Como fazer o Salting: Adicionamos um número aleatório (de 0 a N, como um "sal") ao final da chave na tabela distorcida (`id_empresa_salt = Matriz_Gigante_5`). Na tabela secundária, explodimos cada registro N vezes com os respectivos sais. Agora o Spark fará o JOIN distribuído perfeitamente através de N executores separados, quebrando o gargalo!
  • Ataque 3: AQE (Adaptive Query Execution). Garanto que `spark.sql.adaptive.enabled = true` e `spark.sql.adaptive.skewJoin.enabled = true`. No Spark 3, ele tenta resolver dinamicamente o skew particionando a chave pesada em múltiplas tasks durante a execução (runtime optimization).

Questão de Especialista 7 · Streaming & State Store

Um job de Spark Structured Streaming processando eventos do Kinesis roda estável por 3 dias, mas então a memória dos executores começa a inchar e resulta em falha cataclísmica (OOM). Qual é a provável causa raiz e a solução arquitetural?

A Pegadinha: Jobs de streaming puros não estouram RAM do nada a menos que haja acúmulo de estado contínuo.

A Causa e Resolução:
  • O Problema: O desenvolvedor aplicou uma agregação contínua (Stateful Processing) baseada em janela temporal (ex: contagem de cliques por minuto), mas não configurou um Watermark restrito. O Spark foi obrigado a manter as janelas de segunda-feira, terça-feira e quarta-feira inteiras abertas na memória (State Store) aguardando infinitamente por dados atrasados (Late Data). Após 3 dias, o acúmulo destruiu a RAM (Heap JVM).
  • A Resolução: Inserir a diretiva .withWatermark("timestamp_coluna", "15 minutes") antes do groupBy. Isso diz à engine: "Feche a janela e ejete os dados da memória após 15 minutos do evento mais recente. Se um evento chegar com atraso maior que 15 minutos, jogue fora". A memória estabilizará em um patamar constante e previsível.
Questão de Especialista 8 · Streaming Backpressure

Durante a Black Friday, a vazão de mensagens no seu tópico Kafka salta de 1.000 msg/s para 500.000 msg/s em um minuto. Seu pipeline Spark Streaming tenta consumir e cai imediatamente por falta de recursos. Como blindar o pipeline sem precisar alocar um cluster milionário?

Sintoma de Falha: Por padrão, o Spark tenta engolir todas as mensagens disponíveis no Kafka em cada micro-batch. Num pico de 100x, o batch fica infinitamente pesado.

Contenção de Danos (Throttling):

Você não mexe na arquitetura de rede, você mexe na porta de entrada do Spark configurando o limite rígido de offsets por gatilho: .option("maxOffsetsPerTrigger", "100000"). Ao invés do Spark tentar ler 5 milhões de mensagens de uma vez e morrer (OOM), ele lerá de 100 em 100 mil. Os micro-batches demorarão o tempo normal. A latência geral (lag) do tópico Kafka vai subir durante a madrugada, mas o pipeline continuará vivo e estável processando incansavelmente, e zerará o lag naturalmente quando a febre da Black Friday passar pela manhã.

  t.id_transacao,
  t.valor,
  c.nome_cliente

Questão de Especialista 14 · Live Coding (SQL Avançado: Gaps & Islands)

Entrevista: "Temos uma tabela simples de logings com `user_id` e `data_login` (dia exato). Como você escreve uma query SQL que mostre as datas de início e fim dos períodos em que um usuário fez login ininterruptamente todos os dias (as 'ilhas' de atividade), agrupando os dias seguidos?"

A Lógica do Problema (Gaps and Islands): Um clássico atemporal para separar os especialistas de SQL do resto. Não existe função nativa `GROUP_CONTINUOUSLY`.

WITH rank_dates AS (
  SELECT 
    user_id,
    data_login,
    -- DICA SÊNIOR: A mágica matemática.
    -- Se eu subtrair o Número da Linha (1, 2, 3) da Data do Login (Dia 1, Dia 2, Dia 3), 
    -- o resultado (data base) permanece EXATAMENTE O MESMO para dias consecutivos!
    DATE_SUB('day', ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY data_login), data_login) as grp_ilha
  FROM log_acessos
)
SELECT 
  user_id,
  MIN(data_login) as inicio_sequencia_ininterrupta,
  MAX(data_login) as fim_sequencia_ininterrupta,
  COUNT(data_login) as total_dias_consecutivos
FROM rank_dates
GROUP BY user_id, grp_ilha
ORDER BY user_id, inicio_sequencia_ininterrupta;
A Mágica da Matemática (Ilhas Constantes):

O truque repousa na constância. Considere os logins: 10/Jan, 11/Jan, 12/Jan. O ROW_NUMBER() gera: 1, 2, 3.
10/Jan menos 1 dia = 09/Jan.
11/Jan menos 2 dias = 09/Jan.
12/Jan menos 3 dias = 09/Jan.
Todos os dias consecutivos geram a MESMA DATA MATRIZ (09/Jan). Usamos essa data invisível como âncora do nosso GROUP BY. Brilhante e resolve em uma varredura paralela.

Questão de Especialista 15 · Avaliação de Código (PySpark UDF Internals)

Entrevista: O que acontece fisicamente na arquitetura cliente-servidor do Apache Spark ao longo do tempo quando um desenvolvedor aplica uma função customizada em Python (UDF tradicional) numa tabela de bilhões de linhas?

from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

@udf(StringType())
def mascara_telefone(tel):
    return tel[:4] + "****" + tel[-2:]

df_result = df.withColumn("tel_secreto", mascara_telefone(df["telefone"]))
A Anatomia do Desastre da Serialização (Socket Pickle):
  • O Abismo da JVM x CPython: O Spark roda nativamente em uma JVM (Java/Scala) extremamente otimizada. A engine lê a UDF e entende que não possui binários C++/Java para rodar esse código do usuário. Ela precisa abrir processos de retaguarda (Worker Daemons) em Python (CPython) no sistema operacional de cada nó executor.

  • A Resolução Esperada pelo Especialista: Nunca utilize UDFs em Python se existir uma função equivalente na lib pyspark.sql.functions (Neste caso, F.regexp_replace nativo operaria 100x mais rápido usando o JIT e Tungsten na JVM). Caso a lógica seja incrivelmente customizada (Machine Learning, NumPy pesado), deve-se usar as Pandas UDFs, onde a JVM não usa o horrendo Pickle por socket, mas transfere blocos colunares inteiros na memória compartilhada usando o protocolo Apache Arrow.
Questão (DEA-C01) · Redshift Maintenance & Migrations

Após a exclusão e atualização (UPDATE/DELETE) de milhões de linhas em uma tabela pesada do Amazon Redshift, as queries analíticas ficaram repentinamente muito lentas. Por que isso ocorreu e qual o comando de resgate?

Cenário de Prova: O ciclo de vida dos blocos imutáveis do Redshift e a operação técnica para restabelecer performance.

A Solução:

  • A Causa: O Redshift não exclui fisicamente o dado do disco no momento de um `DELETE` ou `UPDATE`. Ele cria registros fantasmas ("tombstones"). Como resultado, os blocos do disco fragmentam e o otimizador lê os blocos ocultos, causando I/O inútil e quebrando as estatísticas.
  • A Cura: O comando supremo na prova para isso é executar VACUUM DELETE ONLY (recupera o espaço em disco) seguido de um ANALYZE para atualizar as estatísticas do planejador de queries. Nota: Na prova atual, o Auto-Vacuum do Redshift existe, mas em cargas super massivas, o Vacuum manual é exigido nas questões.

Ao realizar milhares de UPSERTs por minuto no Amazon S3 via Apache Spark, as operações Copy-on-Write do Apache Iceberg causam enorme Write Amplification (lentes e caros). Como a alteração física para Merge-on-Read resolve a ingestão, mas impacta os consumidores, e como automatizar a consolidação?

▶

O Copy-on-Write (CoW) é o padrão do Iceberg. Para atualizar 1 linha num Parquet de 1 GB, o Spark lê o arquivo, altera a linha em memória, e escreve um NOVO arquivo de 1 GB. Sob frequentes UPSERTS (CDC via Hudi/Iceberg), o tempo de processamento dispara, gerando OOMs e contas astronômicas de EMR Serverless/Glue.

O Modo Merge-on-Read (MoR):

Ao ativar `write.update.mode = merge-on-read`, o Iceberg deixa de reescrever arquivos grandes. Em vez disso, ele cria arquivos minúsculos de "Positional Deletes" indicando quais linhas dos arquivos originais não valem mais, e grava os dados novos em pequenos "Data Files" separados. A gravação passa a ser ultrarrápida, escalando a ingestão de Streaming quase à perfeição.

O Trade-off e Compaction: O problema do MoR é que o trabalho não sumiu, foi repassado para o Leitor. Quando o Amazon Athena ou Redshift Spectrum tentarem ler a tabela, terão que baixar milhares de arquivos base, baixar milhares de "delete files", e reconciliar tudo em memória (Merge On Read), deixando as consultas analíticas inaceitavelmente lentas. A solução obrigatória é provisionar rotinas diárias assíncronas no EMR/Glue rodando `CALL catalog.system.rewrite_data_files` (Compaction) e `rewrite_position_delete_files` para re-consolidar esses deltas em arquivos base limpos (Major Compaction).

Questão Essencial · Fundamentos

O que é ACID em banco de dados e como isso se traduz nos Data Lakes modernos (Iceberg, Delta)?

Conceito Tradicional: ACID significa Atomicidade (Tudo ou Nada), Consistência (regras validadas), Isolamento (Transações simultâneas não se corrompem) e Durabilidade (Uma vez comitado, o dado sobrevive a falhas de energia). Bancos relacionais (OLTP) garantem isso nativamente.

O Impacto em Big Data (Lakehouse):

Durante uma década, o Hadoop (HDFS/S3) não possuía ACID. Se um job Spark caísse no meio, arquivos parciais ficavam na pasta (leitura suja). Projetos como Apache Iceberg e Delta Lake introduziram metadados transacionais no Lake. Ao escrever no S3, o arquivo de dados fica invisível para os consumidores até que o "commit" atômico aconteça no arquivo de metadados, garantindo Isolamento e Atomicidade para o Data Lake, permitindo UPSERTS concorrentes.

Questão Essencial · Sistemas Distribuídos

O que é o Teorema CAP e como ele guia a escolha entre DynamoDB e bancos relacionais sob stress?

A Regra Inquebrável: O Teorema CAP diz que em um sistema distribuído de rede, você só pode escolher 2 de 3 propriedades: Consistência (todos os nós vêm o mesmo dado na mesma hora), Disponibilidade (o sistema sempre responde) e Tolerância a Partição (o sistema sobrevive se a rede entre os nós cair).

Na Prática (AWS):
  • Amazon RDS (Aurora/PostgreSQL): Escolhe CP (Consistência e Tolerância a Partição) ou CA. Se a rede interna quebrar, o master trava a gravação para não corromper a consistência, ou seja, sacrifica a disponibilidade (indisponível).
  • DynamoDB (Configuração Padrão): Escolhe AP (Availability + Partition Tolerance). Ele garante que o banco não sai do ar, mesmo que tenha que servir um dado milissegundos atrasado (Eventual Consistency), garantindo altíssima disponibilidade sob falhas.
Questão Essencial · Modelagem Física

Qual a diferença física no armazenamento entre bancos OLTP e OLAP, e por que não devemos rodar relatórios de BI no RDS?

OLTP (Online Transaction Processing - Ex: RDS Postgres): Otimizado para milhares de inserts/updates rápidos. O armazenamento é Row-Oriented (orientado a linha). Para ler apenas o valor de vendas de 1 milhão de clientes, o disco tem que carregar o registro inteiro do cliente junto (nome, endereço, telefone), o que causa um overhead catastrófico de I/O em consultas de BI.

OLAP (Online Analytical Processing - Ex: Redshift): Otimizado para Data Warehouses. O armazenamento é Columnar (orientado a coluna). Os dados de uma mesma coluna ficam juntos no disco. Se o analista fizer SUM(vendas), o motor lê APENAS a pequena coluna de vendas, ignorando o resto. É por isso que queries de BI no OLAP são absurdamente mais rápidas.

Questão Avançada · Evolução Arquitetural

Diferença conceitual entre Data Warehouse, Data Lake e Data Lakehouse?

  • Data Warehouse (ex: Teradata, Redshift Clássico): Dados rigidamente estruturados, alto custo de armazenamento e Lock-in de fornecedor (você não consegue ler os arquivos do Teradata com outra ferramenta que não o Teradata). Compute e Storage eram acoplados.
  • Data Lake (ex: Amazon S3 bruto): Repositório central de dados brutos. Armazenamento baratíssimo e infinito. Porém, sem governança ACID, sem comandos UPDATE/DELETE, forçando a reescrita de partições inteiras. Freqüentemente viravam "pântanos de dados" (Data Swamps).
  • Data Lakehouse (ex: Amazon EMR + Iceberg, Databricks): O melhor dos dois mundos. Storage barato no S3 em formatos abertos (Parquet), mas com uma camada de metadados transacionais (Iceberg) acoplada. Entrega ACID, Time Travel e comandos SQL ANSI puros diretamente no S3.
Questão Avançada · Arquitetura Macro

Quais são as características mandatórias de uma Plataforma de Dados Moderna na Nuvem?

  1. Desacoplamento de Storage e Compute: O S3 (Storage) cresce independente do EMR/Spark (Compute). Nunca pagar pelo servidor quando ele não está processando.
  2. Formatos Abertos (Open Formats): Usar Iceberg e Parquet. Isso evita Lock-in. Você pode ler o mesmo arquivo com Spark, Athena, Redshift e Snowflake.
  3. DataOps & CI/CD: Toda infraestrutura via Terraform (IaC) e transformações de regras de negócio via dbt com controle de versão git. Nada é feito manualmente na console.
  4. Governança de Grão Fino: Uso de AWS Lake Formation garantindo acesso a nível de linha e coluna, blindando a empresa contra LGPD (PII Data).
  5. Observabilidade Pró-ativa: Integração de logs, métricas e lineage de forma centralizada (Datadog/CloudWatch), alertando erros antes do usuário.

Questão de Especialista · Tuning AWS Glue

Se um script PySpark já está bem escrito e sem shuffles desnecessários, quais configurações físicas e de infraestrutura do AWS Glue você alteraria para turbinar a performance?

Além de aumentar o tipo do trabalhador (Worker Type) de G.1X para G.2X para mitigar OOM, o arquiteto experiente otimiza a camada de leitura na nuvem (I/O Bound):

  • Job Bookmarks: Se ativado, o Glue rastreia por trás dos panos (via S3 metadados) quais arquivos ele processou ontem. Ao ligar isso, o job vira "incremental-leitura" e só baixa do S3 os novos arquivos, reduzindo o tempo do job de 4 horas para 10 minutos.
  • Ativar o `groupFiles` (Combate a Small Files): Se o bucket S3 estiver lotado de 50.000 arquivos minúsculos (10 KB), o Spark criará 50.000 partições e vai travar a rede (I/O Overhead). Ao configurar `groupFiles: inPartition` e `groupSize: 134217728` (128 MB), o Glue agrupa vários arquivos pequenos em uma única task/memória do executor, processando-os como um grande bloco.
  • Pushdown Predicates: Ao ler do Data Catalog, usar `push_down_predicate = "year = '2024' and month = '10'"`. Isso evita que o Spark baixe o S3 inteiro de 2023 para depois filtrar, jogando o filtro diretamente para o momento da listagem do bucket S3.
Questão de Especialista · Amazon EMR Setup & Troubleshooting

Como você configura os nós do cluster EMR para máxima eficiência de custos e como realiza o Troubleshooting quando ele está lento?

Configuração (Instance Fleets): Um cluster EMR tradicional requer o balanceamento inteligente de nós:

  • Master Node: Gerencia o YARN e HDFS NameNode. Sempre On-Demand (nunca Spot) para não matar o cluster.
  • Core Nodes: Armazenam os dados físicos do HDFS local. Mistura de On-Demand (Garantido) e Reservado.
  • Task Nodes: Não possuem HDFS (stateless). Dedicados apenas a CPU/RAM do Spark. Aqui usamos 100% EC2 Spot Instances. Se a AWS retirar as máquinas no meio da madrugada, não há perda de dados gravados (pois o HDFS não está lá) e o Spark simplesmente recalcula as partições perdidas, garantindo economia de até 80%.

Troubleshooting (YARN & Ganglia):

Se o Job no EMR estiver arrastando, o painel do Glue não serve. O especialista acessa a interface web do YARN Resource Manager para checar o estado da fila de executores (pending vs running) e identificar gargalos de vCores alocados. Usa o Ganglia (ou CloudWatch OS metrics) para avaliar o "Disk Wait I/O". Se os discos estiverem em gargalo constante no Shuffle, o arquiteto troca o hardware do Core Node de `m5` (EBS) para instâncias `i3` ou `i4` que contam com discos locais ultra-rápidos NVMe SSD.

Questão Especialista · Datadog & Observabilidade Proativa

O que é "Observabilidade Proativa", quais métricas chaves um pipeline envia ao Datadog, e quais ajudam mais no Debugging?

Conceito: Observabilidade Reativa é quando a área de negócios te avisa que o dashboard quebrou. Observabilidade Proativa é plugar a telemetria do EMR, MSK e Glue no Datadog e criar Monitores preditivos baseados em anomalias (Machine Learning). O alerta dispara quando o volume ingerido (Bytes) despenca sutilmente, gerando tickets do Jira antes dos SLAs serem quebrados na ponta.

Integração & Fluxo AWS -> Datadog:

Geralmente as métricas de infraestrutura (CPU, Memória, Iteradores) e logs de erro (OOM, Exceptions) no CloudWatch são drenadas usando um Kinesis Data Firehose (ou a Datadog Forwarder Lambda) que envia tudo em streaming via API para o Datadog. Métricas customizadas do Spark (Duração, GC) são enviadas via StatsD diretamente do executor.

Métricas Vitais de Debugging:

  • Kinesis IteratorAge (Métrica Ouro de Streaming): Mede o atraso temporal do pipeline de leitura. Se subir exponencialmente, o Spark/Lambda não está dando conta da vazão.
  • Dead Letter Queue Depth (DLQ): Mostra a quantidade de "registros venenosos" que quebraram o parsing. Alertas no DLQ previnem que perda de dados passe despercebida por meses.
  • JVM Heap Memory e GC Time (Spark): Se a linha de "Garbage Collection Time" atingir 95% e a de "Heap Free" zerar, sabemos antecipadamente que um `OOMKilled` vai ocorrer na próxima hora por causa de Skewness (Dados desbalanceados).

▶

1. Isolamento Físico e Networking (VPC Endpoints):
A borda amarela pontilhada indica que todos os workers do EMR estão implantados em sub-redes totalmente Privadas, sem Internet Gateway (IGW). Eles não têm acesso físico à internet. Para ler do S3, o EMR não sai pelo backbone público da internet, ele roteia o tráfego internamente através do VPC Endpoint (Gateway) para S3. Além disso, todos os dados em repouso no S3 e RDS estão cifrados criptograficamente utilizando o KMS com Customer Managed Keys (CMK). Hackers externos não possuem rotas de TCP/IP alcançáveis até o cluster.

2. O Paradoxo da Governança Multi-tenant (Lake Formation):
Antigamente, duplicaríamos fisicamente os dados (uma cópia para o BR, uma para o MX) ou gerenciaríamos centenas de IAM Policies ilegíveis. Nesta arquitetura "Data Mesh", os dados da tabela S3 Gold são únicos. A segurança é feita logicamente no nível de Compute/Catálogo usando o AWS Lake Formation. Criamos um "Data Filter" (Cell-level security) que diz: "Se a sessão assumiu a Role IAM ConsumerMX, a coluna 'CPF' retorna NULL e as linhas onde 'country' = 'BR' são suprimidas na query". O Athena respeita essa engine automaticamente antes do dado chegar ao usuário.

3. Cultura FinOps e Chargeback:
FinOps em Data Mesh exige Chargeback (cobrança interdepartamental). Os domínios não podem usar o Athena de forma anônima. A plataforma estabelece uma regra IAM mandatória (Attribute-Based Access Control - ABAC) forçando que todos os Workgroups do Athena e todos os clusters Redshift tenham Cost Allocation Tags mandatórias na sua criação (ex: Team=Marketing, Domain=Analytics). System Design Interview (Whiteboard) · Banking & CQRS

O banco quer tirar a carga de leitura do Mainframe transacional e expor uma API de saldo rápido no app celular, e ao mesmo tempo popular o Data Lake. Avalie a topologia abaixo:

Quadro Branco: Mainframe Offloading
Contexto Visual:
  • Componentes Chaves: DMS (CDC), MSK, Flink, DynamoDB, S3 Iceberg, API Gateway
  • Foco: O candidato precisa compreender o padrão CQRS (Command Query Responsibility Segregation). A gravação transacional continua no DB2, mas todas as leituras do App Mobile são despachadas para a réplica (DynamoDB).
Perguntas da Banca (Entrevistadores):
  1. "Nós roteamos os eventos do CDC via Kafka para o Flink. Por que o Flink escreve no DynamoDB e no S3 simultaneamente, em vez de conectarmos o S3 e o App diretamente no Kafka?"
  2. "Se o link entre o Mainframe e o CDC (DMS) cair por 2 horas durante a Black Friday, a API continuará funcionando? Como o banco garante que o cliente não sacou dinheiro além do saldo se a API está desatualizada?"

Ver a Resposta (Gabarito Staff Engineer)

▶

1. CQRS e Separação de Responsabilidade (Command vs Query):
O Kafka é excelente para reter logs sequenciais, mas é péssimo para buscas pontuais (Lookup por chave primária, ex: WHERE id_cliente = 123). O App Mobile precisa de latências de leitura de 10ms. Simultaneamente, o Flink anexa o histórico contábil no S3 (Iceberg) para análises lentas de BI no final do dia.

2. Eventual Consistency e Compensação Transacional:
Sim, a API (leitura) continuará com 100% de uptime (Disponibilidade alta - Teorema CAP), mas retornará saldos desatualizados (Stale Data) se o CDC cair. Para impedir saques fraudulentos por inconsistência, o fluxo de Command (Saque/Transferência) jamais bate nessa API. Transações de saque vão diretamente para o Mainframe (Sistema de Origem) usar Locks transacionais (ACID). A API serve estritamente para visualização de saldo provisório. Quando o CDC religar, o Kafka consome o backlog das 2 horas e o Flink reconstrói o estado final do DynamoDB sem perder dados, garantindo Eventual Consistency.

System Design Interview (Whiteboard) · Prevenção a Fraude (Real-Time PIX)

Em transações financeiras críticas (PIX/Cartão), o SLA de aprovação sistêmica é de 200 milissegundos. Acima disso, a transação cai em Timeout. O diagrama abaixo propõe uma arquitetura sub-segundo na AWS.

Quadro Branco: Motor de Fraudes (Streaming ML)
Contexto Visual:
  • Componentes Chaves: API Gateway, Kinesis Data Streams, Amazon Flink, SageMaker Endpoint, Kinesis Firehose
  • Foco: O candidato avalia uma pipeline reativa (Reactive Streaming). O evento entra via API, buferizado no Kinesis e analisado pelo Flink, que dispara uma inferência (ML) contra o SageMaker para decidir Block/Allow em frações de segundos.
Perguntas da Banca (Entrevistadores):
  1. "No horário comercial, recebemos 10.000 PIX/segundo. O SageMaker Endpoint (Inferência) começou a gargalar e a latência da API de fraude subiu de 50ms para 500ms. O que acontece com o Flink e com o Kinesis nesse cenário?"
  2. "Se uma Availability Zone da AWS cair, as instâncias rodando o Flink morrem. O Kinesis guarda os eventos, mas como o Flink, ao reiniciar em outra zona, lembra do estado complexo de fraude (ex: 'este cliente transferiu $5.000 nos últimos 30 segundos') sem perder nada?"

Ver a Resposta (Gabarito Staff Engineer)

▶

1. Backpressure de Rede:
Se o consumidor final (SageMaker) ficar lento, o Flink não pode receber dados infinitamente na sua memória RAM, senão causa um `OutOfMemoryError`. Nesse caso, ocorre um fenômeno chamado Backpressure (Pressão de retorno). O Flink desacelera intencionalmente a ingestão, parando de "puxar" os registros do Kinesis Data Streams. Como o Kinesis atua como um Buffer durável (retém logs por até 365 dias), os eventos começam a acumular na fila (métrica `IteratorAge` dispara). A solução arquitetural é escalar as instâncias do SageMaker Endpoint (Auto Scaling) e aumentar o paralelismo do Flink via aumento da métrica de Kinesis Processing Units (KPUs).

2. Checkpointing Distribuído (RocksDB):
O Flink é State-Aware. Para não perder o contexto da janela de 30 segundos, ele armazena o "estado" das chaves no disco local usando um banco embarcado chamado RocksDB. Constantemente, o Flink executa o algoritmo de Chandy-Lamport para tirar Snapshots Assíncronos desse RocksDB e enviá-los de forma durável e atômica para um bucket interno do S3 (Checkpointing). Se a Zona cair, o novo contêiner do Flink sobre na AZ-B, faz o download do último checkpoint salvo no S3, reconstrói o estado exato da memória na fração de segundo antes da queda, e avança a leitura no Kinesis.

Ver a Resposta (Gabarito Staff Engineer)

▶

1. Padrão Arquitetural Assíncrono (Token Polling / Webhook):
Por hard-limit do serviço na AWS, conexões síncronas HTTP no API Gateway possuem um Timeout máximo inquebrável de 29 segundos. Não importa se a Lambda demora 5 minutos, a conexão cai. O redesenho arquitetural clássico exige o desacoplamento assíncrono: A UI do React faz um POST no endpoint. A Lambda orquestradora chama a API `StartQueryExecution` do Athena, que não bloqueia o código e responde imediatamente com um ID (ex: ExecutionId: 8a4c2). A API responde para o React com o HTTP `202 Accepted` e o Token. O Frontend passa então a bater num segundo endpoint `GET /status/{token}` (Polling) de segundo em segundo até que a Lambda leia o estado `SUCCEEDED` do Athena, devolvendo o link S3 seguro do arquivo CSV gerado.

2. Segurança Multi-Account (AssumeRole):
A Lambda nunca guarda Access Keys / Secret Keys chumbadas no código para contas externas (isso é uma grave falha de segurança SecOps). A AWS utiliza o conceito de STS (Security Token Service). A conta B (Destino) cria uma "IAM Role de Confiança" afirmando que a Lambda da conta A tem autorização de assumi-la. O código Python da Lambda (boto3) executa sts.assume_role(RoleArn='arn:aws:iam::ContaB:role/DataMeshRole'), pega credenciais temporárias válidas por apenas 1 hora, e então instância o cliente do Athena embutindo esses tokens. Após a execução, o acesso expira, mitigando vazamentos e garantindo a segmentação entre domínios (Mesh Domains).

Isso previne que dados sujos ou arquivos corrompidos invadam a camada Silver do Data Lake.

System Design Interview (Whiteboard) · Fan-Out & Desacoplamento

Quando o processamento pesado de Faturamento central termina, dezenas de outros departamentos (Marketing, Fraude, Contabilidade) precisam agir. Avalie a topologia assíncrona Fan-Out Pub/Sub:

Quadro Branco: Fan-Out Architecture (SNS/SQS)
Contexto Visual:
  • Componentes Chaves: AWS Glue, Amazon SNS, Amazon SQS, AWS Lambda, Data Domains
  • Foco: Padrão Pub/Sub arquitetural onde um único evento (SNS Topic) faz o broadcast da notificação (Fan-out) para múltiplas filas isoladas (SQS), garantindo que cada domínio processe seu consumo no seu próprio ritmo.
Perguntas da Banca (Entrevistadores):
  1. "Por que utilizamos a combinação SNS + SQS em vez de fazer o Glue Job invocar diretamente as 3 Lambdas (`boto3.client('lambda').invoke()`) quando ele termina?"
  2. "O que acontece se a pipeline da Contabilidade estiver enfrentando uma indisponibilidade severa de banco de dados no momento em que o SNS dispara a mensagem?"

Ver a Resposta (Gabarito Staff Engineer)

▶

1. Desacoplamento Absoluto (Anti-Spaghetti):
Fazer o Glue Job invocar os consumidores diretamente cria um acoplamento forte. Se amanhã a empresa criar um 4º departamento (ex: Risco), o time de engenharia central terá que alterar e re-implantar o script do Glue Job de Faturamento. Com o padrão Pub/Sub Fan-Out, o Glue atua como Produtor Agnóstico: ele apenas avisa o SNS ("Faturamento Feito") e desliga. Se o time de Risco quiser consumir amanhã, eles criam sua própria fila SQS e se inscrevem no tópico SNS sozinhos, mantendo os domínios 100% isolados (princípio do Data Mesh e Microserviços).

2. Resiliência por Buffer (Filas Isoladas):
A combinação SNS + SQS garante a resiliência por armazenamento. Quando o SNS faz o broadcast, ele copia a mensagem para as 3 filas SQS em paralelo. Se a Contabilidade estiver fora do ar, a mensagem deles ficará repousando duravelmente dentro do SQS da Contabilidade por até 14 dias (Buffer). Enquanto isso, Fraude e Marketing processam seus dados normalmente. Quando a equipe da Contabilidade resolver seu problema, a Lambda deles volta a funcionar e drena o SQS atrasado. A falha de um domínio não afeta o produtor nem os outros domínios.

System Design Interview (Whiteboard) · Resiliência & Observabilidade

Sistemas distribuídos falham de formas misteriosas. O processamento via Lambda é sensível a timeouts e arquivos malformados. Avalie a estratégia de resiliência (DLQ) e monitoramento:

Quadro Branco: Dead Letter Queue & Datadog
Contexto Visual:
  • Componentes Chaves: SQS, Lambda, SQS DLQ, CloudWatch, Kinesis Firehose, Datadog
  • Foco: Arquitetura de tolerância a falhas configurando Redrive Policies para capturar venenos (Poison Pills) na DLQ. Usa Datadog interligado ao CloudWatch via Firehose para emissão de Alertas preventivos (PagerDuty).
Perguntas da Banca (Entrevistadores):
  1. "O que é uma Dead Letter Queue (DLQ) e por que ela nos salva de loops infinitos (Poison Pills) quando conectada à fila principal?"
  2. "No Datadog, se você pudesse configurar um monitor (alerta) usando apenas uma métrica do SQS para saber se a fila está com gargalo e a ponto de quebrar um SLA, qual métrica você escolheria e por quê?"

Ver a Resposta (Gabarito Staff Engineer)

▶

1. Poison Pill e a Fila DLQ:
Uma Poison Pill (pílula envenenada) é um evento/mensagem corrompido que sempre causará erro na Lambda (ex: um JSON mal formatado faltando a vírgula). Sem a DLQ, a Lambda tenta ler a mensagem, falha, e a mensagem retorna para o SQS. Isso gera um loop infinito (retries incessantes) consumindo custos absurdos de AWS Lambda. A Dead Letter Queue (DLQ) funciona acoplada à fila primária através da política `maxReceiveCount` (ex: 3). Após a Lambda falhar 3 vezes na mesma mensagem, o SQS move automaticamente essa mensagem problemática para a DLQ, limpando a fila primária para o tráfego normal avançar. A engenharia então investiga os erros com calma isolados na DLQ.

2. A Métrica de Ouro do SQS (ApproximateAgeOfOldestMessage):
Engenheiros juniores olham para o volume (`NumberOfMessagesVisible`), o que é enganoso (100.000 mensagens podem ser processadas muito rápido). O Engenheiro Staff monitora a métrica `ApproximateAgeOfOldestMessage`. Se essa métrica ultrapassar, digamos, 20 minutos, significa que a mensagem mais velha na fila está esperando 20 minutos para ser lida. Isso prova categoricamente que os Consumidores (Lambdas/EC2) estão extremamente lentos, travados ou sub-dimensionados. O Datadog dispara um webhook para o PagerDuty para acordar a engenharia, pois o SLA corporativo será rompido em breve.

1. Iceberg Branching (Zero-Copy):
O Apache Iceberg abstrai o Data Lake introduzindo controle de snapshot transacional. Podemos executar ALTER TABLE tbl CREATE BRANCH audit. O Spark escreve os dados novos apenas na branch `audit`. O consumidor final no Athena continua apontando para a branch `main` e não enxerga a mutação em andamento. Quando o "Audit" finaliza via Great Expectations (DQ), chamamos a procedure fast_forward do Iceberg, que instantaneamente atualiza o ponteiro da `main` para os novos dados (Publish atômico).

2. Rollback e Garbage Collection (Orphan Files):
Se o teste de qualidade (Audit) acusar que os dados do Spark estão vazios ou corrompidos, simplesmente abandonamos a branch `audit` e não executamos o "Publish". O consumidor permanece protegido lendo os dados de D-1 (Snapshot anterior da main). Os arquivos físicos Parquet que o Spark escreveu ficarão "órfãos" no bucket S3. Eles serão removidos em background (assincronamente) quando a rotina de manutenção do Iceberg chamar a procedure remove_orphan_files, limpando o lixo físico do S3 sem impactar o banco de dados.

  • Foco: O grande dilema arquitetural de Data Lakes clássicos (arquivos imutáveis) vs Data Lakes Modernos (Iceberg/Hudi) que suportam deleção por nível de linha para conformidade regulatória.

  1. "Em um Data Lake tradicional (Hive/Parquet), deletar uma única linha (o CPF do cliente) que está dentro de um arquivo Parquet de 1GB exige reescrever o arquivo inteiro. Isso mata a performance. Como contornar esse problema físico na nuvem?"

Ver a Resposta (Gabarito Principal Engineer)

▶

1. Padrão Merge-on-Read (Iceberg Row-Level Delete):
Formatos abertos de tabelas transacionais (Apache Iceberg, Hudi, Delta) resolvem esse bloqueio físico de imutabilidade utilizando arquivos isolados de deleção (Delete Files). Ao executar um DELETE FROM user_table WHERE cpf = '123', o motor (Athena/Spark) NÃO reescreve o arquivo Parquet de 1GB (Copy-on-Write). Durante a próxima consulta (Leitura), o Iceberg faz um Merge-on-Read (MOR), ocultando aquela linha dinamicamente. Semanalmente, um job de compactação unifica fisicamente os dados e efetiva a destruição no disco.

Ele identifica automaticamente qualquer arquivo CSV ou Parquet escondido que contenha o PII vazado e envia alertas para a equipe de Segurança (SecOps) via EventBridge. Assim garantimos a totalidade do expurgo dos dados judiciais na organização inteira.
