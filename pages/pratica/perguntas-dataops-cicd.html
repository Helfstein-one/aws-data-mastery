Questão 7 · Apache Spark

Como a memória do executor JVM do Spark é subdividida internamente e como debugar erros de OOM no User Memory vs Execution Memory?

Física da Memória Spark: A memória total (Executor JVM Heap) é subdividida em três grandes blocos controlados pelas propriedades de configuração do Spark:

  • Spark Memory (60% por padrão, via spark.memory.fraction): Subdividido dinamicamente entre Execution Memory (usado para shuffles, joins e agregações) e Storage Memory (usado para caching/persistence e transmissão de variáveis de broadcast).
  • User Memory (40% restante): Reservado para estruturas de dados do próprio usuário em código PySpark (UDFs Python, metadados internos de partições do Spark).
  • Reserved Memory: 300 MB fixos do Spark para garantir a execução estável do motor interno.

Spark JVM Memory Model
Caso de Debug em Processo Seletivo:

Se você receber OOM no User Memory, a causa provável é o uso de Python UDFs pesados sem otimização ou tentativa de processar metadados gigantes no driver. Resolva migrando UDFs Python puras para funções nativas da API DataFrame do Spark (Spark SQL) que rodam nativamente na JVM (otimizadas pelo compilador Catalyst).

Questão 20 · Qualidade de Dados & Glue DQ

Como desenhar um mecanismo de "Circuit Breaker" de Qualidade de Dados na AWS usando o AWS Glue Data Quality e regras DQDL?

Data Quality como Proteção: Consumir dados errados ou corrompidos em relatórios e dashboards gera desconfiança nos negócios. A melhor estratégia é rodar regras de integridade diretamente nos estágios de ingestão e, caso as regras falhem, acionar um disjuntor (Circuit Breaker) que interrompe o fluxo de dados para as camadas finais e isola os dados ruins para investigação.

Uso do AWS Glue Data Quality (DQDL): A linguagem de definição de qualidade do Glue permite criar regras declarativas e de fácil leitura para avaliar seus Data Frames. Um exemplo de arquivo declarativo DQDL:

Rules = [
  RowCount between 1000 and 2000000,
  Completeness "user_id" = 1.0,
  Completeness "email" > 0.95,
  IsUnique "user_id",
  ColumnDataType "created_at" = "Timestamp",
  ColumnValues "status" in ["ATIVO", "INATIVO", "PENDENTE"]
]
Fluxo e Arquitetura do Circuit Breaker:
  1. O Job do AWS Glue ou PySpark lê os dados da camada Bronze e executa a verificação declarada na regra DQDL usando a biblioteca nativa do Glue.
  2. A avaliação retorna um score de sucesso (ex: 85% das regras passaram, mas a unicidade de user_id falhou).
  3. Se o score for menor que o limite aceitável do contrato de qualidade (ex: 100% para chaves primárias e completeness), o pipeline ativa o disjuntor:
    • Grava o lote corrompido em uma pasta isolada no S3 (s3://data-quarantine-bucket/bronze-failures/) para fins de depuração.
    • Gera uma falha explícita no Job do Glue (ou levanta uma exceção no código Python), impedindo que o pipeline envie os dados para a camada Silver.
    • Publica um evento no Amazon EventBridge, que engatilha uma notificação integrada para o time via Slack e ativa alertas no Datadog.
Questão 32 · dbt Core & dbt Cloud no AWS Glue

Como estruturar a integração do dbt com o AWS Glue (usando o dbt-glue adapter) para executar modelos analíticos sobre o motor PySpark, e quais as melhores práticas para gerenciar modelos incrementais em tabelas Apache Iceberg sem sofrer com OOM ou corrupção de snapshots?

Mecanismo dbt-glue: O dbt Core/Cloud utiliza o conector dbt-glue para compilar queries SQL escritas em Jinja e transformá-las em blocos de execução Spark SQL. O dbt se conecta ao AWS Glue através de Interactive Sessions (Sessões Interativas baseadas em Jupyter Notebook Kernel) ou submetendo tarefas transientes de Glue Jobs. O Glue interpreta as tabelas físicas mapeadas no AWS Glue Data Catalog.

Estratégias de Modelos Incrementais & Evolução de Schema no Iceberg:
  • Estratégias de Carga Incremental: Ao atualizar dados em tabelas Iceberg usando dbt incremental, utilize incremental_strategy='merge' em vez de append. A estratégia merge executa um UPSERT lógico no Iceberg baseado em chaves exclusivas. O Iceberg gerencia isso de forma nativa por meio de Merge-on-Read (MoR) (gravação rápida escrevendo arquivos de exclusão) ou Copy-on-Write (CoW) (reescrevendo os arquivos afetados no S3). Para tabelas de escrita massiva, prefira MoR para evitar lentidão no commit Spark.
  • Gestão de DDL Drift: Ative a propriedade do dbt on_schema_change='sync_all_columns'. Graças à flexibilidade de metadados do Apache Iceberg, adicionar ou remover colunas ocorre sem a necessidade de reescrever arquivos Parquet históricos no S3. O Iceberg apenas atualiza o esquema no JSON de metadados da tabela, sincronizando com o Glue Catalog de forma instantânea.
  • Prevenção de OOM no Driver: Evite carregar grandes volumes de dados de logs no driver dbt/Glue executando operações que envolvam collect (como dbt_utils.get_column_values). Limite as transações executando compactação de dados (OPTIMIZE) de forma desacoplada do fluxo de execução do dbt para evitar concorrência no metadados do Iceberg.
Questão 4 · Amazon Athena

Como resolver o erro "Metadata limit exceeded" ou queries Athena que falham por timeout antes de iniciar o scan dos dados?

Causa Física: Quando o Athena executa uma query em uma tabela particionada convencional (ex: particionada por ano/mes/dia/cliente), ele precisa fazer chamadas de API para o AWS Glue Data Catalog para listar os arquivos físicos correspondentes às partições solicitadas. Se a tabela tem milhões de partições, a fase de planejamento da query excede os limites de limite de API do Glue e gera timeout antes do processamento dos dados começar.

A Solução Suprema: Partition Projection

O Partition Projection armazena as regras de geração das partições diretamente como propriedades da tabela no Glue Catalog (ex: ano varia de 2020 a 2026). O Athena calcula em memória os caminhos físicos do S3 baseando-se nas datas passadas no filtro SQL, ignorando completamente as chamadas de API do catálogo e eliminando o timeout.

-- Exemplo de registro de tabela Athena com Partition Projection configurado
CREATE EXTERNAL TABLE sales_projected (
    id_venda string,
    valor double
) 
PARTITIONED BY (ano string, mes string)
LOCATION 's3://my-datalake/sales/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.ano.type' = 'integer',
    'projection.ano.range' = '2020,2026',
    'projection.mes.type' = 'integer',
    'projection.mes.digits' = '2',
    'projection.mes.range' = '1,12',
    'storage.location.template' = 's3://my-datalake/sales/ano=${ano}/mes=${mes}/'
);
Questão 30 · Amazon Redshift Serverless

Como funciona o mecanismo de auto-scaling de concorrência (Concurrency Scaling) do Amazon Redshift Serverless e como o uso inadequado do comando COPY a partir do S3 com arquivos mal-distribuídos pode anular o paralelismo dos slices de computação (Slices Skew)?

Concurrency Scaling no Redshift: O Redshift Serverless dimensiona dinamicamente a computação adicionando recursos adicionais de processamento (clusters transitórios) sob concorrência pesada de leitura. No entanto, na fase de gravação e ingestão via comando COPY, a concorrência e o paralelismo dependem estritamente da estrutura física dos arquivos a serem ingeridos do S3.

O gargalo de Slice Skew na ingestão COPY:
  • Ingestão Sem Divisão (Single File Gzip): Se dispararmos um COPY de um único arquivo compactado gigante de 100 GB em formato Gzip (dados_vendas.csv.gz), o Redshift será incapaz de dividir o arquivo e ler em paralelo. Apenas um único slice de computação no cluster trabalhará descompactando e gravando os registros, enquanto os demais slices ociosos aguardam, gerando lentidão extrema (slice skew).
  • Melhor Prática de Divisão (Split Files): Divida os arquivos de dados na origem no S3 em múltiplos fragmentos comprimidos de tamanhos uniformes e idênticos (ex: 20 arquivos de 5 GB em vez de 1 de 100 GB), com uma quantidade correspondente a um múltiplo do número de compute slices do seu cluster de destino. O comando COPY acionará todos os slices do cluster para carregar cada arquivo em paralelo de forma direta e instantânea.
Questão 63 · Amazon Aurora Replica Lag & Read Scaling

Como mitigar gargalos de performance e isolar o tráfego operacional (OLTP) de gravação durante extrações analíticas massivas no Amazon Aurora PostgreSQL?

Desafio de Concorrência: Consultas analíticas pesadas (Full Table Scans) concorrendo com gravações na instância primária (Writer) geram locks de páginas de banco de dados e saturação de I/O de disco.

Estratégia Arquitetural de Ingestão:
  • Leitura via Reader Endpoint com Autoscaling: Aponte o pipeline analítico (JDBC Spark) estritamente para o Reader Endpoint do Aurora. Configure o auto-scaling do cluster Aurora com base na utilização média de CPU dos nós leitores. À medida que o job analítico inicia, réplicas adicionais são ligadas dinamicamente e as conexões balanceadas em round-robin.
  • Minimização de Lag de Réplica: Devido à arquitetura de armazenamento compartilhado do Aurora (Aurora Storage Volume), as réplicas analíticas não processam gravações físicas de dados nos seus discos. No entanto, elas devem atualizar seus caches locais na memória RAM com os logs de transação da Writer. Monitore a métrica AuroraReplicaLag e garanta que queries pesadas não mantenham transações abertas por longos períodos, o que impediria a réplica de atualizar sua memória (gerando lag artificial).
Questão 67 · Apache Iceberg WAP (Write-Audit-Publish) Pattern

Como funciona o padrão arquitetural WAP (Write-Audit-Publish) no Apache Iceberg e como as branches lógicas da tabela previnem a ingestão de registros órfãos ou inválidos na camada final de Serving?

Gargalo Operacional: Em pipelines analíticos tradicionais (Hive/Parquet puro), se um erro de qualidade de dados ocorrer no final de uma transação batch de 10 milhões de registros, a tabela física já estará modificada, forçando reversões complexas (rollbacks em S3) ou poluindo relatórios ativos de BI.

Arquitetura e Fluxo do WAP:
  • Write (Escrever na Branch): O pipeline PySpark ou dbt grava as alterações apontando para uma branch lógica temporária da tabela Iceberg (ex: df.option("branch", "wap_temp").save(...)). Os dados físicos são salvos no S3, mas o snapshot principal (main branch) da tabela continua inalterado.
  • Audit (Auditar): Ferramentas de validação ativa ou queries SQL rodam contra a branch temporária buscando quebras de contratos de dados (valores negativos, nulos em PKs).
  • Publish (Publicar via Fast-Forward): Se os testes passarem, a engine executa uma chamada de sistema (ex: CALL system.cherry_pick_snapshot()) para avançar a referência da branch main para o snapshot validado. Caso contrário, a branch temporária é descartada, impedindo a exposição dos dados inválidos.
Questão 78 · Star Schema vs. Snowflake no Amazon Redshift

Ao projetar um Data Warehouse corporativo no Amazon Redshift, qual arquitetura de modelagem de dados é preferível entre Star Schema e Snowflake Schema, e qual o impacto dos Joins na execução distribuída do cluster?

Gargalo de Processamento Distribuído: O Amazon Redshift é um banco de dados Massivamente Paralelo (MPP). Em queries distribuídas, realizar joins exige que as fatias de dados de diferentes nós computacionais sejam redistribuídas pela rede (Data Shuffle) para que os registros correspondentes sejam pareados na memória física.

Estratégia Recomendada para o Redshift:
  • Preferência pelo Star Schema: O Star Schema é amplamente preferido em relação ao Snowflake no Redshift. Por possuir dimensões desnormalizadas e achatadas, as queries analíticas exigem apenas um nível de join (Fato ➔ Dimensão). Isso diminui drasticamente a necessidade de shuffles de rede complexos e agiliza a execução da query.
  • O Problema do Snowflake no Redshift: No Snowflake, a normalização fragmenta os dados em múltiplas tabelas (Fato ➔ Cliente ➔ Cidade ➔ Estado). Queries analíticas básicas exigem joins em cascata. O otimizador de plano do Redshift precisará mover dados de várias dimensões entre nós para resolver a query, gerando congestionamento na rede interna do cluster.
  • Otimização com Chaves de Distribuição: No Star Schema, configure a chave de distribuição (DISTKEY) da tabela Fato e da maior dimensão (ex: Cliente) com o mesmo campo ID. O Redshift executará o join localmente sem mover dados de nó em nó. Para as demais dimensões menores (como Tempo e Categoria), use DISTSTYLE ALL para clonar as tabelas em todos os nós, garantindo joins de latência zero.
Questão 82 · Padrão Write-Audit-Publish (WAP) com Apache Iceberg

Como o padrão Write-Audit-Publish, possibilitado por formatos de tabela como Apache Iceberg, evita que dados mal formatados poluam a camada Gold (apresentação) do Data Lake e interfiram nos dashboards?

O Problema da Gravação Suja: Historicamente, os jobs do Spark escrevem os dados diretamente na tabela final. Se o job falhar pela metade ou carregar dados nulos acidentalmente, os dashboards apontados para essa tabela apresentarão dados inconsistentes aos usuários de negócio antes que o time de dados perceba o problema.

O Pipeline Seguro (Branching Analítico):
  • Write (Escrever): O job de ETL do Spark não escreve diretamente na branch principal. Ele cria e escreve os dados em uma ramificação oculta de auditoria no Iceberg (ex: `branch_audit_etl`). Os dashboards do QuickSight ou Tableau conectados no Athena apontam para a branch `main` e continuam lendo os dados de ontem com performance normal.
  • Audit (Auditar): Um job secundário de Data Quality (ex: usando Great Expectations ou Glue Data Quality) é acionado para varrer apenas a `branch_audit_etl`, aplicando regras como limiares estatísticos (standard deviation) e limites nulos.
  • Publish (Publicar): Apenas se a auditoria passar com sucesso, uma operação (stored procedure) atômica do Iceberg `fast_forward` transfere e torna os dados dessa branch visíveis na branch `main`. Toda a transição leva milissegundos e elimina a janela de inconsistência de dados.
Questão 90 · Redshift Managed Storage (RA3) e Custos Operacionais

Qual o argumento financeiro e de governança para convencer um CTO a migrar Clusters Redshift on-premise style (DS2/DC2) para a família RA3 com Data Sharing, quando a empresa possui 5 squads diferentes consumindo e copiando dados uns dos outros?

Cenário: Equipes de Marketing, Risco, Finanças e Vendas rodam complexos pipelines (AWS Glue) toda madrugada apenas para copiar tabelas do "Cluster Core" para seus próprios "Clusters Departamentais", encarecendo a conta da AWS e gerando dessincronia (dados velhos).

A Solução (Storage Desacoplado):
  • Dissociação Paga Apenas o Necessário: Em DC2 (acoplado), escalar o disco para armazenar mais histórico obrigava a pagar por caríssimos chips de CPU adicionais ociosos. No RA3, os dados pesados moram fisicamente no S3 (preço ínfimo de centavos por GB), mantendo a CPU dimensionada apenas para a força da query.
  • Morte do ETL de Cópia via Data Sharing: Com o RA3, o Storage reside no S3. Isso permite habilitar o Data Sharing. O Cluster de Marketing pode ler a tabela de Vendas ao vivo, utilizando apenas o próprio poder computacional de Marketing, sem que o pipeline precise mover um único byte fisicamente, eliminando a fatura do AWS Glue e a obsolescência de dados.
Questão 96 · Redshift RA3, Data Sharing e Estrangulamento de Concorrência (Staff Level)

Sua empresa consolidou dezenas de Terabytes no Amazon Redshift (família RA3) adotando o "Managed Storage". Durante a madrugada, longos processos de ETL de Ingestão saturam os Compute Nodes. Ao mesmo tempo, o time de engenharia global e analistas tentam visualizar os dashboards no QuickSight. A infraestrutura inteira sofre lentidão severa. Como isolar perfeitamente a computação mantendo "Single Source of Truth"?

Cenário: Você deseja parar as filas de "Noisy Neighbors". A diretoria descarta mover os dados lidos para bancos relacionais e exige usar o Redshift DW.

Diagnóstico e Ação (Desacoplamento Arquitetural de CPU):
  • A Causa Física (Acoplamento de Concorrência Clássico): Embora o Redshift RA3 desacople o Storage (guardando dados frios no S3 RMS e caches no SSD local), as cargas de trabalho (ETLs e leituras Ad-Hoc) ainda competem violentamente pelo mesmo cluster Leader e pelos mesmos Slices do Compute Node. Mesmo com o AutoWLM ou Concurrency Scaling ativados, um volume massivo de Ingestões DML (INSERT/UPDATE/COPY) engasga o pipeline da fila, exigindo IOPS intensos no EBS local e travando a CPU que o QuickSight depende.

  • Aurora Global Database (Modelo PC/EC): Sob partições, pode parar escritas na região secundária para garantir consistência física exata (PC). Em estado normal, o Aurora usa replicação física otimizada em nível de storage de baixa latência mas síncrona/consistente para evitar conflitos de dados históricos (EC).

  1. YARN Decommissioning Timeout: Defina yarn.resourcemanager.decommissioning.timeout (ex: 300 segundos). Isso dá tempo para que o nó em processo de terminação transfira seus dados de shuffle local para nós persistentes (Core Nodes) antes de cair.
  2. Spark Decommissioning: Ative spark.decommission.enabled = true e spark.storage.decommission.enabled = true. O Spark proativamente migrará blocos de RDD armazenados em cache e arquivos de shuffle persistidos no disco local do executor sendo finalizado para outros executores ativos no cluster.
Questão 75 · Segurança Cross-Account em Data Lake: Bucket Policy + KMS Key Policy

Em um cenário Data Mesh, um job PySpark rodando na Conta Consumidora A precisa ler dados analíticos Parquet salvos no S3 na Conta Produtora B. Os dados estão encriptados via chave KMS CMK customizada na Conta B. Como devem interagir as políticas IAM da Role da Conta A, a Bucket Policy da Conta B e a Key Policy do KMS da Conta B para permitir o acesso de menor privilégio?

Desafio de Avaliação de Políticas Cross-Account: Em acessos na mesma conta, basta a Role ter permissão no IAM. Em acessos cross-account (contas diferentes), a AWS exige autorização explícita em ambos os lados: na política de identidade do chamador e nas políticas de recurso do proprietário do recurso (Bucket Policy e KMS Key Policy).

Arquitetura de Concessão Cross-Account:
  1. Permissões na Conta Consumidora A (Identity-Based): A Role de execução do Spark na Conta A deve receber permissões explícitas no IAM de leitura no S3 (s3:GetObject, s3:ListBucket) apontando para o ARN do bucket da Conta B, e descriptografia no KMS (kms:Decrypt) apontando para o ARN da chave KMS da Conta B.
  2. Bucket Policy na Conta Produtora B (Resource-Based): A Bucket Policy da Conta B deve autorizar explicitamente o ARN físico da Role da Conta A a listar e ler objetos: 
    {
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::ACCOUNT_A:role/data-processing-role" },
  "Action": ["s3:GetObject", "s3:ListBucket"],
  "Resource": ["arn:aws:s3:::bucket-conta-b", "arn:aws:s3:::bucket-conta-b/*"]
}
  3. KMS Key Policy na Conta Produtora B (Resource-Based): A política da chave KMS customizada na Conta B deve conter um statement autorizando o ARN da Role da Conta A a realizar a descriptografia (kms:Decrypt, kms:DescribeKey). Sem este passo, o Spark baixará os bytes do S3 mas falhará em decodificar o Parquet, gerando erro de I/O.
Questão 76 · Privilege Escalation e Permission Boundaries em Times de Dados

Para dar autonomia a engenheiros de dados em uma grande corporação, foi cedida a eles permissão de criar novas Roles de execução no IAM para Glue e Lambda. Como evitar que um engenheiro abuse dessa autonomia para criar uma Role com permissões administrativas completas (Administrador) e a assuma (Privilege Escalation)?

Risco de Quebra de Governança: Um usuário com permissão de criar Roles (iam:CreateRole) e anexar políticas (iam:AttachRolePolicy) pode anexar a política gerenciada AdministratorAccess a uma Role nova e depois usá-la em um Lambda para alterar a infraestrutura corporativa.

Solução IaC com Permission Boundary:
  • Fronteiras de Permissão do IAM: O administrador de segurança da AWS cria uma política limite chamada Permission Boundary (que descreve as ações máximas que qualquer recurso de dados pode rodar, ex: ler S3, gravar logs, ler Glue, sem acessos administrativos de rede ou billing).
  • Vinculação via Políticas IAM: Na política IAM dos engenheiros de dados, a permissão iam:CreateRole só é concedida sob a condição estrita de que a nova Role criada venha associada à Permission Boundary predefinida: 
    {
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:PutRolePermissionsBoundary"],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "iam:PermissionsBoundary": "arn:aws:iam::123456789012:policy/data-boundary"
    }
  }
}
  • Resultado Prático: Mesmo que o engenheiro crie uma Role e tente anexar AdministratorAccess a ela, o poder de execução efetivo daquela Role será restrito ao escopo declarado na Permission Boundary, mitigando a escalação de privilégios.
Questão 77 · Slowly Changing Dimensions (SCD) no Data Lake

Como gerenciar alterações cadastrais históricas em tabelas de dimensão (Slowly Changing Dimensions - SCD) utilizando ferramentas de processamento de dados na AWS, e quais os trade-offs entre Tipo 1, Tipo 2 e Tipo 4?

Conceito de SCD: Entidades descritivas (como dados cadastrais de clientes ou produtos) mudam de valor lentamente ao longo do tempo. Capturar e registrar essas mudanças de forma controlada é fundamental para manter a consistência e a rastreabilidade histórica em análises analíticas de faturamento e vendas.

Tipos de SCD e Implementação na AWS:
  • SCD Tipo 1 (Sobrescrita Direta): O novo valor cadastral substitui o antigo. Não há histórico.
    • Caso de Uso: Correção de erros ortográficos simples.
    • Implementação: No PySpark/Glue, execute uma query de UPDATE ou um merge direto de partição utilizando formatos transacionais (como Apache Iceberg/HUDI).
  • SCD Tipo 2 (Histórico por Versões com Linhas Adicionais): Uma nova linha é inserida para registrar a mudança, mantendo a linha antiga ativa sob indicadores temporais (colunas data_inicio, data_fim e flag registro_ativo).
    • Caso de Uso: Mudança de endereço de cliente para cálculo de tributação histórica de vendas.
    • Implementação: No Spark/Iceberg, utilize o comando MERGE INTO comparando a chave natural. Se houver diferença nos dados descritivos, expire o registro antigo setando registro_ativo = false, data_fim = timestamp_atual, e insira a nova linha ativa.
  • SCD Tipo 4 (Tabela de Histórico Separada / Outrigger): A dimensão principal mantém sempre apenas o valor atual ativo (estilo Tipo 1), mas cada modificação é gravada em uma tabela satélite separada de histórico (Log de Alterações).
    • Caso de Uso: Rastreabilidade de status de contratos muito dinâmicos sem inflar a tabela de dimensão principal.
    • Implementação: Insira o registro Tipo 1 na dimensão principal via Iceberg e, em paralelo, envie o evento de mudança bruto para um bucket S3 histórico usando Kinesis Data Firehose para compor a tabela histórica de auditoria de forma assíncrona.
Questão 79 · Chaves Substitutas (Surrogate Keys) vs. Chaves Naturais

O que são chaves substitutas (Surrogate Keys) e por que elas são fundamentais em modelagem dimensional de Data Warehouses em vez do uso direto de chaves naturais de negócio vindas dos bancos OLTP?

Conceito de Chave Substituta: Uma chave substituta (Surrogate Key) é um identificador numérico artificial e sequencial (ou um Hash MD5/SHA256 gerado deterministicamente) gerado no Data Warehouse para atuar como chave primária de uma tabela de dimensão. A chave natural é o identificador gerado pelo sistema transacional de origem (ex: id_usuario no banco OLTP ou CPF).

Vantagens Técnicas e Motivações:
  • Independência de Sistemas de Origem: Sistemas transacionais podem ser migrados, resetados ou substituídos. Se duas fontes diferentes usarem o mesmo ID de chave natural para entidades distintas, o Data Warehouse sofrerá colisão. A chave substituta isola o Data Warehouse e garante unicidade global.
  • Suporte a Histórico de Mudanças (SCD Tipo 2): Para registrar a alteração de endereço de um cliente mantendo o histórico, precisaremos de duas linhas na dimensão para a mesma chave natural (ex: duas linhas com CPF 123.456...). Como a chave primária da tabela de dimensão deve ser única, a chave natural não serve. A Surrogate Key diferencia as versões físicas do mesmo cliente (ex: SK `1004` e SK `2854` mapeando para o mesmo CPF).
  • Performance Física de Joins: Fazer joins entre chaves de texto longas (como chaves compostas de string ou UUIDs) é computacionalmente caro. Usar chaves substitutas inteiras (Integers ou BigInt) compactas acelera a comparação na memória do motor analítico (Redshift/Spark) e reduz o tamanho dos índices e das tabelas Fato.

Questão 84 · MLOps e SageMaker Feature Store

O que é "Training-Serving Skew" em Machine Learning e como o SageMaker Feature Store atua mitigando esse problema em vez de simplesmente salvar as agregações diretamente no S3 e no DynamoDB separadamente?

Dissonância Cognitiva do Modelo: O Training-Serving Skew ocorre quando o código Python em batch usado para preparar as variáveis (features) no treinamento usa dados sutilmente diferentes, ou processados com regras matemáticas divergentes da API em tempo real (ex: média de vendas calculada em pandas no notebook vs calculada no backend em Go).

Questão (DEA-C01) · Athena & Otimização S3

Uma query no Amazon Athena está demorando 15 minutos para fazer scan em uma tabela particionada no S3 que tem milhares de arquivos pequenos de 5 KB. Como otimizar o custo e o tempo de resposta?

Cenário de Prova: A prova DEA avalia constantemente o problema do Small Files e a capacidade de reduzir dados escaneados, pois o Athena cobra por TB escaneado ($5/TB).

A Solução Ouro:

  • Tamanho de Arquivo: Otimize (compacte) os arquivos para o target ideal de 128 MB a 256 MB. Arquivos de 5 KB geram overhead extremo de abertura de conexão HTTP/S3 por parte do motor Presto do Athena.
  • Formato Colunar: Converta dados JSON/CSV cruos para Apache Parquet ou ORC usando um Glue ETL Job. Isso permite que o Athena baixe apenas a coluna do SELECT e ignore as outras (economia de IO).
  • Particionamento: Use Partition Projection se for um fluxo de streaming de alta cardinalidade temporal, para evitar consultas constantes ao Glue Data Catalog.
