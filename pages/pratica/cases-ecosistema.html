Cases Ecosistema

Arquiteturas corporativas de ponta a ponta na AWS simulando fluxos de produção em alta escala, segurança regulatória e governança centralizada.

0

Mega Case 0: Plataforma Financeira Full-Stack & Data Mesh (Banco Digital)

A arquitetura definitiva de ponta a ponta: Microserviços, Mensageria, Lambda Architecture (Speed/Batch) e Governança Multi-Camada

Em um banco digital de alta volumetria, a arquitetura exige o isolamento perfeito de domínios transacionais e analíticos. O ecossistema roda dentro de uma VPC corporativa na região sa-east-1, orquestrando fluxos em três pilares principais:

Mega Case 0 — Plataforma Bancária (Lambda Architecture)
Detalhamento das Camadas (Layers):
  • Transacional: Requisições passam pelo API Gateway para os contêineres ECS (Fargate) e Lambdas. O estado é garantido em bancos ACID (RDS PostgreSQL) e bancos chave-valor de baixa latência (DynamoDB).
  • Mensageria & Eventos: Cada transação finalizada dispara um evento Pub/Sub via Amazon SNS, efetuando um Fan-Out para tópicos SQS de resiliência e para esteiras de dados.
  • Speed Layer (Tempo Real): Eventos urgentes vão para o Kinesis Data Streams e são analisados por janelas temporais usando Apache Flink para Detecção de Fraude Sub-segundo.
  • Batch Layer (Data Mesh): Paralelamente, o Kinesis Firehose ingere tudo cru no S3 (Raw Zone). Fluxos massivos de ETL orquestrados rodam no Amazon EMR Serverless (Spark) para modelagem Silver/Gold, protegidos e limpos ativamente via Glue Data Quality e Lake Formation (Security).
  • Observabilidade: O AWS X-Ray cruza as requisições, gerando um ID de rastreio único visualizável no CloudWatch.

Case 2: Plataforma Financeira Data Mesh & Governança com Lake Formation

Implementação orientada a domínios com compartilhamento central de metadados, controle fino de acesso e Data APIs protegidas por cache

Neste caso de uso de uma instituição bancária regulada, múltiplos domínios de negócios geram e gerenciam seus próprios dados. O domínio de Contas Correntes e o domínio de Investimentos precisam compartilhar dados para gerar relatórios unificados sem duplicar armazenamento e sob regras rígidas de compliance (ocultar saldo de investidores VIPs e mascarar CPFs).

Case 2 — Data Mesh: Plataforma Financeira Multi-Domínio
Explicação:
  • Componentes: CASE 2 — DATA MESH: PLATAFORMA FINANCEIRA MULTI-DOMÍNIO, DOMÍNIO PAGAMENTOS, Kinesis Stream, S3 Product Data Port, Glue ETL, DOMÍNIO CRÉDITO, Aurora Credit DB, Lambda Transform, DOMÍNIO RISCO, Redshift Risk DW, Glue Aggregate, MESH GOVERNANCE, Lake Formation Global Catalog, Glue Data Catalog, IAM Cross-Domain, Publish
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.
  • Contexto: O diagrama "Case 2 — Data Mesh: Plataforma Financeira Multi-Domínio" ilustra a arquitetura da solução para o tópico em questão.

Detalhamento do Fluxo Operacional Passo a Passo

  1. Autonomia de Domínio no Lakehouse: Cada domínio gerencia seu pipeline. O Domínio de Contas processa dados históricos transacionais usando o Amazon EMR Serverless rodando jobs PySpark, gerando tabelas no formato Apache Iceberg salvas em um bucket S3 local de contas. O Domínio de Investimentos faz processamento semelhante usando AWS Glue ETL e salvando em seu próprio bucket S3. As tabelas são catalogadas no Glue Data Catalog de cada respectiva conta do domínio.
  2. Registro e Governança no Lake Formation Hub: Os domínios registram seus locais de armazenamento S3 e tabelas no AWS Lake Formation (na conta central de governança ou via links de compartilhamento do AWS Resource Access Manager - RAM). O Lake Formation assume a gerência de permissões lógicas, substituindo as políticas complexas do IAM por controle refinado baseado em tags (TBAC - Tag-Based Access Control) e controle de grão fino.
  3. Segurança a Nível de Linhas e Colunas (Row & Column-level security): O administrador de dados define regras específicas para consumidores externos (ex: domínios de cross-selling ou analytics corporativo):
    • Filtro de Linha (Row Filter): Oculta registros de clientes VIPs cujo saldo acumulado é maior que R$ 500.000,00 (compliance regulatório e privacidade).
    • Filtro de Coluna (Column Masking): Aplica uma máscara SHA-256 ou substitui por asteriscos a coluna numero_cpf, impedindo a exposição de dados sensíveis (LGPD).
  4. Exposição via API de Dados com Caching Protetivo: Para disponibilizar os relatórios analíticos consolidados aos outros times sem liberar acesso direto ao S3 ou Athena (evitando custos e acessos indevidos):
    • O time do produto de dados cria um endpoint no Amazon API Gateway (REST API) integrado ao AWS Lambda.
    • O Lambda dispara consultas SQL otimizadas no Amazon Athena, que executa as queries cruzando dados de Contas e Investimentos.
    • O Athena consulta o Lake Formation em tempo real. O Lake Formation valida o autorizador do Lambda, intercepta a query física e retorna apenas as linhas permitidas e com a coluna CPF mascarada.
    • Para evitar cobranças repetidas do Athena e gargalos de concorrência, o API Gateway Cache é ativado com TTL de 1 hora. Se o mesmo dashboard solicitar os dados de cross-selling novamente, a resposta é entregue instantaneamente a partir do cache na borda.

Interações Principais e Fluxo de Dependências

  • AWS Lake Formation & S3 Storage Registration: O Lake Formation gerencia o acesso ao S3 registrando os caminhos físicos dos buckets. Ao fazer isso, o Lake Formation cria uma role do IAM (com políticas s3:PutObject, s3:GetObject) e assume essa role para descriptografar os dados em tempo de execução via chave KMS.
  • API Gateway Caching & Lambda Execution: Quando uma chamada HTTPS chega na API Gateway, o cache de borda intercepta a requisição. Se for um *Cache Hit*, a API retorna a resposta sem invocar o Lambda ou disparar o Athena, economizando recursos computacionais e reduzindo latências para milissegundos.
  • Cross-Account RAM Grants: O AWS Resource Access Manager (RAM) é utilizado nos bastidores pelo Lake Formation para compartilhar bancos e tabelas entre as contas de produtores e a conta central de Governança ou contas consumidoras, permitindo federação de dados sem duplicação física.

Possibilidades de Desmembramento e Modularização

A arquitetura de Data Mesh é conceitualmente desmembrada por natureza. O seu desacoplamento físico e organizacional na AWS é estruturado da seguinte forma:

1. Contas Produtoras Descentralizadas

Cada domínio de negócio (Contas e Investimentos) reside em uma Conta AWS dedicada. O processamento EMR Serverless ou Glue de cada domínio escreve em buckets S3 locais, e a criptografia utiliza chaves KMS exclusivas gerenciadas por cada time de domínio.

2. Hub de Metadados e Governança

O AWS Lake Formation atua em uma Conta Central de Governança (Data Directory). Ele não armazena arquivos físicos, apenas gerencia os links compartilhados via AWS Resource Access Manager (RAM) e aplica políticas finas de linhas e colunas (TBAC/LF-Tags).

3. Consumidor & Data Product APIs

As APIs de consumo (API Gateway + Lambda + Athena) são implantadas na Conta do Consumidor. O poder computacional das queries SQL analíticas é cobrado da conta que consome, evitando a partilha injusta de custos computacionais (FinOps) nos produtores.

Pontos de Atenção Críticos para Produção (Case 2)

Pontos de Atenção da Engenharia:
  • Cross-Account KMS Key Access & IAM Trusts: O erro clássico em Data Mesh é esquecer de dar permissões para o Lake Formation ler as chaves KMS customizadas (CMK) dos buckets S3 de origem. Certifique-se de que a política da chave KMS na conta produtora permite explicitamente a Role do Lake Formation (da própria conta produtora) descriptografar os dados, e configure a política de confiança (Trust Policy) desta role para aceitar o mapeamento e geração de credenciais temporárias do STS pelo serviço Lake Formation central.
  • Gargalos de Concorrência do Athena: O Athena possui limites padrão de concorrência por conta de queries ativas simultâneas. APIs analíticas expostas para dashboards concorrentes devem obrigatoriamente usar caching ou materializar dados agregados no DynamoDB para contornar falhas de TooManyRequestsException.
  • Consistência e Conflitos de Ocorrência Concorrente (Iceberg OCC): Quando múltiplos jobs no EMR Serverless ou Glue atualizam a mesma tabela Iceberg simultaneamente (ex: inserções históricas), podem ocorrer erros de CommitFailedException devido ao controle de concorrência otimista (OCC). Ajuste as políticas de retentativa nas propriedades da tabela Iceberg (commit.retry.num-retries) no Spark para mitigar falhas.

Case 5: Plataforma Logística Multirregional de Rastreabilidade (CDC)

Replicação ativa-ativa multirregião de remessas e pacotes usando DynamoDB Global Tables, captura de mudanças CDC com DMS e sincronia analítica em Redshift

Uma empresa de courier internacional rastreia pacotes em tempo real transitando entre galpões nos EUA, Europa e América Latina. Para garantir tempos de resposta de API inferiores a 20ms para os operadores logísticos de bipagem, os bancos operacionais devem estar localizados nas regiões físicas mais próximas. A plataforma deve conciliar essas bases de forma ativa-ativa sem conflitos e exportar logs de mudanças para um Data Warehouse centralizado.

Case 5 — Rastreabilidade Global CDC
Explicação:
  • Componentes: MULTI-REGION CDC DYNAMODB, DynamoDB Table (us-east-1), DynamoDB Table (eu-west-1), Global Tables Replication, DynamoDB Streams, AWS Lambda, Amazon S3 (Analytics)
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.
  • Contexto: O diagrama "Case 5 — Rastreabilidade Global CDC" ilustra a arquitetura da solução para o tópico em questão.

Detalhamento do Fluxo Operacional Passo a Passo

  1. Leituras e Escrituras Locais Rápidas com DynamoDB Global Tables: Os operadores de bipes de pacotes nos EUA e na Europa submetem coordenadas de tracking para instâncias regionais do Amazon DynamoDB. Usando o DynamoDB Global Tables, a AWS replica de forma bidirecional e assíncrona todas as atualizações em menos de 1 segundo entre as tabelas regionais. O mecanismo usa a regra Last-Writer-Wins (LWW) para dirimir conflitos de reconciliação de dados.
  2. Captura de Mudanças (CDC) com DynamoDB Streams: Toda alteração de estado (criação, edição ou exclusão do pacote) é empurrada para o DynamoDB Streams. O stream mantém a ordem cronológica estrita das modificações por chave de partição por até 24 horas.
  3. Processamento e Enriquecimento via AWS Lambda: Funções AWS Lambda assíncronas processam os registros em lotes (batch size de 100 eventos). O Lambda lê a imagem anterior e posterior do registro, normaliza a estrutura de dados de auditoria no formato CloudEvents e grava os arquivos compactados em formato colunar JSON no bucket S3 Staging.
  4. Carregamento Paralelo no Redshift Serverless (DW): Um pipeline agendado aciona a instrução SQL COPY no Amazon Redshift Serverless, consumindo de forma otimizada os dados do S3 em paralelo usando múltiplos Compute Slices e disponibilizando relatórios globais de tráfego de cargas sem impactar a performance do app operacional.

Mapeamento de Artefatos de Nuvem & Recursos

Recurso AWS Tipo/Modelo Função Crítica na Plataforma Pontos de Integração

DynamoDB Streams CDC Event Source Captura ordenada de logs de alteração e modificação de chaves operacionais. Invocado nativamente por funções do AWS Lambda.

Interações Principais e Fluxo de Dependências

  • DynamoDB Stream → Lambda: O Lambda utiliza o mecanismo de controle de concorrência por partição (shard) do DynamoDB. Se o processamento de um lote de bipes falhar na Lambda, ela retém o processamento daquele shard específico para evitar fora-de-ordem, enquanto os demais shards continuam processando sem travamentos.
  • S3 Staging → Redshift COPY: O comando COPY no Redshift utiliza arquivos de manifesto JSON gerados pela Lambda. O manifesto garante que apenas arquivos totalmente persistidos no S3 e com escrita consolidada entrem no DW, evitando duplicidade analítica.

Possibilidades de Desmembramento e Modularização

Controlar remessas globais requer redundância e isolamento regional. Esta arquitetura descentraliza o tráfego transacional do analítico:

1. Camada Transacional Regionalizada

Cada região (ex: Virginia, Dublin) grava seus eventos operacionais em tabelas locais do DynamoDB. A sincronização multirregional ativa-ativa de latência sub-segundo ocorre nativamente via rede interna da AWS (DynamoDB Global Tables), blindando a aplicação contra desastres geográficos.

2. Replicação CDC Assíncrona

Instâncias AWS DMS e funções Lambda capturam mutações e logs locais e as gravam de forma desacoplada em buckets S3 Bronze locais. Se o Data Warehouse central falhar, as remessas continuam gravando no S3 regional sem perda de histórico.

3. Data Warehouse Unificado

O Redshift Serverless atua como o nó agregador global. Ele executa comandos COPY consolidados lendo de múltiplos buckets S3 de forma federada. A computação analítica do Redshift é escalada de forma isolada, não concorrendo com as operações de entrega física.

Pontos de Atenção Críticos para Produção (Case 5)

Pontos de Atenção da Engenharia:
  • DynamoDB Last-Writer-Wins (LWW) Conflitos: Global Tables usa o timestamp do sistema para conciliar escritas simultâneas na mesma chave em regiões diferentes. Caso haja bipes simultâneos (ex: divergência de leitura física de pacote), o evento mais recente sobrescreve silenciosamente o anterior. Para evitar perda de logs históricos, desenhe a chave primária combinando id_pacote e um timestamp_bip incremental, tornando os registros imutáveis (append-only).
  • DMS CDC Memory limits: Caso utilizasse o AWS DMS para replicar bancos relacionais complexos como Oracle/Postgres para o Datalake, a replicação sofreria com falta de memória no Replication Instance sob alta volumetria. O uso do DynamoDB com streams nativos elimina esse intermediário, mas exige gerenciamento rigoroso de cotas de execução concorrente do Lambda na conta.

Case 8: Grafos ESG & Inteligência de Créditos de Carbono

Mapeamento de relações de cadeia de suprimentos complexas e transações de crédito de carbono utilizando Amazon Neptune e pipelines analíticos de grafos

Uma instituição financeira verde deseja rastrear a pegada ecológica e transações de créditos de carbono em cadeias produtivas complexas (ex: identificar se uma mineradora adquire insumos de fazendas desmatadas indiretamente). Como as relações são de múltiplos níveis (n-graus de conexões), bancos de dados relacionais e colunares falham na performance de consultas complexas de cruzamento. A arquitetura propõe um banco de dados de Grafos integrado ao Lakehouse.

Case 8 — Grafos ESG & Créditos de Carbono
Explicação:
  • Componentes: ESG GRAPH ANALYTICS ARCHITECTURE, Amazon RDS (Relational Data), AWS Glue (ETL), Amazon Neptune (Graph DB), Amazon SageMaker (Graph NN)
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.
  • Contexto: O diagrama "Case 8 — Grafos ESG & Créditos de Carbono" ilustra a arquitetura da solução para o tópico em questão.

Detalhamento do Fluxo Operacional Passo a Passo

  1. Extração e Estruturação de Relacionamentos no AWS Glue: Os dados brutos de faturas de compras corporativas e licenças de desmatamento chegam ao S3. Um Job do AWS Glue Spark converte as tabelas em estruturas de grafos, gerando dois arquivos CSV no S3: um contendo os Vértices (Empresas, Fazendas, Crachás de Carbono) e outro contendo as Arestas (comprado_de, gerou_crédito, localizado_em).
  2. Carregamento em Massa com Neptune Bulk Loader: Para carregar milhões de relações de forma eficiente sem saturar a CPU do banco de dados, o Glue aciona o Amazon Neptune Bulk Loader usando chamada de API REST. O Neptune lê os CSVs do S3 em paralelo de forma direta e otimizada.
  3. Consultas de Relação com Linguagem Gremlin/SPARQL: Analistas verdes disparam buscas analíticas complexas no Amazon Neptune usando linguagem Gremlin (ex: encontrar conexões em até 5 níveis ligando um cliente varejista a uma fazenda autuada por crime ecológico).
  4. Rastreamento Contínuo com Neptune Streams & Lambda: Cada nova transação gravada no grafo alimenta o Neptune Streams (CDC). Uma função AWS Lambda processa as novidades. Se detectar uma conexão indireta com uma entidade sob sanção ESG, levanta um alerta urgente via Amazon SNS para auditoria.

  • Lambda → Neptune Endpoint: A Lambda de auditoria mantém uma piscina de conexões (connection pool) abertas com o endpoint de leitura do Neptune para acelerar queries Gremlin de validação contínua de novos nós transacionais.

Possibilidades de Desmembramento e Modularização

Gerenciar dependências e conexões complexas de emissões corporativas requer isolamento de dados de rede de dados de relatórios:

1. Transações de Grafo (Neptune)

O cluster Amazon Neptune processa o banco de dados operacional de grafos (nós de empresas, créditos e transações). A equipe de desenvolvimento gerencia as queries Gremlin/SPARQL isoladas de outros bancos de dados da companhia.

2. Mecanismo de Sincronização Assíncrona

Através do Neptune Streams, cada inserção ou atualização no grafo gera um evento que é enviado a uma fila SQS. Uma função Lambda consome esses eventos e salva cópias dos dados estruturados em formato colunar Parquet na camada Bronze do S3.

3. Data Lakehouse Analítico ESG

O Athena e o QuickSight consultam os dados tabulares estruturados na camada Silver/Gold no S3. Isso permite que relatórios ESG em larga escala sejam executados a baixo custo, sem estressar a memória do cluster Neptune com queries analíticas de agregação.

Pontos de Atenção Críticos para Produção (Case 8)

Pontos de Atenção da Engenharia:
  • Neptune Instance Sizing para Grafos Grandes: Ao contrário de bancos relacionais onde o gargalo é I/O de disco, no Neptune o limitador é a memória RAM física. O grafo mantém os índices das relações ativas (SPOG) em memória para responder consultas Gremlin rapidamente. Fazer joins de muitos saltos em grafos gigantes com instâncias pequenas causará estouro de memória (OOM). Dimensione a instância com base no volume total de arestas estimadas.
  • Grafos sem Direcionamento e Loops Infinitos: Em consultas Gremlin, loops cíclicos nas arestas (ex: A → B → C → A) podem travar as queries analíticas em loops infinitos se não forem programadas travas de repetição (como dedup() ou simplePath()). Case 13: Circuit Breaker de Qualidade de Dados (AWS Glue DQDL)

Automação de isolamento de lotes corrompidos (Bad Records) em tempo de execução para blindagem do Data Warehouse

Uma empresa de telecomunicações sofria frequentemente com sistemas legados externos que enviavam arquivos de faturamento diários (CSV) no S3 com colunas numéricas preenchidas com strings (ex: valor "N/A" em vez de nulo) ou arquivos truncados. Quando o pipeline noturno copiava esses dados direto pro Amazon Redshift, relatórios fiscais amanheciam quebrados. A arquitetura de Data Quality Circuit Breaker automatizou a blindagem analítica usando o AWS Glue Data Quality na transição entre Bronze e Silver.

Arquitetura do Circuit Breaker

  1. Definição de Contratos Analíticos: O engenheiro de dados define o contrato de qualidade em DQDL (Data Quality Definition Language), acoplado ao job do Glue: 
    Rules = [
    IsComplete "id_fatura",
    IsUnique "id_fatura",
    ColumnDataType "valor_fatura" = "DOUBLE",
    ColumnValues "status" in ["PAGA", "ATRASADA", "CANCELADA"]
]
  2. Fase de Avaliação Intermediária (Spark Evaluation): O script PySpark no AWS Glue não escreve nada no disco imediatamente. Ele lê a partição diária do S3 (Bronze), converte em um DynamicFrame e submete à API EvaluateDataQuality.
  3. Roteamento por Desvio (Quarantine): A função de avaliação gera um relatório detalhado marcando as linhas específicas que falharam. O Glue particiona os dados ativamente em dois DataFrames lógicos:
    • df_aprovado: Contém apenas registros que passaram nos testes. São salvos na camada Silver (Iceberg) e habilitados para consumo downstream.
    • df_rejeitado: Contém a sujeira. Eles são serializados e desviados para um S3 Quarantine Bucket isolado. Essa gravação não interrompe o job inteiro.
  4. Notificação Proativa e Observabilidade: Para evitar que a quarentena se torne um "buraco negro" esquecido, um alarme é engatilhado. A métrica de falha é empurrada para o CloudWatch. Uma regra do Amazon EventBridge captura o erro e despacha via Amazon SNS um payload formatado em JSON para um Lambda, que alerta a equipe de Data Ops no canal do Slack: "Atenção: 4.500 faturas desviadas para a Quarentena S3. Arquivo de origem: faturas_05_06_2026.csv. Motivo: IsComplete id_fatura = Failed."

Case 25: Desacoplamento Monolítico (RDS para DynamoDB + Aurora Serverless via AWS DMS)

Migração de arquitetura legada (Zero-Downtime) isolando workloads massivos de leitura em NoSQL e garantindo a resiliência transacional

Um banco digital possuía um monolito transacional operando sobre um gigantesco Amazon RDS MySQL. O banco relacional estava estourando seus limites de IOPS (Disco EBS) e sofrendo Connection Exhaustion porque a tabela de "Extratos" sofria milhões de leituras diárias via app, misturadas com as atualizações de "Balanço" do Core Bancário. O tempo de resposta degradou de 20ms para 800ms. A missão era estrangular o monolito sem qualquer downtime.

DMS CDC MIGRATION ARCHITECTURE
Explicação:
  • Componentes: DMS CDC MIGRATION ARCHITECTURE, Legacy Monolith DB (MySQL / Oracle), AWS DMS (CDC Engine), Amazon Kinesis Data Streams, Microservice 1, Microservice 2, Amazon S3 (Data Lake), Read Transaction Logs
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.

Arquitetura de Solução: AWS DMS + Single-Table Design + Aurora

  1. Isolamento com DynamoDB e Modelagem (Single-Table):
    Os engenheiros decidiram que os "Extratos", por serem dados imutáveis, sequenciais de altíssimo volume de leitura, não pertenciam a um banco relacional. Uma tabela no Amazon DynamoDB foi modelada no padrão Single-Table Design: PK = "CONTA#123" e SK = "DATA#2026-06-10". Isso permitiu à API recuperar meses de extratos de um usuário específico em menos de 8ms de forma consistente.
  2. Core Bancário para Aurora Serverless v2:
    A tabela de "Balanços" precisava obrigatoriamente de bloqueio de linha rigoroso (Locks ACID) para evitar fraudes em transações financeiras. Por isso, a tabela relacional foi migrada para o Amazon Aurora Serverless v2. Assim, o banco transacional pode escalar a sua CPU verticalmente (Adição de ACUs em milissegundos) durante o horário comercial e decair à noite, economizando orçamento e garantindo performance isolada do Extrato.
  3. Migração Zero-Downtime usando AWS DMS (Change Data Capture):
    Para evitar queda dos serviços bancários, a migração foi feita usando o AWS Database Migration Service (DMS). O DMS realizou o Full Load (cópia massiva) dos dados originais para os dois novos destinos. Em seguida, ele assumiu a função de CDC (Change Data Capture), lendo o binlog do MySQL originário em tempo real e aplicando as alterações instantaneamente tanto no DynamoDB quanto no Aurora. Após o Lag do DMS chegar a zero, a equipe de engenharia alterou as rotas DNS na API do cliente, concluindo o Cut-over sem que o usuário percebesse.
Resultado de Negócio:

A latência de leitura dos extratos no aplicativo mobile despencou de 800ms para singelos 8ms, suportando dezenas de milhares de usuários simultâneos (On-Demand Capacity). O Core Bancário no Aurora Serverless ganhou fôlego absoluto e parou de emitir alarmes de Throttling de I/O. A migração foi executada em produção sob alta carga e as rotinas de Data Analytics ficaram mais rápidas na nova arquitetura nativa da AWS.

- `id_cliente` não pode ser nulo.
- A chave primária combinada `(data_referencia, id_produto, id_cliente)` deve ser única.
Trade-offs e Desafios (Arquitetura Lambda):

O desafio central de adotar a arquitetura Lambda é evitar a Complexidade de Manutenção ao duplicar a lógica de negócio (Flink/streaming e Spark/batch). Para mitigar, os códigos e regras devem ser o mais isolados possível, ou deve-se explorar frameworks como Apache Beam. Além disso, existe o desafio semântico onde analistas confundem a métrica Intraday com o fechamento oficial. É vital diferenciar fisicamente e por nomenclatura o acesso ao banco operacional ("Captação Estimada") do DW certificado para regulação ("Captação Consolidada/Oficial").

5. O Pitch de Business Value (Proposta de Valor):

Esta plataforma hibrida traduz tecnologia direta para alavancas financeiras críticas (EBITDA). A visão Intraday oferece inteligência competitiva em tempo real: a área comercial pode interceptar resgates anômalos de grande volume instantaneamente, aplicando táticas de retenção antes do dinheiro deixar a instituição, o que blinda a margem e o Net New Money. Paralelamente, a robustez da Visão Batch Oficial garante integridade milimétrica em nível regulatório para conciliações financeiras e balanços (compliance), reduzindo riscos de multas operacionais e otimizando processos manuais custosos no backoffice (redução de OPEX).

Case 38: Automação de Ofícios Jurídicos (Task Tokens)

Case 38 • IA & Integrações

Cenário: Recebimento de +20.000 ofícios/mês processados 2x ao dia via SFTP (7h e 15h). As respostas aos ofícios não podem passar 1 dia sem interação, e 30% dependem de subsídios (dados adicionais de outras áreas do banco), onde há um SLA de 1 dia para solicitar e 5 dias de espera para o retorno do dado.

Desafio: Como gerenciar uma orquestração de IA onde a máquina precisa ler o documento, mas depois pausar o fluxo por até 5 dias sem consumir recursos ou tempo de execução desnecessários?

Solução AWS: Arquitetura "Wait for Task Token". O Step Functions faz a chamada inicial para extrair os dados via Bedrock. Se identificar a necessidade de subsídios, ele envia a solicitação para a API externa contendo um TaskToken e "dorme". A API externa tem até 5 dias para responder com o Token. Ao receber a resposta, o Step Functions "acorda" e continua o workflow. Sem custos ociosos.

Detalhamento Arquitetural:
  • AWS Transfer Family: Ingestão SFTP totalmente gerenciada e segura mapeada diretamente para um bucket S3.
  • Controle de SLAs (DynamoDB): Uma tabela TTL rastreia os "1 dia sem interação" emitindo alertas (EventBridge) caso um fluxo fique travado nas APIs legadas.
