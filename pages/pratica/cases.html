Case 1: Plataforma de Eventos de Streaming E-commerce (High-Throughput)

Ingestão assíncrona em tempo real para prevenção de fraudes e persistência ACID em Lakehouse Iceberg

Este caso prático ilustra a infraestrutura de uma empresa de varejo global que precisa coletar cliques, visualizações, adições ao carrinho e compras em tempo real. O sistema deve atender a dois requisitos conflitantes: baixa latência para alimentar um motor de análise de fraudes em tempo real e estruturação barata no S3 (formato colunar indexado) para análises analíticas e machine learning.

Detalhamento do Fluxo Operacional Passo a Passo

  1. Ingestão Escalável com ECS Fargate & ALB: Os aplicativos de clientes e navegadores web disparam requisições POST para a rota de coleta. O **Application Load Balancer (ALB)** intercepta as chamadas e as balanceia de forma round-robin entre as tarefas do contêiner rodando no **Amazon ECS Fargate**. O uso de Fargate elimina a gerência de servidores de computação tradicionais. O contêiner de ingestão é ultra-leve (escrito em Python FastAPI ou Go) e sua única responsabilidade é validar sintaticamente a estrutura básica e escrever a mensagem assincronamente no Kinesis.
  2. Desacoplamento e Escala com Kinesis Data Streams: O **Kinesis Data Streams** age como buffer absorvendo picos violentos de tráfego. Ele está configurado em modo *Provisionado* ou *On-Demand* com partições (shards) que escalam conforme a volumetria de entrada. A chave de partição (Partition Key) é definida como o id_usuario para garantir que eventos de um mesmo usuário caiam no mesmo shard, mantendo a ordem sequencial das transações.
  3. Caminho Rápido (Speed Path) - Prevenção de Fraudes: Uma função **AWS Lambda** lê micro-lotes (batch window de 1 segundo) diretamente dos Shards do Kinesis com baixíssima latência. O Lambda executa regras de fraude rápidas baseadas em padrões (ex: compras sequenciais em menos de 2 segundos) e atualiza o estado operacional instantaneamente no **Amazon DynamoDB** (chave-valor de latência inferior a 10ms).
  4. Caminho Analítico (Storage/Batch Path) - Firehose e Compactação: Em paralelo, o **Kinesis Data Firehose** consome do stream. Ele realiza buffering (ex: aguarda encher 128MB ou completar 5 minutos) para evitar o problema de arquivos pequenos (*Small Files*). O Firehose lê o catálogo de metadados do **AWS Glue** e converte dinamicamente os payloads JSON para o formato binário colunar **Apache Parquet** antes de gravar os arquivos na camada **Bronze** do Amazon S3.
  5. Camada de Otimização e Qualidade (AWS Glue Spark Job): Um Job periódico do **AWS Glue** (PySpark) lê os arquivos Parquet da camada Bronze. Ele executa três etapas cruciais:
    • De-duplicação: Utiliza o DropDuplicates com base no ID único do evento, tratando duplicidades inevitáveis em sistemas distribuídos (at-least-once).
    • Mecanismo de Data Quality (DQDL): Executa testes declarativos de integridade. Se o lote tiver um índice de falhas intolerável, aciona o disjuntor enviando o lote corrompido para o bucket de **Quarentena** e disparando um alerta no Slack via Amazon EventBridge. Se passar, grava os dados na camada **Silver** em tabelas formatadas em **Apache Iceberg**.
    • Tuning do Iceberg: Executa o comando Spark SQL OPTIMIZE table REWRITE DATA para mesclar arquivos temporários em blocos maiores e remover metadados obsoletos.
  6. Consumo Analítico Federado: Cientistas de dados e analistas de BI utilizam o **Amazon Athena** para realizar consultas SQL analíticas complexas e rodar relatórios no **QuickSight** consumindo diretamente da camada Silver/Gold sem que o processamento interfira na latência transacional da aplicação.

Interações Principais e Fluxo de Dependências

  • ECS Fargate → Kinesis Data Streams: Os contêineres ECS mantêm instâncias persistentes do cliente Boto3 do Kinesis em memória global. Recriar o cliente HTTP/SDK a cada requisição adiciona um handshake SSL lento e desnecessário. A API publica no Kinesis usando PutRecords (em lote de até 500 registros por chamada) para otimizar throughput de rede.
  • Firehose → Glue Schema Catalog → S3 Bronze: O Kinesis Firehose consome continuamente os eventos. A cada intervalo de buffer, ele solicita o esquema de colunas ao Glue Catalog. Caso algum payload JSON possua campos corrompidos impossíveis de converter em Parquet, o Firehose desvia a mensagem para uma pasta específica processing_failed/ no bucket Bronze, permitindo que a ingestão não pare por causa de arquivos mal formatados.

Possibilidades de Desmembramento e Modularização

Para otimizar o ciclo de desenvolvimento, isolar falhas e garantir a governança por equipes autônomas, esta arquitetura pode ser desmembrada em três módulos independentes:

1. Microsserviço de Ingestão (API)

O ALB + ECS Fargate pode ser isolado como um microsserviço de borda com pipeline de CI/CD próprio. Ele expõe um endpoint REST estável e grava no Kinesis sem conhecer os processos analíticos downstream, permitindo deploys frequentes sem impactar o Data Lake.

2. Motor de Prevenção de Fraude

O fluxo de baixa latência (Kinesis Data Streams + Lambda + DynamoDB) pode rodar em uma conta AWS separada de Risco/Segurança. A leitura concorrente das partições do Kinesis garante que análises analíticas pesadas não gerem latência na prevenção de fraudes.

3. Pipeline de Analytics & Lakehouse

A ingestão assíncrona baseada em Kinesis Firehose + Glue Spark + S3 Silver pode ser mantida pela equipe de Engenharia de Dados Central. A transformação e compactação periódica das tabelas Apache Iceberg ocorrem em background, isoladas do tráfego web real-time.

Pontos de Atenção Críticos para Produção (Case 1)

Pontos de Atenção da Engenharia:
  • Throttling de Gravação no Kinesis: Cada Shard do Kinesis suporta no máximo 1 MB/s ou 1000 registros/s de escrita. Sob pico de 50x, se a quantidade de shards não escalar dinamicamente (Split Shards), o ECS receberá erros de ProvisionedThroughputExceededException. Os contêineres devem amortecer isso implementando buffers de memória locais e retentativas exponenciais com Jitter.
  • Buffer do Firehose e Small Files: Configurar o Firehose com buffers pequenos (ex: 5MB ou 60s) gera milhões de arquivos minúsculos no S3. O ideal para o pipeline analítico é fixar o buffer no limite máximo suportado pelo seu SLA (ex: 128MB ou 5 minutos) para que os arquivos cheguem na Bronze com tamanhos saudáveis para leitura.
  • DynamoDB WCU Exhaustion: O Lambda que avalia a fraude pode escalar horizontalmente em milissegundos. Se a tabela do DynamoDB estiver em modo Provisionado com WCUs baixos, o Lambda sofrerá throttling ao registrar transações. Ative o modo **On-Demand (Pay-Per-Request)** na tabela do DynamoDB para mitigar picos agressivos de transações do e-commerce.

Case 2: Plataforma Financeira Data Mesh & Governança com Lake Formation

Implementação orientada a domínios com compartilhamento central de metadados, controle fino de acesso e Data APIs protegidas por cache

Neste caso de uso de uma instituição bancária regulada, múltiplos domínios de negócios geram e gerenciam seus próprios dados. O domínio de **Contas Correntes** e o domínio de **Investimentos** precisam compartilhar dados para gerar relatórios unificados sem duplicar armazenamento e sob regras rígidas de compliance (ocultar saldo de investidores VIPs e mascarar CPFs).

Detalhamento do Fluxo Operacional Passo a Passo

  1. Autonomia de Domínio no Lakehouse: Cada domínio gerencia seu pipeline. O Domínio de Contas processa dados históricos transacionais usando o **Amazon EMR Serverless** rodando jobs PySpark, gerando tabelas no formato **Apache Iceberg** salvas em um bucket S3 local de contas. O Domínio de Investimentos faz processamento semelhante usando **AWS Glue ETL** e salvando em seu próprio bucket S3. As tabelas são catalogadas no **Glue Data Catalog** de cada respectiva conta do domínio.
  2. Registro e Governança no Lake Formation Hub: Os domínios registram seus locais de armazenamento S3 e tabelas no **AWS Lake Formation** (na conta central de governança ou via links de compartilhamento do AWS Resource Access Manager - RAM). O Lake Formation assume a gerência de permissões lógicas, substituindo as políticas complexas do IAM por controle refinado baseado em tags (TBAC - Tag-Based Access Control) e controle de grão fino.
  3. Segurança a Nível de Linhas e Colunas (Row & Column-level security): O administrador de dados define regras específicas para consumidores externos (ex: domínios de cross-selling ou analytics corporativo):
    • Filtro de Linha (Row Filter): Oculta registros de clientes VIPs cujo saldo acumulado é maior que R$ 500.000,00 (compliance regulatório e privacidade).
    • Filtro de Coluna (Column Masking): Aplica uma máscara SHA-256 ou substitui por asteriscos a coluna numero_cpf, impedindo a exposição de dados sensíveis (LGPD).
  4. Exposição via API de Dados com Caching Protetivo: Para disponibilizar os relatórios analíticos consolidados aos outros times sem liberar acesso direto ao S3 ou Athena (evitando custos e acessos indevidos):
    • O time do produto de dados cria um endpoint no **Amazon API Gateway** (REST API) integrado ao **AWS Lambda**.
    • O Lambda dispara consultas SQL otimizadas no **Amazon Athena**, que executa as queries cruzando dados de Contas e Investimentos.
    • O Athena consulta o **Lake Formation** em tempo real. O Lake Formation valida o autorizador do Lambda, intercepta a query física e retorna **apenas as linhas permitidas e com a coluna CPF mascarada**.
    • Para evitar cobranças repetidas do Athena e gargalos de concorrência, o **API Gateway Cache** é ativado com TTL de 1 hora. Se o mesmo dashboard solicitar os dados de cross-selling novamente, a resposta é entregue instantaneamente a partir do cache na borda.

Interações Principais e Fluxo de Dependências

  • AWS Lake Formation & S3 Storage Registration: O Lake Formation gerencia o acesso ao S3 registrando os caminhos físicos dos buckets. Ao fazer isso, o Lake Formation cria uma role do IAM (com políticas s3:PutObject, s3:GetObject) e assume essa role para descriptografar os dados em tempo de execução via chave KMS.
  • API Gateway Caching & Lambda Execution: Quando uma chamada HTTPS chega na API Gateway, o cache de borda intercepta a requisição. Se for um *Cache Hit*, a API retorna a resposta sem invocar o Lambda ou disparar o Athena, economizando recursos computacionais e reduzindo latências para milissegundos.
  • Cross-Account RAM Grants: O AWS Resource Access Manager (RAM) é utilizado nos bastidores pelo Lake Formation para compartilhar bancos e tabelas entre as contas de produtores e a conta central de Governança ou contas consumidoras, permitindo federação de dados sem duplicação física.

Possibilidades de Desmembramento e Modularização

A arquitetura de Data Mesh é conceitualmente desmembrada por natureza. O seu desacoplamento físico e organizacional na AWS é estruturado da seguinte forma:

1. Contas Produtoras Descentralizadas

Cada domínio de negócio (Contas e Investimentos) reside em uma Conta AWS dedicada. O processamento EMR Serverless ou Glue de cada domínio escreve em buckets S3 locais, e a criptografia utiliza chaves KMS exclusivas gerenciadas por cada time de domínio.

2. Hub de Metadados e Governança

O AWS Lake Formation atua em uma Conta Central de Governança (Data Directory). Ele não armazena arquivos físicos, apenas gerencia os links compartilhados via AWS Resource Access Manager (RAM) e aplica políticas finas de linhas e colunas (TBAC/LF-Tags).

3. Consumidor & Data Product APIs

As APIs de consumo (API Gateway + Lambda + Athena) são implantadas na Conta do Consumidor. O poder computacional das queries SQL analíticas é cobrado da conta que consome, evitando a partilha injusta de custos computacionais (FinOps) nos produtores.

Pontos de Atenção Críticos para Produção (Case 2)

Pontos de Atenção da Engenharia:
  • Cross-Account KMS Key Access & IAM Trusts: O erro clássico em Data Mesh é esquecer de dar permissões para o Lake Formation ler as chaves KMS customizadas (CMK) dos buckets S3 de origem. Certifique-se de que a política da chave KMS na conta produtora permite explicitamente a Role do Lake Formation (da própria conta produtora) descriptografar os dados, e configure a política de confiança (Trust Policy) desta role para aceitar o mapeamento e geração de credenciais temporárias do STS pelo serviço Lake Formation central.
  • Gargalos de Concorrência do Athena: O Athena possui limites padrão de concorrência por conta de queries ativas simultâneas. APIs analíticas expostas para dashboards concorrentes devem obrigatoriamente usar caching ou materializar dados agregados no DynamoDB para contornar falhas de TooManyRequestsException.
  • Consistência e Conflitos de Ocorrência Concorrente (Iceberg OCC): Quando múltiplos jobs no EMR Serverless ou Glue atualizam a mesma tabela Iceberg simultaneamente (ex: inserções históricas), podem ocorrer erros de CommitFailedException devido ao controle de concorrência otimista (OCC). Ajuste as políticas de retentativa nas propriedades da tabela Iceberg (commit.retry.num-retries) no Spark para mitigar falhas.

Case 3: Plataforma de IA Generativa & RAG (Retrieval-Augmented Generation)

Ingestão e vetorização de documentos de forma distribuída (Glue/EMR) e orquestração de LLMs com baixa latência usando Amazon Bedrock e OpenSearch Serverless

Este caso de uso descreve a arquitetura de uma assistente virtual de inteligência artificial de alta performance que responde a dúvidas complexas sobre manuais de produtos, logs de suporte e políticas de segurança corporativas. Detalhamento do Fluxo e Arquitetura

Eles empacotam seus jobs PySpark, modelos XGBoost e bibliotecas C++ nativas em Imagens Docker customizadas (Custom Docker Images) guardadas no Amazon ECR.   2. Segurança via IRSA (IAM Roles for Service Accounts): Para garantir a segurança dos dados do Lakehouse (Amazon S3), cada namespace tem seu Service Account mapeado para uma Role IAM específica via OIDC. Se o Pod do "Time A" tentar ler o bucket S3 do "Time B", o AWS IAM bloqueia a requisição. O EKS injeta automaticamente o token STS em tempo real nos pods do Spark.
  3. Autoscaling Extremo com Karpenter (FinOps): Quando um workflow do Airflow (via EKS Operator ou EMR Virtual Cluster API) submete 500 pods de Spark Executors simultaneamente, o cluster Kubernetes precisa de hardware físico na hora. O Karpenter entra em ação: em menos de 45 segundos, ele analisa os requisitos de CPU/RAM dos pods pendentes, consulta o mercado de Spot Instances da AWS para os tipos de instâncias de menor custo e de menor probabilidade de interrupção (ex: mesclando instâncias m5.4xlarge e r6g.8xlarge Graviton) e provisiona os nós exatos necessários. Quando o job acaba, o Karpenter destrói os nós imediatamente, cobrando apenas pelos minutos exatos de processamento da AWS.
  4. Graceful Decommissioning & Shuffle Tracking: Como 80% do cluster usa Spot Instances para processar o Lakehouse, nós recebem frequentemente sinais de desligamento forçados da AWS (Spot Interruption Notice). O Spark é configurado com spark.decommission.enabled=true e spark.dynamicAllocation.shuffleTracking.enabled=true. Antes do nó ser morto, o Kubernetes notifica o pod através de hooks. O Executor que vai ser interrompido migra seus blocos locais de Shuffle via rede de forma proativa para outro Executor ativo sobrevivente (p2p), permitindo que a agregação Spark (DAG) não perca os dados e continue em andamento sem recalcular toda a base.

Desafios e Lições Aprendidas na Produção

Pontos Críticos em EMR on EKS:
  • Overhead do CoreDNS sob Alta Concorrência: Quando milhares de pods Executors do Spark sobem simultaneamente em instantes e todos tentam abrir conexões HTTP AWS SDK simultâneas para os buckets do Amazon S3 ou se comunicarem com a infra do K8s, ocorre uma tempestade massiva de requisições DNS. Isso derruba silenciosamente o CoreDNS padrão do EKS (com logs explodindo com exceções de `java.net.UnknownHostException`). A solução mandatória em arquiteturas Spark at-scale no K8s é implementar o NodeLocal DNSCache do Kubernetes, que mantém um cache DNS distribuído rodando como DaemonSet em cada nó físico, retirando todo o esgotamento TCP de portas do controlador master.
  • Pod Startup Latency e Cold Starts Lentos (Image Pull): Executar imagens Docker gordinhas recheadas de lib de PySpark + LLMs + Scikit (frequentemente de 3 GB a 5 GB) faz com que o tempo de subida inicial do Pod seja totalmente dominado pela demora do download físico da imagem do ECR (Image Pull) nos nós limpos que o Karpenter acabou de ligar. A solução extrema em Big Data envolve o uso do Amazon EBS Snapshot do EKS ou criar e utilizar AMIs pré-baking personalizadas do EKS que já contenham as camadas pesadas do Docker cacheadas em disco (baked-in), resultando em tempos de boot saltando de minutos para menos de 30 segundos.

  3. **Governança por Metas de Produto (SLA/SLO/SLI):** Cada domínio assinou um **Data Contract** contendo SLOs rígidos. Por exemplo, o domínio de Cartões firmou um SLO de entregar a tabela de transações com latência menor que 5 minutos em 99.9% das execuções diárias (SLI de Freshness).
Resultado de Negócio:

A migração reduziu o time-to-data-access (tempo de requisição de dados à disponibilização em queries) de 5 dias úteis para apenas 2 horas por meio do autoatendimento no Polaris. A latência de ingestão caiu de D-1 (lotes diários) para menos de 5 minutos, e os SLOs permitiram mapear e prever falhas de qualidade com transparência, elevando a confiança das equipes de negócios em mais de 95%.

Case 9: Plataforma de Análise de Risco Híbrida em Tempo Real (MLOps + DataOps)

Implementação integrada de MSK, Flink, SageMaker Feature Store e detecção contínua de Drift sob Contratos de Dados

Uma grande instituição financeira precisa avaliar o risco de crédito para transações de pagamentos instantâneos (PIX/TED). O sistema deve validar cada transação de entrada contra contratos de dados rígidos, calcular features agregadas em tempo real com estado (streaming), enriquecer o contexto de inferência buscando no SageMaker Feature Store Online e monitorar continuamente se as populações de dados inferidos sofreram variações estatísticas drásticas que invalidem o modelo preexistente.

Arquitetura da Solução Híbrida

  1. Validação Ativa de Contrato (DataOps): As requisições de pagamentos são ingeridas no **Amazon MSK**. O micro-serviço validador consome as transações de entrada e roda rotinas de checagem contra esquemas JSON de contratos de dados. Mensagens corrompidas são desviadas imediatamente para uma pasta de Quarentena no S3.
  2. Cálculo de Variáveis com Flink (Feature Ingestion): Registros aprovados entram no processador contínuo **Apache Flink**, que calcula agregações temporais de janelas deslizantes (ex: quantidade de tentativas nos últimos 15 min, volume médio por hora). O Flink atualiza estes dados a cada segundo diretamente no **SageMaker Feature Store Online (DynamoDB)**.
  3. Inferência Segura e Grounding: O serviço de crédito (Lambda) recebe a transação ativamente. Ele consulta o SageMaker Feature Store Online obtendo as features em menos de 8ms, anexa no payload e executa a inferência contra o SageMaker Endpoint do modelo.
  4. Detecção de Drift e Retreinamento (MLOps): As requisições e respostas do endpoint do modelo são logadas em buckets S3. Diariamente, um Job do **SageMaker Model Monitor** analisa os logs contra a base de treinamento. Caso identifique um desvio estatístico de População (Data Drift) com Wasserstein distance superior a 0.1, dispara alertas e invoca a Step Functions orquestrando o **SageMaker Pipelines** para re-treinar o modelo com os dados mais recentes na Offline Store S3.
Resultado de Negócio:

A unificação dos ciclos de engenharia e modelagem (DataOps + MLOps) garantiu zero interrupções nos pipelines de crédito por Schema Drift. A taxa de falsos positivos em fraudes de risco contínuo caiu 40% graças à ingestão em tempo real de features no Feature Store Online, e o re-treinamento autônomo reduziu a dependência de intervenção humana.

Case 10: Ingress Analítico Multirregião de Altíssima Disponibilidade (Serverless)

Resultado de Negócio:

A eliminação de Lambdas na etapa de ingress cortou custos operacionais em 65%. O uso de VPC Endpoints reduziu em 92% os custos de transferências de dados de rede da VPC analítica, e a arquitetura ativa-passiva gerenciada pelo Route 53 resultou em 99,999% de disponibilidade global medida.

Case 11: Migração e Sizing de Data Lakehouse de 20 Bilhões de Registros (EMR & Iceberg)

Migração física de dados brutos legados para Apache Iceberg no EMR Serverless detalhando cálculos de ACU, compactação e Object Storage Layout

Um grande marketplace de e-commerce precisa consolidar e migrar 5 anos de transações de vendas do Datalake legado (tabelas externas Hive particionadas por data, totalizando 40 TB e 20 bilhões de registros de dados inconsistentes) para tabelas Apache Iceberg no EMR Serverless. A migração deve evitar gargalos de S3 SlowDown no bucket final, compactar mais de 4 milhões de arquivos pequenos legados na ingestão e definir o dimensionamento ideal do EMR para processar a janela em menos de 8 horas.

Dimensionamento (Sizing) e Configuração das Aplicações

  1. Matemática de Sizing do EMR Serverless (ACUs):
    Considerando a leitura paralela e o volume de shuffle necessário para re-particionar 40 TB, desenhamos a seguinte estrutura:
    • Worker Type Configuration: 4 vCPUs e 32 GB RAM por executor (relacionamento de 8GB por vCPU, ideal para evitar spills frequentes de disco em aggregations de joins).
    • Executors Máximos: Limitado em 100 Workers simultâneos. Isso entrega: 400 vCPUs e 3.200 GB RAM de capacidade máxima computacional.
    • Armazenamento Efêmero por Worker: Configurado em 120 GB de disco NVMe temporário para evitar falhas físicas de estouro de disco local na gravação de partições do Iceberg (Shuffle Disk Space).
  2. Prevenção de S3 SlowDown (Object Storage Layout):
    Para impedir HTTP 503 SlowDowns decorrentes de milhares de threads Spark gravando sequencialmente no mesmo prefixo do S3, ativamos a propriedade do Iceberg 'write.object-storage.enabled' = 'true'. Isso injeta hashes MD5 pseudo-aleatórios na raiz das URIs das partições (ex: s3://gold-bucket/a8f9c1/vendas/data_venda=...), espalhando as conexões por diferentes sub-partições internas da infraestrutura física do S3 e superando o teto de 3.500 escritas/s.
  3. Compactação de Pequenos Arquivos no Spark DDL:
    Os dados de entrada são distribuídos fisicamente via Spark aplicando a cláusula 'write.distribution-mode' = 'hash'. Isso reagrupa os registros pelo hash da partição de destino nos executores corretos antes de iniciar o commit, assegurando que cada executor grave arquivos grandes de ~512 MB, em vez de centenas de arquivos de kilobytes.
Resultado de Negócio:

A migração foi concluída em 5 horas e 40 minutos (SLA cumprido com folga). Os 4 milhões de arquivos pequenos foram compactados em menos de 85.000 arquivos Parquet de 512 MB. As consultas analíticas do Athena sobre a camada Gold tornaram-se 90% mais rápidas devido ao pruning aprimorado de metadados do Iceberg, e o custo do job no EMR Serverless foi de apenas $380 devido ao scaling agressivo em tempo de execução.

Case 12: Redução de Custo de 70% na Migração de EMR EC2 para EKS Spot com Karpenter

Modernização de pipelines Airflow + Spark trocando clusters transientes EMR on EC2 por EKS multitenant com autoscaling JIT

Uma fintech possuía 150 jobs de ETL diários orquestrados pelo Apache Airflow. Cada tarefa do DAG criava um cluster EMR no EC2 (Transient Cluster) para processar os dados e o destruía no final. Essa arquitetura sofria com Tempo de Inicialização (cada EMR demora de 6 a 10 minutos apenas para fazer o bootstrap do Hadoop) e com Desperdício Computacional (pagamento mínimo de 1 hora de EC2 mesmo para jobs de 10 minutos, além da taxa por minuto do EMR). O objetivo era unificar a computação no Kubernetes.

Arquitetura de Solução: EKS + Karpenter + Spark Operator

  1. Substituição de EMR Steps por SparkApplication CRD:
    Os operadores EmrCreateJobFlowOperator e EmrAddStepsOperator do Airflow foram refatorados para o SparkKubernetesOperator. Em vez de provisionar máquinas virtuais, o Airflow agora envia um YAML declarativo (CRD) descrevendo a necessidade de CPU/RAM diretamente para a API do EKS (Spark Operator).
  2. Provisionamento Just-In-Time com Karpenter:
    Foi instalado o Karpenter no Control Plane do EKS, substituindo o Cluster Autoscaler clássico. Quando o Spark Operator solicita 50 pods de executores (ex: 4 vCPUs cada), o Karpenter lê os pods pendentes, envia uma requisição agrupada (Fleet API) e traz instâncias EC2 Spot bare-metal do tamanho exato (ex: m5.12xlarge) em menos de 40 segundos. Sem pré-aquecimento de instâncias ou AMIs pesadas do Hadoop.
  3. Spot Fleet Diversification e Tolerância a Falhas:
    Para evitar interrupções de capacidade Spot, o NodePool do Karpenter foi configurado para aceitar famílias flexíveis (m5, m6i, r5, r6i, c5) baseando-se no tipo de carga de trabalho do Spark. Se a Amazon requisitar a instância Spot de volta (aviso de 2 minutos), o Karpenter e o Kubernetes ejetam os Pods com graciosidade (Graceful Termination) e o motor de resiliência nativo do Apache Spark recomputa os RDDs perdidos do executor falho em outro nó automaticamente.
Resultado de Negócio:

A latência ponta a ponta dos DAGs reduziu em 45% devido ao tempo de provisionamento de infraestrutura cair de 8 minutos para 40 segundos. A fatura mensal de processamento despencou mais de 70% porque o time parou de pagar as licenças caras de software do EMR e passou a faturar EC2 Spot pelo segundo exato de uso através da bin-packing extrema do Karpenter (múltiplos jobs Spark alocados perfeitamente nas mesmas instâncias até encher a RAM).

Case 13: Desacoplamento Monolítico (RDS para DynamoDB + Aurora Serverless via AWS DMS)

Migração de arquitetura legada (Zero-Downtime) isolando workloads massivos de leitura em NoSQL e garantindo a resiliência transacional

Um banco digital possuía um monolito transacional operando sobre um gigantesco Amazon RDS MySQL. O banco relacional estava estourando seus limites de IOPS (Disco EBS) e sofrendo Connection Exhaustion porque a tabela de "Extratos" sofria milhões de leituras diárias via app, misturadas com as atualizações de "Balanço" do Core Bancário. O tempo de resposta degradou de 20ms para 800ms. A missão era estrangular o monolito sem qualquer downtime.

DMS CDC MIGRATION ARCHITECTURE
Explicação:
  • Componentes: DMS CDC MIGRATION ARCHITECTURE, Legacy Monolith DB (MySQL / Oracle), AWS DMS (CDC Engine), Amazon Kinesis Data Streams, Microservice 1, Microservice 2, Amazon S3 (Data Lake), Read Transaction Logs
  • Integração: O fluxo de dados conecta os componentes citados acima. As setas no diagrama indicam a direcionalidade (Eventos, Streaming ou Polling) entre os serviços AWS.
  • Contexto: O diagrama "DMS CDC MIGRATION ARCHITECTURE" ilustra a arquitetura da solução para o tópico em questão.

Arquitetura de Solução: AWS DMS + Single-Table Design + Aurora

  1. Isolamento com DynamoDB e Modelagem (Single-Table):
    Os engenheiros decidiram que os "Extratos", por serem dados imutáveis, sequenciais de altíssimo volume de leitura, não pertenciam a um banco relacional. Uma tabela no Amazon DynamoDB foi modelada no padrão Single-Table Design: PK = "CONTA#123" e SK = "DATA#2026-06-10". Isso permitiu à API recuperar meses de extratos de um usuário específico em menos de 8ms de forma consistente.
  2. Core Bancário para Aurora Serverless v2:
    A tabela de "Balanços" precisava obrigatoriamente de bloqueio de linha rigoroso (Locks ACID) para evitar fraudes em transações financeiras. Por isso, a tabela relacional foi migrada para o Amazon Aurora Serverless v2. Assim, o banco transacional pode escalar a sua CPU verticalmente (Adição de ACUs em milissegundos) durante o horário comercial e decair à noite, economizando orçamento e garantindo performance isolada do Extrato.
  3. Migração Zero-Downtime usando AWS DMS (Change Data Capture):
    Para evitar queda dos serviços bancários, a migração foi feita usando o AWS Database Migration Service (DMS). O DMS realizou o Full Load (cópia massiva) dos dados originais para os dois novos destinos. Em seguida, ele assumiu a função de CDC (Change Data Capture), lendo o binlog do MySQL originário em tempo real e aplicando as alterações instantaneamente tanto no DynamoDB quanto no Aurora. Após o Lag do DMS chegar a zero, a equipe de engenharia alterou as rotas DNS na API do cliente, concluindo o Cut-over sem que o usuário percebesse.
Resultado de Negócio:

A latência de leitura dos extratos no aplicativo mobile despencou de 800ms para singelos 8ms, suportando dezenas de milhares de usuários simultâneos (On-Demand Capacity). O Core Bancário no Aurora Serverless ganhou fôlego absoluto e parou de emitir alarmes de Throttling de I/O. A migração foi executada em produção sob alta carga e as rotinas de Data Analytics ficaram mais rápidas na nova arquitetura nativa da AWS.
