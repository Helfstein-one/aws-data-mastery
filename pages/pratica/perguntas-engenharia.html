Questão 1 · Apache Kafka

O que provoca o "Rebalance Storm" (Tempestade de Rebalanceamento) e como resolver esse travamento no Consumer Group?

Funcionamento Interno: O rebalanceamento ocorre quando o broker coordenador do Kafka detecta que um consumidor do grupo parou de enviar sinais de vida (Heartbeats) ou demorou mais que o limite configurado (max.poll.interval.ms) para processar o lote de mensagens retornado pela chamada poll(). O broker marca a máquina como morta, revoga as partições a ela designadas e as distribui para outras máquinas. Se o atraso no processamento era devido a lentidão de banco ou volume de lote, a próxima máquina também estourará o limite ao herdar o lote pesado, gerando um loop de rebalanciamentos em cadeia (o storm).

Troubleshooting em Entrevista:
  • Sintoma: O lag cresce indefinidamente e a CPU dos consumidores oscila em picos, mas a vazão cai para quase zero.
  • Ação Corretiva: Reduza o tamanho do lote puxado configurando um valor menor em max.poll.records (ex: de 500 para 50) e aumente o tempo limite de tolerância em max.poll.interval.ms (ex: para 10 minutos). Isso dá tempo suficiente para o loop processar os registros sem ser expulso pelo Broker.
Questão 2 · Apache Spark

Como funciona fisicamente o Sort-Merge Join em relação ao Broadcast Hash Join sob o ponto de vista de rede (Shuffle)?

Funcionamento Interno: No Sort-Merge Join (SMJ), o Spark executa um shuffle completo das duas tabelas. Ele lê os dados de todos os nós, calcula o hash da chave do join e transfere os registros correspondentes pela rede para que caiam no mesmo executor. Em seguida, os dados são ordenados em memória e mesclados. É o join mais seguro para tabelas gigantes, mas gera gargalo pesado de rede (Shuffle Write/Read).

No Broadcast Hash Join (BHJ), o Spark pula completamente o shuffle. O Driver copia a tabela menor inteira, cria uma tabela hash em memória e a envia (broadcast) via rede para todos os executores que estão processando as partições da tabela gigante. O join ocorre localmente em memória sem movimentar a tabela gigante.

Cenário de Entrevista:

Você tem uma tabela Fato de Vendas (1 TB) e uma tabela Dimensão de Categoria (20 MB). Se o Spark escolher Sort-Merge por falta de estatísticas, a query demorará horas. Forçamos o Broadcast para evitar o shuffle:

from pyspark.sql.functions import broadcast

# Forçando o Broadcast da tabela pequena (dimensao)
df_final = df_fato_vendas.join(broadcast(df_dim_categoria), "id_categoria", "inner")

Ressalva de Entrevista: Cuidado para não fazer broadcast de tabelas maiores do que a memória disponível no Driver ou nos Executors, pois isso gerará erro de OutOfMemory (OOM).

Questão 3 · dbt (data build tool)

Como lidar com "Late-Arriving Data" (Dados Atrasados) em tabelas incrementais sem reprocessar o Datalake inteiro?

Problema Conceitual: Em modelos incrementais do dbt, usamos filtros para capturar apenas dados novos (ex: data_criacao > (select max(data_criacao) from this)). Se um evento que ocorreu há 5 dias chegar com atraso hoje devido a uma instabilidade no app de origem, esse filtro simples o ignorará, gerando inconsistência histórica nas métricas agregadas.

Solução via dbt (Janela de Lookback):

Configuramos uma janela de retrocesso temporal no filtro incremental. O dbt reprocessará os últimos 3 dias para capturar atrasos comuns e executará um MERGE com base nas chaves primárias:

# models/silver_sales.sql
{{ config(
    materialized='incremental',
    unique_key='id_venda',
    incremental_strategy='merge'
) }}

SELECT * FROM {{ ref('raw_sales') }}
{% if is_incremental() %}
  -- Captura dados novos E dados que chegaram atrasados nos últimos 3 dias
  WHERE data_insercao >= (SELECT DATE_ADD(max(data_insercao), -3) FROM {{ this }})
{% endif %}
Questão 6 · dbt (data build tool)

Qual a diferença prática das estratégias "timestamp" vs "check" no dbt Snapshots e como lidar com exclusões físicas de dados?

Conceito do dbt Snapshot: Usado para criar tabelas de histórico dimensional (SCD Tipo 2) a partir de tabelas mutáveis.

  • Estratégia Timestamp: O dbt monitora uma coluna de data de atualização (ex: updated_at). Se a data da origem for maior que a registrada, uma nova versão da linha é criada. É a estratégia mais performática e recomendada.
  • Estratégia Check: Usada quando a tabela de origem não possui data de modificação. O dbt compara o hash de colunas específicas (ou all) da tabela ativa contra a tabela histórica. Gera maior overhead de processamento.

Perguntado em Entrevista: E se um registro for excluído fisicamente no banco transacional (Hard Delete)?

Por padrão, o dbt Snapshot não invalida registros que sumiram da origem (mantém a linha antiga aberta sem data de fim). Para capturar exclusões físicas e fechar o histórico correspondente, configure a propriedade invalidate_hard_deletes=True no bloco de configuração do snapshot.

Questão 7 · Apache Spark

Como a memória do executor JVM do Spark é subdividida internamente e como debugar erros de OOM no User Memory vs Execution Memory?

Física da Memória Spark: A memória total (Executor JVM Heap) é subdividida em três grandes blocos controlados pelas propriedades de configuração do Spark:

  • Spark Memory (60% por padrão, via spark.memory.fraction): Subdividido dinamicamente entre Execution Memory (usado para shuffles, joins e agregações) e Storage Memory (usado para caching/persistence e transmissão de variáveis de broadcast).
  • User Memory (40% restante): Reservado para estruturas de dados do próprio usuário em código PySpark (UDFs Python, metadados internos de partições do Spark).
  • Reserved Memory: 300 MB fixos do Spark para garantir a execução estável do motor interno.

Caso de Debug em Processo Seletivo:

Se você receber OOM no User Memory, a causa provável é o uso de Python UDFs pesados sem otimização ou tentativa de processar metadados gigantes no driver. Resolva migrando UDFs Python puras para funções nativas da API DataFrame do Spark (Spark SQL) que rodam nativamente na JVM (otimizadas pelo compilador Catalyst).

Como identificar se um erro de OutOfMemory (OOM) no Spark foi motivado por excesso de GC (Garbage Collection Overhead) ou por Disk Spill inadequado, e como ajustar os limites de memória Off-Heap?

Estrutura de Gerenciamento da JVM: Quando o Spark executa shuffles ou joins de dados com desbalanceamento (skew), os executores podem falhar por OOM. Se o erro for `GC overhead limit exceeded`, significa que a JVM gastou mais de 98% do tempo executando o Garbage Collector e liberou menos de 2% de memória Heap.

Questão 20 · Qualidade de Dados & Glue DQ

Como desenhar um mecanismo de "Circuit Breaker" de Qualidade de Dados na AWS usando o AWS Glue Data Quality e regras DQDL?

Data Quality como Proteção: Consumir dados errados ou corrompidos em relatórios e dashboards gera desconfiança nos negócios. A melhor estratégia é rodar regras de integridade diretamente nos estágios de ingestão e, caso as regras falhem, acionar um **disjuntor (Circuit Breaker)** que interrompe o fluxo de dados para as camadas finais e isola os dados ruins para investigação.

Uso do AWS Glue Data Quality (DQDL): A linguagem de definição de qualidade do Glue permite criar regras declarativas e de fácil leitura para avaliar seus Data Frames. Um exemplo de arquivo declarativo DQDL:

Rules = [
  RowCount between 1000 and 2000000,
  Completeness "user_id" = 1.0,
  Completeness "email" > 0.95,
  IsUnique "user_id",
  ColumnDataType "created_at" = "Timestamp",
  ColumnValues "status" in ["ATIVO", "INATIVO", "PENDENTE"]
]
Fluxo e Arquitetura do Circuit Breaker:
  1. O Job do **AWS Glue** ou **PySpark** lê os dados da camada Bronze e executa a verificação declarada na regra DQDL usando a biblioteca nativa do Glue.
  2. A avaliação retorna um score de sucesso (ex: 85% das regras passaram, mas a unicidade de user_id falhou).
  3. Se o score for menor que o limite aceitável do contrato de qualidade (ex: 100% para chaves primárias e completeness), o pipeline ativa o disjuntor:
    • Grava o lote corrompido em uma pasta isolada no S3 (s3://data-quarantine-bucket/bronze-failures/) para fins de depuração.
    • Gera uma falha explícita no Job do Glue (ou levanta uma exceção no código Python), impedindo que o pipeline envie os dados para a camada Silver.
    • Publica um evento no **Amazon EventBridge**, que engatilha uma notificação integrada para o time via Slack e ativa alertas no Datadog.
Questão 28 · Apache Spark Serverless

Como o Apache Spark 3.x+ gerencia o Dynamic Allocation em arquiteturas sem servidores (Serverless) como o AWS Glue e EMR Serverless sem a necessidade do External Shuffle Service (ESS)?

Problema do Dynamic Allocation Serverless: O Dynamic Allocation (alocação dinâmica) permite ao Spark retornar executores ociosos para o cluster a fim de economizar custos e alocar novos se a fila de tasks crescer. No entanto, em clusters tradicionais (YARN), quando um executor é removido, seus dados de shuffle em disco local são apagados. Sem o **External Shuffle Service (ESS)** rodando nos nós para servir esses arquivos de shuffle salvos, o Dynamic Allocation falharia pois o Spark perderia blocos de shuffles calculados.

A Mecânica do Spark 3.x+ (Shuffle Tracking):
  • Spark Shuffle Tracking: O Spark 3.x introduziu a propriedade spark.dynamicAllocation.shuffleTracking.enabled. Quando ativa, o Spark Driver rastreia ativamente quais executores geraram quais arquivos de shuffle. Se um nó for desligado ou retirado pelo autoscaling, o executor copia ativamente seus arquivos de shuffle e dados de cache para outros nós remanescentes ativos ou para o S3 antes de se desligar, protegendo o pipeline de recalculações caras.
Questão 31 · Managed Service for Apache Flink

Sob alta taxa de ingestão de eventos no Amazon MSK, como o Managed Service for Apache Flink gerencia o estado usando o RocksDB StateBackend, quais os impactos arquiteturais do alinhamento de checkpoints sob carga pesada, e como mitigar o backpressure resultante?

Gerenciamento de Estado com RocksDB: No Managed Service for Apache Flink, o estado operacional é armazenado no RocksDBStateBackend. Diferente do backend baseado em memória heap (que pode estourar o Heap OOM da JVM), o RocksDB armazena as chaves e valores em arquivos locais estruturados em árvores LSM (Log-Structured Merge-trees) gravadas no SSD local transiente do nó. O Flink sincroniza esses arquivos assincronamente e incrementalmente com o S3 para persistência permanente.

Impacto de Checkpoint Alignment & Como Mitigar:
  • Checkpoint Alignment (Alinhamento de Checkpoints): Quando um operador Flink consome de múltiplos canais de entrada (ex: join de dois streams Kafka), o operador só inicia o checkpoint quando recebe a barreira de checkpoint (checkpoint barrier) de todos os canais de entrada. Se o Canal A estiver lento, o operador Flink bloqueia os buffers de leitura do Canal B ativo para evitar que os dados ultrapassem a barreira. Isso gera uma retenção de buffers e propaga o Backpressure upstream para os produtores do MSK.
  • Mitigação com Unaligned Checkpoints: A partir do Flink 1.11, ative os Unaligned Checkpoints configurando execution.checkpointing.unaligned: true e garanta o state.backend.incremental: true. Desta forma, as barreiras de checkpoint ultrapassam os buffers de dados em trânsito instantaneamente, sem bloqueio de canais. O Flink persiste os dados em voo (in-flight data) que estavam nos buffers diretamente no estado do checkpoint no S3, reduzindo o tempo de alinhamento a zero.
  • Tuning do RocksDB: Evite estouro de memória física alocando buffers off-heap adequados por meio de state.backend.rocksdb.memory.managed: true (gerenciamento automático de memória de bloco do RocksDB pelo Flink) e configure o parâmetro de compactação de banco local para evitar amplificação de escrita (write amplification).
Questão 32 · dbt Core & dbt Cloud no AWS Glue

Como estruturar a integração do dbt com o AWS Glue (usando o dbt-glue adapter) para executar modelos analíticos sobre o motor PySpark, e quais as melhores práticas para gerenciar modelos incrementais em tabelas Apache Iceberg sem sofrer com OOM ou corrupção de snapshots?

Mecanismo dbt-glue: O dbt Core/Cloud utiliza o conector dbt-glue para compilar queries SQL escritas em Jinja e transformá-las em blocos de execução Spark SQL. O dbt se conecta ao AWS Glue através de Interactive Sessions (Sessões Interativas baseadas em Jupyter Notebook Kernel) ou submetendo tarefas transientes de Glue Jobs. O Glue interpreta as tabelas físicas mapeadas no AWS Glue Data Catalog.

Estratégias de Modelos Incrementais & Evolução de Schema no Iceberg:
  • Estratégias de Carga Incremental: Ao atualizar dados em tabelas Iceberg usando dbt incremental, utilize incremental_strategy='merge' em vez de append. A estratégia merge executa um UPSERT lógico no Iceberg baseado em chaves exclusivas. O Iceberg gerencia isso de forma nativa por meio de **Merge-on-Read (MoR)** (gravação rápida escrevendo arquivos de exclusão) ou **Copy-on-Write (CoW)** (reescrevendo os arquivos afetados no S3). Para tabelas de escrita massiva, prefira MoR para evitar lentidão no commit Spark.
  • Gestão de DDL Drift: Ative a propriedade do dbt on_schema_change='sync_all_columns'. Graças à flexibilidade de metadados do Apache Iceberg, adicionar ou remover colunas ocorre sem a necessidade de reescrever arquivos Parquet históricos no S3. O Iceberg apenas atualiza o esquema no JSON de metadados da tabela, sincronizando com o Glue Catalog de forma instantânea.
  • Prevenção de OOM no Driver: Evite carregar grandes volumes de dados de logs no driver dbt/Glue executando operações que envolvam collect (como dbt_utils.get_column_values). Limite as transações executando compactação de dados (OPTIMIZE) de forma desacoplada do fluxo de execução do dbt para evitar concorrência no metadados do Iceberg.
Questão 33 · AWS Glue Schema Registry & Streaming

Como o AWS Glue Schema Registry assegura a integridade de esquemas estruturados em tempo real de mensagens consumidas do Amazon MSK, quais são as diferenças práticas entre os modos de evolução de schema, e como tratar registros corrompidos sem derrubar o pipeline?

Validação de Esquemas no Fluxo de Ingestão: O AWS Glue Schema Registry armazena e versiona esquemas em formatos de dados comuns (Avro, JSON Schema, Protobuf). Quando um produtor escreve dados no Amazon MSK, o serializador do SDK do Schema Registry consulta o registro central. O SDK valida o payload localmente contra a estrutura de versão ativa e insere um **Schema Version ID único de 16 bytes** no início da mensagem binária publicada no Kafka, eliminando a necessidade de trafegar metadados longos em cada registro.

Tradeoffs de Evolução & Tratamento de Erros:
  • Modos de Evolução de Schema:
    • BACKWARD (Padrão): Os consumidores novos podem ler dados antigos. Permite adicionar colunas opcionais ou remover colunas com valores padrão. Garante estabilidade nos leitores analíticos.
    • FORWARD: Os consumidores antigos conseguem ler os dados gerados com os schemas novos. Excelente quando você tem APIs legadas consumindo o stream.
    • FULL: Compatibilidade total de leitura e escrita. Novas versões aceitam leitores antigos e novos, e vice-versa. Regra mais restritiva de evolução.
  • Desvio para Dead Letter Queue (DLQ): Se um produtor desatualizado enviar um payload inválido, o desserializador Java/Scala do Glue Streaming ou Lambda falhará em tempo de execução ao tentar descriptografar o Schema Version ID. Capture essas exceções de decodificação em blocos try/except (como SchemaNotFoundException ou SerializationException), capture o payload binário bruto e direcione-o assincronamente para um bucket S3 de Quarentena (DLQ) ou tópico Kafka secundário de falhas, disparando alertas no EventBridge sem interromper o pipeline principal.
Questão 46 · FinOps & AWS Glue Tuning

Como a escolha errada de tipo de Worker do AWS Glue (Standard vs G.1X vs G.2X) combinada com desbalanceamento de dados (Data Skew) gera desperdício orçamentário drástico e como mitigar isso em produção?

tradeoffs e Custos de DPU: Workers do Glue cobram por DPU-hora ativada.

  • Worker Standard (1 DPU): Possui 16GB de RAM e 4 vCPUs. Executa até 2 tarefas concorrentes. Não recomendado para workloads pesados.
  • Worker G.1X (1 DPU): Possui 16GB de RAM e 4 vCPUs, mas roda apenas uma tarefa concorrente do Spark. Muito mais seguro para evitar OOM.
  • Worker G.2X (2 DPUs): Possui 32GB de RAM e 8 vCPUs. Indicado para transformações pesadas, ML e joins complexos.
Se o dataset possui Data Skew, um único executor do Spark processará 90% da partição de dados pesada enquanto os outros 99 executores (comprados e ativos a 2 DPUs cada) ficam ociosos aguardando o gargalo terminar. O custo continuará cobrando pelas 200 DPUs inteiras.

Ações Corretivas de FinOps:
  • Glue Auto Scaling: Habilite o Auto Scaling nativo do Glue. O gerenciador dinâmico de recursos desliga executores ociosos assim que o gargalo de shuffle ou processamento paralelo inicial é concluído, pagando apenas pelo tempo real de computação ativa.
  • Ajuste de Worker: Utilize G.1X para transformações normais e reserve G.2X apenas para jobs que de fato exigem grande quantidade de memória temporária ou disco local para operações de Sort e Spill.
Questão 51 · Flink Streaming & Backpressure

Como identificar gargalos de processamento contínuo (Backpressure) e atrasos de Watermarks que travam execuções de janelas temporais no Apache Flink?

Desafio de Streaming: No Flink, se a taxa de eventos recebida for maior que a velocidade de processamento do slot, os buffers internos enchem. Isso propaga uma lentidão upstream (Backpressure) até a fonte (ex: MSK). Adicionalmente, se dados chegarem muito atrasados, o Watermark para de avançar, impedindo a janela de fechar e disparar a query de output.

Diagnóstico e Mitigação:
  • Monitoramento de Backpressure: Acesse a UI do Flink e analise a aba Backpressure de cada operador. Operadores com status "High" estão saturados de processamento. A solução comum é aumentar o paralelismo (número de slots/TaskManagers) ou otimizar a lógica de transformação do operador lento.
  • Watermark Alignment: Em tópicos Kafka com múltiplas partições, se uma partição estiver inativa (Idle) ou muito lenta, o Watermark global (que avança baseado na partição mais lenta) ficará estagnado. Ative a propriedade watermark.alignment para sincronizar o avanço dos watermarks entre partições e defina o parâmetro de idleness para ignorar partições temporariamente inativas.
Questão 62 · AWS Glue Executor OOM Tuning

Seu job do AWS Glue (rodando com workers G.1X) está falhando com erros de JVM OOM (Java heap space) durante um estágio de parse de campos JSON complexos de alta cardinalidade. Como sintonizar o tamanho do worker, a memória e a paginação do Spark sem elevar os custos do pipeline?

Gargalo de Memória: O parsing de JSONs com estruturas variantes gera milhões de objetos de metadados na memória heap, superando os 10 GB úteis do executor G.1X.

Ajustes de Sizing & Tuning:
  • Upgrade de Worker (G.1X para G.2X): Ao migrar para G.2X, a memória disponível para o executor sobe de 10 GB para 24 GB. Como a fatura de DPU dobra, você pode reduzir a quantidade total de workers pela metade. O custo total do job se mantém estável, enquanto a RAM útil por thread Spark aumenta drasticamente, extinguindo a falha física de Heap Space.
  • Parâmetros de Ajuste da JVM: Configure spark.sql.objectHashAggregate.sortBased.fallbackThreshold = 128 para forçar o Spark a fazer agregação em disco antes de estourar a memória. Ajuste também spark.memory.fraction = 0.8 (padrão 0.6) para ceder mais espaço da JVM para armazenamento de shuffle de dados ativos.
Questão 64 · PySpark Union vs UnionByName

Qual o risco físico de utilizar o método .union() para juntar dois DataFrames em PySpark com colunas fora de ordem e como o .unionByName(allowMissingColumns=True) resolve este problema em produção?

Risco de Corrupção de Dados: O método .union() faz o empilhamento dos registros baseando-se estritamente na posição física das colunas (índice), ignorando os nomes lógicos das colunas. Se o schema do DataFrame A for [id_cliente, email] e o do DataFrame B for [email, id_cliente], o Spark mesclará o email com o ID sem acusar erro, corrompendo a tipagem lógica e o conteúdo do data lake final.

Solução de Engenharia:

Utilize df_a.unionByName(df_b, allowMissingColumns=True). Este método faz a junção baseada nos nomes de colunas. Se existirem colunas na tabela B que não constam na tabela A (ou vice-versa), o Spark criará dinamicamente as colunas ausentes em cada lado e as preencherá com valores nulos lógicos, preservando perfeitamente a semântica do schema.

Questão 68 · Spark Catalyst & Whole-Stage CodeGen

Como o Whole-Stage CodeGen do Catalyst Optimizer acelera a execução física de jobs Spark e qual o impacto de UDFs Python tradicionais na quebra deste ciclo de compilação da JVM?

Overhead do Java Clássico: A computação distribuída comum (Iterator-style) avalia registros chamando funções virtuais na pilha JVM para cada registro (ex: Filtro -> Projeção -> Agrupamento), gerando milhões de chamadas e reduzindo o uso dos registradores da CPU física.

Compilação JIT & Quebra de Pipeline:
  • Whole-Stage CodeGen: O Catalyst analisa o plano físico e colapsa múltiplos estágios de transformações em um **único loop em código Java plano**, compilando-o via Janino em tempo de execução. Isso remove todas as chamadas virtuais da JVM e permite que os dados fiquem nos registradores de alta velocidade do processador.
  • Overhead de UDFs Python puras: Uma UDF comum em Python não pode ser compilada pelo Catalyst. Ela força o Spark a extrair os dados da JVM (formato Tungsten), serializar/converter para Python através de sockets (IPC), executar a UDF na CPU do usuário linha a linha, e converter de volta para a JVM. Esse processo desativa o Whole-Stage CodeGen e gera gargalos severos de processamento e latência de rede/memória local.
Questão 72 · Replicação Cross-Account do AWS Glue Catalog

Em uma arquitetura Data Mesh corporativa, como permitir que analistas na conta de Consumo A consultem metadados e façam queries no Athena sobre tabelas hospedadas na conta de Produção B, sem replicar fisicamente os arquivos no S3 e mantendo controle granular de acesso?

Gargalo de Compartilhamento de Metadados: Duplicar pipelines ou arquivos S3 gera redundância, custos massivos de armazenamento e falhas de sincronismo. O acesso direto cross-account ao catálogo de metadados é a solução ideal.

Fluxo e Implementação:
  1. Políticas de Recursos do Glue Catalog (Glue Resource Policy): Na conta Produtora B, configure uma política de catálogo que permita acesso de leitura (glue:GetDatabase, glue:GetTable) para o ID da conta Consumidora A ou para Roles específicos da conta A.
  2. Permissões de S3 Cross-Account: A política do bucket S3 físico na conta Produtora B deve autorizar ações de leitura (s3:GetObject, s3:ListBucket) para a Role de execução do Athena/Glue na conta Consumidora A.
  3. Uso do AWS Lake Formation Cross-Account: Configure o compartilhamento via **AWS Resource Access Manager (RAM)** gerenciado pelo Lake Formation. O administrador da conta B concede permissões LF (ex: SELECT nas tags do banco) diretamente para a conta A. O administrador da conta A aceita o convite do RAM e cria um link local no Glue Catalog (Catalog Link) apontando para o banco de dados remoto da conta B. Os analistas na conta A agora consultam a tabela localmente como se pertencesse à sua própria conta.
Questão 86 · Sizing Dinâmico e Small Files (Spark)

Ao processar terabytes de dados diariamente, como você calcula dinamicamente o particionamento final antes do `.write()` para o S3, a fim de evitar OOM no cluster e combater o Small Files Problem simultaneamente?

Cenário de Desastre: Um engenheiro hardcodou `df.repartition(100)` no final do pipeline. No Natal, a volumetria multiplicou por dez e as partições ficaram com 3GB cada, estourando a RAM dos executores (OOM). Em domingos, a volumetria cai, gerando 100 arquivos de 5KB (Small Files) destruindo a latência do Athena.

A Solução (Matemática Dinâmica no Write):
  • Auto Sizing via Motor: Em versões modernas (EMR 6.x), a maneira mais segura de evitar OOM em partições é delegar o corte ao Catalyst definindo spark.sql.files.maxRecordsPerFile. O arquivo Parquet será "fechado" e salvo ao atingir o limite, independentemente do volume em memória.
  • Heurística de Bytes (Código): O arquiteto extrai um df.count() final (idealmente após um cache/checkpoint) e multiplica por um peso fixo em bytes (tamanho estimado de uma linha serializada). Divide-se o total pela constante alvo (ex: 128 MB).
  • Invocação: O pipeline então invoca df.repartition(calculo_dinamico).write(). A volumetria elástica garante arquivos sempre na faixa de 128-256MB perfeitamente otimizados para Amazon S3.
Questão 87 · Tradeoffs de Coalesce (Spark)

Por que utilizar `.coalesce()` em vez de `.repartition()` imediatamente após a leitura (read) ou de um filtro pesado no Spark pode destruir a performance do seu cluster inteiro, apesar de não realizar shuffle na rede?

Cenário do Erro: Um desenvolvedor lê uma tabela de 5 TB distribuída em 2000 arquivos (2000 tarefas paralelas). Como ele quer gerar apenas 10 arquivos no final do job, ele adiciona `df.coalesce(10)` logo após o filtro inicial, achando que está otimizando o I/O.

A Destruição do Paralelismo (Pushdown/Narrow Deps):
  • Sem Shuffle = Agrupamento Forçado na Origem: O coalesce() não recria partições via rede, ele funde as partições nativas atuais. O Catalyst optimizer do Spark "puxa" essa fundição para o início da árvore de execução.
  • O Gargalo Imediato: Ao forçar 10 partições físicas na memória, o cluster de 100 nós só terá trabalho para 10 slots de CPU. Os outros 90 nós ficarão ociosos durante todo o processamento subsequente (transformações). O job demora dias para rodar.
  • A Abordagem Correta: Use repartition() se precisar aumentar o paralelismo. O coalesce() deve ser usado de forma microscópica apenas imediatamente antes do comando de escrita (`.write()`), sem transformações intermediárias entre eles.
Questão 88 · Sort-Merge Join e Spill to Disk (Spark)

Durante um Join pesado entre duas tabelas de bilhões de linhas, o Spark UI mostra que várias tasks demoraram muito mais que a mediana e registraram volumes altíssimos de "Spill (Memory)" e "Spill (Disk)". O que causa isso e como a arquitetura moderna (AQE) mitiga o problema?

Cenário: O tempo do Sort-Merge Join disparou e os logs mostram Spilling in-memory map of 30.5 GB to disk, forçando a instabilidade do EMR devido à exaustão de IOPs no EBS.

Diagnóstico e Ação via AQE:
  • A Causa Física (Buffer RAM Mapeado): No Sort-Merge Join, após o shuffle de rede, os executores recebem os dados de chaves idênticas e precisam alocá-los em memória (Execution Memory) para realizar o Sort. Se o tamanho da partição recebida for maior que o buffer da JVM, o motor serializa o excesso e joga no disco local do nó (Spill). Como disco EBS é ordens de grandeza mais lento que a RAM, a task paralisa.
  • O Problema da Configuração Estática: Historicamente, os desenvolvedores tentavam mitigar isso chutando valores mais altos no spark.sql.shuffle.partitions (ex: mudando do default 200 para 2000), o que diminuía o tamanho do pedaço e evitava o spill. Porém, se os dados tivessem Data Skew (assimetria da chave do negócio), uma das partições continuaria gigante e spillando, enquanto as outras 1999 ficariam vazias.
  • O Remédio (Adaptive Query Execution): Ativando o AQE (spark.sql.adaptive.enabled=true e spark.sql.adaptive.skewJoin.enabled=true), o Catalyst detecta o skew em runtime. Ao ver uma partição que causará Spill, o Spark a divide proativamente em sub-partições menores e as entrega a executores separados para join particionado, impedindo o OOM sem precisar adivinhar o shuffle.partitions ideal.
Questão 92 · Kinesis, KCL e Falha Oculta no DynamoDB

Uma aplicação consumidora Kinesis parou misteriosamente de avançar a leitura dos eventos, apesar das métricas do Kinesis Stream mostrarem que os Shards estão normais e a Lambda/EC2 do consumidor ter CPU e RAM ociosas. O que falhou no background e por quê?

Cenário: Um engenheiro escalou o Kinesis de 20 para 300 shards após o lançamento de uma campanha de marketing global, porém as métricas de leitura pararam de subir.

DYNAMODB LEASE TABLE THROTTLING (KCL)
Diagnóstico e Ação (Dependência Invertida KCL):
  • A Causa Física (State Backend estrangulado): A Kinesis Client Library (KCL) tenta ser resiliente distribuindo o estado de quem leu qual offset (checkpoint) numa tabela gerenciada do DynamoDB (criada implicitamente sob o mesmo nome da aplicação). Ao escalar para 300 shards bruscamente, as centenas de threads de workers começaram a bombardear essa tabela oculta com chamadas UpdateItem contínuas para gravar os novos offsets de cada micro-batch.
  • O Gargalo: A tabela do DynamoDB provavelmente foi criada com Provisionamento Padrão de baixa capacidade (ex: 10 WCU). A AWS então lançou ProvisionedThroughputExceededException, impedindo a KCL de salvar o offset lido. Se o consumidor não pode salvar o estado, ele entra em modo de bloqueio para não ler dados que ele não poderá confirmar (Exactly-Once).
  • A Mitigação: Alterar as configurações da tabela da KCL no DynamoDB para o modo de cobrança On-Demand (Pay-Per-Request), permitindo que a KCL faça escritas de forma ilimitada durante picos e escale o throughput automaticamente para infinitos WCU instantaneamente.
Questão 93 · Spark Structured Streaming e Exaustão de RAM (OOM)

Em um pipeline stateful que conta visitantes únicos a cada 1 hora de evento, o Spark vêm sofrendo quedas crônicas de Out Of Memory (OOM) após 3 dias rodando ininterruptamente. O que a falta da cláusula `.withWatermark()` provoca fisicamente no executor?

Cenário: Os desenvolvedores configuraram uma janela (Window Aggregation) no DataFrame, mas removeram a instrução de Watermark por acharem "complexa demais", com a justificativa de que confiam nos timestamps dos eventos enviados pelos celulares.

Diagnóstico e Ação (GC e Evicção de Estado):
  • A Causa Física (Crescimento Infinito de Estado): O Spark não sabe se um celular que perdeu sinal no domingo vai mandar os logs na quarta-feira ("Late-arriving data"). Por padrão, sem uma restrição, o Spark nunca desliga o estado das agregações. Ele mantém na RAM dos executores (e no RocksDB state store) a janela de todas as horas dos últimos 3 dias "abertas e prontas para receber atualizações". Com milhões de eventos rodando, esse estado global inevitavelmente satura a heap da JVM, falhando o processo.
  • A Mitigação Estrutural (Watermark Eviction): Ao adicionar .withWatermark("event_time", "2 hours"), o Spark descobre o Global Event Time (a hora do evento mais novo que ele já processou). Ele subtrai 2 horas desse pico e apaga cirurgicamente (evicção) da memória RAM todas as tabelas de estado (janelas) mais velhas que esse limite. Se um evento atrasado tentar chegar fora dessa tolerância (ex: 3 horas de atraso), o Spark o descarta imediatamente. O watermark transforma um consumo infinito de memória em um processamento matematicamente estável e limitado.
Questão 94 · EKS & Apache Spark e Troubleshooting de OOMKilled (Staff Level)

Durante o processamento de um DataFrame no Amazon EKS usando Spark Operator, o Pod do Executor foi abruptamente encerrado pelo Kubernetes com o status 'OOMKilled'. Curiosamente, o Spark UI não reportou falta de memória JVM (heap limit estourado). Qual é o motivo exato de um 'OOMKilled' sem esgotamento de Heap e como você estrutura os recursos de container para mitigar isso?

Cenário: O engenheiro configurou `spark.executor.memory="12g"`. O nó EC2 do K8s tinha bastante memória livre, mas o container falhou misteriosamente antes da heap JVM de 12GB encher.

Diagnóstico e Ação (Memory Overhead e Limites K8s):
  • A Causa Física (Cgroups e Out-of-Heap Memory): O OOMKilled é um sinal do subsistema cgroups do Linux, não da JVM. Quando definimos spark.executor.memory="12g", estamos restringindo apenas a Heap do Java. O Spark frequentemente exige memória adicional (Off-Heap) para operações nativas (como a serialização de PyArrow no PySpark, buffers de rede Netty, alocações diretas de ByteBuffer NIO e buffers de SO). Se o Pod no EKS recebeu um límite estrito (resources.limits.memory="13g"), mas o somatório da Heap + Off-Heap ultrapassar esse valor imposto pelo K8s, o OOM Killer do kernel Linux destrói brutalmente o processo (Sinal SIGKILL 139) sem que o Spark UI perceba, pois não houve OutOfMemoryError na heap Java.
  • A Mitigação Estrutural (Ajuste do Overhead): Para clusters EKS densos, a solução é ajustar o spark.executor.memoryOverhead (o padrão é apenas 10% da executor memory ou 384MB). Se o Job usar muito PySpark UDFs ou buffers de shuffle em C++, deve-se aumentar explicitamente o overhead (ex: spark.executor.memoryOverhead="4g"). Além disso, garantir que o YAML de submissão do K8s tenha limits.memory grande o suficiente para acomodar o cálculo de: Heap + Overhead + Off-Heap, evitando guilhotina do Kernel.

Questão 95 · Transparência em Incidentes de Dados

Conte-me sobre uma vez em que um pipeline que você construiu corrompeu dados em produção. Como você descobriu o erro, como conteve o problema e como reportou à área de negócios?

Questão 96 · Negociação com Engenharia de Software (Backend)
