Infraestrutura, Redes & Segurança

Event-Driven & Mensageria

Desenvolvendo arquiteturas desacopladas e escaláveis. Domine Filas (SQS), Pub/Sub (SNS) e Barramentos de Eventos (EventBridge) para pipelines de dados assíncronos e resilientes.

01

Padrão Pub/Sub & Fan-out com SNS e SQS

Dilema: Como entregar o mesmo evento para múltiplos consumidores independentes?

A arquitetura moderna exige Desacoplamento. Quando um arquivo entra no S3, você não pode criar uma Lambda gigantesca que extrai OCR, gera PDF e atualiza o Banco ao mesmo tempo (isso gera falha em cascata). A solução é o Padrão Fan-out: O S3 notifica um Tópico SNS (Pub/Sub), que "espalha" o evento paralelamente para múltiplas Filas SQS (Queues).

ARQUITETURA DE DADOS: FAN-OUT COM SNS MESSAGE FILTERING

Legenda do Diagrama

  • SNS Topic: Atua como Roteador (Pub/Sub). O S3 aciona o tópico passando atributos na mensagem (ex: type=csv).
  • Filas SQS: Estão inscritas (Subscribed) no SNS. Usam FilterPolicy para só receber mensagens relevantes.
  • Workers: Lambda e ECS consomem o SQS específico com segurança, sem sobrecarga de validação.
Terraform: SNS Fanout com FilterPolicy 
# 1. Cria a Fila SQS e o Tópico SNS
resource "aws_sqs_queue" "csv_loader_queue" { name = "csv-loader-queue" }
resource "aws_sns_topic" "event_upload" { name = "s3-event-upload" }

# 2. Inscreve a Fila no SNS aplicando a Regra de Filtragem!
resource "aws_sns_topic_subscription" "csv_sqs_target" {
  topic_arn = aws_sns_topic.event_upload.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.csv_loader_queue.arn

  # A Mágica da Economia: Filter Policy
  filter_policy = jsonencode({
    type = ["csv"]
  })
}
💡
SNS Message Filtering (A arte da economia)

O SNS não precisa mandar cópia de TUDO para TODAS as filas SQS. Nós usamos a FilterPolicy no SNS. Se o S3 envia um JSON onde "type": "pdf", apenas a Fila de OCR receberá a mensagem. Isso economiza dinheiro de SQS e ciclos de processamento de Lambda, pois a filtragem ocorre no roteador (SNS) e não no código da aplicação!

02

Ciclo de Vida do SQS: Visibility Timeout & DLQ

Dilema: O que acontece se o Worker "crashar" no meio do processamento?

Ao contrário de um Barramento (EventBridge) que apenas "chuta" o evento pra frente, a Fila SQS guarda o estado do evento. Quando um Worker (Lambda, ECS) lê a mensagem (API ReceiveMessage), ela não é deletada! Ela fica invisível para outros workers pelo tempo do Visibility Timeout.

CICLO DE VIDA DA MENSAGEM: FALHAS E DEAD LETTER QUEUE (DLQ)

Legenda do Diagrama

  • Zonda de Invisibilidade: Tempo em que a Lambda tem posse da mensagem. Nenhuma outra Lambda pode vê-la.
  • Falha (Crash): Se a Lambda não rodar DeleteMessage antes do timeout acabar, a invisibilidade expira.
  • DLQ Route: Após falhar 3 vezes (maxReceiveCount), a AWS remove automaticamente a mensagem para a DLQ.
Terraform: SQS com Dead Letter Queue 
# 1. Cria a DLQ (Fila de Rejeição)
resource "aws_sqs_queue" "dlq" {
  name = "worker-dlq"
}

# 2. Cria a Fila Principal vinculada à DLQ
resource "aws_sqs_queue" "main_queue" {
  name                       = "worker-queue"
  visibility_timeout_seconds = 30 # Tempo de Invisibilidade

  # Redrive Policy: Configura a DLQ e o limite de falhas
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.dlq.arn
    maxReceiveCount     = 3
  })
}

Dilemas Clássicos e Soluções

  • A "Poison Pill" (Pílula de Veneno): Se uma mensagem com JSON quebrado entrar na fila, a Lambda lerá, dará erro no código e não chamará DeleteMessage. Após os 30s de Visibility Timeout, a mensagem volta à fila. Isso gerará um loop infinito de consumo e cobrança.

    Solução: Configurar uma DLQ (Dead Letter Queue) no SQS principal com maxReceiveCount = 3. Após 3 tentativas frustradas, a AWS remove a mensagem da fila primária e a guarda na DLQ para auditoria humana, salvando o sistema.

  • Processamento Longo & Duplicidade: Sua Lambda demora 45s processando um vídeo longo, mas seu SQS Visibility Timeout está em 30s. Antes da Lambda terminar e apagar a mensagem, ela reaparece na fila e UMA SEGUNDA LAMBDA pega a mesma tarefa!

    Solução: O Visibility Timeout sempre deve ser no mínimo 6 vezes maior que o Timeout da Lambda. Se a Lambda pode durar 1 min, o Visibility Timeout da fila deve ser 6 minutos. Além disso, no código da Lambda, chame a API ChangeMessageVisibility para pedir mais tempo caso note que vai demorar.
03

Integrações, Triggers e Configurações Letais

EventSourceMapping e as Configurações de Faturamento

SQS como Trigger de Lambda

O SQS não "chama" a Lambda (Push). A AWS usa um serviço interno oculto chamado EventSourceMapping que fica fazendo Polling (Pull) na sua fila. Configurações chaves:

  • BatchSize: (Padrão 10). Em vez de acionar a Lambda 10 vezes, manda as 10 mensagens num array (economiza R$).
  • MaximumBatchingWindowInSeconds: Espera até 5 minutos para encher o Batch antes de invocar a Lambda.

Polling: O Custo Invisível

Fazer Polling contínuo em uma fila SQS vazia (Short Polling) custa muito caro. O ReceiveMessageWaitTimeSeconds deve ser sempre setado para 20 Segundos (Long Polling).

No Long Polling, se a fila está vazia, a conexão HTTP não é fechada imediatamente. Ela fica pendurada na nuvem por 20s. Se chegar uma mensagem no segundo 15, ele devolve e fecha. Isso derruba as requisições faturadas da API SQS em mais de 90%.

04

Limites Matemáticos & A Batalha FIFO vs Standard

Onde o SQS quebra e como lidar com a ordem estrita

Característica / Limite SQS Standard SQS FIFO (First-In, First-Out)
Throughput (TPS) Ilimitado (Scale to Infinity) Limitado a 300 msg/s (Até 3.000 em High Throughput Mode)
Ordenação Best-effort (A ordem não é garantida de chegada). Garantia Absoluta na Ordem (Ideal para Event Sourcing de Contas Bancárias).
Entrega (Delivery) At-Least-Once (Pode ocorrer duplicação de mensagens!) Exactly-Once (Duplicação resolvida pela AWS).
MessageGroupId (Dilema) Não se aplica. Todas as mensagens com o mesmo MessageGroupId (ex: ID da Conta Corrente) ficam "trancadas" sequencialmente para que uma não processe antes da outra no Worker.
Tamanho do Payload Max 256 KB. Max 256 KB. Para arquivos de 10MB, deve-se usar o Padrão Claim-Check (S3 URL).

Plataforma Enterprise: Barramento Global

EventBridge como Sistema Nervoso Central

Apesar do SNS ser ótimo para Fan-out simples de um tópico, as corporações adotaram o Amazon EventBridge (evolução do CloudWatch Events) como Barramento (Bus) da plataforma inteira. Nele, todos os SaaS (Zendesk, Datadog), ERPs e Microserviços jogam eventos no Bus central. O EventBridge usa Content Filtering Avançado (Lendo as variáveis internas do Payload JSON) para criar regras de roteamento massivas sem limite de tópicos.

EVENTBRIDGE ENTERPRISE HUB ARCHITECTURE

Legenda do Diagrama

  • Produtores: Sistemas (ERPs, SaaS) enviam eventos no formato padrão (EventBridge Schema) para o Bus Central.
  • Regras (Rules): Analisam o Content Payload JSON para rotear os eventos massivamente.
  • Targets: EventBridge encaminha (Push) para SQS, SNS ou Kinesis Firehose baseado no matching da regra.
Terraform: EventBridge Content Filtering 
resource "aws_cloudwatch_event_rule" "high_value_br_orders" {
  name        = "capture-br-high-value"
  description = "EventBridge: Filtro de Conteúdo JSON Complexo"
  
  # Lógica de Roteamento baseada no valor dos campos JSON!
  event_pattern = jsonencode({
    "source": ["com.ecommerce.orders"],
    "detail-type": ["OrderCreated"],
    "detail": {
      "country": ["BR"],
      "amount": [{ "numeric": [">", 500] }]
    }
  })
}
🔥
O Dilema da Idempotência Crítica no Standard!

Lembra que o SQS Standard entrega as mensagens "Pelo menos uma vez"? Se um consumidor processa uma venda no banco de dados e morre antes de dar o DeleteMessage, outra máquina processará a venda novamente! A arquitetura exige que todo Worker consumindo SQS Standard seja Idempotente. Usamos uma Tabela de Deduplicação no DynamoDB, gravando o MessageID com a instrução ConditionExpression: attribute_not_exists(PK) para garantir que a mesma transação nunca ocorra duas vezes (Mutação Condicional SQL-less).
