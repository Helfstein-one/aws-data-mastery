Arquitetura de Dados

Guia exaustivo de padrões arquiteturais modernos, mensageria distribuída, triggers dirigidos a eventos, orquestração corporativa e governança de grão fino na nuvem AWS.

01

Os 7 Pilares de uma Arquitetura de Dados Moderna

Diretrizes fundamentais para estruturação de projetos analíticos robustos e resilientes

Pilar 1

Decoupled Storage & Compute

Separação física completa entre a computação (EMR, Athena, Glue) e o armazenamento (Amazon S3). Permite desligar ou escalar máquinas de processamento sem riscos aos dados persistidos.

Pilar 2

Idempotência & Replayability

Todos os jobs devem ser projetados para rodar múltiplas vezes para o mesmo período sem gerar dados duplicados. O reprocessamento deve ser uma operação nativa e segura.

Pilar 3

Governança Fina (Least Privilege)

Acesso lógico centralizado por schemas, tabelas, colunas e linhas (AWS Lake Formation) ao invés de políticas brutas e desorganizadas em buckets S3.

Pilar 4

Observabilidade Ativa

Coleta em tempo real de throughput, latências, taxas de erro e consumo de hardware (YARN/JVM). Alertas automatizados antes que falhas impactem os consumidores.

Pilar 5

Custo-eficiência Nativo

Combinação estratégica de instâncias EC2 Spot transientes para processamento secundário, compressões Parquet ZSTD e S3 Intelligent-Tiering.

Pilar 6

Qualidade Declarativa

Garantia de integridade do dado na transição entre camadas Bronze, Silver e Gold por meio de ferramentas automáticas de validação de schemas (Glue Data Quality, Great Expectations).

Pilar 7

Infraestrutura como Código (IaC)

Toda a infraestrutura, permissões IAM, bancos e tabelas externas catalogadas criadas via scripts declarativos (Terraform/CDK), eliminando intervenções manuais.

02

Padrões de Mensageria e Event-Driven (SQS & SNS)

Comunicação assíncrona desacoplada, tratamento de falhas, padrões avançados e infraestrutura como código (Terraform)

A mensageria assíncrona é a espinha dorsal de sistemas distribuídos modernos. Ela substitui chamadas diretas síncronas HTTP (que causam acoplamento forte e falhas em cascata) por filas e tópicos intermediários. Na AWS, os serviços nativos fundamentais para essa arquitetura são o **Amazon SQS** e o **Amazon SNS**.

Publish-Subscribe (Pub-Sub) - Amazon SNS

Distribuição 1-para-N (Broadcast)

O produtor publica a mensagem em um Tópico SNS. Múltiplos consumidores (filas SQS, Lambdas, Webhooks, endpoints HTTPS) assinam esse tópico e recebem uma cópia independente de cada mensagem. Ideal para espalhar eventos de negócios comuns (ex: "venda_concluida") para múltiplos domínios analíticos independentes.

Point-to-Point (Queue) - Amazon SQS

Processamento 1-para-1 (Buffer & Escalabilidade)

O produtor envia a mensagem para uma Fila SQS. Apenas um único consumidor processa cada mensagem por vez. Quando o processamento termina com sucesso, o consumidor exclui a mensagem da fila. Se o consumidor falhar, a mensagem retorna à fila após o período de visibilidade. Ideal para amortecer picos de carga (Throttling) e desacoplar escrita em bancos relacionais.

Internals e Dimensionamento Crítico do Amazon SQS

  • Standard vs FIFO Queues:
    • Standard: Taxa de transferência virtualmente ilimitada. Oferece entrega *at-least-once* (pelo menos uma vez, podendo haver duplicidade) e ordenação por *best-effort* (sem garantia estrita).
    • FIFO (First-In-First-Out): Limite de até 3.000 mensagens/segundo com batching (ou mais usando high throughput mode). Garante entrega *exactly-once* (exatamente uma vez no nível da fila) e ordenação estrita. Exige a definição de MessageGroupId (para ordenar grupos de mensagens) e MessageDeduplicationId (ou deduplicação baseada em hash do conteúdo).
  • Visibility Timeout (Tempo de Visibilidade): Quando um consumidor lê uma mensagem da fila, ela permanece fisicamente na fila mas fica "invisível" para outros consumidores por este intervalo de tempo.
    Regra de Sizing Fundamental: O Visibility Timeout deve ser configurado para no mínimo 6 vezes o tempo de execução máximo esperado do seu consumidor (ex: se o Lambda demora até 10 segundos para processar um lote, o Visibility Timeout deve ser de pelo menos 60 segundos). Caso contrário, a mensagem voltará a ficar visível antes de o processamento acabar, gerando duplicidade extrema e concorrência na gravação dos mesmos dados.
  • Short Polling vs Long Polling:
    • Short Polling: O SQS consulta apenas um subconjunto de seus servidores físicos de fila e retorna imediatamente, mesmo vazia. Aumenta drasticamente o número de requests cobrados.
    • Long Polling (Padrão Recomendado): O SQS espera até que uma mensagem chegue ou o timeout expire (máximo de 20 segundos) antes de responder. **Reduz custos operacionais e requisições vazias a zero.**

O Padrão Claim Check (Contornando o Limite de 256 KB)

O limite físico máximo de payload para mensagens do SQS e do SNS é de **256 KB**. Quando pipelines de dados precisam trafegar registros volumosos (ex: grandes objetos JSON ou metadados de arquivos analíticos), aplicamos o **Claim Check Pattern**:

Passo Entidade Produtora Transporte (SQS) Entidade Consumidora
Ação Grava o payload bruto pesado no bucket **S3** (camada temporária ou raw). Envia uma mensagem curta para o SQS contendo o Bucket Name e o Object Key (URI). Lê a mensagem curta da fila, usa as coordenadas para baixar o payload direto do **S3** e executa o processamento.
Implementação PySpark/Python: Consumidor Claim Check

Abaixo está o script executado em uma task do ECS Fargate ou no Spark para resolver o payload utilizando Claim Check:

import json
import boto3

s3_client = boto3.client('s3')

def process_sqs_message_claim_check(sqs_record):
    # 1. Parse da mensagem curta da fila SQS
    message_body = json.loads(sqs_record['body'])
    
    # 2. Verifica se a mensagem contém as referências do S3 (Claim Check)
    if 's3_bucket' in message_body and 's3_key' in message_body:
        bucket = message_body['s3_bucket']
        key = message_body['s3_key']
        
        # 3. Baixa o payload pesado diretamente do S3
        print(f"Baixando payload pesado de s3://{bucket}/{key}")
        s3_object = s3_client.get_object(Bucket=bucket, Key=key)
        payload_data = json.loads(s3_object['Body'].read().decode('utf-8'))
        
        # 4. Processa os dados pesados
        execute_data_processing(payload_data)
        
        # Opcional: deletar o arquivo temporário do S3 após processamento bem-sucedido
        # s3_client.delete_object(Bucket=bucket, Key=key)
    else:
        # Processamento comum para payloads menores de 256 KB
        execute_data_processing(message_body)

def execute_data_processing(data):
    print(f"Processando registros: {len(data)}")

Infraestrutura como Código (Terraform)

Abaixo está a implementação IaC completa de um padrão **Fan-out** resiliente contendo um Tópico SNS associado a uma fila SQS FIFO com Dead Letter Queue (DLQ), encriptação via chaves KMS e política de filtragem de atributos.

# 1. Chave KMS para Encriptação de Mensagens (Repouso)
resource "aws_kms_key" "sns_sqs_key" {
  description             = "Chave KMS para encriptar topicos e filas de dados"
  deletion_window_in_days = 7
  enable_key_rotation     = true
}

# 2. Topico SNS FIFO de Origem
resource "aws_sns_topic" "data_events_topic" {
  name                        = "vendas-events.fifo"
  fifo_topic                  = true
  content_based_deduplication = true
  kms_master_key_id           = aws_kms_key.sns_sqs_key.arn
}

# 3. Fila SQS FIFO Secundária (Dead Letter Queue)
resource "aws_sqs_queue" "analytics_dlq" {
  name                        = "analytics-processing-dlq.fifo"
  fifo_queue                  = true
  kms_master_key_id           = aws_kms_key.sns_sqs_key.arn
  message_retention_seconds   = 1209600 # Retém por 14 dias para auditoria
}

# 4. Fila SQS FIFO Principal (Consumer de Ingestão)
resource "aws_sqs_queue" "analytics_queue" {
  name                        = "analytics-processing-queue.fifo"
  fifo_queue                  = true
  kms_master_key_id           = aws_kms_key.sns_sqs_key.arn
  visibility_timeout_seconds  = 180 # 3 minutos (compatível com Lambda/Glue rápidos)
  message_retention_seconds   = 345600 # 4 dias

  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.analytics_dlq.arn
    maxReceiveCount     = 3 # Move para DLQ após 3 falhas de processamento
  })
}

# 5. Permissão para o SNS Enviar Mensagens para o SQS
resource "aws_sqs_queue_policy" "analytics_queue_policy" {
  queue_url = aws_sqs_queue.analytics_queue.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid       = "AllowSNSSend"
        Effect    = "Allow"
        Principal = "*"
        Action    = "sqs:SendMessage"
        Resource  = aws_sqs_queue.analytics_queue.arn
        Condition = {
          ArnEquals = {
            "aws:SourceArn" = aws_sns_topic.data_events_topic.arn
          }
        }
      }
    ]
  })
}

# 6. Assinatura do Tópico SNS direcionando para a Fila SQS com Message Filtering
resource "aws_sns_topic_subscription" "sns_to_sqs_subscription" {
  topic_arn = aws_sns_topic.data_events_topic.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.analytics_queue.arn

  # Apenas envia para esta fila se o evento for do domínio 'faturamento' ou 'vendas_online'
  filter_policy = jsonencode({
    domain = ["faturamento", "vendas_online"]
    source = [{"anything-but" : "legacy_system"}]
  })
}
Resiliência de Batching em Consumidores Lambda / ECS:
Para evitar reprocessar todas as mensagens corretas de um lote (batch) quando apenas uma mensagem falha, ative a opção ReportBatchItemFailures no gatilho do SQS. No retorno da sua função, envie um JSON contendo o array batchItemFailures com os IDs das mensagens específicas que deram erro. O SQS as manterá na fila principal para nova tentativa e removerá as mensagens bem-sucedidas imediatamente.

Amazon EventBridge e Arquiteturas Event-Driven

Disparos automatizados baseados em eventos lógicos, roteamento cross-account e agendamentos serverless globais

Pipelines analíticos eficientes não rodam em agendamentos fixos (cron jobs) se os dados originais chegam de forma contínua ou flutuante. A arquitetura **Event-Driven (orientada a eventos)** responde instantaneamente a mudanças físicas de infraestrutura ou de negócios usando o **Amazon EventBridge**.

Conceitos Chave do Amazon EventBridge

  • Barramentos de Eventos (Event Buses):
    • Default Event Bus: Recebe automaticamente todos os eventos gerados pelos próprios serviços da AWS (ex: modificações no S3, alteração de estados do EC2/ECS/Glue).
    • Custom Event Buses: Criados para receber eventos das suas próprias aplicações customizadas (ex: microsserviço no ECS publica "event_type": "pedido_pago"). Suporta barramentos centralizados e compartilhamento cross-account para centralizar auditoria de dados.
  • Regras de Roteamento (Rules) e Filtros de Padrão (Event Patterns): As regras aplicam padrões de correspondência (JSON matching) para interceptar apenas eventos específicos antes de enviá-los para um ou mais alvos (targets). 
    // Exemplo de Event Pattern para interceptar apenas arquivos Parquet criados na camada Raw do S3
{
  "source": ["aws.s3"],
  "detail-type": ["Object Created"],
  "detail": {
    "bucket": {
      "name": ["empresa-data-lake-raw"]
    },
    "object": {
      "key": [{ "suffix": ".parquet" }]
    }
  }
}
  • EventBridge Scheduler vs EventBridge Rules (Cron):
    • Rules (Cron clássica): Baseada no barramento de eventos padrão, ideal para tarefas clássicas de infraestrutura em intervalos curtos.
    • Scheduler: Um serviço altamente otimizado para agendamentos individuais de alta densidade (milhões de schedules independentes). Suporta janelas flexíveis de execução, fuso horário nativo (Timezone), controle de retentativas automáticas com Dead Letter Queue (DLQ) associada ao target, e entrega do tipo *at-least-once*.

Input Transformers: Higienização de Payloads

Muitas vezes, o evento gerado pela AWS é gigante e contém dezenas de propriedades de metadados inúteis. Usando o **Input Transformer**, você filtra e mapeia apenas as chaves necessárias antes de disparar o Target final (evitando que o Glue ou ECS gaste CPU decodificando metadados redundantes da AWS):

// 1. Input Paths Map (extrai propriedades do evento S3)
{
  "s3_bucket": "$.detail.bucket.name",
  "s3_file_key": "$.detail.object.key"
}

// 2. Input Template (formato limpo entregue ao Target, ex: Glue Job)
{
  "raw_bucket_path": "s3:///",
  "ingested_at": ""
}

Orquestração e Workflows de Dados (Step Functions)

Orquestração serverless, DAGs programáticas, tratamento de erros, Map States e integrações Glue/EMR/ECS

Um pipeline complexo possui dependências rígidas: a camada Silver só pode rodar se a Bronze finalizar com sucesso, e a Gold depende de múltiplas tabelas da Silver. Para isso, usamos orquestradores de fluxo (Workflows). O **AWS Step Functions** destaca-se como o orquestrador serverless nativo por excelência na nuvem.

AWS Step Functions

Serverless State Machine

Melhor opção para fluxos integrando serviços AWS (Lambda, Glue, ECS, EMR, Athena, SQS, SNS). Cobra por transição de estado. Latência extremamente baixa, suporte visual completo e zero servidores para gerenciar.

AWS Glue Workflows

Orquestrador Interno Simplificado

Indicado apenas quando o ecossistema é 100% baseado em Crawlers e Glue Jobs. Muito limitado em termos de controle de fluxo lógico complexo, ifs/choices e integrações com computação customizada externa.

Amazon MWAA (Managed Airflow)

Programmatic Python DAGs

O padrão ouro do mercado para pipelines complexos e heterogêneos. Ideal para times de engenharia que preferem escrever dependências como código Python e integrar com bancos on-premises.

Step Functions: Standard vs Express Workflows

Característica Standard Workflows Express Workflows
Tempo de Execução Máximo Até 1 ano. Até 5 minutos.
Preço Cobrado por transição de estados (passos). Cobrado por volume de requisições e duração da computação (GB-segundo).
Taxa de Invocação Até 2.000 execuções por segundo. **Mais de 100.000 execuções por segundo**.
Garantia de Execução **Exactly-Once**. Histórico detalhado de passos no console visual para debugging. **At-Least-Once**. Logs enviados apenas para o CloudWatch. Sem console de visualização histórica passo a passo.

Arquitetura Lambda

Combinação balanceada de processamento Batch e Speed Layers para consistência e baixa latência

A Arquitetura Lambda resolve o tradeoff entre velocidade e consistência dividindo os dados recebidos em dois caminhos paralelos:

  • Batch Layer (Lote - Fria): Salva o dado bruto imutável (camada Bronze do S3) e executa transformações complexas de alta exatidão em períodos programados (ex: a cada hora ou dia) usando AWS Glue ou EMR.
  • Speed Layer (Tempo Real - Quente): Processa os eventos instantaneamente com latência de milissegundos usando AWS Kinesis ou Flink para gerar métricas rápidas (ex: contadores dos últimos 5 minutos).
  • Serving Layer (Consumo): Combina as queries das duas camadas (histórico consolidado + dados rápidos recentes) para entregar o resultado unificado para dashboards ou APIs.

Arquitetura Kappa

Pipeline único baseado puramente em streaming e logs imutáveis de eventos

A Arquitetura Kappa remove a complexidade de manter duas bases de código separadas (Batch e Speed). Ela assume que **tudo é um fluxo contínuo de dados (streaming)**:

  • Os dados de entrada são armazenados em um log imutável ordenado por tempo (ex: tópicos com retenção longa no Amazon MSK / Apache Kafka).
  • Há um único motor de processamento (ex: Spark Structured Streaming ou Flink) lendo as mensagens e gravando na Serving Layer.
  • Reprocessamento histórico: Se uma regra de negócio mudar ou um bug for detectado, reinicia-se o ponteiro (offset) do consumidor Kafka para a posição zero (início dos tempos) e processa-se novamente as mensagens históricas pelo mesmo pipeline único.
Código PySpark Structured Streaming (Padrão Kappa) escrevendo em Iceberg

Abaixo está um script em PySpark Structured Streaming. Ele consome dados em tempo real do Amazon MSK (Kafka), decodifica o payload JSON, aplica uma janela de agregação de 5 minutos com tolerância de atraso (Watermark) de 10 minutos e escreve em uma tabela Apache Iceberg no S3.

from pyspark.sql import SparkSession
from pyspark.sql.functions import col, from_json, expr, window
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Inicializa sessão do Spark configurada para o Apache Iceberg
spark = SparkSession.builder \
    .appName("KappaKafkaToIceberg") \
    .config("spark.sql.extensions", "org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions") \
    .config("spark.sql.catalog.glue", "org.apache.iceberg.spark.SparkCatalog") \
    .config("spark.sql.catalog.glue.catalog-impl", "org.apache.iceberg.spark.SparkGlueCatalog") \
    .config("spark.sql.catalog.glue.warehouse", "s3://my-datalake-warehouse-bucket/metadata/") \
    .getOrCreate()

schema = StructType([
    StructField("transaction_id", StringType(), True),
    StructField("user_id", StringType(), True),
    StructField("amount", DoubleType(), True),
    StructField("timestamp", TimestampType(), True)
])

# Consumindo do Amazon MSK (Kafka)
df_kafka = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092") \
    .option("subscribe", "transactions-topic") \
    .option("startingOffsets", "latest") \
    .load()

# Decodificando dados
df_decoded = df_kafka.selectExpr("CAST(value AS STRING)") \
    .select(from_json(col("value"), schema).alias("data")) \
    .select("data.*")

# Agregação por Janela Temporal (Event-time) de 5 minutos com Watermarking
df_aggregated = df_decoded \
    .withWatermark("timestamp", "10 minutes") \
    .groupBy(
        window(col("timestamp"), "5 minutes"),
        col("user_id")
    ) \
    .agg(expr("sum(amount) as total_gasto")) \
    .select(
        col("window.start").alias("janela_inicio"),
        col("window.end").alias("janela_fim"),
        col("user_id"),
        col("total_gasto")
    )

# Gravando na tabela de Serving (Apache Iceberg) de forma contínua
query = df_aggregated.writeStream \
    .format("iceberg") \
    .outputMode("append") \
    .option("path", "glue.db.aggregated_transactions") \
    .option("checkpointLocation", "s3://my-datalake-warehouse-bucket/checkpoints/agg_transactions/") \
    .start()

query.awaitTermination()

Data Mesh: Governança Descentralizada

Organização socio-técnica baseada em domínios de negócio e dados como produto compartilhados de forma distribuída

Diferente de arquiteturas monolíticas centrais, o **Data Mesh** descentraliza a custódia das informações baseando-se em quatro pilares fundamentais:

  1. Domain-Oriented Ownership: A responsabilidade de ingerir e limpar o dado é da equipe do domínio gerador (ex: o time de Vendas gerencia o pipeline de vendas; o time de Logística cuida de entregas).
  2. Data as a Product: Os dados limpos de cada domínio são expostos como produtos documentados e acessíveis a outros domínios de negócio.
  3. Self-Serve Data Platform: Uma plataforma única central gerenciada (infra/governança/S3) que provê ferramentas automatizadas para que as equipes criem seus pipelines sem precisar acionar um time central de TI.
  4. Federated Computational Governance: Definição de padrões de conformidade globais (ex: criptografia obrigatória KMS, tags padrão) auditados de forma automatizada por APIs.

Mecânica de Compartilhamento Cross-Account na AWS

Em topologias corporativas reais de Data Mesh, cada domínio reside em uma conta AWS distinta, enquanto uma conta de governança central gerencia as permissões globais usando o **AWS Lake Formation** e o **AWS RAM**:

  • Compartilhamento Federado por Metastore: O proprietário dos dados (Produtor) concede permissão ao catálogo de metadados para a conta central de Governança. A central gerencia quem pode visualizar ou acessar essas tabelas usando políticas corporativas globais.
  • Glue Data Catalog Resource Links: Na conta consumidora, para evitar ler um catálogo remoto diretamente, cria-se um Resource Link (link de recurso local) no Glue Catalog. O Athena aponta para esse Resource Link, que redireciona de forma invisível e transparente a consulta ao catálogo produtor original.
  • Bucket Policies Cruzadas: A conta consumidora precisa de permissão de leitura física no S3. O produtor deve configurar uma Bucket Policy que permita a ação s3:GetObject e s3:ListBucket para a Role/IAM do executor na conta de destino, validada pelo Lake Formation.
Manual Prático do Especialista em Dados - Recursos Cloud de Arquitetura & Sharing:

1. AWS Lake Formation (Cross-Account Granting)
• Como funciona na prática: O Lake Formation atua como um wrapper de segurança sobre o Glue Catalog e o S3. Em vez de gerenciar permissões no S3 e no Glue separa-mente, você concede privilégios SQL (SELECT, DESCRIBE) a contas externas ou usuários locais diretamente no console ou via API.
• Gargalos Físicos e Redirecionamento de Credenciais (Vending System): O principal gargalo do Lake Formation é o limite de requisições à API do STS (Security Token Service), responsável por gerar credenciais temporárias para o Athena ler dados no S3. Em queries de altíssima concorrência executadas por dezenas de usuários em lote, o Athena pode apresentar throttling de STS.
• Como evitar falhas: Faça o registro do bucket S3 no Lake Formation no modo Hybrid Access Mode ou habilite o cache de credenciais do Athena para reduzir chamadas ao STS.

2. AWS RAM (Resource Access Manager)
• Como funciona na prática: RAM permite compartilhar recursos de infraestrutura da AWS (como subnets VPC, tabelas Glue e licenças de software) entre contas da mesma AWS Organization sem precisar de replicação física de recursos.
• Gargalo e Comportamento: O RAM em si não possui gargalo de taxa de dados de tráfego, pois atua puramente no plano de controle de metadados. Apenas gerencia o handshake de convite/aceitação entre contas. As cotas principais são de limites de recursos compartilhados por conta (padrão 5.000 recursos por região).

Paradigmas de Modelagem em Modern Data Lakehouses

Tuning analítico comparando Modelagem Dimensional, Data Vault 2.0 e OBT (One Big Table)

Em lagos de dados analíticos, a estrutura física como os dados são organizados afeta diretamente o tempo de execução e a performance financeira das queries no Athena/Presto ou Redshift:

Dimensional Modeling (Star Schema)

Dividido entre Tabelas Fato (métricas/eventos) e Tabelas Dimensão (atributos descritivos) unidas por chaves primárias/estrangeiras.

  • Mecanismo: Estrutura limpa baseada nos princípios de Ralph Kimball. Dimensões conformadas são reutilizadas em múltiplos fatos.
  • Vantagens: Fácil de compreender e modelar em ferramentas tradicionais de BI e OLAP.
  • Desvantagens no Lake: Alta penalidade física. Como os dados estão salvos no S3, fazer queries que juntam Fatos e múltiplas Dimensões exige shuffles e joins computacionais caros na leitura.
Data Vault 2.0

Separação rígida de chaves de negócio (Hubs), relacionamentos (Links) e dados descritivos/histórico de alterações (Satellites).

  • Mecanismo: Hubs guardam chaves de negócios, Links representam joins e Satellites rastreiam as mudanças cronologicamente.
  • Vantagens: Altamente escalável para ingestões corporativas ágeis em paralelo e auditoria histórica perfeita de registros.
  • Desvantagens no Lake: Querying direto impraticável. Exige dezenas de joins de metadados para construir uma simples visão consumível, sobrecarregando o Athena. Deve ser usado apenas na camada de integração (Silver), nunca no Serving (Gold).
OBT (One Big Table)

Desnormalização completa das tabelas analíticas em uma única tabela gigantesca e achatada contendo fatos e dimensões juntos.

  • Mecanismo: O dbt ou Spark resolve os joins na gravação (gravação pesada), gerando arquivos físicos únicos com todas as colunas unificadas.
  • Vantagens: Velocidade de leitura excepcional no Athena/Presto. Elimina 100% de shuffles de rede na leitura de queries analíticas de BI.
  • Desvantagens: Altíssima redundância de dados (write amplification), duplicando o custo de armazenamento bruto S3 (embora mitigado pela compressão nativa de colunas Parquet/ZSTD).

Modelagem Dimensional Profunda

Diferenças fundamentais entre processamento transacional (OLTP), analítico (OLAP), e o impacto físico de Star vs. Snowflake Schema no ecossistema AWS

OLTP vs. OLAP: Propósito e Arquitetura Físicas

A arquitetura física de um banco de dados é projetada especificamente para o padrão de acessos que ele atende. Tentar usar um banco transacional para analítico, ou vice-versa, gera sérios problemas de escala e gargalos de IO/CPU:

Característica OLTP (Online Transaction Processing) OLAP (Online Analytical Processing)
Propósito Operações de escrita rápidas diárias (INSERT, UPDATE, DELETE). Consultas analíticas complexas e agregações históricas (SUM, AVG, GROUP BY).
Padrão de Query Acessa poucos registros específicos por vez (busca por ID ou chave primária). Varre milhões de linhas agregando poucas colunas (full scans).
Normalização Altamente normalizado (geralmente até a 3ª Forma Normal - 3NF) para eliminar redundâncias e evitar anomalias de escrita. Desnormalizado (Star Schema ou OBT) para reduzir o número de joins necessários e otimizar velocidade de leitura.
Armazenamento Orientado a Linhas (Row-oriented). Excelente para ler/gravar uma linha completa rapidamente. Orientado a Colunas (Columnar). Lê do disco apenas as colunas envolvidas na query, maximizando compressão.
Tecnologias AWS Amazon RDS (PostgreSQL/MySQL), Amazon Aurora. Amazon Redshift, Amazon Athena (com S3).

Star Schema vs. Snowflake Schema: O Embate do Data Warehouse

Dentro de um Data Warehouse tradicional (como o Redshift) ou Lakehouse moderno, a organização das tabelas dimensionais determina o custo computacional das queries:

Kimball Star Schema

Estrutura Desnormalizada Estrela

O centro do diagrama é a tabela Fato, que é cercada diretamente por tabelas de Dimensão. As dimensões não são normalizadas; por exemplo, os atributos de cidade, estado e país de uma dimensão cliente residem na própria tabela de cliente.

✓ Vantagem: Apenas um nível de join para associar qualquer dimensão ao fato. Menor shuffle de rede em leitura.

✗ Desvantagem: Redundância de dados e maior espaço consumido (embora mitigado por compressões colunares modernos).

Inmon Snowflake Schema

Estrutura Normalizada Floco de Neve

As dimensões do Star Schema são normalizadas em múltiplas tabelas satélites. A tabela de cliente aponta para uma tabela de cidades, que aponta para estados, etc., criando ramificações que lembram um floco de neve.

✓ Vantagem: Menor redundância de dados (Single Source of Truth de atributos descritivos) e menor espaço em disco analítico.

✗ Desvantagem: Queries exigem múltiplos joins aninhados (fatos ➔ clientes ➔ cidades ➔ estados), degradando severamente a performance no S3/Athena.

Métrica Star Schema Snowflake Schema
Normalização das Dimensões Não (Totalmente Desnormalizadas) Sim (Normalizadas em tabelas auxiliares)
Número de Joins Baixo (Apenas Fato ➔ Dimensão) Alto (Joins recursivos entre dimensões filhas)
Desempenho no Redshift/Athena Excelente (Favorece joins simples colunares) Ruim/Médio (Gera shuffles de rede excessivos)
Manutenção e Carga (ETL) Mais complexo no carregamento de dados Mais simples (dados estruturados e limpos)
Espaço em Disco Maior (Redundância de strings) Menor (Chaves ID compactas)

Como Otimizar Joins Dimensionais na AWS

Em ambientes distribuídos da AWS, o maior gargalo de performance de joins entre tabelas é o Data Shuffle (transferência física de partições de dados entre os nós computacionais via rede local do datacenter). Veja como mitigar isso:

Amazon Redshift
Redshift Distribution Keys
  • DISTSTYLE KEY: Defina a mesma chave de distribuição (ex: id_cliente) na tabela Fato e na tabela Dimensão Cliente gigante. O Redshift salvará as fatias de dados correspondentes no mesmo nó físico, executando um **Colocated Join** sem nenhum tráfego de rede.
  • DISTSTYLE ALL: Para dimensões pequenas (ex: dim_tempo, dim_categoria), copie a tabela inteira em todos os nós computacionais do cluster. Isso elimina shuffles de rede no join analítico.
Amazon Athena & S3
Desnormalização Total (OBT)
Como o Athena lê dados diretamente do S3 de forma serverless, joins pesados exigem que o motor analítico distribua dados dinamicamente na memória RAM. A melhor prática no S3/Athena é a desnormalização completa em **One Big Table (OBT)**. O custo extra de armazenamento do S3 é insignificante em comparação ao ganho de velocidade de leitura e corte de custos de processamento de queries Athena.

Tuning de Performance: Casos Degradados & Soluções

Troubleshooting prático de gargalos de processamento, CPU, memória e IO na AWS

AWS Glue · Out Of Memory
Caso 1: Driver/Executor OOM (Spark Exception)
Sintoma: O Glue Job falha após rodar por alguns minutos com o log: java.lang.OutOfMemoryError: Java heap space.
Causa: Data Skew (desbalanceamento) gritante. Muitas chaves nulas ou vazias agrupadas sob a mesma chave de agregação/join concentram gigabytes in uma única partição Spark/JVM.
Solução: Salgar a chave de join para redistribuição (Salting), aumentar o número de partições ou reescalar workers padrão de G.1X (4 vCPU, 16GB RAM) para G.2X (8 vCPU, 32GB RAM) com maior poder de processamento.
AWS EMR · Garbage Collection
Caso 2: Spark FetchFailed e GC Overhead
Sintoma: EMR Job lento com constantes falhas de FetchFailedException: Failed to connect to host no estágio de shuffle.
Causa: Pause longo por JVM Garbage Collection (GC) devido ao uso excessivo de objetos temporários na memória dos executors, fazendo a máquina perder comunicação com o coordenador YARN.
Solução: Mudar o coletor de lixo para G1GC e definir o executor memory overhead correto:
--conf spark.executor.extraJavaOptions="-XX:+UseG1GC"
--conf spark.yarn.executor.memoryOverhead=4096
Amazon Athena · Custo & Tempo
Caso 3: Varredura de Terabytes desnecessária
Sintoma: Queries simples demoram minutos e escaneiam terabytes de dados no S3, gerando altos custos analíticos.
Causa: Layout de arquivos ruim (dados em JSON ou arquivos sem particionamento explícito) e falta do uso do Partition Projection no Glue Catalog.
Solução: Converter dados para Parquet comprimido com Snappy/ZSTD e ativar o Partition Projection para ler apenas os blocos de dados específicos solicitados na cláusula WHERE da query Athena.
RDS & Aurora · Gargalo OLTP
Caso 4: Picos de CPU (100%) e Timeout
Sintoma: O banco de dados congela no meio do dia, estourando conexões com erro Too many connections.
Causa: Falta de índices adequados para queries analíticas e estouro de concorrência por falta de um pooler de conexões centralizado.
Solução: Criar índices B-Tree específicos nas chaves de busca mais comuns, criar **Aurora Read Replicas** para direcionar queries de leitura (BI/ETL) e implementar o Amazon RDS Proxy para reaproveitar conexões ativas.
DICA DE ANÁLISE: Query Plan Tuning no PostgreSQL (Aurora/RDS)

Use o comando EXPLAIN ANALYZE para auditar queries lentas. Abaixo, identificamos um scan sequencial lento (Seq Scan) que é resolvido imediatamente criando um índice:

-- 1. Query lenta original (executando Seq Scan em tabela gigante)
EXPLAIN ANALYZE SELECT * FROM transacoes WHERE status = 'PROCESSADO' AND data_criacao >= '2026-06-01';
-- Output de exemplo: -> Seq Scan on transacoes (cost=0.00..85421.23 rows=42152 width=142) (actual time=0.015..942.302 loops=1)

-- 2. Correção: Criar um índice composto para os campos do filtro
CREATE INDEX idx_transacoes_status_data ON transacoes (status, data_criacao);

-- 3. Nova validação do plano (verificando Index Scan de milissegundos)
EXPLAIN ANALYZE SELECT * FROM transacoes WHERE status = 'PROCESSADO' AND data_criacao >= '2026-06-01';
-- Output: -> Index Scan using idx_transacoes_status_data on transacoes (cost=0.42..342.12 rows=42152 width=142) (actual time=0.021..14.120 loops=1)

O Problema de Small Files & Particionamento do S3

Técnicas de compactação de arquivos e regras de ouro de particionamento físico

Gravar arquivos muito pequenos (KB ou poucos MB) no S3 degrada severamente a performance das ferramentas analíticas. O Spark ou Athena gastam mais tempo executando chamadas REST de listagem (ListObjects) e lendo metadados das partições do que abrindo os dados propriamente ditos.

Regras de Ouro de Particionamento

  • Cardinalidade Média: Evite criar caminhos de partição baseados em campos com cardinalidade muito alta (ex: user_id ou transaction_id). Isso resulta em milhões de pastas no S3 com um arquivo de poucos bytes dentro.
  • Tamanho Ideal: Prefira manter o tamanho do arquivo no S3 entre 128 MB e 512 MB. Esse é o tamanho ótimo para divisão de leitura do bloco HDFS/Spark.
  • Cardinalidade Certa: Particione por campos lógicos de busca recorrente no WHERE, como data_ano, data_mes, ou categoria_macro.
Solução 1: Compaction Manual PySpark

Coalesce & Repartition

Agrupar e reescrever o dataset em partições balanceadas antes da persistência final.

Solução 2: Iceberg Optimize

Compactação Nativa (Transacional)

Comando DDL do Apache Iceberg para reescrever e compactar metadados sem interferir em leituras simultâneas.

Código PySpark: Script Batch para Compaction e Gravação

Abaixo está um script PySpark clássico executando a consolidação de milhares de pequenos arquivos em um conjunto enxuto de arquivos de tamanho controlado:

from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("S3CompactionJob").getOrCreate()

# 1. Ler milhares de pequenos arquivos fragmentados na Bronze
df_fragmentado = spark.read.parquet("s3://my-datalake-bronze/raw_data/ano=2026/mes=06/*")

# 2. Re-particionar baseando-se em volumetria e cardinalidade para atingir ~128MB por arquivo
# Usamos repartition() para balancear em partições menores na memória
df_compactado = df_fragmentado.repartition(4) 

# 3. Gravar na Silver de forma atômica
df_compactado.write \
    .mode("overwrite") \
    .parquet("s3://my-datalake-silver/consolidated_data/ano=2026/mes=06/")

Frameworks de Modelagem: Kimball & Teorema CAP

Modelagem Dimensional para Data Warehousing e tradeoff de consistência em sistemas distribuídos

A modelagem de dados define como a informação será estruturada para facilitar o consumo analítico pelas áreas de negócios.

Esquema Star (Modelo Dimensional de Kimball)

O Star Schema é projetado para otimizar queries analíticas rápidas através do desacoplamento de tabelas:

  • Tabelas Fato (Fact Tables): Armazenam as métricas numéricas e quantitativas dos eventos de negócios (ex: fato_vendas com quantidade, preço total, desconto) e chaves estrangeiras.
  • Tabelas Dimensão (Dimension Tables): Armazenam os atributos qualitativos que dão contexto e detalhamento à fato (ex: dim_cliente, dim_produto, dim_tempo).
  • SCD (Slowly Changing Dimensions): Gerenciamento da mudança de dados cadastrais históricos nas dimensões:
    • SCD Tipo 1: Sobrescreve o registro antigo (sem histórico).
    • SCD Tipo 2: Cria uma nova linha mantendo colunas data_inicio, data_fim e flag ativo para rastrear todo o histórico.
    • SCD Tipo 3: Cria novas colunas para salvar o valor anterior (guarda apenas o estado atual e o imediatamente anterior).
-- Exemplo de inserção de dados em Dimensão Tipo 2 (Histórico Completo)
INSERT INTO dim_cliente (id_cliente, nome, cidade, data_inicio, data_fim, flag_ativo)

UPDATE dim_cliente SET data_fim = '2026-06-02', flag_ativo = FALSE WHERE id_cliente = 42 AND flag_ativo = TRUE;
INSERT INTO dim_cliente (id_cliente, nome, cidade, data_inicio, data_fim, flag_ativo)
VALUES (42, 'Mauricio Helfstein', 'Rio de Janeiro', '2026-06-03', NULL, TRUE);

O Teorema CAP nos Bancos de Dados AWS

O Teorema CAP dita que um sistema distribuído pode garantir apenas duas de três propriedades simultaneamente:

Pilar Teorema Definição Operacional Serviço AWS Correspondente
C - Consistência Todos os nós leem o mesmo dado simultaneamente após uma atualização. DynamoDB Strong Consistent Reads / Aurora DB
A - Disponibilidade Toda requisição não-com falha recebe uma resposta de sucesso (mesmo sem garantia de dados recentes). Amazon DynamoDB (Eventual Consistency)
P - Partição (Tolerância) O sistema continua funcionando mesmo se houver falhas de rede isolando nós. Multi-AZ RDS / Aurora Global Database

Tradeoffs de Tecnologia: Comparativo de Performance

Análise crítica das ferramentas mais populares para tomadas de decisão arquiteturais fundamentadas

Nenhuma tecnologia é perfeita para todos os casos de uso. O papel do arquiteto de dados é balancear tradeoffs de latência, throughput, custo operacional e complexidade de código.

Tecnologia A vs B Vencedor Performance Vantagens da Opção A Vantagens da Opção B Recomendação de Decisão
Apache Spark vs Apache Flink Flink (latência)
Spark (vazão batch)		 Excelente throughput para processamento massivo em lote (Batch) e microlotes de segundos. Curva de aprendizado menor. Processamento nativo evento a evento em tempo real real (milissegundos). Gerenciamento de estado complexo superior. Use Spark por padrão para ETLs gerais. Use Flink se latências abaixo de 1 segundo forem um requisito de negócio inegociável.
AWS Kinesis vs Amazon MSK (Kafka) MSK (Kafka) (vazão pura) Serverless nativo, integração zero-code com Firehose/Lambda, sem custos fixos mínimos de infraestrutura. Throughput de gigabytes por segundo, retenção em disco customizada (longo prazo), ecossistema Kafka aberto completo. Use Kinesis para economizar tempo de infraestrutura. Use MSK se já possuir pipelines corporativos baseados em Kafka ou altíssimo volume.

Escala horizontalmente ao infinito com latência estável abaixo de 10ms independente do tamanho do banco. Use RDS para dados altamente estruturados e relacionais. Use DynamoDB para dados chave-valor transacionais rápidos de alta concorrência.

APIs de Dados & API Gateway na AWS

Arquitetura de Data-as-a-Service (DaaS), integração direta sem servidores (Lambda-less) e gerenciamento de concorrência

Em plataformas modernas de dados, a exposição direta de data warehouses ou data lakes aos clientes e microservices consome recursos excessivos e introduz vulnerabilidades de segurança. O paradigma de APIs de Dados (Data APIs) resolve isso encapsulando o acesso aos dados atrás de uma camada HTTP padronizada, gerenciada por políticas de autenticação, throttling e cache.

REST APIs

Simplicidade e CRUD

Ideal para endpoints estáticos, relatórios estruturados e paginação uniforme via verbos HTTP clássicos (GET/POST). Perfeito para consumo por parceiros externos usando Amazon API Gateway.

GraphQL (AWS AppSync)

Flexibilidade do Consumidor

Permite que o cliente solicite exatamente as colunas e nós necessários em um único request (evitando over-fetching). Ideal para dashboards interativos que consolidam dados do DynamoDB, OpenSearch e Aurora RDS.

gRPC (Microserviços)

Baixa Latência & Stream

Utiliza Protocol Buffers (protobuf) e HTTP/2. Indicado para comunicação interna de alta performance entre microsserviços de dados ou streaming bidirecional de eventos.

Arquitetura de API de Dados na AWS: Padrões de Integração

Há dois caminhos principais para a construção de APIs de dados no ecossistema AWS:

  • 1. Integração Direta de Serviço (Direct Integration / Lambda-less): O Amazon API Gateway comunica-se diretamente com o serviço de destino (geralmente o DynamoDB) sem a necessidade de um compute intermediário (Lambda). As requisições HTTP e payloads de resposta são convertidos via **Velocity Template Language (VTL)**.
    Vantagens: Latência extremamente baixa (sem cold starts), custos drasticamente menores (elimina taxas de execução de Lambda e concorrência) e simplicidade de manutenção.
  • 2. Caminho Computacional (Compute-backed API): O API Gateway direciona a chamada a uma função AWS Lambda que executa lógica complexa de negócios, agrega dados de múltiplos bancos de dados ou executa consultas SQL em ferramentas de backend analítico (como o Amazon Athena ou o Redshift Data API).
    Vantagens: Flexibilidade de validação de dados, controle de joins dinâmicos em código e processamento customizado.
Exemplo prático: Terraform e VTL Mapping Template para Integração Direta com DynamoDB

O exemplo abaixo mostra como configurar no Terraform uma rota do API Gateway que mapeia um parâmetro do path diretamente para uma consulta de chave primária no DynamoDB usando VTL, sem usar Lambda:

# Recurso de Integração do API Gateway direto com o DynamoDB
resource "aws_api_gateway_integration" "dynamodb_integration" {
  rest_api_id             = aws_api_gateway_rest_api.data_api.id
  resource_id             = aws_api_gateway_resource.user_data.id
  http_method             = aws_api_gateway_method.get_user_data.http_method
  type                    = "AWS"
  integration_http_method = "POST"
  uri                     = "arn:aws:apigateway:$${var.aws_region}:dynamodb:action/GetItem"
  credentials             = aws_iam_role.apigateway_dynamodb_role.arn

  # Mapeamento do Request HTTP para o formato do DynamoDB usando VTL
  request_templates = {
    "application/json" = <<EOF
{
  "TableName": "tabela_usuario_bronze",
  "Key": {
    "user_id": {
      "S": "$method.request.path.userId"
    }
  }
}
EOF
  }
}

# Template de Resposta para converter o formato do DynamoDB de volta para JSON limpo
resource "aws_api_gateway_integration_response" "dynamodb_response" {
  rest_api_id = aws_api_gateway_rest_api.data_api.id
  resource_id = aws_api_gateway_resource.user_data.id
  http_method = aws_api_gateway_method.get_user_data.http_method
  status_code = "200"

  response_templates = {
    "application/json" = <<EOF
#set($input = $input.path('$'))
{
  "userId": "$input.Item.user_id.S",
  "email": "$input.Item.email.S",
  "status": "$input.Item.status.S",
  "dataRegistro": "$input.Item.created_at.S"
}
EOF
  }
}

Caching & Throttling: Proteção de Motores Analíticos

Diferente de bancos de dados transacionais rápidos, motores como **Amazon Athena** e **Amazon Redshift Serverless** são projetados para processamento analítico volumoso e têm limites rígidos de concorrência ativa. Expor uma API de dados sobre esses motores sem proteção pode derrubar os sistemas ou causar contas astronômicas de processamento devido ao escaneamento repetido de dados do S3.

  • API Gateway Caching: O cache do API Gateway reduz a carga de trabalho de consulta em bancos de dados analíticos downstream. Ao ativar o cache com um Time-to-Live (TTL) específico, chamadas idênticas com os mesmos parâmetros recebem a resposta do cache sem re-executar queries no Athena ou Redshift.
  • Throttling e Usage Plans: Configure políticas de limite de requisições por segundo (RPS) e limites de rajadas (Burst Limit) no API Gateway. Isso impede ataques de negação de serviço e garante uma distribuição justa de recursos entre os consumidores analíticos.
  • Result Caching do Athena: O Athena armazena por padrão os resultados de consultas em um bucket S3 de controle. Se a mesma query exata for submetida em um intervalo curto de tempo, o Athena pode retornar os dados sem precisar varrer novamente o S3 (reduzindo custo FinOps), contanto que as tabelas de origem não tenham sido alteradas.
Ponto de Atenção em Entrevistas de Arquitetura:

Se perguntado sobre como servir dados analíticos em tempo real de forma segura e econômica para milhares de usuários simultâneos:

  • Resposta Errada: Conectar o API Gateway e uma Lambda rodando queries no Athena diretamente no S3 para cada requisição.
  • Resposta Correta: Criar um pipeline assíncrono. O processamento Spark ou dbt resume os dados analíticos no Athena/S3, salva essas visões agregadas prontas no **DynamoDB** (ou **Amazon ElastiCache**), e o API Gateway faz a leitura direta e de baixíssima latência (Lambda-less) no DynamoDB.
