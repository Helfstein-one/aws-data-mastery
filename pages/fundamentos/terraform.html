Terraform & Infra as Code

Arquitetura de infraestrutura como código para Engenharia de Dados. Crie Data Lakes, Buckets, roles IAM e pipelines escaláveis de forma declarativa.

01

Conceitos Básicos de Terraform

Declarativo, Agnóstico e Gerenciamento de Estado

O Terraform (desenvolvido pela HashiCorp) permite criar, alterar e gerenciar infraestrutura de forma segura e previsível usando a linguagem HCL (HashiCorp Configuration Language). Em ambientes de dados, usamos Terraform para criar S3 Buckets, IAM Roles, EMR Clusters, Glue Jobs e todo o perímetro de rede.

Providers
AWS Provider
O Terraform utiliza Providers (plugins) para interagir com APIs de provedores de nuvem. No nosso caso, o provedor aws é o motor que converte o código HCL em chamadas REST para a AWS (ex: CreateBucket).
State (Estado)
O tfstate e o Backend
O Terraform armazena o mapa da infraestrutura real em um arquivo chamado terraform.tfstate. Para colaboração em equipe, esse arquivo NUNCA deve ir para o Git. A melhor prática é usar um S3 Backend com bloqueio via DynamoDB (State Lock).
02

Estrutura e Comandos Principais

O workflow do Engenheiro IaC

Um projeto Terraform padrão possui os seguintes arquivos:

  • main.tf: A lógica central e recursos.
  • variables.tf: Declaração de variáveis dinâmicas (ex: env, region).
  • outputs.tf: Valores que queremos exportar (ex: ARN do bucket).
  • providers.tf: Configuração de backend e provider.
HCL (Terraform) 
# Exemplo: Criação de um Bucket S3 para o Data Lake Raw
resource "aws_s3_bucket" "datalake_raw" {
  bucket = "empresa-datalake-raw-${var.environment}"
  
  tags = {
    Environment = var.environment
    Team        = "Data Engineering"
  }
}

# Bloqueio de acesso público
resource "aws_s3_bucket_public_access_block" "block_public" {
  bucket                  = aws_s3_bucket.datalake_raw.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

O Workflow: Init, Plan, Apply

1. Inicialização
terraform init
Faz o download dos providers (AWS) e inicializa o backend (conexão com S3 para o state).
2. Planejamento
terraform plan
Gera um plano de execução detalhando exatamente o que será criado (+), modificado (~) ou deletado (-).
3. Execução
terraform apply
Aplica o plano na nuvem e atualiza o tfstate. Em CI/CD, roda como terraform apply -auto-approve.

04

Boas Práticas: Módulos e Meta-Argumentos

Escrevendo código DRY (Don't Repeat Yourself) para a Plataforma

Quando a infraestrutura de dados cresce, manter tudo num único arquivo `main.tf` torna-se impossível. Engenheiros Seniores utilizam Módulos para encapsular lógicas e Meta-Argumentos para criar recursos dinamicamente.

Meta-Argumentos em Ação

for_each
Criação Iterativa
Ao invés de duplicar blocos para criar 3 buckets diferentes, passamos um mapa ou lista de strings para a propriedade for_each, e o Terraform cria um recurso por item iterado.
dynamic
Blocos Dinâmicos
Ideal para criar listas de regras dentro de um recurso (ex: liberar 5 portas em um Security Group). O dynamic block age como um "for loop" dentro da definição de um recurso.
data sources
Leitura de Estado
Quando você precisa referenciar uma VPC que já existe na AWS e não foi criada por você via Terraform, você usa blocos data "aws_vpc" para importar seus atributos (como o ID) e anexar ao seu novo recurso.
Terraform - for_each no Data Lake
locals {
  buckets = ["raw", "trusted", "refined"]
}

resource "aws_s3_bucket" "data_lake" {
  for_each      = toset(local.buckets)
  bucket        = "mycompany-datalake-${each.key}-us-east-1"
  force_destroy = false
}

# Isso criará 3 buckets com um único bloco de código!

Anatomia de um Componente de Dados

Quando desenvolvemos um módulo complexo (como um Cluster EMR ou um Data Lakehouse S3), quebrar a infraestrutura em múltiplos arquivos `.tf` melhora drasticamente a legibilidade em vez de colocar tudo em um main.tf de mil linhas. Abaixo a estrutura ideal de arquivos para um componente:

1. providers.tf & backend.tf
Conexão & Estado
providers.tf define as versões dos provedores (AWS, Random) e a região. backend.tf informa onde o state será salvo (Bucket S3) e o controle de lock (DynamoDB).
2. variables.tf & outputs.tf
Entradas e Saídas
variables.tf declara os parâmetros aceitos pelo componente (tamanho da máquina, ambiente). outputs.tf devolve dados (ARNs, IDs) para que outros módulos possam consumir essa infraestrutura.
3. locals.tf
Variáveis Calculadas
Diferente das variables (que vêm de fora), os locals armazenam lógica interna, formatações de string e tags comuns geradas em tempo de execução para evitar repetição.
4. main.tf
Recurso Principal
Reserva-se o main.tf estritamente para o coração do componente. Se for um módulo de banco de dados, aqui fica o aws_db_instance. O resto vai para arquivos secundários.
5. iam.tf
Identidade & Permissões
Centraliza todas as Roles, Policies e assumable roles (`aws_iam_role`, `aws_iam_policy`). Separar o IAM previne que engenheiros cometam acidentes de segurança ao misturar permissões com recursos computacionais.
6. security.tf & vpc.tf
Redes e Proteção
vpc.tf para criação/importação de Subnets, Route Tables e Gateways. security.tf abriga os Security Groups, NACLs e chaves de criptografia KMS.
7. versions.tf
Travamento de Versão
Garante a imutabilidade do código fixando as versões permitidas do binário do Terraform e dos Providers (ex: AWS), prevenindo quebras catastróficas por atualizações de dependências.
05

Cases Reais: A Plataforma Self-Service

Como a Engenharia de Dados habilita Analistas de forma segura

Case 1: Ambientes Separados (Workspaces vs Pastas)

Cenário: O time de dados precisava replicar a infraestrutura de Produção para um ambiente de Staging para testar novas versões do Airflow sem quebrar as dags ativas.

Ação: Em vez de criar um código Terraform isolado, foi arquitetada uma estrutura baseada em pastas separadas para cada ambiente (/env/prod e /env/stg), onde ambas invocam o mesmo Módulo raiz (/modules/airflow), apenas passando um arquivo .tfvars diferente (com o tamanho reduzido de EC2 para Staging).

Case 2: Automação de Roles (IAM) via Módulo

Cenário: Todo novo Cientista de Dados contratado precisava abrir um ticket no Jira para que a Segurança criasse sua Role de acesso ao SageMaker e ao S3.

A Otimização: O time de Infraestrutura criou um módulo do Terraform chamado aws_data_scientist_role. Agora, um engenheiro só precisa adicionar o nome do cientista em uma lista de strings no `main.tf` do repositório, e o CI/CD (GitHub Actions) aplica o Terraform, gerando a role com o princípio do privilégio mínimo automaticamente.

06

Boas Práticas de Modularização e Estrutura

Organizando Repositórios Complexos na AWS

Um repositório Terraform mal estruturado vira um grande monolito rapidamente, tornando os processos de plan lerdos e arriscados (um erro pode destruir componentes que não deveriam ser tocados). A modularização inteligente é a chave.

A Árvore de Pastas Perfeita (Folder Structure)

Uma arquitetura de pastas de nível Sênior separa os Módulos (o "como fazer") das Composições/Ambientes (o "o que criar").

Estrutura de Diretórios
terraform-data-platform/
├── modules/                         # Módulos Reutilizáveis (Lógica Genérica)
│   ├── s3-data-lake/                # Módulo para criar buckets criptografados do Lakehouse
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── emr-serverless-app/          # Módulo para o Compute Engine
│   └── iam-data-role/               # Módulo de Governança de Perfis IAM
│
├── environments/                    # Uso prático dos Módulos (State separado)
│   ├── dev/
│   │   ├── main.tf                  # Chama os modules/* passando vars pequenas
│   │   ├── terraform.tfvars         # Ex: instance_count = 1
│   │   └── backend.tf               # Aponta para o State de Dev
│   │
│   ├── stg/
│   │
│   └── prod/
│       ├── main.tf                  # Chama os mesmos modules/*
│       ├── terraform.tfvars         # Ex: instance_count = 10 (Alta disponibilidade)
│       └── backend.tf               # Aponta para o State de Prod
│
├── scripts/                         # Automações de CI/CD (GitHub Actions / GitLab CI)
└── README.md
1. Módulos Burros
Princípio da Injeção
Módulos (/modules) não devem possuir valores hardcoded. Tudo (nomes, VPC IDs, tamanhos) deve vir do variables.tf. Eles devem ser genéricos o suficiente para serem chamados por Dev, Stg ou Prod.
2. Estados Isolados
Blast Radius
Ao usar a pasta /environments, cada ambiente possui seu próprio terraform.tfstate. Se houver corrupção no arquivo de estado de Dev, a plataforma de Prod continua intocada e operando 100%.
3. Componentes Granulares
State File Size
Evite colocar IAM, Redes, S3 e EMR na mesma camada. Times muito maduros até separam o environments/prod/ em pastas como network/, storage/ e compute/, acelerando os *deploys*.
