Sustentação de Projetos de Dados (RUN)

A transição de BUILD para RUN e a manutenção contínua do ecossistema analítico

O ciclo de vida de um produto de dados não termina no "Deploy". A fase de Sustentação (RUN) é responsável por garantir que as esteiras de dados operem dentro do SLA. A sustentação exige automação, monitoramento proativo e processos bem definidos de resolução de incidentes.

O Custo Oculto do "Build-Only":

Organizações que negligenciam o "RUN" tendem a gerar Technical Debt maciço. Sem uma equipe dedicada para sustentação, novos projetos são paralisados pelas constantes falhas na produção legada.

Gestão Baseada no Teorema de Pareto (Regra 80/20)

Um dos maiores desafios do PMO na Sustentação é o volume de incidentes (Data Quality, Resource Issues). Utilizamos o Teorema de Pareto:

Análise de Causa Raiz (RCA)

Geralmente, 80% dos incidentes de sustentação são causados por apenas 20% dos componentes. Um banco de origem problemático pode ser responsável por dezenas de alertas semanais.

Ação e Priorização

A equipe de RUN não deve focar apenas em religar o serviço (Workaround). Após categorizar os incidentes, os top 20% ofensores são escalados para a equipe de BUILD como "Refatoração Crítica" (Bug-Fix permanente).

O Ecossistema de Sustentação

DATA PLATFORM STAKEHOLDERS
Diagrama: Arquitetura de Stakeholders da Data Platform Esta representação mapeia a dinâmica de forças que operam no ecossistema de dados, divididas em quatro quadrantes essenciais:
■ Patrocinadores (Sponsors) - Verde: Executivos C-Level (CFO, Head de Produto) responsáveis por alocar budget (financiamento) e ditar a visão estratégica. São os "donos" do ROI da plataforma.
■ Produtores (Producers) - Âmbar: Engenheiros de Backend, APIs e SecOps que geram os dados brutos e eventos transacionais. Sua principal entrega para a plataforma são logs e dados sistêmicos.
■ Consumidores (Consumers) - Azul: Analistas de BI, Cientistas de Dados (ML) e Áreas de Negócio. Eles não produzem, apenas extraem os dados limpos e governados para gerar modelos preditivos, dashboards e insights acionáveis.
■ Engenharia e PMO - Rosa: O núcleo construtor. Engenheiros de Dados desenvolvem as pipelines de ingestão e transformação, enquanto o Data PMO orquestra, prioriza as demandas dos consumidores e gerencia o backlog da plataforma.

O Loop Contínuo do Cloud FinOps (Economics)

Gerenciar o *Cloud Economics* de uma Plataforma Analítica na AWS exige um processo iterativo. O framework da FinOps Foundation delineia três fases contínuas pelas quais o PMO de Dados e os Engenheiros navegam:

1. Inform (Visibilidade)

Você não pode otimizar o que não pode ver. É mandatório aplicar uma política estrita de **Tagging** (Ex: `CostCenter`, `Environment`, `Domain`) em cada AWS Glue Job e Bucket S3. Usa-se o AWS Cost Explorer para ratear a conta exata para cada tribo de negócio.

2. Optimize (Otimização)

Ação direta na infraestrutura. Trocar instâncias EC2 antigas pelas com processadores Graviton (ARM) para melhor relação preço/performance. Usar instâncias Spot para Spark Executors efêmeros no Amazon EMR. Adotar S3 Intelligent-Tiering para mover automaticamente dados frios para camadas mais baratas, e negociar Savings Plans ou Compute Pledges com a AWS.

3. Operate (Operação)

Otimizar uma vez não basta. A etapa Operate incorpora FinOps na cultura (Cloud Economics). Cria-se AWS Budgets e AWS Cost Anomaly Detection com alertas via SNS/Slack para interceptar anomalias de faturamento em tempo real. Se um analista fizer uma query incorreta (full scan) no Athena gerando pico de $500 em 1h, o time de engenharia é notificado na hora para investigar.

FINOPS LIFECYCLE IN DATA
Diagrama: O Fluxo Contínuo de FinOps (Inform, Optimize, Operate) Este fluxo ilustra como as práticas de Cloud Economics são implementadas na automação de sustentação de dados:
1. Inform (Visibilidade): O AWS Cost Explorer é a porta de entrada, permitindo granularidade e alocação de custos por meio de tags de recursos (quem gastou e onde).
2. Monitoramento e Detecção (Operate): O AWS Budgets estipula limiares de gastos permitidos e trabalha com alertas automatizados para prevenir estouro de orçamento.
3. Recomendações e Tuning (Optimize): Ferramentas como o Compute Optimizer sugerem reduções de capacidade sobressalente (rightsizing) ou mudança de família de instâncias.
4. Ação: Em caso de anomalia, alertas são disparados via SNS/Slack, resultando em uma Ação pela engenharia (ex: matar uma query no Athena presa ou migrar clusters para Spot/Graviton). As setas contínuas reforçam que FinOps não é uma tarefa pontual, e sim um ciclo perene da plataforma.

Confiabilidade de Dados: SLA vs SLO vs SLI

Para mensurar a confiabilidade e saúde da plataforma de dados, tomamos emprestado os conceitos de Engenharia de Confiabilidade do Site (SRE) do Google (referência: Google SRE Book), adaptando-os para pipelines de dados:

SLI (Service Level Indicator)

A métrica exata medida no momento. Ex: Atraso (latência) de ingestão do Kafka para o S3, ou a porcentagem de registros que falharam nos testes de Data Quality do Great Expectations.

SLO (Service Level Objective)

A meta ou intervalo aceitável para o SLI. Acordado internamente entre a Engenharia e o PMO. Ex: "99.9% dos dados do CRM devem estar no Data Lake até as 08:00 AM".

SLA (Service Level Agreement)

O contrato de negócios formal com o cliente/negócio que envolve penalidades se o SLO não for cumprido. Ex: Se o pipeline de faturamento atrasar mais de 4h, há devolução parcial do pagamento de licenciamento (multa).

Fluxo de Sustentação (Níveis de Atendimento)

A estrutura padrão de resposta a incidentes de dados obedece à pirâmide de níveis de suporte:

Boas Práticas & Legenda de SLA

  • Nível 1 (Monitoramento / Plantonista): Triagem inicial e resolução de problemas mapeados via playbooks. Exemplo de Playbook: Se um pipeline de streaming do Apache Flink falhar por backpressure intenso, o N1 reinicia a aplicação com paralelismo aumentado temporariamente. SLA típico: 15-30 minutos.
  • Nível 2 (Engenheiro Pleno): Análise de causa raiz (RCA) para falhas complexas ou novas. Aplica Hotfixes (códigos emergenciais) ou ajusta infraestrutura para reestabelecer o serviço. SLA típico: 2-4 horas.
  • Nível 3 (Arquiteto / Especialista / Dev): Resolve o débito técnico deixado pelo Hotfix. Desenvolve o Bug Fix Permanente e refatoração estrutural no backlog oficial (sprints regulares). SLA típico: 1-2 Sprints.
FLUXO DE SUSTENTAÇÃO (NÍVEIS DE ATENDIMENTO)
Legenda: Escalação de incidentes em 4 estágios. CloudWatch Alarm detecta anomalia → PagerDuty (SNS Alert) notifica plantonista → N1 Support (Monitor) triagem inicial via playbook → N2 Engineer (Hotfix) correção temporária → CodeDeploy (Deploy) publica fix em produção. As setas vermelhas indicam urgência e progressão.

Referências & Notas de Curadoria

Literatura técnica, frameworks de gestão e literatura de referência para este módulo.

Data Product Management

Escaping the Build Trap

Melissa Perri (O'Reilly, 2019): O guia definitivo sobre Gestão de Produto (Product Management), focado na transição de entregas táticas (features) para entregas estratégicas (resultados/outcomes) – essencial para embasar o Data Product Canvas.

Domain-Oriented Data

Data Mesh: Delivering Data-Driven Value

Zhamak Dehghani (O'Reilly, 2022): O livro fundacional da criadora do Data Mesh. Detalha os 4 princípios fundamentais, incluindo Data as a Product e Domain-Oriented Ownership.

Confiabilidade & CI/CD

Data Contracts

Chad Sanderson (2023): Literatura sobre como garantir a confiabilidade de dados na origem, implementando Circuit Breakers no CI/CD entre times de Engenharia de Software e Engenharia de Dados.

Priorização de Backlog

RICE Scoring Model

Intercom Framework: Metodologia de priorização que equilibra Reach, Impact, Confidence e Effort. Ajuda o PMO de Dados a justificar decisões quantitativas na priorização do Backlog analítico.

OKRs & Execução

Measure What Matters

John Doerr (Portfolio Penguin, 2018): A bíblia dos OKRs. Doerr, aluno de Andy Grove na Intel, documenta como o framework foi adotado pelo Google, Gates Foundation e Bono (ONE Campaign). Essencial para alinhar OKRs de dados com a estratégia corporativa.

Scrum & Agilidade

Scrum: A Arte de Fazer o Dobro na Metade do Tempo

Jeff Sutherland (Crown Business, 2014): Co-criador do Scrum, Sutherland detalha os princípios por trás do framework ágil mais popular do mundo. Referência obrigatória para PMOs que adotam Sprints e cerimônias ágeis em projetos de dados.

Extreme Programming

Extreme Programming Explained

Kent Beck (Addison-Wesley, 1999): O manifesto do XP. Beck introduziu TDD, Pair Programming e Continuous Integration — práticas que são a espinha dorsal de pipelines de dados confiáveis e testáveis.

Lean & Eliminação de Desperdício

The Lean Startup

Eric Ries (Crown Business, 2011): Ries adapta os princípios Lean da Toyota para startups de tecnologia. O conceito de MVP (Minimum Viable Product) é diretamente aplicável à criação de MVPs Analíticos — validar hipóteses de dados antes de investir em pipelines complexos.

Toyota Production System

Toyota Production System

Taiichi Ohno (Productivity Press, 1988): A origem do Kanban e do Lean. Ohno criou o sistema de produção que revolucionou a manufatura e que décadas depois inspirou o Agile Software Development e o Kanban para TI.

Gestão de Alto Rendimento

High Output Management

Andy Grove (Vintage, 1983): O criador dos OKRs na Intel. Grove ensina que a produtividade de um gestor é medida pelo output de sua organização — não pelo seu esforço individual. Conceito fundamental para PMOs de dados.

Produtos de Tecnologia

Inspired: How to Create Tech Products Customers Love

Marty Cagan (Wiley, 2018): Cagan, ex-VP de Produto no eBay, argumenta que os melhores produtos nascem de times empoderados ("empowered teams") — não de roadmaps top-down. Referência para Data Product Managers que querem ir além de feature factories.

Kanban para TI

Kanban: Successful Evolutionary Change

David J. Anderson (Blue Hole Press, 2010): Anderson adaptou o Kanban da Toyota para o desenvolvimento de software. O livro detalha WIP Limits, Lead Time, Cycle Time e políticas de fluxo — métricas essenciais para times de sustentação de dados (RUN).

Confiabilidade de Sistemas (SRE)

Site Reliability Engineering (Google SRE Book)

Niall Richard Murphy et al. (O'Reilly, 2016): A fundação da engenharia de confiabilidade moderna pelo Google. Essencial para compreender SLI, SLO, SLA e a cultura de blameless postmortems, aplicando esses conceitos diretamente à resiliência das pipelines de dados.
