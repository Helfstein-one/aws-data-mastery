01

A Evolução do SQL Analítico

De bancos transacionais (OLTP) a Data Lakes distribuídos (OLAP)

Em Engenharia de Dados, o SQL não é usado para inserir um usuário em uma aplicação web, mas sim para processar Terabytes de dados em cluster. Motores MPP (Massively Parallel Processing) como Amazon Redshift, Athena (Presto/Trino) e Apache Spark dependem fortemente do padrão ANSI SQL.

OLTP vs OLAP
O Paradigma Analítico
Transacional (PostgreSQL, RDS): Otimizado para Row-based storage. Operações rápidas de INSERT/UPDATE de registros únicos.
Analítico (Redshift, Iceberg): Otimizado para Columnar storage (Parquet). Operações massivas de agregação (SUM, COUNT) lendo apenas colunas específicas e ignorando linhas não relevantes.
Organização Lógica
Modelagem Multidimensional
Enquanto bancos web usam Normalização (3NF) para evitar redundância, em Data Warehousing (Kimball) usamos o modelo Star Schema: Fatos (métricas) centralizados apontando para Dimensões (contexto). Nos Data Lakes modernos (One Big Table - OBT), frequentemente desnormalizamos para evitar JOINs massivos em rede.
01.5

Fundamentos: DML, DDL e Filtros

As ferramentas essenciais do dia a dia

Apesar dos motores modernos de Data Lakehouse serem extremamente sofisticados, as operações cotidianas ainda dependem do domínio absoluto da tríade clássica do SQL: Filtragem, Agregação e Junção.

1. DDL e DML Básico

Em ambientes de Data Warehouse como Redshift, é comum criarmos tabelas temporárias ou fazermos operações de UPSERT (Merge) para gerenciar dimensões que mudam lentamente (SCD).

SQL
-- Criando Tabela (DDL)
CREATE TABLE raw.users (
    user_id INT PRIMARY KEY,
    name VARCHAR(255),
    created_at TIMESTAMP
);

-- Inserindo Dados (DML)
INSERT INTO raw.users (user_id, name, created_at)
VALUES (1, 'Ana', CURRENT_TIMESTAMP);

-- Merge (UPSERT)
MERGE INTO gold.users_dim t
USING raw.users s
ON t.user_id = s.user_id
WHEN MATCHED THEN
  UPDATE SET name = s.name
WHEN NOT MATCHED THEN
  INSERT (user_id, name, created_at) VALUES (s.user_id, s.name, s.created_at);

2. Agregações e Filtros Avançados

O uso correto de GROUP BY aliado ao HAVING permite filtrar resultados depois da agregação, poupando a necessidade de sub-queries.

SQL
SELECT 
    department,
    COUNT(employee_id) as total_employees,
    AVG(salary) as avg_salary
FROM hr.employees
WHERE status = 'ACTIVE' -- Filtra ANTES de agregar
GROUP BY department
HAVING COUNT(employee_id) > 10 -- Filtra DEPOIS de agregar
ORDER BY avg_salary DESC;

Mestrado em JOINs (Cruza de Tabelas)

O coração de qualquer modelagem relacional. É crucial entender o comportamento de cada JOIN não apenas pela teoria dos conjuntos, mas por suas consequências no motor de processamento (Data Skew, Cartesian Products).

Estratégias de JOIN no SQL
SQL - JOINs Essenciais 
-- 1. INNER JOIN: Mantém APENAS registros que existem em A e B.
-- Perigoso se o id do cliente for NULL, você perderá a venda!
SELECT v.id_venda, c.nome 
FROM vendas v
INNER JOIN clientes c ON v.id_cliente = c.id_cliente;

-- 2. LEFT JOIN (O mais utilizado na engenharia): Mantém TUDO da tabela A (esquerda).
-- Se B não existir, preenche com NULL. 
-- Boas práticas: Sempre que fizer LEFT JOIN, verifique a explosão de cardinalidade (se B tiver IDs duplicados, a linha de A vai se duplicar).
SELECT v.id_venda, c.nome 
FROM vendas v
LEFT JOIN clientes c ON v.id_cliente = c.id_cliente;

-- 3. SUBQUERY com JOIN (Otimizando filtros ANTES do JOIN)
-- Em bases gigantes, é muito mais eficiente reduzir as tabelas antes de cruzar.
SELECT v.id_venda, c_ativos.nome
FROM vendas v
INNER JOIN (
    SELECT id_cliente, nome FROM clientes WHERE status = 'ATIVO'
) c_ativos ON v.id_cliente = c_ativos.id_cliente;

Arrays e LATERAL JOIN (Explosão de Dados)

Bancos modernos (PostgreSQL, Snowflake, Athena) suportam tipos complexos como ARRAY e JSON. Para tabularizar esses arrays em colunas, usamos UNNEST ou LATERAL JOIN.

SQL - Trabalhando com Arrays e LATERAL 
-- ARRAY: Extraindo dados de uma lista
SELECT 
    id_pedido, 
    tags[1] as primeira_tag -- Extrai o primeiro elemento (depende do dialecto, array pode começar em 0 ou 1)
FROM pedidos;

-- LATERAL JOIN / UNNEST / EXPLODE
-- Se a tabela tem: id_pedido=1, produtos=['A', 'B']
-- O UNNEST transforma em duas linhas: (1, 'A') e (1, 'B').
SELECT 
    p.id_pedido,
    item
FROM pedidos p
CROSS JOIN UNNEST(p.lista_produtos) AS t(item); -- Athena / Presto

-- No PostgreSQL usa-se LATERAL ou FROM UNNEST
SELECT 
    p.id_pedido,
    item
FROM pedidos p, LATERAL unnest(p.lista_produtos) as item;

Pivot Tables Puras em SQL

Existem sintaxes prontas (como o PIVOT do Snowflake ou Spark), mas a abordagem universal e mais rápida é usar agregação combinada com lógica de condição inline.

SQL - Transformando Linhas em Colunas (Pivot Clássico) 
SELECT 
    id_loja,
    SUM(CASE WHEN mes = 'JAN' THEN valor ELSE 0 END) as receita_jan,
    SUM(CASE WHEN mes = 'FEV' THEN valor ELSE 0 END) as receita_fev,
    SUM(CASE WHEN mes = 'MAR' THEN valor ELSE 0 END) as receita_mar
FROM vendas
GROUP BY id_loja;

02

SQL Avançado: CTEs e Window Functions

O arsenal do Engenheiro e Analista de Dados

Common Table Expressions (CTEs)

O uso da cláusula WITH melhora a legibilidade, modulariza o código e em muitos otimizadores de query (como o Catalyst do Spark), permite a criação de planos lógicos otimizados de execução, em vez de subqueries encadeadas difíceis de dar manutenção.

SQL 
WITH DailySales AS (
    SELECT 
        DATE(order_timestamp) as sales_date,
        store_id,
        SUM(total_amount) as daily_revenue
    FROM raw_orders
    WHERE status = 'COMPLETED'
    GROUP BY 1, 2
),
StoreRanking AS (
    SELECT 
        sales_date,
        store_id,
        daily_revenue,
        RANK() OVER(PARTITION BY sales_date ORDER BY daily_revenue DESC) as rank_per_day
    FROM DailySales
)
SELECT * FROM StoreRanking WHERE rank_per_day <= 3;

Window Functions (Funções de Janela) & Funções Estatísticas

As Window Functions permitem calcular agregações relativas a uma linha atual, mantendo o nível de detalhe da linha (ao contrário do GROUP BY, que colapsa os dados). Juntamente com estatísticas avançadas, formam o arsenal essencial de um Cientista e Engenheiro de Dados.

Navegação Temporal
LEAD() e LAG()
Compara a linha atual com a anterior ou a próxima. Útil para calcular o churn ou o crescimento dia contra dia (MoM, YoY).
Ranking
ROW_NUMBER(), RANK(), DENSE_RANK()
Gera numeração ou classificação. Essencial para Deduplicação (Top N registros) e para encontrar os campeões de vendas em cada categoria.
SQL - Ranking & Deduplicação 
SELECT 
    user_id,
    purchase_amount,
    -- ROW_NUMBER: Numeração estrita e única (1, 2, 3, 4...). Ideal para deduplicar.
    ROW_NUMBER() OVER(PARTITION BY category ORDER BY purchase_amount DESC) as rn,
    
    -- RANK: Pula números em caso de empate (1, 1, 3, 4...)
    RANK() OVER(PARTITION BY category ORDER BY purchase_amount DESC) as rnk,
    
    -- DENSE_RANK: Não pula números no empate (1, 1, 2, 3...)
    DENSE_RANK() OVER(PARTITION BY category ORDER BY purchase_amount DESC) as dense_rnk
FROM transactions;

SQL - LEAD e LAG (Séries Temporais) 
-- Exemplo Clássico: Variação Mês a Mês (MoM)
WITH VendasMensais AS (
    SELECT 
        mes,
        SUM(valor) as receita_atual
    FROM vendas
    GROUP BY mes
)
SELECT 
    mes,
    receita_atual,
    -- LAG puxa o valor da linha ANTERIOR (mes-1)
    LAG(receita_atual) OVER(ORDER BY mes) as receita_mes_passado,
    
    -- LEAD puxa o valor da linha SEGUINTE (mes+1)
    LEAD(receita_atual) OVER(ORDER BY mes) as receita_proximo_mes,
    
    -- Calculando o crescimento percentual
    ((receita_atual * 1.0 / LAG(receita_atual) OVER(ORDER BY mes)) - 1) * 100 as cresc_percentual
FROM VendasMensais;

Agregações Analíticas (MAX, MIN, COUNT, STDDEV, PERCENTILE)

Além das agregações básicas, motores como Snowflake, Redshift e Spark SQL oferecem cálculos estatísticos essenciais para análise exploratória e detecção de anomalias.

SQL - Estatística Descritiva 
SELECT 
    store_id,
    COUNT(1) as total_transactions,
    MAX(amount) as max_ticket,
    MIN(amount) as min_ticket,
    
    -- Desvio Padrão (STDDEV): Indica a dispersão/volatilidade dos valores.
    -- Se o STDDEV for muito alto, a média (AVG) não é representativa.
    STDDEV(amount) as ticket_volatility,
    
    -- Percentil 90: O valor em que 90% das transações estão abaixo dele.
    -- Muito mais robusto que a Média (AVG) para ignorar outliers milionários.
    PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY amount) as p90_ticket
FROM sales
GROUP BY store_id
HAVING COUNT(1) > 1000; -- Aplica as estatísticas apenas a lojas com volume (Filtro Pós-Agregação)

Lógica Condicional Inline (CASE WHEN)

O CASE WHEN é frequentemente subutilizado. Ele não serve apenas para criar novas colunas, mas também para agregações condicionais (Pivot) dentro de um único SUM() ou COUNT(), economizando múltiplos JOINs.

SQL - CASE WHEN em Agregação (Pivoting) 
SELECT 
    customer_id,
    -- Conta apenas compras acima de 100, no mesmo GROUP BY
    COUNT(CASE WHEN amount > 100 THEN transaction_id ELSE NULL END) as high_value_purchases,
    
    -- Soma o valor gasto, mas atribui peso 2 para finais de semana
    SUM(
        CASE 
            WHEN day_of_week IN ('SAT', 'SUN') THEN amount * 2 
            ELSE amount 
        END
    ) as weighted_spend,
    
    -- Categorização inline baseada em múltiplas condições
    CASE 
        WHEN SUM(amount) > 5000 THEN 'Platinum'
        WHEN SUM(amount) > 1000 THEN 'Gold'
        ELSE 'Silver' 
    END as customer_tier
FROM transactions
GROUP BY customer_id;

A Jornada de Execução (Query Plan)

Entender a ordem em que um motor SQL processa a query é fundamental. O código SQL que você escreve é apenas uma declaração lógica. O motor vai refatorá-lo completamente.

Plano de Execução SQL (Catalyst/Optimizer)
Sequência Lógica vs Execução:

Você escreve: SELECT -> FROM -> WHERE -> GROUP BY -> HAVING -> ORDER BY

O Motor Executa: FROM (Lê os dados) -> WHERE (Filtra partições) -> GROUP BY (Agrega e faz Shuffle) -> HAVING (Filtra agregações) -> SELECT (Seleciona colunas) -> ORDER BY (Ordena memória limitadamente).

Desenhando queries para alta performance

Engenheiros de Dados experientes precisam saber como o banco vai executar sua query por debaixo dos panos, e como extrair valor de tipos de dados complexos (JSON, Arrays).

Debugging
O Comando EXPLAIN
Use EXPLAIN ANALYZE antes de rodar queries em produção. Ele mostra o Plano de Execução, revelando gargalos como Seq Scan (Full Table Scan) e sugerindo onde índices ou partições estão falhando.
Tratamento JSON
Unnest / Lateral View
Ao receber logs brutos contendo Arrays ou JSON, usamos UNNEST (Presto/Athena) ou LATERAL VIEW EXPLODE (Spark/Hive) para "achatar" listas e transformar 1 linha em múltiplas linhas tabulares.
SQL Athena (UNNEST)
-- Achatando um Array de tags JSON de um evento de clique
SELECT 
    event_id,
    user_id,
    tag
FROM raw_events
CROSS JOIN UNNEST(event_tags) AS t(tag)
WHERE event_name = 'page_view';

SQL em Data Lakes: Formatos Abertos

O Motor vs O Armazenamento

No paradigma tradicional, o PostgreSQL "possui" os dados e os gerencia nativamente. No paradigma de Lakehouse na AWS, o dado está no Amazon S3 (em arquivos abertos como Parquet), a tabela lógica está no AWS Glue Data Catalog e você a consulta usando Athena ou EMR.

SQL Athena (Iceberg DDL) 
CREATE TABLE glue_catalog.gold.dim_customers (
    customer_id BIGINT,
    customer_name VARCHAR,
    signup_date DATE,
    ltv DECIMAL(10,2)
)
PARTITIONED BY (signup_date)
LOCATION 's3://meu-datalake-gold/dim_customers/'
TBLPROPERTIES (
  'table_type' ='ICEBERG',
  'format'='parquet',
  'write_compression'='snappy'
);
SQL Athena (Iceberg UPSERT) 
-- Sincronizando dados alterados e novos (Upsert)
MERGE INTO glue_catalog.gold.dim_customers t
USING stg_customers_updates s
ON t.customer_id = s.customer_id
WHEN MATCHED THEN 
  UPDATE SET 
    t.customer_name = s.customer_name,
    t.ltv = s.ltv
WHEN NOT MATCHED THEN 
  INSERT (customer_id, customer_name, signup_date, ltv)
  VALUES (s.customer_id, s.customer_name, s.signup_date, s.ltv);

Boas Práticas de Modelagem Analítica

Organizando Terabytes de dados para consumo eficiente

Consultar dados crus (Raw/Bronze) diretamente em dashboards é uma receita certa para lentidão e altos custos. O motor SQL precisa que os dados estejam modelados para evitar Joins complexos em tempo real.

Star Schema (Kimball)
O Padrão Ouro
Centraliza os eventos em uma tabela longa e estreita (Fato) e as descrições em tabelas curtas e largas (Dimensões). Permite leitura rápida e agregações simples.
OBT / Denormalization
One Big Table
Em bancos colunares modernos, realizar joins pode ser caro. Criamos uma "Única Tabela Grande" onde as dimensões já estão pré-juntadas (desnormalizadas), reduzindo o tempo de leitura ao custo de maior espaço de armazenamento.
Data Vault
Auditoria e Histórico
Modelo focado na camada Enterprise (Hubs, Links, Satellites). Altamente auditável e escalável para múltiplos sistemas de origem, porém demasiadamente complexo para consumo direto por analistas.

Cases Reais de Otimização e Avanço

Arquitetura em ação no mundo corporativo

Case 1: Refatoração com Predicate Pushdown

Cenário: Uma query analítica lendo um bucket S3 com formato Parquet estava demorando 4 horas no Athena.

Ação: A tabela original não estava particionada e a query executava um Full Table Scan (lia todos os arquivos do bucket). O time reescreveu a tabela usando o formato Iceberg particionado por data_evento.

A Otimização: Ao adicionar a cláusula WHERE data_evento = '2026-06-01', o motor do Athena conseguiu ignorar 99% dos arquivos do bucket antes mesmo de lê-los (fenômeno conhecido como Predicate Pushdown), reduzindo a execução para 5 minutos.

Comandos Avançados Adicionais

Existem padrões complexos que resolvem problemas difíceis de estrutura.

SQL - CTE Recursiva (Hierarquias)
-- Encontrando toda a cadeia de liderança de um funcionário
WITH RECURSIVE employee_hierarchy AS (
    -- Caso Base: o CEO (sem gerente)
    SELECT id, name, manager_id, 1 as level
    FROM employees WHERE manager_id IS NULL

    UNION ALL

    -- Passo Recursivo: junta os funcionários com os gerentes encontrados
    SELECT e.id, e.name, e.manager_id, h.level + 1
    FROM employees e
    JOIN employee_hierarchy h ON e.manager_id = h.id
)
SELECT * FROM employee_hierarchy;
SQL - Pivot Analítico Manual
-- Transformando linhas em colunas (quando o banco não suporta PIVOT nativo)
SELECT 
    vendedor_id,
    SUM(CASE WHEN trimestre = 'Q1' THEN valor_venda ELSE 0 END) AS total_q1,
    SUM(CASE WHEN trimestre = 'Q2' THEN valor_venda ELSE 0 END) AS total_q2,
    SUM(CASE WHEN trimestre = 'Q3' THEN valor_venda ELSE 0 END) AS total_q3
FROM vendas
GROUP BY vendedor_id;
