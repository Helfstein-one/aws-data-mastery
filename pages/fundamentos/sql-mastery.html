Arquitetura relacional vs Lakehouse, modelagem, funções de janela (Window Functions), CTEs e boas práticas para queries analíticas distribuídas.

01

A Evolução do SQL Analítico

De bancos transacionais (OLTP) a Data Lakes distribuídos (OLAP)

Em Engenharia de Dados, o SQL não é usado para inserir um usuário em uma aplicação web, mas sim para processar Terabytes de dados em cluster. Motores MPP (Massively Parallel Processing) como Amazon Redshift, Athena (Presto/Trino) e Apache Spark dependem fortemente do padrão ANSI SQL.

OLTP vs OLAP
O Paradigma Analítico
Transacional (PostgreSQL, RDS): Otimizado para Row-based storage. Operações rápidas de INSERT/UPDATE de registros únicos.
Analítico (Redshift, Iceberg): Otimizado para Columnar storage (Parquet). Operações massivas de agregação (SUM, COUNT) lendo apenas colunas específicas e ignorando linhas não relevantes.
Organização Lógica
Modelagem Multidimensional
Enquanto bancos web usam Normalização (3NF) para evitar redundância, em Data Warehousing (Kimball) usamos o modelo Star Schema: Fatos (métricas) centralizados apontando para Dimensões (contexto). Nos Data Lakes modernos (One Big Table - OBT), frequentemente desnormalizamos para evitar JOINs massivos em rede.
01.5

Fundamentos: DML, DDL e Filtros

As ferramentas essenciais do dia a dia

Apesar dos motores modernos de Data Lakehouse serem extremamente sofisticados, as operações cotidianas ainda dependem do domínio absoluto da tríade clássica do SQL: Filtragem, Agregação e Junção.

1. DDL e DML Básico

Em ambientes de Data Warehouse como Redshift, é comum criarmos tabelas temporárias ou fazermos operações de UPSERT (Merge) para gerenciar dimensões que mudam lentamente (SCD).

SQL
-- Criando Tabela (DDL)
CREATE TABLE raw.users (
    user_id INT PRIMARY KEY,
    name VARCHAR(255),
    created_at TIMESTAMP
);

-- Inserindo Dados (DML)
INSERT INTO raw.users (user_id, name, created_at)
VALUES (1, 'Ana', CURRENT_TIMESTAMP);

-- Merge (UPSERT)
MERGE INTO gold.users_dim t
USING raw.users s
ON t.user_id = s.user_id
WHEN MATCHED THEN
  UPDATE SET name = s.name
WHEN NOT MATCHED THEN
  INSERT (user_id, name, created_at) VALUES (s.user_id, s.name, s.created_at);

2. Agregações e Filtros Avançados

O uso correto de GROUP BY aliado ao HAVING permite filtrar resultados depois da agregação, poupando a necessidade de sub-queries.

SQL
SELECT 
    department,
    COUNT(employee_id) as total_employees,
    AVG(salary) as avg_salary
FROM hr.employees
WHERE status = 'ACTIVE' -- Filtra ANTES de agregar
GROUP BY department
HAVING COUNT(employee_id) > 10 -- Filtra DEPOIS de agregar
ORDER BY avg_salary DESC;
02

SQL Avançado: CTEs e Window Functions

O arsenal do Engenheiro e Analista de Dados

Common Table Expressions (CTEs)

O uso da cláusula WITH melhora a legibilidade, modulariza o código e em muitos otimizadores de query (como o Catalyst do Spark), permite a criação de planos lógicos otimizados de execução, em vez de subqueries encadeadas difíceis de dar manutenção.

SQL 
WITH DailySales AS (
    SELECT 
        DATE(order_timestamp) as sales_date,
        store_id,
        SUM(total_amount) as daily_revenue
    FROM raw_orders
    WHERE status = 'COMPLETED'
    GROUP BY 1, 2
),
StoreRanking AS (
    SELECT 
        sales_date,
        store_id,
        daily_revenue,
        RANK() OVER(PARTITION BY sales_date ORDER BY daily_revenue DESC) as rank_per_day
    FROM DailySales
)
SELECT * FROM StoreRanking WHERE rank_per_day <= 3;

Window Functions (Funções de Janela)

As Window Functions permitem calcular agregações relativas a uma linha atual, mantendo o nível de detalhe da linha (ao contrário do GROUP BY, que colapsa os dados). É essencial para calcular médias móveis, ranking e valores de D-1 (Lead/Lag).

Navegação Temporal
LEAD() e LAG()
Compara a linha atual com a anterior ou a próxima. Útil para calcular o churn ou o crescimento dia contra dia (MoM, YoY).
Ranking
ROW_NUMBER() e RANK()
Gera numeração ou classificação. Amplamente utilizado para Deduplicação (pegar o evento mais recente particionado pelo user_id ordenado pela data decrescente e manter apenas rn = 1).
02.5

Técnicas Avançadas e Otimização

Desenhando queries para alta performance

Engenheiros de Dados experientes precisam saber como o banco vai executar sua query por debaixo dos panos, e como extrair valor de tipos de dados complexos (JSON, Arrays).

Debugging
O Comando EXPLAIN
Use EXPLAIN ANALYZE antes de rodar queries em produção. Ele mostra o Plano de Execução, revelando gargalos como Seq Scan (Full Table Scan) e sugerindo onde índices ou partições estão falhando.
Tratamento JSON
Unnest / Lateral View
Ao receber logs brutos contendo Arrays ou JSON, usamos UNNEST (Presto/Athena) ou LATERAL VIEW EXPLODE (Spark/Hive) para "achatar" listas e transformar 1 linha em múltiplas linhas tabulares.
SQL Athena (UNNEST)
-- Achatando um Array de tags JSON de um evento de clique
SELECT 
    event_id,
    user_id,
    tag
FROM raw_events
CROSS JOIN UNNEST(event_tags) AS t(tag)
WHERE event_name = 'page_view';
03

SQL em Data Lakes: Formatos Abertos

O Motor vs O Armazenamento

No paradigma tradicional, o PostgreSQL "possui" os dados e os gerencia nativamente. No paradigma de Lakehouse na AWS, o dado está no Amazon S3 (em arquivos abertos como Parquet), a tabela lógica está no AWS Glue Data Catalog e você a consulta usando Athena ou EMR.

SQL Athena (Iceberg DDL) 
CREATE TABLE glue_catalog.gold.dim_customers (
    customer_id BIGINT,
    customer_name VARCHAR,
    signup_date DATE,
    ltv DECIMAL(10,2)
)
PARTITIONED BY (signup_date)
LOCATION 's3://meu-datalake-gold/dim_customers/'
TBLPROPERTIES (
  'table_type' ='ICEBERG',
  'format'='parquet',
  'write_compression'='snappy'
);
04

Boas Práticas de Modelagem Analítica

Organizando Terabytes de dados para consumo eficiente

Consultar dados crus (Raw/Bronze) diretamente em dashboards é uma receita certa para lentidão e altos custos. O motor SQL precisa que os dados estejam modelados para evitar Joins complexos em tempo real.

Star Schema (Kimball)
O Padrão Ouro
Centraliza os eventos em uma tabela longa e estreita (Fato) e as descrições em tabelas curtas e largas (Dimensões). Permite leitura rápida e agregações simples.
OBT / Denormalization
One Big Table
Em bancos colunares modernos, realizar joins pode ser caro. Criamos uma "Única Tabela Grande" onde as dimensões já estão pré-juntadas (desnormalizadas), reduzindo o tempo de leitura ao custo de maior espaço de armazenamento.
Data Vault
Auditoria e Histórico
Modelo focado na camada Enterprise (Hubs, Links, Satellites). Altamente auditável e escalável para múltiplos sistemas de origem, porém demasiadamente complexo para consumo direto por analistas.

Cases Reais de Otimização e Avanço

Arquitetura em ação no mundo corporativo

Case 1: Refatoração com Predicate Pushdown

Cenário: Uma query analítica lendo um bucket S3 com formato Parquet estava demorando 4 horas no Athena.

Ação: A tabela original não estava particionada e a query executava um Full Table Scan (lia todos os arquivos do bucket). O time reescreveu a tabela usando o formato Iceberg particionado por data_evento.

A Otimização: Ao adicionar a cláusula WHERE data_evento = '2026-06-01', o motor do Athena conseguiu ignorar 99% dos arquivos do bucket antes mesmo de lê-los (fenômeno conhecido como Predicate Pushdown), reduzindo a execução para 5 minutos.

Comandos Avançados Adicionais

Existem padrões complexos que resolvem problemas difíceis de estrutura.

SQL - CTE Recursiva (Hierarquias)
-- Encontrando toda a cadeia de liderança de um funcionário
WITH RECURSIVE employee_hierarchy AS (
    -- Caso Base: o CEO (sem gerente)
    SELECT id, name, manager_id, 1 as level
    FROM employees WHERE manager_id IS NULL

    UNION ALL

    -- Passo Recursivo: junta os funcionários com os gerentes encontrados
    SELECT e.id, e.name, e.manager_id, h.level + 1
    FROM employees e
    JOIN employee_hierarchy h ON e.manager_id = h.id
)
SELECT * FROM employee_hierarchy;
SQL - Pivot Analítico Manual
-- Transformando linhas em colunas (quando o banco não suporta PIVOT nativo)
SELECT 
    vendedor_id,
    SUM(CASE WHEN trimestre = 'Q1' THEN valor_venda ELSE 0 END) AS total_q1,
    SUM(CASE WHEN trimestre = 'Q2' THEN valor_venda ELSE 0 END) AS total_q2,
    SUM(CASE WHEN trimestre = 'Q3' THEN valor_venda ELSE 0 END) AS total_q3
FROM vendas
GROUP BY vendedor_id;
