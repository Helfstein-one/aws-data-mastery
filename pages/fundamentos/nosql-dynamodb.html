NoSQL & Amazon DynamoDB

A arquitetura definitiva de bancos Serverless: Single-Table Design, GSIs, e Change Data Capture (CDC) via Streams para alta volumetria e latência na casa dos milissegundos.

01

Conceitos Core & O Paradigma NoSQL

O DynamoDB rompe com o modelo relacional tradicional

O Amazon DynamoDB é um banco de dados NoSQL chave-valor e de documentos, totalmente gerenciado, multi-AZ e serverless. Projetado por Werner Vogels (CTO da Amazon) para sobreviver a picos massivos de tráfego de E-commerce, ele garante latência de milissegundos em qualquer escala (seja 1 GB ou 100 TB).

RDBMS Clássico DynamoDB Definição Arquitetural
Tabela Table Coleção de Itens. Sem schema fixo, exceto pelas Chaves Primárias.
Linha / Registro Item Coleção de Atributos. Limite físico estrito de 400 KB por item.
Coluna Attribute Tipos suportados: Escalares (String, Number, Binary), Documentos (List, Map) e Sets.
Primary Key Partition Key (PK) A PK passa por uma função de Hash que determina exatamente em qual partição física de armazenamento da AWS o dado residirá.
Composite Key PK + Sort Key (SK) A PK agrupa itens no mesmo disco (Item Collection); a SK organiza os itens de forma Lexicográfica (alfabética/numérica) dentro dessa partição.
02

Modelagem Avançada: Single-Table Design

A Engenharia por trás do "Fim do N+1"

A "Regra de Ouro" da AWS para o DynamoDB é: Mantenha o número de tabelas o menor possível (idealmente 1). O padrão Single-Table Design (STD) elimina a necessidade de JOINs consolidando múltiplas entidades.

SINGLE-TABLE DESIGN: VISUALIZAÇÃO DE PARTICIONAMENTO
DE RELACIONAL (ERD) PARA DYNAMODB (ADJACENCY LIST)

Legenda do Diagrama

  • Item Collection: Toda a caixa tracejada representa uma Partição Física (disco) da AWS onde PK=USER#101.
  • Adjacency List: Perfil, Pedido e Itens coexistem juntos no mesmo disco, ordenados alfabeticamente pela SK.
  • Query Range: Buscar por SK begins_with("ORDER") retorna os pedidos na hora, eliminando JOINs relacionais.
Terraform: Tabela Genérica Single-Table
resource "aws_dynamodb_table" "ecommerce" {
  name         = "ecommerce-single-table"
  billing_mode = "PAY_PER_REQUEST" # On-Demand (Serverless Scale)
  hash_key     = "PK"
  range_key    = "SK"

  attribute { name = "PK"; type = "S" }
  attribute { name = "SK"; type = "S" }
}
💡
Por que modelar assim? (Adjacency List Pattern)

Se um Banco Relacional normaliza os dados usando Chaves Estrangeiras (ERD clássico do Power Designer com 3 tabelas diferentes), o DynamoDB os desnormaliza e pre-junta em uma Adjacency List. Ao acessar a aplicação, você faz uma Query(PK="USER#101") e a rede retorna, em um único bloco, tanto o perfil do usuário quanto suas faturas e pedidos, pois todos compartilham a mesma Partição Física Exclusiva.

EXEMPLO 2: REDE SOCIAL (1:N:N) - ADJACENCY LIST AVANÇADA
🔥
Padrão de Acesso Massivo (Rede Social)

Imagine carregar o Feed de um Usuário. No mundo SQL, faríamos um `SELECT * FROM Users JOIN Posts JOIN Comments`. No DynamoDB, armazenamos o Perfil, os Posts e os Comentários do Post na mesma partição. A chave `USER#alex99` agrupa tudo. Uma única Query varre a partição e devolve a tela inteira renderizada em menos de 10 milissegundos.

Hierarquia e Padrões de SK (Sort Key)

A chave de ordenação usa delimitadores para construir buscas hierárquicas. Exemplo: Se a SK for PAIS#ESTADO#CIDADE (Ex: BR#SP#SAOPAULO), você pode usar o operador matemático begins_with("BR#SP") para retornar todas as cidades de SP em uma única query otimizada.

EXEMPLO 3: IOT TIME-SERIES (SK COMO TIMESTAMP)

Neste exemplo 3 (IoT), demonstramos como salvar leituras contínuas de sensores. Ao invés de uma Adjacency List de entidades diferentes, usamos a Sort Key como um Timestamp (ISO-8601). Isso é fundamental pois a Sort Key suporta operadores matemáticos. Podemos fazer `Query(PK="SENSOR#T78", SK BETWEEN data1 AND data2)` e o DynamoDB agirá como uma Timeseries Database extremamente veloz.

EXEMPLO 4: GAMING LEADERBOARD (GLOBAL SECONDARY INDEX)

Legenda do Diagrama

  • Tabela Base: Organizada por Jogador (PK) e Jogo (SK). Ótima para ver o histórico do Jogador.
  • GSI (Global Secondary Index): Clona os dados invertendo a lógica: agrupa pelo Jogo (GSI_PK) e ordena pela Pontuação (GSI_SK) para gerar o Ranking Mundial nativamente.
Terraform: Criando o GSI de Leaderboard
resource "aws_dynamodb_table" "gaming" {
  name         = "gaming-leaderboards"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "PK"
  range_key    = "SK"

  attribute { name = "PK"; type = "S" }
  attribute { name = "SK"; type = "S" }
  attribute { name = "Score"; type = "N" } # Número

  # GSI: Invertendo os atributos para Placar
  global_secondary_index {
    name               = "LeaderboardIndex"
    hash_key           = "SK"       # ID do Jogo vira PK
    range_key          = "Score"    # Score vira a SK para ordenação
    projection_type    = "INCLUDE"
    non_key_attributes = ["PlayerName"]
  }
}

No Exemplo 4 (Gaming Leaderboard), entramos no território dos Global Secondary Indexes (GSI). A Tabela Base é modelada para o Padrão de Acesso primário: Recuperar todo o histórico de um Jogador (`PK=PLAYER#ID`). Mas e se o negócio exigir um Ranking Global por Jogo? A Tabela Base falharia (exigiria um *Scan* letal).

⚠️
A Mágica do GSI (Inversão de Índice)

O GSI é um índice clonado em background pela AWS. Nele, nós invertemos a chave: A GSI_PK passa a ser o ID do Jogo (`GAME#ZELDA`) e a GSI_SK passa a ser o Score. Dessa forma, podemos realizar uma Query simples ordenando numericamente e o Leaderboard sai pronto, sem onerar a tabela primária.

03

Matemática de Provisionamento: RCU & WCU

Entendendo a cobrança por trás das operações do banco

A diferença do DynamoDB para RDBMS é que você não escolhe instâncias de servidor (CPU/RAM). Você provisiona Capacidade de Leitura e Escrita baseada em requisições por segundo e tamanho do Payload em KB.

Read Capacity Unit (RCU)

1 RCU permite ler 1 item de até 4 KB por segundo (em consistência Forte).

  • Strongly Consistent: 1 leitura = 1 RCU (até 4KB).
  • Eventually Consistent: 2 leituras = 1 RCU (metade do preço!).
  • Transactional: 1 leitura = 2 RCUs (o dobro do preço).

Ex: Ler 10 itens de 3KB via Query Forte:

R: (10 * (4KB arredondado)) / 4 = 10 RCUs.

Write Capacity Unit (WCU)

1 WCU permite escrever 1 item de até 1 KB por segundo.

  • Standard Write: 1 escrita = 1 WCU (até 1KB).
  • Transactional Write: 1 escrita = 2 WCUs.
  • O tamanho é sempre arredondado para cima. Se você escrever 1.5 KB, custará 2 WCUs.

Ex: Escrever 5 itens de 2.5KB:

R: (2.5 -> 3KB). 5 * 3 = 15 WCUs.

04

DynamoDB Streams & Integração Lakehouse

O Change Data Capture (CDC) do NoSQL da AWS

O DynamoDB Streams captura uma sequência cronológica de eventos de mutação na tabela (INSERT, MODIFY, REMOVE) e garante a retenção em shard por 24 horas. É a principal mecânica de integração Event-Driven do banco.

ARQUITETURA DE CDC COM DYNAMODB STREAMS

Você pode configurar o Stream com opções de StreamViewType, como:

  • KEYS_ONLY: Apenas a PK e SK do item modificado.
  • NEW_IMAGE: Todo o estado do item após a modificação.
  • OLD_IMAGE: O estado do item antes da modificação.
  • NEW_AND_OLD_IMAGES: O *antes* e o *depois*, perfeito para detecção de anomalias com Lambdas.
05

Implementação em Terraform: Billing & TTL

Provisionamento Enterprise via HCL

Abaixo, a configuração padrão para inicializar uma tabela com Auto-scaling (PAY_PER_REQUEST), habilitando o Time To Live (TTL) para exclusão automática de registros antigos (sem consumir WCU), e o GSI.

main.tf (HCL) 
resource "aws_dynamodb_table" "ecommerce" {
  name         = "ecommerce-single-table"
  billing_mode = "PAY_PER_REQUEST" # On-Demand, escala até 40K WCUs sem provisionamento
  hash_key     = "PK"
  range_key    = "SK"

  attribute { name = "PK"; type = "S" }
  attribute { name = "SK"; type = "S" }
  attribute { name = "GSI1PK"; type = "S" }
  attribute { name = "GSI1SK"; type = "S" }

  # Apaga itens velhos de graça se eles contiverem o atributo unix timestamp "ExpirationTime"
  ttl {
    attribute_name = "ExpirationTime"
    enabled        = true
  }

  global_secondary_index {
    name               = "GSI1"
    hash_key           = "GSI1PK"
    range_key          = "GSI1SK"
    projection_type    = "INCLUDE"
    non_key_attributes = ["Status", "TotalValue"]
  }

  stream_enabled   = true
  stream_view_type = "NEW_AND_OLD_IMAGES"
}

Simulador de Entrevista & Boas Práticas

Resolvendo Problemas Críticos de Modelagem

Cenário Corporativo (Desafio) Padrão Arquitetural / Solução
1. "Hot Partition": Uma eleição fez com que a chave PK=VOTO#CANDIDATO_X recebesse 5.000 requisições/seg. Ocorreu Throttling. Implementar Write Sharding. Adicionamos um sufixo aleatório na PK (ex: VOTO#CANDIDATO_X_1 a _10). Isso espalha a carga por 10 partições físicas, resolvendo o afunilamento térmico do hardware.
2. Precisamos buscar todos os usuários por Data de Criação, algo que não está na PK base da tabela. Criar um GSI (Global Secondary Index) onde a Partition Key pode ser algo global (ex: USER_GROUP) e a Sort Key é a CreatedAt, projetando os atributos desejados da tabela original.
3. Qual a diferença letal entre Scan e Query no seu script de faturamento? A Query busca apenas a partição específica e é RCU-eficiente (ex: 2 RCUs). O Scan lê a tabela inteira (mesmo que haja filtros pós-leitura), podendo consumir milhares de RCUs atoa e causar pico de fatura. Regra: Jamais use Scan em produção.
4. O DynamoDB tem limite de 400KB por item. O usuário subiu um JSON de metadados de 2MB. O que fazer? Usar o padrão S3 Offloading. Salvar o payload grande no S3 e gravar apenas a URL do objeto no atributo do item no DynamoDB.
