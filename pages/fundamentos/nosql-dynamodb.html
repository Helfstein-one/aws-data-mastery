DynamoDB NoSQL Single-Table K-V Store Streams

Conceitos Core do DynamoDB

O Amazon DynamoDB é um banco de dados NoSQL chave-valor e de documentos, totalmente gerenciado e *serverless*. Ele foi projetado para rodar aplicações de alto desempenho em qualquer escala. A estrutura base do DynamoDB rompe com o modelo relacional tradicional:

RDBMS Clássico DynamoDB Definição no NoSQL
Tabela Table Coleção de Itens. Sem schema fixo.
Linha / Registro Item Coleção de Atributos (limite de 400KB por item).
Coluna Attribute Dado fundamental. Tipos: String, Number, Binary, Map, List.
Primary Key Partition Key (PK) Define em qual nó/partição o dado será armazenado (Hashing físico).
Composite Key PK + Sort Key (SK) A PK agrupa itens na mesma partição física, e a SK ordena os itens lexograficamente dentro dessa partição.
⚡

Single-Table Design

A "Regra de Ouro" do DynamoDB ditada pela AWS é: Mantenha o número de tabelas o menor possível (idealmente apenas 1). O padrão Single-Table Design (STD) consolida diferentes entidades (Ex: Clientes, Pedidos, Itens de Pedido) em uma única tabela usando nomes genéricos de PK e SK.

💡
Por que Single-Table?

O DynamoDB não possui JOINs. Se você normalizar os dados em múltiplas tabelas, precisará fazer múltiplas requisições de rede para carregar uma página (Problema N+1). No STD, você pre-calcula e "pre-junta" os dados gravando-os em Coleções de Itens (Item Collections) baseadas na mesma PK. Com apenas um Query() na PK do Cliente, você retorna os dados do cliente e todos os seus pedidos na mesma requisição de milissegundos.

Exemplo de Mapeamento Single-Table

Item Collection (PK = CUSTOMER#123) 
PK                 SK                    EntityType   Attributes
------------------ --------------------- ------------ -------------------------
CUSTOMER#123       PROFILE#123           Customer     { "Name": "Maria", "Tier": "Gold" }
CUSTOMER#123       ORDER#998             Order        { "Date": "2023-10-01", "Total": 150 }
CUSTOMER#123       ORDER#999             Order        { "Date": "2023-10-15", "Total": 320 }

Fazendo uma operação Query(PK="CUSTOMER#123", SK begins_with "ORDER#"), você recupera nativamente todo o histórico de compras da Maria, já ordenado (pois a SK dita a ordem de armazenamento físico na partição).

🔍

Índices Secundários (GSIs e LSIs)

A arquitetura de chave primária serve para otimizar os padrões de acesso mais frequentes. Porém, e quando precisamos consultar a tabela por atributos não previstos na Chave Primária? É aqui que entram os Índices Secundários.

Global Secondary Index (GSI)

Permite criar uma nova Partition Key e nova Sort Key copiando (projetando) os dados da tabela base para uma estrutura otimizada nos bastidores.

  • Pode ser criado ou apagado a qualquer momento.
  • Tem sua própria capacidade provisionada de leitura/escrita.
  • Consome o dobro do armazenamento e custo de escrita, pois replica o item.
  • As leituras no GSI são fortemente Eventuais (Eventual Consistency).

Local Secondary Index (LSI)

Mantém a mesma Partition Key da tabela principal, mas altera a Sort Key. Usado quando você precisa classificar a mesma coleção de itens de formas diferentes.

  • Obrigatório: Só pode ser criado no momento da criação da tabela.
  • Limita o tamanho da partição base a 10GB.
  • Usa a capacidade de provisionamento da tabela principal.
  • Suporta leituras fortemente consistentes.

DynamoDB Streams & Change Data Capture (CDC)

O DynamoDB Streams captura uma sequência cronológica de eventos de nível de item em qualquer tabela. Trata-se do verdadeiro Change Data Capture (CDC) do ecossistema NoSQL da AWS.

Ao habilitar o Stream, sempre que um item for criado, alterado ou excluído, o DynamoDB envia um log com a alteração que fica disponível por 24 horas. Esses fluxos são o gatilho perfeito para uma AWS Lambda que processa eventos em near-real-time.

🔥
Use Cases Poderosos do DynamoDB Streams:
  • Replicação de dados em Analytics: Ingestão contínua das mutações da tabela para o S3 Lakehouse ou agregação/Roll-Up views (CQRS).
  • Auditoria e Log de Transações.
  • Notificações Automáticas (ex: Disparar um e-mail de "Boas-vindas" sempre que um Insert ocorrer na tabela de Users).
  • Sincronização com OpenSearch para habilitar Full-Text Search dos dados da tabela.

Padrões de Precificação Básicos

O DynamoDB oferece dois modos flexíveis de cobrança, adequados para as diferentes maturidades do seu workload:

  • On-Demand: Você não provisiona capacidade. O DynamoDB escala automaticamente e cobra exatemente pelos Write Request Units (WRU) e Read Request Units (RRU) consumidos. Ideal para cargas imprevisíveis, Data Lakes e workloads esporádicos.
  • Provisioned (Com Auto Scaling): Você especifica os WCU (Write Capacity Units) e RCU (Read Capacity Units). Mais barato em cenários com tráfego denso e previsível (baseline constante).
