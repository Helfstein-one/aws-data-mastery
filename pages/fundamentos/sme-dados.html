SME, Delivery & Cultura Ágil

O papel do Subject Matter Expert (SME), metodologias ágeis aplicadas a dados, métricas de fluxo, ritos e gestão de backlog.

O Papel Crítico do SME (Subject Matter Expert)

O SME atua como a ponte vital entre os engenheiros de dados e as regras de negócio complexas do sistema de origem. Enquanto a engenharia foca em escalabilidade, governança e performance, o SME detém o conhecimento profundo sobre o que o dado significa. Ele garante que as transformações aplicadas no pipeline não distorçam a realidade do negócio.

Por que o SME é indispensável?

Sem um SME, a equipe técnica pode ingerir e processar terabytes de dados perfeitamente sob a ótica da infraestrutura, mas entregar tabelas que não respondem às perguntas de negócio. O SME valida o mapeamento de domínios, regras de qualidade e o glossário de negócios, mitigando o risco de construir "o produto certo do jeito errado".

Waterfall vs. Ágil: Quando Usar Cada Abordagem

A escolha entre metodologias não é uma questão de "certo ou errado", mas de contexto. No setor bancário, ambas coexistem — projetos regulatórios com escopo fixo (BACEN, LGPD) podem exigir Waterfall, enquanto produtos de dados com alto grau de experimentação se beneficiam do Ágil.

"Scrum não é uma metodologia. É um framework que expõe problemas organizacionais que antes ficavam escondidos sob camadas de processos burocráticos."
— Jeff Sutherland, Scrum: The Art of Doing Twice the Work in Half the Time (2014)

As 4 Metodologias Ágeis Essenciais

Cada metodologia ágil resolve um problema diferente. O PMO de Dados deve conhecer todas para orquestrar o framework mais adequado ao contexto do time e do projeto:

🏉 Scrum

Autor: Jeff Sutherland & Ken Schwaber (1995)

Framework baseado em Sprints (ciclos de 2-4 semanas) com papéis definidos (Product Owner, Scrum Master, Dev Team). Cerimônias: Planning, Daily, Review, Retrospective.

Quando usar: Projetos de dados com escopo parcialmente definido, onde o backlog pode ser priorizado e fatiado em entregas incrementais. Ex: construção de um Data Lakehouse.

📋 Kanban

Autor: David J. Anderson (2010), inspirado por Taiichi Ohno (Toyota, 1950s)

Sistema de fluxo contínuo com foco em visualização do trabalho, limitação de WIP (Work In Progress) e melhoria incremental. Não possui sprints fixos.

Quando usar: Sustentação (RUN) de plataformas de dados, suporte a incidentes, equipes que precisam de flexibilidade para priorizar sob demanda. Ex: time de Data Ops.

⚡ Extreme Programming (XP)

Autor: Kent Beck (1999)

Foco em excelência técnica: TDD (Test-Driven Development), Pair Programming, Refactoring contínuo, Integração Contínua e entregas frequentes (releases semanais).

Quando usar: Times de engenharia de dados altamente técnicos que precisam de qualidade de código impecável. Ex: desenvolvimento de frameworks internos de ETL.

🏭 Lean

Autor: Taiichi Ohno (Toyota Production System, 1950s), popularizado por Eric Ries (The Lean Startup, 2011)

Filosofia de eliminação de desperdício (Muda). Os 7 desperdícios de Lean aplicados a dados: código não-usado, documentação excessiva, espera por acessos IAM, handoffs entre times, features nunca consumidas, defeitos em produção, processamento desnecessário.

Quando usar: Validação rápida de hipóteses com dados (MVP Analytics). Ex: antes de construir um pipeline completo, criar uma prova de conceito com dados amostrais no Jupyter Notebook.

"Lean thinking muda a pergunta fundamental de 'como podemos fazer isso mais rápido?' para 'deveríamos estar fazendo isso em primeiro lugar?'"
— Eric Ries, The Lean Startup (Crown Business, 2011)

Agile para Dados: Por que o Scrum tradicional falha?

Muitas organizações tentam empurrar o *Scrum para Engenharia de Software* goela abaixo na Engenharia de Dados. Isso causa frustração imediata, pois a incerteza inicial em dados é muito maior: "O campo que o negócio precisa sequer existe preenchido no banco de origem".

A Importância dos "Spikes"

Em Engenharia de Dados, uma User Story nunca deve ser estimada (no Planning Poker) se a origem dos dados for uma "Caixa Preta". Em vez disso, o PMO deve priorizar um Spike Técnico (Time-boxed). O engenheiro passa 2 dias apenas investigando o banco de origem e reporta a qualidade. Só então, na sprint seguinte, estima-se o trabalho real.

Definition of Ready (DoR) Estrito

Um Card só pode entrar no fluxo de desenvolvimento (In Progress) se cumprir o DoR rigoroso: Os acessos de IAM já foram concedidos? O Data Contract foi assinado pelo produtor? O banco de origem tem histórico de pelo menos 6 meses para o modelo treinar? Se faltar um requisito, a task volta para o *Backlog Refinement*.

Framework ICE: Priorização Quantitativa

O ICE Score, criado por Sean Ellis (autor de Hacking Growth), é um dos métodos mais objetivos para priorizar iniciativas de dados. Cada item recebe uma nota de 1 a 10 em três dimensões:

I — Impact (Impacto)

Qual o impacto esperado se essa iniciativa for bem-sucedida? Considere: receita gerada, custo evitado, clientes impactados ou risco mitigado.

Exemplo: Um modelo de detecção de fraude PIX pode evitar R$ 2M/mês em perdas = Impact: 9

C — Confidence (Confiança)

Quão confiante o time está de que essa iniciativa vai funcionar? Baseado em evidências, dados históricos, spikes técnicos já realizados.

Exemplo: Já fizemos um spike e o modelo atingiu 85% de precisão com dados amostrais = Confidence: 8

E — Ease (Facilidade)

Quão fácil é implementar? Considere: complexidade técnica, dependências de outros times, acessos IAM necessários, disponibilidade de dados.

Exemplo: Dados já existem na Gold Layer, precisa apenas treinar modelo = Ease: 7

ICE Score = (Impact + Confidence + Ease) / 3

Exemplo: (9 + 8 + 7) / 3 = 8.0 — Alta prioridade

Iniciativa Impact Confidence Ease ICE Score Decisão
Modelo Anti-Fraude PIX (SageMaker) 9 8 7 8.0 ✅ Priorizar
Dashboard Real-Time de Transações 7 9 6 7.3 ⏳ Backlog (próximo quarter)

Um erro comum é priorizar tarefas fáceis porém de baixo impacto. No exemplo acima, "Refatorar Nomes de Colunas" tem ICE 7.0, mas o Impact é apenas 2. O PMO deve usar o ICE como input, nunca como decisão final. Sempre questione: "Se esta tarefa for bem-sucedida, o CEO vai notar?" Se a resposta for não, desça a prioridade.

Deep Dive: ICE vs. RICE no Cenário Bancário

Ao adicionar a variável Reach (Alcance), a priorização pode ser invertida, especialmente em bancos de varejo onde o volume dita o ROI:

ICE = Média Simples (Impact + Confidence + Ease)

RICE = (Reach × Impact × Confidence) / Effort

Iniciativa Reach Impact Confidence Effort ICE (1-10) RICE Score
Motor de Risco PMEs 100.000 clientes 7 90% (0.9) 4 (Meses) 7.0 (Média) 157.500
Dash. Diretoria 20 executivos 9 100% (1.0) 1 (Mês) 9.3 (Média) 180

Conclusão: Pelo ICE, o Dashboard para a Diretoria ganha pela facilidade e alto impacto percebido (9.3 vs 7.0). No entanto, o RICE expõe a verdadeira escala de negócios (157.500 vs 180), forçando o banco a focar no Motor de Risco que atinge massivamente as PMEs.

Ritos Ágeis Adaptados para Dados

Os cerimoniais ágeis tradicionais precisam ser ajustados para a realidade de engenharia de dados, onde a incerteza técnica costuma ser maior.

  • Backlog Grooming (Refinamento de Dados): O papel do SME brilha aqui. O refinamento não é apenas ler histórias, mas sim traduzir regras de negócio complexas em queries lógicas ou definições de transformação. Durante a sessão, o SME orienta a equipe de engenharia mostrando quais filtros temporais aplicar, quais status ignorar e como lidar com dados duplicados lógicos (ex: estornos de cartão). O SME deve apresentar o mapeamento de domínios e até mesmo pseudo-código SQL para balizar o desenvolvimento. Sem isso, a engenharia assume premissas incorretas.
  • Sprint Review: Não demonstre código de pipeline ou logs de orquestrador. A revisão deve focar em demonstrar o valor final e funcional ao usuário: queries funcionais, dashboards atualizados ou resultados práticos.

— Ken Schwaber & Jeff Sutherland, The Scrum Guide

Quadro Kanban / Fluxo de Entrega (Scrum Board)

O fluxo de entrega ágil (Delivery Flow) no desenvolvimento de pipelines e produtos de dados demanda etapas específicas de validação e qualidade para garantir que as entregas gerem valor confiável ao negócio.

KANBAN BOARD PARA ENGENHARIA DE DADOS
1. Backlog / Refinement

A porta de entrada. Aqui as histórias são detalhadas pelo SME e Produto. Aplica-se a Definition of Ready (DoR): O ticket tem regras de negócio claras? Acessos IAM liberados? Amostra de dados disponível? Se não, a tarefa não avança para desenvolvimento.

2. In Dev

Engenheiros constroem o pipeline (ex: PySpark, SQL). É crucial aplicar WIP Limits (Work In Progress) para evitar a sobrecarga e garantir que o foco seja finalizar tarefas antes de puxar novas ("Stop starting, start finishing").

3. Code Review

Validação técnica por pares via Pull Requests (PRs). Verifica-se aderência às boas práticas de CI/CD (ex: AWS CodeBuild/CodePipeline), padronização de nomenclatura e eficiência das queries.

4. QA / Data Quality

A validação vai além do código. Testa-se a saúde dos dados (Completude, Unicidade, Precisão, Frescor) utilizando ferramentas como Great Expectations ou AWS Glue DataBrew/Data Quality. Dados corrompidos bloqueiam o pipeline.

5. UAT (User Acceptance Testing)

Homologação com o usuário final (Stakeholder / Analista de BI). Verifica-se se os dados na camada Gold / Consumo respondem às perguntas de negócio definidas no planejamento.

6. Done

A tarefa só chega aqui se cumprir a Definition of Done (DoD): Pipeline produtivo, dados validados, governança aplicada (tags, permissões Lake Formation), documentação (Catálogo/Glossário) atualizada e SLAs estabelecidos.

Gargalos e Boas Práticas:
  • Falta de DoR: Histórias mal refinadas travam a coluna In Dev, pois engenheiros param para tirar dúvidas de regras de negócio com o SME.
  • Acúmulo em QA: Se os testes de Data Quality falham frequentemente, o time precisa investir mais tempo em automação de testes unitários de dados e mock datasets durante a fase In Dev.
  • WIP Limit Violado: Muitas tarefas em paralelo resultam em alto Lead Time. Focar na resolução colaborativa (Pairing) para destravar itens parados em Code Review ou QA.

Métricas de Fluxo em Dados

A gestão eficaz do backlog exige medir como as entregas fluem pelo sistema. No ecossistema de dados, adaptamos as métricas clássicas de fluxo e introduzimos indicadores de qualidade:

Lead Time

O tempo total desde que um requisito é solicitado pelo stakeholder até a sua disponibilização em produção para consumo.

Cycle Time

O tempo que a equipe de engenharia leva para implementar a task, a partir do momento em que ela entra ativamente em desenvolvimento ("In Progress").

DQI (Data Quality Index) — Deep Dive Matemático

Métrica contínua que avalia a saúde dos dados entregues. Em operações maduras, o DQI é uma média ponderada das dimensões fundamentais de qualidade:

DQI = (w₁×Completude + w₂×Unicidade + w₃×Precisão + w₄×Frescor) / ∑w

Conceitualmente: Não basta entregar os dados; eles precisam ser confiáveis. Por exemplo, se a Completude de um campo crítico for 90% (w=0.4), a Unicidade 100% (w=0.3) e o Frescor (SLA) 80% (w=0.3), o DQI será (0.4×90 + 0.3×100 + 0.3×80) = 36 + 30 + 24 = 90%. Qualquer valor abaixo de 95% bloqueia o pipeline no ambiente Gold.

"Pare de começar e comece a terminar. Otimize o fluxo de valor focando no tempo de ciclo e na limitação do trabalho em progresso (WIP)."
— David J. Anderson, Kanban: Successful Evolutionary Change for Your Technology Business

Course Correction (Ajuste de Rota)

Na engenharia de dados, descobertas tardias no meio da Sprint podem inviabilizar todo o planejamento. É essencial ter protocolos bem definidos para Pivoting (Ajuste de Rota).

Protocolo de Pivoting Rápido:

Se uma Squad descobre no meio da Sprint que os dados da fonte possuem, por exemplo, 80% de valores nulos, o time deve abortar o desenvolvimento da feature original imediatamente. O bloqueio é sinalizado e um processo de Pivoting é acionado: o esforço é redirecionado para investigar a anomalia ou para outra história do backlog, evitando o desperdício de tempo e recursos da equipe.

Estimativa: T-Shirt vs Planning Poker

Extreme Programming

Extreme Programming Explained

Kent Beck (Addison-Wesley, 1999): O manifesto do XP. Beck introduziu TDD, Pair Programming e Continuous Integration — práticas que são a espinha dorsal de pipelines de dados confiáveis e testáveis.

Lean & Eliminação de Desperdício

The Lean Startup

Eric Ries (Crown Business, 2011): Ries adapta os princípios Lean da Toyota para startups de tecnologia. O conceito de MVP (Minimum Viable Product) é diretamente aplicável à criação de MVPs Analíticos — validar hipóteses de dados antes de investir em pipelines complexos.

Toyota Production System

Toyota Production System

Taiichi Ohno (Productivity Press, 1988): A origem do Kanban e do Lean. Ohno criou o sistema de produção que revolucionou a manufatura e que décadas depois inspirou o Agile Software Development e o Kanban para TI.

Gestão de Alto Rendimento

High Output Management

Andy Grove (Vintage, 1983): O criador dos OKRs na Intel. Grove ensina que a produtividade de um gestor é medida pelo output de sua organização — não pelo seu esforço individual. Conceito fundamental para PMOs de dados.

Produtos de Tecnologia

Inspired: How to Create Tech Products Customers Love

Marty Cagan (Wiley, 2018): Cagan, ex-VP de Produto no eBay, argumenta que os melhores produtos nascem de times empoderados ("empowered teams") — não de roadmaps top-down. Referência para Data Product Managers que querem ir além de feature factories.

Kanban para TI

Kanban: Successful Evolutionary Change

David J. Anderson (Blue Hole Press, 2010): Anderson adaptou o Kanban da Toyota para o desenvolvimento de software. O livro detalha WIP Limits, Lead Time, Cycle Time e políticas de fluxo — métricas essenciais para times de sustentação de dados (RUN).
