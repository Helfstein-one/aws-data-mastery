Fundamentos: REST vs HTTP vs WebSocket

Entendendo os três tipos de API Gateway e quando usar cada um em plataformas de dados

O Amazon API Gateway é um serviço totalmente gerenciado que permite criar, publicar, manter, monitorar e proteger APIs em qualquer escala. Ele funciona como a porta de entrada para suas aplicações — recebendo todas as chamadas de API, gerenciando milhões de chamadas concorrentes, autorizando acessos e direcionando requisições para os serviços corretos.

REST API REST
REST API (v1)
O produto original e mais completo. Suporta todos os recursos: caching nativo, uso de usage plans, API keys, throttling por método, modelos de validação JSON Schema, custom domain names e integração direta com serviços AWS (SQS, Kinesis, S3, Step Functions) sem Lambda intermediário.

Quando usar: APIs complexas que necessitam de validação de payload, caching, usage plans, integrações diretas com serviços AWS ou VPC Link para backends privados.
HTTP API HTTP
HTTP API (v2)
API mais leve e até 70% mais barata que a REST API. Latência menor (single-digit ms). Suporta JWT authorizers nativos (sem Lambda Authorizer), CORS automático e integrações Lambda/HTTP. Não suporta API caching nativo, usage plans, request/response transformations via VTL.

Quando usar: Microsserviços simples, backends serverless com Cognito/JWT, APIs de alto volume onde custo é crítico.
WebSocket API WS
WebSocket API
Comunicação bidirecional persistente em tempo real. O API Gateway mantém as conexões WebSocket abertas e roteia mensagens via route keys ($connect, $disconnect, $default, ou rotas customizadas). Ideal para notificações push, dashboards em tempo real e chats.

Quando usar: Streaming de eventos ao vivo (pipeline status, alertas de data quality), dashboards analíticos com refresh em tempo real.

Tipos de Integração do API Gateway

O API Gateway suporta 5 tipos de integração com backends. A escolha impacta diretamente custo, latência e capacidade de transformação de payloads:

Tipo 1
AWS_PROXY (Lambda Proxy)
O payload inteiro (headers, body, path params, query strings) é encaminhado diretamente ao Lambda em um formato JSON padronizado. A resposta do Lambda deve incluir statusCode, headers e body. Vantagem: zero configuração de mapeamento. Desvantagem: sem transformação pelo Gateway.
Tipo 2
AWS (Service Integration)
Integração direta com serviços AWS (SQS, Kinesis, SNS, S3, Step Functions, DynamoDB) sem passar por Lambda. Usa VTL (Velocity Template Language) para mapear request/response. Custo zero de compute — ideal para ingestão de alta escala.
Tipo 3
HTTP / HTTP_PROXY
Repassa a requisição para um endpoint HTTP externo (ECS, EC2, on-premise via PrivateLink). HTTP_PROXY encaminha tudo sem modificação; HTTP permite transformações VTL. Usado com VPC Link para backends privados.
Tipo 4
MOCK
Retorna uma resposta diretamente do API Gateway sem chamar backend algum. Útil para stubs de desenvolvimento, documentação interativa (Swagger UI) e testes de contrato sem infraestrutura.

Lambda Handler — CRUD Completo com DynamoDB

import json
import boto3
import uuid
from datetime import datetime, timezone
from typing import Any, Dict
from decimal import Decimal

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('Products')


def response(status: int, body: Any, headers: Dict = {}) -> Dict:
    """Helper padronizado de resposta Lambda Proxy."""
    base_headers = {
        "Content-Type": "application/json",
        "Access-Control-Allow-Origin": "*",  # CORS
    }
    return {
        "statusCode": status,
        "headers": {**base_headers, **headers},
        "body": json.dumps(body, default=str),
    }


def list_products(event: Dict) -> Dict:
    """GET /products — Lista produtos com filtro e paginação."""
    params = event.get("queryStringParameters") or {}
    category = params.get("category")
    limit = int(params.get("limit", 20))
    exclusive_start_key = params.get("nextToken")

    scan_kwargs = {"Limit": limit}
    if category:
        scan_kwargs["FilterExpression"] = "category = :c"
        scan_kwargs["ExpressionAttributeValues"] = {":c": category}
    if exclusive_start_key:
        scan_kwargs["ExclusiveStartKey"] = {"productId": exclusive_start_key}

    result = table.scan(**scan_kwargs)
    return response(200, {
        "items": result["Items"],
        "count": result["Count"],
        "nextToken": result.get("LastEvaluatedKey", {}).get("productId"),
    })


def create_product(event: Dict) -> Dict:
    """POST /products — Cria produto com idempotência via requestId."""
    body = json.loads(event["body"])
    # Idempotência: usa clientRequestToken se fornecido
    product_id = body.get("clientRequestToken") or str(uuid.uuid4())

    item = {
        "productId": product_id,
        "name": body["name"],
        "category": body["category"],
        "price": Decimal(str(body["price"])),
        "stock": body.get("stock", 0),
        "createdAt": datetime.now(timezone.utc).isoformat(),
        "updatedAt": datetime.now(timezone.utc).isoformat(),
    }

    # condition_expression garante idempotência (não sobrescreve se existe)
    try:
        table.put_item(Item=item, ConditionExpression="attribute_not_exists(productId)")
        return response(201, item, {"Location": f"/products/{product_id}"})
    except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
        # Produto já existe — retorna o existente (idempotente)
        existing = table.get_item(Key={"productId": product_id})["Item"]
        return response(200, existing)


def get_product(event: Dict) -> Dict:
    """GET /products/{productId} — Busca produto por ID."""
    product_id = event["pathParameters"]["productId"]
    result = table.get_item(Key={"productId": product_id})
    item = result.get("Item")
    if not item:
        return response(404, {"error": f"Product {product_id} not found"})
    return response(200, item)


def update_product(event: Dict) -> Dict:
    """PUT /products/{productId} — Atualização parcial com optimistic locking."""
    product_id = event["pathParameters"]["productId"]
    body = json.loads(event["body"])
    body["updatedAt"] = datetime.now(timezone.utc).isoformat()

    update_expr = "SET " + ", ".join(f"#{k} = :{k}" for k in body)
    expr_names  = {f"#{k}": k for k in body}
    expr_values = {f":{k}": (Decimal(str(v)) if isinstance(v, float) else v)
                   for k, v in body.items()}

    result = table.update_item(
        Key={"productId": product_id},
        UpdateExpression=update_expr,
        ExpressionAttributeNames=expr_names,
        ExpressionAttributeValues=expr_values,
        ConditionExpression="attribute_exists(productId)",
        ReturnValues="ALL_NEW",
    )
    return response(200, result["Attributes"])


def delete_product(event: Dict) -> Dict:
    """DELETE /products/{productId} — Remoção lógica (soft delete)."""
    product_id = event["pathParameters"]["productId"]
    table.update_item(
        Key={"productId": product_id},
        UpdateExpression="SET #s = :deleted, updatedAt = :ts",
        ExpressionAttributeNames={"#s": "status"},
        ExpressionAttributeValues={
            ":deleted": "DELETED",
            ":ts": datetime.now(timezone.utc).isoformat(),
        },
        ConditionExpression="attribute_exists(productId)",
    )
    return response(204, {})


# Router principal — single Lambda function com roteamento por método+path
ROUTES = {
    ("GET",    "/products"):             list_products,
    ("POST",   "/products"):             create_product,
    ("GET",    "/products/{productId}"): get_product,
    ("PUT",    "/products/{productId}"): update_product,
    ("DELETE", "/products/{productId}"): delete_product,
}

def lambda_handler(event: Dict, context) -> Dict:
    method = event.get("httpMethod")
    resource = event.get("resource")
    handler = ROUTES.get((method, resource))
    if not handler:
        return response(404, {"error": "Route not found"})
    try:
        return handler(event)
    except Exception as e:
        return response(500, {"error": "Internal server error", "detail": str(e)})

VTL — Velocity Template Language: Transformação sem Lambda

A VTL permite transformar requests e responses diretamente no API Gateway, eliminando o custo e latência de invocar Lambda para simples mapeamentos:

## Request mapping: converte POST /events para SQS SendMessage
## Integration Request Template — application/json
#set($body = $util.escapeJavaScript($input.body))
Action=SendMessage
&MessageBody=$body
&MessageGroupId=$input.path('$.userId')
&MessageDeduplicationId=$context.requestId

## Response mapping: transforma resposta do SQS para JSON limpo
## Integration Response Template — 200
{
  "messageId": "$input.path('$.SendMessageResponse.SendMessageResult.MessageId')",
  "requestId": "$context.requestId",
  "status": "accepted",
  "timestamp": "$context.requestTimeEpoch"
}
✅ Boas Práticas: Validação de Schema Sempre ative o Request Validator no API Gateway antes de chamar o backend. Um schema JSON inválido rejeitado no Gateway economiza uma invocação Lambda, reduz custos e retorna um 400 claro ao cliente — sem consumir quota de processamento.

# Terraform: API Gateway integração direta com Kinesis — sem Lambda!
resource "aws_api_gateway_integration" "kinesis_put" {
  rest_api_id             = aws_api_gateway_rest_api.data_api.id
  resource_id             = aws_api_gateway_resource.events.id
  http_method             = aws_api_gateway_method.post_events.http_method
  type                    = "AWS"
  integration_http_method = "POST"
  uri = "arn:aws:apigateway:${var.region}:kinesis:action/PutRecord"
  credentials             = aws_iam_role.apigw_kinesis_role.arn

  request_templates = {
    "application/json" = jsonencode({
      StreamName    = "$$input.path('$.streamName')"
      Data          = "$$util.base64Encode($$input.body)"
      PartitionKey  = "$$input.path('$.userId')"
    })
  }
}

# Resposta: extraindo SequenceNumber do XML do Kinesis
resource "aws_api_gateway_integration_response" "kinesis_200" {

  status_code = "200"

  response_templates = {

      {
        "sequenceNumber": "$$input.path('$.PutRecordResponse.SequenceNumber')",
        "shardId": "$$input.path('$.PutRecordResponse.ShardId')",
        "requestId": "$$context.requestId",

  }

Lambda Authorizer — Implementação Completa

import json
import jwt  # pip install python-jose[cryptography]
import boto3
from functools import lru_cache
from typing import Dict, Any


secrets_client = boto3.client('secretsmanager')


@lru_cache(maxsize=1)
def get_jwt_secret() -> str:
    """Cache da chave JWT — evita chamadas repetidas ao Secrets Manager."""
    response = secrets_client.get_secret_value(SecretId='prod/api/jwt-secret')
    return response['SecretString']


def build_policy(principal_id: str, effect: str, resource: str,
                  context: Dict = {}) -> Dict:
    """Constrói a IAM Policy Document retornada ao API Gateway."""
    return {
        "principalId": principal_id,
        "policyDocument": {
            "Version": "2012-10-17",
            "Statement": [{
                "Action": "execute-api:Invoke",
                "Effect": effect,
                "Resource": resource,  # arn:aws:execute-api:region:acct:api-id/stage/method/path
            }],
        },
        "context": context,  # Injetado no contexto — disponível no Lambda backend
    }


def lambda_handler(event: Dict, context: Any) -> Dict:
    """Token-based Lambda Authorizer com cache de policy."""
    token = event.get("authorizationToken", "")
    method_arn = event["methodArn"]

    # Remove prefixo "Bearer " se presente
    token = token.replace("Bearer ", "").strip()

    if not token:
        raise Exception("Unauthorized")  # API GW retorna 401

    try:
        secret = get_jwt_secret()
        payload = jwt.decode(token, secret, algorithms=["HS256"])

        user_id = payload["sub"]
        user_role = payload.get("role", "reader")
        tenant_id = payload.get("tenant_id")

        # Wildcard: permite todas as rotas da API para este usuário
        api_arn = "/".join(method_arn.split("/")[:2]) + "/*"

        return build_policy(
            principal_id=user_id,
            effect="Allow",
            resource=api_arn,
            context={
                "userId": user_id,
                "role": user_role,
                "tenantId": tenant_id or "",
            }
        )

    except jwt.ExpiredSignatureError:
        raise Exception("Unauthorized")  # 401
    except jwt.InvalidTokenError:
        raise Exception("Unauthorized")  # 401
    except Exception:
        raise Exception("Unauthorized")  # 401 para qualquer falha

Boas Práticas de Produção

Caching, CORS, error handling, versionamento, Blue/Green e idempotência

Performance
🚀 API Caching
Ative cache por stage (0.5 a 237 GB). Configure TTL diferente por recurso: GET /products → 300s; GET /users/{id} → 60s; POST/PUT/DELETE → cache desabilitado.

Header de cache: Cache-Control: max-age=300 na request invalida o cache do Gateway. Controle via requireAuthorizationForCacheControl para evitar bypass.
Cross-Origin
🌐 CORS Configuration
Configure CORS no API Gateway, não no Lambda. Crie um método OPTIONS em cada resource com resposta mock:

Access-Control-Allow-Origin: https://app.empresa.com
Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS
Access-Control-Allow-Headers: Content-Type,Authorization,X-Api-Key
Access-Control-Max-Age: 600
Resiliência
🔄 Error Handling & Retry
Mapeie todos os erros possíveis via Gateway Responses:
• 400 — Bad request (schema inválido)
• 401 — Unauthorized (auth falhou)
• 403 — Forbidden (sem permissão)
• 429 — Too Many Requests (throttle)
• 500 — Internal error (Lambda falhando)
• 502 — Bad Gateway (resposta inválida do Lambda)
• 503 — Service Unavailable
Sempre retorne JSON estruturado com requestId.
Idempotência
🔁 Idempotent POST
Use clientRequestToken no body ou Idempotency-Key no header. Armazene tokens no DynamoDB com TTL de 24h. Se o token já existe, retorne a resposta original sem reprocessar. Fundamental para evitar duplicação em retry após timeout.
Versionamento
📌 API Versioning
Estratégias:
• URL Path: /v1/products → /v2/products (mais explícito, cache-friendly)
• Header: Accept: application/vnd.api+json;version=2
• Stage Variables: mesmo endpoint, Lambda alias diferente (v1 → Lambda:prod, v2 → Lambda:v2)
Nunca quebre contratos de APIs existentes sem versão nova.
Deploy
🟩 Blue/Green Deployment
Use Canary Releases no Stage para controlar tráfego gradualmente:
1. Deploy nova versão com 5% canary
2. Monitore métricas por 15-30 min
3. Se OK → promova para 100%
4. Se erro → rollback automático
Combine com Lambda Aliases (BLUE/GREEN) para rollback instantâneo.

Perguntas & Questões de Entrevista

25+ questões técnicas profundas sobre API Gateway para entrevistas de Staff/Senior Engineer

1. Qual a diferença entre REST API e HTTP API no API Gateway, e quando usar cada um?FUNDAMENTOS
REST API (v1) é o produto completo e maduro: suporta caching nativo, usage plans, API keys, throttling por método individual, integrações diretas com serviços AWS (SQS, Kinesis, S3, Step Functions) via tipo AWS sem Lambda, modelos de validação JSON Schema, custom authorizers com contexto rico e VPC Link via NLB. Custo: $3.50/milhão.

HTTP API (v2) é mais leve e barato ($1.00/milhão, ~70% mais barato). Latência menor (~5ms vs ~10ms). Suporta JWT authorizers nativos (Cognito e qualquer IdP OAuth2), CORS automático, mas não suporta: API caching, usage plans, integrações AWS diretas (sem Lambda), VTL transformations, per-method throttling.

Regra de ouro: Use HTTP API para microserviços simples com Lambda/JWT onde custo importa. Use REST API quando precisar de qualquer uma destas features: caching, integração direta com SQS/Kinesis, usage plans ou transformação de payload.
2. Como o Token Bucket funciona para throttling e o que acontece quando ele está cheio?THROTTLING
O API Gateway usa o algoritmo Token Bucket: o "balde" tem capacidade máxima igual ao burst limit. Tokens são adicionados à taxa de steady-state rate por segundo (ex: 10.000 tokens/s). Cada request consome 1 token.

  • Se o balde tem tokens → request passa imediatamente
  • Se o balde está vazio → request recebe 429 Too Many Requests
  • O balde se enche até o burst limit durante períodos de baixo tráfego, permitindo picos momentâneos
Defaults por conta AWS: 10.000 req/s steady-state, 5.000 burst. Isso é um limite de conta, compartilhado entre todas as APIs. Em produção, configure throttle por stage e por método (ex: DELETE com burst=20, POST com burst=500). Clientes que excedem o limite devem implementar exponential backoff com jitter.
3. Como implementar idempotência em uma API POST com alta disponibilidade?IDEMPOTÊNCIA
O padrão recomendado em AWS usa DynamoDB como store de idempotência:

  • 1. Client gera um clientRequestToken (UUID v4) e envia no header Idempotency-Key ou no body
  • 2. Lambda tenta inserir o token no DynamoDB com ConditionExpression: attribute_not_exists(token) + TTL de 24h
  • 3a. Sucesso (primeira vez): processa a operação normalmente, salva o resultado junto ao token
  • 3b. Falha ConditionCheck (token já existe): retorna o resultado salvo anteriormente sem reprocessar
Lambda Powertools for Python tem implementação pronta com decorador @idempotent que automatiza todo esse fluxo. TTL deve ser maior que o timeout máximo de retry do cliente.
4. Qual a diferença entre tipo de integração AWS vs AWS_PROXY?INTEGRAÇÃO
AWS_PROXY (Lambda Proxy): O API Gateway encaminha o evento inteiro ao Lambda em um formato padronizado (headers, body, pathParameters, queryStringParameters, requestContext). O Lambda é responsável por retornar uma resposta no formato correto (statusCode, headers, body). Não há transformação no Gateway. Mais simples de configurar.

AWS (não-proxy): Permite usar VTL Templates para transformar o request antes de enviar ao backend e transformar a resposta antes de devolver ao cliente. Usado obrigatoriamente para integrações diretas com SQS, Kinesis, S3, DynamoDB e Step Functions — onde você precisa formatar o payload conforme a API do serviço AWS. Mais poderoso mas requer conhecimento de VTL.
5. Como funciona o Lambda Authorizer e qual é o impacto de performance?AUTENTICAÇÃO
O Lambda Authorizer é uma função Lambda invocada pelo API Gateway antes de processar a requisição. Existem dois tipos:

  • TOKEN: recebe um header (ex: Authorization Bearer) e retorna uma IAM Policy Document (Allow/Deny) + contexto
  • REQUEST: recebe headers, query strings e path params — mais flexível para auth multi-fator
Performance: A invocação do Lambda Authorizer adiciona latência (~5-50ms de cold start até ~1ms warm). O API Gateway cacheia a política IAM resultante pelo TTL configurado (0-3600s). Com TTL=300s, o Lambda Authorizer só é invocado na primeira requisição de um token e depois fica em cache. Atenção: se o usuário for bloqueado/deletado, a política cached ainda permite acesso até o TTL expirar.
6. Como fazer Blue/Green deployment de uma API sem downtime?DEPLOY
O API Gateway suporta Canary Releases nativas no stage. O processo:

  • 1. Crie um deployment com a nova versão
  • 2. Configure canary no stage: percentTraffic=10 + deploymentId=novo
  • 3. Monitore métricas de 4XX/5XX e latência P99 por 15-30 minutos
  • 4a. Sucesso: aws apigateway update-stage --patch-operations op=remove,path=/canarySettings (promove 100%)
  • 4b. Falha: aws apigateway delete-deployment (rollback imediato)
Para Lambda, combine com Lambda Aliases (BLUE/GREEN) e stage variables apontando para o alias correto.
7. Quando usar VPC Link vs integração Lambda direta para backends privados?ARQUITETURA
VPC Link é necessário quando o backend roda em recursos privados de VPC que não são Lambda: containers ECS Fargate, instâncias EC2, EKS pods. O VPC Link cria uma conexão ENI gerenciada entre o API Gateway e um NLB (REST API) ou ALB/NLB (HTTP API) dentro da VPC.

Lambda direto (AWS_PROXY) é mais simples e serverless — não requer VPC nem NLB. A invocação do Lambda acontece via AWS service endpoint internamente, sem passar pela internet.

Decisão: Use Lambda quando o processamento é stateless e serverless. Use VPC Link quando o backend tem estado (DB connection pool), precisa de baixa latência constante (sem cold start), é um microserviço existente em container ou quando o tempo de execução do Lambda (15min max) é insuficiente.
8. Como evitar cold starts em Lambda quando usado com API Gateway?PERFORMANCE
Estratégias em ordem de eficácia:

  • Lambda Snapstart (Java): Cria snapshot do estado inicializado, elimina quase 100% do cold start
  • Provisioned Concurrency: Mantém N instâncias Lambda sempre quentes. Custo adicional mas elimina cold start para tráfego até N concurrent. Ideal para SLAs rígidos
  • Minimizar pacote de deploy: Menos dependências = inicialização mais rápida. Use Lambda Layers para dependências compartilhadas
  • Otimizar init code: Mova conexões DB, SDK clients e caches para fora do handler (nível de módulo)
  • Warm-up com EventBridge: Dispare invocações de aquecimento a cada 5 minutos para manter containers ativos
  • HTTP API: Menor overhead que REST API = menor latência percebida
9. Como implementar paginação eficiente em uma API GET /items?API DESIGN
O padrão recomendado é cursor-based pagination (não offset/limit) para DynamoDB:

  • Response: { "items": [...], "nextToken": "base64EncodedLastEvaluatedKey" }
  • Request seguinte: GET /items?nextToken=abc&limit=20
  • O nextToken é o LastEvaluatedKey do DynamoDB encodado em base64
Vantagens vs offset: Consistente mesmo com inserções simultâneas; sem "cursor drift"; não requer COUNT(*) no banco; performance O(1) independente da página. Validação: Sempre valide e sanitize o nextToken para evitar injection — use criptografia simétrica (AES) para ofuscar o cursor.
10. O que são Gateway Responses e por que são importantes?ERROR HANDLING
Gateway Responses são as respostas de erro que o próprio API Gateway gera — antes de chegar ao backend. Isso inclui: UNAUTHORIZED (401), ACCESS_DENIED (403), DEFAULT_4XX (400), THROTTLED (429), DEFAULT_5XX (500).

Por padrão, o API Gateway retorna JSON genérico e sem headers CORS. Ao customizar Gateway Responses:
  • Você garante formato de erro consistente com o resto da API
  • Adiciona headers CORS (sem isso, o browser bloqueia até erros 4XX/5XX)
  • Inclui requestId para correlação de logs
  • Retorna mensagens de erro amigáveis ao cliente
Configure via Terraform com aws_api_gateway_gateway_response para cada tipo de erro.
11. Como o API Gateway trata o payload de uma requisição para o DynamoDB sem Lambda?INTEGRAÇÃO DIRETA
Usando integração do tipo AWS com VTL templates. O fluxo:

  • Integration Request Template: transforma o JSON da request para o formato da API DynamoDB (ex: {"TableName": "...", "Item": {"pk": {"S": "..."}}})
  • API Gateway assina a chamada com credenciais IAM da role configurada
  • DynamoDB retorna XML (PutItem, GetItem, etc.)
  • Integration Response Template: transforma o XML/JSON de resposta do DynamoDB para o formato desejado pelo cliente
Isso elimina completamente o Lambda da cadeia — reduz custo, latência e pontos de falha. O tradeoff é a complexidade do VTL. Para operações simples (GetItem, PutItem), a economia é significativa em alto volume.
12. Como versionar APIs sem quebrar clientes existentes?API VERSIONING
As principais estratégias com seus tradeoffs:

  • URL Path: /v1/products → /v2/products. Mais explícito, cache-friendly, fácil de logar/monitorar. Desvantagem: prolifera URLs.
  • Stage Variable: Mesma URL, stage variable altera o Lambda Alias invocado. Transparente ao cliente. Desvantagem: versão invisível na URL.
  • Header: Accept-Version: 2 ou Accept: application/vnd.api.v2+json. Mais "puro" REST. Desvantagem: difícil de testar com browser, não funciona bem com caching.
Regra: Use URL Path para APIs públicas. Stage variables para APIs internas. Nunca remova campos de response sem versão nova — apenas adicione campos novos (Backward Compatibility).
13. Como debugar um erro 502 Bad Gateway no API Gateway?TROUBLESHOOTING
502 Bad Gateway significa que o API Gateway recebeu uma resposta inválida do backend. Causas comuns:

  • Lambda retornou formato inválido: O Lambda Proxy exige {"statusCode": 200, "body": "..."}. Se statusCode for string ao invés de int, ou se o body não for string, o API Gateway retorna 502
  • Lambda timeout: Se o Lambda excede o Integration Timeout (29s max no API Gateway), retorna 504 (mas pode aparecer como 502)
  • Lambda excedeu concorrência: Se Lambda atingiu o limite de concorrência reservada, retorna erro que vira 502
  • Resposta do backend HTTP muito grande: API Gateway tem limite de 10MB para payload
Debug: Ative logging_level = "INFO" no método settings do stage. Verifique CloudWatch Logs do API Gateway (não do Lambda) para ver o request/response exato. Use X-Ray para ver onde a latência está.
14. Qual é o impacto de usar API Gateway em um contexto de streaming de dados de alta frequência?DATA ENGINEERING
O API Gateway tem um integration timeout máximo de 29 segundos (hardlimit) e não suporta streaming de response (chunked transfer encoding). Para ingestão de alta frequência:

  • Use integração direta com Kinesis (sem Lambda): API GW → PutRecord. Throughput: até 1MB/s por shard, sem overhead de Lambda
  • Para batch ingest: use PutRecords (até 500 records por request) via integração direta
  • Limite de payload: 10MB max por request. Para IoT com payloads pequenos, o batch é essencial
  • Alternativa de alta escala: para volumes acima de 10.000 events/s, considere IoT Core (MQTT) ou MSK como alternativa ao API Gateway
  • Throttling: configure throttle específico para o endpoint de ingestão com burst alto
15. Como garantir que sua API Gateway Private (VPC) não seja acessível externamente?SEGURANÇA
Uma API PRIVATE no API Gateway só pode ser acessada de dentro da VPC via Interface VPC Endpoint (PrivateLink):

  • Crie um VPC Endpoint do tipo Interface para com.amazonaws.region.execute-api
  • Configure a Resource Policy da API para apenas permitir chamadas que venham do VPC Endpoint: "Condition": {"StringEquals": {"aws:SourceVpce": "vpce-XXXX"}}
  • Configure endpoint_configuration.types = ["PRIVATE"] no Terraform
  • Use Security Groups no VPC Endpoint para limitar quais recursos internos podem chamar a API
Mesmo com PRIVATE, sem a Resource Policy correta, qualquer VPC com o endpoint poderia acessar. A combinação endpoint_type PRIVATE + Resource Policy + SG é a configuração mais segura.
16. O que é um Usage Plan e como implementar multi-tenancy com API Keys?MULTI-TENANT
Usage Plans definem limites de acesso (throttling e quota) que podem ser associados a API Keys de clientes:

  • Crie tiers: Basic (1000 req/dia, 10 req/s), Standard (100k req/dia, 100 req/s), Premium (ilimitado, 1000 req/s)
  • Cada cliente/parceiro recebe uma API Key única
  • Associe cada API Key ao Usage Plan correspondente
  • O API Gateway aplica os limites automaticamente por API Key
  • Monitore consumo via CloudWatch com dimensão por API Key
Atenção: API Keys no API Gateway não são mecanismo de autenticação segura — são apenas identificadores para throttling/quota. Use sempre em conjunto com Cognito ou Lambda Authorizer para autenticação real.

Case 2: FinTech — API de Transações com Segurança Multi-camada

PCI-DSS Compliant, Cognito + Lambda Authorizer, audit log completo

Desafio

# Fluxo de autenticação multi-camada
Client (Mobile App)

Client → API GW: POST /transactions

  5. Envia para Lambda de processamento com contexto completo

Case 4: IoT — Telemetria de Alta Frequência com Throttling Inteligente

100k dispositivos, 1M leituras/min, throttling por device group

Desafio Técnico

Rede de sensores industriais enviando dados de temperatura/pressão a cada segundo. Dispositivos em zonas de conectividade instável fazem retry agressivo. Sem throttling, um "storm" de retries pode derrubar o sistema.

Solução

# Throttling por grupo de dispositivos via Usage Plans

# Grupo A: Sensores críticos (linha de produção)
critical_plan:
  throttle: { burst: 5000, rate: 2000 }
  quota: none

# Grupo B: Sensores de monitoramento ambiental
standard_plan:
  throttle: { burst: 1000, rate: 500 }
  quota: { limit: 10_000_000, period: MONTH }

# WAF: bloqueia IPs com > 5000 req/5min (proteção contra storms)
# SQS: buffer com visibilidade 30s + DLQ para falhas
# Lambda: batch size 50 mensagens (PutRecords Kinesis)
💡 Pattern: Adaptive Throttling Dispositivos que recebem 429 implementam backoff exponencial com jitter: wait = min(base * 2^attempt + random(0, 1000), max_wait). Isso distribui os retries ao longo do tempo, evitando thundering herd.

Case 5: Multi-tenant SaaS — API de Dados com Isolamento por Tenant

Silo model: DynamoDB + Row-Level Security via Lambda Authorizer

Arquitetura Multi-tenant

# Lambda Authorizer injeta tenantId no contexto
def lambda_handler(event, context):
    token = jwt.decode(event["authorizationToken"], secret)
    tenant_id = token["tenant_id"]
    user_role  = token["role"]

    return {
        "principalId": token["sub"],
        "policyDocument": allow_policy(event["methodArn"]),
        "context": {
            "tenantId": tenant_id,   # Injetado como $context.authorizer.tenantId
            "role": user_role,
        }
    }

# Lambda backend usa tenantId para isolar dados no DynamoDB
def get_data(event, context):
    # Pega do contexto injetado pelo Authorizer — nunca do request body!
    tenant_id = event["requestContext"]["authorizer"]["tenantId"]

    # Query com filter por tenant (Row-Level Security)
    result = table.query(
        KeyConditionExpression=Key("pk").eq(f"TENANT#{tenant_id}")
    )
    return response(200, result["Items"])
⚠️ Security Pattern O tenantId NUNCA deve vir do request body (suscetível a tampering). Sempre injete via Lambda Authorizer do JWT validado. O backend deve usar somente o valor do $context.authorizer para garantir isolamento entre tenants.
