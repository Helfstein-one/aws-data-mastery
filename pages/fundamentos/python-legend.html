Tipos Primitivos, Estruturas & Tipagem

O arsenal fundamental e as estruturas de dados nativas.

Python é Dinamicamente Tipada (o tipo é verificado em tempo de execução) e Fortemente Tipada (o interpretador não faz coerção implícita imprevisível, ex: `1 + "2"` gera erro, diferente do Javascript).

Type Hints (A Partir do Python 3.5)

Embora dinâmico, o uso de Type Hints é mandatório na Engenharia de Software moderna para garantir a manutenibilidade via linter (Mypy).

from typing import List, Dict, Optional, Union

def calcular_salario(base: float, bonus: Optional[float] = None) -> float:
    if bonus:
        return base + bonus
    return base

# Listas e Dicionários tipados
funcionarios: List[str] = ["Alice", "Bob"]
salarios: Dict[str, float] = {"Alice": 5000.0, "Bob": 4500.0}

Estruturas de Dados Embutidas (Built-ins)

Listas (List)

Mutáveis, ordenadas, permitem duplicatas. Internamente implementadas como Arrays Dinâmicos em C.

my_list = [1, 2, "A"]

Complexidade: Busca O(N). Insert/Append no final O(1).

Dicionários (Dict)

Pares chave-valor, mutáveis. Internamente implementadas como Hash Tables de altíssima performance.

my_dict = {"id": 1, "status": "active"}

Complexidade: Busca/Insert em O(1).

Conjuntos (Set)

Não ordenados, sem índices, não permitem duplicatas. Essencial para lógica de conjuntos (Interseção, União).

my_set = {1, 2, 3}

Complexidade: Busca em O(1). Extremamente rápido para deduplicação: list(set(lista_duplicada)).

Tuplas (Tuple)

Imutáveis, ordenadas. Como não podem mudar de tamanho, ocupam menos memória e são mais rápidas que listas.

my_tuple = (1, 2, 3)

Usadas para chaves de dicionários (pois são *hashable*) ou retorno múltiplo em funções.

Boas Práticas de Código Python em Pipelines

Escrevendo códigos Pythonics (PEP8), seguros e autodocumentados

Em ambientes de Engenharia de Dados, pipelines de dados mudam constantemente. Para garantir que seu código continue inteligível e manutenível por diferentes desenvolvedores, aplique as regras da PEP 8 e convenções estruturadas:

  • Nomenclatura (snake_case vs CamelCase):
    • Use snake_case (letras minúsculas com underline) para variáveis, funções e métodos lógicos (ex: def carregar_dados_s3()).
    • Use CamelCase (iniciais maiúsculas sem espaçamento) exclusivamente para declarações de Classes lógicas e Types complexos (ex: class SparkConnector).
    • Constantes Globais imutáveis devem ser declaradas em maiúsculas (ex: DEFAULT_S3_BUCKET = "trusted-zone").
  • Tipagem de Variáveis e Assinaturas (Static Type Hinting): A tipagem estática do Python (através do pacote typing) previne a passagem acidental de tipos incorretos em tempo de compilação/teste estático. Use o mypy no CI/CD para validar.
Exemplo Prático: Tipagem Explícita e Implícita em Python

Veja a diferença de legibilidade de código ao tipar as variáveis explícita e implicitamente:

# Tipagem Implícita (Dificulta auditoria e linting estático)
def calcular_imposto_legado(dados):
    valores = [d["preco"] for d in dados]
    return sum(valores) * 0.15

# Tipagem Explícita (Recomendado para Especialistas)
from typing import List, Dict, Any, Union

def calcular_imposto_pyspark(dados: List[Dict[str, Any]]) -> float:
    valores: List[float] = [float(d["preco"]) for d in dados]
    return sum(valores) * 0.15

Estruturas de Dados Fundamentais e Complexidade Big-O

Em processamento de dados local ou pipelines Python puros, a escolha da estrutura de dados nativa dita o consumo de memória e a latência de processamento de buscas. Conhecer a complexidade de tempo (Big-O) evita gargalos clássicos:

Estrutura Inserção/Append Busca por Elemento (`x in collection`) Uso de Memória Caso de Ingestão Ideal
List O(1) amortizado O(N) (Pesquisa linear) Baixo / Sequencial Manter ordem física de colunas ou acumular batches ordenados de registros.
Set O(1) O(1) (Hash table lookup) Médio (Hash tables exigem padding) Filtrar IDs duplicados de transações recebidos em lote da Raw Layer.
Dict O(1) O(1) (Busca de chaves) Alto (Armazena chaves, hashes e valores) Representar registros e mapeamento de chaves para consultas rápidas (*Lookup Tables*).
Otimização de Loops: Compreensão de Listas (List Comprehension): Loops tradicionais (for x in lista: ...) em Python interpretado geram custos de interpretação a cada ciclo. A compreensão de listas ([processa(x) for x in lista]) é executada no nível da linguagem C sob o capô, gerando ganhos de até 25% na velocidade de processamento. 
# Código Ineficiente (Iteração Lenta com loops)
ids_invalidos = []
for transacao in transacoes:
    if transacao.valor <= 0:
        ids_invalidos.append(transacao.id)

# Código Pythonic O(1) Lookup & List Comprehension
# Se ids_blacklist for um SET em vez de LIST, a pesquisa 'in' cai de O(N) para O(1)
ids_blacklist = {"uuid-1", "uuid-2", "uuid-3"}
transacoes_validas = [t for t in transacoes if t.id not in ids_blacklist]

Performance, Vetorização e Otimização com Pandas DataFrame

Pandas é amplamente utilizado para manipulação local de volumes médios de dados. No entanto, o Pandas foi escrito em C/Cython. Utilizar laços manuais do Python sobre DataFrames é um dos maiores gargalos cometidos por engenheiros:

  • Anti-Pattern (iterrows): O método .iterrows() converte cada linha em um objeto Pandas Series do Python em tempo de execução, gerando um overhead computacional massivo.
  • Vectorization (Vetorização): Operações vetorizadas enviam a instrução de cálculo diretamente para arrays nativos do C (NumPy) sem passar pelo interpretador Python a cada linha (SIMD - Single Instruction, Multiple Data).
Técnicas de Performance: Iteração Manual vs. Vetorização no Pandas
import pandas as pd
import numpy as np

df = pd.DataFrame({"valor_dolar": np.random.uniform(1, 100, 1_000_000)})
taxa = 5.30

# ANTI-PATTERN: iterrows (Lento - pode levar vários segundos)
valores_reais = []
for index, row in df.iterrows():
    valores_reais.append(row["valor_dolar"] * taxa)
df["valor_real_lento"] = valores_reais

# PADRÃO OURO: Vetorização (Ultra Rápido - milissegundos)
df["valor_real_rapido"] = df["valor_dolar"] * taxa  # Processamento C nativo

Otimização de Tipos de Dados no Pandas: Por padrão, o Pandas pode inferir inteiros como int64 e decimais como float64, consumindo mais memória do que o necessário. Além disso, strings repetidas consomem muita RAM. Podemos otimizar a memória utilizando downcast e convertendo tipos de strings para category:

# Redução drástica do tamanho do DataFrame na RAM
def otimizar_dataframe(df: pd.DataFrame) -> pd.DataFrame:
    for col in df.columns:
        # Downcast de inteiros
        if df[col].dtype == "int64":
            df[col] = pd.to_numeric(df[col], downcast="integer")
        # Downcast de floats
        elif df[col].dtype == "float64":
            df[col] = pd.to_numeric(df[col], downcast="float")
        # Conversão de objetos/strings repetitivos para Category (Consome muito menos RAM)
        elif df[col].dtype == "object":
            if df[col].nunique() / len(df[col]) < 0.5: # Menos de 50% de valores únicos
                df[col] = df[col].astype("category")
    return df

Orientação a Objetos Avançada (OOP)

A anatomia de Classes, Dunder Methods, Decorators e Herança.

Python aborda a Orientação a Objetos de forma muito pragmática. Diferente do Java/C#, não há restrição estrita de `private` (usa-se convenção com underscore _), mas existe um poder massivo através da manipulação do ciclo de vida e metaprogramação (Magic Methods).

A. O Ciclo de Vida do Objeto (Dunder Methods Base)

class ConexaoBanco:
    # 1. __new__: Aloca a memória. Chamado ANTES do __init__. Usado em Design Patterns como Singleton.
    def __new__(cls, *args, **kwargs):
        print("1. Alocando memória")
        instance = super(ConexaoBanco, cls).__new__(cls)
        return instance

    # 2. __init__: Inicializa o estado.
    def __init__(self, uri: str):
        print("2. Inicializando estado")
        self.uri = uri
        self.conectado = False

    # 3. __del__: O Destrutor. Invocado quando o Garbage Collector apaga o objeto.
    def __del__(self):
        print("3. Fechando conexões órfãs")
        self.conectado = False

    # 4. __str__: Representação para o Usuário (ex: print(obj))
    def __str__(self):
        return f"<ConexaoBanco na URI {self.uri}>"

    # 5. __repr__: Representação para o Desenvolvedor (Debugging)
    def __repr__(self):
        return f"ConexaoBanco('{self.uri}')"

    # 6. __call__: Permite invocar o objeto como se fosse uma função: obj()
    def __call__(self):
        print("Objeto invocado como função!")

B. Decoradores Estruturais e Encapsulamento

Python não requer getters/setters clássicos como no Java. A linguagem adota o Princípio do Acesso Uniforme via Properties.

@property, @classmethod e @staticmethod
class Empregado:
    salario_base_empresa = 1000  # Class Attribute

    def __init__(self, nome: str, cargo: str):
        self.nome = nome
        self._salario = 0  # Atributo protegido (convenção _)

    # 1. ENCAPSULAMENTO: Transforma método em atributo
    @property
    def salario(self):
        return self._salario

    # Setter (Controla a entrada de dados)
    @salario.setter
    def salario(self, valor):
        if valor < 0:
            raise ValueError("Salário não pode ser negativo")
        self._salario = valor

    # 2. INSTANCE METHOD: Opera na instância (requer 'self')
    def promover(self):
        self.salario *= 1.2

    # 3. CLASS METHOD: Opera na classe (requer 'cls'). Excelente para Padrões de Fábrica.
    @classmethod
    def alterar_base_empresa(cls, nova_base):
        cls.salario_base_empresa = nova_base
        
    @classmethod
    def construtor_alternativo(cls, texto_csv: str):
        nome, cargo = texto_csv.split(",")
        return cls(nome, cargo)

    # 4. STATIC METHOD: Não requer estado da classe nem da instância. Função utilitária.
    @staticmethod
    def validar_cpf(cpf: str) -> bool:
        return len(cpf) == 11

Orientação a Objetos Voltada para Dados

Os 4 Pilares da Programação aplicados na construção de conectores.

Pipelines monolíticos em scripts lineares acumulam complexidade, redundância de código e dificultam a testabilidade de partes isoladas. Aplicar OOP modulariza a arquitetura:

1. Abstração

Oculte a complexidade das interações físicas criando interfaces genéricas. O usuário do conector não precisa saber como o Spark estabelece a conexão sob o capô, apenas chama connector.read().

2. Encapsulamento

Proteja e controle o estado interno da classe. Variáveis sensíveis do Spark (como tokens de autenticação ou credenciais de banco) devem ser protegidas como membros privados/protegidos (ex: self._client_key).

3. Herança

Permite especializar conectores sem reescrever o código base. Uma classe S3Connector herda de uma classe abstrata DataConnector todos os logs, configurações e métodos comuns.

4. Polimorfismo

Diferentes classes podem implementar o mesmo método com assinaturas idênticas, mas comportamentos internos diferentes. Tanto S3Connector quanto JDBCConnector respondem a .read() retornando um DataFrame.

Código: Implementação Prática dos 4 Pilares de OOP para Engenharia de Dados

O script abaixo exemplifica a abstração de conectores de Datalake usando a biblioteca nativa abc do Python:

from abc import ABC, abstractmethod
from pyspark.sql import SparkSession, DataFrame

# 1. Abstração: Define a interface genérica
class DataConnector(ABC):
    def __init__(self, spark: SparkSession):
        self._spark = spark # Encapsulamento de membro protegido

    @abstractmethod
    def read(self, source_path: str) -> DataFrame:
        pass

# 2. Herança: S3Connector especializa a classe abstrata
class S3Connector(DataConnector):
    def read(self, source_path: str) -> DataFrame:
        # Polimorfismo: leitura específica do S3
        print(f"Lendo arquivos Parquet de: {source_path}")
        return self._spark.read.parquet(source_path)

# 3. Polimorfismo: JDBCConnector implementa o mesmo método lendo de Bancos Relacionais
class JDBCConnector(DataConnector):
    def __init__(self, spark: SparkSession, url: str):
        super().__init__(spark)
        self.__url = url # Membro estritamente privado (Private)

    def read(self, source_path: str) -> DataFrame:
        print(f"Lendo tabela {source_path} via JDBC")
        return self._spark.read.format("jdbc") \
            .option("url", self.__url) \
            .option("dbtable", source_path) \
            .load()

Design Patterns de Engenharia de Dados

Padrões de projeto para frameworks de processamento.

Padrões de projeto (Design Patterns) clássicos do GoF resolvem problemas de design comuns em frameworks analíticos de dados:

1. Factory Method (Fábrica de Conectores)

Centraliza a lógica de criação de objetos, permitindo instanciar conectores S3, JDBC ou Kafka dinamicamente com base nas strings de conexão de entrada, desacoplando o código de ingestão:

class ConnectorFactory:
    @staticmethod
    def get_connector(conn_type: str, spark: SparkSession, **kwargs) -> DataConnector:
        if conn_type.lower() == "s3":
            return S3Connector(spark)
        elif conn_type.lower() == "jdbc":
            return JDBCConnector(spark, url=kwargs["url"])
        else:
            raise ValueError(f"Tipo de conector '{conn_type}' desconhecido.")

2. Builder Pattern (Construção Fluida de Pipelines)

Permite configurar transformações complexas encadeadas em DataFrames de forma legível e modular:

class PipelineBuilder:
    def __init__(self, df: DataFrame):
        self.df = df

    def filter_active(self) -> 'PipelineBuilder':
        self.df = self.df.filter("status = 'Ativo'")
        return self

    def normalize_dates(self, date_col: str) -> 'PipelineBuilder':
        import pyspark.sql.functions as F
        self.df = self.df.withColumn(date_col, F.to_date(F.col(date_col), "yyyy-MM-dd"))
        return self

    def build(self) -> DataFrame:
        return self.df

# Chamada fluida do Builder (Clean Code)
df_processado = PipelineBuilder(df_bruto) \
    .filter_active() \
    .normalize_dates("data_criacao") \
    .build()

3. Repository Pattern (Isolamento de Estado e Metadados)

Isola a lógica de leitura/escrita de metadados do Datalake, permitindo que a aplicação salve o estado das execuções sem acoplamento direto com o banco:

class ExecutionRepository(ABC):
    @abstractmethod
    def save_log(self, job_name: str, status: str, records_processed: int) -> None:
        pass

class DynamoDBExecutionRepository(ExecutionRepository):
    def save_log(self, job_name: str, status: str, records_processed: int) -> None:

4. Strategy Pattern (Leitura Dinâmica de Formatos)

Permite injetar dinamicamente diferentes algoritmos de leitura física (CSV, Parquet, JSON) no conector em tempo de execução, mantendo a classe do pipeline isolada das particularidades de cada formato:

class FileReadStrategy(ABC):
    @abstractmethod
    def read_file(self, filepath: str) -> DataFrame:
        pass

class ParquetReadStrategy(FileReadStrategy):
    def __init__(self, spark: SparkSession):
        self.spark = spark
    def read_file(self, filepath: str) -> DataFrame:
        return self.spark.read.parquet(filepath)

class CSVReadStrategy(FileReadStrategy):
    def __init__(self, spark: SparkSession):
        self.spark = spark
    def read_file(self, filepath: str) -> DataFrame:
        return self.spark.read.option("header", "true").csv(filepath)

class FlexiblePipeline:
    def __init__(self, strategy: FileReadStrategy):
        self.strategy = strategy  # Injeção da estratégia

    def run(self, filepath: str) -> DataFrame:
        return self.strategy.read_file(filepath)

5. Otimização de Memória com __slots__ em Classes de Entidades

Por padrão, cada objeto em Python cria um dicionário __dict__ interno dinâmico para poder receber novos atributos a qualquer momento. Em Big Data, ao representar milhões de registros estruturados como objetos Python em memória, esse overhead consome centenas de Megabytes de RAM. Utilizar __slots__ impede o uso do dicionário dinâmico, economizando até 70% de RAM:

# Sem __slots__ (Consome alta memória por dicionário interno)
class LinhaDatalakeLegada:
    def __init__(self, id_transacao: str, valor: float):
        self.id_transacao = id_transacao
        self.valor = valor

# Com __slots__ (Reduz em até 70% o uso de RAM por instância física)
class LinhaDatalakeOtimizada:
    __slots__ = ("id_transacao", "valor")  # Trava atributos fixos
    
    def __init__(self, id_transacao: str, valor: float):
        self.id_transacao = id_transacao
        self.valor = valor

6. Ingestão Eficiente com Generators (yield vs Listas Completas)

Ao extrair dados de bancos transacionais OLTP (PostgreSQL, Oracle) usando Python, acumular todos os dados em listas na memória RAM causa estouro de heap (OOM). Generators (yield) transmitem os dados de forma lazy:

# ANTI-PATTERN: fetchall() acumula tudo na memória do servidor local
def carregar_dados_lista(cursor) -> list:
    return cursor.fetchall()  # Perigo de OOM para tabelas grandes

# PADRÃO OURO: yield streaming paginado de dados
def streaming_dados_generator(cursor, batch_size=1000):
    while True:
        linhas = cursor.fetchmany(batch_size)
        if not linhas:
            break
        for linha in linhas:
            yield linha  # Retorna de forma preguiçosa (Lazy Evaluation)

Padrões Arquiteturais Avançados em Engenharia de Dados

Além dos padrões criacionais e estruturais clássicos, a arquitetura moderna de plataformas de dados exige desacoplamento estrito entre a representação dos dados na RAM (DataFrames, Records) e as camadas físicas de persistência:

  • Dependency Injection (Injeção de Dependência): Evite que seus conectores ou classes de transformação instanciem a própria sessão do Spark (SparkSession.builder...) internamente. Injete o Spark ativamente no construtor da classe. Isso permite mockar sessões do Spark em ambientes de testes locais unitários de forma extremamente ágil.
  • Data Mapper vs. Active Record em Dados:
    • Active Record (Evitar para Big Data): O próprio objeto de dados conhece a lógica de persistência no banco (ex: df.save_to_s3()). Gera alto acoplamento e quebra o princípio de responsabilidade única (SRP).
    • Data Mapper (Recomendado): Uma classe isolada do sistema é encarregada de fazer a leitura e escrita (o mapeamento físico) do DataFrame na origem/destino (ex: a classe S3Connector gerencia o S3, mantendo o DataFrame isolado de saber onde será armazenado).
Exemplo Prático: Dependency Injection e Data Mapper

O código abaixo ilustra a injeção da dependência do Spark e o isolamento completo da persistência usando o padrão Data Mapper:

# 1. Dependency Injection no construtor da Classe de Transformação
class ClientTransformer:
    def __init__(self, spark: SparkSession):
        self.spark = spark  # SparkSession injetado de fora (testável!)

    def clean_data(self, df: DataFrame) -> DataFrame:
        import pyspark.sql.functions as F
        return df.filter(F.col("status") == "ATIVO").withColumn("nome", F.upper(F.col("nome")))

# 2. Data Mapper para Persistência (Isolando o DataFrame do destino físico)
class S3DataMapper:
    def __init__(self, s3_path: str):
        self.s3_path = s3_path

    def save(self, df: DataFrame) -> None:
        # Lógica física de gravação encapsulada
        df.write.mode("overwrite").parquet(self.s3_path)
