Amazon DocumentDB NoSQL (Documento compatível com MongoDB) Totalmente gerenciado, escala para milhões de leituras por segundo integrando JSON nativo. Amazon Redshift MPP Data Warehouse (OLAP) Armazenamento colunar com processamento massivo em paralelo para petabytes de dados analíticos. Latência de gravação linha a linha péssima. Não deve ser usado como banco de API de microsserviços. Data Warehousing corporativo centralizado, agregação histórica pesada e queries de BI corporativo.

Comparativo e Matriz de Decisão: SQL vs. NoSQL vs. SQS

trade-offs arquiteturais entre persistência transacional, escalabilidade e desacoplamento assíncrono

Um erro de design comum em arquiteturas distribuídas na AWS é tentar usar a mesma tecnologia para objetivos computacionais opostos. Abaixo detalhamos a comparação física e lógica das soluções:

Característica SQL (ex: Aurora Postgres) NoSQL (ex: DynamoDB) SQS (Simple Queue Service)
Natureza do Serviço Banco de Dados Relacional estruturado (Tabelas/Esquemas rígidos). Banco de Dados Não-Relacional distribuído (Chave-Valor/Documento). Mensageria / Fila de Mensagens distribuída (Fila FIFO ou Standard).
Garantias de Consistência Transações ACID estritas (isolação serializável, chaves estrangeiras, consistência forte imediata). Eventualmente consistente (consistência forte sob demanda pagando taxa adicional). Sem ACID nativo multi-tabelas clássico. Exactly-Once (em filas FIFO) ou At-Least-Once (filas Standard). Desacoplamento temporal.
Escalabilidade de Escrita Vertical (Writer único no Aurora, escala até limites da máquina). Réplicas apenas lêem. Horizontal infinita (auto-scaling automático adicionando partições baseadas nas PKs). Praticamente infinita (escala automaticamente sem provisionamento prévio).
Padrão de Consulta Queries ad-hoc altamente complexas, joins multi-tabelas, agregações arbitrárias (GROUP BY). Apenas por chaves primárias e índices secundários conhecidos (GSI/LSI). Sem joins. Apenas leitura destrutiva sequencial (consumidor lê a mensagem da fila e a deleta após processar).
Decisão de Uso (Quando Escolher?) Quando a integridade relacional é lei e as queries são imprevisíveis (ex: fechamento contábil, BI flexível). Quando o padrão de acesso é conhecido e você exige escala linear infinita com latência estável milissegunda. Para desacoplar microsserviços, amortecer picos de carga de escrita (Buffer/Throttling) e garantir resiliência assíncrona.

SQL vs NoSQL: O Veredito de Quando Usar

✅ Quando usar SQL (Relacional)
  • Integridade Financeira/ACID: Quando o sistema transaciona dinheiro (ex: transferências bancárias, pagamentos) e não pode existir a mínima chance de o débito ocorrer sem o crédito.
  • Padrão de Consulta Imprevisível: Quando os analistas de negócio ou usuários precisam fazer buscas flexíveis e dinâmicas, exigindo JOIN, GROUP BY, ou filtros ad-hoc complexos.
  • Relacionamentos Complexos M:N: Quando você tem muitas entidades fortemente acopladas (ex: ERPs, sistemas de RH, Gestão de Inventário).
  • Dados Estritamente Tabulares: Onde o schema (colunas) raramente muda.
✅ Quando usar NoSQL (Chave-Valor/Doc)
  • Ultra Baixa Latência em Escala: Quando o banco precisa responder em menos de 10ms, seja para 100 usuários ou 10 milhões de usuários (ex: Leaderboards de Jogos, Catálogos de Streaming, Sessões Web).
  • Esquema Flexível / JSON: Quando cada item pode ter atributos diferentes (ex: catálogo de E-commerce, onde uma camisa tem "Tamanho" e uma TV tem "Polegadas").
  • Padrão de Acesso Previsível: Quando você sabe de antemão que 95% das buscas serão "Busque o Usuário pelo ID" e não precisa de relacionamentos em tempo de consulta.
  • Carga Massiva de Escrita (High Write Throughput): Sistemas de IoT, logs e tracking de cliques que bombardeiam o banco de dados o tempo todo.
Regra de Ouro da Arquitetura Decisória:
1. Use SQS na borda (Ingress) sempre que receber dados de sensores ou eventos externos massivos de e-commerce. A fila garante que a sua API responda "202 Accepted" em milissegundos, impedindo que picos de tráfego derrubem ou gerem exaustão de conexões físicas no banco de dados.
2. Use o NoSQL (DynamoDB) para dados operacionais desestruturados ou rastreamento rápido de estado de curta duração (ex: se o pagamento foi processado ou não).
3. Use o SQL (Aurora) apenas quando a mensagem for validada e precisar de consistência relacional estrita (ex: alterar balanço de contas bancárias ou gerar a fatura consolidada final do cliente).

Modelagem Física e Lógica (RDBMS)

O Modo Clássico (Power Designer) de Garantir Integridade (ACID)

Bancos Relacionais (como Amazon RDS PostgreSQL ou Aurora) baseiam-se na Normalização. O objetivo não é "pre-juntar" os dados no disco como no NoSQL, mas sim separá-los logicamente para evitar redundância, garantindo a integridade via Foreign Keys (Chaves Estrangeiras).

Exemplo 1: E-commerce (Relações 1:1 e 1:N)

Em um sistema transacional, um Usuário pode ter apenas um Perfil (Relação 1:1 usando constraint UNIQUE na FK) e pode ter vários Pedidos (Relação 1:N).

Exemplo 2: ERP de Inventário (Relação N:M)

Aqui está o coração do RDBMS: Relações Muitos-Para-Muitos. Um Produto tem vários Fornecedores, e um Fornecedor fornece vários Produtos. O banco relacional exige a criação de uma Tabela Associativa (Junction Table) para mapear essa cardinalidade.

RDS ERD: ERP INVENTÁRIO (JUNCTION TABLE)

Legenda do Diagrama

  • Junction Table: Tabela PRODUCT_SUPPLIER essencial para mapear a relação N:M. No banco, ela contém Duas Foreign Keys compondo sua Primary Key.
  • Garantia ACID: Se tentar deletar um Fornecedor que já tem Produto associado, o RDBMS barra a exclusão (Restrict) garantindo Integridade Referencial.

Amazon DynamoDB: Architecture & Single-Table Design

Modelagem NoSQL avançada, RCU/WCU, GSI, LSI e Hot Partitions

Bancos NoSQL corporativos como o DynamoDB diferem substancialmente do modelo relacional tradicional. Eles são otimizados para latência milissegunda consistente independente do tamanho da tabela, desde que as chaves de acesso sejam perfeitamente modeladas (Acesso em O(1)).

Capacity: RCU, WCU e Modo On-Demand

Em modo Provisionado, a métrica raiz de throughput são RCUs (Read Capacity Units) e WCUs (Write Capacity Units). 1 WCU permite gravar 1 KB por segundo. 1 RCU permite ler 4 KB/s se a consistência for eventual, ou requer 2 RCUs para garantir Strong Consistency.

O modo On-Demand é recomendado quando a carga é altamente imprevisível. Você paga por requisição sem estipular limites prévios, deixando o Dynamo escalonar agressivamente por debaixo dos panos.

Balanceamento HASH e Hot Partitions

O throughput provisionado de uma tabela (ex: 3.000 WCU) é dividido igualmente pelo número de partições físicas SSD (ex: 3 partições = 1.000 WCU por partição). Se a sua Partition Key (PK) for uma data atual (2026-06-10), todas as gravações do dia cairão na mesma partição (Hot Partition). O Dynamo estourará um ProvisionedThroughputExceededException ao atingir 1.000 WCU, mesmo com 2.000 WCUs sobrando na tabela. Use Hash Sharding/UUIDs para a PK.

Modelagem: Single-Table Design, GSI e LSI

  • Single-Table Design: Diferente do modelo Relacional (Normalização 3NF com FKs), no DynamoDB a regra de ouro é colocar todos os tipos de entidades em uma única tabela física. Para relacionar entidades 1:N (Ex: Usuário e seus Pedidos), você agrupa os itens empilhando as Sort Keys (SK) sob a mesma Partition Key. Exemplo: PK="USER#123", SK="PROFILE" para dados do usuário; PK="USER#123", SK="ORDER#99" para seus pedidos.
  • Global Secondary Index (GSI): Se você precisa buscar pedidos por "Data" em vez de "Usuário", você cria um GSI. O GSI é uma tabela réplica física, mantida asíncronamente pela AWS, que escolhe novos atributos para assumirem os papéis de nova PK/SK. Cuidado: GSIs possuem seu próprio pool de RCU/WCUs e podem sofrer throttling se mal dimensionados.
  • Local Secondary Index (LSI): Compartilha a mesma PK da tabela base, mas muda a SK. Só pode ser criado no momento de criação da tabela (limite físico de 10GB por partição).
Integração Zero-ETL do DynamoDB com Aurora/Redshift:

A nova feature de integração AWS permite espelhar o DynamoDB para o Amazon Redshift ou S3 (usando DynamoDB Export/Kinesis Streams) sem escrever código Lambda, habilitando queries analíticas SQL complexas (com JOINs) em tempo quase real sem prejudicar o desempenho transacional da tabela NoSQL.

Desenho de Arquitetura: Data Engineering CDC (DynamoDB & RDS para Iceberg)

Para um engenheiro de dados, o desafio de bancos transacionais NoSQL e SQL (DynamoDB e Aurora) é que não é possível rodar queries analíticas pesadas (GROUP BY, JOIN em milhões de linhas) diretamente na origem sem derrubar a aplicação. A solução é montar um Change Data Capture (CDC) contínuo para extrair apenas o delta (o que mudou) e consolidar num formato colunar como Apache Iceberg no S3.

📚 Documentação Oficial AWS:

A AWS recomenda arquiteturas de CDC orientadas a eventos utilizando DynamoDB Streams nativo para capturar alterações em nível de item. Isso não consome WCU/RCU da tabela principal e garante ordem estrita para entrega ao Kinesis ou Lambda (AWS Prescriptive Guidance: Stream data from DynamoDB to S3).

Amazon ECS: Teoria de Containers & Launch Types

Diferenças fundamentais entre ECS Fargate e ECS on EC2, estrutura de blueprints e segurança

O Amazon ECS (Elastic Container Service) é o serviço de orquestração de containers altamente escalável e de alta performance nativo da AWS. Diferente do Kubernetes (EKS), o ECS foca em simplificar o deploy eliminando a necessidade de gerenciar nós de controle complexos (Control Plane).

Launch Type
ECS Fargate (Serverless)
Como funciona: A AWS gerencia toda a computação. O engenheiro declara apenas o tamanho de CPU e Memória da Task.
Tradeoffs: Menor overhead operacional, isolamento físico de segurança por task (micro-VMs Firecracker). Custo ligeiramente superior por recurso ativo e boot time mais longo.
Launch Type
ECS on EC2 (Gerenciado)
Como funciona: O cluster ECS usa instâncias EC2 gerenciadas no seu próprio grupo de Auto Scaling como workers de container.
Tradeoffs: Controle total do sistema operacional, suporte a volumes EBS locais e GPUs dedicadas. Exige gerenciar patches do SO e agentes do ECS instalados nas máquinas.

Arquitetura ECS: Cluster, Service, Task & Task Definition

A tabela a seguir explica a hierarquia de objetos lógicos dentro do ecossistema do ECS:

Componente Propósito Análogo Físico
Cluster Agrupamento lógico de computação (Fargate ou EC2) em subredes privadas. Data Center Virtualizado
Task Definition O blueprint em formato JSON definindo a imagem Docker, portas, variáveis de ambiente e volumes. Dockerfile / Docker Compose
Task A instância ativa e executável do container em si, rodando de forma isolada na VPC. Container Ativo (Docker Run)
Service Gerenciador que garante que a quantidade solicitada de Tasks esteja saudável, integrando-as ao Load Balancer. Process Daemon / Orquestrador

Segurança de Containers: Task Role vs. Task Execution Role

Um erro de segurança recorrente em projetos de ECS é conceder permissões excessivas às instâncias que executam os containers. A AWS divide a identidade IAM no ECS em duas camadas de privilégio de grão fino:

  • Task Execution Role: Utilizada pelo agente do ECS rodando na infraestrutura (antes do container iniciar). Permissões típicas: baixar a imagem do container do ECR, enviar logs de stdout para o CloudWatch, descriptografar variáveis sensíveis vindas do Secrets Manager ou System Manager Parameter Store.
  • Task Role: Utilizada pela sua aplicação de fato rodando dentro do container (após a inicialização). Permissões típicas: ler/gravar dados em um bucket S3, consultar uma tabela do DynamoDB, ou publicar mensagens em um tópico SNS.

Escrita em Quorum (Write Quorum) no Aurora

Para otimizar escritas, o Aurora utiliza um sistema de quórum distribuído. Cada bloco de dados é segmentado e gravado em 6 instâncias de storage (2 por AZ). Uma escrita é considerada um commit válido assim que 4 das 6 instâncias confirmam a gravação física (4/6 Write Quorum). Leituras de blocos requerem a confirmação de 3 de 6 cópias (3/6 Read Quorum) para reconstruir dados consistentes caso ocorram falhas parciais em storage pools.

Multi-AZ DB Instance vs DB Cluster (RDS Tradicional)

Se você não utiliza Aurora, a AWS oferece dois modelos de alta disponibilidade no RDS PostgreSQL/MySQL: Multi-AZ DB Instance, onde o Standby é fisicamente idêntico mas bloqueado para leitura (failover de ~60-120s); e o novo Multi-AZ DB Cluster, que usa três instâncias ativas (2 Readers e 1 Writer) e acelera commits escrevendo simultaneamente nos SSDs locais de duas réplicas legíveis, diminuindo o failover para ~35s.

Estratégias de Snapshots, Backups e RTO/RPO

  • Automated Backups (RDS Tradicional): A AWS tira um snapshot diário do disco EBS inteiro e arquiva os Transaction Logs (WAL) a cada 5 minutos no S3. O RPO (Recovery Point Objective) máximo é de ~5 minutos para Point-in-Time Recovery (PiTR). Restaurações demoram o tempo necessário para provisionar e "esquentar" (hydrate) os blocos do S3 para um novo disco EBS.
  • Continuous Backups (Aurora): No Aurora, o backup é completamente contínuo e streaming. Como a camada de storage é baseada em logs, o storage engine transfere micro-blocos para o S3 em tempo real de forma assíncrona, sem impactar a CPU do banco, atingindo impacto nulo de I/O em backups pesados.

Amazon RDS Proxy: Connection Pooling

Microsserviços serverless esgotam rapidamente a memória (RAM) da instância RDS por conexões ociosas (o Postgres consome ~10MB por TCP inativa). O RDS Proxy gerencia um Connection Pool, multiplexando dezenas de clientes em poucas conexões físicas com o DB. Além disso, em caso de failover do Aurora, ele redireciona instantaneamente as chamadas HTTP para o novo Writer, mascarando a interrupção da aplicação (sem timeouts de DNS).

Migração e CDC com AWS DMS e SCT

Para migrar de bancos legados (ex: Oracle local ou RDS Monolítico) para Aurora sem downtime, utiliza-se o AWS Database Migration Service (DMS) acompanhado do SCT (Schema Conversion Tool).

O DMS se conecta ao banco de origem, realiza o Full Load da base inicial e então ativa o CDC (Change Data Capture). O CDC lê nativamente os transaction logs do banco de origem (ex: wal2json no Postgres) e aplica os INSERT/UPDATES na nova base Aurora. Quando o "Lag" do DMS se aproxima de 0s, a engenharia simplesmente "vira a chave" do tráfego na aplicação.

Guia Operacional: Monitoramento & Troubleshooting Avançado

CLI Cheat Sheet: Operando e Diagnosticando ECS & Load Balancers

# 1. Obter informações de tarefas rodando no ECS
aws ecs list-tasks --cluster prod-analytics-cluster

# 2. Descrever detalhes de uma task específica (verificar se há erros de Out of Memory - OOM)
aws ecs describe-tasks \
  --cluster prod-analytics-cluster \
  --tasks arn:aws:ecs:us-east-1:123456789012:task/prod-analytics-cluster/99b6622

# 3. Forçar um redesploy limpo sem alterar a Task Definition
aws ecs update-service \
  --cluster prod-analytics-cluster \
  --service analytics-service \
  --force-new-deployment

# 4. Interagir diretamente (SSH/Bash) dentro do container ECS rodando no Fargate
aws ecs execute-command \
  --cluster prod-analytics-cluster \
  --task 99b66223a4 \
  --container api-container \
  --interactive \
  --command "/bin/sh"

# 5. Verificar o status de integridade do ALB Target Group
aws elbv2 describe-target-health \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:12345678:targetgroup/tg-ecs-analytics/bc51

SQL Diagnostics para Administradores de Bancos (PostgreSQL RDS / Aurora)

Em momentos de travamento no banco, utilize as queries estruturadas abaixo para descobrir e encerrar locks e processos órfãos consumindo CPU:

Query 1: Listar conexões ativas ordenadas por tempo de execução (identificar queries travando)
SELECT pid, age(query_start, clock_timestamp()), usename, state, query 
FROM pg_stat_activity 
WHERE state != 'idle' 
ORDER BY query_start ASC 
LIMIT 10;
Query 2: Identificar Locks Ativos (Tabelas bloqueadas por transações pendentes)
SELECT
    blocked_locks.pid     AS blocked_pid,
    blocked_activity.usename  AS blocked_user,
    blocking_locks.pid    AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query    AS blocked_statement,
    blocking_activity.query   AS blocking_statement
FROM  pg_catalog.pg_locks         blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks         blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
Comando 3: Derrubar transação bloqueadora específica via ID do processo (PID)
-- Termina a query de forma limpa
SELECT pg_cancel_backend(blocking_pid);

-- Força o encerramento imediato da conexão física com o banco
SELECT pg_terminate_backend(blocking_pid);
