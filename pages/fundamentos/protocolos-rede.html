Módulo: Infra, Redes & Segurança

Protocolos de Rede e TLS

Domine a comunicação em rede desde o controle de transporte (TCP/SCTP) até a segurança da camada de aplicação com HTTPS e a mecânica completa do TLS Handshake.

01

Camada de Transporte (L4)

A Camada de Transporte (Layer 4 do Modelo OSI) é a responsável por pegar os pacotes brutos roteados pelo IP (Layer 3) e transformá-los em conexões lógicas úteis para as aplicações. É aqui que decidimos entre garantia de entrega e velocidade.

  • 1. TCP (Transmission Control Protocol): É o protocolo mais usado na internet (navegação web, banco de dados, emails). O TCP é "Orientado à Conexão", o que significa que ele executa um "aperto de mãos" de três vias (Three-Way Handshake: SYN, SYN-ACK, ACK) antes de enviar qualquer dado. Ele garante que os pacotes cheguem na ordem certa e sem perdas, mas tem alta latência inicial.
  • 2. UDP (User Datagram Protocol): É "Connectionless". Ele simplesmente "atira" os pacotes para o destino sem checar se chegaram, sem handshake e sem ordem. É a escolha primária para Streaming de Vídeo, VoIP e Jogos Online, onde perder um *frame* é aceitável, mas esperar (lag) não é.
  • 3. SCTP (Stream Control Transmission Protocol): Um protocolo avançado que funde as garantias do TCP com a agilidade baseada em mensagens do UDP. Ele brilha em ambientes de Telecom e 5G porque suporta Multi-homing (um endpoint pode ter múltiplos endereços IP ativos simultaneamente) e evita o problema de bloqueio de linha (Head-of-line blocking), permitindo fluxos de dados paralelos dentro de uma mesma conexão.
02

Camada de Aplicação (HTTP vs HTTPS)

Sobre as fundações sólidas do TCP, trafega a linguagem universal da Web: o HTTP (Hypertext Transfer Protocol).

Em sua forma natural, o HTTP transmite dados em Cleartext (texto puro). Se um atacante interceptar o tráfego da rede (ataque Man-in-the-Middle), ele poderá ler abertamente senhas, tokens de API e PII. A evolução óbvia foi adicionar uma camada blindada, criando o HTTPS (HTTP Secure). O HTTPS não é um protocolo novo em si, mas sim o tráfego HTTP tradicional encapsulado dentro de um túnel encriptado (o protocolo TLS).

03

Deep Dive: TLS Handshake & AWS

O TLS (Transport Layer Security) — que substituiu o antigo SSL — é uma obra-prima criptográfica. A dificuldade da criptografia em redes abertas é o "Problema da Troca de Chaves": como o cliente e o servidor concordam com uma senha para criptografar os dados, sem que alguém copie essa senha no exato momento em que eles a estão combinando?

🔐
Criptografia Assimétrica vs Simétrica O TLS resolve o impasse unindo o melhor dos dois mundos. Ele usa Criptografia Assimétrica (Par de Chaves Pública/Privada - lentas) estritamente para que o cliente e o servidor concordem de forma segura e invisível sobre uma Chave Simétrica temporária (muito mais rápida). Após esse acordo, o túnel é fechado e os dados massivos trafegam sob a chave simétrica.

Esse acordo seguro é chamado de TLS Handshake, ilustrado no diagrama da arquitetura AWS abaixo.

O Processo na Nuvem AWS

Ao criar uma arquitetura moderna na AWS, gerenciar essas chaves complexas é brutal. Por isso, utilizamos o AWS ACM (Certificate Manager) para emitir e rotacionar Certificados X.509 automaticamente.

A melhor prática de arquitetura (ilustrada acima) é a Terminação TLS na Borda (TLS Offloading). O AWS CloudFront ou o Application Load Balancer (ALB) recebe o tráfego pesado e o pesado custo computacional de realizar o TLS Handshake com o cliente da internet. Uma vez que o tráfego está dentro da VPC (onde a AWS garante a segurança da rede subjacente), o ALB encaminha as requisições como HTTP em texto puro para os containers ECS, economizando CPU das suas aplicações.

04

TCP Internals: Flow & Congestion Control

Para engenheiros de infraestrutura, entender que o TCP "garante entrega" não é suficiente. É preciso entender como ele faz isso sem sobrecarregar a rede mundial.

  • Sliding Window (Controle de Fluxo): É o mecanismo onde o receptor avisa ao transmissor quanto espaço de buffer ele ainda tem disponível (o tamanho da "janela"). Se o receptor estiver sobrecarregado processando dados (ex: gargalo de CPU num banco de dados recebendo ingestão massiva), ele diminui o tamanho da janela até chegar a zero, forçando o remetente (cliente) a pausar o envio. Isso evita que pacotes sejam descartados na porta do receptor.
  • Congestion Control (Slow Start & Congestion Avoidance): O TCP assume que qualquer pacote perdido é culpa de "congestionamento" nos roteadores intermediários. Quando uma conexão começa, ele inicia o algoritmo Slow Start, mandando poucos pacotes e dobrando a quantidade a cada Round Trip Time (RTT). Se houver perda, ele entra em Congestion Avoidance, cortando drasticamente a velocidade pela metade. É por isso que você nunca atinge a banda máxima da sua internet no exato milissegundo inicial de um download.
05

A Revolução do UDP: QUIC e HTTP/3

O TCP reinou absoluto na web por 40 anos, mas seu maior defeito arquitetural é o Head-of-Line Blocking (Bloqueio de Cabeceira). Como o TCP garante ordem estrita, se você estiver baixando 10 imagens simultaneamente e o pacote da Imagem 1 se perder na rede, o protocolo paralisa o fluxo inteiro (mesmo que os pacotes da Imagem 2 e 3 já tenham chegado) até retransmitir a Imagem 1.

⚡
O Protocolo QUIC (Criado pelo Google) Para resolver isso, a indústria decidiu criar o HTTP/3, mas abandonou o TCP! O HTTP/3 roda em cima do QUIC, que por sua vez roda em cima do UDP. A genialidade é recriar o controle de pacotes perdidos na camada de aplicação (dentro do QUIC), mas permitindo streams multiplexados independentes. Assim, se a Imagem 1 atrasar, a Imagem 2 e 3 continuam rendenrizando livremente. Além disso, o QUIC funde o TLS Handshake com a conexão inicial, cravando a latência de handshake de 3 viagens para apenas 1 (0-RTT em reconexões)!
06

WebSocket vs HTTP (Stateful vs Stateless)

Na camada L7, temos dois paradigmas brutais de como gerenciar as sessões sobre conexões TCP:

  • O Modelo Stateless (HTTP/REST): Toda requisição do cliente é isolada e tem um fim claro. O servidor processa a requisição, envia a resposta (Response) e a "transação lógica" morre. Se o servidor quiser avisar o cliente de algo no futuro, não consegue, pois o cliente é quem dita quando abrir conexões (Polling).
  • O Modelo Stateful (WebSockets): Iniciado através de um HTTP Upgrade Request (Protocol Switching), a conexão TCP subjacente é mantida aberta persistentemente no servidor. A partir desse momento, estabelece-se um duto Bidirecional Full-Duplex. É crucial em mercados financeiros (Tickers de Bolsa), chats em tempo real e jogos, pois o Servidor pode "empurrar" (Push) mensagens ativamente para milhares de clientes sem que eles tenham que perguntar.

Nota de Arquitetura AWS: Manter milhões de WebSockets abertos (Idle TCP Connections) derruba firewalls tradicionais e load balancers devido ao esgotamento de portas efêmeras e File Descriptors. O API Gateway WebSocket API resolve esse pesadelo abstraindo a manutenção de conexões abertas por trás da cortina da AWS, disparando apenas invocações pontuais do AWS Lambda (Stateless) para você através de ConnectionIds.
