Software Testing na Engenharia de Dados

Garanta a sanidade dos seus pipelines construindo uma Pirâmide de Testes robusta, do Unitário ao End-to-End, usando Pytest, Fakers, Testes Mutantes e Contratos de Dados.

01

A Pirâmide de Testes Adaptada para Dados

Diferenças entre Unitário, Funcional, Integração e End-to-End (E2E).

Em engenharia de software clássica, a Pirâmide de Testes dita que você deve ter muitos Testes Unitários (rápidos e baratos) na base, e poucos Testes E2E (lentos e caros) no topo. Em engenharia de dados, esse conceito é adaptado porque dados possuem gravidade, volume e estado externo constante (Bancos, Storages).

1. Testes Unitários e Funcionais

Isolamento Total: Testa a menor unidade lógica (ex: uma função de limpeza de CPF ou um cálculo de desconto). Não toca em banco de dados nem internet.

Comportamental (BDD): Foca na regra de negócio (se X acontecer, Y deve ser retornado). Usa bibliotecas como `pytest` e isola os componentes externos usando unittest.mock (Mocks & Stubs).

2. Testes de Integração

Limites do Sistema: Verifica se os seus módulos conversam bem com componentes externos, como um banco de dados real. Geralmente usa containers efêmeros locais (via Testcontainers ou Docker Compose) para gravar em um PostgreSQL de teste e garantir que a query rodou sem quebrar schemas.

3. Testes End-to-End (E2E)

A Jornada Completa: Pega um arquivo cru no "S3 local", processa pelo Spark job e valida a tabela final no "Redshift local". Lento, custoso e instável, mas simula o usuário final (ou o dashboard) consumindo o pipeline.

Testes Mutantes

Uma métrica implacável. Usando a lib mutmut, o Python "quebra" (sofre mutação de operadores, ex: de `>` para `<`) o seu código fonte de propósito. Se os seus testes passarem mesmo com o código quebrado, significa que seus testes são cegos (falsos positivos). Os testes PRECISAM falhar diante de mutantes.

02

Ecossistema Python de Testes (Show me the Code!)

Pytest, Faker e a construção das três camadas da pirâmide.

1. Teste Unitário (pytest + Faker + Mocks)

A ferramenta `Faker` gera nomes e dados aleatórios para evitar hardcode.

import pytest
from faker import Faker
from unittest.mock import patch
from src.etl.transform import calcular_imposto

fake = Faker('pt_BR')

def test_calculo_imposto_positivo():
    # Arrange (Preparação)
    nome = fake.name()
    salario = 5000.0
    
    # Act (Ação)
    imposto = calcular_imposto(salario)
    
    # Assert (Verificação)
    assert imposto == 500.0, f"Cálculo falhou para o usuário {nome}"

# Teste com Mock (Isolando a chamada de banco de dados da função)
@patch('src.etl.extract.obter_do_banco')
def test_extracao_falha_graciosamente(mock_banco):
    # Simula o banco estourando erro
    mock_banco.side_effect = ConnectionError("Banco fora do ar")
    
    with pytest.raises(ConnectionError):
         from src.etl.extract import iniciar_pipeline
         iniciar_pipeline()
2. Teste de Integração (PySpark Testing)

Testes no PySpark exigem a inicialização de uma `SparkSession` local. Em grandes projetos, criamos isso em um conftest.py como uma fixture de escopo "session" para não iniciar o Spark a cada novo teste (o que mataria a memória).

import pytest
from pyspark.sql import SparkSession
from pyspark.sql import Row

@pytest.fixture(scope="session")
def spark():
    # Inicia Spark Local de forma muito leve
    spark = SparkSession.builder \
        .master("local[1]") \
        .appName("TestIntegration") \
        .config("spark.sql.shuffle.partitions", "1") \
        .getOrCreate()
    yield spark
    spark.stop()

def test_agregacao_spark_integra_sucesso(spark):
    # Dataframe MOCK Local
    dados = [Row(id=1, val=100), Row(id=2, val=200)]
    df = spark.createDataFrame(dados)
    
    # Chama a função real de transformação do ETL
    from src.etl.transform import agregar_valores
    df_result = agregar_valores(df)
    
    # Coleta e verifica (Integração Lógica do Spark Executada)
    assert df_result.collect()[0]["soma_val"] == 300
3. Teste End-to-End (E2E) Pipeline Completo

Um teste E2E real varre todo o fluxo de ingestão e gravação, interagindo com o FileSystem ou Buckets.

import os
import pytest
from src.pipeline_main import rodar_pipeline_diario

def test_pipeline_e2e_completo(tmp_path):
    # Setup de Pastas Temporárias (tmp_path é injetado pelo pytest)
    entrada_dir = tmp_path / "raw"
    saida_dir = tmp_path / "gold"
    entrada_dir.mkdir()
    
    # 1. Cria dado CSV de input na ponta inicial
    arquivo_input = entrada_dir / "vendas.csv"
    arquivo_input.write_text("id,valor\n1,10\n2,20")
    
    # 2. Roda a pipeline inteira (Ação E2E)
    rodar_pipeline_diario(source=str(entrada_dir), target=str(saida_dir))
    
    # 3. Valida a Ponta Final (Verifica se gerou Parquet e se tem as linhas certas)
    arquivos_saida = list(saida_dir.glob("*.parquet"))
    assert len(arquivos_saida) > 0, "O pipeline não gerou os arquivos parquet no final"
    
    # Valida conteúdo final com Pandas
    import pandas as pd
    df_final = pd.read_parquet(arquivos_saida[0])
    assert df_final["valor"].sum() == 30
03

Data Quality as Code (Contratos de Dados)

Validações estatísticas na esteira usando Great Expectations e PyDeequ.

Testes de código garantem que o software funciona. Mas em engenharia de dados, se o dado mudar o seu perfil silenciosamente (ex: a coluna idade começar a vir negativa), o software não quebra, mas a empresa sofre perdas financeiras (Schema/Data Drift). É aqui que entram os Testes de Contrato de Dados (Data Quality as Code).

Great Expectations

Funciona criando "expectativas" declarativas em formato JSON. Ele lê um DataFrame Pandas/Spark ou banco relacional e gera relatórios HTML ("Data Docs") automáticos.

expect_column_values_to_not_be_null("cpf")

expect_column_values_to_be_between("idade", 0, 120)

Perfeito para criar um Circuit Breaker no Airflow e pausar o pipeline se o dado for tóxico.

PyDeequ (Amazon Deequ)

Desenvolvido pela própria Amazon focado estritamente em grandes volumes via Apache Spark. Em vez de iterar linha por linha para testar o contrato, ele traduz os "testes" em instruções otimizadas do Catalyst (Engine do Spark) e faz agregação de massa (Single Pass).

Muito usado em Data Lakes severos (Petabytes) para profilamento e anomalias estatísticas sem matar o cluster EMR.
