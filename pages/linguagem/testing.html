Software Testing (E2E) na Engenharia de Dados

Baseado nos Fundamentos de Engenharia de Dados (Joe Reis), garanta a sanidade dos seus pipelines construindo uma Pirâmide de Testes robusta, do Unitário ao End-to-End, usando Pytest, Fakers, Testes Mutantes, Qualidade de Dados e Testes Massivos de Performance em ferramentas da AWS.

01

A Pirâmide de Testes Adaptada para Dados

Diferença entre a abordagem Clássica e a Engenharia de Dados.

Em engenharia de software clássica, a Pirâmide de Testes (Martin Fowler) dita que você deve ter muitos Testes Unitários (rápidos) na base, e poucos Testes E2E (lentos) no topo. Em engenharia de dados, esse conceito é adaptado porque dados possuem gravidade, volume e estado (Bancos, Storages).

Estrutura de Diretórios & Orquestração

Como organizar o código do projeto de dados para testes maduros.

Uma base de código escalável precisa isolar claramente os tipos de testes. Abaixo, a estrutura recomendada para projetos PySpark:

📁 Estrutura de Pastas (Data Pipeline)

project_root/
├── src/
│   ├── jobs/
│   │   └── financial_clearing.py  # Código Spark principal
│   └── utils/
│       └── transformations.py     # Lógicas de UDFs e Maps
├── tests/
│   ├── conftest.py                # Fixtures globais (SparkSession)
│   ├── unit/
│   │   └── test_transformations.py
│   ├── integration/
│   │   └── test_financial_clearing.py
│   └── e2e/
│       └── orchestrator_test.py
├── Makefile
└── requirements-dev.txt

Configuração Global (pytest.ini)

O pytest.ini centraliza as configurações do seu runner. Nele, você pode registrar marcadores (ex: @pytest.mark.slow para testes que não devem rodar em todo commit) e variáveis de ambiente.

⚙️ pytest.ini

[pytest]
# Diretórios onde o pytest deve buscar os testes
testpaths = tests

# Opções padrão do terminal (verbosity e summary)
addopts = -v -ra --tb=short

# Registro de markers customizados
markers =
    slow: marca o teste como lento (testes de E2E pesados)
    integration: marca o teste como de integração
    performance: testes de stress e benchmark

# Variáveis de ambiente default para os testes
env =
    AWS_DEFAULT_REGION=us-east-1
    APP_ENV=test

Orquestrando os Testes E2E (Testcontainers)

Para orquestrar testes E2E, o padrão ouro é utilizar Testcontainers [Ref: Docs Oficiais] e CI/CD Runners. Em vez de testar na AWS (o que gera custos e instabilidade), subimos dependências via Docker em tempo de pipeline.

🐍 tests/e2e/test_with_docker.py

import pytest
from testcontainers.postgres import PostgresContainer
from testcontainers.kafka import KafkaContainer
import psycopg2

@pytest.fixture(scope="session")
def postgres_db():
    """Sobe um PostgreSQL em Docker para o teste e destrói ao final."""
    with PostgresContainer("postgres:15-alpine") as postgres:
        # Passa a URL de conexão para os testes rodarem
        yield postgres.get_connection_url()

    """Sobe um Kafka em Docker para injetar mensagens."""
    with KafkaContainer("confluentinc/cp-kafka:7.3.0") as kafka:
        yield kafka.get_bootstrap_server()

    """
    Seu job Spark rodará local, conectará no broker Kafka efêmero para ler a fila
    e salvará no Postgres efêmero. 
    """

  • Setup Idempotente: O `pytest` invoca as fixtures que sobem os containers em portas randômicas (evitando colisões no CI/CD).
  • Run & Assert: O PySpark consome o Kafka efêmero e grava no Postgres efêmero. O teste verifica as tabelas no Postgres.
  • Teardown Automático: Os contêineres são destruídos quando o contexto do `with` encerra, não deixando "lixo" na máquina do desenvolvedor.

Deep Dive: O Papel do conftest.py

Injeção de dependência e controle de sessão no Pytest.

O conftest.py é um arquivo mágico no pytest. Tudo que for declarado nele fica disponível para toda a suíte de testes daquela pasta, sem necessidade de import.

Na Engenharia de Dados, o uso mais crítico do conftest.py é criar uma SparkSession local com scope de sessão. O Spark demora alguns segundos para inicializar a JVM. Se cada teste instanciar uma sessão, a suíte demorará horas. Se criarmos uma com scope="session", ela é instanciada apenas uma vez para todos os testes.

🐍 tests/conftest.py

import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    """
    Cria uma SparkSession em memória.
    O scope='session' garante que a JVM suba apenas 1 vez por run do Pytest.
    """
    spark = SparkSession.builder \
        .master("local[2]") \
        .appName("FinancialTests") \
        .config("spark.sql.shuffle.partitions", "2") \
        .config("spark.ui.enabled", "false") \
        .getOrCreate()
    
    yield spark  # Retorna a sessão para os testes
    
    spark.stop() # Teardown: Encerra a JVM no final

Otimização: O plugin pytest-pyspark

Escrever a fixture de inicialização do Spark manualmente é útil para entender o funcionamento, mas em projetos profissionais, a recomendação é usar o plugin oficial pytest-pyspark. Ao instalá-lo (pip install pytest-pyspark), ele injeta automaticamente uma fixture chamada spark no seu ambiente, já configurada para testes.

⚙️ pytest.ini (Com pytest-pyspark)

[pytest]
# Configura o plugin nativo para já inicializar o Spark
spark_options =
    spark.app.name: my-pytest-spark-tests
    spark.executor.instances: 1
    spark.sql.shuffle.partitions: 2
    spark.ui.enabled: false

Com essa configuração, você pode deletar a fixture manual do conftest.py e apenas chamar def test_algo(spark): nas suas funções.

Gerando Massas de Dados Fictícias com Faker

Para testar lógicas de dados, não utilize bases reais (risco de vazamento de PII/LGPD). Crie fixtures no conftest.py utilizando a biblioteca faker para gerar milhares de registros consistentes sob demanda.

🐍 tests/conftest.py (Fixture Faker)

import pytest
from faker import Faker
import pandas as pd

@pytest.fixture
def fake_transactions_df(spark):
    """
    Gera um Spark DataFrame com 10.000 transações financeiras fake.
    Ideal para testar lógicas de agregação e performance leve.
    """
    fake = Faker('pt_BR')
    
    # Gerando dados massivos
    data = []
    for _ in range(10000):
        data.append({
            "tx_id": fake.uuid4(),
            "cliente_nome": fake.name(),
            "cpf": fake.cpf(),
            "valor": round(fake.pyfloat(min_value=1.0, max_value=50000.0), 2),
            "data_tx": fake.date_this_year(),
            "status": fake.random_element(elements=('APPROVED', 'DENIED', 'PENDING'))
        })
        
    # Converte para Pandas e depois para Spark (eficiente para mocks grandes)
    pdf = pd.DataFrame(data)
    df_spark = spark.createDataFrame(pdf)
    
    return df_spark

Testes Funcionais em PySpark: Financeiro

Lógica, anomização de dados sensíveis e tipagem em Spark.

Vamos testar um evento financeiro: a ingestão de milhares de transações de cartão de crédito. O pipeline deve classificar transações > $10.000 como suspeitas (Fraude) e tipar corretamente as colunas.

1. A Lógica de Transformação (src)

🐍 src/utils/transformations.py

import pyspark.sql.functions as F
from pyspark.sql.types import DoubleType, StringType

def apply_financial_rules(df):
    # Tipagem rigorosa
    df = df.withColumn("amount", F.col("amount").cast(DoubleType()))
    
    # Regra de Fraude
    df = df.withColumn(
        "is_suspicious", 
        F.when(F.col("amount") > 10000.0, True).otherwise(False)
    )
    
    # Anomização de dados sensíveis (LGPD)
    df = df.withColumn(
        "card_number", 
        F.concat(F.lit("****-****-****-"), F.substring(F.col("card_number"), -4, 4))
    )
    return df

2. O Teste Funcional (Pytest Extensivo)

Usamos o Pytest para passar DataFrames controlados para a função e fazemos assertions rígidas. Note como recebemos o spark via injeção de dependência do nosso conftest.py.

🐍 tests/integration/test_financial_clearing.py

import pytest
from src.utils.transformations import apply_financial_rules
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, BooleanType

def test_apply_financial_rules_types_and_logic(spark):
    # 1. Arrange: Cria DataFrame de Mock de Eventos Financeiros
    mock_data = [
        ("tx_01", "1234567812345678", "5000.0"),  # Normal
        ("tx_02", "8765432187654321", "15000.0"), # Suspeita
        ("tx_03", "1111222233334444", None)       # Edge case: Nulo
    ]
    columns = ["tx_id", "card_number", "amount"]
    df_input = spark.createDataFrame(mock_data, columns)
    
    # 2. Act: Aplica transformações
    df_result = apply_financial_rules(df_input)
    
    # 3. Assert: Coleta resultados para o driver node
    result_data = df_result.collect()
    
    # Teste de Anomização de Cartão (LGPD)
    assert result_data[0]["card_number"] == "****-****-****-5678"
    assert result_data[1]["card_number"] == "****-****-****-4321"
    
    # Teste de Regra de Fraude
    assert result_data[0]["is_suspicious"] is False
    assert result_data[1]["is_suspicious"] is True
    assert result_data[2]["is_suspicious"] is False # Nulos não dão erro matemático
    
    # Teste de Tipagem (Schema Enforcement)
    assert df_result.schema["amount"].dataType == DoubleType()
    assert df_result.schema["is_suspicious"].dataType == BooleanType()

Data Quality as Code

Integridade em tempo de execução com PyDeequ. [Ref: AWS Data Quality]

Além dos testes unitários, precisamos garantir a qualidade estatística dos dados no final do pipeline (Ex: Evitar que uma query SQL crie duplicatas em massa).

🐍 PyDeequ - Validação Estatística

from pydeequ.checks import *
from pydeequ.verification import *

# Regras de Negócio de uma tabela Dimensão de Clientes
check = Check(spark, CheckLevel.Error, "Integridade Clientes Financeiros")

checkResult = VerificationSuite(spark) \
    .onData(df_clientes) \
    .addCheck(
        check.isComplete("cpf") \
             .isUnique("cliente_id") \
             .isNonNegative("score_serasa") \
             .hasPattern("email", r'^\S+@\S+\.\S+$')
    ) \
    .run()

if checkResult.status == "Error":
    raise Exception("Qualidade de Dados violada. Pipeline abortado!")

Testes de Performance & Stress em Cloud

Validando a resiliência e os gargalos (bottlenecks) em sistemas massivos distribuídos.

Em engenharia de dados, um código que passa perfeitamente no teste unitário pode destruir o cluster de produção se tentar fazer um .collect() em 1 Terabyte de dados. Para mitigar isso, executamos Testes de Performance e Carga (Stress Tests) avaliando Latência (Tempo) e Throughput (Vazão).

Mensageria (Kafka/MSK, Kinesis, SQS)

Testamos filas estressando os produtores. Como testar: Escreva um script (ex: Locust, JMeter ou Python multi-threading) que gere milhares de payloads falsos por segundo.

Métricas vitais:
- Consumer Lag: A diferença entre o que é produzido e o que é consumido (se subir eternamente, o pipeline quebrou).
- Throughput Limits: Limites de IOPS (Provisioned vs On-Demand) ou limites de Shards do Kinesis (Write/Read ProvisionedThroughputExceededException).

Apache EMR (EC2 / YARN)

Clusters EMR são testados via submissão massiva de jobs pesados que forçam o *Shuffle*.

Métricas vitais:
- Spill to Disk: Quando a memória acaba e o Spark joga arquivos temporários no disco (lento demais). Ajuste: aumentar spark.executor.memory.
- Overhead da YARN: Se os executors morrem por OOM (Out Of Memory Error).
- Tempo de Boot: Medir o tempo que as Bootstrap Actions tomam ao escalar instâncias do EC2 via Auto-Scaling.

AWS Glue (Serverless ETL)

Sendo serverless, o Glue não requer gerência da YARN, mas exige o "Tuning Financeiro".

Métricas vitais:
- O Sweet Spot (Custo/Tempo): O teste consiste em rodar o job com 2 DPUs, 5 DPUs e 10 DPUs. Você perceberá que a partir de certo ponto (ex: 7 DPUs), colocar mais poder computacional não deixa o código mais rápido (limitado pelo I/O do S3 ou mal particionamento), gerando apenas desperdício de dinheiro.
- Cold Starts: Tempo que o Glue leva para preparar o cluster escondido antes de rodar seu código.

EMR Serverless

O EMR Serverless une o melhor do Glue com o ecossistema do EMR.

Métricas vitais:
- Pre-initialized Capacity vs Cold Start: O teste compara rodar o job num ambiente "frio" (esperando minutos para bootar) versus configurar Pre-initialized Capacity, onde a AWS mantém workers quentes. Testa-se a penalidade de custo de manter esses workers versus o ganho de tempo (Latência de Startup) do pipeline.

Automatizando Benchmarks (pytest-benchmark)

Na Engenharia de Dados, você pode medir o tempo exato de execução e alocação de memória usando o plugin pytest-benchmark acoplado aos seus testes. [Ref: Pytest Docs]

🐍 tests/performance/test_shuffle_benchmark.py

import pytest
from pyspark.sql import functions as F

def operacao_pesada_spark(df):
    """Simula um GroupBy massivo que causa Shuffle"""
    return df.groupBy("status")              .agg(F.sum("valor").alias("total"), F.count("tx_id").alias("qtd"))              .collect()

@pytest.mark.performance
def test_benchmark_aggregate_transactions(benchmark, fake_transactions_df):
    """
    Mede a performance (tempo, min, max, variância) da operação Spark.
    O pytest-benchmark irá rodar a função várias vezes (rounds) para calcular estatísticas.
    """
    
    # Executa a função monitorando a performance
    result = benchmark(operacao_pesada_spark, fake_transactions_df)
    
    # Garante que o pipeline rodou corretamente além de ser rápido
    assert len(result) == 3  # APPROVED, DENIED, PENDING

Referências & Boas Práticas da Indústria

As Golden Rules recomendadas para testar pipelines distribuídos na AWS e Databricks.

Baseado em pesquisas de arquiteturas modernas (Databricks, AWS e Apache Spark Communitites), consolidamos as melhores práticas para que seu ambiente de CI/CD (GitHub Actions, GitLab CI) rode seus testes Spark + Docker sem dor de cabeça:

1. Desative a Spark UI nos Testes

A Spark UI (porta 4040) gasta um tempo gigantesco subindo servidores Web no driver. Em um container Docker executando um pipeline de CI/CD, isso não só é inútil como penaliza a performance e causa falhas de port-binding. Adicione sempre: spark.ui.enabled = false e spark.ui.showConsoleProgress = false.

2. Portas Efêmeras (Evite Hardcode)

Quando usar Testcontainers, nunca defina manualmente as portas (ex: mapear Kafka na 9092 rígida). O Testcontainers seleciona portas host randômicas livres. Isso permite que seus testes rodem em modo paralelo de maneira segura usando ferramentas como pytest-xdist.

3. Separe Lógica Core de Infraestrutura

Mantenha a lógica de transformação de dados em funções puras (recebem DataFrame e retornam DataFrame) para testá-las rápido via Testes Unitários. O I/O com S3, Redshift ou Kafka deve ser isolado nos jobs orquestradores e validado através dos Testes de Integração com Docker.

4. Spark Connect vs Local Mode

Para testes rápidos em código, master("local[*]") é suficiente. No entanto, para projetos arquiteturalmente distribuídos, estude a arquitetura de Cliente-Servidor separada usando o novo Spark Connect.
