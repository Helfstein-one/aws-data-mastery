Software Testing (E2E) na Engenharia de Dados

Da Pirâmide de Testes Clássica à validação de grandes volumes de transações financeiras em Spark. Aprenda Pytest, Mocks, Conftest, Quality as Code e Orquestração.

01

A Pirâmide de Testes Adaptada para Dados

Em engenharia de software clássica, a Pirâmide de Testes dita que você deve ter muitos Testes Unitários (rápidos) na base, e poucos Testes E2E (lentos) no topo. Em engenharia de dados, esse conceito é adaptado porque dados possuem gravidade, volume e estado (Bancos, Storages).

A Pirâmide de Testes para Pipelines

End-to-End (E2E)

Lento & Caro (AWS Real)

Testcontainers

Testes de Integração

Lógicas isoladas (Mocks rápidos)

Moto Mocks

Unit Tests (Base)

Validação isolada de lógicas de negócio. Exemplo: Testar se a função `anonymize_cpf(df)` retorna os asteriscos corretos. Mockamos as conexões do AWS S3 e Spark. Ferramentas: pytest, moto.

Integration Tests (Meio)

Testar se os componentes se falam. Exemplo: O código Spark consegue gravar parquet no S3 Localstack? Usa contêineres efêmeros (Testcontainers) ou SparkSession local.

End-to-End (Topo)

Roda todo o pipeline desde a ingestão do dado na fila até a agregação no Data Warehouse. Demorado, caro, mas testa a confiabilidade total. Ferramentas: Airflow, AWS Step Functions.

02

Estrutura de Diretórios & Orquestração

Uma base de código escalável precisa isolar claramente os tipos de testes. Abaixo, a estrutura recomendada para projetos PySpark:

📁 Estrutura de Pastas (Data Pipeline)

project_root/
├── src/
│   ├── jobs/
│   │   └── financial_clearing.py  # Código Spark principal
│   └── utils/
│       └── transformations.py     # Lógicas de UDFs e Maps
├── tests/
│   ├── conftest.py                # Fixtures globais (SparkSession)
│   ├── unit/
│   │   └── test_transformations.py
│   ├── integration/
│   │   └── test_financial_clearing.py
│   └── e2e/
│       └── orchestrator_test.py
├── Makefile
└── requirements-dev.txt

Orquestrando os Testes E2E

Para orquestrar testes E2E, o padrão ouro é utilizar Testcontainers e CI/CD Runners. Em vez de testar na AWS (o que gera custos e instabilidade), subimos dependências via Docker em tempo de pipeline:

  • Setup: O pytest invoca um fixture que sobe um contêiner Kafka, um LocalStack (S3) e um PostgreSQL (Redshift mock).
  • Run: O teste insere dados no tópico Kafka.
  • Assert: O PySpark roda, consome o Kafka e salva no LocalStack. O teste lê o S3 e garante que a tabela de Fato foi preenchida com as métricas agregadas.
  • Teardown: Os contêineres são destruídos automaticamente.

03

Deep Dive: O Papel do conftest.py

O conftest.py é um arquivo mágico no pytest. Tudo que for declarado nele fica disponível para toda a suíte de testes daquela pasta, sem necessidade de import.

Na Engenharia de Dados, o uso mais crítico do conftest.py é criar uma SparkSession local com scope de sessão. O Spark demora alguns segundos para inicializar a JVM. Se cada teste instanciar uma sessão, a suíte demorará horas. Se criarmos uma com scope="session", ela é instanciada apenas uma vez para todos os testes.

🐍 tests/conftest.py

import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="session")
def spark():
    """
    Cria uma SparkSession em memória.
    O scope='session' garante que a JVM suba apenas 1 vez por run do Pytest.
    """
    spark = SparkSession.builder \
        .master("local[2]") \
        .appName("FinancialTests") \
        .config("spark.sql.shuffle.partitions", "2") \
        .config("spark.ui.enabled", "false") \
        .getOrCreate()
    
    yield spark  # Retorna a sessão para os testes
    
    spark.stop() # Teardown: Encerra a JVM no final

Testes Extensivos em PySpark: Setor Financeiro

Vamos testar um evento financeiro: a ingestão de milhares de transações de cartão de crédito. O pipeline deve classificar transações > $10.000 como suspeitas (Fraude) e tipar corretamente as colunas.

1. A Lógica de Transformação (src)

🐍 src/utils/transformations.py

import pyspark.sql.functions as F
from pyspark.sql.types import DoubleType, StringType

def apply_financial_rules(df):
    # Tipagem rigorosa
    df = df.withColumn("amount", F.col("amount").cast(DoubleType()))
    
    # Regra de Fraude
    df = df.withColumn(
        "is_suspicious", 
        F.when(F.col("amount") > 10000.0, True).otherwise(False)
    )
    
    # Anomização de dados sensíveis (LGPD)
    df = df.withColumn(
        "card_number", 
        F.concat(F.lit("****-****-****-"), F.substring(F.col("card_number"), -4, 4))
    )
    return df

2. O Teste Funcional (Pytest Extensivo)

Usamos o Pytest para passar DataFrames controlados para a função e fazemos assertions rígidas. Note como recebemos o spark via injeção de dependência do nosso conftest.py.

🐍 tests/integration/test_financial_clearing.py

import pytest
from src.utils.transformations import apply_financial_rules
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, BooleanType

def test_apply_financial_rules_types_and_logic(spark):
    # 1. Arrange: Cria DataFrame de Mock de Eventos Financeiros
    mock_data = [
        ("tx_01", "1234567812345678", "5000.0"),  # Normal
        ("tx_02", "8765432187654321", "15000.0"), # Suspeita
        ("tx_03", "1111222233334444", None)       # Edge case: Nulo
    ]
    columns = ["tx_id", "card_number", "amount"]
    df_input = spark.createDataFrame(mock_data, columns)
    
    # 2. Act: Aplica transformações
    df_result = apply_financial_rules(df_input)
    
    # 3. Assert: Coleta resultados para o driver node
    result_data = df_result.collect()
    
    # Teste de Anomização de Cartão (LGPD)
    assert result_data[0]["card_number"] == "****-****-****-5678"
    assert result_data[1]["card_number"] == "****-****-****-4321"
    
    # Teste de Regra de Fraude
    assert result_data[0]["is_suspicious"] is False
    assert result_data[1]["is_suspicious"] is True
    assert result_data[2]["is_suspicious"] is False # Nulos não dão erro matemático
    
    # Teste de Tipagem (Schema Enforcement)
    assert df_result.schema["amount"].dataType == DoubleType()
    assert df_result.schema["is_suspicious"].dataType == BooleanType()

Data Quality as Code (Deequ / Great Expectations)

Além dos testes unitários, precisamos garantir a qualidade estatística dos dados no final do pipeline (Ex: Evitar que uma query SQL crie duplicatas em massa).

🐍 PyDeequ - Validação Estatística

from pydeequ.checks import *
from pydeequ.verification import *

# Regras de Negócio de uma tabela Dimensão de Clientes
check = Check(spark, CheckLevel.Error, "Integridade Clientes Financeiros")

checkResult = VerificationSuite(spark) \
    .onData(df_clientes) \
    .addCheck(
        check.isComplete("cpf") \
             .isUnique("cliente_id") \
             .isNonNegative("score_serasa") \
             .hasPattern("email", r'^\S+@\S+\.\S+$')
    ) \
    .run()

if checkResult.status == "Error":
    raise Exception("Qualidade de Dados violada. Pipeline abortado!")
