O Problema de Small Files & Particionamento do S3

Técnicas de compactação de arquivos e regras de ouro de particionamento físico

Gravar arquivos muito pequenos (KB ou poucos MB) no S3 degrada severamente a performance das ferramentas analíticas. O Spark ou Athena gastam mais tempo executando chamadas REST de listagem (ListObjects) e lendo metadados das partições do que abrindo os dados propriamente ditos.

Regras de Ouro de Particionamento

  • Cardinalidade Média: Evite criar caminhos de partição baseados em campos com cardinalidade muito alta (ex: user_id ou transaction_id). Isso resulta em milhões de pastas no S3 com um arquivo de poucos bytes dentro.
  • Tamanho Ideal: Prefira manter o tamanho do arquivo no S3 entre 128 MB e 512 MB. Esse é o tamanho ótimo para divisão de leitura do bloco HDFS/Spark.
  • Cardinalidade Certa: Particione por campos lógicos de busca recorrente no WHERE, como data_ano, data_mes, ou categoria_macro.
Solução 1: Compaction Manual PySpark

Coalesce & Repartition

Agrupar e reescrever o dataset em partições balanceadas antes da persistência final.

Solução 2: Iceberg Optimize

Compactação Nativa (Transacional)

Comando DDL do Apache Iceberg para reescrever e compactar metadados sem interferir em leituras simultâneas.

Código PySpark: Script Batch para Compaction e Gravação

Abaixo está um script PySpark clássico executando a consolidação de milhares de pequenos arquivos em um conjunto enxuto de arquivos de tamanho controlado:

from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("S3CompactionJob").getOrCreate()

# 1. Ler milhares de pequenos arquivos fragmentados na Bronze
df_fragmentado = spark.read.parquet("s3://my-datalake-bronze/raw_data/ano=2026/mes=06/*")

# 2. Re-particionar baseando-se em volumetria e cardinalidade para atingir ~128MB por arquivo
# Usamos repartition() para balancear em partições menores na memória
df_compactado = df_fragmentado.repartition(4) 

# 3. Gravar na Silver de forma atômica
df_compactado.write \
    .mode("overwrite") \
    .parquet("s3://my-datalake-silver/consolidated_data/ano=2026/mes=06/")
Compactação Atômica no Apache Iceberg

No Lakehouse moderno, você pode compactar os arquivos de dados rodando um comando de otimização nativo no Athena:

OPTIMIZE analytics_db.historical_sales REWRITE DATA USING bin_pack;

Tuning de Performance: Casos Degradados & Soluções

Troubleshooting prático de gargalos de processamento, CPU, memória e IO na AWS

AWS Glue · Out Of Memory
Caso 1: Driver/Executor OOM (Spark Exception)
Sintoma: O Glue Job falha após rodar por alguns minutos com o log: java.lang.OutOfMemoryError: Java heap space.
Causa: Data Skew (desbalanceamento) gritante. Muitas chaves nulas ou vazias agrupadas sob a mesma chave de agregação/join concentram gigabytes in uma única partição Spark/JVM.
Solução: Salgar a chave de join para redistribuição (Salting), aumentar o número de partições ou reescalar workers padrão de G.1X (4 vCPU, 16GB RAM) para G.2X (8 vCPU, 32GB RAM) com maior poder de processamento.
AWS EMR · Garbage Collection
Caso 2: Spark FetchFailed e GC Overhead
Sintoma: EMR Job lento com constantes falhas de FetchFailedException: Failed to connect to host no estágio de shuffle.
Causa: Pause longo por JVM Garbage Collection (GC) devido ao uso excessivo de objetos temporários na memória dos executors, fazendo a máquina perder comunicação com o coordenador YARN.
Solução: Mudar o coletor de lixo para G1GC e definir o executor memory overhead correto:
--conf spark.executor.extraJavaOptions="-XX:+UseG1GC"
--conf spark.yarn.executor.memoryOverhead=4096
Amazon Athena · Custo & Tempo
Caso 3: Varredura de Terabytes desnecessária
Sintoma: Queries simples demoram minutos e escaneiam terabytes de dados no S3, gerando altos custos analíticos.
Causa: Layout de arquivos ruim (dados em JSON ou arquivos sem particionamento explícito) e falta do uso do Partition Projection no Glue Catalog.
Solução: Converter dados para Parquet comprimido com Snappy/ZSTD e ativar o Partition Projection para ler apenas os blocos de dados específicos solicitados na cláusula WHERE da query Athena.
RDS & Aurora · Gargalo OLTP
Caso 4: Picos de CPU (100%) e Timeout
Sintoma: O banco de dados congela no meio do dia, estourando conexões com erro Too many connections.
Causa: Falta de índices adequados para queries analíticas e estouro de concorrência por falta de um pooler de conexões centralizado.
Solução: Criar índices B-Tree específicos nas chaves de busca mais comuns, criar Aurora Read Replicas para direcionar queries de leitura (BI/ETL) e implementar o Amazon RDS Proxy para reaproveitar conexões ativas.
DICA DE ANÁLISE: Query Plan Tuning no PostgreSQL (Aurora/RDS)

Use o comando EXPLAIN ANALYZE para auditar queries lentas. Abaixo, identificamos um scan sequencial lento (Seq Scan) que é resolvido imediatamente criando um índice:

-- 1. Query lenta original (executando Seq Scan em tabela gigante)
EXPLAIN ANALYZE SELECT * FROM transacoes WHERE status = 'PROCESSADO' AND data_criacao >= '2026-06-01';
-- Output de exemplo: -> Seq Scan on transacoes (cost=0.00..85421.23 rows=42152 width=142) (actual time=0.015..942.302 loops=1)

-- 2. Correção: Criar um índice composto para os campos do filtro
CREATE INDEX idx_transacoes_status_data ON transacoes (status, data_criacao);

-- 3. Nova validação do plano (verificando Index Scan de milissegundos)
EXPLAIN ANALYZE SELECT * FROM transacoes WHERE status = 'PROCESSADO' AND data_criacao >= '2026-06-01';
-- Output: -> Index Scan using idx_transacoes_status_data on transacoes (cost=0.42..342.12 rows=42152 width=142) (actual time=0.021..14.120 loops=1)

Crise 1: Gargalo e OOM em Streaming (Black Friday)

Resolução de backpressure severo em computação distribuída e controle financeiro de escala sob pico abrupto

A Crise Operacional
Durante o maior pico de tráfego da Black Friday, a esteira de eventos no Amazon MSK registrou alta de 15x. Os jobs Spark em EMR Serverless sofreram estouro de memória (JVM OOM) devido à leitura massiva e sem controle de buffers, gerando um lag de processamento de 12 minutos. A equipe de negócios ficou sem visibilidade de vendas, travando o algoritmo dinâmico de precificação de ofertas.
Impacto Estratégico & FinOps
  • Antes: Lag analítico de 12 minutos. Fatura de instâncias AWS do EMR escalando para $45.000 por dia em auto-scaling de nós ineficientes.
  • Depois: Latência reduzida para 1.8 segundos. Custo operacional reduzido para $8.000 por dia (82% de economia).
  • Valor: Blindagem imediata do volume de faturamento da empresa ao reativar as ofertas dinâmicas de preços.
CRISE: JVM OOM E BACKPRESSURE NO SPARK STREAMING

A Resolução Técnica

  1. Configuração de Rate Limiting: Injeção da diretiva spark.streaming.kafka.maxRatePerPartition no Spark para limitar o número de mensagens por partição em cada micro-batch, estabilizando o uso de memória Heap dos Workers.
  2. Orquestração Spot com Karpenter: Substituição dos nós estáticos por um mix dinâmico de instâncias Spot baseadas em arquitetura Graviton da AWS (r6g/m6g), garantindo performance por um terço do custo.

Com isso, os dashboards de vendas do time de negócios voltaram a refletir o status real dos clientes com latência de apenas 1.8 segundos, garantindo a continuidade das nossas ofertas dinâmicas."

Crise 7: Atraso de SLA por Desalinhamento em Tabelas Mesh (Cross-Account)

Automação e governança cross-account para sanar quebras de catálogo de metadados no Data Mesh

A Crise Operacional
Na topologia Data Mesh da empresa, a Conta AWS Produtora atualizou a partição da tabela de vendas e efetuou deploy de modificações físicas de colunas de metadados. Como a atualização do catálogo cross-account com a Conta Consumidora era feita via scripts manuais desatualizados, a Conta Consumidora analítica ficou bloqueada de ler os dados por 6 horas. O atraso violou o SLA de entrega de dados diários exigidos pela presidência.

  • Depois: Tempo de sincronização e liberação do metadado reduzido de 6 horas para 2 minutos.

Crise 8: Schema Drift Silencioso e Queda de SLA

Liderança Especialista e a reconstrução da confiança após uma mudança estrutural não comunicada

1. O Cenário Técnico e o Conflito

Incidente Técnico: O pipeline analítico core (responsável por alimentar os dashboards de faturamento) falhou durante a madrugada. A causa raiz foi um "Schema Drift": a equipe de engenharia de software do microsserviço de vendas origem alterou o tipo de dado da coluna de amount (de INT para STRING formatado) e removeu o campo transaction_date, substituindo-o por created_at. O pipeline Spark (Lakehouse) quebrou no momento do cast de leitura e o SLA crítico de entrega das 08h00 foi rompido.

Conflito Humano: O time de análise de negócios está furioso devido aos relatórios em branco. Dentro da engenharia, instalou-se o "finger-pointing" (jogo da culpa). A squad de dados acusa a squad de origem de amadorismo por quebrar a retrocompatibilidade. A squad de origem defende que a mudança era vital para uma nova funcionalidade do front-end e que não pode ser freada por "relatórios legados". Os desenvolvedores estão desmotivados e o clima é de tensão bélica.

2. A Ação do Especialista (Resolução Comportamental)
  • Liderança
    Desarmando a trincheira: O Especialista I assume o controle do war room. Em vez de alimentar a culpa, ele blinda o time de dados da pressão de negócios e chama o Tech Lead da origem para uma call 1:1. Ele alinha que o objetivo não é punir a mudança, mas reestabelecer o serviço. O especialista promove a visão de "um único time corporativo", reduzindo a postura defensiva e engajando ambas as squads na mitigação.
  • Solução de Problemas
    Visão 360 e Ação Rápida: Ele orienta a criação imediata de uma branch de hotfix. A solução tática é injetar uma camada de compatibilidade temporária (um parsing condicional no Spark) que lê o schema novo e o mapeia para o formato antigo, salvando o fechamento do dia.
  • Orientação a Resultados
    Conciliando Prazos: Com o dashboard no ar, ele prioriza a estabilidade. Negocia com a gerência a alocação de 3 dias do sprint atual para construir testes de validação de schema estritos no pipeline de ingestão.
Equipe Técnica
Causa Raiz & Troubleshooting
"Tivemos um schema evolution que quebrou nosso DAG por incompatibilidade de tipos no campo de amount. Vamos implementar um hotfix usando um cast defensivo no Spark e aplicar a função coalesce() para tratar a data. A longo prazo, implementaremos o Great Expectations na ingestão."
Equipe de Negócio
Operação diária & SLA
"Nossos relatórios matinais atrasaram devido a uma mudança não mapeada no formato como as vendas chegam até nós. Já estabilizamos a leitura e os painéis estarão 100% atualizados até às 11h. Pedimos desculpas pelo impacto na operação."
C-Level Negócio (CEO/CFO)
Receita, Risco & Impacto Macro
"O atraso de hoje expôs uma fragilidade de acoplamento entre os sistemas transacionais e nosso Lake. Fizemos a contenção, mas para proteger o OKR de confiabilidade, realocarei parte da capacidade desta sprint para criar barreiras automáticas de bloqueio contra dados mal formatados."
C-Level Tecnologia (CIO/CTO)
TCO, Dívida Técnica & Arquitetura
"O incidente operacional de hoje demonstra o risco de operarmos em silos. O custo de recuperação manual é alto (OPEX) e afeta a tomada de decisão. A estratégia mitigadora definitiva será a governança via Contratos de Dados (Data Contracts) exigida antes de qualquer release."
4. Lições Aprendidas (Hardening & Prevenção)

O Especialista I transforma a crise em oportunidade arquitetural estabelecendo Contratos de Dados (Data Contracts) corporativos. Fica documentado (produção de documentação interna) que a squad de origem assinará um schema estrito no registro (Schema Registry). Qualquer quebra de compatibilidade falhará a esteira de CI/CD do microsserviço (Shift-Left), impedindo que o erro de tipagem alcance o ambiente analítico. A comunicação flui de reativa para preventiva.

Crise 12: Esgotamento de Conexões e Hot Partitions no DynamoDB

Queda abrupta de performance em ingestão serverless e throttling de gravação (ProvisionedThroughputExceeded).

A Crise Operacional

Durante o lançamento de uma nova feature no App, milhares de dispositivos enviaram telemetria simultaneamente. As funções Lambda escalaram massivamente, exaurindo o pool de conexões do RDS e, no fallback para DynamoDB, concentraram gravações em uma única Partition Key (ID da campanha), causando Hot Partitions. O App começou a devolver erro 500 para os usuários finais.

1. Triage & Contenção

Ação imediata: Ativar On-Demand Capacity no DynamoDB temporariamente para absorver o pico elástico sem teto rígido de WCU. Implementar circuit breaker no API Gateway com Rate Limiting agressivo para conter a tempestade de requisições e proteger o backend de falha total.

2. Mitigação Permanente

Implementar SQS na frente das Lambdas (Queue-Based Load Leveling) para suavizar a curva de gravação. Refatorar a Partition Key do DynamoDB adicionando um Suffix aleatório (Write Sharding: campanha_id + rand(1,50)) para distribuir as gravações uniformemente por dezenas de partições físicas sob o capô da AWS.

Crise 14: Fila SQS Envenenada (Poison Pill)

Evento mal formatado causando retentativas infinitas e travando o lag de processamento de um sistema inteiro.

A Crise Operacional

Um parceiro alterou o payload JSON do webhook. A Lambda que consome do SQS falha ao dar `json.loads()` em um campo específico e joga exceção. Como a mensagem não é deletada do SQS (ausência de ACK), a fila retenta a mesma mensagem infinitamente. O Lag (ApproximateNumberOfMessagesVisible) salta de zero para 500k em 2 horas, paralisando o processamento em tempo real de fraude.

1. Triage & Contenção

Remover a integração (trigger) da Lambda temporariamente para parar os logs excessivos no CloudWatch e o custo de invocação inútil. Configurar um script de emergência (Boto3) para capturar o payload problemático, identificar o padrão anômalo e dar purge na fila apenas desses pacotes específicos.

2. Mitigação Permanente

Implementar a dobradinha essencial: Dead-Letter Queue (DLQ) no SQS. Configurar o maxReceiveCount = 3. Se a mensagem falhar 3 vezes, a própria AWS a move para a DLQ, destravando o pipeline para mensagens saudáveis. Além disso, usar o AWS Glue Schema Registry ou Pydantic na borda para validar contratos de dados (Data Contracts) antes mesmo de enfileirar no backend.
