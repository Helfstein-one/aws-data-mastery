DataOps: Ciclos de Automação, Linhagem e Testabilidade

Garantindo resiliência, monitoramento de schemas e automação em pipelines de dados corporativos

DataOps é uma metodologia ágil voltada para o desenvolvimento e operacionalização de pipelines de dados. Na AWS, envolve a aplicação de práticas de engenharia de software (como CI/CD, testes unitários de dados e IaC) para mitigar quebras e garantir alta qualidade contínua.

Governança
Data Contracts (Contratos)
Definição formal e declarativa do schema e regras de negócios esperados na origem de dados analíticos. Impede que alterações não retrocompatíveis quebrem os pipelines analíticos a jusante (Schema Drift).
Qualidade
Testes Automatizados
Uso de bibliotecas de validação ativa (ex: Soda Core ou Great Expectations) rodando integradas a orquestradores para abortar execuções de dados inválidos antes que poluam a camada Silver/Gold.
Rastreabilidade
Data Lineage (Linhagem)
Mapeamento dinâmico do caminho percorrido pelos dados, do local de origem aos relatórios (ex: via padrões abertos como OpenLineage), simplificando a depuração e auditorias regulatórias.

Implementação de Data Contracts via JSON Schema em PySpark

Para garantir que o payload de entrada de uma fila (Kinesis/MSK) ou pasta S3 obedece estritamente ao contrato de dados acordado:

import jsonschema
from pyspark.sql.functions import udf
from pyspark.sql.types import BooleanType

# 1. Definição do Contrato de Dados Declarativo (Esquema e Regras)
DATA_CONTRACT = {
    "$schema": "http://json-schema.org/draft-07/schema#",
    "title": "ContratoClienteCadastrado",
    "type": "object",
    "properties": {
        "id_cliente": {"type": "integer"},
        "email": {"type": "string", "format": "email"},
        "idade": {"type": "integer", "minimum": 18},
        "data_cadastro": {"type": "string", "pattern": "^\\d{4}-\\d{2}-\\d{2}$"}
    },
    "required": ["id_cliente", "email", "idade"]
}

# 2. UDF Spark para validar cada linha contra o contrato
def validate_contract(row_json_str):
    try:
        data = json.loads(row_json_str)
        jsonschema.validate(instance=data, schema=DATA_CONTRACT)
        return True
    except Exception:
        return False

validate_contract_udf = udf(validate_contract, BooleanType())

# 3. Aplicação do contrato no DataFrame Spark e separação da Quarentena
df_raw = spark.read.text("s3://my-datalake/bronze/input/")
df_validated = df_raw.withColumn("valido", validate_contract_udf(df_raw["value"]))

df_clean = df_validated.filter(df_validated["valido"] == True)
df_quarantine = df_validated.filter(df_validated["valido"] == False)

# Salva registros saudáveis na Silver e envia rejeitados para correção
df_clean.write.format("iceberg").save("prod.silver.clientes")
df_quarantine.write.parquet("s3://my-datalake/quarantine/clientes/")

Infraestrutura como Código (IaC) com Terraform para Data Lake AWS

Provisionamento idempotente de uma tabela de banco de dados com auditoria via Lake Formation e S3 usando Terraform:

# 1. Definição do S3 Bucket para a camada Silver
resource "aws_s3_bucket" "silver_layer" {
  bucket = "prod-lakehouse-silver-layer"
}

# 2. Definição do Database no AWS Glue Data Catalog
resource "aws_glue_catalog_database" "silver_db" {
  name = "silver_lakehouse"
}

# 3. Cadastro do local do S3 no Lake Formation para Credential Vending
resource "aws_lakeformation_resource" "s3_silver_registration" {
  arn = aws_s3_bucket.silver_layer.arn
}

# 4. Concessão de acesso com granularidade de colunas ao Engenheiro de Dados
resource "aws_lakeformation_permissions" "developer_grant" {
  principal   = "arn:aws:iam::123456789012:role/DataEngineerRole"
  permissions = ["SELECT"]

  table_with_columns {
    database_name = aws_glue_catalog_database.silver_db.name
    name          = "clientes"
    column_names  = ["id_cliente", "email", "idade"] # cpf omitido para privacidade
  }
}

MLOps: Ciclo de Vida do Modelo, Feature Store e Monitoramento

Orquestrando treinamento e monitoramento de modelos em produção sob a governança da AWS

MLOps estende as práticas de DevOps e DataOps para incorporar inteligência artificial e modelos preditivos em sistemas de produção de alta confiabilidade. Na AWS, o ecossistema centraliza-se em torno do **Amazon SageMaker**.

MLOps · Componente 1

SageMaker Feature Store

Repositório centralizado de variáveis analíticas. A Online Store (servida via DynamoDB de baixíssima latência) provê features em milissegundos para inferência em tempo real. A Offline Store (salva no S3 como Parquet/Iceberg) alimenta pipelines de treinamento em lote.

MLOps · Componente 2

SageMaker Model Registry

Cataloga e versiona modelos treinados. Permite gerenciar ciclos de aprovação manual ou automática baseados no cumprimento de limites de assertividade em ambientes de teste antes do deploy em produção.

MLOps · Componente 3

Model Monitor (Drift)

Varre continuamente as requisições que chegam ao Endpoint. Compara a distribuição física dos dados preditos (inferidos) contra a de treino, identificando desvios conceituais (Concept Drift) e populacionais (Data Drift) com alertas.

Implementação de SageMaker Pipelines com Python SDK

Código para definir de forma programática um pipeline de treinamento de modelos estruturado:

import sagemaker
from sagemaker.workflow.parameters import ParameterString
from sagemaker.workflow.steps import TrainingStep
from sagemaker.workflow.pipeline import Pipeline

session = sagemaker.Session()
role = sagemaker.get_execution_role()

# 1. Parâmetros de Entrada de Execução dinâmicos
input_data = ParameterString(
    name="InputDataUrl",
    default_value="s3://my-datalake/silver/features/dataset.parquet"
)

# 2. Definição do Estimador de Treinamento (XGBoost container)
image_uri = sagemaker.image_uris.retrieve("xgboost", session.boto_region_name, "1.5-1")
estimator = sagemaker.estimator.Estimator(
    image_uri=image_uri,
    role=role,
    instance_count=1,
    instance_type="ml.m5.xlarge",
    output_path="s3://my-datalake/models/artifacts/",
    sagemaker_session=session
)

# 3. Definição do Step de Treino
step_train = TrainingStep(
    name="TreinamentoXGBoost",
    estimator=estimator,
    inputs={
        "train": sagemaker.inputs.TrainingInput(
            s3_data=input_data,
            content_type="application/x-parquet"
        )
    }
)

# 4. Criação do Pipeline do SageMaker
pipeline = Pipeline(
    name="PipelineCreditoClientes",
    parameters=[input_data],
    steps=[step_train],
    sagemaker_session=session
)

# Grava e valida a estrutura lógica no SageMaker Hub
pipeline.upsert(role_arn=role)
# Executa o pipeline
execution = pipeline.start()

Estratégias de Deploy Avançadas para Modelos de ML na AWS

Estratégia Vazão de Rede / Roteamento Prós / Vantagens Contras / Desvantagens
Shadow Deployment 100% no modelo ativo. Produção copia requisições e envia para o novo modelo de forma assíncrona descartando respostas. Segurança extrema. Valida performance computacional do novo modelo sem impactar a resposta do usuário. Dobro do custo de infraestrutura ativo, pois requer duas instâncias de endpoints completas.
Canary Releases Percentual incremental (ex: 5% a 95%) migrando tráfego real baseado em tempos programados ou métricas de erro. Mitiga impacto em caso de bug no modelo, permitindo Rollback ágil no CloudWatch. Complexidade de orquestração no API Gateway/Application Load Balancer.
Testes A/B Divisão estática por tráfego ou identificação de grupos de usuários (ex: 50/50). Permite medir diretamente impacto no negócio (melhoria em vendas, cliques ou conversão). Duração longa, exigindo análises estatísticas para comprovação de hipóteses (p-value).

Git & CI/CD

Git Flow & Versionamento para Dados

Estratégias de versionamento, Git Actions, rollback e boas práticas aplicadas a pipelines de engenharia de dados (DataOps).

O que é o Git Flow em Dados?

No contexto de Engenharia de Dados, versionamento vai muito além do código-fonte (Python/Scala). Um Git Flow maduro envolve versionar infraestrutura (IaC), códigos de orquestração (Airflow), definições de schema e pipelines de transformação (dbt) de forma integrada e segura para não corromper o Data Lake.

Comandos Essenciais do Git
  • git init / clone: Inicializar ou baixar repositório.
  • git checkout -b <branch>: Criar e mudar para nova branch.
  • git add . / commit -m: Adicionar e persistir mudanças localmente.
  • git rebase origin/main: Atualizar sua branch com as últimas mudanças da main (evita merge commits sujos).
  • git push origin <branch>: Enviar código para o repositório remoto.
  • git stash: Salvar mudanças locais temporariamente sem commitar.
Estratégias de Rollback Seguras
  • git revert <commit_hash>: Recomendado. Cria um novo commit desfazendo as alterações do commit defeituoso. Mantém o histórico limpo e auditável.
  • git reset --hard <commit_hash>: Perigoso. Apaga o histórico local até o commit especificado. Nunca use na branch main de produção!
  • Rollback em Dados (Lógica + Estado): Reverter o código do Git é apenas 50%. Você também precisa reverter os dados afetados (Ex: usar Time Travel no Apache Iceberg: CALL system.rollback_to_timestamp(...)).

GitHub Actions (CI/CD) em DataOps

O CI/CD automatiza os testes e deploys para garantir que um PR ruim não quebre a produção.

.github/workflows/deploy_pipeline.yml
name: Data Pipeline CI/CD

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

jobs:
  test_and_lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.9'
      - name: Install dependencies
        run: pip install pytest flake8 black
      - name: Run Black & Flake8 (Linting)
        run: |
          black --check src/
          flake8 src/
      - name: Run Unit Tests (Pytest)
        run: pytest tests/

  deploy_to_aws:
    needs: test_and_lint
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v2
        with:
          role-to-assume: arn:aws:iam::123456789012:role/DeployRole
          aws-region: us-east-1
      - name: Sync scripts to S3
        run: aws s3 sync src/ s3://meu-lake-artifacts/scripts/
Perguntas e Cases: Entrevistas sobre Git em Dados

P1: "Você mergeou um PR que quebrou a lógica de cálculo de receita no Spark em Produção. Como você atua?"
Resposta Esperada: "Primeiro, abro um PR com git revert do commit defeituoso para restaurar o código funcional o mais rápido possível e dou deploy. Depois, atuo no lado dos dados: utilizo os recursos de Time Travel do formato (Iceberg/Delta) para restaurar a tabela da camada Gold para o estado anterior à execução do job defeituoso. Em seguida, investigo a causa raiz localmente."

P2: "Por que não podemos versionar grandes arquivos .csv ou .parquet no Git?"
Resposta Esperada: "O Git foi feito para versionamento de arquivos de texto (código fonte), e rastrear diffs em binários pesados incha o repositório, deixando-o lento (Git Bloat). Para versionar dados (Machine Learning ou Data Lakes), devemos usar ferramentas específicas como DVC (Data Version Control) ou o versionamento em nível de formato de tabela (Apache Iceberg Snapshots)."
