Cálculo Exaustivo de Alocação de Memória e Cores

Fórmulas práticas e dimensionamento matemático para servidores r5.4xlarge e c5.9xlarge

Dimensionar incorretamente as configurações de submissão do Spark gera instabilidade ou desperdício severo de custos de infraestrutura analítica no EMR. Abaixo estão descritas as contas detalhadas para duas famílias de instâncias EC2 de hardware distintos:

Cenário 1: Instância Memory-Optimized (r5.4xlarge)

  • Hardware Físico: 16 vCPUs (cores) e 128 GB RAM.
  • Reserva do S.O. & YARN: 1 core e 4 GB RAM. Sobram 15 cores e 124 GB RAM.
  • Cores por Executor: Fixado em 5 cores (limite ótimo de vazão I/O).
  • Quantidade de Executores por nó: 15 / 5 = 3 executores por nó.
  • Memória total disponível por executor: 124 GB / 3 = 41.3 GB.
  • Ajuste do Overhead (10%):
    • spark.executor.memory = 37g
    • spark.executor.memoryOverhead = 4g (37g * 0.10 ≈ 3.7g -> arredondado para 4g).

Cenário 2: Instância Compute-Optimized (c5.9xlarge)

  • Hardware Físico: 36 vCPUs (cores) e 72 GB RAM.
  • Reserva do S.O. & YARN: 1 core e 4 GB RAM. Sobram 35 cores e 68 GB RAM.
  • Cores por Executor: Fixado em 5 cores.
  • Quantidade de Executores por nó: 35 / 5 = 7 executores por nó.
  • Memória total disponível por executor: 68 GB / 7 = 9.7 GB.
  • Ajuste do Overhead (10%):
    • spark.executor.memory = 8g
    • spark.executor.memoryOverhead = 1g (excedente necessário para operações de runtime).

Alocação Estática vs Alocação Dinâmica (Dynamic Allocation)

Em ambientes de produção na AWS, a escolha entre alocação de recursos estática ou dinâmica afeta diretamente o custo e a resiliência dos jobs Spark:

  • Alocação Estática: Define um número fixo de executores que permanecem ativos e reservados durante todo o ciclo de vida da aplicação (ex: spark.executor.instances = 20).
    Uso recomendado: Jobs críticos de ETL em lote recorrentes onde o volume de dados é previsível e o job necessita de recursos estáveis constantes do início ao fim para bater o SLA.
  • Alocação Dinâmica (Dynamic Allocation): Permite que o Spark aloque executores sob demanda de acordo com a carga de trabalho de cada Task na fila (Stage/Job), devolvendo executores ociosos ao cluster (YARN/K8s/EMR).
    Configuração Recomendada no EMR: 
    spark.dynamicAllocation.enabled = true
spark.dynamicAllocation.minExecutors = 1
spark.dynamicAllocation.maxExecutors = 100
spark.dynamicAllocation.executorIdleTimeout = 60s
spark.dynamicAllocation.schedulerBacklogTimeout = 1s

    Parâmetros de Tuning:
    • schedulerBacklogTimeout: Tempo que o Spark aguarda (padrão 1s) com tarefas pendentes na fila antes de solicitar novos executores.
    • executorIdleTimeout: Tempo de inatividade do executor (padrão 60s) antes que ele seja desligado e devolvido ao pool.
    • External Shuffle Service & Shuffle Tracking: Para ativar a alocação dinâmica com segurança sem perder resultados intermediários de shuffle de executores desalocados, configure spark.shuffle.service.enabled = true. No Spark 3.x+ rodando em Kubernetes, utilize a opção moderna de **Shuffle Tracking** (spark.dynamicAllocation.shuffleTracking.enabled = true) para reter os dados de shuffle ativamente sem depender do External Shuffle Service.

Garbage Collection & Heap Tuning

Otimização de pausas Stop-The-World e JVM Tuning avançado

Configurações para Garbage Collector G1

O G1GC divide a memória Heap da JVM em pequenas regiões e analisa qual região possui maior volume de dados inúteis para liberar primeiro, evitando a suspensão de threads executores.

spark.executor.extraJavaOptions =
  -XX:+UseG1GC
  -XX:InitiatingHeapOccupancyPercent=35
  -XX:G1HeapRegionSize=16m
  -verbose:gc -XX:+PrintGCDetails

Identificação de gargalos de GC no Spark UI

Analise a coluna GC Time no Executors Tab: Se o tempo de GC superar 10% do tempo de processamento total, você deve aumentar a memória dos executores ou reduzir o paralelismo local diminuindo cores.

Shuffle, Skew e Salting

Resolução de gargalos causados por desbalanceamento em joins e shuffles

O Data Skew (desvio de dados) ocorre quando uma chave específica acumula mais de 80% do volume físico dos dados (ex: chaves nulas ou registros de auditoria padrão). O executor encarregado por processar essa chave demorará muito mais tempo que os demais, deixando os cores ociosos e estendendo a duração do estágio.

Otimização via Salting (Distribuição de Chave no Join)

import pyspark.sql.functions as F
n_salts = 30

# Tabela principal: adiciona salt aleatório
df_large_salted = df_large.withColumn(
    "salt", (F.rand() * n_salts).cast("int")
).withColumn("salted_key", F.concat(F.col("key"), F.lit("_"), F.col("salt")))

# Tabela de lookup: explode criando todas as combinações de salts
df_small_exploded = df_small.withColumn(
    "salt", F.explode(F.array([F.lit(i) for i in range(n_salts)]))
).withColumn("salted_key", F.concat(F.col("key"), F.lit("_"), F.col("salt")))

df_joined = df_large_salted.join(df_small_exploded, "salted_key").drop("salt", "salted_key")

Estratégias de Join no Spark

Mapeamento de cruzamentos analíticos em nível de rede e disco

Broadcast Hash Join
✓ Sem Shuffle
Copia e envia a tabela pequena inteira para todos os executores na memória. Elimina totalmente a movimentação de rede. Indicado para tabelas de dimensões pequenas.
Sort-Merge Join
Shuffle
Ordena dados de ambas as tabelas após redistribuir partições pela chave. Extremamente robusto e seguro para conjuntos massivos que excedem a RAM do executor.
Shuffle Hash Join
Shuffle
Distribui as chaves em hash maps locais. Consome muita RAM no executor para manter o mapeamento ativo durante a fase de busca.

Erros Comuns no Apache Spark

Troubleshooting e erros clássicos de JVM

Out of Memory (OOM)
Java heap space / GC overhead limit exceeded
Causa: Driver ou executores esgotaram a RAM devido a partições excessivamente volumosas (>2 GB) ou chamadas brutas de `.collect()`.

Fix: Aumente o número de partições no shuffle ou aloque mais memória física no Spark Submit.
Dynamic Allocation
ExecutorLostFailure (heartbeat timeout)
Causa: Executor ocupado demais com Garbage Collection pesado, paralisando threads e perdendo comunicação com o Driver.

Fix: Ajuste as opções do GC para utilizar o G1GC e aumente o timeout de conexões.

AWS Glue: ETL Serverless e Dynamic Frames

Processamento orientado a eventos e integração nativa com o Data Catalog

Abstração
Dynamic Frames
Extensão dos DataFrames do Spark que permite lidar com schemas semi-estruturados e inconsistentes sem necessidade de definir DDLs rígidos previamente.
Estado
Job Bookmarks
Persiste o estado do processamento para evitar reprocessamento de dados já ingeridos em execuções anteriores no S3 ou JDBC.
Governança
Glue Data Quality
Implementa regras automáticas de qualidade (DQDL) para validar a integridade dos dados durante o pipeline de ETL.

Como Funciona

O Glue utiliza um ambiente Spark totalmente gerenciado. Ele abstrai a gestão de clusters, permitindo focar no código Python/Scala. O Data Catalog atua como um Metastore centralizado para o Lakehouse.

  • Interactive Sessions: Permite desenvolvimento rápido via Jupyter Notebooks sem esperar minutos pelo provisionamento de clusters.
  • Glue Flex: Classe de execução de baixo custo (até 35% de economia) para jobs não críticos, utilizando capacidade excedente da AWS (similar ao Spot).

Performance & Configurações

  • Worker Auto Scaling: Disponível no Glue 3.0+, escala dinamicamente o número de workers conforme a carga do job, reduzindo custos em shuffles ou processamentos variáveis.
  • Tipos de Workers:
    • G.1X: 4 vCPUs, 16 GB RAM, 64 GB Disk. (1 DPU)
    • G.2X: 8 vCPUs, 32 GB RAM, 128 GB Disk. (2 DPUs)
    • G.4X/G.8X: Para jobs de altíssima escala e memória intensiva.

Amazon EMR on EC2: Clusters Customizados

Máximo controle sobre a infraestrutura e tuning de performance

Como Funciona & Arquitetura

O EMR on EC2 permite rodar o ecossistema Hadoop completo. A separação física dos nós permite otimização de custos e performance:

  • Master Node: Orquestra o cluster. Para alta disponibilidade, use 3 Masters.
  • Core Nodes: Processamento e Armazenamento (HDFS). Essenciais para jobs que dependem de escrita local persistente.
  • Task Nodes: Computação pura. Use 100% Spot Instances aqui para FinOps agressivo.
  • Managed Scaling: Redimensiona o cluster automaticamente em segundos com base em métricas do YARN, muito mais eficiente que o Auto Scaling tradicional do EC2.

Performance & Configurações

  • Instance Fleets: Permite misturar até 30 tipos de instâncias EC2, garantindo que o cluster suba mesmo com baixa disponibilidade de certos tipos de Spot.
  • EMR Runtime: Ativado por padrão nas versões 6.x+, traz otimizações de query e melhor integração com S3 (EMRFS).
  • Configuração via JSON: Permite tunar o `spark-defaults`, `yarn-site` e `capacity-scheduler` diretamente no provisionamento.
  • Graceful Decommissioning: Vital para clusters que utilizam Spot nos Task Nodes. O YARN gerencia o desligamento da instância transferindo dados locais de shuffle antes do nó ser removido, mitigando erros de FetchFailedException.
  • Ajuste de YARN Queues: Utilizando o CapacityScheduler, você pode criar filas lógicas que particionam os recursos do cluster EC2 entre múltiplos pipelines concorrentes.

Amazon EMR Serverless: Agilidade e Escala

Operação sem gerenciamento de servidores com performance de EMR

Como Funciona

O EMR Serverless desacopla o gerenciamento de instâncias da execução do job. Você cria uma "Application" (Spark ou Hive) e submete "Job Runs".

  • Pre-initialized Capacity: Mantém um pool de workers "quentes" prontos para processar. Elimina o tempo de boot de 5-10 min do EC2, iniciando o processamento em segundos.
  • Isolamento: Cada Job Run roda em um ambiente isolado, evitando conflitos de bibliotecas ou competição de recursos entre diferentes pipelines.

Performance & Configurações

  • Configuração de Workers: Diferente do Glue, você tem controle granular sobre os recursos de cada worker (ex: 2 vCPU e 16 GB RAM) até limites de 16 vCPU / 120 GB por worker.
  • Customização de Disco: É possível configurar o armazenamento efêmero por worker (de 20GB a 200GB), crucial para shuffles pesados.
  • FinOps: Você paga apenas pelo que consome (vCPU, RAM, Storage por segundo), ideal para workloads esporádicos ou com picos imprevisíveis.
  • Custom Docker Images: Você pode empacotar bibliotecas Python/C++ complexas no Amazon ECR em uma imagem base customizada, acelerando a inicialização e garantindo isolamento total (multi-tenant).
  • VPC e Redes Privadas: EMR Serverless provisiona ENIs diretamente nas suas sub-redes VPC, garantindo conectividade privada e segura a bancos como RDS e Redshift.
15.5

Amazon EMR on EKS: Processamento Multi-Tenant

Orquestração de jobs Spark como contêineres nativos no Kubernetes com alta densidade

Como Funciona

O EMR on EKS permite executar aplicativos Apache Spark diretamente em clusters do Amazon Elastic Kubernetes Service (EKS). Diferente do YARN tradicional, o EKS agenda pods (Driver e Executors) no cluster K8s, permitindo rodar workloads analíticos ao lado de microsserviços.

  • Isolamento Multi-Tenant: Jobs de equipes diferentes rodam em namespaces separados.
  • IRSA (IAM Roles for Service Accounts): O EKS injeta permissões granulares via OIDC. Cada job assume uma Role IAM específica, garantindo que o Pod A só acesse o Bucket A, melhorando drasticamente a segurança em relação ao EMR EC2.

Performance & Configurações

  • Autoscaling com Karpenter: O Karpenter provisiona nós EC2 otimizados "just-in-time" para os pods pendentes do Spark, escalando massivamente em segundos e maximizando a taxa de acerto de Spot Instances.
  • Custom Docker Images: Empacote dependências complexas (ML, drivers nativos) em imagens Docker, acelerando os cold starts e garantindo constância no runtime.
  • Shuffle Tracking: No EKS, o Spark Shuffle Tracking evita a perda de dados cruciais quando pods em nós Spot são interrompidos pelo Auto Scaler.

Performance Callout: Dicas de Tuning

Otimizações cruciais para grandes volumes de dados

📦 Small Files em Spark

Ter milhares de arquivos pequenos no S3 causa overhead massivo de metadados. Solução: Use df.repartition(n) ou df.coalesce(n) visando arquivos de ~128MB.

🚀 Speculative Execution

Evita que "stragglers" (tasks lentas) atrasem o job inteiro ao lançar cópias em outros nós. Configure spark.speculation=true.

EMR Bootstrap Action Script

Exemplo real de script Shell para provisionar bibliotecas e pacotes nos nós do cluster no startup

O script de bootstrap roda como root em cada máquina do cluster (Master, Core e Task) antes dos serviços Hadoop/Spark serem iniciados. Deve ser armazenado no S3:

#!/bin/bash
# EmrBootstrap.sh - Provisionamento de dependências
set -e

# Instalação de bibliotecas Python globais
sudo pip3 install \
  pandas \
  pyarrow \
  cryptography \
  great-expectations

# Download de JARs adicionais para conectores no diretório do Spark
sudo wget -P /usr/lib/spark/jars/ \
  https://repo1.maven.org/maven2/org/postgresql/postgresql/42.6.0/postgresql-42.6.0.jar

echo "Bootstrap finalizado com sucesso."

Erros Comuns no AWS EMR

Casos práticos e troubleshooting em nível de cluster

EC2 · Inicialização
Bootstrap Action failed
Causa: Script de bootstrap na inicialização do EC2 travou ou retornou código de erro diferente de zero.

Fix: Valide caminhos de arquivos no S3 e execute scripts localmente de forma prévia.
Spot · Interrupção
FetchFailed devido a desligamento de nós Spot
Causa: Instância Spot contendo dados parciais de shuffle foi desligada abruptamente pelo provedor cloud.

Fix: Ative a propriedade spark.shuffle.service.enabled=true para persistir shuffles em nós estáveis (Core).
