AWS Lake Formation CLI

Definição programática de filtros de linha e permissões de coluna via AWS CLI

O Lake Formation permite declarar filtros para restringir o acesso a dados sigilosos por meio de linha. O comando abaixo cria um filtro para permitir que analistas vejam apenas registros de vendas da região 'Sul':

# 1. Criação do Filtro de Linha no Lake Formation
aws lakeformation create-data-cells-filter \
  --cli-input-json '{
    "DataCellsFilter": {
      "TableCatalogId": "123456789012",
      "DatabaseName": "trusted_db",
      "TableName": "cliente_trusted",
      "Name": "filtro_regiao_sul",
      "RowFilter": {
        "FilterExpression": "regiao = '\''Sul'\''"
      },
      "ColumnNames": ["id_cliente", "nome", "data_atualizacao", "regiao"]
    }
  }'

# 2. Concessão de acesso ao filtro para um Role específico de Analistas
aws lakeformation grant-permissions \
  --principal '{ "DataLakePrincipalIdentifier": "arn:aws:iam::123456789012:role/AnalistasSulRole" }' \
  --resource '{
    "TableWithColumns": {
      "CatalogId": "123456789012",
      "DatabaseName": "trusted_db",
      "Name": "cliente_trusted",
      "ColumnWildcard": {}
    }
  }' \
  --permissions '["SELECT"]'

Controle de Acesso Baseado em Atributos (ABAC) com LF-Tags

Uso de tags de metadados para concessão simplificada e dinâmica de privilégios

Em ambientes com centenas de tabelas, conceder acessos individuais via RBAC (Role-Based Access Control) torna-se insustentável. O **ABAC (Attribute-Based Access Control)** no Lake Formation resolve isso através de tags de governança chamadas **LF-Tags**:

  • Associação de LF-Tags: Você define tags de múltiplos valores (ex: Confidencialidade = [Publica, Restrita, Sensivel] ou Domain = [Vendas, BI, Finanças]) e as vincula a bancos de dados, tabelas ou colunas.
  • Políticas Dinâmicas (Grants): Em vez de conceder privilégios na tabela cliente_trusted para a Role X, você concede privilégios SELECT a qualquer Principal cuja sessão IAM contenha tags que casem com a LF-Tag associada à tabela (ex: Domain = Vendas).
Política IAM do Principal para Enforcer de Tags (ABAC):
Para que o ABAC funcione cross-account ou no contexto local, o Principal IAM deve carregar as tags de sessão correspondentes. A política IAM abaixo garante que os usuários só consigam assumir a Role do Athena se as tags de controle baterem: 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "EnforceABACTagging",
            "Effect": "Allow",
            "Action": [
                "lakeformation:GetDataAccess",
                "glue:GetDatabase",
                "glue:GetTable",
                "glue:GetTables"
            ],
            "Resource": "*",
            "Condition": {
                "StringEquals": {
                    "aws:PrincipalTag/Domain": "${aws:ResourceTag/Domain}",
                    "aws:PrincipalTag/Confidencialidade": "Restrita"
                }
            }
        }
    ]
}

AWS Secrets Manager na Engenharia de Dados

Gerenciamento de credenciais sob criptografia envelope, controle de acesso IAM e rotação com Lambda

Em pipelines de big data profissionais, armazenar credenciais de bancos de dados relacionais (JDBC do RDS/Aurora), tokens de APIs SaaS (Salesforce, Ads) ou chaves privadas em texto aberto em códigos ou arquivos do S3 é uma infração grave de segurança. O AWS Secrets Manager centraliza esses segredos, protegendo-os com criptografia envelope baseada em chaves KMS CMK e automatizando sua rotação física periódica sem downtime.

1. Boas Práticas de Implementação & Governança

  • Criptografia Customizada (CMK): Nunca utilize a chave padrão de criptografia gerenciada pela AWS (aws/secretsmanager) para encriptar segredos em Datalakes de grande porte. Se um job Spark ou Lambda na conta precisar ler o segredo, ela exigirá permissões de descriptografia que poderiam expor chaves genéricas. Utilize chaves KMS gerenciadas pelo cliente (Customer Managed Key - CMK) dedicadas a cada domínio de segurança (ex: key/finance-secrets).
  • Controle de Acesso IAM por Políticas de Recurso: Além de autorizar as roles IAM executoras a lerem o segredo, associe políticas de recurso (Resource-Based Policies) anexadas diretamente ao segredo, rejeitando de forma explícita conexões que venham de fora da VPC analítica corporativa (utilizando a chave de condição aws:sourceVpce).
  • Secrets Rotation Automatizada via Lambda: Para cumprir conformidades regulatórias de auditoria (como PCI-DSS, HIPAA e LGPD), as senhas dos bancos analíticos devem ser rotacionadas a cada 30 ou 90 dias de forma transparente. O AWS Secrets Manager possui integração nativa com o RDS. Ativar a rotação cria uma função Lambda que executa a troca segura da senha master do RDS e atualiza a chave JSON do segredo, sem interromper conexões ativas.

2. Recuperação Segura de Credenciais com PySpark (Glue / EMR)

Abaixo está o padrão recomendado de desenvolvimento de engenharia para extrair credenciais do Secrets Manager de forma segura em tempo de execução usando o SDK Boto3 em Python/Spark:

import boto3
import json
from botocore.exceptions import ClientError
from pyspark.sql import SparkSession

def get_database_secret(secret_name, region_name="us-east-1"):
    # Cria o client do Secrets Manager
    session = boto3.session.Session()
    client = session.client(
        service_name='secretsmanager',
        region_name=region_name
    )

    try:
        get_secret_value_response = client.get_secret_value(
            SecretId=secret_name
        )
    except ClientError as e:
        # Erros comuns: ResourceNotFoundException, AccessDeniedException
        raise ValueError(f"Erro ao obter segredo {secret_name}: {str(e)}")

    # Trata resposta que pode vir em string (JSON) ou binário (Binary)
    if 'SecretString' in get_secret_value_response:
        secret = get_secret_value_response['SecretString']
        return json.loads(secret)
    else:
        raise TypeError("O segredo recuperado não está no formato de texto esperado.")

# ----------------- USO NO JOB SPARK -----------------
spark = SparkSession.builder.appName("SecureIngestion").getOrCreate()

# Recupera o segredo do banco Aurora RDS
credentials = get_database_secret("prod/aurora/finance")
db_user = credentials["username"]
db_password = credentials["password"]
db_host = credentials["host"]
db_port = credentials["port"]
db_name = credentials["dbname"]

# Monta URL JDBC de conexão de forma dinâmica e segura (sem Hardcoded credentials)
jdbc_url = f"jdbc:postgresql://{db_host}:{db_port}/{db_name}"

df_trusted = spark.read     .format("jdbc")     .option("url", jdbc_url)     .option("dbtable", "public.vendas_consolidado")     .option("user", db_user)     .option("password", db_password)     .option("driver", "org.postgresql.Driver")     .load()

# Dados carregados de forma segura!
df_trusted.show(5)

AWS IAM na Engenharia de Dados: Roles, Trusts & Boundaries

Configuração robusta de papéis, relações de confiança, grupos SSO e limites de menor privilégio para Big Data

A governança de segurança baseada no AWS IAM (Identity and Access Management) é o alicerce de qualquer pipeline analítico corporativo. Em ambientes modernos, dividimos estritamente os acessos de usuários humanos (que realizam consultas e desenvolvem código) dos acessos de máquinas e microsserviços (que executam processamentos pesados e rotinas agendadas).

Mapeamento de Grupos Humanos vs Roles de Máquinas

Entidade IAM Tipo de Recurso Usuário / Destino Permissões Recomendadas & Boas Práticas
Grupo: DataEngineers IAM SSO Group Engenheiros de Dados Permissão para criar pipelines (Glue, EMR), gerenciar IaC e usar o comando iam:PassRole apenas sobre Roles específicas de dados.
Grupo: DataAnalysts IAM SSO Group Analistas de BI / Cientistas Acesso restrito de leitura no Athena, consulta no QuickSight e visualização de tabelas no Glue Catalog via Lake Formation. Sem acessos de gravação direta em buckets S3 de produção.
Role: GlueSparkJobRole IAM Service Role AWS Glue ETL (Spark Engine) Leitura na camada Bronze, escrita na Silver, descriptografia de dados via chaves KMS específicas e publicação de logs no CloudWatch.
Role: EMRServerlessRole IAM Service Role EMR Serverless Workgroups Leitura e escrita de tabelas analíticas (S3/Iceberg), controle de recursos do cluster Spark/YARN e acesso de criptografia envelope no KMS.

Como funcionam as Relações de Confiança (Trust Policies)

Para que uma Role do IAM seja assumida por um serviço específico da AWS (como o motor computacional do AWS Glue), a Role deve obrigatoriamente possuir uma Trust Policy (Relação de Confiança) que autorize o principal correspondente a chamar o método sts:AssumeRole. Se a relação de confiança estiver vazia ou mal configurada, o Spark falhará instantaneamente ao subir a JVM com erros de acesso não autorizado.

Trust Policy JSON Recomendada para o AWS Glue: 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "glue.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

Permission Boundaries (Fronteiras de Permissão)

Em ambientes corporativos complexos, os engenheiros de dados têm permissão para criar novas Roles de execução para microsserviços e funções Lambdas. Porém, isso abre uma brecha crítica de segurança chamada Privilege Escalation (Escalação de Privilégios), onde um usuário poderia criar uma Role com privilégios de administrador global e assumi-la para burlar controles do IAM.

A Permission Boundary é uma política de controle aplicada como limite que define as permissões máximas que uma Role criada pode exercer. Mesmo que o engenheiro anexe a política AdministratorAccess à Role de execução de um contêiner, as permissões efetivas finais serão a intersecção matemática da política anexada com a Permission Boundary de dados, impedindo qualquer acesso a áreas proibidas (como faturamentos, segurança ou exclusão de logs).

Declaração IaC Completa com Terraform

O exemplo prático abaixo ilustra a criação de uma Role IAM de execução do AWS Glue Spark, com uma política de menor privilégio associada para S3/KMS e vinculando uma política limite de Permission Boundary:

# 1. Definição da Permission Boundary (Limite Máximo de Permissões)
resource "aws_iam_policy" "boundary" {
  name        = "data-engineering-permission-boundary"
  description = "Fronteira limite para garantir que nenhuma role crie recursos fora de dados"
  policy      = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = [
          "s3:GetObject",
          "s3:PutObject",
          "s3:ListBucket",
          "glue:GetTable",
          "glue:GetPartitions",
          "kms:Decrypt",
          "kms:GenerateDataKey"
        ]
        Resource = "*"
      }
    ]
  })
}

# 2. Criação da Role do IAM com a Trust Policy do AWS Glue e a Permission Boundary
resource "aws_iam_role" "glue_execution_role" {
  name                 = "glue-processing-execution-role"
  permissions_boundary = aws_iam_policy.boundary.arn

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Action    = "sts:AssumeRole"
        Effect    = "Allow"

        }

}

# 3. Anexação de Políticas de Menor Privilégio locais
resource "aws_iam_policy" "s3_access_policy" {

Observabilidade: Os 4 Golden Signals com DataDog

Centralização de logs, métricas e detecção de anomalias com a principal ferramenta de Data Observability do mercado

Em pipelines analíticos corporativos de alta escala, a observabilidade centralizada é crítica. Substituímos o monitoramento fragmentado pela integração robusta com o DataDog, coletando dados de execução da JVM/Spark, vazão física e monitoramento de anomalias.

Os 4 Golden Signals Aplicados a Dados

1. Latência: Tempo total de processamento de cada etapa do pipeline (leitura, shuffle e gravação). Métricas enviadas ao DataDog como data.pipeline.duration.
2. Tráfego (Throughput): Taxa de records lidos/escritos por segundo e volumetria em bytes processados: data.pipeline.records_processed.
3. Erros: Exceções de OOM, falhas de parse de schemas e quebras técnicas reportadas via logs estruturados: data.pipeline.error_count.
4. Saturação: Uso de memória heap/off-heap nos executores e limites de CPU dos nós EMR: spark.driver.jvm.memory_used.

Arquitetura de Coleta DataDog na AWS

Fluxo de Telemetria e Alertas

Os jobs Glue e EMR enviam métricas para o DataDog de duas formas principais:

  1. Spark Datadog Integration: O Spark envia métricas JMX e YARN para o Datadog Agent rodando como daemon no EMR ou coletadas via integrações integradas de métricas do CloudWatch.
  2. Datadog API Direct Ingestion: O próprio Job Spark faz requisições HTTPS na API do Datadog para publicar métricas customizadas de negócio.
Glue Job ➔ AWS Secrets (DD_API_KEY) ➔ DataDog API ➔ Slack Alert/Incident

Código de Produção: Envio de Métricas Customizadas ao DataDog com PySpark

O exemplo abaixo demonstra como um job do AWS Glue busca com segurança a chave da API do Datadog no **Secrets Manager** e publica métricas de progresso de ingestão diretamente na API do Datadog:

import time
import requests
import json
import boto3
from pyspark.sql import SparkSession

def get_dd_api_key():
    # Recupera a chave secreta do DataDog do Secrets Manager
    client = boto3.client('secretsmanager', region_name='us-east-1')
    try:
        response = client.get_secret_value(SecretId="prod/datadog/api_key")
        secret_dict = json.loads(response['SecretString'])
        return secret_dict['DD_API_KEY']
    except Exception as e:
        print(f"Erro ao recuperar chave do Datadog: {e}")
        return None

def send_metric_to_datadog(metric_name, value, tags=[]):
    api_key = get_dd_api_key()
    if not api_key:
        return
    
    url = "https://api.datadoghq.com/api/v2/series"
    headers = {
        "Content-Type": "application/json",
        "DD-API-KEY": api_key
    }
    
    # Payload no formato v2 da API do Datadog
    payload = {
        "series": [
            {
                "metric": metric_name,
                "type": 3,  # GAUGE
                "points": [
                    {
                        "timestamp": int(time.time()),
                        "value": float(value)
                    }
                ],
                "resources": [
                    {
                        "type": "host",
                        "name": "aws-glue-spark-job"
                    }
                ],
                "tags": tags + ["env:production", "project:customer-churn"]
            }
        ]
    }
    
    try:
        response = requests.post(url, headers=headers, json=payload, timeout=5)
        if response.status_code != 202:
            print(f"Erro ao enviar métrica Datadog: {response.text}")
    except Exception as e:
        print(f"Falha de rede ao conectar com Datadog: {e}")

# --- EXECUÇÃO DENTRO DO PIPELINE SPARK ---
spark = SparkSession.builder.appName("DataDogMetricsJob").getOrCreate()

# Exemplo de leitura de dados e processamento
df = spark.read.parquet("s3://company-datalake-silver/vendas/")
start_time = time.time()
record_count = df.count()
duration = time.time() - start_time

# Publica métricas customizadas no Datadog
send_metric_to_datadog("data.pipeline.records_processed", record_count, tags=["layer:silver", "table:vendas"])
send_metric_to_datadog("data.pipeline.duration", duration, tags=["layer:silver", "table:vendas"])

print("Métricas operacionais enviadas com sucesso ao DataDog!")
Detecção de Anomalias (Anomaly Alerts): No painel do Datadog, configure um **Anomaly Monitor** sobre a métrica data.pipeline.duration. O algoritmo de machine learning do Datadog detectará se a execução de hoje demorou mais que 3 desvios padrão em comparação com as últimas segundas-feiras, alertando sobre possíveis travamentos de GC ou processamento de arquivos corrompidos antes que o SLA diário seja violado.

Qualidade de Dados na AWS

Dimensões de qualidade, validações nas camadas Bronze/Silver/Gold, ferramentas (Glue DQ, Great Expectations, dbt) e padrões de contingência

A qualidade de dados deixou de ser uma verificação passiva posterior e passou a ser tratada como parte integrante do ciclo de engenharia de software (DataOps). Em ecossistemas modernos de dados na AWS, a integridade do dado deve ser ativamente testada e garantida em todas as etapas de transição lógica de armazenamento.

1. As 7 Dimensões Fundamentais de Qualidade de Dados

Qualquer framework de validação de dados baseia-se em dimensões clássicas que medem a aptidão do dado para consumo:

Dimensão Definição Conceitual Exemplo Prático
Acurácia (Accuracy) Se o dado reflete fielmente a realidade física ou a fonte autoritativa de origem. O saldo bancário registrado no DW coincide com o saldo real do banco de dados OLTP transacional.
Completude (Completeness) A presença de todos os registros e colunas esperadas para o processamento. Nenhuma linha do lote de vendas pode ter a coluna id_usuario nula ou em branco.
Consistência (Consistency) Se a informação permanece idêntica e sem contradições quando correlacionada entre tabelas. O total de vendas somado na tabela Fato coincide com a soma registrada nos relatórios de auditoria financeira.
Integridade (Integrity) A conformidade das estruturas de dados e a presença de relações válidas (integridade referencial). Todo id_produto na tabela de vendas deve existir na tabela dimensão de produtos.
Validade (Validity) O alinhamento do formato do dado com regras sintáticas específicas de domínio. A coluna de e-mail deve obedecer a uma expressão regular do tipo ^[\w\.-]+@[\w\.-]+\.\w+$.
Unicidade (Uniqueness) A ausência de duplicidade para chaves de entidades. A combinação de id_transacao e timestamp na tabela Silver deve ser única.
Tempestividade (Timeliness) O frescor do dado (Freshness) em relação à sua utilidade e às janelas acordadas de SLA. Os dados analíticos D-1 devem estar consolidados e disponíveis no S3 até as 07:00 da manhã diariamente.

2. Camadas Lógicas de Qualidade no Lakehouse (Arquitetura Medalhão)

Para otimizar custos computacionais e evitar gargalos, as validações de qualidade de dados devem ser distribuídas pelas camadas do Data Lakehouse:

Bronze / Raw Layer

Qualidade Sintática & Schema

Foco em validar a estrutura física do arquivo (se está corrompido, formato esperado CSV/JSON/Parquet) e aplicar Schema Enforcement (bloquear tipos primitivos incompatíveis). Registros corrompidos ou mal formatados são imediatamente rejeitados.

Silver / Trusted Layer

Qualidade Semântica & Domínio

Validação lógica de regras de negócio estáticas por linha. Verifica-se o preenchimento de nulos obrigatórios, limites numéricos válidos (ex: idade > 0 e < 120), formatação de strings (CPF, CEP) e remoção ativa de duplicidades através de técnicas de de-deduplication.

Gold / Refined Layer

Qualidade Analítica & Estatística

Validação holística agregada e integridade referencial. Aplicação de testes volumétricos (se a tabela de hoje teve variação suspeita de volume de linhas) e testes estatísticos (Z-Score) para identificar outliers em médias ou distribuições numéricas complexas.

3. Ecossistema AWS e Implementação Prática

Abaixo estão os principais caminhos para implementar e automatizar validações de qualidade de dados na AWS:

AWS Glue Data Quality (DQDL)

Integrado nativamente com o AWS Glue Catalog e Glue ETL, permite avaliar dados sem escrever códigos de validação complexos em Spark. Ele utiliza a linguagem declarativa **DQDL (Data Quality Definition Language)**.

Exemplo de Script PySpark integrado com AWS Glue Data Quality:

Abaixo está um exemplo de código Spark rodando dentro do AWS Glue para validar um lote contra regras DQDL:

import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job

# Inicialização do Contexto
glueContext = GlueContext(SparkContext.getOrCreate())

# Leitura da tabela de origem (camada Bronze)
dyFrame_bronze = glueContext.create_dynamic_frame.from_catalog(
    database="datalake_bronze", 
    table_name="vendas_raw"
)

# Definição das Regras DQDL para validação na Silver
regras_dqdl = """
Rules = [
    RowCount > 100,
    Completeness "id_venda" = 1.0,
    IsUnique "id_venda",
    ColumnValues "valor_total" >= 0,
    ColumnValues "status" in ["APROVADO", "CANCELADO", "PENDENTE"]
]
"""

# Execução da Avaliação de Qualidade
dq_results = EvaluateDataQuality.apply(
    frame=dyFrame_bronze,
    ruleset=regras_dqdl,
    publishing_options={
        "resultsS3Prefix": "s3://meu-bucket-auditoria/data-quality-results/",
        "metricsRepository": "GlueCatalog"
    }
)

# Verificação do Status das Regras
# O Glue cria um DynamicFrame com o resultado detalhado de cada regra
df_results = dq_results.toDF()
regras_falhas = df_results.filter(df_results["Outcome"] == "Failed")

if regras_falhas.count() > 0:
    print("ALERTA: O lote de dados violou regras de integridade do contrato!")
    # Lógica de Circuit Breaker: Salvar logs de falha e interromper execução
    raise ValueError("Falha de qualidade de dados. Interrompendo pipeline.")

Great Expectations (Open Source no EMR/Fargate)

Para plataformas multi-cloud ou equipes que preferem frameworks de código aberto maduros, o **Great Expectations** permite criar "Expectation Suites" declarativas em formato JSON. No EMR ou Fargate, o engenheiro escreve scripts Python que rodam essas validações em DataFrames do Spark ou Pandas, gerando relatórios ricos em formato HTML salvos automaticamente no S3.

dbt Tests (Transformação no Warehouse)

Ao realizar modelagem analítica na Gold (como tabelas agregadas no Redshift ou Athena), o dbt gerencia a qualidade através de dois tipos de testes:

  • Generic Tests: Declarados no arquivo schema.yml (como unique, not_null, accepted_values e relationships para integridade de chaves primárias/estrangeiras).
  • Singular Tests: Queries SQL customizadas salvas na pasta tests/. Se a consulta retornar qualquer registro (ex: vendas com data no futuro ou joins sem correspondência), o teste falha.

4. Tratamento de Falhas de Qualidade: Padrão Bad Records & Quarantine

Interromper completamente os pipelines por falha de qualidade é problemático para operações contínuas. A melhor abordagem é aplicar o padrão de Tratamento de Bad Records (Quarentena):

1. Detecção & Separação

Filtros Lógicos

O processador Spark ou Lambda aplica as validações de schema e domínio. Em vez de descartar os dados ruins ou quebrar o script, o DataFrame é dividido em dois: df_good (registros conformes) e df_bad (registros que falharam nos testes).

2. Isolamento (Quarentena)

Roteamento de Bad Records

O df_good prossegue para a gravação na camada Silver. O df_bad é escrito em um bucket S3 separado para quarentena (ex: s3://quarantine-bucket/layer-silver/vendas/), anexando metadados sobre o erro (código da regra que falhou, timestamp da validação).

3. Alerta & Re-processamento

Notificação e Correção

Um alerta EventBridge envia notificações via Slack ou Datadog para que os engenheiros corrijam a origem ou ajustem as regras. Uma vez resolvido o problema na origem, os dados da quarentena podem ser re-ingeridos sem perda histórica.

09.5

Data Quality: Regras e Boas Práticas Avançadas

Otimização de validações, Data Contracts e mitigação de falsos positivos na malha de dados

Garantir a integridade através do Data Quality não é apenas criar regras DQDL, mas arquitetar onde e como os dados são barrados. Implementar testes demais eleva custos e reduz a performance do pipeline de ETL. Implementar testes de menos destrói a confiança nos painéis executivos.

Boas Práticas de Validação (Left-Shifting)

  • Shift-Left Testing: Faça os testes o mais "à esquerda" possível no pipeline. Validações de esquema e tipos de dados devem ocorrer no produtor (microsserviço) via Data Contracts (ex: JSON Schema ou Protobuf validados contra o Glue Schema Registry antes de ir pro Kafka). Validações de negócios (ex: valor da venda não pode ser negativo) devem ocorrer na camada Silver.
  • Amostragem (Sampling): Executar regras estatísticas (ex: desvio padrão de preços) em Terabytes de dados diários causa lentidão catastrófica no Glue. Otimize aplicando o Glue Data Quality apenas sobre as partições recém-ingeridas (Incremental DQ) ou utilizando amostragem estatística segura (ex: avaliando apenas 5% dos registros de logs não-críticos).

Mitigação de Falsos Positivos

  • Limites Dinâmicos (Dynamic Thresholds): Evite regras hardcoded como RowCount > 10000. Em finais de semana o volume cai e a regra quebraria o pipeline sem motivo. Use limites dinâmicos com análise de ML ou baseados em métricas passadas (ex: volume >= 80% da média móvel dos últimos 7 dias).
  • Categorização de Criticidade: Nem todo erro deve parar o pipeline. Separe as regras em duas severidades:
    • Warning (Aviso): Gera alertas no Datadog/Slack, mas não quebra a ingestão.
    • Error/Halt (Crítico): Quebra a DAG ou desvia os dados para a Quarentena imediatamente.
09.6

Contratos de Dados (Data Contracts) em Produção

Mecanismos ativos de validação de schemas em microsserviços e integração com o AWS Glue Schema Registry

Um Contrato de Dados (Data Contract) é um acordo formal entre os produtores (ex: times de microsserviços) e os consumidores (times analíticos). Ele previne que alterações silenciosas de esquema (*Schema Drift*) na origem interrompam pipelines downstream. O contrato define a estrutura (campos, tipos, obrigatoriedade) e é validado de forma ativa e impeditiva.

Etapa 1

Definição Declarativa

O contrato é definido usando especificações neutras de formato como **JSON Schema**, **Apache Avro** ou **Protobuf** e registrado centralmente no **AWS Glue Schema Registry**.

Etapa 2

Validação no Produtor

Antes de publicar mensagens no Kafka/Kinesis, a aplicação de origem serializa e valida o payload localmente contra o registro de schemas. Erros de incompatibilidade travam o deploy ou desviam a escrita.

Etapa 3

Garantia de Evolução

Regras rígidas de compatibilidade (ex: BACKWARD_ALL) são aplicadas no Registry para rejeitar deploys na origem que quebrem os leitores analíticos (ex: remoção de colunas existentes).

Código de Produção: Registro e Validação de Schema com Boto3

O exemplo abaixo demonstra como validar dinamicamente um payload de evento de vendas contra o **AWS Glue Schema Registry** antes de publicá-lo para a ingestão analítica:

import json
import jsonschema
import boto3
from jsonschema import validate

# 1. Definição do Contrato de Dados (JSON Schema)
schema_contrato = {
    "$schema": "http://json-schema.org/draft-07/schema#",
    "title": "ContratoVenda",
    "type": "object",
    "properties": {
        "id_venda": {"type": "string"},
        "valor_total": {"type": "number", "minimum": 0.0},
        "id_cliente": {"type": "integer"},
        "email_comprador": {"type": "string", "format": "email"},
        "itens": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "sku": {"type": "string"},
                    "quantidade": {"type": "integer", "minimum": 1}
                },
                "required": ["sku", "quantidade"]
            }
        }
    },
    "required": ["id_venda", "valor_total", "id_cliente"]
}

def validar_e_publicar_evento(evento):
    # Passo A: Validação Local contra o JSON Schema do Contrato
    try:
        validate(instance=evento, schema=schema_contrato)
        print("✓ Evento validado localmente contra o Contrato de Dados.")
    except jsonschema.exceptions.ValidationError as e:
        print(f"✗ Erro de Violação de Contrato: {e.message}")
        raise ValueError("Payload inválido de acordo com o contrato de dados.")

    # Passo B: Validação e checagem de compatibilidade no AWS Glue Schema Registry
    glue = boto3.client('glue', region_name='us-east-1')
    try:
        # Verifica se o schema está registrado e é compatível
        response = glue.check_schema_version(
            SchemaId={
                'RegistryName': 'data-contracts-registry',
                'SchemaName': 'ContratoVenda'
            },
            SchemaDefinition=json.dumps(schema_contrato)
        )
        print(f"✓ Schema verificado no AWS Registry. Status: {response['Status']}")
    except glue.exceptions.EntityNotFoundException:
        # Se não existir, cria sob política de evolução controlada
        glue.create_schema(
            RegistryId={'RegistryName': 'data-contracts-registry'},
            SchemaName='ContratoVenda',
            DataFormat='JSON',
            Compatibility='BACKWARD_ALL',
            SchemaDefinition=json.dumps(schema_contrato)
        )
        print("✓ Novo contrato de dados registrado sob regras BACKWARD_ALL.")

    # Proceder com a gravação no stream de ingestão...
    print("✓ Evento enviado para a fila de streaming analítico.")

# Exemplo de Payload saudável
venda_ok = {
    "id_venda": "vda-908",
    "valor_total": 450.50,
    "id_cliente": 44920,
    "email_comprador": "cliente@email.com",
    "itens": [{"sku": "SKU-990", "quantidade": 2}]
}

validar_e_publicar_evento(venda_ok)

Plataforma de Testes de Engenharia de Dados

Pirâmide de Testes de Dados, BDD, testes unitários/integrados/E2E, testes mutantes e dados sintéticos com Faker

O Paradigma da Pirâmide de Testes de Dados

Diferente do desenvolvimento de software tradicional, o teste de dados valida tanto a lógica do código (código ETL) quanto a conformidade e comportamento físico dos dados (schemas e distribuições estatísticas). Adotamos o modelo de Pirâmide adaptado para Pipelines Analíticos:

Testes Funcionais vs Comportamentais (BDD)

Enquanto os testes funcionais validam o "como" as operações matemáticas ocorrem, o Behavior-Driven Development (BDD) valida o comportamento esperado dos dados em termos de regras de negócio compreensíveis pelo time de produto. Harness de Testes Unitários em PySpark

O script abaixo demonstra a implementação de testes unitários isolados em Pytest, usando Fixtures para criar a sessão Spark em memória e a biblioteca Faker para gerar mocks dinâmicos de dados:

# tests/test_sales_pipeline.py
import pytest
from faker import Faker
from pyspark.sql import SparkSession
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

fake = Faker()

@pytest.fixture(scope="session")
def spark_session():
    """Cria sessão Spark local na JVM do container de testes (Sem dependência de AWS)"""
    return SparkSession.builder \
        .master("local[*]") \
        .appName("PySpark-Unit-Tests") \
        .config("spark.sql.shuffle.partitions", "1") \
        .getOrCreate()

def calculate_comission(df):
    """Regra de negócio a ser testada funcionalmente"""
    from pyspark.sql.functions import col, when
    return df.withColumn(
        "comissao",
        when(col("canal") == "ONLINE", col("valor") * 0.05)
        .otherwise(col("valor") * 0.10)
    ).withColumn("status", when(col("valor") > 100.0, "APPROVED").otherwise("DRAFT"))

def test_calculate_comission_online(spark_session):
    # Geração de dados dinâmicos de teste usando Faker
    schema = StructType([
        StructField("id_venda", StringType(), False),
        StructField("canal", StringType(), False),
        StructField("valor", DoubleType(), False)
    ])
    
    # Gerando dados mocks consistentes
    mock_id = fake.uuid4()
    mock_data = [(mock_id, "ONLINE", 1000.0)]
    
    df_input = spark_session.createDataFrame(mock_data, schema=schema)
    df_output = calculate_comission(df_input)
    
    result = df_output.collect()
    assert len(result) == 1
    assert result[0]["id_venda"] == mock_id
    assert result[0]["comissao"] == 50.0
    assert result[0]["status"] == "APPROVED"

Em testes de integração, validamos a escrita em repositórios temporários (S3 ephemere/local ou MinIO) e a comunicação com o Glue Schema Registry:

import os
import shutil
import pytest
from pyspark.sql import SparkSession

@pytest.fixture(scope="module")
def local_lakehouse_dir():

    path = "/tmp/local_lakehouse/sales"
    if os.path.exists(path):
        shutil.rmtree(path)
    os.makedirs(path)
    yield path
    shutil.rmtree(path)

def test_write_to_local_lakehouse(spark_session, local_lakehouse_dir):
    data = [("vda-101", 350.0), ("vda-102", 450.0)]
    df = spark_session.createDataFrame(data, ["id_venda", "valor"])

Testes Mutantes (Mutation Testing) com Mutmut

Os testes mutantes garantem a qualidade dos seus assertions de teste. A biblioteca **Mutmut** modifica sutilmente o seu código ETL de produção (ex: trocando valor > 100.0 por valor >= 100.0, ou trocando * 0.05 por / 0.05) e roda a suite de testes.
Se todos os testes passarem mesmo após o código ter sido sabotado, significa que os testes têm lacunas de validação (Mutante Sobreviveu). Se pelo menos um teste falhar, o mutante foi **morto**, provando a eficácia do seu harness de testes.

Arquitetura da Plataforma de Testes de Dados (Ephemeral Schemas)

Para testar pipelines de dados na nuvem sem gerar poluição física ou colisões concorrentes em PRs (Pull Requests), adote a seguinte arquitetura:

  • Schemas Efêmeros (Dynamic Sandbox): A cada Pull Request disparado no GitHub Actions, o pipeline de CI cria dinamicamente um prefixo físico de sandbox (ex: s3://data-lake-sandbox/pr-42/) e registra bancos temporários no Glue Catalog no formato sandbox_pr42_db.
  • Validação de Volumetria e Distribuição: Injeta-se uma fração representativa de dados reais (ou dados sintéticos em escala criados por Faker) e valida-se distribuições estatísticas das saídas em relação a médias históricas usando **Great Expectations** ou **AWS Glue Data Quality**, prevenindo anomalias de regressão antes do merge.
Manual Prático do Especialista em Dados - Recursos Cloud de Segurança & Governança:

1. AWS KMS (Key Management Service)
• Como funciona na prática: KMS executa criptografia envelope. Ele gera chaves de dados (Data Keys) para que os microsserviços (ex: EMR, Athena, Glue) possam encriptar e desencriptar dados físicos.
• Limites Físicos e Throttling em Alta Escala: KMS possui um limite estrito de requisições por segundo (TPS) dependendo da região AWS (geralmente entre 5.500 e 10.000 requests/s). Se o Athena tentar ler uma tabela com 50.000 pequenos arquivos Parquet individuais criptografados, cada leitura de arquivo exigirá uma API `kms:Decrypt`, excedendo a cota do KMS e travando a query com erro de acesso.
• Resolução: Use o **S3 Bucket Keys**. Ao invés de o S3 requisitar uma chave ao KMS para cada arquivo, o S3 obtém uma chave de balde temporária que vale por minutos, diminuindo as chamadas ao KMS em até 99%.

2. AWS Secrets Manager
• Como funciona na prática: É um repositório central criptografado de segredos com suporte a rotação dinâmica (via Lambdas integrados).
• Gargalo e Boas Práticas: Secrets Manager suporta apenas ~2.000 requisições de API por segundo por padrão. Chamar a API `get_secret_value` para cada partição gravada no cluster Spark gerará throttling. O engenheiro de dados deve recuperar o segredo uma única vez no Driver do Spark e repassá-lo de forma segura aos Workers ou criar um cache do segredo em memória.

3. AWS IAM (Identity and Access Management)
• Como funciona na prática: Plano de controle global de autenticação e autorização na AWS.
• Gargalo de Chaining e Avaliação Logística: IAM possui limites rígidos no tamanho dos documentos de políticas (ex: no máximo 10.240 caracteres por política gerenciada). Se você tentar adicionar caminhos de buckets S3 granulares individualmente, atingirá o limite de tamanho rapidamente. A melhor abordagem para lagos de dados corporativos é registrar os diretórios no AWS Lake Formation, limpando as políticas do IAM e delegando o controle de acesso ao motor de segurança lógica do Lake Formation.

Erros Comuns em Governança & Arquitetura

Incidentes clássicos de segurança e organização em lagos de dados

Organização · Data Lake
Data Swamp (Pântano de Dados)
Causa: Ingestão massiva desordenada sem definição de owners, sem schemas registrados e sem validações de catálogo de metadados.

Fix: Implante Glue Crawlers associados a esquemas e ative auditoria automatizada das colunas no Glue Catalog.
Segurança · PII
Exposição de PII em tabelas Gold de BI
Causa: Ingestão descuidada que permitiu a passagem de documentos ou dados pessoais (CPF, e-mails) sem anonimização.

Fix: Implante rotinas de varredura com Amazon Macie e configure regras de mascaramento lógico em nível de coluna no Lake Formation.
