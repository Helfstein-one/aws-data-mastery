01

Amazon ECS: Teoria de Containers & Launch Types

Diferenças fundamentais entre ECS Fargate e ECS on EC2, estrutura de blueprints e segurança

O Amazon ECS (Elastic Container Service) é o serviço de orquestração de containers altamente escalável e de alta performance nativo da AWS. Diferente do Kubernetes (EKS), o ECS foca em simplificar o deploy eliminando a necessidade de gerenciar nós de controle complexos (Control Plane).

Launch Type
ECS Fargate (Serverless)
Como funciona: A AWS gerencia toda a computação. O engenheiro declara apenas o tamanho de CPU e Memória da Task.
Tradeoffs: Menor overhead operacional, isolamento físico de segurança por task (micro-VMs Firecracker). Custo ligeiramente superior por recurso ativo e boot time mais longo.
Launch Type
ECS on EC2 (Gerenciado)
Como funciona: O cluster ECS usa instâncias EC2 gerenciadas no seu próprio grupo de Auto Scaling como workers de container.
Tradeoffs: Controle total do sistema operacional, suporte a volumes EBS locais e GPUs dedicadas. Exige gerenciar patches do SO e agentes do ECS instalados nas máquinas.

Arquitetura ECS: Cluster, Service, Task & Task Definition

A tabela a seguir explica a hierarquia de objetos lógicos dentro do ecossistema do ECS:

Componente Propósito Análogo Físico
Cluster Agrupamento lógico de computação (Fargate ou EC2) em subredes privadas. Data Center Virtualizado
Task Definition O blueprint em formato JSON definindo a imagem Docker, portas, variáveis de ambiente e volumes. Dockerfile / Docker Compose
Task A instância ativa e executável do container em si, rodando de forma isolada na VPC. Container Ativo (Docker Run)
Service Gerenciador que garante que a quantidade solicitada de Tasks esteja saudável, integrando-as ao Load Balancer. Process Daemon / Orquestrador

Segurança de Containers: Task Role vs. Task Execution Role

Um erro de segurança recorrente em projetos de ECS é conceder permissões excessivas às instâncias que executam os containers. A AWS divide a identidade IAM no ECS em duas camadas de privilégio de grão fino:

  • Task Execution Role: Utilizada pelo **agente do ECS** rodando na infraestrutura (antes do container iniciar). Permissões típicas: baixar a imagem do container do ECR, enviar logs de stdout para o CloudWatch, descriptografar variáveis sensíveis vindas do Secrets Manager ou System Manager Parameter Store.
  • Task Role: Utilizada pela **sua aplicação** de fato rodando dentro do container (após a inicialização). Permissões típicas: ler/gravar dados em um bucket S3, consultar uma tabela do DynamoDB, ou publicar mensagens em um tópico SNS.

AWS Load Balancers: ALB vs. NLB vs. GLB

Entendendo as camadas L7, L4, L3, roteamento inteligente e estratégias de connection draining

A distribuição de requisições analíticas e operacionais entre instâncias é realizada pela camada de **Elastic Load Balancing (ELB)**. Escolher a camada de balanceamento errada prejudica a latência e impede o uso de protocolos modernos.

Application Load Balancer (ALB) - L7

Camada: HTTP, HTTPS, HTTP/2 e gRPC (Layer 7).
Funcionalidade: Roteamento inteligente por caminhos de URL (Path-based) e headers. Ideal para APIs e microsserviços operacionais baseados em REST.

Network Load Balancer (NLB) - L4

Camada: TCP, UDP, TLS (Layer 4).
Funcionalidade: Latências ultra-baixas na casa de microssegundos. Escala para milhões de requisições por segundo instantaneamente. Ideal para streaming e mensageria (Kafka/Kafka Connect).

Gateway Load Balancer (GLB) - L3

Camada: Roteador de pacotes IP puros (Layer 3).
Funcionalidade: Intercepta tráfego de rede bruto para direcionar a firewalls virtuais de terceiros (Palo Alto, Fortinet) para inspeção profunda de pacotes.

Deregistration Delay (Connection Draining)

Durante uma atualização de versão do microsserviço (Rolling Update), o ECS desliga as Tasks antigas e ativa as novas. Se o Load Balancer fechar a conexão abruptamente, clientes receberão erros HTTP. O **Deregistration Delay** (antigo Connection Draining) especifica o tempo (ex: 30 a 300 segundos) que o Load Balancer deve esperar para que as requisições ativas/em trânsito na Task antiga sejam concluídas, impedindo novas conexões de caírem na Task em processo de encerramento.

Decodificando Códigos de Erro de Ingress (ALB Troubleshooting)

  • HTTP 502: Bad Gateway: O Load Balancer recebeu uma resposta inválida ou falha de conexão do container. Causas comuns: o container falhou antes de responder, a porta declarada no Target Group está incorreta, ou a aplicação travou devido a estouro de memória (OOM).
  • HTTP 503: Service Unavailable: O ALB não encontrou instâncias de container saudáveis registradas no Target Group para responder à requisição, ou os pools de processamento estão saturados.
  • HTTP 504: Gateway Timeout: O container mestre demorou mais que o timeout limite definido no ALB (default 60s) para enviar o cabeçalho de resposta. Comum em queries SQL complexas executadas de forma síncrona que travam o backend da API.

IaC Completa: Terraform de ECS Fargate + ALB

Este código Terraform provisiona uma infraestrutura completa: cluster ECS, Task Definition baseada em Fargate com duas roles lógicas distintas, Service associado a um Target Group, e um Application Load Balancer roteando na porta 80:

# 1. Criação do Cluster ECS
resource "aws_ecs_cluster" "cluster" {
  name = "prod-analytics-cluster"
}

# 2. Roles IAM do ECS (Execução vs Task)
resource "aws_iam_role" "execution_role" {
  name = "ecs-task-execution-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{ Action = "sts:AssumeRole", Effect = "Allow", Principal = { Service = "ecs-tasks.amazonaws.com" } }]
  })
}

resource "aws_iam_role_policy_attachment" "execution_policy" {
  role       = aws_iam_role.execution_role.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}

resource "aws_iam_role" "task_role" {
  name = "ecs-app-task-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{ Action = "sts:AssumeRole", Effect = "Allow", Principal = { Service = "ecs-tasks.amazonaws.com" } }]
  })
}

# Permissões específicas da aplicação (ex: S3) na Task Role
resource "aws_iam_role_policy" "app_s3_policy" {
  name = "app-s3-permissions"
  role = aws_iam_role.task_role.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{ Action = ["s3:PutObject", "s3:GetObject"], Effect = "Allow", Resource = "arn:aws:s3:::prod-analyt-bucket/*" }]
  })
}

# 3. Task Definition Fargate
resource "aws_ecs_task_definition" "app" {
  family                   = "analytics-api"
  network_mode             = "awsvpc" # Obrigatório para Fargate
  requires_compatibilities = ["FARGATE"]
  cpu                      = "512"  # 0.5 vCPU
  memory                   = "1024" # 1 GB
  execution_role_arn       = aws_iam_role.execution_role.arn
  task_role_arn            = aws_iam_role.task_role.arn

  container_definitions = jsonencode([{
    name      = "api-container"
    image     = "nginx:latest"
    essential = true
    portMappings = [{
      containerPort = 80
      hostPort      = 80
    }]
  }])
}

# 4. ALB e Target Group
resource "aws_lb_target_group" "tg" {
  name        = "tg-ecs-analytics"
  port        = 80
  protocol    = "HTTP"
  vpc_id      = var.vpc_id
  target_type = "ip" # Obrigatório para modo awsvpc

  health_check {
    path                = "/"
    healthy_threshold   = 3
    unhealthy_threshold = 3
    timeout             = 5
    interval            = 15
  }
}

resource "aws_lb" "alb" {
  name               = "ecs-alb"
  internal           = false
  load_balancer_type = "application"
  security_groups    = [var.alb_sg_id]
  subnets            = var.public_subnet_ids
}

resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.alb.arn
  port              = "80"
  protocol          = "HTTP"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.tg.arn
  }
}

# 5. ECS Service interligado ao ALB Target Group
resource "aws_ecs_service" "service" {
  name            = "analytics-service"
  cluster         = aws_ecs_cluster.cluster.id
  task_definition = aws_ecs_task_definition.app.arn
  desired_count   = 2
  launch_type     = "FARGATE"

  network_configuration {
    subnets         = var.private_subnet_ids
    security_groups = [var.ecs_sg_id]
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.tg.arn
    container_name   = "api-container"
    container_port   = 80
  }

  depends_on = [aws_lb_listener.http]
}

Bancos de Dados Relacionais: RDS vs. Aurora Internals

Mapeamento físico do armazenamento compartilhado do Aurora, quorums, serverless v2 e RDS Proxy

Entender a física e os tradeoffs de performance das engines OLTP na nuvem da AWS é indispensável para evitar gargalos em migrações e cargas de dados massivas de plataformas analíticas.

trade-offs de Arquitetura de Dados: RDS vs. Aurora

RDS Tradicional: Utiliza armazenamento de blocos padrão da AWS (Amazon EBS). A réplica secundária Multi-AZ é sincronizada a nível de blocos de disco físico. Escritas lentas na primária replicam síncrona e fisicamente, dobrando a latência de I/O em rede.

Amazon Aurora: Desacopla completamente processamento (SQL Engine) de armazenamento. O armazenamento é virtualizado e estruturado em logs (Log-structured storage), espalhado em 6 réplicas físicas em 3 AZs. Não há replicação de blocos de disco; em vez disso, o Aurora envia apenas os redo logs para o storage compartilhado.

Escrita em Quorum (Write Quorum) no Aurora

Para otimizar escritas, o Aurora utiliza um sistema de quórum distribuído. Cada bloco de dados é segmentado e gravado em 6 instâncias de storage (2 por AZ). Uma escrita é considerada um commit válido assim que 4 das 6 instâncias confirmam a gravação física (4/6 Write Quorum). Leituras de blocos requerem a confirmação de 3 de 6 cópias (3/6 Read Quorum) para reconstruir dados de forma consistente caso ocorram falhas parciais em storage pools.

Aurora Read Replicas (Zero-Copy Storage Link)

Em um banco RDS tradicional, cada Réplica de Leitura tem seu próprio volume EBS individual, gerando atrasos (Replica Lag) sob fluxos intensos de escrita. No Aurora, todas as réplicas de leitura (até 15) enxergam e compartilham o mesmo volume virtual lógico do Writer. Como não há replicação física de disco, o Replica Lag é insignificante (< 10ms), servindo como barreira contra dados desatualizados em queries analíticas.

Amazon RDS Proxy: Connection Pooling & Multiplexing

Microsserviços serverless (como lambdas disparadas por eventos rápidos) ou dezenas de tarefas ECS podem subir centenas de conexões TCP de banco de dados concorrentes em segundos. Isso esgota rapidamente a memória da instância RDS (que consome cerca de 10MB por conexão inativa do Postgres). O **RDS Proxy** atua como uma barreira transparente:

  • Connection Pooling: Mantém um pool de conexões físicas estabelecidas abertas com o banco de dados.
  • Multiplexing (Multiplexação): Permite que dezenas de conexões de clientes compartilhem a mesma conexão física ativa do banco caso não estejam executando transações simultâneas.
  • Failover Acelerado: Em caso de failover (Writer principal cair), o RDS Proxy redireciona as conexões automaticamente para a nova réplica promovida a Writer sem forçar o cliente a renegociar handshakes TCP demorados, reduzindo o tempo de interrupção de 30s para menos de 3s.

Guia Operacional: Monitoramento & Troubleshooting Avançado

Queries SQL de tuning de bancos, comandos CLI cruciais de diagnóstico do ECS e Load Balancers

CLI Cheat Sheet: Operando e Diagnosticando ECS & Load Balancers

# 1. Obter informações de tarefas rodando no ECS
aws ecs list-tasks --cluster prod-analytics-cluster

# 2. Descrever detalhes de uma task específica (verificar se há erros de Out of Memory - OOM)
aws ecs describe-tasks \
  --cluster prod-analytics-cluster \
  --tasks arn:aws:ecs:us-east-1:123456789012:task/prod-analytics-cluster/99b6622

# 3. Forçar um redesploy limpo sem alterar a Task Definition
aws ecs update-service \
  --cluster prod-analytics-cluster \
  --service analytics-service \
  --force-new-deployment

# 4. Interagir diretamente (SSH/Bash) dentro do container ECS rodando no Fargate
aws ecs execute-command \
  --cluster prod-analytics-cluster \
  --task 99b66223a4 \
  --container api-container \
  --interactive \
  --command "/bin/sh"

# 5. Verificar o status de integridade do ALB Target Group
aws elbv2 describe-target-health \
  --target-group-arn arn:aws:elasticloadbalancing:us-east-1:12345678:targetgroup/tg-ecs-analytics/bc51

SQL Diagnostics para Administradores de Bancos (PostgreSQL RDS / Aurora)

Em momentos de travamento no banco, utilize as queries estruturadas abaixo para descobrir e encerrar locks e processos órfãos consumindo CPU:

Query 1: Listar conexões ativas ordenadas por tempo de execução (identificar queries travando)
SELECT pid, age(query_start, clock_timestamp()), usename, state, query 
FROM pg_stat_activity 
WHERE state != 'idle' 
ORDER BY query_start ASC 
LIMIT 10;
Query 2: Identificar Locks Ativos (Tabelas bloqueadas por transações pendentes)
SELECT
    blocked_locks.pid     AS blocked_pid,
    blocked_activity.usename  AS blocked_user,
    blocking_locks.pid    AS blocking_pid,
    blocking_activity.usename AS blocking_user,
    blocked_activity.query    AS blocked_statement,
    blocking_activity.query   AS blocking_statement
FROM  pg_catalog.pg_locks         blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks         blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.database IS NOT DISTINCT FROM blocked_locks.database
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
    AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
    AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
    AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
    AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
    AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
    AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;
Comando 3: Derrubar transação bloqueadora específica via ID do processo (PID)
-- Termina a query de forma limpa
SELECT pg_cancel_backend(blocking_pid);

-- Força o encerramento imediato da conexão física com o banco
SELECT pg_terminate_backend(blocking_pid);

Tipos de Bancos de Dados AWS: Guia de Tomada de Decisão

Mapeamento completo de engines de banco, tipos de dados e quando usar

Banco AWS Modelo / Engine Vantagem Crítica trade-offs / Limites Caso de Uso Recomendado
Amazon RDS Relacional (OLTP) - Postgres, MySQL, Oracle, SQL Server Compatibilidade total com drivers e bibliotecas tradicionais. Replicação Multi-AZ lenta baseada em EBS. Dificuldade de escalar escritas globalmente. Sistemas transacionais legados, ERPs clássicos, CRMs com relações complexas de chaves estrangeiras.
Amazon Aurora Relacional (OLTP compatível) - Postgres/MySQL Armazenamento compartilhado atômico de log, auto-healing, failover em 3s, até 15 réplicas sem lag de leitura. Custo superior ao RDS tradicional para instâncias muito pequenas (não analíticas). **Sistemas transacionais modernos de altíssima concorrência** e APIs corporativas escaláveis.
Amazon DynamoDB NoSQL (Chave-Valor / Documento) Serverless, escala infinita com latência estável inferior a 10ms (single-digit). Latência global via Global Tables. Não suporta joins relacionais natively. Exige modelagem rigorosa de acesso (Single-Table Design). Carrinhos de compras, catálogo de produtos, sessão de usuários e logs de auditoria rápida.
Amazon DocumentDB NoSQL (Documento compatível com MongoDB) Totalmente gerenciado, escala para milhões de leituras por segundo integrando JSON nativo. Não suporta queries de joins analíticos complexos de forma performática. Gerenciadores de conteúdo (CMS), catálogos com atributos altamente dinâmicos e variáveis.
Amazon ElastiCache Em Memória (Redis / Memcached) Latência sub-milissegundo para queries repetidas e processamento de pub/sub rápido. Dados voláteis na RAM (mesmo com persistência ligada, o custo de RAM por GB é altíssimo). Caching de sessões HTTP, tabelas de classificação em tempo real e buffers de mensagens de alta vazão.
Amazon Neptune Grafo (RDF / Property Graph) Armazena e navega em relacionamentos altamente interconectados com velocidade milissegunda. Linguagens de query específicas (Gremlin, SPARQL). Sistemas de detecção de fraude, motores de recomendação de amigos/produtos e redes sociais.
Amazon Timestream Séries Temporais (Time-Series) Auto-scaling nativo para bilhões de métricas de IoT diárias, ciclo de vida automático (in-memory para magnetic storage). Restrito a dados ordenados por timestamp imutáveis. Telemetria IoT de sensores industriais, métricas de aplicações de infraestrutura, logs de cliques.
Amazon Redshift MPP Data Warehouse (OLAP) Armazenamento colunar com processamento massivo em paralelo para petabytes de dados analíticos. Latência de gravação linha a linha péssima. Não deve ser usado como banco de API de microsserviços. **Data Warehousing corporativo centralizado**, agregação histórica pesada e queries de BI corporativo.

Comparativo e Matriz de Decisão: SQL vs. NoSQL vs. SQS

trade-offs arquiteturais entre persistência transacional, escalabilidade e desacoplamento assíncrono

Um erro de design comum em arquiteturas distribuídas na AWS é tentar usar a mesma tecnologia para objetivos computacionais opostos. Abaixo detalhamos a comparação física e lógica das soluções:

Característica SQL (ex: Aurora Postgres) NoSQL (ex: DynamoDB) SQS (Simple Queue Service)
Natureza do Serviço Banco de Dados Relacional estruturado (Tabelas/Esquemas rígidos). Banco de Dados Não-Relacional distribuído (Chave-Valor/Documento). Mensageria / Fila de Mensagens distribuída (Fila FIFO ou Standard).
Garantias de Consistência Transações ACID estritas (isolação serializável, chaves estrangeiras, consistência forte imediata). Eventualmente consistente (consistência forte sob demanda pagando taxa adicional). Sem ACID nativo multi-tabelas clássico. Exactly-Once (em filas FIFO) ou At-Least-Once (filas Standard). Desacoplamento temporal.
Escalabilidade de Escrita Vertical (Writer único no Aurora, escala até limites da máquina). Réplicas apenas lêem. Horizontal infinita (auto-scaling automático adicionando partições baseadas nas PKs). Praticamente infinita (escala automaticamente sem provisionamento prévio).
Padrão de Consulta Queries ad-hoc altamente complexas, joins multi-tabelas, agregações arbitrárias (GROUP BY). Apenas por chaves primárias e índices secundários conhecidos (GSI/LSI). Sem joins. Apenas leitura destrutiva sequencial (consumidor lê a mensagem da fila e a deleta após processar).
Decisão de Uso (Quando Escolher?) **Quando a integridade relacional é lei** e as queries são imprevisíveis (ex: fechamento contábil, BI flexível). **Quando o padrão de acesso é conhecido** e você exige escala linear infinita com latência estável milissegunda. **Para desacoplar microsserviços**, amortecer picos de carga de escrita (Buffer/Throttling) e garantir resiliência assíncrona.

Qual a Melhor Decisão de Quando Usar? (Arquitetura de Ingress Segura)

Em sistemas produtivos resilientes, o design de ingress combina os três serviços em um fluxo cooperativo:

Regra de Ouro da Arquitetura Decisória:
1. Use **SQS** na borda (Ingress) sempre que receber dados de sensores ou eventos externos massivos de e-commerce. A fila garante que a sua API responda "202 Accepted" em milissegundos, impedindo que picos de tráfego derrubem ou gerem exaustão de conexões físicas no banco de dados.
2. Use o **NoSQL (DynamoDB)** para dados operacionais desestruturados ou rastreamento rápido de estado de curta duração (ex: se o pagamento foi processado ou não).
3. Use o **SQL (Aurora)** apenas quando a mensagem for validada e precisar de consistência relacional estrita (ex: alterar balanço de contas bancárias ou gerar a fatura consolidada final do cliente).
