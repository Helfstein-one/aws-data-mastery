Tiers de Custo & Ciclo de Vida do S3

Otimização de custos FinOps e políticas de transição automática de dados

O Amazon S3 oferece diferentes classes de armazenamento para otimizar o custo de acordo com a frequência de acesso e a durabilidade necessária para os dados do Lakehouse:

Tier Padrão de Acesso Custo Armaz. Custo Recup. Caso de Uso
S3 Standard Frequente Alto ($$$) Zero Dados ativos, Gold layer, Dashboards em tempo real.
S3 Intelligent-Tiering Desconhecido Médio ($$) Zero Silver layer com padrões de acesso imprevisíveis.
S3 Standard-IA Infrequente Baixo ($) Por GB Backups mensais, auditoria recente.
S3 Glacier Instant Retrieval Arquivamento (ms) Muito Baixo ($) Por GB Dados históricos que precisam de acesso imediato.
S3 Glacier Deep Archive Arquivamento (horas) Mínimo ($) Por GB Raw (Bronze) antigo, conformidade regulatória (7+ anos).
FinOps Callout: S3 Lifecycle Policies

Implemente políticas de ciclo de vida para automatizar a redução de custos sem intervenção manual:

  • Transition Bronze (Raw) to Glacier Deep Archive: Mova dados originais após 1-2 anos. Eles servem apenas para "re-processing" em desastres.
  • Use Intelligent-Tiering for Silver: Camadas intermediárias costumam ter acesso volátil. Deixe o S3 monitorar e mover para IA automaticamente.
  • Keep Gold in Standard/IA: Camadas de consumo final devem priorizar latência baixa para ferramentas de BI.

Internals do Apache Parquet

Estrutura física do arquivo: Row Groups, Pages e Metadata Footer

O Parquet agrupa registros em fatias horizontais chamadas Row Groups (tipicamente contendo 128 MB a 512 MB de dados). Dentro de cada Row Group, as colunas são salvas sequencialmente em Column Chunks, divididos em Pages binárias de 1 MB comprimidas (com Snappy, Gzip ou ZSTD).

Estrutura Binária do Arquivo Parquet

Ao ler um arquivo Parquet, o motor SQL (Athena/Spark) lê primeiro os **últimos bytes** do arquivo (Footer), que contém os metadados do schema e as estatísticas. A partir disso, ele sabe exatamente quais offsets de bytes ler e quais Row Groups pular:

--------------------------------------------------
| [ Cabeçalho: Magic Number "PAR1" ]             |
--------------------------------------------------
| [ Row Group 1 ]                                |
|   - Column Chunk "id_cliente" (Data Pages...)   |
|   - Column Chunk "valor"      (Data Pages...)   |
--------------------------------------------------
| [ Row Group 2 ]                                |
|   - Column Chunk "id_cliente" (Data Pages...)   |
|   - Column Chunk "valor"      (Data Pages...)   |
--------------------------------------------------
| [ Metadata Footer ] (Lido Primeiro!)           |
|   - Schema e tipos de dados                    |
|   - Row Group 1: col "valor" Min: 10, Max: 50   |
|   - Row Group 2: col "valor" Min: 51, Max: 100  |
--------------------------------------------------
| [ Magic Number final "PAR1" ]                  |
--------------------------------------------------

Integração do Parquet com o AWS Glue Data Catalog

Para expor arquivos Parquet armazenados no Amazon S3 a motores de consulta como Athena e Redshift Spectrum, a tabela deve ser declarada no AWS Glue Data Catalog como uma tabela externa (EXTERNAL_TABLE).

O Glue Data Catalog atua como um Metastore compatível com Hive. Ao criar a tabela, é estritamente necessário configurar as bibliotecas Java corretas de serialização e desserialização (SerDe) e as classes de Input/Output. No caso do formato Parquet, essas classes lidam com a tradução entre a representação binária física no S3 e os registros virtuais lidos em SQL.

  • InputFormat: org.apache.hadoop.hive.ql.io.parquet.MapredParquetInputFormat (Instrui como os arquivos devem ser fatiados e escaneados para o motor Hadoop).
  • OutputFormat: org.apache.hadoop.hive.ql.io.parquet.MapredParquetOutputFormat (Usado quando motores gravam novos dados na tabela).
  • SerDe Library: org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe (Extrai os tipos de dados binários do Parquet e converte-os no schema lógico estruturado em colunas do Hive).
Infraestrutura como Código (Terraform) - Tabela Parquet com Boas Práticas

O exemplo abaixo cria uma tabela particionada no AWS Glue Data Catalog otimizada para Parquet no Amazon S3. Boas práticas aplicadas em IaC: declaração explícita de compressão (ZSTD/SNAPPY) e configuração de Partition Projection, que acelera consultas Athena eliminando consultas de listagem onerosas no Amazon S3 ou no próprio Glue Catalog.

resource "aws_glue_catalog_table" "tabela_parquet_lakehouse" {
  name          = "tb_vendas_consolidadas"
  database_name = aws_glue_catalog_database.silver_db.name
  table_type    = "EXTERNAL_TABLE"

  parameters = {
    "EXTERNAL"            = "TRUE"
    "parquet.compression" = "ZSTD"

    # Boas práticas: Partition Projection para o AWS Athena
    "projection.enabled"           = "true"
    "projection.ano.type"          = "integer"
    "projection.ano.range"         = "2020,2030"
    "projection.mes.type"          = "integer"
    "projection.mes.range"         = "1,12"
    "projection.mes.digits"        = "2"
    "storage.location.template"    = "s3://my-datalake-silver/vendas/ano=$${ano}/mes=$${mes}/"
  }

  partition_keys {
    name = "ano"
    type = "int"
  }
  partition_keys {
    name = "mes"
    type = "int"
  }

  storage_descriptor {
    location      = "s3://my-datalake-silver/vendas/"
    input_format  = "org.apache.hadoop.hive.ql.io.parquet.MapredParquetInputFormat"
    output_format = "org.apache.hadoop.hive.ql.io.parquet.MapredParquetOutputFormat"

    ser_de_info {
      name                  = "my-stream"
      serialization_library = "org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe"

      parameters = {
        "serialization.format" = "1"
      }
    }

    columns {
      name = "id_venda"
      type = "string"
    }
    columns {
      name = "valor_total"
      type = "double"
    }
  }
}

Apache Iceberg: Otimização de Transações ACID

Como o Iceberg substitui o diretório físico baseado em Hive no S3

Em estruturas Hive tradicionais, uma tabela é mapeada para diretórios físicos como s3://bucket/ano=2026/. Adicionar arquivos exige renomeação lenta no S3. O Apache Iceberg elimina a dependência de diretórios físicos e controla a tabela por meio de uma árvore hierárquica de arquivos de metadados imutáveis.

Transações ACID
Atomicidade com Snapshots
Novas escritas gravam novos arquivos Parquet e geram um novo snapshot. Caso ocorra erro de execução, o snapshot antigo continua ativo sem dados corrompidos.
Hidden Partitioning
Partições Ocultas
Iceberg computa transformações automaticamente. Não há necessidade de informar colunas de partição redundantes em filtros de query.
Schema Evolution
Evolução Invariante
O rastreamento de colunas é feito por IDs numéricos internos. Alterações como RENAME ou DROP COLUMN não exigem reescrita dos dados.

Controle de Concorrência Otimista (OCC) e Conflitos de Commits

O Apache Iceberg utiliza **Controle de Concorrência Otimista (Optimistic Concurrency Control - OCC)** para garantir isolamento transacional serializável durante escritas simultâneas de múltiplos jobs Spark/Flink no mesmo catálogo:

  • Como funciona: Ao iniciar uma operação de escrita (ex: UPDATE ou INSERT), o gravador assume que não haverá conflito, lê o snapshot ativo da tabela (ex: s1), escreve os novos arquivos Parquet correspondentes e gera um novo metadados de snapshot proposto (ex: s2).
  • Fase de Commit: O gravador tenta atualizar o ponteiro da tabela no catálogo de metadados (como o **AWS Glue Data Catalog**) do snapshot s1 para o s2 através de uma operação atômica de comparação e troca (CAS - Compare-And-Swap).
    Se outro job concorrente concluiu um commit primeiro, o ponteiro da tabela no Glue já mudou para s3. O commit do primeiro job falha com uma exceção do tipo CommitFailedException.
  • Estratégia de Retentativa (Conflict Resolution): Em caso de colisão, o Iceberg tenta resolver o conflito automaticamente sem falhar o job:
    1. O gravador lê o novo snapshot ativo (s3) para verificar se as alterações do commit concorrente conflitam diretamente com os arquivos alterados localmente (ex: se ambos alteraram a mesma linha ou partição em um UPDATE concorrente).
    2. Se não houver sobreposição física direta de dados (como INSERTs paralelos em partições diferentes), o Iceberg mescla os manifestos e faz uma nova tentativa automática de commit apontando para um novo snapshot consolidado.
    3. Se houver conflito direto de dados (Row-level collision), a transação falha definitivamente para evitar corrupção e anomalias de escrita.
  • Parâmetros de Tuning de Commits no Spark: Para otimizar o tratamento de concorrência em tabelas com alta taxa de atualização, configure os limites de retentativas na tabela Iceberg: 
    ALTER TABLE minha_tabela SET TBLPROPERTIES (
  'commit.retry.num-retries' = '15', -- Número máximo de tentativas de re-commit
  'commit.retry.min-wait-ms' = '100',  -- Tempo mínimo de espera exponencial
  'commit.retry.max-wait-ms' = '2000' -- Tempo máximo de espera exponencial
);

Estratégias de Ingestão: Copy-on-Write (CoW) vs Merge-on-Read (MoR)

O Apache Iceberg oferece duas abordagens fundamentais para gerenciar operações de alteração de dados (UPDATE, DELETE, MERGE). A escolha da estratégia impacta diretamente o throughput de escrita e a latência de leitura:

Copy-on-Write (CoW)

Qualquer atualização ou exclusão reescreve por completo os arquivos de dados que contêm as linhas modificadas.

  • Mecanismo: Lê o arquivo Parquet original, aplica as edições/deletions em memória e grava um novo arquivo Parquet inteiro. O novo snapshot aponta apenas para o arquivo novo.
  • Prós: Leitura limpa e veloz sem overhead de processamento ou joins em tempo de query.
  • Contras: Alto custo de escrita (Write Amplification). Modificar uma única linha em um arquivo de 100MB força o Spark a reescrever 100MB de dados no S3.
  • Uso Ideal: Tabelas de leitura pesada (Read-Heavy) com atualizações esporádicas ou em lotes massivos fora do horário comercial.
Merge-on-Read (MoR)

Atualizações e exclusões são gravadas em arquivos de exclusão ("Delete Files") separados, preservando os arquivos originais.

  • Mecanismo: As alterações são salvas imediatamente em arquivos de exclusão posicional ou por igualdade. O arquivo original não é tocado.
  • Prós: Escrita extremamente rápida e eficiente com baixíssimo consumo de I/O no EMR/Glue.
  • Contras: Custo computacional na leitura (Read Amplification). O motor de query precisa ler o arquivo original e aplicar um join dinâmico com o arquivo de exclusões para omitir os registros apagados.
  • Uso Ideal: Cargas de streaming (Near-Real-Time) ou tabelas com alta frequência de atualizações em tempo real.
Diferença entre Delete Files no MoR:
• Position Deletes: Grava o caminho exato do arquivo de dados e a linha física (offset) do registro deletado. É o mais performático para leitura, pois o join dinâmico é feito por índice direto de offset.
• Equality Deletes: Grava apenas o valor da chave que determina a deleção (ex: id_cliente = 543). A leitura é mais lenta pois exige avaliar predicados em todas as linhas.

Definição de Tabela com Spark SQL DDL de Alta Performance

Ao criar tabelas produtivas na AWS com Spark SQL, aplique configurações avançadas de engine para garantir escalabilidade física, compactação inteligente e controle de deleção:

CREATE TABLE glue_catalog.trusted_db.vendas_trusted (
    id_venda STRING,
    id_cliente STRING,
    valor_venda DOUBLE,
    data_venda DATE,
    canal_venda STRING
)
USING iceberg
PARTITIONED BY (days(data_venda))
TBLPROPERTIES (
    -- Define a estratégia padrão para atualizações e exclusões (MoR para escrita rápida)
    'write.delete.mode' = 'merge-on-read',
    'write.update.mode' = 'merge-on-read',
    'write.merge.mode' = 'merge-on-read',
    
    -- Compactação inteligente de formatos e codecs robustos
    'write.format.default' = 'parquet',
    'write.parquet.compression-codec' = 'zstd', -- ZSTD oferece melhor balanço taxa/desempenho
    'write.parquet.compression-level' = '7',
    
    -- Otimização física para prevenção de S3 SlowDown (Object Storage layout)
    -- Habilita hashes pseudo-aleatórios nos prefixos S3 para espalhar partições físicas
    'write.object-storage.enabled' = 'true',
    
    -- Distribuição das tarefas de escrita no Spark para evitar arquivos pequenos (Small Files)
    'write.distribution-mode' = 'hash', -- Distribui partições usando hash nos Workers Spark
    
    -- Autolimpeza básica (Retenção de metadados e histórico de time travel)
    'history.expire.max-snapshot-age-ms' = '259200000', -- Expira snapshots com mais de 3 dias (259200000 ms)
    'history.expire.min-snapshots-to-keep' = '5'
);

Z-Order Clustering (Curva de Morton) vs. Particionamento Hierárquico

Em volumes de dados muito grandes (Petabytes), o particionamento físico tradicional (ex: particionar por ano/mes/dia) gera problemas de "Overpartitioning" se o grão de busca for muito fino, criando milhões de arquivos pequenos. A alternativa para consultas que filtram por múltiplas colunas simultaneamente é o Z-Order Clustering:

Funcionalidade / Critério Particionamento Hierárquico Tradicional Z-Order Clustering (Multidimensional)
Conceito Físico Separa fisicamente os arquivos em diretórios separados no S3. Mapeia dados multidimensionais em uma única dimensão (curva em Z) mantendo a localidade lógica de múltiplas colunas no mesmo arquivo.
Campos Ideais Baixa cardinalidade (ex: regiao, canal_venda, ano). Alta cardinalidade filtrada em conjunto (ex: id_usuario e codigo_produto simultaneamente).
Custo de Escrita Baixo (Spark grava em pastas separadas). Alto (exige reordenação física global do DataFrame com alta demanda de CPU e Shuffle de memória). 
-- Otimizando o layout físico com Z-Order no Athena / Spark SQL
ALTER TABLE prod.silver.transacoes WRITE ORDERED BY ZORDER (id_usuario, codigo_produto);

Write-Audit-Publish (WAP) com Apache Iceberg

O padrão WAP garante que pipelines de dados nunca exponham dados corrompidos aos relatórios finais (camada Gold/Serving). Ele funciona gravando dados em uma **branch lógica temporária** (Write), rodando testes de qualidade/contratos (Audit), e avançando a branch principal (Publish) apenas em caso de sucesso:

# Exemplo de fluxo de trabalho WAP usando PySpark com Apache Iceberg
# 1. Escreve os dados na branch temporária 'wap_branch'
df_novos_dados.write \
    .format("iceberg") \
    .option("branch", "wap_branch") \
    .mode("append") \
    .save("prod.silver.transacoes")

# 2. Audit: Executa consultas de qualidade direcionadas para a branch wap_branch
df_audit = spark.read \
    .format("iceberg") \
    .option("branch", "wap_branch") \
    .load("prod.silver.transacoes")

erros_encontrados = df_audit.filter("valor_transacao < 0").count()

# 3. Publish: Se auditoria passar, faz o Fast-Forward da branch principal para a wap_branch
if erros_encontrados == 0:
    print("Sucesso! Mesclando alterações na branch main.")
    spark.sql("CALL prod.system.cherry_pick_snapshot('silver.transacoes', 'wap_branch')")
else:
    raise ValueError(f"Auditoria falhou. Encontrados {erros_encontrados} registros invalidos!")

Metadata-Only Queries (Consulta de Custo Zero)

Consultas de agregação simples (ex: SELECT COUNT(*), MAX(data_atualizacao) FROM tabela) em tabelas Iceberg bem compactadas são respondidas diretamente **lendo apenas os arquivos Manifestos (Avro)** de metadados, sem carregar um único byte dos arquivos físicos Parquet no S3. O Athena e o Spark resolvem a query em milissegundos com custo zero de varredura (Data Scanned = 0MB).

Manual Prático do Especialista em Dados - Recursos Cloud de Armazenamento:

1. Amazon S3 (Simple Storage Service)
• Como funciona na prática: O S3 não possui diretórios reais, mas sim um índice de chaves (Key-Value flat structure). Os prefixos são representados por barras ("/").
• Limites Físicos e Gargalos: Cada prefixo lógico suporta no máximo 3.500 requisições de escrita (PUT/POST/DELETE) e 5.500 requisições de leitura (GET/HEAD) por segundo. Se você acumular milhares de arquivos em s3://bucket/ano=2026/mes=06/dia=05/, um cluster Spark EMR com centenas de executores concorrentes atingirá esse limite, gerando HTTP 503 SlowDown.
• Resolução com Iceberg: Ativando write.object-storage.enabled=true, o Iceberg injeta um hash na raiz dos paths físicos (ex: s3://bucket/data/a5b1c8df/ano=2026/mes=06/), gerando múltiplos caminhos paralelos que espalham os arquivos por partições internas do S3, escalando a vazão infinitamente.

2. AWS Glue Data Catalog
• Como funciona na prática: Funciona como o catálogo de metadados Hive-compatible centralizado da AWS. Guarda apenas ponteiros, estatísticas e schemas estruturais (não lê ou armazena os dados físicos).
• Gargalos e Transações ACID: Em tabelas Hive tradicionais, uma alteração exige que o Glue Catalog mude centenas de partições em lote, o que gera inconsistência (queries concorrentes enxergam a tabela parcialmente atualizada). No Iceberg, o Glue Catalog armazena apenas um único ponteiro que aponta para o arquivo v3.metadata.json ativo. A transação é concluída alterando atomicamente esse ponteiro. Se dois processos Spark tentarem atualizar o ponteiro no Glue Catalog concorrentemente, o catálogo aplica uma trava otimista (Compare-And-Swap), rejeitando a transação do mais lento para garantir consistência perfeita.

Iceberg REST Catalogs: Federação Aberta e Compartilhamento de Dados

Como o protocolo REST descentraliza o controle de metadados permitindo federação de dados multi-engine com Apache Polaris

Tradicionalmente, tabelas Iceberg na AWS apontam para o Glue Data Catalog. Porém, em arquiteturas modernas e heterogêneas onde diferentes ferramentas (como Spark no EMR, Snowflake, Databricks e Athena) precisam ler e gravar simultaneamente no mesmo Datalake, o Glue Catalog torna-se limitador. A solução é o **Iceberg REST Catalog**, um padrão de API aberto implementado por ferramentas como **Apache Polaris** e **Unity Catalog OSS**:

  • Stateless API Protocol: O REST Catalog define um contrato REST padronizado para operações de catálogo (ex: carregar tabelas, registrar snapshots, atualizar schemas). Qualquer motor analítico compatível com o Iceberg pode se conectar a qualquer REST catalog de forma transparente.
  • Credential Vending (Venda de Credenciais): Ao invés de conceder permissões de leitura/escrita S3 diretamente para o Snowflake ou Databricks (o que exporia dados sensíveis), o REST Catalog (ex: Polaris) atua como o validador de identidade. Ele solicita credenciais temporárias do S3 via STS e as envia de volta ao motor analítico em conjunto com o caminho do arquivo JSON de metadados, limitando o acesso da query estritamente aos arquivos da tabela solicitada.

Manutenção de Tabelas Iceberg

Compactação física de arquivos pequenos e purificação de snapshots antigos

Com o tempo, sucessivos commits geram arquivos manifestos e snapshots em excesso no S3. A manutenção regular é obrigatória:

-- Execução via Spark SQL no EMR/Glue
-- 1. Compacta arquivos pequenos em arquivos ideais de 512 MB
CALL glue_catalog.system.rewrite_data_files(
  table => 'trusted_db.cliente_trusted',
  strategy => 'sort',
  sort_order => 'id_cliente ASC',
  options => map('max-file-size-bytes', '536870912')
);

-- 2. Limpa snapshots de Time Travel mais antigos que 3 dias
CALL glue_catalog.system.expire_snapshots(
  table => 'trusted_db.cliente_trusted',
  older_than => TIMESTAMP '2026-05-30 00:00:00'
);

-- 3. Limpa arquivos órfãos não associados a metadados
CALL glue_catalog.system.remove_orphan_files(
  table => 'trusted_db.cliente_trusted'
);

Código PySpark para Upserts (MERGE INTO)

Exemplo real de aplicação de CDC em lote processando dados para a camada Silver

O exemplo abaixo demonstra como atualizar dados existentes no Lakehouse e inserir novos registros usando comandos nativos ACID no PySpark:

from pyspark.sql import SparkSession

spark = SparkSession.builder \
    .appName("IcebergUpsertExample") \
    .getOrCreate()

# Registra visualmente o DataFrame incremental de origem
updates_df = spark.createDataFrame([
    (101, "Mauricio", 1500.0, "2026-06-02"),
    (105, "Ana", 2500.0, "2026-06-02")
], ["id_cliente", "nome", "limite_credito", "data_atualizacao"])

updates_df.createOrReplaceTempView("incremental_updates")

# Execução do merge atômico ACID
spark.sql("""
    MERGE INTO glue_catalog.trusted_db.cliente_trusted target
    USING incremental_updates source
    ON target.id_cliente = source.id_cliente
    WHEN MATCHED THEN
      UPDATE SET 
        target.nome = source.nome,
        target.limite_credito = source.limite_credito,
        target.data_atualizacao = source.data_atualizacao
    WHEN NOT MATCHED THEN
      INSERT (id_cliente, nome, limite_credito, data_atualizacao)
      VALUES (source.id_cliente, source.nome, source.limite_credito, source.data_atualizacao)
""")

Manutenção Crítica de Metadados e Limpeza do Apache Iceberg

Em ambientes de streaming ou batches frequentes (ex: micro-batches rodando a cada 5 minutos), o Apache Iceberg cria um snapshot a cada commit realizado com sucesso. Isso causa dois problemas de infraestrutura severos no Data Lake:

  • Metadados Inflados (Metadata Bloat): O arquivo metadata.json e os manifestos crescem cumulativamente. Um leitor (ex: query Athena) precisa baixar todo o histórico de snapshots ativos para montar a visão lógica da tabela, gerando latências de segundos apenas na etapa de parsing do catálogo.
  • Arquivos Órfãos e Históricos: À medida que snapshots antigos expiram, os arquivos físicos Parquet correspondentes continuam no bucket S3, acumulando custos silenciosos de FinOps.

Para mitigar esses gargalos, implemente uma rotina regular de **Manutenção e Compactação do Iceberg** via Spark SQL ou Procedure em seu orquestrador:

Comandos de Manutenção do Apache Iceberg (Spark SQL / Procedures)

Execute estes comandos sequenciais em um Job Spark mensal ou semanal para limpar metadados e arquivos obsoletos:

-- 1. Expirar Snapshots Antigos (Mantém histórico de Time-Travel por apenas 7 dias)
CALL glue_catalog.system.expire_snapshots(
  table => 'trusted_db.cliente_trusted',
  older_than => TIMESTAMP '2026-05-30 00:00:00.000',
  retain_last => 10
);

-- 2. Deletar Arquivos Órfãos (Arquivos físicos no S3 que não constam em nenhum metadados ativo)
CALL glue_catalog.system.remove_orphan_files(
  table => 'trusted_db.cliente_trusted',
  older_than => TIMESTAMP '2026-05-30 00:00:00.000'
);

-- 3. Compactar Arquivos Pequenos (Otimiza a leitura transformando arquivos pequenos em blocos de 128MB/512MB)
CALL glue_catalog.system.rewrite_data_files(
  table => 'trusted_db.cliente_trusted',
  strategy => 'binpack',
  options => map('target-file-size-bytes', '536870912') -- Otimiza para arquivos de 512MB
);

-- 4. Reescrever Manifestos (Consolida manifestos esparsos em blocos sequenciais compactados)
CALL glue_catalog.system.rewrite_manifests(
  table => 'trusted_db.cliente_trusted'
);

Erros Comuns em Storage & Resoluções

Prevenção e troubleshooting de falhas físicas no S3

S3 · Limite
S3 SlowDown (503 HTTP Service Unavailable)
Causa: Mais de 3.500 requests PUT/DELETE ou 5.500 GET por segundo no mesmo prefixo do S3.

Fix: Habilite hashes de partição no S3 ou use o Apache Iceberg, que gera caminhos distribuídos dinamicamente sem agrupar tudo na mesma pasta física.
Iceberg · Commit
CommitFailedException (Concurrent write conflict)
Causa: Duas rotinas Spark tentaram gravar no mesmo snapshot imutável simultaneamente. O segundo commit falhou no controle de concorrência.

Fix: Adicione retentativas automáticas no Spark Conf: `spark.sql.catalog.glue_catalog.commit.num-retries = 10`.
