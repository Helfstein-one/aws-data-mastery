FinOps & Otimização de Custos

FinOps na Engenharia de Dados

Melhores práticas para o controle, monitoramento e otimização financeira de infraestruturas analíticas na nuvem AWS.

01

Conceitos e Pilares de FinOps para Dados

A cultura de responsabilidade financeira compartilhada aplicada ao pipeline de dados

O conceito de FinOps (Cloud Financial Operations) para dados vai além de simplesmente cortar custos. Trata-se de maximizar o valor de cada dólar gasto em computação (Spark, EMR, Athena, Redshift) e armazenamento (Amazon S3). Como os volumes analíticos crescem exponencialmente, a arquitetura deve ser desenhada com eficiência de custos desde o primeiro dia (Cost-Optimized Architecture).

Pilar 1

Informar (Inform)

Dar visibilidade completa aos times de engenharia e negócios sobre de onde vêm os custos por meio de tags claras de Cost Allocation.

Pilar 2

Otimizar (Optimize)

Executar ações de tuning, como ajustar DPUs do Glue, habilitar ciclos de vida no S3 e usar instâncias Spot/Graviton no EMR.

Pilar 3

Operar (Operate)

Tornar a governança contínua com alarmes de orçamento do AWS Budgets e revisões de anomalia automatizadas.

02

Boas Práticas de Engenharia de Custos

Otimização granular dos principais componentes do pipeline analítico AWS

Amazon S3 Lifecycle
Ciclo de vida inteligente
Transicione dados da camada Bronze (raw) para Glacier Flexible Archive após 60 ou 90 dias. Mantenha apenas o necessário para reprocessamento imediato em Standard Tier para mitigar custos de armazenamento fixo.
AWS Glue Tuning
DPU Optimization & Auto Scaling
Nunca utilize mais DPUs do que a sua volumetria exige. Ative o Auto Scaling no Glue (Spark) para ajustar a quantidade de executores dinamicamente e evitar desperdício de cobranças em períodos de ociosidade.
Amazon EMR Compute
Spot Instances & Graviton
Use instâncias **Graviton (m6g, r6g)** que entregam até 40% melhor performance por dólar gasto. Aloque nós do tipo **Core** em instâncias On-Demand para resiliência e nós **Task** em instâncias Spot com até 70% de desconto.
Athena Optimization
Partitioning & Parquet Conversion
O Athena cobra $5 por TB escaneado. Converta seus dados estruturados para Parquet (colunar compactado) e filtre queries usando partições explicitamente. Isso reduz o custo de scan em até 90%.
03

Como Analisar Custos Analíticos na AWS

Ferramentas centrais e fluxos de auditoria financeira

Para rastrear de onde vem cada centavo gasto, a AWS oferece ferramentas específicas de monitoramento financeiro. A principal fonte de verdade absoluta para auditoria granular é o AWS Cost and Usage Report (CUR), que exporta logs detalhados de faturamento diretamente para um bucket S3 para análise no Athena:

Fluxo de Exportação e Análise do CUR

O CUR exporta arquivos de faturamento diários no formato Parquet para o S3. Um crawler do Glue cataloga os arquivos, permitindo consultar custos usando queries SQL analíticas diretamente no Athena:

-- Exemplo de query para encontrar custos de queries do Athena por usuário/assumidor de role
SELECT 
    line_item_usage_account_id AS conta_aws,
    line_item_resource_id AS query_execution_id,
    split_part(line_item_resource_id, '-', 1) AS engine,
    SUM(line_item_unblended_cost) AS custo_dolar
FROM 
    billing_cur_database.cur_table
WHERE 
    line_item_product_code = 'AmazonAthena'
    AND usage_start_date >= current_date - interval '30' day
GROUP BY 
    1, 2
ORDER BY 
    custo_dolar DESC
LIMIT 10;
AWS Budgets e Anomalias de Custo: Configure o **AWS Cost Anomaly Detection** utilizando Machine Learning nativo para identificar picos de consumo atípicos (ex: um loop infinito no Spark gerando 100 novas instâncias EC2) e notificar imediatamente o time via Slack ou e-mail.
04

Estratégia de Tagging com Terraform IaC

Taggeamento consistente de recursos de dados para exploração no Cost Explorer

As tags de alocação de custos (Cost Allocation Tags) devem ser ativadas no painel da AWS Billing Console após o deploy. Sem elas, o AWS Cost Explorer exibirá apenas custos globais, impossibilitando identificar qual squad, projeto ou ambiente gastou mais.

Abaixo, apresentamos o código declarativo **Terraform IaC** que define tags obrigatórias padrão em todos os recursos do pipeline usando default_tags no provider da AWS:

# 1. Configuração do Provider com tags padrão
provider "aws" {
  region = "us-east-1"

  default_tags {
    tags = {
      Environment = "production"
      CostCenter  = "102040-data-analytics"
      Owner       = "data-engineering-team"
      Project     = "customer-churn-analysis"
      ManagedBy   = "terraform"
    }
  }
}

# 2. Exemplo de recurso: Bucket S3 com tags específicas herdando as tags globais
resource "aws_s3_bucket" "silver_lakehouse" {
  bucket = "company-datalake-silver-production"

  tags = {
    DataClassification = "confidential-pii"
    StorageType        = "lakehouse-iceberg"
  }
}

# 3. Exemplo de EMR Serverless Application com tags herdadas e locais
resource "aws_emrserverless_application" "spark_app" {
  name          = "spark-churn-analytics"
  release_label = "emr-6.10.0"
  type          = "spark"

  initial_capacity {
    initial_capacity_type = "Driver"
    initial_capacity_config {
      worker_count = 1
      worker_configuration {
        cpu    = "4 vCPU"
        memory = "16 GB"
      }
    }
  }

  tags = {
    ExecutionSchedule = "daily-04am"
  }
}
Explorando no Cost Explorer: Após aplicar o código Terraform acima, acesse o AWS Billing → Cost Allocation Tags e selecione as chaves CostCenter, Environment e Project como ativas. Em 24 horas, você poderá filtrar e agrupar gráficos de custos no **Cost Explorer** por esses valores lógicos.
