Route 53 & CloudFront: Roteamento Global e CDNs

Como distribuir APIs, blindar pontos de entrada e acelerar o tráfego na borda da AWS

A primeira linha de defesa e otimização de latência para aplicações que interagem com dados analíticos reside na borda (Edge Locations) da nuvem AWS. Combinamos o **Route 53** e o **CloudFront** para balancear geograficamente as requisições e isolar a infraestrutura física de servidores.

DNS Roteamento
Amazon Route 53
Conceito: Serviço de DNS público e privado altamente resiliente.
Melhores Práticas: Utilizar políticas de Roteamento por Latência ou Geolocalização para direcionar requisições analíticas ao datacenter mais próximo; configurar Failover ativo-passivo automático monitorando endpoints; utilizar o Route 53 Resolver para ligar redes locais à nuvem de forma privada.
Edge Caching
Amazon CloudFront
Conceito: CDN que armazena respostas dinâmicas em cache na borda.
Melhores Práticas: Otimizar TTLs de cache para relatórios consolidados; utilizar Origin Shield para centralizar requisições e reduzir chamadas ao ALB; rodar autorização rápida usando CloudFront Functions (latência de microssegundos) e blindar acessos com AWS WAF contra ataques de DDoS.

Provisionamento do CloudFront & Route 53 com Terraform

Código declarativo de provisionamento para uma distribuição CloudFront apontando para um bucket S3 privado usando OAC (Origin Access Control):

# 1. Criação do Bucket S3 privado para armazenamento estático
resource "aws_s3_bucket" "data_hosting" {
  bucket = "prod-analises-estaticas-host"
}

# 2. Configuração de Origin Access Control (OAC) para blindar o bucket
resource "aws_cloudfront_origin_access_control" "oac" {
  name                              = "s3_oac_secure"
  origin_access_control_origin_type = "s3"
  signing_behavior                  = "always"
  signing_protocol                  = "sigv4"
}

# 3. Criação da Distribuição CloudFront
resource "aws_cloudfront_distribution" "cdn" {
  origin {
    domain_name              = aws_s3_bucket.data_hosting.bucket_regional_domain_name
    origin_id                = "S3-DataBucket"
    origin_access_control_id = aws_cloudfront_origin_access_control.oac.id
  }

  enabled             = true
  is_ipv6_enabled     = true
  default_root_object = "index.html"

  default_cache_behavior {
    allowed_methods  = ["GET", "HEAD"]
    cached_methods   = ["GET", "HEAD"]
    target_origin_id = "S3-DataBucket"

    forwarded_values {
      query_string = false
      cookies {
        forward = "none"
      }
    }

    viewer_protocol_policy = "redirect-to-https"
    min_ttl                = 0
    default_ttl            = 3600  # Cache por 1 hora
    max_ttl                = 86400
  }

  restrictions {
    geo_restriction {
      restriction_type = "none"
    }
  }

  viewer_certificate {
    cloudfront_default_certificate = true
  }
}

API Gateway & ALB: Gateways de Entrada de Dados

Conceito de Ingress L7, Throttling e Ingestão Direta Síncrona e Assíncrona

As requisições de ingestão ou consumo de dados chegam aos servidores através de gateways de entrada. A escolha entre o **Amazon API Gateway** (totalmente serverless) e o **Application Load Balancer (ALB)** baseia-se em tradeoffs de latência, volumetria e lógica de roteamento.

🔌 Módulo Dedicado Disponível Para um estudo aprofundado sobre API Gateway — incluindo CRUD REST completo, Terraform IaC, chamadas assíncronas com SQS/Kinesis/Step Functions, autenticação avançada (Cognito, Lambda Authorizer, IAM SigV4), WAF, observabilidade e 5 cases reais — acesse o módulo completo:

🔌 API Gateway Deep Dive →
Serverless Gateway
Amazon API Gateway
Conceito: Gateway de borda para expor endpoints REST/HTTP/WebSockets.
Melhores Práticas: Ativar controle de Throttling via Token Bucket (para evitar negação de serviço); realizar validações sintáticas estruturadas de schemas de payloads; utilizar integração de serviço direta com SQS/Kinesis para fluxos assíncronos, pulando custos desnecessários do Lambda.
Layer 7 Load Balancing
Application Load Balancer (ALB)
Conceito: Balanceador de carga gerenciado focado em HTTP/HTTPS (L7).
Melhores Práticas: Utilizar roteamentos avançados (Listener Rules) por Headers, HTTP Methods ou caminhos de URL; configurar timeouts de requisição agressivos para liberar threads nos containers; ativar gRPC para comunicação de microsserviços de dados de altíssimo throughput.

Provisionamento do API Gateway com Integração Direta SQS no Terraform

Este código configura uma rota pública no API Gateway que publica diretamente mensagens em uma fila SQS, otimizando drasticamente custos operacionais ao eliminar concorrência de Lambda:

# 1. Fila SQS alvo do Ingress
resource "aws_sqs_queue" "ingest_queue" {
  name = "prod-incoming-transactions-queue"
}

# 2. Role IAM permitindo ao API Gateway publicar no SQS
resource "aws_iam_role" "apigw_sqs_role" {
  name = "apigw-sqs-writer-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action    = "sts:AssumeRole"
      Effect    = "Allow"
      Principal = { Service = "apigateway.amazonaws.com" }
    }]
  })
}

resource "aws_iam_role_policy" "apigw_sqs_policy" {
  name = "apigw-sqs-policy"
  role = aws_iam_role.apigw_sqs_role.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Action   = ["sqs:SendMessage"]
      Effect   = "Allow"
      Resource = aws_sqs_queue.ingest_queue.arn
    }]
  })
}

# 3. Criação da REST API e recurso
resource "aws_api_gateway_rest_api" "api" {
  name = "IngestionAPI"
}

resource "aws_api_gateway_resource" "send" {
  rest_api_id = aws_api_gateway_rest_api.api.id
  parent_id   = aws_api_gateway_rest_api.api.root_resource_id
  path_part   = "send"
}

# 4. Método HTTP POST para recepção de payloads
resource "aws_api_gateway_method" "post" {
  rest_api_id   = aws_api_gateway_rest_api.api.id
  resource_id   = aws_api_gateway_resource.send.id
  http_method   = "POST"
  authorization = "NONE"
}

# 5. Integração com SQS - Sem Lambda intermediário
resource "aws_api_gateway_integration" "integration" {
  rest_api_id             = aws_api_gateway_rest_api.api.id
  resource_id             = aws_api_gateway_resource.send.id
  http_method             = aws_api_gateway_method.post.http_method
  type                    = "AWS"
  integration_http_method = "POST"
  uri                     = "arn:aws:apigateway:${var.region}:sqs:path/${var.account_id}/${aws_sqs_queue.ingest_queue.name}"
  credentials             = aws_iam_role.apigw_sqs_role.arn

  request_parameters = {
    "integration.request.header.Content-Type" = "'application/x-www-form-urlencoded'"
  }

  request_templates = {
    "application/json" = "Action=SendMessage&MessageBody=$input.body"
  }
}

Código Prático: Provisionamento de ALB para Múltiplas Aplicações (EMR no EC2 & ECS Fargate)

O exemplo abaixo demonstra como configurar em Terraform um **Application Load Balancer (ALB)** público que atua como ponto único de entrada (Ingress), roteando tráfego baseado no caminho da URL para a interface web de um cluster **EMR no EC2 (nó Master)** e para microsserviços de dados rodando em **ECS Fargate**:

# 1. Provisionamento do Application Load Balancer Público
resource "aws_lb" "ingress_alb" {
  name               = "prod-ingress-load-balancer"
  internal           = false
  load_balancer_type = "application"
  security_groups    = [aws_security_group.alb_sg.id]
  subnets            = [aws_subnet.public_az1.id, aws_subnet.public_az2.id]
  tags               = { Environment = "production" }
}

# 2. Target Group para a API Analítica rodando em ECS Fargate (porta 8080)
resource "aws_lb_target_group" "ecs_api_tg" {
  name        = "tg-prod-ecs-analytics-api"
  port        = 8080
  protocol    = "HTTP"
  vpc_id      = aws_vpc.main.id
  target_type = "ip" # Necessário para modo awsvpc do Fargate

  health_check {
    path                = "/health"
    interval            = 30
    timeout             = 5
    healthy_threshold   = 3
    unhealthy_threshold = 3
  }
}

# 3. Target Group para a Spark UI / Zeppelin rodando no Master do EMR no EC2 (porta 18080)
resource "aws_lb_target_group" "emr_master_tg" {
  name        = "tg-prod-emr-spark-ui"
  port        = 18080
  protocol    = "HTTP"
  vpc_id      = aws_vpc.main.id
  target_type = "instance" # Mapeamento direto de Instâncias EC2

  health_check {
    path                = "/jobs/" # Endpoint padrão do Spark History Server
    port                = "18080"
    interval            = 45
    timeout             = 10
  }
}

# 4. Listener HTTPS (Porta 443) do ALB
resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.ingress_alb.arn
  port              = 443
  protocol          = "HTTPS"
  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  certificate_arn   = var.ssl_certificate_arn

  # Ação padrão: Direciona para a API de dados no ECS
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.ecs_api_tg.arn
  }
}

# 5. Regra Adicional de Roteamento para a Spark UI do EMR por Caminho (Path-Based routing)
resource "aws_lb_listener_rule" "emr_spark_ui_rule" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 10 # Prioridade maior que a default rule

  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.emr_master_tg.arn
  }

  condition {
    path_pattern {
      values = ["/sparkhistory*", "/sparkhistory/*"]
    }
  }
}

# 6. Associação física do nó Master do EMR no Target Group
resource "aws_lb_target_group_attachment" "emr_master_attachment" {
  target_group_arn = aws_lb_target_group.emr_master_tg.arn
  target_id        = var.emr_master_instance_id # ID da instância EC2 do nó Master do EMR
  port             = 18080
}
03

VPC & VPC Endpoints: Segurança e FinOps de Rede

Otimizando o roteamento privado, subredes e economizando milhares de dólares eliminando tráfego NAT

A **VPC (Virtual Private Cloud)** é a fundação de segurança lógica da AWS. Em arquiteturas analíticas e pipelines de dados de alta escala, o roteamento de rede incorreto é uma das maiores fontes de custos inesperados. O tráfego de dados de subredes privadas para o S3 ou DynamoDB através de **NAT Gateways** gera faturas altíssimas (tarifado por GB processado).

Subredes Lógicas
VPC Subnet Topologies
Conceito: Divisões físicas de IPs de acordo com a visibilidade de internet.
Melhores Práticas: Isolar bases de dados e clusters Spark (Glue, EMR) em Subredes Isoladas (sem rota de internet); colocar NAT Gateways de forma redundante em múltiplas AZs nas subredes públicas; blindar conexões de portas usando Security Groups de grão fino e regras de NACLs nas bordas de subredes.
FinOps de Rede
VPC Endpoints (PrivateLink)
Conceito: Pontos de conexões internos de rede que evitam tráfegos públicos.
Melhores Práticas: Criar obrigatoriamente **Gateway Endpoints** para S3 e DynamoDB (gratuitos) para associar diretamente às tabelas de rotas privadas; utilizar **Interface Endpoints** (PrivateLink) para outros serviços (Kinesis, Glue, Secrets Manager) a fim de garantir que as chaves e dados nunca transitem pela internet pública.

Provisionamento de VPC com Gateway Endpoint para S3 com Terraform

Este código provisiona uma rede corporativa contendo subredes públicas e privadas, e cria a ponte privada direta com o S3 para economizar taxas de tráfego de dados do NAT Gateway:

# 1. Criação da VPC
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16"
  enable_dns_hostnames = true
  enable_dns_support   = true
  tags                 = { Name = "prod-analytics-vpc" }
}

# 2. Subredes Públicas (onde residem ALBs e NAT Gateways)
resource "aws_subnet" "public_az1" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.1.0/24"
  availability_zone = "us-east-1a"
  tags              = { Name = "public-subnet-1a" }
}

# 3. Subredes Privadas (onde residem EMR Serverless e Glue Jobs)
resource "aws_subnet" "private_az1" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.10.0/24"
  availability_zone = "us-east-1a"
  tags              = { Name = "private-subnet-1a" }
}

# 4. Tabela de rotas para a Subrede Privada
resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "private-rt" }
}

resource "aws_route_table_association" "private" {
  subnet_id      = aws_subnet.private_az1.id
  route_table_id = aws_route_table.private.id
}

# 5. VPC Gateway Endpoint para S3 - Roteamento Interno Gratuito
resource "aws_vpc_endpoint" "s3" {
  vpc_id            = aws_vpc.main.id
  service_name      = "com.amazonaws.us-east-1.s3"
  vpc_endpoint_type = "Gateway"

  # Associa automaticamente à tabela de rotas das subredes privadas
  route_table_ids = [aws_route_table.private.id]
  tags            = { Name = "s3-gateway-endpoint" }
}

# 6. Conectividade Multi-Account / Multi-VPC com Transit Gateway
# Quando diferentes contas da AWS precisam interagir de forma privada (ex: Conta Ingestion conectada ao Data Lake na Conta Storage)
# sem expor o tráfego a internet pública.
resource "aws_ec2_transit_gateway" "tgw" {
  description = "Transit Gateway Centralizador para Roteamento Analitico Multi-Account"
  tags        = { Name = "central-analytics-tgw" }
}

resource "aws_ec2_transit_gateway_vpc_attachment" "attachment" {
  subnet_ids         = [aws_subnet.private_az1.id]
  transit_gateway_id = aws_ec2_transit_gateway.tgw.id
  vpc_id             = aws_vpc.main.id
}

Topologias VPC Multi-Account & Peering de Rede

Em grandes plataformas de dados organizadas em Data Mesh ou arquiteturas de múltiplas contas (Multi-Account Setup), as VPCs de contas diferentes (ex: Ingestion, Processamento e Serving) precisam de conexões rápidas. As duas principais abordagens de roteamento privado são:

  • VPC Peering: Estabelece uma conexão direta ponto-a-ponto entre duas VPCs. O tráfego corre na infraestrutura global interna da AWS e não é cobrado por tráfego cruzado se as VPCs estiverem na mesma região e AZ. É o modelo de menor custo (zero custo de processamento, apenas tráfego inter-AZ se aplicável) e menor latência.
  • AWS Transit Gateway (TGW): Funciona como um hub ou roteador virtual na nuvem que conecta dezenas de VPCs e redes locais (Direct Connect / VPN). É o modelo ideal para gerenciamento e escala centralizados. No entanto, o TGW possui tarifas por hora e um custo de processamento por gigabyte transitado. *Aviso FinOps:* Para pipelines massivos de ETL que movem Petabytes, o TGW pode inflar exponencialmente a fatura; prefira VPC Peering direto para as rotas principais de movimentação de dados volumosos.
