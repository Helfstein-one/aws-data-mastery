Serving & Analytics de Dados

Arquiteturas analíticas de alto desempenho no S3 com Amazon Athena Serverless e Data Warehouses Massivamente Paralelos com Amazon Redshift.

01

Amazon Athena: Introdução Teórica & Funcionamento

O motor serverless de consultas interativas sobre dados armazenados de forma distribuída no S3

O Amazon Athena é um serviço de consulta interativa serverless que permite analisar dados diretamente no Amazon S3 utilizando SQL padrão. O Athena é construído sobre o motor open-source Trino (antigo Presto), especializado em queries ad-hoc de baixa latência em escala petabyte. Por ser totalmente serverless, não há necessidade de provisionar ou gerenciar clusters (computação desacoplada de armazenamento), e você é cobrado estritamente pelo volume de dados escaneados por consulta.

Arquitetura
Computação Desacoplada
O Athena lê dados brutos do S3 em tempo de execução. O processamento SQL é distribuído dinamicamente entre workers gerenciados pela AWS, sem persistência local.
Integração
Glue Data Catalog
Funciona como o repositório central de metadados. O Glue armazena a estrutura de schemas, tabelas e caminhos S3 (serdes) que o Athena interpreta para rodar SQL.
Mapeamento
Partition Pruning
Em vez de ler o bucket inteiro, o Athena usa chaves de partição (pastas no S3) para ignorar arquivos irrelevantes, reduzindo o volume escaneado e o custo.

Partition Projection Avançado

Otimização de tempo e I/O de consultas via computação de caminhos baseados em metadados:

Como Funciona

Tradicionalmente, o Athena consulta o AWS Glue Catalog para listar as partições físicas de uma tabela no S3. Em tabelas com milhões de partições, essa consulta de metadados torna-se o principal gargalo de performance analítica.

O Partition Projection inverte esse modelo: ao invés de ler metadados do catálogo, o Athena calcula os caminhos das partições no S3 em tempo de execução, baseando-se em regras configuradas no DDL. Isso elimina a latência de rede entre o motor de query e o repositório de metadados.

Performance & Vantagens

  • Latência Zero de Metadados: Redução drástica no tempo de planejamento da query (Planning Time) para datasets massivos.
  • Automatização: Elimina a necessidade de rodar MSCK REPAIR TABLE ou chamadas de API AlterTable para registrar novas partições.
  • Escalabilidade: Ideal para buckets com alta cardinalidade de partições (ex: por minuto, por IoT device ID).
💡 Insight Técnico: O Partition Projection é especialmente poderoso para dados de logs e telemetria onde o crescimento de partições é contínuo e previsível (baseado em tempo).

DDL Multi-Chave com Partition Projection (Ano, Mês, ID de Cliente)

Abaixo está o DDL para mapear partições que misturam data com IDs numéricos de clientes de forma dinâmica:

CREATE EXTERNAL TABLE clickstream_logs (
    event_id string,
    event_name string,
    user_id string
)
PARTITIONED BY (year string, month string, client_id string)
ROW FORMAT SERDE 'org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe'
LOCATION 's3://meu-datalake-gold/logs/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.year.type' = 'integer',
    'projection.year.range' = '2024,2030',
    'projection.month.type' = 'integer',
    'projection.month.range' = '1,12',
    'projection.month.digits' = '2',
    'projection.client_id.type' = 'integer',
    'projection.client_id.range' = '1,100',
    'storage.location.template' = 's3://meu-datalake-gold/logs/year=${year}/month=${month}/client=${client_id}/'
);

Melhores Práticas (Storage & API)

  • Formatos Colunares: Sempre armazene dados em Parquet ou ORC para permitir o Predicate Pushdown em nível de coluna.
  • Intervalos Reais: Configure o projection.COLUMN.range o mais próximo possível da realidade para evitar que o Athena tente calcular caminhos inexistentes.
  • Tipos de Dados: Use enum para listas fixas de valores e date para partições temporais complexas.

Integração via API & S3

O Partition Projection é configurado via TBLPROPERTIES na criação ou alteração da tabela. Ele altera o comportamento da API do Athena durante a execução, mas os dados no S3 devem seguir um padrão de nomenclatura consistente definido no storage.location.template.

✓ Pro Tip: Combine Partition Projection com S3 Inventory para auditar a consistência entre o template configurado e os arquivos físicos no bucket.
01.5

Amazon Athena: Federated Query & Workgroups

Consultas federadas nativas, gerenciamento de concorrência massiva e isolamento de carga de trabalho

Federated Query (Consultas Federadas)

O Athena Federated Query permite aos engenheiros consultarem dados diretamente em fontes externas (como Amazon RDS, DynamoDB, Redshift, Snowflake, etc.) fazendo JOINs em tempo real com o Data Lake no S3 sem precisar desenvolver complexos pipelines de ETL (CDC).

  • Arquitetura Serverless: Utiliza funções AWS Lambda com conectores pré-construídos que agem como interfaces de comunicação, convertendo respostas dos bancos operacionais para o formato colunar Apache Arrow.
  • Predicate Pushdown: O motor do Athena empurra inteligentemente os filtros (WHERE) para a fonte original através da Lambda, garantindo que o RDS ou DynamoDB trafegue pela rede apenas os dados estritamente necessários, minimizando latências e OOM.

Workgroups & Capacity Reservations (FinOps e Isolamento)

Para evitar que consultas analíticas pesadas (ETLs) impactem dashboards executivos de tempo real no QuickSight, o Athena provê mecanismos robustos de segregação:

  • Athena Workgroups: Permitem separar usuários, times ou aplicações. Cada Workgroup pode ter limites de bytes escaneados e métricas CloudWatch dedicadas, bloqueando automaticamente queries que estouram o orçamento configurado.
  • Provisioned Capacity: Para SLAs rígidos sem concorrência compartilhada, clientes alocam blocos de DPUs (Data Processing Units) dedicados. Isso blinda as queries críticas contra o enfileiramento padrão "noisy neighbor" nas regiões superlotadas da AWS.
  • Result Reuse: Para concorrência extrema (centenas de visualizações do mesmo dashboard na mesma hora), o recurso Result Reuse retorna o cache computado anteriormente da query do S3, reduzindo o tempo de resposta e zerando o custo repetido de scan analítico.

Manutenção de Tabelas Apache Iceberg no Lakehouse

Técnicas essenciais de Compaction (OPTIMIZE) e limpeza de versões antigas (VACUUM) via Athena/Spark

Em arquiteturas modernas de Lakehouse usando o formato Apache Iceberg, a escrita de múltiplos micro-batches ou pipelines de streaming gera o clássico Small Files Problem (milhares de arquivos pequenos que degradam a performance de leitura devido à latência de abertura de arquivos no S3). Além disso, atualizações frequentes geram arquivos de metadata antigos e arquivos órfãos. Para manter a performance ideal, realizamos manutenções contínuas:

1. Compaction (OPTIMIZE)

O processo de Compaction consolida arquivos pequenos em arquivos maiores otimizados para leitura (geralmente ~512MB ou 1GB). Ele lê múltiplos arquivos de dados e os reescreve de forma combinada e sequencial, gerando novos manifestos de metadados.

-- Comando SQL no Amazon Athena v3 para rodar Compaction
OPTIMIZE iceberg_db.tb_vendas REWRITE DATA (
    'bin-pack' -- Consolida arquivos sem reordenar
);

2. Remoção de Históricos (VACUUM)

O Iceberg provê suporte a Time Travel mantendo snapshots antigos. Sem manutenção, o storage do S3 cresce indefinidamente. O VACUUM (ou expiração de snapshots) apaga os snapshots obsoletos e deleta fisicamente os arquivos do S3.

-- Comando SQL no Amazon Athena para remover dados antigos
VACUUM iceberg_db.tb_vendas RETAIN 7 DAYS; -- Exclui snapshots com mais de 7 dias
✓ Pro Tip (Manutenção Automatizada via PySpark): Para datasets de grande escala, configure tarefas diárias ou semanais via AWS Glue ou EMR usando a API do Spark para gerenciar a expiração de metadados e otimização física: 
# Execução de Spark SQL para otimização de layout de dados
spark.sql("CALL glue_catalog.system.rewrite_data_files(table => 'iceberg_db.tb_vendas', options => map('max-file-size-bytes', '536870912'))")

# Expiração de Snapshots antigos para economizar custos de S3
spark.sql("CALL glue_catalog.system.expire_snapshots(table => 'iceberg_db.tb_vendas', older_than => TIMESTAMP '2026-06-01 00:00:00')")
02

Amazon Redshift: Introdução Teórica & Arquitetura MPP

O Data Warehouse corporativo escalável baseado em processamento massivamente paralelo

O Amazon Redshift é um serviço de Data Warehouse analítico rápido e totalmente gerenciado em escala petabyte. Ele é construído com base em uma arquitetura de Shared-Nothing e processamento MPP (Massively Parallel Processing). Ao contrário dos bancos transacionais tradicionais (OLTP), que armazenam registros em linhas para rápida inserção/atualização, o Redshift armazena dados em colunas (columnar storage). Isso reduz drasticamente a necessidade de I/O em queries analíticas, pois apenas as colunas envolvidas na query são lidas do disco.

Arquitetura
Leader Node
O nó de coordenação. Recebe a query SQL da aplicação, faz o parsing, gera o plano de execução otimizado, compila código C++ otimizado para o plano e distribui para os Compute Nodes.
Processamento
Compute Nodes & Slices
Os nós que realizam o processamento real. Cada Compute Node possui múltiplos Slices (unidades de processamento com disco e memória dedicados) que executam a query compilada em paralelo.
Armazenamento
RA3 & Managed Storage
Os nós modernos da série RA3 utilizam caches locais SSD de altíssima performance para dados quentes, enquanto o storage frio é arquivado de forma transparente e ilimitada no Amazon S3.

Diagrama da Arquitetura e Fluxo de Consultas MPP

Otimizações de Modelagem Física: Chaves e Distribuição

A performance das consultas no Redshift depende de como os dados são organizados nos discos de cada nó (slices). Configuramos isso via Sort Keys e Distribution Styles (DISTSTYLE):

Conceito Estratégia Cenário Ideal
DISTSTYLE AUTO Padrão inicial Redshift escolhe e muda de ALL para KEY conforme o crescimento do dataset.
DISTSTYLE KEY Baseado em Coluna Colunas que participam frequentemente de JOINS em comum entre fatos e dimensões.
DISTSTYLE ALL Replicação Completa Tabelas de dimensões muito pequenas (< 2-3M registros) copiadas em todos os nós.
DISTSTYLE EVEN Distribuição Circular Tabelas grandes sem chaves claras de JOINS comuns. Balanceamento uniforme garantido.

Sort Keys: Compound vs Interleaved

  • Compound Sort Keys (Padrão): Melhores quando as queries filtram com base em colunas em uma ordem fixa (ex: data_venda e depois id_cliente). O Redshift ordena fisicamente os dados nesta ordem hierárquica.
  • Interleaved Sort Keys: Dá o mesmo peso para todas as colunas em filtros arbitrários (ex: filtro por id_cliente de forma isolada ou data_venda de forma isolada). Útil para tabelas analíticas ad-hoc dinâmicas. Requer manutenção constante de `VACUUM`.

DDL de Produção Otimizado (Redshift):

CREATE TABLE fct_vendas (
    id_venda INT ENCODE az64,
    id_cliente INT ENCODE az64,
    valor_total NUMERIC(12,2) ENCODE az64,
    data_venda TIMESTAMP ENCODE az64
)
DISTSTYLE KEY
DISTKEY(id_cliente)
COMPOUND SORTKEY(data_venda, id_cliente);
✓ Compressão AZ64: Sempre utilize a codificação colunar moderna az64 para tipos numéricos e temporais no Redshift. Ela fornece alta compressão física em disco com performance de descompressão até 70% superior a LZO/ZSTD.

Amazon Redshift Spectrum: Queries diretas no S3

Configuração de tabelas externas sem ingestão física de dados no cluster DW

O Redshift Spectrum permite consultar dados do seu Data Lake S3 diretamente pelo cluster Redshift, sem precisar ingeri-los (eliminando custos de storage do cluster). Ele executa queries sob demanda utilizando uma camada computacional separada do Redshift.

Guia de Configuração e Criação de Tabela Externa

-- 1. Criação do Schema Externo apontando para o Glue Data Catalog
CREATE EXTERNAL SCHEMA spectrum_schema
FROM DATA CATALOG
DATABASE 'trusted_db'
IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftSpectrumRole'
CREATE EXTERNAL DATABASE IF NOT EXISTS;

-- 2. Criação de Tabela Externa no S3 mapeada via Spectrum
CREATE EXTERNAL TABLE spectrum_schema.logs_externos(
    event_id VARCHAR(50),
    event_type VARCHAR(50),
    user_id VARCHAR(50)
)
ROW FORMAT SERDE 'org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe'
STORED AS PARQUET
LOCATION 's3://meu-datalake-gold/logs/';

Análise de Performance de Query via EXPLAIN

Como ler o plano de execução do Redshift e identificar gargalos de redistribuição de dados na rede

Para otimizar queries lentas, execute o comando EXPLAIN na frente do SELECT. O Redshift retorna a árvore de passos do otimizador. O foco principal deve ser a identificação de movimentação física na rede:

EXPLAIN SELECT * FROM fct_vendas v JOIN dim_cliente c ON v.id_cliente = c.id_cliente;
Identificando Gargalos de Distribuição no Plano
  • DS_BCAST_INNER (Broadcast): Muito custoso. O Redshift está copiando a tabela interna inteira na rede para todos os nós por falta de chave de distribuição comum.
    Fix: Mude a chave de distribuição das tabelas para `KEY` usando a chave comum de Join.
  • DS_DIST_BOTH (Re-distribuição): Ambas as tabelas estão sendo re-particionadas em memória via rede durante o Join.
    Fix: Configure chaves idênticas de distribuição KEY na coluna de junção de ambas as tabelas.
  • DS_DIST_NONE (Ideal): Sem tráfego de rede. Os dados a serem unidos já residem nas mesmas fatias de disco locais. Esse é o Join ideal de alta performance.

Exemplo Prático 1: Plano Não Otimizado (DS_BCAST_INNER)

Abaixo vemos o plano gerado quando a tabela menor dim_cliente não possui distribuição por chave compartilhada, exigindo broadcast físico de seus registros para todos os compute nodes:

# EXPLAIN OUTPUT (Tabelas com distribuição circular ou não correspondentes)
XN Hash Join DS_BCAST_INNER  (cost=100.25..54200.40 rows=2500000 width=128)
  Hash Cond: (v.id_cliente = c.id_cliente)
  ->  XN Seq Scan on fct_vendas v  (cost=0.00..25000.00 rows=2500000 width=84)
  ->  XN Hash  (cost=50.00..50.00 rows=50000 width=44)
        ->  XN Seq Scan on dim_cliente c  (cost=0.00..50.00 rows=50000 width=44)

Exemplo Prático 2: Plano Otimizado (DS_DIST_NONE)

Abaixo vemos o plano gerado quando ambas as tabelas são distribuídas pela chave correspondente (id_cliente). Os dados residem nos mesmos discos locais, anulando a necessidade de tráfego de rede:

# EXPLAIN OUTPUT (Ambas as tabelas otimizadas com DISTSTYLE KEY no id_cliente)
XN Hash Join DS_DIST_NONE  (cost=100.25..25150.00 rows=2500000 width=128)
  Hash Cond: (v.id_cliente = c.id_cliente)
  ->  XN Seq Scan on fct_vendas v  (cost=0.00..25000.00 rows=2500000 width=84)
  ->  XN Hash  (cost=50.00..50.00 rows=50000 width=44)
        ->  XN Seq Scan on dim_cliente c  (cost=0.00..50.00 rows=50000 width=44)

Ingestão e Exportação Massiva (COPY & UNLOAD)

Operações otimizadas de trânsito de dados entre S3 e Redshift

-- Ingestão rápida via comando COPY (S3 para Redshift)
COPY fct_vendas
FROM 's3://meu-datalake-gold/vendas/'
IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
FORMAT AS PARQUET;

-- Exportação paralela via comando UNLOAD (Redshift para S3)
UNLOAD ('SELECT * FROM fct_vendas')
TO 's3://meu-datalake-gold/export/vendas/'
IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
FORMAT AS PARQUET
CLEANPATH;

Erros Comuns no Consumo & Soluções

Troubleshooting de performance em queries analíticas e cargas de data warehouse

Redshift · COPY
Comando COPY extremamente lento ou travado
Causa: Ingestão baseada em arquivo único massivo CSV bruto no S3. O Redshift não consegue paralelizar e apenas uma slice processa o arquivo todo.

Fix: Salve os dados em múltiplos arquivos Parquet compactados (Snappy/ZSTD) no S3. Alinhe o número de arquivos com o número múltiplo de slices de disco do cluster Redshift.
Athena · Custo
Queries custando dezenas de dólares por execução
Causa: Query varrendo arquivos sem compressão ou sem particionamento, escaneando o bucket do datalake inteiro (Full Table Scan).

Fix: Sempre use formato Parquet, filtre usando colunas de partição ocultas do Iceberg, ou configure Partition Projection limitando o volume de bytes escaneados.
