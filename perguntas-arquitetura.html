Questão 4 · Amazon Athena

Como resolver o erro "Metadata limit exceeded" ou queries Athena que falham por timeout antes de iniciar o scan dos dados?

Causa Física: Quando o Athena executa uma query em uma tabela particionada convencional (ex: particionada por ano/mes/dia/cliente), ele precisa fazer chamadas de API para o AWS Glue Data Catalog para listar os arquivos físicos correspondentes às partições solicitadas. Se a tabela tem milhões de partições, a fase de planejamento da query excede os limites de limite de API do Glue e gera timeout antes do processamento dos dados começar.

A Solução Suprema: Partition Projection

O Partition Projection armazena as regras de geração das partições diretamente como propriedades da tabela no Glue Catalog (ex: ano varia de 2020 a 2026). O Athena calcula em memória os caminhos físicos do S3 baseando-se nas datas passadas no filtro SQL, ignorando completamente as chamadas de API do catálogo e eliminando o timeout.

-- Exemplo de registro de tabela Athena com Partition Projection configurado
CREATE EXTERNAL TABLE sales_projected (
    id_venda string,
    valor double
) 
PARTITIONED BY (ano string, mes string)
LOCATION 's3://my-datalake/sales/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.ano.type' = 'integer',
    'projection.ano.range' = '2020,2026',
    'projection.mes.type' = 'integer',
    'projection.mes.digits' = '2',
    'projection.mes.range' = '1,12',
    'storage.location.template' = 's3://my-datalake/sales/ano=${ano}/mes=${mes}/'
);
Questão 9 · FinOps & S3

Em pipelines de streaming massivo de dados para o S3, como o custo de requisições de API (GET/PUT) pode superar o custo de armazenamento físico e como mitigar isso?

O Tradeoff Oculto de FinOps: O S3 cobra centavos por Gigabyte armazenado, mas cobra um valor fixo por 1.000 requisições PUT/POST ou 10.000 requisições GET/LIST. Se um pipeline de streaming escreve micro-arquivos no S3 a cada 5 segundos, o número de operações PUT gerará milhares de dólares na fatura AWS mensal, enquanto o espaço físico de armazenamento consumido seria ínfimo.

Como Otimizar em Escala de Produção:
  • Buffer temporal de escrita: Aumente o tamanho da janela de flush dos produtores (ex: Kinesis Firehose buffer de 5MB ou 120 segundos) para acumular eventos em memória e fazer um único PUT de arquivo maior, reduzindo o número absoluto de chamadas de API do S3.
  • Use formatos transacionais com manifestos: Formatos como o Apache Iceberg reduzem drasticamente as chamadas caras de listagem (LIST) do S3 usando ponteiros diretos em JSON nos arquivos de metadados para localizar os arquivos físicos Parquet de leitura, otimizando o custo de leitura analítica.
Questão 26 · Apache Iceberg & Concorrência

Sob gravações simultâneas massivas de múltiplos jobs (Spark, Flink, Athena) na mesma tabela Apache Iceberg no S3, como tratar falhas de CommitFailedException (Write Conflict) e configurar retentativas no catálogo?

Controle de Concorrência Otimista (OCC): O Apache Iceberg utiliza o controle de concorrência otimista (OCC). Quando um gravador inicia um commit, ele lê a versão atual do metadados. Ao concluir a gravação dos arquivos físicos Parquet, ele tenta escrever o novo arquivo de metadados JSON comparando se a tabela mudou desde o início (Compare-and-Swap). Se outro job executou um commit antes dele, o commit falha por conflito de concorrência, disparando CommitFailedException.

Ação Corretiva em Produção:
  • Ajuste de Retentativas de Commit (Commit Retries): Configure as propriedades da tabela Iceberg no Spark para forçar retentativas de merge em caso de conflitos concorrentes: 
    -- Configura retentativas exponenciais no commit da tabela
ALTER TABLE prod.trusted.vendas SET TBLPROPERTIES (
  'commit.retry.num-retries' = '15',
  'commit.retry.min-wait-ms' = '100',
  'commit.retry.max-wait-ms' = '5000'
);
  • Isolamento de Operações e Lock Manager: Para catálogos compartilhados com altíssima concorrência (como Apache Hive ou Glue Data Catalog), ative mecanismos de Lock no Spark se estiver rodando transações ACID complexas que exigem consistência forte, ou separe a escrita de dados brutos por partição temporal isolando os caminhos de escrita (ex: partições por hora).
  • Compactação Assíncrona: Evite executar compactação de arquivos pequenos (OPTIMIZE) na mesma transação e janela horária de escrita de dados novos. Programe jobs de compactação assíncronos que rodem em horários de baixo tráfego operacional analítico.
Questão 30 · Amazon Redshift Serverless

Como funciona o mecanismo de auto-scaling de concorrência (Concurrency Scaling) do Amazon Redshift Serverless e como o uso inadequado do comando COPY a partir do S3 com arquivos mal-distribuídos pode anular o paralelismo dos slices de computação (Slices Skew)?

Concurrency Scaling no Redshift: O Redshift Serverless dimensiona dinamicamente a computação adicionando recursos adicionais de processamento (clusters transitórios) sob concorrência pesada de leitura. No entanto, na fase de gravação e ingestão via comando COPY, a concorrência e o paralelismo dependem estritamente da estrutura física dos arquivos a serem ingeridos do S3.

O gargalo de Slice Skew na ingestão COPY:
  • Ingestão Sem Divisão (Single File Gzip): Se dispararmos um COPY de um único arquivo compactado gigante de 100 GB em formato Gzip (dados_vendas.csv.gz), o Redshift será incapaz de dividir o arquivo e ler em paralelo. Apenas um único slice de computação no cluster trabalhará descompactando e gravando os registros, enquanto os demais slices ociosos aguardam, gerando lentidão extrema (slice skew).
  • Melhor Prática de Divisão (Split Files): Divida os arquivos de dados na origem no S3 em múltiplos fragmentos comprimidos de tamanhos uniformes e idênticos (ex: 20 arquivos de 5 GB em vez de 1 de 100 GB), com uma quantidade correspondente a um múltiplo do número de compute slices do seu cluster de destino. O comando COPY acionará todos os slices do cluster para carregar cada arquivo em paralelo de forma direta e instantânea.
Questão 34 · Amazon Athena Federated Query

Como desenhar e otimizar uma arquitetura de consultas federadas (Federated Query) com Amazon Athena usando conectores Lambda para realizar joins entre o S3 Data Lake e bancos transacionais RDS/DynamoDB sob restrições de tempo de execução (timeouts) e custos?

Mecanismo Athena Federated Query: O Athena utiliza conectores pré-construídos executados no AWS Lambda (comunicação baseada em Apache Arrow) para ler metadados e schemas de sistemas não catalogados diretamente no Glue. O Athena compila a query SQL analítica e converte o acesso ao RDS/DynamoDB em invocações Lambda paralelas. O Lambda busca as linhas correspondentes e devolve batches de dados colunares diretamente ao Athena, que realiza o join final na memória da engine analítica Presto/Trino.

Soluções de Otimização e Segurança:
  • Predicate Pushdown (Pushdown de Predicados): Garanta que o conector do Athena empurre as cláusulas WHERE diretamente para a consulta executada pelo Lambda no banco de dados relacional. Sem pushdown, o Lambda tentaria puxar tabelas inteiras do RDS (ex: 50 GB de dados) sobre a rede para o Athena, gerando custos catastróficos de tráfego NAT, saturação da CPU do RDS e estourando o timeout físico de 15 minutos do Lambda.
  • Limitação e Pruning de Colunas: Evite queries analíticas com SELECT * em consultas federadas. Selecione apenas as colunas necessárias para reduzir a carga de serialização Apache Arrow nos contêineres Lambda do conector.
  • Caching com DynamoDB e Athena: Para buscas federadas frequentes contra dados que mudam pouco (ex: tabelas de CEP ou catálogos de produtos no DynamoDB), ative o cache de resultados analíticos de metadados e registros no conector Lambda (configurando a variável de ambiente metadata_caching_ttl do conector) ou materialize o join no S3 de forma agendada para evitar invocações repetidas de APIs.
Questão 41 · Athena & Lake Formation Performance

O que motiva a lentidão catastrófica no Query Planning Time do Amazon Athena em tabelas do Datalake protegidas com Lake Formation (Cell-Level Security), e como a evolução do stack arquitetural contorna essa debilidade?

Causa Raiz de Lentidão em Segurança Granular: Quando as proteções de linhas e colunas (Cell-Level Security) do Lake Formation estão habilitadas, o Athena não pode mais injetar credenciais e fazer o plano de consulta direto. O Lake Formation assume o fluxo, atuando como um "filtro" avaliador. Para cada query, o LF precisa listar os arquivos de dados brutos e calcular intersecções complexas de ACL na camada de planejamento. Em tabelas particionadas no formato Glue/Hive, onde existem dezenas de milhares de micro-pastas (s3://.../ano=2024/mes=01/), o motor satura a API do Glue e o planejamento (que deveria levar 0,5s) chega a estourar 30s a 120s antes que um único byte seja lido do S3.

Ação Corretiva em Alta Escala:
  • Conversão para Formatos Transacionais Abertos (Apache Iceberg): O Apache Iceberg elimina completamente as lentas varreduras hierárquicas da API do AWS Glue Catalog (que causa o estrangulamento do Lake Formation). O Iceberg concentra os apontamentos físicos das partições ativas dentro do S3 na forma de arquivos de manifestos compactos. Assim que a tabela transiciona para Iceberg, o Lake Formation e o Athena extraem os metadados diretamente do manifesto no S3. Isso resulta em um Query Planning de latência estável quase ignorável, permitindo aplicação massiva de segurança por coluna sem destruir a performance interativa.
Questão 52 · Data Modeling & Athena Performance

Por que queries analíticas executando Joins em tabelas modeladas em Star Schema apresentam sérios gargalos no Amazon Athena, e como a desnormalização OBT (One Big Table) contorna esse limite?

Gargalo do Presto/Athena: O Amazon Athena é serverless e não possui índices de banco de dados ou chaves estrangeiras físicas. Para executar um Join de Star Schema (tabela Fato enorme com múltiplas tabelas Dimensão pequenas), o Athena precisa ler todos os arquivos Parquet de todas as tabelas no S3, carregar em memória e fazer shuffles de rede gigantescos para mesclar os dados na hora da query.

A Abordagem OBT (One Big Table):

Desnormalizar todos os campos descritivos diretamente na tabela fato durante a gravação Silver->Gold elimina a necessidade de fazer Joins em tempo de consulta. O Athena executará leituras diretas em arquivos Parquet únicos. Devido à compressão por coluna (Parquet/ZSTD), o custo extra de armazenar dados repetidos é mínimo, enquanto a query executa até 10 vezes mais rápido, reduzindo drasticamente o volume de dados escaneados e o custo por query.

Questão 60 · DynamoDB Sizing & Particionamento

Dada uma tabela DynamoDB de 35 GB de dados com pico de tráfego de 4.500 WCUs e 8.000 RCUs (leituras fortemente consistentes), calcule o número exato de partições físicas alocadas e o rendimento (throughput) resultante por partição.

Desafio Técnico: A performance do DynamoDB é horizontal e dividida igualmente entre as partições baseando-se em limites físicos. Um dimensionamento incorreto pode induzir a erros de ProvisionedThroughputExceededException.

Resolução Matemática do Especialista:

Para determinar o número de partições, utilizamos as restrições físicas de capacidade (1.000 WCU / 3.000 RCU por partição) e tamanho (10 GB por partição):

  • Fórmula de Capacidade: Partições_Capacidade = (8.000 RCU / 3.000) + (4.500 WCU / 1.000) = 2.67 + 4.5 = 7.17 partições
  • Fórmula de Armazenamento: Partições_Armazenamento = 35 GB / 10 GB = 3.5 partições
  • Total de Partições Físicas: Teto( Max(7.17, 3.5) ) = Teto(7.17) = 8 partições físicas
  • Capacidade Efetiva por Partição:
    • RCU por partição: 8.000 / 8 = 1.000 RCUs
    • WCU por partição: 4.500 / 8 = 562.5 WCUs

Se o tráfego de leitura de um único item/ID (Hot Key) ultrapassar 1.000 RCUs em um segundo, a requisição sofrerá Throttling, mesmo que os outros 7.000 RCUs globais da tabela estejam ociosos.

Questão 63 · Amazon Aurora Replica Lag & Read Scaling

Como mitigar gargalos de performance e isolar o tráfego operacional (OLTP) de gravação durante extrações analíticas massivas no Amazon Aurora PostgreSQL?

Desafio de Concorrência: Consultas analíticas pesadas (Full Table Scans) concorrendo com gravações na instância primária (Writer) geram locks de páginas de banco de dados e saturação de I/O de disco.

Estratégia Arquitetural de Ingestão:
  • Leitura via Reader Endpoint com Autoscaling: Aponte o pipeline analítico (JDBC Spark) estritamente para o Reader Endpoint do Aurora. Configure o auto-scaling do cluster Aurora com base na utilização média de CPU dos nós leitores. À medida que o job analítico inicia, réplicas adicionais são ligadas dinamicamente e as conexões balanceadas em round-robin.
  • Minimização de Lag de Réplica: Devido à arquitetura de armazenamento compartilhado do Aurora (Aurora Storage Volume), as réplicas analíticas não processam gravações físicas de dados nos seus discos. No entanto, elas devem atualizar seus caches locais na memória RAM com os logs de transação da Writer. Monitore a métrica AuroraReplicaLag e garanta que queries pesadas não mantenham transações abertas por longos períodos, o que impediria a réplica de atualizar sua memória (gerando lag artificial).
Questão 67 · Apache Iceberg WAP (Write-Audit-Publish) Pattern

Como funciona o padrão arquitetural WAP (Write-Audit-Publish) no Apache Iceberg e como as branches lógicas da tabela previnem a ingestão de registros órfãos ou inválidos na camada final de Serving?

Gargalo Operacional: Em pipelines analíticos tradicionais (Hive/Parquet puro), se um erro de qualidade de dados ocorrer no final de uma transação batch de 10 milhões de registros, a tabela física já estará modificada, forçando reversões complexas (rollbacks em S3) ou poluindo relatórios ativos de BI.

Arquitetura e Fluxo do WAP:
  • Write (Escrever na Branch): O pipeline PySpark ou dbt grava as alterações apontando para uma branch lógica temporária da tabela Iceberg (ex: df.option("branch", "wap_temp").save(...)). Os dados físicos são salvos no S3, mas o snapshot principal (main branch) da tabela continua inalterado.
  • Audit (Auditar): Ferramentas de validação ativa ou queries SQL rodam contra a branch temporária buscando quebras de contratos de dados (valores negativos, nulos em PKs).
  • Publish (Publicar via Fast-Forward): Se os testes passarem, a engine executa uma chamada de sistema (ex: CALL system.cherry_pick_snapshot()) para avançar a referência da branch main para o snapshot validado. Caso contrário, a branch temporária é descartada, impedindo a exposição dos dados inválidos.
Questão 69 · Rateio de Custos Athena & FinOps

Como gerenciar de forma transparente e auditar financeiramente queries concorrentes em um Data Lake multi-departamento no Amazon Athena para ratear a fatura de faturamento final (AWS CUR)?

Desafio de Auditoria: Se todos os departamentos (Marketing, Financeiro, Ciência de Dados) rodarem consultas analíticas sob o mesmo Workgroup padrão (primary), a AWS gerará uma única cobrança consolidada, impedindo a rastreabilidade e o rateio de custos.

Solução Arquitetural de FinOps:

Divida a infraestrutura lógica do Athena criando Workgroups específicos para cada centro de custo. Associe tags IaC exclusivas a esses grupos de trabalho no Terraform. As queries executadas herdam essas tags, que são propagadas de forma granular para o AWS Cost and Usage Report (CUR). Utilizando queries SQL no Athena sobre o CUR, é possível extrair o volume de dados escaneados (QueryBytes) agrupado pelo nome do Workgroup, calculando a fatura exata de cada time de forma dinâmica e automatizada.

Questão 71 · Apache Iceberg Concorrência & CommitFailedException

Durante escritas simultâneas de pipelines de streaming (Flink/Spark) e jobs batch de compactação periódica na mesma tabela Apache Iceberg no S3, o Spark lança frequentemente CommitFailedException. Como funciona o Controle de Concorrência Otimista (OCC) do Iceberg e como mitigar estes erros em produção?

Mecanismo de Conflito de Commit: O Apache Iceberg utiliza **Controle de Concorrência Otimista (OCC)**. Quando um escritor tenta commitar um novo Snapshot, ele lê os metadados mais recentes, cria as alterações físicas no S3 e tenta atualizar o ponteiro do metadado atual (via DynamoDB lock ou Glue Catalog). Se outro escritor (ex: compactação de arquivos) commitar um snapshot antes, o escritor atual falha se houver sobreposição nos dados alterados.

Ações de Resolução de Conflitos:
  • Isolamento de Snapshot (Snapshot Isolation): Configure a operação de compactação para rodar sem conflitar com novas inserções. Como a compactação apenas reorganiza arquivos físicos sem alterar o conteúdo lógico dos dados, ela pode ser commitada com segurança se o Iceberg souber resolver merge de arquivos de metadados concorrentes de append.
  • Políticas de Retry Automático: Ajuste as propriedades de retry da tabela Iceberg para dar tempo aos escritores de tentarem novamente após falhas concorrentes:
    • commit.retry.num-retries: Aumente para 20 ou 30 tentativas.
    • commit.retry.min-wait-ms e commit.retry.max-wait-ms: Configure backoff exponencial para evitar sobrecarga no catálogo de metadados.
  • Segregação por Partições: Garanta que os fluxos concorrentes estejam escrevendo em partições físicas diferentes da tabela, permitindo que a engine resolva os commits sem conflitos lógicos diretos.
Questão 78 · Star Schema vs. Snowflake no Amazon Redshift

Ao projetar um Data Warehouse corporativo no Amazon Redshift, qual arquitetura de modelagem de dados é preferível entre Star Schema e Snowflake Schema, e qual o impacto dos Joins na execução distribuída do cluster?

Gargalo de Processamento Distribuído: O Amazon Redshift é um banco de dados Massivamente Paralelo (MPP). Em queries distribuídas, realizar joins exige que as fatias de dados de diferentes nós computacionais sejam redistribuídas pela rede (Data Shuffle) para que os registros correspondentes sejam pareados na memória física.

Estratégia Recomendada para o Redshift:
  • Preferência pelo Star Schema: O **Star Schema é amplamente preferido** em relação ao Snowflake no Redshift. Por possuir dimensões desnormalizadas e achatadas, as queries analíticas exigem apenas um nível de join (Fato ➔ Dimensão). Isso diminui drasticamente a necessidade de shuffles de rede complexos e agiliza a execução da query.
  • O Problema do Snowflake no Redshift: No Snowflake, a normalização fragmenta os dados em múltiplas tabelas (Fato ➔ Cliente ➔ Cidade ➔ Estado). Queries analíticas básicas exigem joins em cascata. O otimizador de plano do Redshift precisará mover dados de várias dimensões entre nós para resolver a query, gerando congestionamento na rede interna do cluster.
  • Otimização com Chaves de Distribuição: No Star Schema, configure a chave de distribuição (DISTKEY) da tabela Fato e da maior dimensão (ex: Cliente) com o mesmo campo ID. O Redshift executará o join localmente sem mover dados de nó em nó. Para as demais dimensões menores (como Tempo e Categoria), use DISTSTYLE ALL para clonar as tabelas em todos os nós, garantindo joins de latência zero.
Questão 80 · One Big Table (OBT) e Queries de Alta Performance no Athena

Por que a modelagem desnormalizada completa em uma única tabela analítica gigante (One Big Table - OBT) superou o uso de Star Schema e Snowflake Schema no S3/Athena, e qual o impacto financeiro e de CPU dessa abordagem?

Desafio Serverless de Consultas S3: O Amazon Athena é uma engine baseada em Presto/Trino que executa queries diretamente em arquivos colunares (Parquet/ORC) salvos no Amazon S3. Diferente de um banco de dados tradicional com discos SSD locais rápidos, a leitura física de dados no Athena envolve latência de rede HTTP para cada requisição ao S3.

Vantagens Computacionais e Financeiras de OBT no Athena:
  • Eliminação Total de Joins e Shuffles: Em um Star Schema, a query Athena precisa ler os arquivos da tabela Fato e de todas as Dimensões no S3, carregar os dados na memória RAM dos nós do Athena e executar a junção de dados. Em OBT, todos os atributos descritivos já estão desnormalizados fisicamente na mesma linha de dados do arquivo. O Athena lê um único caminho de arquivo do S3 e executa filtros diretos sem gastar CPU ou tempo executando joins de rede.
  • Mitigação do Custo de Armazenamento Via Parquet/ZSTD: Embora a OBT tenha alta redundância (duplicando strings de nomes de clientes ou produtos milhões de vezes), os formatos de armazenamento colunares (como Parquet) organizam os dados por coluna e aplicam algoritmos de compressão pesados (Snappy ou ZSTD). Strings repetidas consecutivamente são comprimidas a frações mínimas do tamanho original. O custo de armazenamento extra no S3 é quase irrelevante frente ao ganho em performance analítica.
  • Economia Financeira de Querying: O Athena cobra pelo volume de dados escaneado no S3. Como a OBT é salva em formato colunar Parquet, se uma query ler apenas colunas como valor_venda e nome_cliente, o Athena lerá apenas as colunas solicitadas, varrendo muito menos dados do S3 em comparação a varrer tabelas inteiras em joins, gerando queries até 10x mais rápidas e baratas.
Questão 82 · Padrão Write-Audit-Publish (WAP) com Apache Iceberg

Como o padrão Write-Audit-Publish, possibilitado por formatos de tabela como Apache Iceberg, evita que dados mal formatados poluam a camada Gold (apresentação) do Data Lake e interfiram nos dashboards?

O Problema da Gravação Suja: Historicamente, os jobs do Spark escrevem os dados diretamente na tabela final. Se o job falhar pela metade ou carregar dados nulos acidentalmente, os dashboards apontados para essa tabela apresentarão dados inconsistentes aos usuários de negócio antes que o time de dados perceba o problema.

O Pipeline Seguro (Branching Analítico):
  • Write (Escrever): O job de ETL do Spark não escreve diretamente na branch principal. Ele cria e escreve os dados em uma ramificação oculta de auditoria no Iceberg (ex: `branch_audit_etl`). Os dashboards do QuickSight ou Tableau conectados no Athena apontam para a branch `main` e continuam lendo os dados de ontem com performance normal.
  • Audit (Auditar): Um job secundário de Data Quality (ex: usando Great Expectations ou Glue Data Quality) é acionado para varrer apenas a `branch_audit_etl`, aplicando regras como limiares estatísticos (standard deviation) e limites nulos.
  • Publish (Publicar): Apenas se a auditoria passar com sucesso, uma operação (stored procedure) atômica do Iceberg `fast_forward` transfere e torna os dados dessa branch visíveis na branch `main`. Toda a transição leva milissegundos e elimina a janela de inconsistência de dados.
Questão 89 · Athena e o Paradoxo do "Small Files Problem"

Ao orquestrar um pipeline puramente baseado em SQL no Amazon Athena para transformar dados brutos em Parquet no Lakehouse, por que um loop de `INSERT INTO` destrói a latência de leitura, e como o `CTAS` resolve o problema arquiteturalmente?

Cenário: Um engenheiro agendou uma rotina que executa `INSERT INTO tb_gold SELECT * FROM tb_silver WHERE data = hoje` a cada 5 minutos. Após 1 semana, o dashboard do QuickSight que lia a `tb_gold` passou a demorar 40 segundos para renderizar, mesmo filtrando apenas 1 dia de dados.

Diagnóstico e Ação (Motor Trino):
  • A Causa Física (I/O Overhead): O INSERT INTO no Athena anexa diretamente os resultados ao diretório S3 da tabela. Executar a query a cada 5 minutos gera 288 pequenos arquivos (alguns KBs) por dia. O motor gasta 90% do tempo negociando handshakes TLS e abrindo cabeçalhos HTTPs no S3, e apenas 10% lendo os dados.
  • A Solução CTAS (Create Table As Select): Em cenários de consolidação, usamos o CTAS para ler todos os micro-arquivos da tb_silver e recriar a tabela particionada. A Engine Trino paraleliza a escrita na memória dos workers e unifica o resultado final em blocos gigantes de Parquet (128MB+), curando instantaneamente a performance do QuickSight.
Questão 90 · Redshift Managed Storage (RA3) e Custos Operacionais

Qual o argumento financeiro e de governança para convencer um CTO a migrar Clusters Redshift on-premise style (DS2/DC2) para a família RA3 com Data Sharing, quando a empresa possui 5 squads diferentes consumindo e copiando dados uns dos outros?

Cenário: Equipes de Marketing, Risco, Finanças e Vendas rodam complexos pipelines (AWS Glue) toda madrugada apenas para copiar tabelas do "Cluster Core" para seus próprios "Clusters Departamentais", encarecendo a conta da AWS e gerando dessincronia (dados velhos).

A Solução (Storage Desacoplado):
  • Dissociação Paga Apenas o Necessário: Em DC2 (acoplado), escalar o disco para armazenar mais histórico obrigava a pagar por caríssimos chips de CPU adicionais ociosos. No RA3, os dados pesados moram fisicamente no S3 (preço ínfimo de centavos por GB), mantendo a CPU dimensionada apenas para a força da query.
  • Morte do ETL de Cópia via Data Sharing: Com o RA3, o Storage reside no S3. Isso permite habilitar o Data Sharing. O Cluster de Marketing pode ler a tabela de Vendas ao vivo, utilizando apenas o próprio poder computacional de Marketing, sem que o pipeline precise mover um único byte fisicamente, eliminando a fatura do AWS Glue e a obsolescência de dados.
Questão 95 · Amazon Athena, Parquet e Explosão de Custos por Scans Ineficientes (Staff Level)

Um time de BI utiliza o Amazon Athena para consultar tabelas do S3 armazenadas em Parquet (comprimidas em Snappy). Apesar do Parquet ser colunar, o custo na fatura da AWS atingiu níveis críticos, e as métricas do Athena mostram dezenas de Terabytes sendo "escaneados" diariamente para consultas simples que retornam poucas linhas. O que causa varreduras excessivas em formatos colunares e como corrigir definitivamente?

Cenário: Os engenheiros implementaram Particionamento por `ano/mes/dia`, as consultas possuem os filtros `WHERE data_particao = ...`, e as querys selecionam apenas 3 colunas em vez de `SELECT *`. Mesmo assim, os scans estão gigantescos.

Diagnóstico e Ação (Small Files, Block Sizes e Predicate Pushdown Oculto):
  • A Causa Física (Distorção do Footer do Parquet): Se um ETL rodando em Spark (ou Kinesis Firehose) gerar 10.000 pequenos arquivos de 100KB dentro da partição de hoje, o Athena (Trino) precisa abrir a rede para ler o Footer/Metadata de todos esses arquivos (para encontrar onde estão os blocos das 3 colunas). O S3 e o Athena faturam baseados em um limite mínimo de cobrança por arquivo lido (10MB). Consultar 10.000 arquivos de 100KB faz o Athena faturar como se fossem lidos 100 GB (10.000 * 10MB mínimos). Outro problema: Mesmo em arquivos grandes, se a coluna da cláusula WHERE cliente_id = 999 não estiver ordenada fisicamente antes de escrever no S3, o Athena terá que varrer todos os RowGroups do arquivo Parquet, pois o arquivo não contém estatísticas (Min/Max values) otimizadas nos blocos para um descarte rápido.
  • A Mitigação Estrutural (Compactação e Ordenação no S3): Implementar uma rotina de Compaction diária (usando AWS Glue ou um CTAS do próprio Athena) para consolidar milhares de pequenos arquivos em grandes blocos ideais (~128MB a 512MB). Mais importante ainda: Na escrita compactada, aplicar um ORDER BY (colunas_mais_filtradas) no momento de gerar o Parquet. Isso otimiza os metadados do Parquet (Estatísticas de Min/Max por chunk), habilitando o motor Trino a dar um "Skip" limpo nos blocos físicos inteiros do S3 pela rede sem baixar seus dados, garantindo assim um Predicate Pushdown perfeito e estancando a sangria financeira.
Questão 96 · Redshift RA3, Data Sharing e Estrangulamento de Concorrência (Staff Level)

Sua empresa consolidou dezenas de Terabytes no Amazon Redshift (família RA3) adotando o "Managed Storage". Durante a madrugada, longos processos de ETL de Ingestão saturam os Compute Nodes. Ao mesmo tempo, o time de engenharia global e analistas tentam visualizar os dashboards no QuickSight. A infraestrutura inteira sofre lentidão severa. Como isolar perfeitamente a computação mantendo "Single Source of Truth"?

Cenário: Você deseja parar as filas de "Noisy Neighbors". A diretoria descarta mover os dados lidos para bancos relacionais e exige usar o Redshift DW.

Diagnóstico e Ação (Desacoplamento Arquitetural de CPU):
  • A Causa Física (Acoplamento de Concorrência Clássico): Embora o Redshift RA3 desacople o Storage (guardando dados frios no S3 RMS e caches no SSD local), as cargas de trabalho (ETLs e leituras Ad-Hoc) ainda competem violentamente pelo mesmo cluster Leader e pelos mesmos Slices do Compute Node. Mesmo com o AutoWLM ou Concurrency Scaling ativados, um volume massivo de Ingestões DML (INSERT/UPDATE/COPY) engasga o pipeline da fila, exigindo IOPS intensos no EBS local e travando a CPU que o QuickSight depende.
  • A Mitigação Estrutural (Redshift Data Sharing Producer/Consumer): A estratégia de Staff Engineer é criar um ambiente Multi-Cluster sem copiar os dados. Você mantém o cluster RA3 original dedicado puramente à gravação e transformações intensas (o Cluster "Produtor"). Você então provisiona um segundo cluster Redshift (ou até um Redshift Serverless Pay-Per-Query) atuando como "Consumidor", focado em Servir Dashboards. Através da funcionalidade nativa Redshift Data Sharing, o Cluster Consumidor lê logicamente as tabelas do Produtor direto do Managed Storage via rede ultra rápida da AWS, gerando "Zero Cópias de Dados". A CPU e o Cache Local do Cluster Produtor ficam 100% livres de usuários do QuickSight, garantindo SLAs rigorosos e alta segurança.
Questão 97 · Amazon Aurora, Failover Drops e Connection Pooling (Staff Level)

Sua arquitetura utiliza Amazon Aurora Serverless v2 e ECS com microsserviços pesados. Durante uma manutenção preventiva da AWS (Failover do Writer para um Reader), a aplicação falhou em redirecionar o tráfego instantaneamente, derrubando transações de clientes por 30 a 60 segundos com erros de DNS "Connection Refused". Como você projetaria a resiliência perfeita (Zero-Drop) para o banco de dados nesse tipo de evento?

Cenário: O banco de dados Aurora em si realizou o failover muito rapidamente, mas a camada aplicacional demorou a se recuperar, causando impacto sensível à experiência do cliente (UX).

Diagnóstico e Ação (Failover Transparente via Proxy):
  • A Causa Física (TTL de DNS e TCP Drops): O Aurora Cluster promove uma réplica de leitura (Reader) a nó mestre (Writer) em cerca de 3 a 5 segundos. O problema está no cliente (ECS/Lambdas): eles possuem um cache local de DNS e conexões TCP (Socket) físicas abertas apontando para o IP antigo da máquina que caiu. Quando o nó antigo morre, os pacotes TCP caem num buraco negro (Blackhole). As linguagens/drivers padrões demoram dezenas de segundos para dar timeout e re-resolver o Endpoint DNS do Cluster para descobrir o novo IP da réplica promovida.
  • A Mitigação Estrutural (RDS Proxy + Smart Drivers): Um Engenheiro Staff insere o Amazon RDS Proxy entre a aplicação e o Aurora. A aplicação conecta no Proxy (que nunca cai). Quando ocorre um Failover, o Proxy mantém a conexão com a aplicação aberta (Multiplexing), enquanto rapidamente derruba a rota do backend comutada e transfere o tráfego interno para o novo Writer em milissegundos, evitando que a aplicação sequer perceba a troca de IP físico. Em paralelo, pode-se usar o AWS Advanced JDBC Driver que detecta ativamente topologias do cluster sem depender de TTL de DNS.
Questão 98 · DynamoDB Throttling & Hot Partitions (Staff Level)

O dashboard global do Amazon DynamoDB mostra que sua tabela "Pedidos" está configurada com 10.000 WCUs (Write Capacity Units) provisionados. Durante a Black Friday, você injetou 2.500 gravações por segundo e a tabela estourou com erros `ProvisionedThroughputExceededException`. Como isso é possível se você estava usando apenas 25% da sua capacidade WCU contratada?

Cenário: Ao investigar a Partition Key (PK), você nota que ela foi modelada usando o campo `data_compra` (ex: `2026-11-27`). As Sort Keys (SK) usavam o `id_pedido`.

Diagnóstico e Ação (Hash Sharding e Modelagem NoSQL):
  • A Causa Física (Partition Math e Hot Partitions): O DynamoDB não aloca o WCU como uma pool mágica universal. Fisicamente, a tabela é dividida em nós de armazenamento de ~10GB. A AWS divide a sua capacidade total (10.000 WCU) igualmente entre essas partições. Digamos que a tabela tenha 10 partições internas: cada partição tem um teto de 1.000 WCU. O DynamoDB usa a Partition Key (PK) e aplica um algoritmo Hash (MD5 interno) para determinar em qual partição o dado cai. Como a PK era apenas a `data_compra`, todos os 2.500 pedidos daquele mesmo dia possuíam o mesmo valor e o mesmo Hash. Consequentemente, todo o tráfego do Brasil foi afunilado para uma única partição física minúscula de 1.000 WCU (Hot Partition), causando o Throttling imediato, enquanto as outras 9 partições ficaram ociosas com 0 tráfego.
  • A Mitigação Estrutural (Write Sharding e Randomization): A chave de partição deve ter alta cardinalidade. O Engenheiro Staff corrige o design mudando a PK para algo verdadeiramente disperso, como `id_cliente` ou um UUID. Se for absolutamente necessário consultar por data no padrão de acesso de escrita pesada, você anexa um sufixo aleatório à data (`2026-11-27_01`, `2026-11-27_02` até N), uma técnica conhecida como Write Sharding, espalhando artificialmente o evento sobre as várias partições da AWS.
Questão 99 · Transição de Relacional para NoSQL (Single-Table Design) (Staff Level)

Sua equipe precisa migrar um banco de dados Relacional contendo Tabelas `Clientes` e Tabela `Faturas` com chave estrangeira. No MySQL, obter as faturas do cliente era um `JOIN` simples. No Amazon DynamoDB, as operações de JOIN não existem. Como você estruturaria essa entidade dupla fisicamente para garantir acesso em O(1) e consistência total?

Cenário: Muitos engenheiros inexperientes tentariam criar duas tabelas distintas no DynamoDB (`TabelaCliente`, `TabelaFatura`), forçando a camada da aplicação (Lambda/ECS) a fazer queries consecutivas para juntar os dados na memória (Application-level JOIN), destruindo o limite de rede e violando as práticas do Dynamo.

Diagnóstico e Ação (Single-Table Design via Empilhamento PK/SK):
  • A Solução Física (Coleções de Itens Empilhados): Para substituir os JOINs com eficiência O(1), adotamos o padrão Single-Table Design. Criamos apenas uma única Tabela no DynamoDB. Definimos a PK genérica como `PK` e a Sort Key como `SK`.
  • A Mitigação Estrutural:
    1. Inserimos o cliente assim: `PK = CLIENTE#100` e `SK = PERFIL#100`. Os atributos dessa linha contêm Nome e Email.
    2. Inserimos a fatura do cliente assim: `PK = CLIENTE#100` e `SK = FATURA#A1` (Valor R$ 50). Outra fatura como `SK = FATURA#B2`.
    3. Quando a API precisar do "JOIN", ela realiza um simples `Query` na tabela pedindo onde `PK = CLIENTE#100`. Como a PK é idêntica para o Perfil e para as Faturas, o motor SSD local do DynamoDB agrupa esses itens no mesmo bloco físico contíguo no disco. A query retorna o Cliente e todas as Faturas na mesma requisição com latência milissegunda perfeita.
