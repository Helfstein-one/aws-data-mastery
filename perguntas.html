Questão 1 · Apache Kafka

O que provoca o "Rebalance Storm" (Tempestade de Rebalanceamento) e como resolver esse travamento no Consumer Group?

Funcionamento Interno: O rebalanceamento ocorre quando o broker coordenador do Kafka detecta que um consumidor do grupo parou de enviar sinais de vida (Heartbeats) ou demorou mais que o limite configurado (max.poll.interval.ms) para processar o lote de mensagens retornado pela chamada poll(). O broker marca a máquina como morta, revoga as partições a ela designadas e as distribui para outras máquinas. Se o atraso no processamento era devido a lentidão de banco ou volume de lote, a próxima máquina também estourará o limite ao herdar o lote pesado, gerando um loop de rebalanciamentos em cadeia (o storm).

Troubleshooting em Entrevista:
  • Sintoma: O lag cresce indefinidamente e a CPU dos consumidores oscila em picos, mas a vazão cai para quase zero.
  • Ação Corretiva: Reduza o tamanho do lote puxado configurando um valor menor em max.poll.records (ex: de 500 para 50) e aumente o tempo limite de tolerância em max.poll.interval.ms (ex: para 10 minutos). Isso dá tempo suficiente para o loop processar os registros sem ser expulso pelo Broker.
Questão 2 · Apache Spark

Como funciona fisicamente o Sort-Merge Join em relação ao Broadcast Hash Join sob o ponto de vista de rede (Shuffle)?

Funcionamento Interno: No Sort-Merge Join (SMJ), o Spark executa um shuffle completo das duas tabelas. Ele lê os dados de todos os nós, calcula o hash da chave do join e transfere os registros correspondentes pela rede para que caiam no mesmo executor. Em seguida, os dados são ordenados em memória e mesclados. É o join mais seguro para tabelas gigantes, mas gera gargalo pesado de rede (Shuffle Write/Read).

No Broadcast Hash Join (BHJ), o Spark pula completamente o shuffle. O Driver copia a tabela menor inteira, cria uma tabela hash em memória e a envia (broadcast) via rede para todos os executores que estão processando as partições da tabela gigante. O join ocorre localmente em memória sem movimentar a tabela gigante.

Cenário de Entrevista:

Você tem uma tabela Fato de Vendas (1 TB) e uma tabela Dimensão de Categoria (20 MB). Se o Spark escolher Sort-Merge por falta de estatísticas, a query demorará horas. Forçamos o Broadcast para evitar o shuffle:

from pyspark.sql.functions import broadcast

# Forçando o Broadcast da tabela pequena (dimensao)
df_final = df_fato_vendas.join(broadcast(df_dim_categoria), "id_categoria", "inner")

Ressalva de Entrevista: Cuidado para não fazer broadcast de tabelas maiores do que a memória disponível no Driver ou nos Executors, pois isso gerará erro de OutOfMemory (OOM).

Questão 3 · dbt (data build tool)

Como lidar com "Late-Arriving Data" (Dados Atrasados) em tabelas incrementais sem reprocessar o Datalake inteiro?

Problema Conceitual: Em modelos incrementais do dbt, usamos filtros para capturar apenas dados novos (ex: data_criacao > (select max(data_criacao) from this)). Se um evento que ocorreu há 5 dias chegar com atraso hoje devido a uma instabilidade no app de origem, esse filtro simples o ignorará, gerando inconsistência histórica nas métricas agregadas.

Solução via dbt (Janela de Lookback):

Configuramos uma janela de retrocesso temporal no filtro incremental. O dbt reprocessará os últimos 3 dias para capturar atrasos comuns e executará um MERGE com base nas chaves primárias:

# models/silver_sales.sql
{{ config(
    materialized='incremental',
    unique_key='id_venda',
    incremental_strategy='merge'
) }}

SELECT * FROM {{ ref('raw_sales') }}
{% if is_incremental() %}
  -- Captura dados novos E dados que chegaram atrasados nos últimos 3 dias
  WHERE data_insercao >= (SELECT DATE_ADD(max(data_insercao), -3) FROM {{ this }})
{% endif %}
Questão 4 · Amazon Athena

Como resolver o erro "Metadata limit exceeded" ou queries Athena que falham por timeout antes de iniciar o scan dos dados?

Causa Física: Quando o Athena executa uma query em uma tabela particionada convencional (ex: particionada por ano/mes/dia/cliente), ele precisa fazer chamadas de API para o AWS Glue Data Catalog para listar os arquivos físicos correspondentes às partições solicitadas. Se a tabela tem milhões de partições, a fase de planejamento da query excede os limites de limite de API do Glue e gera timeout antes do processamento dos dados começar.

A Solução Suprema: Partition Projection

O Partition Projection armazena as regras de geração das partições diretamente como propriedades da tabela no Glue Catalog (ex: ano varia de 2020 a 2026). O Athena calcula em memória os caminhos físicos do S3 baseando-se nas datas passadas no filtro SQL, ignorando completamente as chamadas de API do catálogo e eliminando o timeout.

-- Exemplo de registro de tabela Athena com Partition Projection configurado
CREATE EXTERNAL TABLE sales_projected (
    id_venda string,
    valor double
) 
PARTITIONED BY (ano string, mes string)
LOCATION 's3://my-datalake/sales/'
TBLPROPERTIES (
    'projection.enabled' = 'true',
    'projection.ano.type' = 'integer',
    'projection.ano.range' = '2020,2026',
    'projection.mes.type' = 'integer',
    'projection.mes.digits' = '2',
    'projection.mes.range' = '1,12',
    'storage.location.template' = 's3://my-datalake/sales/ano=${ano}/mes=${mes}/'
);
Questão 5 · Segurança AWS

Como o AWS Lake Formation garante a segurança granular se o usuário final não tem acesso físico ao Bucket S3 no IAM?

Mecanismo de Credential Vending: Este é um conceito avançado de segurança. O usuário final (ou a role do Athena/EMR) tem permissões concedidas diretamente no Lake Formation (ex: acesso de leitura à coluna X da tabela Y). No entanto, a role do usuário não tem nenhuma permissão física de leitura (s3:GetObject) nas políticas do IAM associadas ao bucket S3 onde a tabela está salva.

Passo a Passo do Fluxo de Autenticação:
  1. O usuário executa a query SELECT coluna_permitida FROM tabela no Athena.
  2. O Athena envia a solicitação para o Lake Formation validando se o usuário possui essa permissão lógica.
  3. Se autorizado, o Lake Formation assume temporariamente uma Role de serviço interna que possui privilégios de leitura no bucket S3 físico.
  4. O Lake Formation gera credenciais temporárias de curto prazo (Credential Vending) e as entrega de volta ao motor do Athena.
  5. O Athena lê fisicamente os blocos de dados Parquet diretamente do S3 usando as credenciais temporárias concedidas, aplica os filtros de linha/coluna e retorna o resultado limpo para o usuário, bloqueando qualquer possibilidade de bypass.
Questão 6 · dbt (data build tool)

Qual a diferença prática das estratégias "timestamp" vs "check" no dbt Snapshots e como lidar com exclusões físicas de dados?

Conceito do dbt Snapshot: Usado para criar tabelas de histórico dimensional (SCD Tipo 2) a partir de tabelas mutáveis.

  • Estratégia Timestamp: O dbt monitora uma coluna de data de atualização (ex: updated_at). Se a data da origem for maior que a registrada, uma nova versão da linha é criada. É a estratégia mais performática e recomendada.
  • Estratégia Check: Usada quando a tabela de origem não possui data de modificação. O dbt compara o hash de colunas específicas (ou all) da tabela ativa contra a tabela histórica. Gera maior overhead de processamento.

Perguntado em Entrevista: E se um registro for excluído fisicamente no banco transacional (Hard Delete)?

Por padrão, o dbt Snapshot não invalida registros que sumiram da origem (mantém a linha antiga aberta sem data de fim). Para capturar exclusões físicas e fechar o histórico correspondente, configure a propriedade invalidate_hard_deletes=True no bloco de configuração do snapshot.

Questão 7 · Apache Spark

Como a memória do executor JVM do Spark é subdividida internamente e como debugar erros de OOM no User Memory vs Execution Memory?

Física da Memória Spark: A memória total (Executor JVM Heap) é subdividida em três grandes blocos controlados pelas propriedades de configuração do Spark:

  • Spark Memory (60% por padrão, via spark.memory.fraction): Subdividido dinamicamente entre Execution Memory (usado para shuffles, joins e agregações) e Storage Memory (usado para caching/persistence e transmissão de variáveis de broadcast).
  • User Memory (40% restante): Reservado para estruturas de dados do próprio usuário em código PySpark (UDFs Python, metadados internos de partições do Spark).
  • Reserved Memory: 300 MB fixos do Spark para garantir a execução estável do motor interno.

Caso de Debug em Processo Seletivo:

Se você receber OOM no User Memory, a causa provável é o uso de Python UDFs pesados sem otimização ou tentativa de processar metadados gigantes no driver. Resolva migrando UDFs Python puras para funções nativas da API DataFrame do Spark (Spark SQL) que rodam nativamente na JVM (otimizadas pelo compilador Catalyst).

Questão 8 · Segurança AWS

Por que utilizar a governança baseada em tags (LF-TBAC) no Lake Formation é superior a Named Resource Access em ambientes com milhares de tabelas?

Limitação de Named Resources (RBAC): Em ambientes corporativos gigantes, conceder acesso apontando explicitamente para o nome do banco e da tabela (ex: GRANT SELECT ON db.tabela1 TO role) gera uma explosão de políticas de acesso. É impossível manter, auditar e escala esse modelo para 10.000 tabelas.

Funcionamento da Governança baseada em Tags (TBAC):

O Administrador cria chaves de tags lógicas no Lake Formation (ex: tag Area=Financeiro, tag Sensibilidade=PII) e as vincula a bancos, tabelas ou colunas específicas. Em seguida, cria uma única regra lógica de acesso no Lake Formation: "A equipe de Contabilidade pode ler qualquer tabela que contenha a tag Area=Financeiro E Sensibilidade=Publico". Quando uma nova tabela do financeiro é criada pelo Glue Crawler, basta atribuir a tag para que as permissões de acesso sejam herdadas automaticamente, sem necessidade de atualizar nenhuma política do IAM ou concessões nominais.

Questão 9 · FinOps & S3

Em pipelines de streaming massivo de dados para o S3, como o custo de requisições de API (GET/PUT) pode superar o custo de armazenamento físico e como mitigar isso?

O Tradeoff Oculto de FinOps: O S3 cobra centavos por Gigabyte armazenado, mas cobra um valor fixo por 1.000 requisições PUT/POST ou 10.000 requisições GET/LIST. Se um pipeline de streaming escreve micro-arquivos no S3 a cada 5 segundos, o número de operações PUT gerará milhares de dólares na fatura AWS mensal, enquanto o espaço físico de armazenamento consumido seria ínfimo.

Como Otimizar em Escala de Produção:
  • Buffer temporal de escrita: Aumente o tamanho da janela de flush dos produtores (ex: Kinesis Firehose buffer de 5MB ou 120 segundos) para acumular eventos em memória e fazer um único PUT de arquivo maior, reduzindo o número absoluto de chamadas de API do S3.
  • Use formatos transacionais com manifestos: Formatos como o Apache Iceberg reduzem drasticamente as chamadas caras de listagem (LIST) do S3 usando ponteiros diretos em JSON nos arquivos de metadados para localizar os arquivos físicos Parquet de leitura, otimizando o custo de leitura analítica.

Questão 11 · Migração de Dados (CDC)

O que provoca latência de replicação (Source/Target Latency) em tarefas CDC do AWS DMS e como otimizar o processamento de colunas LOB?

Funcionamento de LOBs (Large Objects): Colunas contendo grandes cadeias de texto ou dados binários (JSON, CLOB, BLOB) degradam a replicação contínua do DMS.

  • Full LOB Mode: O DMS replica o registro normal e, em seguida, executa uma consulta cara de retorno na origem para extrair os dados da coluna LOB. Isso gera uma latência absurda de rede e banco em tabelas com alta concorrência.
  • Limited LOB Mode: O DMS aloca um buffer fixo em memória (ex: 32 KB) para ler os LOBs na mesma requisição de varredura. Dados de LOB maiores que o buffer configurado são truncados. É a opção de alta performance recomendada para produção.

Tuning no Target para Alta Vazão (Batch Apply):

Por padrão, o DMS executa instruções SQL uma a uma no banco de destino. Mude o parâmetro de processamento da tarefa para o modo Batch Apply (configuração BatchApplyEnabled = true) para acumular alterações e aplicá-las em transações em lote agrupadas, reduzindo a latência do Target.

Questão 12 · Teorema PACELC

Qual o tradeoff de consistência e latência (Teorema PACELC) ao escolher entre Aurora Global Database e DynamoDB Global Tables?

Entendendo o Teorema PACELC: Uma extensão do teorema CAP. Ele dita: Se houver uma partição de rede (P), escolha entre Disponibilidade (A) ou Consistência (C). Caso contrário (E - Else), escolha entre Latência (L) ou Consistência (C).

Tradeoffs em Entrevista Técnica:
  • DynamoDB Global Tables (Modelo PA/EL): Sob partições de rede, mantém a disponibilidade local alta (PA). Em estado normal, prioriza latências de escrita extremamente baixas em milissegundos nas regiões locais enviando replicações de forma assíncrona (EL), garantindo eventual consistência entre regiões distantes.
  • Aurora Global Database (Modelo PC/EC): Sob partições, pode parar escritas na região secundária para garantir consistência física exata (PC). Em estado normal, o Aurora usa replicação física otimizada em nível de storage de baixa latência mas síncrona/consistente para evitar conflitos de dados históricos (EC).
Questão 13 · AWS Compute Tradeoffs

Para processar arquivos pesados (ex: arquivos gzip de 5GB) vindos de streaming, qual o tradeoff de arquitetura entre usar AWS Lambda acionado por SQS/Kinesis versus ECS Fargate Tasks?

Diferenças Físicas e Concorrência: AWS Lambda possui limites severos: timeout máximo de 15 minutos, limite de armazenamento temporário (/tmp) configurável até 10GB, e concorrência máxima da conta (concurrency limit). O ECS Fargate, por outro lado, pode executar tarefas sem limite de tempo de execução, com discos de armazenamento efêmeros maiores e memória e CPU muito superiores.

Análise de Engenharia:
  • Lambda (Cold Start & Concorrência): O Lambda escala quase instantaneamente, mas se milhares de arquivos pesados entrarem no pipeline de uma vez, a inicialização dos containers temporários (Cold Starts) e o download do arquivo de 5GB estourarão os 15 minutos limite da Lambda, fazendo a execução falhar no meio.
  • ECS Fargate (Resiliência): O Fargate demora cerca de 30-60 segundos para subir (Task provision latency), mas garante processamento contínuo sem limites de timeout ou estouro de disco para descompactar o arquivo.
Questão 14 · Apache Spark Memory

Como identificar se um erro de OutOfMemory (OOM) no Spark foi motivado por excesso de GC (Garbage Collection Overhead) ou por Disk Spill inadequado, e como ajustar os limites de memória Off-Heap?

Estrutura de Gerenciamento da JVM: Quando o Spark executa shuffles ou joins de dados com desbalanceamento (skew), os executores podem falhar por OOM. Se o erro for `GC overhead limit exceeded`, significa que a JVM gastou mais de 98% do tempo executando o Garbage Collector e liberou menos de 2% de memória Heap.

Ação Corretiva em Escala de Produção:
  • Ajuste de GC: Se o GC estiver estourando, use a configuração -XX:+UseG1GC e aumente o tamanho da região do G1GC para evitar fragmentação de objetos gigantes.
  • Habilitando Off-Heap Memory: Configure a alocação de memória direta fora do controle do Garbage Collector para operações do motor Tungsten, reduzindo OOMs drásticamente:
    • spark.memory.offHeap.enabled = true
spark.memory.offHeap.size = 4g
Questão 15 · Database Replication Lag

Como mitigar latência de gravação no banco de destino (Target Database Lag) durante cargas massivas no AWS DMS CDC e como configurar o buffer de transações em memória?

Mecânica Interna do DMS: O DMS lê as alterações do transaction log da origem (ex: WAL do Postgres ou Redo Log do Oracle), envia para o Replication Instance e aplica as mudanças no Target. Se a taxa de escritas na origem for maior que a velocidade com que o DMS consegue abrir conexões e executar sentenças SQL de forma serializada no destino, o CDC lag aumentará indefinidamente.

Configuração para Ingestão Otimizada (Batch Apply Mode):

O DMS, por padrão, executa as modificações linha por linha (Transactional Mode). Para habilitar o agrupamento de logs transacionais em buffer e aplicar em batch nas tabelas do destino, modifique a configuração JSON da Task:

{
  "TargetMetadata": {
    "SupportLobs": true,
    "FullLobMode": false,
    "LobChunkSize": 64,
    "LimitedLobSize": 32
  },
  "TargetLimit": {
    "BatchApplyEnabled": true,
    "BatchApplyTimeoutMin": 1,
    "BatchApplyTimeoutMax": 30
  }
}
Questão 16 · FinOps & Query Economics

Como desenhar o gráfico de custo de consultas e identificar o ponto de cruzamento (crossover point) financeiro entre usar consultas severless no Amazon Athena versus subir um cluster Amazon EMR?

A Economia da Query: O Amazon Athena cobra $5.00 por Terabyte de dados escaneados. Se suas queries de analytics escaneiam dezenas de Terabytes de dados diariamente para relatórios gerenciais, o custo mensal do Athena crescerá de forma linear direta. O Amazon EMR Serverless (ou EC2), no entanto, cobra por segundo de recurso computacional ativo (vCPU e memória), independentemente do volume lido.

Tradeoff e Tomada de Decisão:
  • Volume Baixo/Ad-Hoc: Se os dados analisados totalizam menos que 2 TB por dia, use **Amazon Athena**. Você não paga nada se não rodar queries, economizando custos de setup e idle time.
  • Volume Alto/Pipelines Recorrentes: Acima do ponto de cruzamento de volume (crossover point), compensa financeiramente agendar jobs no **EMR Serverless** com alocação otimizada de recursos. O EMR fará o scan mais rápido sob recursos dedicados sem risco de throttling ou custos lineares gigantes do Athena.
Questão 17 · Contratos de Dados & Governança

Como implementar um contrato de dados (Data Contract) resiliente na AWS para garantir o alinhamento de esquema e evitar que mudanças não retrocompatíveis quebrem os pipelines analíticos downstream?

Conceito de Contrato de Dados: Um contrato de dados é um acordo formal entre os geradores de dados (sistemas produtores/microsserviços) e os consumidores de dados (times analíticos). Ele define a estrutura dos payloads (campos, tipos, formatos), regras semânticas, termos de SLA e propriedade de dados. O objetivo é bloquear alterações silenciosas de esquema (Schema Drift) diretamente na origem.

Arquitetura na AWS: Para viabilizar esta governança de maneira automatizada e assíncrona:

  • Mecanismo de Validação: O microsserviço produtor serializa as mensagens usando formatos binários autopredicativos (como Apache Avro ou Protocol Buffers) ou schemas JSON, registrando-os no **AWS Glue Schema Registry**. O produtor valida cada payload localmente antes do envio. Se a estrutura violar o contrato ativo, a publicação falha imediatamente.
  • GitOps e CI/CD do Contrato: Os esquemas dos contratos são declarados em arquivos JSON Schema no repositório Git. Qualquer modificação no contrato passa por um pipeline de pull-request onde o GitHub Actions faz a validação de compatibilidade retroativa contra o Glue Schema Registry usando a AWS CLI (modo de validação BACKWARD, impedindo remoção de campos requeridos ou mudança de tipos).
  • Circuit Breaker Downstream: Caso um payload fora do formato passe por brechas (como migrações desordenadas), o Spark Streaming ou AWS Lambda de ingestão na camada Bronze utiliza o Schema Registry para decodificar a mensagem. Em caso de erro de deserialização, a mensagem corrompida é desviada para um bucket de quarentena no S3 para análise e alertas são enviados via Amazon SNS para o canal de engenharia.
Questão 18 · Computação & Balanceamento

Como arquitetar uma ingestão serverless de dados em tempo real tolerante a falhas utilizando Amazon ECS (Fargate) e Application Load Balancer (ALB) sob picos de tráfego extremos?

Arquitetura e Desafio Técnico: Quando expomos endpoints de recebimento de webhooks analíticos ou APIs de telemetria externa, precisamos tolerar picos violentos de acesso concorrente sem sobrecarregar ou perder mensagens. O uso de **AWS Lambda** pode esbarrar em custos de computação sob tráfego estável contínuo e em timeouts sob carga. O **Amazon ECS com Fargate** atua como uma camada computacional baseada em contêineres gerenciados e escaláveis, ideal para lidar com conexões persistentes e fluxos de alta vazão.

Configuração de Produção e Boas Práticas:

  • Distribuição do ALB e SSL Termination: O **ALB (Application Load Balancer)** fica exposto publicamente nas sub-redes públicas, executando a terminação SSL/TLS (poupando processamento das tarefas do ECS). Ele executa roteamento de requisições por round-robin ou conexões mínimas para as **ECS Tasks** que rodam em sub-redes privadas seguras.
  • Graceful Shutdown (Desligamento Suave): Containers expostos ao tráfego podem perder requisições em andamento durante atualizações ou autoscaling se forem desligados de forma brusca. No ECS, configure o parâmetro stopTimeout (padrão 30s) e certifique-se de que a aplicação em Python/FastAPI ou Go escuta o sinal SIGTERM enviado pelo ECS, parando de aceitar novas requisições HTTP, efetuando o flush do buffer de dados para o Kinesis e, finalmente, finalizando a tarefa de forma controlada.
  • Estratégia de Auto-scaling Eficaz: Configure uma política de **Target Tracking Scaling** no ECS Service baseada em ALBRequestCountPerTarget em vez de CPU genérica. Isso permite antecipar picos de tráfego escalando contêineres Fargate antes que a CPU atinja 100% de uso, o que causaria timeout nas conexões.
Questão 19 · Observabilidade & Datadog

Como configurar uma observabilidade avançada de pipelines de dados analíticos na AWS usando o Datadog para monitoramento de latência e qualidade?

Monitoramento além do CloudWatch: Embora as métricas padrão da AWS (como uso de CPU no EMR ou contagem de erros de Lambda) ajudem, elas não são suficientes para diagnosticar lentidões complexas em pipelines analíticos de múltiplos estágios (Ex: Spark -> S3 -> Redshift -> Athena). O **Datadog** unifica logs, traces distribuídos e métricas personalizadas em um único plano de visualização.

Padrão de Monitoramento de Engenharia no Datadog:
  • Distributed Tracing (APM) no Spark: Configure o Datadog Agent como um DaemonSet (no EMR em Kubernetes) ou ative a biblioteca Java Datadog APM no Spark Submit (-javaagent:/caminho/dd-java-agent.jar). Isso permite visualizar exatamente quanto tempo cada Task do Spark gasta lendo arquivos Parquet do S3 vs executando processamento em memória, identificando shuffles problemáticos de rede.

  RowCount between 1000 and 2000000,
  Completeness "user_id" = 1.0,
  Completeness "email" > 0.95,
  IsUnique "user_id",
  ColumnDataType "created_at" = "Timestamp",
  ColumnValues "status" in ["ATIVO", "INATIVO", "PENDENTE"]
]

  1. O Job do **AWS Glue** ou **PySpark** lê os dados da camada Bronze e executa a verificação declarada na regra DQDL usando a biblioteca nativa do Glue.
  2. A avaliação retorna um score de sucesso (ex: 85% das regras passaram, mas a unicidade de user_id falhou).
  3. Se o score for menor que o limite aceitável do contrato de qualidade (ex: 100% para chaves primárias e completeness), o pipeline ativa o disjuntor:
    • Grava o lote corrompido em uma pasta isolada no S3 (s3://data-quarantine-bucket/bronze-failures/) para fins de depuração.
    • Gera uma falha explícita no Job do Glue (ou levanta uma exceção no código Python), impedindo que o pipeline envie os dados para a camada Silver.

  • Melhor Prática de Divisão (Split Files): Divida os arquivos de dados na origem no S3 em múltiplos fragmentos comprimidos de tamanhos uniformes e idênticos (ex: 20 arquivos de 5 GB em vez de 1 de 100 GB), com uma quantidade correspondente a um múltiplo do número de compute slices do seu cluster de destino. O comando COPY acionará todos os slices do cluster para carregar cada arquivo em paralelo de forma direta e instantânea.

Sob alta taxa de ingestão de eventos no Amazon MSK, como o Managed Service for Apache Flink gerencia o estado usando o RocksDB StateBackend, quais os impactos arquiteturais do alinhamento de checkpoints sob carga pesada, e como mitigar o backpressure resultante?

Gerenciamento de Estado com RocksDB: No Managed Service for Apache Flink, o estado operacional é armazenado no RocksDBStateBackend. Diferente do backend baseado em memória heap (que pode estourar o Heap OOM da JVM), o RocksDB armazena as chaves e valores em arquivos locais estruturados em árvores LSM (Log-Structured Merge-trees) gravadas no SSD local transiente do nó. O Flink sincroniza esses arquivos assincronamente e incrementalmente com o S3 para persistência permanente.

Impacto de Checkpoint Alignment & Como Mitigar:
  • Checkpoint Alignment (Alinhamento de Checkpoints): Quando um operador Flink consome de múltiplos canais de entrada (ex: join de dois streams Kafka), o operador só inicia o checkpoint quando recebe a barreira de checkpoint (checkpoint barrier) de todos os canais de entrada. Isso gera uma retenção de buffers e propaga o Backpressure upstream para os produtores do MSK.

Desta forma, as barreiras de checkpoint ultrapassam os buffers de dados em trânsito instantaneamente, sem bloqueio de canais. O Flink persiste os dados em voo (in-flight data) que estavam nos buffers diretamente no estado do checkpoint no S3, reduzindo o tempo de alinhamento a zero.
  • Tuning do RocksDB: Evite estouro de memória física alocando buffers off-heap adequados por meio de state.backend.rocksdb.memory.managed: true (gerenciamento automático de memória de bloco do RocksDB pelo Flink) e configure o parâmetro de compactação de banco local para evitar amplificação de escrita (write amplification).

Como o AWS Glue Schema Registry assegura a integridade de esquemas estruturados em tempo real de mensagens consumidas do Amazon MSK, quais são as diferenças práticas entre os modos de evolução de schema, e como tratar registros corrompidos sem derrubar o pipeline?

Quando um produtor escreve dados no Amazon MSK, o serializador do SDK do Schema Registry consulta o registro central. O SDK valida o payload localmente contra a estrutura de versão ativa e insere um **Schema Version ID único de 16 bytes** no início da mensagem binária publicada no Kafka, eliminando a necessidade de trafegar metadados longos em cada registro.

Tradeoffs de Evolução & Tratamento de Erros:
  • Modos de Evolução de Schema:
    • BACKWARD (Padrão): Os consumidores novos podem ler dados antigos. Permite adicionar colunas opcionais ou remover colunas com valores padrão. Garante estabilidade nos leitores analíticos.
    • FORWARD: Os consumidores antigos conseguem ler os dados gerados com os schemas novos. Excelente quando você tem APIs legadas consumindo o stream.
    • FULL: Compatibilidade total de leitura e escrita. Novas versões aceitam leitores antigos e novos, e vice-versa. Regra mais restritiva de evolução.
  • Desvio para Dead Letter Queue (DLQ): Se um produtor desatualizado enviar um payload inválido, o desserializador Java/Scala do Glue Streaming ou Lambda falhará em tempo de execução ao tentar descriptografar o Schema Version ID. Capture essas exceções de decodificação em blocos try/except (como SchemaNotFoundException ou SerializationException), capture o payload binário bruto e direcione-o assincronamente para um bucket S3 de Quarentena (DLQ) ou tópico Kafka secundário de falhas, disparando alertas no EventBridge sem interromper o pipeline principal.
Questão 34 · Amazon Athena Federated Query

Como desenhar e otimizar uma arquitetura de consultas federadas (Federated Query) com Amazon Athena usando conectores Lambda para realizar joins entre o S3 Data Lake e bancos transacionais RDS/DynamoDB sob restrições de tempo de execução (timeouts) e custos?

Mecanismo Athena Federated Query: O Athena utiliza conectores pré-construídos executados no AWS Lambda (comunicação baseada em Apache Arrow) para ler metadados e schemas de sistemas não catalogados diretamente no Glue. O Athena compila a query SQL analítica e converte o acesso ao RDS/DynamoDB em invocações Lambda paralelas. O Lambda busca as linhas correspondentes e devolve batches de dados colunares diretamente ao Athena, que realiza o join final na memória da engine analítica Presto/Trino.

Soluções de Otimização e Segurança:
  • Predicate Pushdown (Pushdown de Predicados): Garanta que o conector do Athena empurre as cláusulas WHERE diretamente para a consulta executada pelo Lambda no banco de dados relacional. Sem pushdown, o Lambda tentaria puxar tabelas inteiras do RDS (ex: 50 GB de dados) sobre a rede para o Athena, gerando custos catastróficos de tráfego NAT, saturação da CPU do RDS e estourando o timeout físico de 15 minutos do Lambda.
  • Limitação e Pruning de Colunas: Evite queries analíticas com SELECT * em consultas federadas. Selecione apenas as colunas necessárias para reduzir a carga de serialização Apache Arrow nos contêineres Lambda do conector.
  • Caching com DynamoDB e Athena: Para buscas federadas frequentes contra dados que mudam pouco (ex: tabelas de CEP ou catálogos de produtos no DynamoDB), ative o cache de resultados analíticos de metadados e registros no conector Lambda (configurando a variável de ambiente metadata_caching_ttl do conector) ou materialize o join no S3 de forma agendada para evitar invocações repetidas de APIs.
Questão 35 · AWS Lake Formation Cell-Level Security

Como o AWS Lake Formation executa a reescrita dinâmica de consultas SQL no Athena sob filtros de segurança de grão fino em nível de coluna e linha (Cell-Level Security), e de que forma essa reescrita impacta a latência de planejamento e como evitar falhas de OOM?

Mecanismo de Reescrita de Consultas: Quando uma query analítica (ex: SELECT * FROM vendas) é submetida ao Athena por um usuário com restrições de segurança do Lake Formation, a engine não lê os arquivos diretamente do S3. O Athena solicita autorização à API GetTemporaryGlueTableCredentials do Lake Formation. O Lake Formation compila e reescreve a query adicionando filtros dinamicamente (ex: substituindo o acesso físico por uma sub-query estruturada com as linhas e colunas permitidas ao usuário: SELECT id, data, valor FROM vendas WHERE pais_origem = 'BR'). O Athena então compila e executa este plano reescrito de forma transparente.

Gargalos e Melhores Práticas de Produção:
  • Latência na Fase de Query Planning: Sob tabelas contendo milhões de registros e centenas de partições ativas no S3, o tempo necessário para o Lake Formation reescrever o plano de consulta analítica e calcular as intersecções de controle de acesso baseado em tags (TBAC) pode demorar vários segundos, adicionando atrasos consideráveis à fase inicial da query (Planning Time) no Athena.
  • Prevenção de Falhas de OOM no Lake Formation Client: Se houver uma quantidade massiva de filtros de linha cruzados aplicados a diferentes grupos do IAM, a engine de compilação do plano de dados analíticos no Athena pode sofrer saturação de memória.
    • Recomendação 1: Evite filtros de linha complexos baseados em lógicas aninhadas como SUBSTRING ou conversões pesadas de tipos de dados. Prefira filtros baseados em chaves de particionamento físico (ex: regiao = 'norte') para que o pruning de arquivos S3 ocorra no nível físico mais rápido possível.
    • Recomendação 2: Divida tabelas muito grandes com requisitos de segurança completamente distintos em tabelas/bancos do Glue separados fisicamente no S3. O desmembramento e o isolamento físico no Data Lake reduzem o overhead do planejamento analítico do Lake Formation.
Questão 36 · AWS IAM Trust Policies & Confused Deputy

Como configurar uma Relação de Confiança (Trust Policy) cross-account para integrar a conta de dados da AWS com plataformas SaaS de terceiros (como Snowflake ou Databricks) mitigando o problema do Deputado Confuso (Confused Deputy) por meio da propriedade sts:ExternalId?

Relação de Confiança Cross-Account: Para integrar o Datalake S3 com ferramentas SaaS de parceiros, a conta de dados do cliente cria uma Role do IAM e anexa uma política de segurança (Trust Policy) que permite à conta da ferramenta SaaS (ex: conta AWS do Snowflake) assumir essa role para ler/escrever arquivos Parquet.

O Gargalo do Confused Deputy & Solução:
  • O Problema do Deputado Confuso: Ocorre se um terceiro SaaS (o "deputado") usa uma role genérica ou dependências de contas mapeadas para múltiplos clientes. Se um Cliente A (malicioso) fornecer ao SaaS o ARN da Role do Cliente B, o SaaS tentará se conectar à conta do Cliente B. Sem validação, a AWS aprovaria o acesso pois o principal de origem (a conta do Snowflake) é legítimo. Isso exporia dados do Cliente B para o Cliente A.
  • Mitigação com sts:ExternalId: A AWS e os provedores SaaS solucionam isso usando um identificador exclusivo (External ID). O Snowflake gera um UUID exclusivo para o cliente. A Trust Policy da Role na conta AWS do Cliente B deve ter uma cláusula Condition específica: 
    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::444455556666:root" -- Conta do SaaS
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "snowflake-cliente-b-uuid-12345"
        }
      }
    }
  ]
}
    Quando o Snowflake tentar acessar o S3 do Cliente B, ele enviará o External ID exclusivo do Cliente B na requisição STS. Se um atacante tentar usar o ARN do Cliente B com as credenciais do Cliente A, o Snowflake enviará o External ID do Cliente A, que não corresponderá à Trust Policy do Cliente B, fazendo com que o STS rejeite a conexão imediatamente.
Questão 37 · AWS IAM Permission Boundaries vs SCPs

Qual a diferença prática de aplicação e avaliação lógica entre Permission Boundaries e Service Control Policies (SCPs) no AWS Organizations, e como essas estruturas impedem escalada de privilégios em times de engenharia?

Service Control Policies (SCPs): São políticas de governança centralizadas aplicadas em nível de conta, OU (Organizational Unit) ou organização no AWS Organizations. Elas definem o limite máximo de permissões para a conta inteira (incluindo o usuário Root). Uma SCP que bloqueia a exclusão do S3 Guard (ex: s3:DeleteBucket) impede qualquer Role da conta de fazê-lo, independente das políticas do IAM local.

Diferença de Escopo e Avaliação Lógica:
  • Permission Boundaries (Fronteiras de Permissão): São aplicadas a usuários ou Roles locais do IAM. Elas definem as permissões máximas efetivas que uma entidade do IAM pode ter. É usada principalmente para delegar a criação de papéis (roles locais de Glue, Lambda, EMR) a Engenheiros de Dados. Isso evita que o engenheiro crie uma Role com AdministratorAccess para uso próprio e escale seus privilégios (Privilege Escalation), já que as ações da nova role estarão sempre limitadas pela Permission Boundary.
  • Mecanismo de Avaliação Lógica (Intersecção de Permissões): Na AWS, as permissões efetivas finais de uma chamada de API são a interseção lógica de:
    Identity-Based Policy (IAM Policy) AND Permission Boundary AND SCP (Organizations) AND Resource-Based Policy (S3 Bucket/KMS Key).
    Se qualquer uma dessas camadas declarar um Deny explícito, a requisição é sumariamente negada.
Questão 38 · IAM Role Chaining & EKS IRSA

Como o EKS IRSA (IAM Roles for Service Accounts) utiliza provedores OIDC para conceder privilégios granulares a pods Spark, e quais os limites e desvantagens de usar o encadeamento de roles (Role Chaining) em pipelines de dados complexos?

Mecanismo IRSA com OIDC: Em vez de dar permissões genéricas para as instâncias EC2 do nó do EKS (EC2 Instance Profile), o IRSA associa roles do IAM diretamente a Service Accounts do Kubernetes. O EKS atua como um provedor OpenID Connect (OIDC). Ao criar o pod, o EKS injeta um token OIDC JWT (JSON Web Token) no pod e configura variáveis de rede. O driver/executor Spark lê o token OIDC e chama a API do STS AssumeRoleWithWebIdentity, recebendo credenciais analíticas temporárias.

Impactos do Encadeamento de Roles (Role Chaining) em Big Data:
  • Role Chaining (Encadeamento de Roles): Ocorre quando um pod ou serviço assume a Role A (local) e, a partir dela, chama a API do STS para assumir a Role B (em outra conta de dados). Isso é muito comum em arquiteturas multicloud ou multi-contas.
  • A Desvantagem de Sessão Limite de 1 Hora: Quando uma role assume outra role em sequência via código (Role Chaining), a validade máxima das credenciais do STS geradas é fixada no limite de 1 hora, mesmo se a role de destino estiver configurada para suportar até 12 horas. Em grandes pipelines Spark analíticos de conciliação que demoram 2 ou mais horas de processamento, as conexões de S3 começarão a falhar por credenciais expiradas no meio do job.
  • Perda de Rastreabilidade (Audit Trail): O encadeamento de roles mascara o ARN do usuário principal no CloudTrail, exibindo apenas o nome da role intermediária, dificultando auditorias de acesso e conformidade.
  • Boas Práticas de Engenharia: Evite o encadeamento manual de roles. Configure o Lake Formation cross-account para realizar o compartilhamento federado de dados, permitindo que a Role A leia as tabelas da outra conta de forma direta via STS temporário gerenciado pelo Lake Formation (que atualiza as chaves transparentemente sem limites de 1 hora).
Questão 39 · Arquitetura EMR

Comparativo Avançado: Quais são os trade-offs arquiteturais entre EMR on EC2, EMR Serverless e EMR on EKS no que tange a FinOps, inicialização de Jobs e isolamento multi-tenant?

Cenário de Entrevista: A empresa planeja consolidar 50 pipelines diários. Cada um utiliza dependências Python conflituosas (Pandas 1.0 vs Pandas 2.0). A prioridade é otimização severa de custos ociosos sem sacrificar estabilidade.

Resposta Técnica:
  • EMR on EC2: Inadequado para o requisito. Obriga a clusterização isolada por pipeline, o que gera alto custo em períodos ociosos. Alternativamente, criar um mega-cluster EC2 compartilhado falharia em lidar com o isolamento de ambientes Python, gerando choques de bibliotecas e dificultando upgrades (Vendor Lock-in no EMR release).
  • EMR on EKS: Excelente para alta densidade. O isolamento é perfeitamente solucionado submetendo jobs com Custom Docker Images via Kubernetes. Se acoplado com o autoscaler Karpenter rodando Instâncias Spot, o cluster escala e contrai em segundos por custo de infraestrutura mínimo. Ideal se o time de plataforma for proficiente no ecossistema de K8s.
  • EMR Serverless: Solução mais fácil (low-ops) com ótimo FinOps. Possui pre-initialized capacity que inicia jobs quase imediatamente. O ambiente de execução para cada Job Run é isolado em micro-VMs próprias, podendo carregar Custom Docker Images ou bibliotecas empacotadas via Virtualenv local do S3. Resolve os problemas sem a complexidade de gerenciar um Control Plane de Kubernetes.
Questão 40 · EMR & Resiliência Spot

Como arquitetar resiliência no EMR on EC2 ou EMR on EKS para mitigar perdas catastróficas de dados via FetchFailedException quando instâncias Spot são desligadas pelo provedor AWS?

Problema Crítico de Shuffle e Instâncias Spot: O Spot AWS pode remover um nó com um aviso prévio curto (2 minutos). Se um Executor Spark operando no nó Spot estava retendo os blocos de dados intermediários de um pesado GROUP BY (dados de shuffle), o desligamento repentino apagará esses dados de disco local. As tarefas downstream (Reduce) falharão por FetchFailedException, forçando a DAG do Spark a retroceder os estágios (stages) e recalcular toda a base, podendo causar atrasos de horas.

Técnicas de Mitigação: Graceful Decommissioning & Shuffle Tracking:
  • No EMR on EC2: Projete o cluster utilizando Spot Instances estritamente para Task Nodes (puramente computacionais sem réplicas HDFS de storage). Ative a flag do YARN de Graceful Node Decommissioning. Quando a AWS envia o sinal de interrupção, o YARN marca o nó como "DECOMMISSIONING" e copia ativamente os dados locais cruciais do NodeManager para as máquinas Core (On-Demand) remanescentes nos 2 minutos disponíveis de tolerância, resguardando o progresso da query.
  • No EMR on EKS (Spark 3.2+): Habilite a propriedade spark.dynamicAllocation.shuffleTracking.enabled=true e ative o Executor Decommissioning nativo do K8s (spark.decommission.enabled=true e spark.storage.decommission.shuffleBlocks.enabled=true). Com isso configurado, ao receber o SIGTERM de finalização, o pod executor inicia uma migração paralela forçada transferindo (push-based) seus dados Shuffle e RDD/Cache via rede P2P para um pod sobrevivente.
Questão 41 · Athena & Lake Formation Performance

O que motiva a lentidão catastrófica no Query Planning Time do Amazon Athena em tabelas do Datalake protegidas com Lake Formation (Cell-Level Security), e como a evolução do stack arquitetural contorna essa debilidade?

Causa Raiz de Lentidão em Segurança Granular: Quando as proteções de linhas e colunas (Cell-Level Security) do Lake Formation estão habilitadas, o Athena não pode mais injetar credenciais e fazer o plano de consulta direto. O Lake Formation assume o fluxo, atuando como um "filtro" avaliador. Para cada query, o LF precisa listar os arquivos de dados brutos e calcular intersecções complexas de ACL na camada de planejamento. Em tabelas particionadas no formato Glue/Hive, onde existem dezenas de milhares de micro-pastas (s3://.../ano=2024/mes=01/), o motor satura a API do Glue e o planejamento (que deveria levar 0,5s) chega a estourar 30s a 120s antes que um único byte seja lido do S3.

Ação Corretiva em Alta Escala:
  • Conversão para Formatos Transacionais Abertos (Apache Iceberg): O Apache Iceberg elimina completamente as lentas varreduras hierárquicas da API do AWS Glue Catalog (que causa o estrangulamento do Lake Formation). O Iceberg concentra os apontamentos físicos das partições ativas dentro do S3 na forma de arquivos de manifestos compactos. Assim que a tabela transiciona para Iceberg, o Lake Formation e o Athena extraem os metadados diretamente do manifesto no S3. Isso resulta em um Query Planning de latência estável quase ignorável, permitindo aplicação massiva de segurança por coluna sem destruir a performance interativa.
Questão 42 · ECS Fargate vs Lambda

Comparativo Avançado: Como o ciclo de vida (Cold Start) impacta a escolha entre AWS Lambda e ECS Fargate na Ingestão de Telemetria IoT e quais estratégias de autoscaling o Fargate exige para não gerar perdas (Dropped Connections)?

Cenário de Entrevista: O cliente precisa ingerir sinais contínuos de sensores de frota 24/7. Ocasionalmente o tráfego dobra instantaneamente. Decida o compute.

Resposta Técnica:
  • O Problema do Cold Start em APIs: AWS Lambda sofre de Cold Starts quando a concorrência explode subitamente, pois a AWS aloca instâncias isoladas (microVMs Firecracker). Se a inicialização do ambiente de execução (especialmente Java/C# ou Python com muitas bibliotecas) demorar 5 segundos, as requisições HTTPS do cliente durante o pico sofrerão latência gigantesca e possíveis Timeouts pelo API Gateway.
  • A Vantagem do ECS Fargate "Always-On": O ECS opera com instâncias containerizadas persistentes. Tarefas já ativas suportam concorrência interna alta assíncrona (ex: um servidor FastAPI no Fargate processando 2000 req/s por contêiner simultaneamente através de async/await e connection pooling), não precisando invocar novas VMs linha a linha.
  • Auto-scaling Tuning no ECS: O ECS demora muito mais para subir uma nova tarefa Fargate (Task Provisioning Latency, ~30 a 60 segundos por pull de imagem Docker pesada) em comparação com milissegundos do Lambda. Portanto, no ECS, devemos escalar antes da crise: usar o Target Tracking Scaling Policy fixado em, digamos, 50% de uso de CPU (e não 90%), ou criar regras proativas preditivas baseadas no horário de pico, de forma que os novos contêineres estejam com status RUNNING antes que os servidores ativos enfileirem e percam as conexões (Dropped Connections).
Questão 43 · Armazenamento ECS Fargate

Como gerenciar gargalos de armazenamento efêmero ao baixar e processar blocos massivos de dados estruturados (>50GB) dentro do ECS Fargate, dada a limitação de disco containerizada?

Desafio Técnico em ETL Serverless: Tarefas tradicionais do Fargate sobem com um disco de armazenamento efêmero restrito (20GB). Tentativas de baixar um dump do Salesforce de 100GB via API dentro da Task irão encher o disco local, derrubando silenciosamente o container via "No Space Left on Device".

Solução Arquitetural de Storage:
  • Expansão de Disco Efêmero (Ephemeral Storage): Ajustar a configuração da Task Definition no parâmetro ephemeralStorage para solicitar um montante até o limite máximo de 200GB (que acarretará em custos proporcionais atrelados ao tempo de vida da task).
  • EFS (Elastic Block Store) Mount Ponto Ouro: Para arquivos gigantescos ou processamentos de caches massivos de ML no modelo de processamento batch via ECS, a Amazon agora suporta acoplar volumes do Amazon EFS (Elastic File System) nas Fargate Tasks. O container monta o EFS via NFS no diretório de extração local, podendo manipular Terabytes de informações elásticas sob demanda persistente com concorrência para múltiplos containers paralelos lerem do mesmo storage se necessário.
Questão 44 · Data Quality & Custos FinOps

Como otimizar os custos computacionais proibitivos de execução de regras de Data Quality (DQDL ou Great Expectations) que analisam a unicidade ou a completude em tabelas gigantescas (Petabytes) do Data Lake?

Cenário de Entrevista: Executar IsUnique "id_cliente" em uma tabela de 5 Petabytes todos os dias leva horas e consome recursos massivos de Spark Shuffle para calcular o agrupamento completo.

Resposta Técnica (Técnicas de Escala):
  • Isolamento Incremental (Push-down): Nunca execute testes de Data Quality na tabela integral a cada execução de batch. Restrinja o DataFrame lido passando predicados de tempo no pushdown, avaliando apenas a partição ingerida no dia (ex: df.filter("data_ingestao = current_date")). Teste a integridade apenas sobre os incrementos da jornada (Delta).
  • Aproximação Probabilística: Se o teste de unicidade (IsUnique) e contagem exata não for estritamente financeiro e sim comportamental, troque contagens exatas onerosas (como COUNT(DISTINCT id)) por algoritmos probabilísticos leves embutidos na engine (como o HyperLogLog no Spark/Presto). O algoritmo fornece ~98% de precisão gastando uma fração minúscula de RAM e processamento.
  • DQ Integrado via Iceberg/Delta: Bancos e formatos modernos (Apache Iceberg) mantêm metadados com contagens de colunas, mínimos, máximos e nulos pré-computados (File-Level Stats) sem a necessidade de varrer os dados fisicamente. Queries otimizadas podem extrair métricas de completude lendo apenas as tabelas de manifesto de forma gratuita e imediata.
Questão 45 · FinOps & Segurança (KMS)

Como as chaves do AWS KMS podem inflar de forma silenciosa e catastrófica o faturamento de consultas no Athena/EMR em tabelas com criptografia SSE-KMS, e qual a estratégia para mitigar custos de chamadas de API KMS?

O Ralo de Dinheiro Oculto: Por padrão, a criptografia SSE-KMS no S3 exige que, para cada bloco ou arquivo lido/escrito no bucket, seja executada uma chamada de API `kms:Decrypt` ou `kms:GenerateDataKey`. Quando consultas analíticas no Athena ou EMR varrem dezenas de milhões de pequenos arquivos em buckets S3 protegidos, a conta AWS é tarifada em centavos por requisição KMS. Esse custo de chamadas de API KMS pode superar com folga o custo de armazenamento e computação combinados.

A Solução Otimizada: S3 Bucket Keys

Habilite a propriedade S3 Bucket Key nas configurações do bucket. Quando ativada, a AWS gera uma chave de bucket de curto prazo no nível do S3 e a utiliza para criptografar/descriptografar dados locais. Isso reduz o volume de chamadas de API do KMS para o S3 em até 99%, derrubando o custo operacional de segurança de forma imediata.

Questão 46 · FinOps & AWS Glue Tuning

Como a escolha errada de tipo de Worker do AWS Glue (Standard vs G.1X vs G.2X) combinada com desbalanceamento de dados (Data Skew) gera desperdício orçamentário drástico e como mitigar isso em produção?

tradeoffs e Custos de DPU: Workers do Glue cobram por DPU-hora ativada.

  • Worker Standard (1 DPU): Possui 16GB de RAM e 4 vCPUs. Executa até 2 tarefas concorrentes. Não recomendado para workloads pesados.
  • Worker G.1X (1 DPU): Possui 16GB de RAM e 4 vCPUs, mas roda apenas uma tarefa concorrente do Spark. Muito mais seguro para evitar OOM.
  • Worker G.2X (2 DPUs): Possui 32GB de RAM e 8 vCPUs. Indicado para transformações pesadas, ML e joins complexos.
Se o dataset possui Data Skew, um único executor do Spark processará 90% da partição de dados pesada enquanto os outros 99 executores (comprados e ativos a 2 DPUs cada) ficam ociosos aguardando o gargalo terminar. O custo continuará cobrando pelas 200 DPUs inteiras.

Ações Corretivas de FinOps:
  • Glue Auto Scaling: Habilite o Auto Scaling nativo do Glue. O gerenciador dinâmico de recursos desliga executores ociosos assim que o gargalo de shuffle ou processamento paralelo inicial é concluído, pagando apenas pelo tempo real de computação ativa.
  • Ajuste de Worker: Utilize G.1X para transformações normais e reserve G.2X apenas para jobs que de fato exigem grande quantidade de memória temporária ou disco local para operações de Sort e Spill.
Questão 47 · FinOps & Networking

Como auditar custos ocultos de Data Transfer e NAT Gateway gerados por tarefas analíticas no EMR/Glue que processam dados do S3 em subredes privadas, e qual a solução arquitetural ideal de custo zero?

A Pegadinha das Redes na AWS: Quando executores do EMR ou Glue rodam em subredes privadas de uma VPC, por padrão, qualquer chamada à internet ou serviços AWS (incluindo o S3) é roteada através do **NAT Gateway** da subrede. A AWS cobra uma tarifa por gigabyte processado (Data Processing charge) no NAT Gateway. Varrer 10 TB de dados no S3 geraria cerca de $450 apenas em tarifas de transferência de rede no NAT Gateway.

A Solução Suprema: Gateway VPC Endpoint para S3

Crie um **VPC Endpoint do tipo Gateway** para o S3 na tabela de roteamento da sua VPC privada. Essa configuração cria uma rota interna privada direta e gratuita entre os recursos da subrede privada e o S3, desviando do NAT Gateway e reduzindo o custo de transferência de dados desse tráfego para **zero**.

Questão 48 · IA Generativa & Caching Semântico

Como projetar um mecanismo de Caching Semântico usando Redis em uma plataforma de dados com LLMs para evitar custos redundantes de tokens de inferência e reduzir a latência de buscas duplicadas?

Cenário de Desperdício: Em aplicações de RAG corporativo ou de buscas internas em linguagem natural, múltiplos usuários realizam perguntas semanticamente muito similares (ex: "Qual é o faturamento de vendas de maio de 2026?" vs "Quanto faturamos nas vendas em maio de 26?"). Processar cada uma enviando-a ao Bedrock Sonnet consome milhares de tokens e eleva a latência.

Impacto no RAG: Se a estratégia de quebra do documento for ruim, informações importantes de um parágrafo serão cortadas pela metade entre dois chunks diferentes. Isso degrada o embedding do vetor (dilui o significado) e impede que o LLM responda com precisão.

Análise de Estratégias:
  • Chunking Estático (Character/Token Limit): Divide o texto em um número fixo de caracteres ou tokens (ex: 512 tokens) com uma zona de overlap (ex: 10%). É rápido e simples de rodar via Glue Spark, mas pode cortar frases no meio, destruindo o contexto.

Garante que uma unidade lógica de conteúdo (ex: um capítulo ou tabela inteira) permaneça íntegra no mesmo chunk, maximizando a relevância semântica recuperada pela query vetorial.

Questão 57 · VPC Endpoints & Custos NAT

Associe um Gateway Endpoint para S3 e DynamoDB diretamente à tabela de rotas das subredes privadas. O Gateway Endpoint roteia o tráfego de dados de forma transparente pela rede privada interna da AWS para os serviços sem sair para a internet pública e sem passar pelo NAT Gateway. O recurso é gratuito e elimina 100% da tarifa por GB do NAT para esses serviços.

Ressalva de Entrevista: Outros serviços (como Kinesis, Secrets Manager ou Glue Schema Registry) requerem Interface Endpoints (PrivateLink), que utilizam Elastic Network Interfaces (ENIs) locais e cobram uma taxa fixa horária mais taxa de dados menor, sendo ainda assim muito mais em conta que o NAT Gateway para grandes volumes.

Questão 60 · DynamoDB Sizing & Particionamento

Dada uma tabela DynamoDB de 35 GB de dados com pico de tráfego de 4.500 WCUs e 8.000 RCUs (leituras fortemente consistentes), calcule o número exato de partições físicas alocadas e o rendimento (throughput) resultante por partição.

Desafio Técnico: A performance do DynamoDB é horizontal e dividida igualmente entre as partições baseando-se em limites físicos. Um dimensionamento incorreto pode induzir a erros de ProvisionedThroughputExceededException.

Resolução Matemática do Especialista:

Para determinar o número de partições, utilizamos as restrições físicas de capacidade (1.000 WCU / 3.000 RCU por partição) e tamanho (10 GB por partição):

  • Fórmula de Capacidade: Partições_Capacidade = (8.000 RCU / 3.000) + (4.500 WCU / 1.000) = 2.67 + 4.5 = 7.17 partições
  • Fórmula de Armazenamento: Partições_Armazenamento = 35 GB / 10 GB = 3.5 partições
  • Total de Partições Físicas: Teto( Max(7.17, 3.5) ) = Teto(7.17) = 8 partições físicas
  • Capacidade Efetiva por Partição:
    • RCU por partição: 8.000 / 8 = 1.000 RCUs
    • WCU por partição: 4.500 / 8 = 562.5 WCUs

Se o tráfego de leitura de um único item/ID (Hot Key) ultrapassar 1.000 RCUs em um segundo, a requisição sofrerá Throttling, mesmo que os outros 7.000 RCUs globais da tabela estejam ociosos.

Questão 67 · Apache Iceberg WAP (Write-Audit-Publish) Pattern

Como funciona o padrão arquitetural WAP (Write-Audit-Publish) no Apache Iceberg e como as branches lógicas da tabela previnem a ingestão de registros órfãos ou inválidos na camada final de Serving?

Gargalo Operacional: Em pipelines analíticos tradicionais (Hive/Parquet puro), se um erro de qualidade de dados ocorrer no final de uma transação batch de 10 milhões de registros, a tabela física já estará modificada, forçando reversões complexas (rollbacks em S3) ou poluindo relatórios ativos de BI.

Arquitetura e Fluxo do WAP:
  • Write (Escrever na Branch): O pipeline PySpark ou dbt grava as alterações apontando para uma branch lógica temporária da tabela Iceberg (ex: df.option("branch", "wap_temp").save(...)). Os dados físicos são salvos no S3, mas o snapshot principal (main branch) da tabela continua inalterado.
  • Audit (Auditar): Ferramentas de validação ativa ou queries SQL rodam contra a branch temporária buscando quebras de contratos de dados (valores negativos, nulos em PKs).
  • Publish (Publicar via Fast-Forward): Se os testes passarem, a engine executa uma chamada de sistema (ex: CALL system.cherry_pick_snapshot()) para avançar a referência da branch main para o snapshot validado. Caso contrário, a branch temporária é descartada, impedindo a exposição dos dados inválidos.
Questão 68 · Spark Catalyst & Whole-Stage CodeGen

Como o Whole-Stage CodeGen do Catalyst Optimizer acelera a execução física de jobs Spark e qual o impacto de UDFs Python tradicionais na quebra deste ciclo de compilação da JVM?

Overhead do Java Clássico: A computação distribuída comum (Iterator-style) avalia registros chamando funções virtuais na pilha JVM para cada registro (ex: Filtro -> Projeção -> Agrupamento), gerando milhões de chamadas e reduzindo o uso dos registradores da CPU física.

Compilação JIT & Quebra de Pipeline:
  • Whole-Stage CodeGen: O Catalyst analisa o plano físico e colapsa múltiplos estágios de transformações em um **único loop em código Java plano**, compilando-o via Janino em tempo de execução. Isso remove todas as chamadas virtuais da JVM e permite que os dados fiquem nos registradores de alta velocidade do processador.
  • Overhead de UDFs Python puras: Uma UDF comum em Python não pode ser compilada pelo Catalyst. Ela força o Spark a extrair os dados da JVM (formato Tungsten), serializar/converter para Python através de sockets (IPC), executar a UDF na CPU do usuário linha a linha, e converter de volta para a JVM. Esse processo desativa o Whole-Stage CodeGen e gera gargalos severos de processamento e latência de rede/memória local.

Questão 65 · Broadcast Join Driver OOM

Por que forçar um Broadcast Join (BHJ) em um DataFrame que excede o limite configurado em autoBroadcastJoinThreshold pode estourar a memória (OOM) do Driver Node antes mesmo dos executores iniciarem o processamento?

Gargalo do Fluxo do Broadcast: Ao executar um Broadcast Join, o Driver Node do Spark precisa realizar um download físico completo (collect) de todos os dados do DataFrame broadcasted a partir dos nós do cluster para sua memória JVM local.
